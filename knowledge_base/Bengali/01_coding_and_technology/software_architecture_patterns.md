# সফটওয়্যার আর্কিটেকচার প্যাটার্নস
স্থাপত্য হল একটি সিস্টেম কীভাবে সংগঠিত হয় সে সম্পর্কে কাঠামোগত সিদ্ধান্তের সেট — এর কী উপাদান রয়েছে, তারা কীভাবে যোগাযোগ করে এবং দায়িত্বগুলি কোথায় থাকে। ভাল আর্কিটেকচার একটি সিস্টেমকে বোঝা, পরিবর্তন করা এবং স্কেল করা সহজ করে তোলে। খারাপ স্থাপত্য প্রতিটি পরিবর্তন একটি সংগ্রাম করে তোলে. এই ফাইলে প্রধান প্যাটার্ন, কখন প্রতিটি ব্যবহার করতে হবে এবং ট্রেড-অফ জড়িত রয়েছে।
---

## মনোলিথ বনাম মাইক্রোসার্ভিস
এটি সবচেয়ে মৌলিক স্থাপত্য সিদ্ধান্ত, এবং এটি সঠিক হওয়ার মূল্য।
| দৃষ্টিভঙ্গি | মনোলিথ | মাইক্রোসার্ভিস |
|---------|----------|---------------|
| **গঠন** | একক স্থাপনযোগ্য ইউনিট | অনেক ছোট, স্বাধীনভাবে স্থাপনযোগ্য পরিষেবা |
| **ডেটা** | ভাগ করা ডাটাবেস | প্রতিটি পরিষেবা তার ডেটার মালিক |
| **যোগাযোগ** | ইন-প্রসেস ফাংশন কল | নেটওয়ার্ক কল (HTTP, gRPC, মেসেজিং) |
| **স্কেলিং** | পুরো অ্যাপ্লিকেশন স্কেল করুন | স্কেল পৃথক পরিষেবা |
| **নিয়োগ** | একক মুক্তি চক্র | স্বাধীন স্থাপনা |
| **জটিলতা** | প্রাথমিকভাবে বিকাশ করা সহজ | অপারেশনাল জটিলতা (নেটওয়ার্কিং, মনিটরিং) |
| **এর জন্য সেরা** | ছোট দল, প্রাথমিক পর্যায়ের পণ্য | বড় দল, জটিল ডোমেইন, উচ্চ স্কেল |
### একটি মনোলিথ দিয়ে কখন শুরু করবেন
অধিকাংশ অ্যাপ্লিকেশন একটি মনোলিথ হিসাবে শুরু করা উচিত. এটি তৈরি করা, পরীক্ষা করা, স্থাপন করা এবং ডিবাগ করা সহজ। আপনার ডোমেনের সীমানাগুলির একটি পরিষ্কার ছবি থাকলে আপনি সর্বদা পরে পরিষেবাগুলি বের করতে পারেন৷ এটিকে কখনও কখনও "মডুলার মনোলিথ" বলা হয় - পরিষ্কার অভ্যন্তরীণ সীমানা সহ একটি মনোলিথ যা পরে নিষ্কাশনকে সহজ করে তোলে।
### কখন মাইক্রোসার্ভিসে যেতে হবে
মাইক্রোসার্ভিস বিবেচনা করুন যখন:
- দলগুলি যথেষ্ট বড় যে সমন্বয় একটি বাধা হয়ে দাঁড়ায়।
- সিস্টেমের বিভিন্ন অংশের খুব আলাদা স্কেলিং প্রয়োজনীয়তা রয়েছে।
- আপনার উপাদানগুলির স্বাধীন স্থাপনার প্রয়োজন।
- আপনার ডোমেনে স্পষ্ট আবদ্ধ প্রসঙ্গ রয়েছে (নীচে DDD দেখুন)।

## স্তরযুক্ত আর্কিটেকচার (N-Tier)
সবচেয়ে সাধারণ আর্কিটেকচার প্যাটার্ন। কোড স্তরগুলিতে সংগঠিত, প্রতিটি একটি নির্দিষ্ট দায়িত্ব সহ।
```
â”Œ─────────────────────────┐
│   Presentation Layer    │  ← UI, controllers, API endpoints
├─────────────────────────┤
│   Application Layer     │  ← Use cases, orchestration
├─────────────────────────┤
│   Domain Layer          │  ← Business logic, entities
├─────────────────────────┤
│   Infrastructure Layer  │  ← Database, external services, file I/O
└─────────────────────────┘
```

| স্তর | দায়িত্ব | নিয়ম |
|-------|---------------|------|
| **উপস্থাপনা** | ব্যবহারকারী/HTTP অনুরোধগুলি পরিচালনা করুন | শুধুমাত্র অ্যাপ্লিকেশন স্তর কল করতে পারেন |
| **আবেদন** | অর্কেস্ট্রেট ব্যবহারের ক্ষেত্রে | ডোমেন লেয়ার কল করতে পারেন |
| **ডোমেন** | মূল ব্যবসা যুক্তি | অন্যান্য স্তরের উপর নির্ভর করা উচিত নয় |
| **অবকাঠামো** | প্রযুক্তিগত উদ্বেগ | ডোমেনে সংজ্ঞায়িত ইন্টারফেস প্রয়োগ করে |
**মূল নিয়ম**: নির্ভরতা অভ্যন্তরের দিকে নির্দেশ করে। ডোমেন স্তর ডাটাবেস বা ওয়েব ফ্রেমওয়ার্ক সম্পর্কে জানে না।

## ইভেন্ট-চালিত আর্কিটেকচার
উপাদানগুলি নির্গত এবং **ঘটনা** - যা ঘটেছে তার প্রতি প্রতিক্রিয়া করে যোগাযোগ করে।
| প্যাটার্ন | বর্ণনা |
|---------|---------------|
| **ইভেন্ট বিজ্ঞপ্তি** | পরিষেবা A "OrderPlaced" নির্গত করে; পরিষেবা বি, সি, ডি প্রতিক্রিয়া |
| **ইভেন্ট সোর্সিং** | সমস্ত রাজ্যের পরিবর্তনগুলিকে ইভেন্টের ক্রম হিসাবে সংরক্ষণ করুন (শুধুমাত্র বর্তমান অবস্থা নয়) |
| **CQRS** | লেখার মডেল (কমান্ড) থেকে পৃথক পঠিত মডেল (কোয়েরি) |
### ইভেন্ট সোর্সিং
একটি ডাটাবেসে "বর্তমান অবস্থা" সংরক্ষণ করার পরিবর্তে, একটি ইভেন্ট হিসাবে প্রতিটি রাজ্যের পরিবর্তন সঞ্চয় করুন:
```
OrderCreated(order_id=123, total=$50)
OrderPaid(order_id=123, payment_id=456)
OrderShipped(order_id=123, tracking=ABC)
```

সুবিধা: সম্পূর্ণ অডিট ট্রেইল, অতীতের যেকোনো অবস্থা পুনর্গঠন করার ক্ষমতা, ভোক্তাদের বিচ্ছিন্ন করা। চ্যালেঞ্জ: ইভেন্ট স্কিমা বিবর্তন, চূড়ান্ত ধারাবাহিকতা, ডিবাগিং জটিলতা।
### CQRS (কমান্ড কোয়েরি রেসপনসিবিলিটি সেগ্রিগেশন)
| পাশ | উদ্দেশ্য | ডাটাবেস |
|------|---------|----------|
| **আদেশ (লিখুন)** | মিউটেশন পরিচালনা করুন; ব্যবসার নিয়ম প্রয়োগ করুন | লেখার জন্য অপ্টিমাইজ করা (সাধারণকৃত) |
| **কোয়েরি (পড়ুন)** | পড়ার অনুরোধ পরিবেশন করুন | পড়ার জন্য অপ্টিমাইজ করা (অসাধারণ) |
ইভেন্ট সোর্সিংয়ের সাথে স্বাভাবিকভাবেই CQRS জোড়া: লেখার দিক থেকে ইভেন্টগুলি পঠন-অনুকূলিত ভিউতে প্রজেক্ট করা হয়।

## বার্তা সারি এবং ইভেন্ট ব্রোকার
যখন পরিষেবাগুলিকে অ্যাসিঙ্ক্রোনাসভাবে যোগাযোগ করার প্রয়োজন হয়, তখন বার্তা সারিগুলি হল মেরুদণ্ড৷
| টুল | প্রকার | জন্য সেরা |
|------|------|----------|
| **অ্যাপাচি কাফকা** | বিতরণ করা ইভেন্ট লগ | উচ্চ-থ্রুপুট ইভেন্ট স্ট্রিমিং, ইভেন্ট সোর্সিং |
| **র্যাবিটএমকিউ** | রাউটিং সহ বার্তা ব্রোকার | টাস্ক সারি, জটিল রাউটিং প্যাটার্ন |
| **AWS SQS** | পরিচালিত সারি | AWS-নেটিভ, সরল সারিবদ্ধ |
| **AWS SNS** | পাব/সাব বিজ্ঞপ্তি | একাধিক গ্রাহকদের ফ্যান-আউট |
| **গুগল পাব/সাব** | পরিচালিত পাব/সাব | GCP-নেটিভ ইভেন্ট স্ট্রিমিং |
| **রেডিস স্ট্রিম** | লাইটওয়েট স্রোত | সহজ ইভেন্ট লগিং, ক্যাশিং ব্যবহারের ক্ষেত্রে |
### মেসেজিং প্যাটার্ন
| প্যাটার্ন | বর্ণনা |
|---------|---------------|
| **পয়েন্ট-টু-পয়েন্ট** | একজন প্রযোজক, প্রতি বার্তায় একজন ভোক্তা |
| **প্রকাশ/সাবস্ক্রাইব** | একজন প্রযোজক, একাধিক গ্রাহক |
| **অনুরোধ/উত্তর** | অ্যাসিঙ্ক ট্রান্সপোর্টের উপর সিঙ্ক্রোনাস-স্টাইল |
| **মৃত চিঠির সারি** | যে বার্তাগুলি প্রক্রিয়াকরণে ব্যর্থ হয় সেগুলি পরিদর্শনের জন্য একটি পৃথক সারিতে যায় |

## ডোমেন-চালিত ডিজাইন (DDD)
ডিডিডি হল সফ্টওয়্যার ডিজাইনের একটি কৌশলগত পদ্ধতি যা প্রযুক্তিগত উদ্বেগের পরিবর্তে ব্যবসায়িক ধারণাগুলির চারপাশে কোডকে কেন্দ্র করে।
### মূল ধারণা
| ধারণা | বর্ণনা |
|---------|---------------|
| **সীমাবদ্ধ প্রসঙ্গ** | একটি সীমানা যার মধ্যে একটি ডোমেন মডেল সামঞ্জস্যপূর্ণ (যেমন, "অর্ডারিং", "শিপিং", "বিলিং") |
| **সর্বব্যাপী ভাষা** | বিকাশকারী এবং ডোমেন বিশেষজ্ঞদের মধ্যে ভাগ করা শব্দভাণ্ডার |
| **সমষ্টি** | সম্পর্কিত সত্তার ক্লাস্টারগুলি ডেটা পরিবর্তনের জন্য একক ইউনিট হিসাবে বিবেচিত হয় |
| **সত্তা** | পরিচয় সহ বস্তু (যেমন, একটি user_id সহ একটি ব্যবহারকারী) |
| **মূল্য বস্তু** | পরিচয় ছাড়া বস্তু; তাদের বৈশিষ্ট্য দ্বারা সংজ্ঞায়িত (যেমন, অর্থ, ঠিকানা) |
| **ডোমেন ইভেন্ট** | ডোমেনে ঘটেছে এমন কিছু (যেমন, OrderPlaced) |
| **দুর্নীতি বিরোধী স্তর** | আপনার ডোমেন এবং বাহ্যিক সিস্টেমের মধ্যে অনুবাদ স্তর |
### যখন DDD সাহায্য করে
ব্যবসার ডোমেন জটিল হলে DDD সবচেয়ে মূল্যবান হয় — ভাবুন ই-কমার্স, লজিস্টিকস, আর্থিক পরিষেবা, স্বাস্থ্যসেবা। যদি আপনার ডোমেন সহজ হয় (একটি ব্লগ, একটি টোডো অ্যাপ), DDD ওভারকিল।

## ক্যাশিং কৌশল
ক্যাশিং কর্মক্ষমতা উন্নত করার সবচেয়ে কার্যকর উপায়গুলির মধ্যে একটি, তবে এটি সামঞ্জস্যের চারপাশে জটিলতার পরিচয় দেয়।
| কৌশল | বর্ণনা | বাণিজ্য বন্ধ |
|------------|-------------|------------|
| **ক্যাশে-সাইড** | অ্যাপ্লিকেশন প্রথমে ক্যাশে চেক করে; মিস উপর DB থেকে লোড | সরল; চূড়ান্ত ধারাবাহিকতা |
| **লিখুন** | ক্যাশে এবং ডিবিতে একই সাথে লিখুন | সামঞ্জস্যপূর্ণ; আস্তে লেখে |
| **লেখা-পিছনে** | ক্যাশে লিখুন; async DB-তে লিখুন | দ্রুত লেখেন; তথ্য হারানোর ঝুঁকি |
| **পড়ুন** | স্বচ্ছভাবে মিস করার সময় ডিবি থেকে ক্যাশে লোড হয় | ক্যাশে-একপাশে থেকে সহজ |
### কি ক্যাশে করবেন
| স্তর | কি | টুলস |
|-------|------|-------|
| **CDN** | স্ট্যাটিক সম্পদ, API প্রতিক্রিয়া | ক্লাউডফ্রন্ট, ক্লাউডফ্লেয়ার |
| **আবেদন** | গণনা করা ফলাফল, সেশন ডেটা | Redis, Memcached |
| **ডাটাবেস** | প্রশ্নের ফলাফল, প্রায়শই অ্যাক্সেস করা সারি | ক্যোয়ারী ক্যাশে, বস্তুগত ভিউ |
**ক্যাশে অবৈধকরণ** কুখ্যাতভাবে কঠিন। সাধারণ কৌশলগুলি: TTL (টাইম-টু-লাইভ), ইভেন্ট-চালিত অবৈধকরণ (ডেটা পরিবর্তনে পরিষ্কার ক্যাশে), এবং LRU (অন্যতম সম্প্রতি ব্যবহৃত) উচ্ছেদ।

## সঠিক আর্কিটেকচার নির্বাচন করা
সর্বজনীনভাবে "সেরা" আর্কিটেকচার নেই। সঠিক পছন্দ নির্ভর করে:
| ফ্যাক্টর | মনোলিথের পক্ষে যখন... | মাইক্রোসার্ভিসের পক্ষে যখন... |
|---------|---------------|--------------------------------------------|
| **দলের আকার** | < 10 developers | >20 ডেভেলপার, একাধিক দল |
| **ডোমেন জটিলতা** | সহজ বা ভালভাবে বোঝা | জটিল, অনেক আবদ্ধ প্রসঙ্গ |
| **স্কেল প্রয়োজনীয়তা** | ইউনিফর্ম স্কেলিং প্রয়োজন | বিভিন্ন উপাদানের জন্য বিভিন্ন স্কেল প্রয়োজন |
| **ডিপ্লয়মেন্ট ক্যাডেন্স** | একক মুক্তি চক্র | স্বাধীন স্থাপনার প্রয়োজন |
| **প্রযুক্তি বৈচিত্র** | এক স্ট্যাক ঠিক আছে | বিভিন্ন পরিষেবার জন্য বিভিন্ন প্রযুক্তির প্রয়োজন |
**ব্যবহারিক পরামর্শ**: একটি মডুলার মনোলিথ দিয়ে শুরু করুন। আপনার একটি স্পষ্ট প্রয়োজন এবং স্পষ্ট ডোমেন সীমানা থাকলেই পরিষেবাগুলি বের করুন৷ সময়ের আগে মাইক্রোসার্ভিসগুলি শিল্পের সবচেয়ে সাধারণ স্থাপত্যগত ভুলগুলির মধ্যে একটি।
