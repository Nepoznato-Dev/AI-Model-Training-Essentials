# পরীক্ষা পদ্ধতি
টেস্টিং হল আপনি কীভাবে আত্মবিশ্বাস অর্জন করেন যে আপনার কোড কাজ করে — এবং আরও গুরুত্বপূর্ণ, এটিতে পরিবর্তনগুলি ইতিমধ্যে যা কাজ করে তা ভেঙে দেয় না। ভাল পরীক্ষা ব্যবহারকারীদের করার আগে বাগ ধরা দেয়, নথি প্রত্যাশিত আচরণ, এবং নির্ভীক রিফ্যাক্টরিং সক্ষম করে। এই ফাইলটি পরীক্ষার কৌশলগুলির সম্পূর্ণ বর্ণালী কভার করে, ইউনিট পরীক্ষা থেকে শুরু করে শেষ থেকে শেষ পর্যন্ত পরীক্ষা, এবং নীতিগুলি যা পরীক্ষাকে কার্যকর করে।

## টেস্টিং পিরামিড
টেস্টিং পিরামিড একটি প্রকল্পে পরীক্ষার আদর্শ বিতরণ বর্ণনা করে।
```
        /  E2E  \          ← Few; slow; expensive; test the whole system
       /─────────\
      / Integration\       ← Some; test how components work together
     /───────────────\
    /   Unit Tests    \    ← Many; fast; cheap; test individual functions
   /─────────────────────\
```

| স্তর | গণনা | গতি | খরচ | এটা কি পরীক্ষা করে |
|-------|---------|------|------|---------------|
| **ইউনিট** | অনেক | দ্রুত (ms) | কম | স্বতন্ত্র ফাংশন, ক্লাস, পদ্ধতি |
| **একীকরণ** | কিছু | মাঝারি (100ms-s) | মাঝারি | কিভাবে উপাদান মিথস্ক্রিয়া; ডাটাবেস প্রশ্ন; API কল |
| **E2E** | অল্প কিছু | ধীর (সেকেন্ড-মিনিট) | উচ্চ | সম্পূর্ণ ব্যবহারকারী বাস্তব সিস্টেমের মাধ্যমে প্রবাহিত |

## ইউনিট পরীক্ষা
বিচ্ছিন্নভাবে কোডের পৃথক ইউনিট পরীক্ষা করা হচ্ছে।
### নীতিমালা
| নীতি | বর্ণনা |
|------------|-------------|
| **দ্রুত** | প্রতিটি পরীক্ষা মিলিসেকেন্ডে চালানো উচিত |
| **বিচ্ছিন্ন** | পরীক্ষা একে অপরের উপর নির্ভর করে না; কোন ভাগ করা রাষ্ট্র |
| **নিশ্চয়তাবাদী** | প্রতিবার একই ইনপুট → একই আউটপুট (কোন এলোমেলোতা নেই, সময় নির্ভরতা নেই) |
| **স্ব-পরীক্ষা** | পরীক্ষা স্বয়ংক্রিয়ভাবে পাস বা ব্যর্থ হয়; কোন ম্যানুয়াল পরিদর্শন |
| **সময়োপযোগী** | কোডের পাশে বা আগে লেখা (TDD) |
### একটি পরীক্ষার অ্যানাটমি
| পর্যায় | বর্ণনা |
|-------|---------------|
| **ব্যবস্থা করুন** | পরীক্ষার ডেটা এবং নির্ভরতা সেট আপ করুন |
| **আইন** | ফাংশন বা পদ্ধতি পরীক্ষা করা হচ্ছে কল করুন |
| **দাবি** | ফলাফল প্রত্যাশা মেলে যাচাই করুন |
### কি পরীক্ষা করবেন
| বিভাগ | উদাহরণ |
|----------|---------|
| **সুখের পথ** | সাধারণ ইনপুট প্রত্যাশিত আউটপুট তৈরি করে |
| **এজ কেস** | খালি ইনপুট, শূন্য, শূন্য, সর্বোচ্চ মান, একক উপাদান |
| **ত্রুটির ক্ষেত্রে** | অবৈধ ইনপুট, অনুপস্থিত ডেটা, অনুমতি অস্বীকৃত |
| **সীমানা শর্ত** | অফ-বাই-এক; ঠিক সীমাতে |
### উপহাস এবং স্টাবিং
| মেয়াদ | বর্ণনা | কখন ব্যবহার করবেন |
|------|---------------|---------------|
| **মক** | একটি জাল বস্তু যা রেকর্ড করে যে এটিকে কীভাবে বলা হয়েছিল | মিথস্ক্রিয়া যাচাই করা (এই পদ্ধতিটি বলা হত?) |
| **অসম্পূর্ণ** | একটি জাল বস্তু যা পূর্বনির্ধারিত মান প্রদান করে | পরীক্ষার তথ্য প্রদান করা হচ্ছে (ডাটাবেস থেকে এই ব্যবহারকারীকে ফিরিয়ে দিন) |
| **গুপ্তচর** | একটি মোড়ক যা একটি বাস্তব বস্তুর কল রেকর্ড করে | আংশিক যাচাইকরণ |
| **জাল** | একটি সরলীকৃত কিন্তু কার্যকরী বাস্তবায়ন | পরীক্ষার জন্য ইন-মেমরি ডাটাবেস |
| মকিং লাইব্রেরি | ভাষা |

| **মকিটো** | জাভা |
| **Moq** | C# |

## ইন্টিগ্রেশন টেস্টিং
পরীক্ষা করা হচ্ছে কিভাবে একাধিক উপাদান একসাথে কাজ করে।
| কি পরীক্ষা করতে হবে | উদাহরণ |
|---------------|---------|
| **ডাটাবেস প্রশ্ন** | ওআরএম কি সঠিক এসকিউএল তৈরি করে? সূচক ব্যবহার করা হয়? |
| **API শেষ পয়েন্ট** | সম্পূর্ণ অনুরোধ-প্রতিক্রিয়া চক্র কাজ করে? |
| **পরিষেবা মিথস্ক্রিয়া** | পরিষেবা A কি সঠিকভাবে B পরিষেবাকে কল করে? |
| **বাহ্যিক নির্ভরতা** | পেমেন্ট গেটওয়ে ইন্টিগ্রেশন কাজ করে? |
### কৌশল
| কৌশল | বর্ণনা | বাণিজ্য বন্ধ |
|------------|-------------|------------|
| **প্রকৃত নির্ভরতা** | একটি বাস্তব ডাটাবেস ব্যবহার করুন, বাস্তব বার্তা সারি | সবচেয়ে বাস্তবসম্মত; ধীর সেট আপ করা কঠিন |
| **পরীক্ষা পাত্র** | প্রতিটি পরীক্ষা চালানোর জন্য ডকার পাত্রে স্পিন আপ করুন | ভাল ভারসাম্য; প্রজননযোগ্য |
| **ইন-মেমরি বিকল্প** | PostgreSQL এর পরিবর্তে H2; ইন-মেমরি বার্তা বাস | দ্রুত; বাস্তব বিশ্বের সমস্যা মিস করতে পারে |
| **চুক্তি পরীক্ষা** | যাচাই করুন যে পরিষেবাগুলি তাদের API চুক্তিকে সম্মান করে | ইন্টারফেস পরিবর্তন ধরা |

## এন্ড-টু-এন্ড (E2E) পরীক্ষা
ব্যবহারকারীর দৃষ্টিকোণ থেকে সম্পূর্ণ সিস্টেম পরীক্ষা করা হচ্ছে।
| টুল | প্রকার | জন্য সেরা |
|------|------|----------|
| **নাট্যকার** | ব্রাউজার অটোমেশন | ওয়েব অ্যাপ্লিকেশন; ক্রস ব্রাউজার |
| **সাইপ্রেস** | ব্রাউজার অটোমেশন | ওয়েব অ্যাপ্লিকেশন; বিকাশকারী অভিজ্ঞতা |
| **সেলেনিয়াম** | ব্রাউজার অটোমেশন | উত্তরাধিকার; ব্যাপক ভাষা সমর্থন |
| **ডিটক্স** | মোবাইল E2E | নেটিভ অ্যাপস প্রতিক্রিয়া |
| **অ্যাপিয়াম** | মোবাইল E2E | নেটিভ এবং হাইব্রিড মোবাইল অ্যাপস |
| **মায়েস্ট্রো** | মোবাইল E2E | মোবাইল অ্যাপস; সহজ YAML সিনট্যাক্স |
| **k6 / পঙ্গপাল** | লোড টেস্টিং | লোড অধীনে কর্মক্ষমতা |
### E2E সেরা অভ্যাস
| অনুশীলন | কেন |
|------------|------|
| **শুধুমাত্র জটিল পথ পরীক্ষা করুন** | E2E পরীক্ষা ধীর হয়; সবচেয়ে গুরুত্বপূর্ণ কি ফোকাস |
| **পরীক্ষা ডেটা কারখানা ব্যবহার করুন** | প্রোগ্রামগতভাবে পরীক্ষার ডেটা তৈরি করুন; বীজ তথ্যের উপর নির্ভর করবেন না |
| **পরীক্ষার পর পরিষ্কার করুন** | প্রতিটি পরীক্ষা একটি পরিচিত অবস্থায় সিস্টেম ছেড়ে দেওয়া উচিত |
| **ইউআই বিশদ পরীক্ষা করা এড়িয়ে চলুন** | পরীক্ষা আচরণ, CSS ক্লাস বা উপাদান অবস্থান নয় |
| **সিআইতে চালান** | E2E পরীক্ষা অবশ্যই প্রতিটি পরিবর্তনে স্বয়ংক্রিয়ভাবে চলতে হবে |

## টেস্ট-চালিত উন্নয়ন (TDD)
প্রথমে পরীক্ষাটি লিখুন, তারপর পাস করার জন্য কোডটি লিখুন।
| ধাপ | বর্ণনা |
|------|---------------|
| **1। লাল** | একটি ব্যর্থ পরীক্ষা লিখুন যা পছন্দসই আচরণ বর্ণনা করে |
| **2। সবুজ** | পরীক্ষা পাস করার জন্য সর্বনিম্ন কোড লিখুন |
| **3. রিফ্যাক্টর** | পরীক্ষা সবুজ রাখার সময় কোড পরিষ্কার করুন |
| সুবিধা | বর্ণনা |
|---------|---------------|
| **ডিজাইন ফিডব্যাক** | পরীক্ষাগুলি আপনাকে বাস্তবায়নের আগে ইন্টারফেস সম্পর্কে চিন্তা করতে বাধ্য করে |
| **রিগ্রেশন নিরাপত্তা** | প্রতিটি বাগ একটি পরীক্ষা পায়; বাগ কখনই ফিরে আসতে পারে না |
| **ডকুমেন্টেশন** | পরীক্ষাগুলি প্রত্যাশিত আচরণের জীবন্ত ডকুমেন্টেশন হিসাবে কাজ করে |
| **আত্মবিশ্বাস** | উচ্চ পরীক্ষার কভারেজ নির্ভীক রিফ্যাক্টরিং সক্ষম করে |

## আচরণ-চালিত উন্নয়ন (BDD)
BDD TDD প্রসারিত করে প্রাকৃতিক ভাষায় পরীক্ষা লিখে যা ব্যবহারকারীর দৃষ্টিকোণ থেকে আচরণ বর্ণনা করে।
### দেওয়া-যখন-তারপর বিন্যাস
```
Given a user with an empty shopping cart
When they add a "Python Book" priced at $29.99
Then the cart total should be $29.99
And the cart should contain 1 item
```

| টুল | ভাষা |
|------|------------|
| **শসা** | জাভা, জাভাস্ক্রিপ্ট, রুবি, এবং অন্যান্য |
| **আচরণ** | পাইথন |
| **স্পেকফ্লো** | C# |
| **বিদ্রূপ** (বর্ণনা/এটি সহ) | জাভাস্ক্রিপ্ট |

## ব্যবহারিক টিপস
- **নাম পরিষ্কারভাবে পরীক্ষা করে।**`test_calculates_tax_for_high_earner`আপনাকে বলে কী ভেঙেছে। `test_1`আপনাকে কিছুই বলে না।
- **প্রতি পরীক্ষায় একটি দাবি (যখন ব্যবহারিক হয়)।** ব্যর্থতা নির্ণয় করা সহজ করে তোলে।
- **ইমপ্লিমেন্টেশন বিশদ পরীক্ষা করবেন না।** টেস্ট আচরণ। যদি আপনি অভ্যন্তরীণ রিফ্যাক্টর করেন, তাহলে পরীক্ষাগুলি ভাঙা উচিত নয়।
- **তৃতীয়-পক্ষের কোড পরীক্ষা করা এড়িয়ে চলুন।** বহিরাগত লাইব্রেরি উপহাস করুন; তাদের সাথে আপনার কোডের মিথস্ক্রিয়া পরীক্ষা করুন।
- **পরীক্ষা দ্রুত করুন।** যদি আপনার টেস্ট স্যুট 10 মিনিট সময় নেয়, তাহলে বিকাশকারীরা এটি চালানো বন্ধ করে দেবে। নিরলসভাবে অপ্টিমাইজ করুন।
- **মৃত পরীক্ষাগুলি মুছুন।** পরীক্ষাগুলি যেগুলি সর্বদা পাস করে বা অপসারিত কোড পরীক্ষা করে তা হল গোলমাল।
- **পরীক্ষার কোডকে প্রোডাকশন কোডের মতো ব্যবহার করুন।** এটি পঠনযোগ্য, রক্ষণাবেক্ষণযোগ্য এবং সুগঠিত হওয়া উচিত।

## সারাংশ
পরীক্ষা করা ঐচ্ছিক নয় - আপনি কীভাবে সফ্টওয়্যার তৈরি করেন যা ভাঙে না। টেস্টিং পিরামিড আপনাকে অনেক দ্রুত ইউনিট পরীক্ষা, কিছু ইন্টিগ্রেশন পরীক্ষা এবং কয়েকটি E2E পরীক্ষার দিকে পরিচালিত করে। TDD এবং BDD কাঠামোগত পদ্ধতি প্রদান করে। মকিং পরীক্ষার জন্য ইউনিটকে বিচ্ছিন্ন করে। কোড কভারেজ প্রস্থ পরিমাপ করে কিন্তু গভীরতা নয়। সবচেয়ে গুরুত্বপূর্ণ নীতিটি হল: যদি এটি পরীক্ষা না করা হয় তবে এটি ভেঙে গেছে - আপনি এখনও এটি জানেন না।
