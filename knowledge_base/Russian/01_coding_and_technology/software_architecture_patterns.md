# Шаблоны архитектуры программного обеспечения
Архитектура — это набор структурных решений о том, как организована система: какие компоненты она имеет, как они взаимодействуют и где лежат обязанности. Хорошая архитектура упрощает понимание, модификацию и масштабирование системы. Плохая архитектура делает каждое изменение трудным. В этом файле описаны основные шаблоны, случаи использования каждого из них и возможные компромиссы.
---

## Монолит против микросервисов
Это самое фундаментальное архитектурное решение, и его стоит принять правильно.
| Аспект | Монолит | Микросервисы |
|--------|----------|---------------|
| **Структура** | Одиночный развертываемый блок | Множество небольших, независимо развертываемых сервисов |
| **Данные** | Общая база данных | Каждый сервис владеет своими данными |
| **Общение** | Внутрипроцессные вызовы функций | Сетевые вызовы (HTTP, gRPC, обмен сообщениями) |
| **Масштабирование** | Масштабируйте все приложение | Масштаб индивидуальных услуг |
| **Развертывание** | Единый цикл выпуска | Независимые развертывания |
| **Сложность** | Проще разработать на начальном этапе | Сложность эксплуатации (сеть, мониторинг) |
| **Лучше всего** | Небольшие команды, продукты на ранней стадии | Большие команды, сложные области, масштаб |
### Когда начинать с монолита
Большинство приложений должны запускаться как монолит. Его проще создавать, тестировать, развертывать и отлаживать. Вы всегда сможете извлечь сервисы позже, когда у вас будет более четкое представление о границах вашего домена. Иногда его называют «модульным монолитом» — монолитом с четкими внутренними границами, которые облегчают извлечение в дальнейшем.
### Когда использовать микросервисы
Рассмотрите микросервисы, когда:
- Команды настолько велики, что координация становится узким местом.
— Разные части системы имеют очень разные требования к масштабированию.
- Вам необходимо самостоятельное развертывание компонентов.
– Ваш домен имеет четко ограниченный контекст (см. DDD ниже).

## Многоуровневая архитектура (N-уровень)
Самый распространенный архитектурный образец. Код организован по слоям, каждый из которых несет определенную ответственность.
```
â”Œ─────────────────────────┐
│   Presentation Layer    │  ← UI, controllers, API endpoints
├─────────────────────────┤
│   Application Layer     │  ← Use cases, orchestration
├─────────────────────────┤
│   Domain Layer          │  ← Business logic, entities
├─────────────────────────┤
│   Infrastructure Layer  │  ← Database, external services, file I/O
└─────────────────────────┘
```

| Слой | Ответственность | Правило |
|-------|---------------|------|
| **Презентация** | Обработка пользовательских/HTTP-запросов | Можно вызвать только прикладной уровень |
| **Приложение** | Оркестрация вариантов использования | Можно вызвать слой домена |
| **Домен** | Основная бизнес-логика | Не должно зависеть от других слоев |
| **Инфраструктура** | Технические концерны | Реализует интерфейсы, определенные в Domain |
**Основное правило**: зависимости направлены внутрь. Уровень домена не знает ни базы данных, ни веб-фреймворка.

## Архитектура, управляемая событиями
Компоненты взаимодействуют, излучая и реагируя на **события** — то, что произошло.
| Узор | Описание |
|---------|-------------|
| **Уведомление о событии** | Служба A выдает «OrderPlaced»; услуги B, C, D реагируют |
| **Поиск мероприятий** | Сохраняйте все изменения состояния как последовательность событий (а не только текущее состояние) |
| **CQRS** | Отделить модель чтения (запросы) от модели записи (команды) |
### Источник событий
Вместо хранения «текущего состояния» в базе данных сохраняйте каждое изменение состояния как событие:
```
OrderCreated(order_id=123, total=$50)
OrderPaid(order_id=123, payment_id=456)
OrderShipped(order_id=123, tracking=ABC)
```

Преимущества: полный контрольный журнал, возможность восстановить любое прошлое состояние, разделение потребителей. Проблемы: эволюция схемы событий, конечная согласованность, сложность отладки.
### CQRS (разделение ответственности за командный запрос)
| Сиде | Цель | База данных |
|------|---------|----------|
| **Команда (запись)** | Обрабатывать мутации; обеспечивать соблюдение бизнес-правил | Оптимизировано для записи (нормализовано) |
| **Запрос (Чтение)** | Обслуживать запросы на чтение | Оптимизировано для чтения (денормализовано) |
CQRS естественным образом сочетается с источником событий: события со стороны записи проецируются в представления, оптимизированные для чтения.

## Очереди сообщений и брокеры событий
Когда службам необходимо взаимодействовать асинхронно, очереди сообщений являются основой.
| Инструмент | Тип | Лучшее для |
|------|------|----------|
| **Апач Кафка** | Распределенный журнал событий | Высокопроизводительная потоковая передача событий, источник событий |
| **RabbitMQ** | Брокер сообщений с маршрутизацией | Очереди задач, сложные шаблоны маршрутизации |
| **AWS SQS** | Управляемая очередь | AWS-родная, простая организация очередей |
| **AWS SNS** | Уведомление о публикации/подписке | Рассылка нескольким подписчикам |
| **Google Pub/Sub** | Управляемый паб/суб | Потоковая передача событий в GCP |
| **Потоки Redis** | Легкий поток | Простая регистрация событий и варианты использования кэширования |
### Шаблоны обмена сообщениями
| Узор | Описание |
|---------|-------------|
| **Точка-точка** | Один производитель, один потребитель на сообщение |
| **Опубликовать/подписаться** | Один продюсер, несколько подписчиков |
| **Запрос/Ответ** | Синхронный стиль вместо асинхронного транспорта |
| **Очередь недоставленных писем** | Сообщения, не прошедшие обработку, помещаются в отдельную очередь для проверки |

## Доменно-ориентированное проектирование (DDD)
DDD — это стратегический подход к проектированию программного обеспечения, который сосредотачивает код вокруг бизнес-концепций, а не технических проблем.
### Ключевые понятия
| Концепция | Описание |
|---------|-------------|
| **Ограниченный контекст** | Граница, в пределах которой является согласованной модель предметной области (например, «Заказ», «Доставка», «Выставление счетов») |
| **Вездесущий язык** | Общий словарный запас разработчиков и экспертов в предметной области |
| **Агрегаты** | Кластеры связанных объектов рассматриваются как единое целое при изменении данных |
| **Объекты** | Объекты с идентификатором (например, Пользователь с user_id) |
| **Объекты значений** | Объекты без идентичности; определяются их атрибутами (например, Деньги, Адрес) |
| **События домена** | Что-то, что произошло в домене (например, OrderPlaced) |
| **Антикоррупционный уровень** | Уровень перевода между вашим доменом и внешними системами |
### Когда помогает DDD
DDD наиболее ценен, когда сфера бизнеса сложна — например, электронная коммерция, логистика, финансовые услуги, здравоохранение. Если ваш домен простой (блог, приложение todo), DDD будет излишним.

## Стратегии кэширования
Кэширование — один из наиболее эффективных способов повышения производительности, но он усложняет обеспечение согласованности.
| Стратегия | Описание | Компромисс |
|----------|-------------|-----------|
| **Кэш** | Приложение сначала проверяет кэш; загружает из БД при промахе | Простой; конечная согласованность |
| **Сквозная запись** | Запись в кэш и БД одновременно | Последовательный; медленнее пишет |
| **Запись** | Запись в кэш; асинхронная запись в БД | Быстро пишет; риск потери данных |
| **Чтение** | Кэш загружается из БД при промахе прозрачно | Проще, чем кэшировать |
### Что кэшировать
| Слой | Что | Инструменты |
|-------|------|-------|
| **CDN** | Статические ресурсы, ответы API | CloudFront, Cloudflare |
| **Приложение** | Вычисленные результаты, данные сеанса | Redis, Memcached |
| **База данных** | Результаты запроса, часто используемые строки | Кэш запросов, материализованные представления |
**Аннулирование кэша** является чрезвычайно сложной задачей. Общие стратегии: TTL (время жизни), аннулирование на основе событий (очистка кэша при изменении данных) и вытеснение LRU (наименее недавно использовавшийся).

## Шаблоны проектирования
### НАДЕЖНЫЕ Принципы
| Принцип | Что это значит |
|-----------|--------------|
| **S** — Единая ответственность | У класса должна быть одна причина для изменения |
| **O** — Открыто/Закрыто | Открыто для расширения, закрыто для модификации |
| **L** — Лисков Замена | Подтипы должны заменять свои базовые типы |
| **I** — Разделение интерфейса | Множество специфических интерфейсов > один интерфейс общего назначения |
| **D** — Инверсия зависимостей | Зависите от абстракций, а не от конкретики |
### Общие шаблоны
| Узор | Намерение | Пример |
|---------|--------|---------|
| **Синглтон** | Убедитесь, что класс имеет только один экземпляр | Пул соединений с базой данных |
| **Фабрика** | Создавать объекты без указания точного класса | `UserFactory.create(type="admin")`|
| **Наблюдатель** | Уведомлять иждивенцев при изменении состояния | Слушатели событий, pub/sub |
| **Стратегия** | Алгоритмы замены во время выполнения | Стратегия оплаты: кредитная карта, PayPal, криптовалюта |
| **Репозиторий** | Абстрактный доступ к данным за чистым интерфейсом | `UserRepository.find_by_id(123)`|
| **Декоратор** | Динамическое добавление поведения | Журналирование декоратора вокруг сервиса |
| **Адаптер** | Обеспечьте совместную работу несовместимых интерфейсов | Устаревший адаптер API |

## Выбор правильной архитектуры
Не существует универсально «лучшей» архитектуры. Правильный выбор зависит от:
| Фактор | Отдавайте предпочтение Монолиту, когда... | Отдавайте предпочтение микросервисам, когда... |
|--------|------------------------|------------------------------|
| **Размер команды** | < 10 developers | >20 разработчиков, несколько команд |
| **Сложность домена** | Просто или понятно | Сложные, многие ограниченные контексты |
| **Требования к масштабу** | Равномерное масштабирование потребностей | Разным компонентам нужен разный масштаб |
| **Периодичность развертывания** | Единый цикл выпуска | Требуются независимые развертывания |
| **Разнообразие технологий** | Один стек — это нормально | Разным службам нужны разные технологии |
**Практический совет**: начните с модульного монолита. Извлекайте услуги только тогда, когда у вас есть явная потребность и четкие границы домена. Преждевременные микросервисы — одна из самых распространенных архитектурных ошибок в отрасли.
