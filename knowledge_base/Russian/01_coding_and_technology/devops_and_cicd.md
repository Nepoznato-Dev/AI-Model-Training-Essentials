# DevOps и CI/CD
DevOps — это сочетание культурной философии, практик и инструментов, которое позволяет командам быстрее и надежнее доставлять программное обеспечение. Он разрушает стену между разработчиками (которые хотят вносить изменения) и операторами (которые хотят стабильности). CI/CD — непрерывная интеграция и непрерывная доставка — это основа автоматизации, которая делает это возможным.
---

## Конвейеры CI/CD
### Что на самом деле означает CI/CD
| Срок | Что он делает |
|------|-------------|
| **Непрерывная интеграция (CI)** | Разработчики часто объединяют код; каждое слияние запускает автоматические сборки и тесты |
| **Непрерывная доставка (CD)** | Код всегда находится в состоянии развертывания; выпуск в производство — это решение вручную |
| **Непрерывное развертывание** | Каждое изменение, прошедшее тестирование, автоматически поступает в производство — никаких ручных ворот |
### Типичные этапы конвейера
| Этап | Что происходит | Инструменты |
|-------|-------------|-------|
| **Источник** | Разработчик отправляет код в Git | GitHub, GitLab, Bitbucket |
| **Строить** | Скомпилировать код, установить зависимости | Maven, Gradle, npm, pip |
| **Тест** | Модуль запуска, интеграция, проверка на наличие ворсинок | Jest, pytest, JUnit |
| **Пакет** | Создайте образ или артефакт Docker | Докер, Сборочные пакеты |
| **Развертывание (промежуточный вариант)** | Развертывание в промежуточной среде | Кубернетес, ECS, ВМ |
| **Тестирование (постановочное)** | Интеграционные тесты, дымовые тесты | Селен, Почтальон |
| **Развертывание (производство)** | Запустить в производство | Сине-зеленый, канареечный, перекатной |
| **Монитор** | Наблюдайте за работоспособностью, ошибками, производительностью | Прометей, Графана, Датадог |
### Сравнение инструментов CI/CD
| Инструмент | Тип | Сила |
|------|------|----------|
| **Действия GitHub** | Облачный CI/CD | Глубоко интегрирован с GitHub; Рабочие процессы YAML |
| **GitLab CI** | Встроенный CI/CD | Единая платформа для репо + конвейер |
| **Дженкинс** | Самостоятельный CI/CD | Широкие возможности настройки; массивная экосистема плагинов |
| **КругCI** | Облачный CI/CD | Быстрый; хорошо подходит для контейнерных рабочих процессов |
| **АргоКД** | GitOps для Kubernetes | Декларативное развертывание на основе Git |

## Докер и контейнеры
### Почему контейнеры?
До появления контейнеров классической проблемой было «на моей машине это работает». Контейнеры решают эту проблему, упаковывая приложение со всеми его зависимостями — библиотеками, средой выполнения, конфигурацией — в единый портативный модуль, который одинаково работает где угодно.
### Основы Docker
| Концепция | Описание |
|---------|-------------|
| **Изображение** | Шаблон только для чтения с приложением и зависимостями |
| **Контейнер** | Запуск экземпляра изображения |
| **Докерфайл** | Рецепт создания имиджа |
| **Реестр** | Хранилище для образов (Docker Hub, ECR, GCR) |
| **Объем** | Постоянное хранилище, выдерживающее перезапуск контейнера |
| **Сеть** | Изолированный сетевой уровень для контейнеров |
### Лучшие практики Dockerfile
```dockerfile
# Use specific base image tags, not 'latest'
FROM python:3.12-slim

# Set working directory
WORKDIR /app

# Copy dependency file first (leverage Docker layer caching)
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# Copy application code
COPY . .

# Run as non-root user
USER appuser

# Expose port and define entrypoint
EXPOSE 8000
CMD ["python", "main.py"]
```

Ключевые методы: используйте базовые образы slim/alpine, запускайте их без полномочий root, используйте кэширование слоев, используйте `.dockerignore`, сканируйте образы на наличие уязвимостей (`trivy`, `docker scan`) и устанавливайте ограничения на ресурсы.
### Создание Docker
Для совместного запуска нескольких контейнеров (приложение + база данных + кеш):
```yaml
services:
  app:
    build: .
    ports: ["8000:8000"]
    depends_on: [db, redis]
    environment:
      DATABASE_URL: postgresql://user:pass@db:5432/mydb
  db:
    image: postgres:16
    volumes: [pgdata:/var/lib/postgresql/data]
  redis:
    image: redis:7-alpine
volumes:
  pgdata:
```

## Кубернетес (K8s)
Kubernetes — это оркестратор контейнеров отраслевого стандарта. Он управляет развертыванием, масштабированием и работой контейнерных приложений.
### Основная архитектура
| Компонент | Роль |
|-----------|------|
| **Плоскость управления** | Управляет кластером (API-сервер, планировщик и т. д., диспетчер контроллеров) |
| **Узел** | Рабочая машина (виртуальная или физическая), на которой работают контейнеры |
| **Капсула** | Наименьшая развертываемая единица; один или несколько контейнеров, которые используют общую сеть |
| **Сервис** | Стабильная конечная точка сети, которая направляет трафик на модули |
| **Развертывание** | Декларативное определение желаемого состояния модуля (реплики, изображения и т. д.) |
| **Вход** | Правила HTTP-маршрутизации для внешнего трафика |
| **ConfigMap/Секрет** | Конфигурация и конфиденциальные данные, внедренные в модули |
### Основные команды kubectl
```bash
kubectl get pods                    # List pods
kubectl get services                # List services
kubectl describe pod <name>         # Detailed pod info
kubectl logs <pod-name>             # View pod logs
kubectl exec -it <pod> -- /bin/sh   # Shell into a pod
kubectl apply -f deployment.yaml    # Apply a manifest
kubectl rollout status deploy/myapp # Check rollout progress
kubectl scale deploy/myapp --replicas=5  # Scale to 5 replicas
```

### Шлем
Helm — менеджер пакетов Kubernetes. **Диаграмма** – это набор предварительно настроенных ресурсов Kubernetes. Думайте об этом как`apt`или`brew`для K8s.
```bash
helm install my-release bitnami/postgresql   # Install a chart
helm upgrade my-release bitnami/postgresql   # Upgrade
helm rollback my-release 1                   # Rollback to revision 1
helm list                                    # List releases
```

## Инфраструктура как код (IaC)
IaC относится к конфигурации инфраструктуры так же, как вы относитесь к коду приложения: управление версиями, тестирование и развертывание через конвейеры.
### Терраформ против Ансибла
| Инструмент | Тип | Подход | Лучшее для |
|------|------|----------|----------|
| **Терраформировать** | Обеспечение | Декларативный (HCL); государственный | Создание облачных ресурсов (VPC, ВМ, базы данных) |
| **Ансибл** | Конфигурация | Декларативный (YAML); без агента | Настройка серверов, установка программного обеспечения |
| **Пулуми** | Обеспечение | Императив (Python, Go, TS) | Команды, предпочитающие настоящие языки программирования |
| **Облачное формирование** | Обеспечение | Декларативный (YAML/JSON); AWS-родной | Инфраструктура только для AWS |
### Пример терраформирования
```hcl
provider "aws" {
  region = "us-east-1"
}

resource "aws_instance" "web" {
  ami           = "ami-0c55b159cbfafe1f0"
  instance_type = "t3.micro"

  tags = {
    Name = "web-server"
  }
}
```

Лучшие практики: используйте модули для повторного использования, храните состояние удаленно (S3 + DynamoDB для блокировки), никогда не жёстко кодируйте секреты и контролируйте все версии.

## Мониторинг и наблюдаемость
### Три столпа
| Столб | Что это вам говорит | Инструменты |
|--------|------------------|-------|
| **Показатели** | Численные измерения с течением времени (ЦП, частота запросов, частота ошибок) | Прометей, CloudWatch, Datadog |
| **Журналы** | Дискретные события с контекстом (ошибки, запросы, изменения состояния) | ELK Stack, Loki, журналы CloudWatch |
| **Следы** | Сквозной путь запроса между службами | Егерь, Рентген, Зипкин |
### Прометей + стек Grafana
Стандартный стек мониторинга с открытым исходным кодом:
| Компонент | Роль |
|-----------|------|
| **Прометей** | База данных временных рядов; извлекает метрики из сервисов |
| **Графана** | Визуализация и информационные панели |
| **Менеджер оповещений** | Направляет оповещения в Slack, PagerDuty, по электронной почте |
| **Экспортёр узлов** | Предоставляет показатели системного уровня (ЦП, ОЗУ, диск) |
| **Экспортер Blackbox** | Опрашивает конечные точки (HTTP, TCP, ICMP) |
### Ключевые показатели для отслеживания
| Категория | Метрики |
|----------|---------|
| **Инфраструктура** | ЦП, ОЗУ, использование диска, сетевой ввод-вывод |
| **Приложение** | Частота запросов, задержка (p50, p95, p99), частота ошибок |
| **База данных** | Количество запросов, медленные запросы, использование пула соединений |
| **Бизнес** | Регистрации, конверсии, доход |

## Стратегии развертывания
| Стратегия | Как это работает | Риск | Откат |
|----------|-------------|------|----------|
| **Постоянное обновление** | Постепенно заменяйте старые экземпляры новыми | Некоторые пользователи используют старую версию, некоторые — новую | Вернуться к предыдущему изображению |
| **Сине-зеленый** | Запустите две идентичные среды; переключить трафик | Двойные затраты на инфраструктуру во время перехода | Мгновенное переключение назад |
| **Канарейка** | Направьте небольшой % трафика на новую версию; постепенно увеличиваться | Комплексное управление дорожным движением | Вернуть трафик в стабильное состояние |
| **Флаги функций** | Разверните код, но спрячьте функции за переключателями | Сложность кода из условной логики | Выключить |

## ГитОпс
GitOps доводит IaC до логического завершения: репозиторий Git является единственным источником достоверной информации о желаемом состоянии вашей инфраструктуры и приложений.
| Принцип | Описание |
|-----------|-------------|
| **Декларативный** | Все, что описано в виде кода (YAML, HCL) |
| **Версия** | Git — источник истины |
| **Автоматизировано** | Инструменты постоянно согласовывают желаемое состояние с фактическим |
| **Поддается проверке** | Каждое изменение — это коммит Git |
**ArgoCD** и **Flux** — ведущие инструменты GitOps для Kubernetes. Вы вносите изменение в свой репозиторий Git, и инструмент автоматически развертывает его в кластере.

## Реагирование на инцидент
Когда что-то сломалось в 3 часа ночи:
1. **Подтвердите** предупреждение.
2. **Оцените масштаб**: какие службы, пользователи и данные затронуты?
3. **Определите** основную причину — проверьте журналы, метрики, последние развертывания.
4. **Содержите**, если это возможно: автоматические выключатели, флажки функций, переключение трафика.
5. **Исправить** — откат или исправление вперед.
6. **Общайтесь** — обновляйте информацию о заинтересованных сторонах и пользователях (страница состояния).
7. **Посмертное** — в течение 24–48 часов задокументируйте основную причину и меры по устранению.
Цель состоит не только в том, чтобы устранить инцидент, но и в том, чтобы тот же инцидент не повторился.
