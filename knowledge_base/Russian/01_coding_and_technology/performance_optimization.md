# Оптимизация производительности
Оптимизация производительности — это практика ускорения работы программного обеспечения: сокращение времени отклика, увеличение пропускной способности, снижение использования памяти и устранение узких мест. Это один из самых важных навыков, которыми может обладать разработчик, потому что медленное программное обеспечение теряет пользователей, тратит ресурсы и всех расстраивает. Но это также одна из самых распространенных ошибок: разработчики оптимизируют неправильные вещи, основываясь на интуиции, а не на фактах.
---

## Золотое правило
> **Сначала измерьте, а потом оптимизируйте.** Никогда не оптимизируйте, основываясь на предположениях. Профилируйте код, найдите фактическое узкое место и устраните его.
| Анти-шаблон | Почему это плохо |
|-------------|-------------|
| **Преждевременная оптимизация** | Тратить время на ускорение кода, который не медленный |
| **Оптимизация без измерения** | Исправление неправильного узкого места; нет возможности проверить улучшение |
| **Жертвуя читабельностью ради скорости** | Нечитаемый код обходится дороже, чем выигрыш в производительности |
| **Кеширование всего** | Устаревшие данные, раздувание памяти, сложность |
---

## Профилирование
Прежде чем вы сможете сделать что-то быстрее, вам нужно знать, *куда* тратится время.
| Тип инструмента | Что он измеряет | Примеры |
|-----------|-----------------|----------|
| **Профилировщик ЦП** | Какие функции потребляют больше всего процессорного времени | cProfile (Python), perf (Linux), Chrome DevTools (JS) |
| **Профилировщик памяти** | Распределение памяти и утечки | трассировкаmalloc (Python), Valgrind, heaptrack |
| **Профилировщик ввода-вывода** | Узкие места дискового и сетевого ввода-вывода | iotop, strace, Wireshark |
| **APM (мониторинг производительности приложений)** | Сроки сквозного запроса | Новая Реликвия, Datadog, Jaeger |
| **Инструменты разработчика браузера** | Фронтенд-рендеринг, выполнение JavaScript, сеть | Инструменты разработчика Chrome, Профилировщик Firefox |
### Рабочий процесс профилирования
| Шаг | Описание |
|------|-------------|
| 1. Выявление медленной работы | Пользователи сообщают о медленной загрузке страниц; мониторинг показывает высокую задержку |
| 2. Профилируйте полный путь | Найдите, какой компонент занимает больше всего времени |
| 3. Детализация | Профилируйте этот конкретный компонент, чтобы найти «горячую» функцию |
| 4. Устраните узкие места | Примените соответствующую оптимизацию |
| 5. Измерьте еще раз | Проверьте улучшение; проверить наличие регрессий |

## Алгоритмическая оптимизация
Самый большой прирост производительности достигается за счет выбора лучших алгоритмов, а не за счет микрооптимизации.
| Изменить | Улучшение |
|--------|------------|
| Линейный поиск O(n) → Поиск по хэш-таблице O(1) | 100x+ для больших наборов данных |
| Вложенный цикл O(n²) → Сортировка + двоичный поиск O(n log n) | Порядки для больших n |
| Повторные вычисления → Мемоизация/кэширование | Устраняет избыточную работу |
| Конкатенация строк в цикле → Построитель/объединение | Избегает копирования квадратичных строк |
| Несортированные данные → Отсортированные данные с бинарным поиском | O(log n) вместо O(n) на каждый поиск |

## Стратегии кэширования
Кэширование сохраняет вычисленные результаты, поэтому их не нужно пересчитывать.
| Тип кэша | Местоположение | Скорость | Пожизненная |
|-----------|----------|-------|----------|
| **Кэш процессора** | Л1/Л2/Л3 | ~1 нс | Автоматический |
| **В памяти** | Оперативная память приложений (dict, HashMap) | ~100 нс | Пока не будет очищен или выселен |
| **Распределенный кэш** | Redis, Memcached | ~1 мс | Настраиваемый срок жизни |
| **CDN** | Граничные серверы по всему миру | ~10-50 мс | Настраиваемый срок жизни |
| **Кэш браузера** | Браузер пользователя | ~1 мс | Заголовки HTTP-кэша |
| **Кэш запросов к базе данных** | Уровень базы данных или ORM | ~1–10 мс | До изменения данных |
### Шаблоны кэширования
| Узор | Описание | Когда использовать |
|---------|-------------|-------------|
| **Кэш** | Приложение проверяет кэш; загрузки из БД при промахе; хранит в кэше | Самый распространенный; простой |
| **Сквозная запись** | Запись в кэш и БД одновременно | Когда читает >> пишет; последовательность важна |
| **Отложенная запись** | Запись в кэш; асинхронно писать в БД | Высокая пропускная способность записи; некоторый риск потери данных |
| **TTL (Время жить)** | Записи кэша истекают через заданное время | Когда данные периодически меняются |
| **Аннулирование** | Явное удаление устаревших записей кэша | Когда вы точно знаете, когда изменяются данные |
### Инвалидация кэша
Две самые сложные проблемы в информатике: аннулирование кэша, присвоение имен вещам и ошибки отклонения на единицу.
| Стратегия | Описание |
|----------|-------------|
| **На основе TTL** | Срок действия записей истекает через N секунд; просто, но может содержать устаревшие данные |
| **Управляемый событиями** | Недействителен при изменении данных; более сложный, но точный |
| **В зависимости от версии** | Укажите номер версии; приращение изменений |
| **На основе тегов** | Теги, связанные с записями кэша; сделать недействительными все записи с тегом |

## Оптимизация базы данных
Базы данных часто являются самым узким местом в веб-приложениях.
| Техника | Описание | Воздействие |
|-----------|-------------|--------|
| **Индексирование** | Добавьте индексы к столбцам, используемым в WHERE, JOIN, ORDER BY | Запросы в 10-1000 раз быстрее |
| **Оптимизация запросов** | Избегайте SELECT *; используйте EXPLAIN для анализа запросов | Уменьшить ввод-вывод |
| **Пул соединений** | Повторное использование подключений к базе данных вместо создания новых | Устранить накладные расходы на соединение |
| **Читать реплики** | Направление запросов на чтение к базам данных-репликам | Распределить нагрузку чтения |
| **Разделение** | Разделение больших таблиц на более мелкие разделы | Более быстрые запросы к большим наборам данных |
| **Денормализация** | Добавьте избыточные данные, чтобы избежать объединений | Более быстрое чтение; медленнее пишет |
| **Материализованные представления** | Предварительно рассчитанные результаты запроса | Мгновенные сложные запросы |
| **Профилактика N+1** | Используйте JOIN, быструю загрузку или пакетные запросы | Устраните тысячи запросов |

## Параллелизм и параллелизм
| Концепция | Описание | Когда использовать |
|---------|-------------|-------------|
| **Многопоточность** | Несколько потоков в одном процессе | Задачи, связанные с вводом-выводом (сеть, диск) |
| **Многопроцессорная обработка** | Несколько процессов (в обход GIL в Python) | Задачи, связанные с процессором |
| **Асинхронный/ожидание** | Кооперативная многозадачность; одна нить | Высокопараллельный ввод-вывод (веб-серверы) |
| **Вычисления на графическом процессоре** | Тысячи параллельных ядер | Матричные операции; обработка изображений; МЛ |
### Асинхронность и многопоточность
| Аспект | Асинхронный/Ожидание | Резьба |
|--------|------------|-----------|
| **Модель** | Кооператив (контроль выхода заданий) | Вытесняющее (ОС переключает потоки) |
| **Накладные расходы** | Очень низкий (без переключения контекста) | Высшее (создание потоков, переключение контекста) |
| **Сложность** | Более простые рассуждения (один поток) | Условия гонки, взаимоблокировки, блокировки |
| **Лучший вариант** | Множество одновременных операций ввода-вывода | Блокировка операций, которые нельзя сделать асинхронными |
| **Ограничение** | Невозможно использовать код, привязанный к процессору, без блокировки | GIL в Python ограничивает настоящий параллелизм |

## Производительность внешнего интерфейса
| Техника | Описание | Воздействие |
|-----------|-------------|--------|
| **Минификация** | Удалите пробелы и сократите имена переменных | Файлы на 20–40 % меньше |
| **Объединение** | Объединение нескольких файлов в меньшее количество запросов | Меньше HTTP-запросов |
| **Разделение кода** | Загружайте только тот код, который необходим для текущей страницы | Более быстрая начальная загрузка |
| **Отложенная загрузка** | Загружайте изображения и компоненты, когда они необходимы | Ускоренный первоначальный рендер |
| **Дерево трясётся** | Удалить неиспользуемый код из пакетов | Меньшие пакеты |
| **Оптимизация изображения** | Используйте WebP/AVIF; отзывчивые изображения; ленивая загрузка | Изображения на 50–80% меньше |
| **CDN** | Обслуживание статических ресурсов с пограничных серверов | Снижение задержки во всем мире |
| **HTTP/2 и HTTP/3** | Мультиплексирование; сжатие заголовка; 0-РТТ | Более быстрые издержки протокола |
| **Работники сферы обслуживания** | Кэшировать ресурсы для автономного использования; push-уведомления | Более быстрые повторные посещения |

## Оптимизация памяти
| Техника | Описание |
|-----------|-------------|
| **Объединение объектов** | Повторное использование объектов вместо создания новых |
| **Потоковая передача** | Обрабатывать данные порциями вместо загрузки всего в память |
| **Генераторы/итераторы** | Выдавайте значения доходности по одному вместо построения списков |
| **Файлы, отображаемые в памяти** | Доступ к большим файлам без их полной загрузки |
| **Настройка сборки мусора** | Настройте параметры GC в соответствии с вашей рабочей нагрузкой |
| **Выбор структуры данных** | Используйте массивы вместо связанных списков для локальности кэша; использовать наборы для тестирования членства |

## Краткое содержание
Оптимизация производительности — это систематический процесс: измерьте, определите узкое место, устраните его, снова измерьте. Самый большой выигрыш достигается за счет улучшения алгоритмов и устранения ненужной работы, а не за счет микрооптимизации. Кэширование, индексирование базы данных и параллелизм — самые мощные инструменты. Производительность внешнего интерфейса зависит от минимизации размера полезной нагрузки и количества циклов передачи данных. И самое главное правило всегда одно: не угадывай — профиль.
