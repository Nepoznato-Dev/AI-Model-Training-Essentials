# Лучшие практики безопасности
Практическое руководство по защите приложений, инфраструктуры и данных — от разработки до производства.
---

## Топ-10 OWASP (2021 г.) — Обзор
1. **Нарушение контроля доступа**: пользователи могут получить доступ к ресурсам, к которым им не следует обращаться.
2. **Ошибки шифрования**: слабое или отсутствующее шифрование.
3. **Внедрение**: внедрение SQL, NoSQL, команды ОС или LDAP.
4. **Небезопасный дизайн**: архитектурные недостатки.
5. **Неправильная конфигурация безопасности**: пароли по умолчанию, открытые порты, подробные ошибки.
6. **Уязвимые и устаревшие компоненты**: известные CVE в зависимостях.
7. **Ошибки идентификации и аутентификации**: ненадежные пароли, неправильное управление сеансом.
8. **Нарушения целостности программного обеспечения и данных**: атаки на цепочку поставок, неподписанные обновления.
9. **Ошибки регистрации и мониторинга безопасности**: нарушений не обнаружено.
10. **Подделка запросов на стороне сервера (SSRF)**: злоупотребление сервером для отправки запросов во внутренние системы.

## Проверка ввода и кодирование вывода
### Правила проверки
– **Белый список > Черный список**: определите разрешенные шаблоны (например, регулярное выражение для электронной почты), а не блокируйте известные плохие шаблоны.
- **Ограничения длины**: установите максимальную длину, чтобы предотвратить переполнение буфера и DoS.
- **Проверка типов**: убедитесь, что целые числа являются целыми числами, а логические значения являются логическими значениями.
– **Используйте проверенные библиотеки**. Для проверки электронной почты, URL-адреса и даты используйте стандартные библиотеки (например,`email-validator`в Python,`validator.js`в Node).
### Кодировка вывода
- **Кодировка HTML**: закодируйте `<`, `>`, `&`, `"`, `'`, чтобы предотвратить XSS.
- **Параметризация SQL**: никогда не объединяйте вводимые пользователем данные в запросы SQL. Используйте параметризованные запросы (подготовленные операторы) или ORM.
- **Эскейпирование оболочки**: избегайте создания команд оболочки на основе пользовательского ввода; если это неизбежно, используйте`shlex.quote()`или аналогичный.

## Аутентификация и авторизация
### Управление паролями
- **Хеширование**: храните пароли с помощью надежного и медленного алгоритма хеширования: **Argon2id** (предпочтительно), **bcrypt**, **scrypt** или **PBKDF2**.
- **Соль**: добавьте уникальную соль для каждого пользователя.
- **Минимальная длина**: обязательно используйте не менее 12–16 символов.
- **MFA (Многофакторная аутентификация)**: для конфиденциальных операций требуется второй фактор (TOTP, SMS, аппаратный ключ).
- **Ограничение скорости**: предотвращение попыток перебора на конечных точках входа в систему (например, 5 попыток в течение 5 минут для каждого IP-адреса/пользователя).
### Управление сеансами
- Используйте безопасные файлы cookie SameSite только для HTTP для токенов сеанса.
- Установите соответствующие сроки истечения срока действия.
- Недействительные сеансы при выходе из системы и смене пароля.
– Избегайте раскрытия идентификаторов сеансов в URL-адресах.
### OAuth2/OIDC
- Используйте хорошо зарекомендовавшие себя библиотеки (например, Authlib, PyJWT, Passport.js, Spring Security).
- Тщательно проверьте идентификационные токены (подпись, эмитент, аудитория, срок действия).
- Используйте параметры состояния для предотвращения CSRF.
- Сохраняйте секреты клиентов в тайне.
### JWT (веб-токены JSON)
- **Знак**: используйте RS256 или ES256 (асимметричный) для большей безопасности; HS256 (симметричный) приемлем, если общие секреты управляются хорошо.
- **Проверка**: всегда проверяйте подпись, эмитента (`iss`), аудиторию (`aud`) и срок действия (`exp`).
- **Сохраняйте короткий срок действия**: 15–60 минут для токенов доступа; используйте токены обновления для более длительных сеансов.
- **Безопасное хранение**: никогда не храните JWT в localStorage (уязвимо для XSS); вместо этого используйте файлы cookie только для HTTP.

## Безопасность API
### Аутентификация
- Всегда аутентифицируйте вызовы API (кроме общедоступных конечных точек).
– Предпочитайте ключи API или токены OAuth2 базовой аутентификации (которая отправляет учетные данные при каждом запросе).
### Ограничение и регулирование скорости
- Применяйте ограничения скорости для каждого пользователя и для каждого IP-адреса, чтобы предотвратить злоупотребления и DoS.
– Верните`429 Too Many Requests`с заголовком `Retry-After`.
### CORS (совместное использование ресурсов между источниками)
– Разрешать только определенные источники происхождения (никогда`*`в рабочей версии).
- Проверьте заголовок`Origin`на стороне сервера.
### Проверка ввода
- Проверьте все параметры запроса, включая заголовки и тело.
– Отклонять непредвиденные поля (`"strict": true` или`additionalProperties: false`в схеме JSON).
### HTTPS/TLS
- Обеспечить использование HTTPS в производстве.
- Используйте HSTS (HTTP Strict Transport Security), чтобы заставить браузеры использовать HTTPS.
- Используйте TLS 1.2 или 1.3 (отключите TLS 1.0/1.1).

## Управление секретами
### Никогда не жёстко кодируйте секреты
- Не передавайте секреты (ключи API, пароли, URL-адреса баз данных) в систему контроля версий.
- Используйте переменные среды или инструменты управления секретами.
### Инструменты
| Инструмент | Описание |
|------|-------------|
| **Хранилище ХашиКорп** | Динамические секреты корпоративного уровня |
| **Менеджер секретов AWS / Azure Key Vault / Диспетчер секретов GCP** | Облачный |
| **СОПС** | Зашифровать секреты в файлах и зафиксировать их (с помощью KMS или GPG) |
| **Секреты Docker** | Для режима Swarm; Секреты Kubernetes (рассмотрим внешний CSI-драйвер Secrets Store) |
### Вращение
- Регулярно меняйте секреты и сервисные аккаунты.
- Автоматизируйте вращение, где это возможно.

## Управление зависимостями
### Сканирование уязвимостей
| Язык/Платформа | Инструменты |
|-------------------|-------|
| **Питон** | `safety`,`pip-audit`,`bandit`|
| **Узел** | `npm audit`,`yarn audit`,`snyk`|
| **Ржавчина** | `cargo audit`|
| **Вперёд** | `govulncheck`|
| **Общие** | `Dependabot`(GitHub), `Renovate`,`Trivy`|
### Исправления
- Обновляйте зависимости до исправленных версий.
- Настройте автоматические запросы на получение второстепенных обновлений или обновлений исправлений.
- Просмотрите журналы изменений на предмет критических изменений.
### Целостность цепочки поставок
- Используйте файлы блокировки пакета (`package-lock.json`,`Cargo.lock`,`go.sum`), чтобы обеспечить воспроизводимость сборок.
- Проверьте контрольные суммы загруженных зависимостей.
- Отдавайте предпочтение официальным реестрам и доверяйте только проверенным издателям.

## Безопасность инфраструктуры
### Брандмауэры
- Заблокируйте все входящие порты, кроме явно необходимых (например, 80, 443).
- Ограничьте доступ SSH к определенным диапазонам IP-адресов (или используйте хост VPN/бастион).
- Используйте группы безопасности (AWS) или NSG (Azure) для детального контроля.
### Усиление защиты ОС
- Регулярно применяйте обновления безопасности (`sudo apt upgrade`,`yum update`).
- Отключите ненужные службы и учетные записи по умолчанию.
- Используйте Fail2ban для блокировки попыток перебора по SSH.
- Усиление SSH: отключите вход с правами root, используйте аутентификацию на основе ключей, измените порт по умолчанию (необязательно).
### Сегментация сети
- Размещайте базы данных и кэши в частных подсетях без доступа к Интернету.
– Используйте DMZ для общедоступных сервисов.
- Применяйте принцип наименьших привилегий к доступу к сети.
### Секреты инфраструктуры
- Никогда не храните секреты в переменных среды CI/CD, если они не зашифрованы.
— Используйте роли IAM облачного провайдера для экземпляров EC2/VM вместо долгосрочных ключей.

## Ведение журнала и мониторинг
### Что регистрировать
- События аутентификации (успех/неуспех).
- Решения по контролю доступа (сбои авторизации).
- Действия администратора (создание пользователя, удаление, изменение разрешений).
- Изменения схемы базы данных.
- Системные ошибки и исключения.
- Запросы и ответы API (редактирование конфиденциальных данных).
### Что не регистрировать
- Пароли, секреты, токены, PII (персональная информация), если она не хеширована/отредактирована.
- Полные номера кредитных карт.
### Оповещение
- Настройте оповещения для:
  - Несколько неудачных входов в систему (потенциальный перебор).
  - Необычные схемы доступа (например, из новых мест, в неурочное время).
  - Созданы новые учетные записи администратора.
  - Высокая частота ошибок или скачки задержек.
- Используйте SIEM (информация о безопасности и управление событиями) для расширенной корреляции.
### Хранение журнала
- Храните журналы не менее 30–90 дней в зависимости от нормативных требований.
- Храните журналы в централизованной системе с защитой от несанкционированного доступа (например, ELK Stack, Splunk, Datadog).

## Безопасный жизненный цикл разработки (SDL)
1. **Обучение**. Убедитесь, что разработчики понимают распространенные уязвимости.
2. **Моделирование угроз**. Выявляйте потенциальные угрозы на ранних стадиях проектирования.
3. **Стандарты безопасного кодирования**. Обеспечивайте их соблюдение с помощью линтеров и контрольных списков проверки кода.
4. **SAST** (статическое тестирование безопасности приложений): сканирование исходного кода на наличие уязвимостей (SonarQube, CodeQL).
5. **DAST** (динамическое тестирование безопасности приложений): сканирование запущенных приложений (OWASP ZAP, Burp Suite).
6. **SCA** (Анализ состава программного обеспечения): сканирование зависимостей.
7. **Тестирование на проникновение**: регулярные упражнения по этическому взлому.
8. **Награда за обнаружение ошибок**. Поощряйте внешних исследователей ответственно подходить к поиску уязвимостей.
9. **План реагирования на инциденты**. Составьте четкий план на случай обнаружения нарушения.
---

## Контрольный список действий на случай чрезвычайной ситуации (при подозрении на взлом)
1. **Не паникуйте** — действуйте быстро.
2. **Изолируйте** затронутые системы (при необходимости отключите их от сети).
3. **Сохраняйте доказательства**: записывайте журналы, дампы памяти и образы дисков.
4. **Определите** масштаб: какие системы, какие данные.
5. **Ротируйте** все скомпрометированные учетные данные и секреты.
6. **Исправьте** уязвимость.
7. **Уведомить** затронутых пользователей и регулирующие органы, если необходимо (в установленные законом сроки).
8. **Проведите вскрытие**, чтобы понять основную причину и улучшить процессы.
