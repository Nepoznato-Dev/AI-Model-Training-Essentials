# Дизайн и архитектура API
API (интерфейс прикладного программирования) — это то, как компоненты программного обеспечения взаимодействуют друг с другом. Хорошо спроектированный API интуитивно понятен, последователен, и с ним приятно работать. Плохо спроектированный вариант вызывает путаницу, ошибки и разочарование. В этом файле описаны принципы, шаблоны и методы создания API, которые разработчики действительно хотят использовать.
---

## Принципы REST API
REST (передача репрезентативного состояния) — доминирующий архитектурный стиль веб-API. Он рассматривает данные как **ресурсы**, идентифицируемые URL-адресами, и использует методы HTTP для работы с ними.
### Основные принципы
| Принцип | Описание |
|-----------|-------------|
| **Ресурсы** | Все является ресурсом с URI (`/users/123`,`/orders/456`) |
| **Методы HTTP** | GET (чтение), POST (создание), PUT (замена), PATCH (частичное обновление), DELETE (удаление) |
| **Безгражданство** | Каждый запрос содержит всю необходимую информацию; нет состояния сеанса на стороне сервера |
| **Единый интерфейс** | Согласованные имена ресурсов, стандартные методы, стандартные коды состояния |
| **Представительство** | Ресурсы могут быть представлены в нескольких форматах (JSON, XML) |
### Соглашения об именах ресурсов
| Делать | Не |
|----|-------|
| `/users`(существительное во множественном числе) | `/user`(единственное число) |
| `/users/123/orders`(вложенный) |  __ЗАЩИЩЕНО_3__ |
| `/products?category=electronics`(параметры запроса для фильтрации) | `/productsByCategory/electronics`|
| Используйте дефисы:`/user-profiles`| Используйте подчеркивание:`/user_profiles`|
### HTTP-методы и идемпотентность
| Метод | Цель | Идемпотент? | Безопасный? |
|--------|---------|-------------|-------|
| **ПОЛУЧИТЬ** | Прочитать ресурс | ✅ Да | ✅ Да |
| **ПОСТ** | Создать ресурс | ❌ Нет | ❌ Нет |
| **ВСТАВИТЬ** | Заменить ресурс полностью | ✅ Да | ❌ Нет |
| **ИСПРАВЛЕНИЕ** | Частично обновить ресурс | ❌ Нет* | ❌ Нет |
| **УДАЛИТЬ** | Удалить ресурс | ✅ Да | ❌ Нет |
*PATCH можно сделать идемпотентным при тщательном проектировании.
### Коды состояния HTTP
| Код | Значение | Когда использовать |
|------|---------|-------------|
| **200** | ОК | Успешное ПОЛУЧЕНИЕ, ПОЛОЖЕНИЕ, ИСПРАВЛЕНИЕ, УДАЛЕНИЕ |
| **201** | Создано | Успешный POST (ресурс создан) |
| **204** | Нет содержания | Успешное УДАЛЕНИЕ (нечего возвращать) |
| **400** | Неверный запрос | Неверный ввод или неверный запрос |
| **401** | Несанкционированный | Отсутствует или недействительна аутентификация |
| **403** | Запрещено | Аутентифицирован, но не авторизован |
| **404** | Не найдено | Ресурс не существует |
| **409** | Конфликт | Дублирующийся ресурс или конфликт состояний |
| **422** | Необрабатываемый объект | Валидный JSON, но есть семантические ошибки |
| **429** | Слишком много запросов | Превышен лимит скорости |
| **500** | Внутренняя ошибка сервера | Неожиданная ошибка сервера |
| **502** | Плохой шлюз | Сбой восходящего сервиса |
| **503** | Услуга недоступна | Временная перегрузка или техническое обслуживание |

## Управление версиями API
API развиваются. Когда вам нужно внести критические изменения, управление версиями позволяет существующим клиентам продолжать работу.
| Стратегия | Пример | Плюсы | Минусы |
|----------|---------|------|------|
| **URL-путь** | `/v1/users`,`/v2/users`| Простой, явный | Изменения URL-адресов в каждой версии |
| **Параметр запроса** | `/users?version=2`| Гибкий | Легко забыть |
| **Заголовок** |  __ЗАЩИЩЕНО_3__ | Чистые URL-адреса | Менее обнаруживаемый |
| **Нет версий** | Только эволюция схемы | Самый простой | Серьезные изменения затрагивают каждого |
**Рекомендация**: для ясности используйте управление версиями URL-путей (`/v1/`). Поддержка хотя бы одной предыдущей версии. Устаревшие старые версии с четкими сроками.

## Методы аутентификации
| Метод | Как это работает | Лучшее для |
|--------|-------------|----------|
| **Ключи API** | Секретный ключ в заголовке (`X-API-Key: abc123`) | Межсерверная, простая интеграция |
| **OAuth2** | Делегирование на основе токенов с областями | Сторонний доступ, авторизованные пользователем приложения |
| **JWT** | Автономный токен с претензиями | Аутентификация без сохранения состояния между службами |
| **Базовая аутентификация** | Имя пользователя:пароль в кодировке Base64 | Только разработка — никогда производство без TLS |
| **Сеансовые файлы cookie** | Идентификатор сеанса на стороне сервера в файле cookie только для HTTP | Традиционные веб-приложения |
### Поток OAuth2 (упрощенный)
1. Клиент перенаправляет пользователя на сервер авторизации.
2. Пользователь входит в систему и предоставляет разрешение.
3. Сервер авторизации возвращает код авторизации.
4. Клиент обменивает код на токен доступа (и, возможно, токен обновления).
5. Клиент использует токен доступа для вызова API.
6. Когда срок действия токена доступа истечет, используйте токен обновления, чтобы получить новый.

## Стили API: REST, GraphQL и gRPC
| Особенность | ОТДЫХ | ГрафQL | гРПК |
|---------|------|---------|------|
| **Формат данных** | JSON (обычно) | JSON | Протобуф (двоичный) |
| **Конечные точки** | Несколько (по одному на ресурс) | Единая конечная точка | Определено файлом .proto |
| **Чрезмерная выборка** | Обычный (получите больше, чем нужно) | Нет (клиент указывает поля) | Нет (определено схемой) |
| **Неполная выборка** | Требуется несколько звонков | Нет (получите именно то, что нужно) | Нет |
| **В режиме реального времени** | Требуются веб-сокеты | Подписки встроенные | Потоковое встроенное |
| **Кэширование** | HTTP-кэширование работает естественным образом | Сложнее кэшировать | Ограниченная |
| **Кривая обучения** | Низкий | Средний | Средний–Высокий |
| **Лучше всего** | Публичные API, приложения CRUD | Сложные пользовательские интерфейсы, мобильные приложения | Внутренние микросервисы, высокопроизводительные |

## Разбивка на страницы, фильтрация и сортировка
Для конечных точек, возвращающих списки:
| Техника | Пример | Когда использовать |
|-----------|---------|-------------|
| **Смещение/предел** | `?offset=20&limit=10`| Простой; работает с небольшими наборами данных |
| **На основе курсора** | `?cursor=abc123&limit=10`| Большие наборы данных; стабильные результаты |
| **Клавиатура** | `?created_after=2024-01-01&limit=10`| Очень эффективен; требует уникальный ключ |
```json
// Cursor-based response
{
  "data": [...],
  "pagination": {
    "next_cursor": "abc123",
    "has_more": true
  }
}
```

## Ограничение скорости
Защитите свой API от злоупотреблений и обеспечьте справедливое использование.
| Стратегия | Как это работает |
|----------|-------------|
| **Фиксированное окно** | N запросов на временное окно (например, 100/час) |
| **Раздвижное окно** | Более детальный; подсчитывает запросы в скользящем окне |
| **Корзина токенов** | Токены добавляются по фиксированной ставке; каждый запрос потребляет токен |
Верните`429 Too Many Requests`с заголовками:```
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1625097600
Retry-After: 60
```

## Обработка ошибок
Последовательные ответы на ошибки значительно упрощают работу с API:
```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Invalid input data",
    "details": [
      {
        "field": "email",
        "issue": "Invalid email format"
      }
    ]
  }
}
```

**Принципы**: используйте последовательную структуру ошибок, включайте сообщения, требующие действий, используйте стандартные коды состояния HTTP, регистрируйте ошибки на стороне сервера с помощью корреляционных идентификаторов и никогда не раскрывайте трассировки стека или внутренние детали.

## Шаблоны шлюзов API
Шлюз API находится между клиентами и серверными службами, обеспечивая единую точку входа.
| Ответственность | Описание |
|---------------|-------------|
| **Маршрутизация** | Прямые запросы к соответствующим серверным службам |
| **Аутентификация** | Проверка токенов на уровне шлюза |
| **Ограничение скорости** | Применяйте глобальные или индивидуальные ограничения |
| **Трансформация** | Преобразование между протоколами (REST ↔ gRPC) |
| **Кэширование** | Кэшировать общие ответы |
| **Мониторинг** | Централизованное ведение журнала и метрики |
| **Балансировка нагрузки** | Распределить трафик по экземплярам службы |
| Инструмент | Тип |
|------|------|
| **Конг** | API-шлюз с открытым исходным кодом (на базе Nginx) |
| **Шлюз AWS API** | Полностью управляемый, интегрированный с AWS |
| **Управление API Azure** | Управляемый шлюз с порталом для разработчиков |
| **Посланник / Истио** | Сервисная сетка с возможностями API-шлюза |
| **Траефик** | Автоматическое обнаружение, интеграция Let's Encrypt |

## Вебхуки
Веб-хуки позволяют вашему API передавать события клиентам в режиме реального времени, вместо того, чтобы заставлять клиентов опрашивать изменения.
| Аспект | Лучшая практика |
|--------|--------------|
| **Доставка** | POST-запрос с полезной нагрузкой JSON на URL-адрес клиента |
| **Безопасность** | Подписывать полезные данные с помощью HMAC; клиент проверяет подпись |
| **Надежность** | Повторить неудачную доставку с экспоненциальной задержкой |
| **Идемпотентность** | Включите уникальный идентификатор события; клиент обрабатывает дубликаты |
| **Версии** | Включить версию API в полезные данные вебхука |

## Контрольный список проектирования
- [ ] Ресурсы представляют собой существительные во множественном числе (`/users`, а не`/getUser`)
- [ ] Правильно используются HTTP-методы (GET для чтения, POST для создания и т. д.)
- [ ] Согласованный формат ответа об ошибке
- [ ] Пагинация для всех конечных точек списка
- [ ] Ограничение скорости с помощью четких заголовков
- [ ] Определена стратегия управления версиями API
- [ ] Аутентификация и авторизация на месте
- [ ] Проверка ввода на всех конечных точках
- [] Поддерживается документация OpenAPI/Swagger.
- [ ] CORS настроен правильно
- [ ] HTTPS применяется в производстве
- [ ] Ключи идемпотентности для операций POST, где это необходимо.
