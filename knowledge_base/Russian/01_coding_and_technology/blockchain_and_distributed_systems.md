# Блокчейн и распределенные системы
Блокчейн — это особый тип распределенной системы — децентрализованный реестр, предназначенный только для добавления, где записи (блоки) связаны криптографическими хэшами. Распределенные системы — это более широкая область, позволяющая нескольким компьютерам работать вместе как один. Обе концепции важны для понимания современной инфраструктуры: от криптовалюты до распределенных баз данных и алгоритмов консенсуса, лежащих в основе глобальных сервисов.
---

## Основы распределенных систем
### Почему распределенные системы?
| Мотивация | Описание |
|-----------|-------------|
| **Масштабируемость** | Добавьте больше машин, чтобы справиться с большей нагрузкой |
| **Отказоустойчивость** | Система продолжает работать, даже если некоторые машины выходят из строя |
| **Географическое распространение** | Обслуживать пользователей из близлежащих центров обработки данных |
| **Специализация** | Разные машины решают разные задачи |
### Ключевые понятия
| Концепция | Описание | Вызов |
|---------|-------------|-----------|
| **Консенсус** | Получение согласия всех узлов по значению | Сетевые разделы; Византийские разломы |
| **Репликация** | Копирование данных на несколько узлов | Согласованность и доступность |
| **Разделение (шардинг)** | Разделение данных по узлам | Горячие точки; перекрестные запросы |
| **Модели согласованности** | Гарантии того, что увидят разные читатели | Сильная консистенция медленная; конечная согласованность может удивить пользователей |
| **Теорема CAP** | У вас может быть только 2 параметра: Согласованность, Доступность, Допуск разделов | На практике требуется толерантность к разделению; выберите C или A |
### Теорема CAP
| Выбор | Что вы получаете | От чего ты отказываешься | Пример |
|--------|-------------|-----------------|---------|
| **КП** | Согласованный + терпимый к разделению | Некоторые узлы могут быть недоступны во время разделов | HBase, MongoDB, Redis |
| **АП** | Доступно + устойчивость к разделам | Чтения могут возвращать устаревшие данные | Кассандра, DynamoDB, CouchDB |
| **Калифорния** | Последовательный + доступный | Терпеть не могу сетевые разделы | Одноузловые базы данных (не распределенные по-настоящему) |

## Алгоритмы консенсуса
Как распределенные узлы согласовывают состояние системы?
| Алгоритм | Тип | Отказоустойчивость | Используется в |
|-----------|------|----------------|---------|
| **Паксос** | Устойчивость к сбоям | До f отказов с 2f+1 узлами | Гугл Чабби; фундаментальная теория |
| **Плот** | Устойчивость к сбоям | До f отказов с 2f+1 узлами | и т.д., Консул, ТиКВ |
| **ПБФТ** | Византийская отказоустойчивость | До f отказов с 3f+1 узлами | Ткань Hyperledger |
| **Доказательство работы** | Византийская отказоустойчивость | Зависит от хэш-мощности | Биткойн |
| **Доказательство доли** | Византийская отказоустойчивость | Зависит от ставки | Эфириум 2.0, Кардано |
### Плот (упрощенный)
| Роль | Ответственность |
|------|---------------|
| **Лидер** | Обрабатывает все запросы клиентов; отправляет записи журнала подписчикам |
| **Подписчик** | Отвечает на запросы лидера; голоса на выборах |
| **Кандидат** | Запрашивает голоса, чтобы стать лидером |
1. Все узлы начинаются как последователи.
2. Если последователь не слышит лидера в течение избирательного тайм-аута, он становится кандидатом.
3. Кандидаты запрашивают голоса; тот, кто наберет больше всего голосов, становится лидером
4. Лидер реплицирует записи журнала последователям.
5. Когда большинство подтвердит, запись фиксируется.

## Блокчейн
### Как работает блокчейн
| Компонент | Описание |
|-----------|-------------|
| **Блокировать** | Пакет транзакций + метаданные + хэш предыдущего блока |
| **Хеш** | Криптографический отпечаток содержимого блока |
| **Цепочка** | Каждый блок ссылается на хэш предыдущего блока, создавая неизменяемую цепочку |
| **Консенсус** | Участники сети договариваются, какие блоки добавить |
| **Дерево Меркла** | Дерево хэшей, суммирующее все транзакции в блоке |
### Почему блокчейн трудно взломать
1. Каждый блок содержит хэш предыдущего блока.
2. Изменение любой транзакции меняет хэш блока.
3. Измененный хеш разрывает цепочку — все последующие блоки становятся невалидными.
4. Злоумышленнику потребуется повторно добыть все последующие блоки И контролировать >50% сети.
### Типы блокчейнов
| Тип | Доступ | Валидатор | Пример |
|------|--------|-----------|---------|
| **Публичный доступ (без разрешения)** | Каждый может читать и писать | Открытый консенсус (PoW, PoS) | Биткойн, Эфириум |
| **Частное (разрешено)** | Ограниченный доступ | Известные валидаторы | Гиперледжер, Корда |
| **Консорциум** | Управляется группой организаций | Избранные валидаторы | R3 Corda для банковского дела |
### Смарт-контракты
Самоисполняющийся код, хранящийся в блокчейне, который запускается при выполнении заранее определенных условий.
| Платформа | Язык | Примечательная особенность |
|----------|----------|-----------------|
| **Эфириум** | Солидити, Вайпер | Крупнейшая экосистема смарт-контрактов |
| **Солана** | Руст, С | Высокая пропускная способность; низкие комиссии |
| **Кардано** | Хаскелл (Плутус) | рецензируемый; формальная проверка |
| **Гиперледжер** | Го, Java, JavaScript | Предприятие; разрешено |

| Валюта | Консенсус | Поставка | Основное использование |
|----------|-----------|--------|-------------|
| **Биткойн** | Доказательство работы | 21 миллион (ограничено) | Средство сбережения; цифровое золото |
| **Эфириум** | Доказательство доли | Нет жесткого ограничения | Смарт-контракты; Дефи; НФЦ |

| **Кардано** | Доказательство доли (Уроборос) | 45 миллиардов (ограничено) | Академический подход; устойчивость |

## Распределенные базы данных
| База данных | Архитектура | Последовательность | Лучшее для |
|----------|-------------|-------------|----------|
| **Кассандра** | Широкая колонка; одноранговая связь | Настраиваемый (в конечном итоге для кворума) | Высокая пропускная способность записи; временной ряд |
| **МонгоБД** | Документ; наборы реплик | Событие (с опцией причинно-следственной связи) | Гибкая схема; быстрое развитие |
| **ТаракановаяБД** | Распределенный SQL; Плот консенсус | Сильный | Распределенный SQL; глобальное развертывание |
| **ТибД** | Распределенный SQL; Плот (через ТиКВ) | Сильный | MySQL-совместимый; горизонтальное масштабирование |
| **ДинамоБД** | Ключ-значение; управляемый | Возможный (или сильный при последовательном чтении) | Бессерверный; Интеграция с AWS |
| **Гаечный ключ** | Распределенный SQL; Паксос | Сильный | Гугл Облако; глобальная согласованность |

## Шаблоны распределенных систем
| Узор | Описание | Вариант использования |
|---------|-------------|----------|
| **Выборы лидера** | Выберите один узел для координации | Лидер плота; Хранитель зоопарка |
| **Репликация** | Копирование данных для обеспечения избыточности и масштабирования чтения | Реплики баз данных; CDN |
| **Шардинг** | Разделить данные по диапазону ключей или хешу | Крупномасштабные базы данных |
| **MapReduce** | Разделить вычисления по узлам; совокупные результаты | Обработка больших данных |
| **Протокол сплетен** | Узлы периодически делятся состоянием со случайными узлами | Членство в кластере; обнаружение неисправностей |
| **Двухфазная фиксация** | Координация транзакций на нескольких узлах | Распределенные базы данных |
| **Шаблон «Сага»** | Серия локальных сделок с компенсирующими действиями | Микросервисные транзакции |
| **Автоматический выключатель** | Прекратите звонить в неисправную службу; быстро потерпеть неудачу | Устойчивость; предотвратить каскадные сбои |

## Проблемы в распределенных системах
| Вызов | Описание | смягчение последствий |
|-----------|-------------|------------|
| **Сетевые разделы** | Узлы не могут общаться | компромисс CAP; повторить попытку с отсрочкой |
| **Перекос часов** | Разные узлы имеют разные часы | Используйте логические часы; НТП; не полагайтесь на время настенных часов |
| **Византийские разломы** | Узлы, которые лгут или ведут себя произвольно | Консенсус БФТ; блокчейн |
| **Расщепление мозга** | Два узла думают, что они лидеры | фехтование; решения на основе кворума |
| **Каскадные сбои** | Одна неудача вызывает другие | автоматические выключатели; переборки; изящная деградация |
| **Согласованность данных** | Синхронизация реплик | Модели согласованности; разрешение конфликтов |

## Краткое содержание
Распределенные системы — это то, как современное программное обеспечение масштабируется, выдерживает сбои и обслуживает пользователей по всему миру. Алгоритмы консенсуса (Raft, Paxos) обеспечивают согласие узлов. Блокчейны добавляют криптографическую проверку и децентрализацию для создания надежных реестров. Распределенные базы данных (Cassandra, CockroachDB, DynamoDB) обрабатывают данные в любом масштабе. Фундаментальный компромисс, зафиксированный теоремой CAP, заключается между согласованностью и доступностью, когда сеть ненадежна. Понимание этих концепций необходимо для создания систем, работающих в масштабах Интернета.
