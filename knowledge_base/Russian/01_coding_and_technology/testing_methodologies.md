# Методики тестирования
Тестирование — это способ обрести уверенность в том, что ваш код работает — и, что более важно, что изменения в нем не нарушат то, что уже работает. Хорошее тестирование выявляет ошибки раньше, чем это сделают пользователи, документирует ожидаемое поведение и позволяет бесстрашно проводить рефакторинг. Этот файл охватывает весь спектр стратегий тестирования, от модульных тестов до сквозных тестов, а также принципы, которые делают тестирование эффективным.
---

## Пирамида тестирования
Пирамида тестирования описывает идеальное распределение тестов в проекте.
```
        /  E2E  \          ← Few; slow; expensive; test the whole system
       /─────────\
      / Integration\       ← Some; test how components work together
     /───────────────\
    /   Unit Tests    \    ← Many; fast; cheap; test individual functions
   /─────────────────────\
```

| Уровень | Граф | Скорость | Стоимость | Что он тестирует |
|-------|-------|-------|------|---------------|
| **Единица** | Многие | Быстро (мс) | Низкий | Отдельные функции, классы, методы |
| **Интеграция** | Некоторые | Средний (100 мс/с) | Средний | Как взаимодействуют компоненты; запросы к базе данных; API-вызовы |
| **E2E** | Мало | Медленно (секунды-минуты) | Высокий | Полный поток пользователей через реальную систему |
---

## Модульное тестирование
Тестирование отдельных блоков кода изолированно.
### Принципы
| Принцип | Описание |
|-----------|-------------|
| **Быстро** | Каждый тест должен выполняться за миллисекунды |
| **Изолировано** | Тесты не зависят друг от друга; нет общего состояния |
| **Детерминированный** | Один и тот же ввод → один и тот же вывод каждый раз (без случайности, без зависимости от времени) |
| **Самопроверка** | Тест проходит или не проходит автоматически; нет ручного контроля |
| **Своевременно** | Написано рядом с кодом или перед ним (TDD) |
### Анатомия теста
| Фаза | Описание |
|-------|-------------|
| **Упорядочить** | Настройка тестовых данных и зависимостей |
| **Действие** | Вызов тестируемой функции или метода |
| **Утверждать** | Убедитесь, что результат соответствует ожиданиям |
### Что тестировать
| Категория | Примеры |
|----------|---------|
| **Счастливый путь** | Обычные входные данные производят ожидаемые результаты |
| **Крайние случаи** | Пустой ввод, ноль, ноль, максимальные значения, один элемент |
| **Случаи ошибок** | Неверный ввод, данные отсутствуют, разрешение отклонено |
| **Граничные условия** | Off-by-one; точно в пределах |
### Издевательство и заглушка
| Срок | Описание | Когда использовать |
|------|-------------|-------------|
| **Мок** | Поддельный объект, записывающий, как он был назван | Проверка взаимодействий (был ли вызван этот метод?) |
| **Завершение** | Поддельный объект, возвращающий заранее определенные значения | Предоставление тестовых данных (вернуть этого пользователя из базы данных) |
| **Шпион** | Обертка, записывающая обращения к реальному объекту | Частичная проверка |
| **Фейк** | Упрощенная, но работающая реализация | База данных в памяти для тестов |
| Издевательская библиотека | Язык |
|----------------|--------|
| **unittest.mock** | Питон |
| **Шутка** | JavaScript/TypeScript |
| **Мокито** | Ява |
| **Минимальный заказ** | С# |
| **свидетельствовать/гомочить** | Перейти |

## Интеграционное тестирование
Тестирование того, как несколько компонентов работают вместе.
| Что тестировать | Пример |
|-------------|---------|
| **Запросы к базе данных** | Выдает ли ORM правильный SQL? Используются ли индексы? |
| **Конечные точки API** | Работает ли полный цикл запрос-ответ? |
| **Взаимодействие со службами** | Правильно ли служба A вызывает службу B? |
| **Внешние зависимости** | Работает ли интеграция платежного шлюза? |
### Стратегии
| Стратегия | Описание | Компромисс |
|----------|-------------|-----------|
| **Реальные зависимости** | Используйте реальную базу данных и реальную очередь сообщений | Самый реалистичный; помедленнее; сложнее настроить |
| **Тестовые контейнеры** | Запускайте Docker-контейнеры для каждого тестового запуска | Хороший баланс; воспроизводимый |
| **Альтернативы в памяти** | H2 вместо PostgreSQL; шина сообщений в памяти | Быстрый; может пропустить реальные проблемы |
| **Контрактное тестирование** | Убедитесь, что службы соблюдают свои контракты API | Отслеживает изменения интерфейса |

## Сквозное (E2E) тестирование
Тестирование всей системы с точки зрения пользователя.
| Инструмент | Тип | Лучшее для |
|------|------|----------|
| **Драматург** | Автоматизация браузера | веб-приложения; кроссбраузерный |
| **Кипарис** | Автоматизация браузера | веб-приложения; опыт разработчика |
| **Селен** | Автоматизация браузера | Наследие; широкая языковая поддержка |
| **Детокс** | Мобильный E2E | Нативные приложения React |
| **Аппиум** | Мобильный E2E | Нативные и гибридные мобильные приложения |
| **Маэстро** | Мобильный E2E | Мобильные приложения; простой синтаксис YAML |
| **k6 / Саранча** | Нагрузочное тестирование | Производительность под нагрузкой |
### Лучшие практики E2E
| Практика | Почему |
|----------|-----|
| **Тестировать только критические пути** | E2E-тесты медленные; сосредоточьтесь на самом важном |
| **Использовать фабрики тестовых данных** | Создавать тестовые данные программно; не полагайтесь на исходные данные |
| **Уборка после тестов** | Каждый тест должен оставлять систему в известном состоянии |
| **Избегайте тестирования деталей пользовательского интерфейса** | Тестируйте поведение, а не классы CSS или позиции элементов |
| **Выполнить в CI** | E2E-тесты должны запускаться автоматически при каждом изменении |

## Разработка через тестирование (TDD)
Сначала напишите тест, а затем напишите код, чтобы он прошел.
| Шаг | Описание |
|------|-------------|
| **1. Красный** | Напишите неудачный тест, описывающий желаемое поведение |
| **2. Зеленый** | Напишите минимальный код, чтобы пройти тест |
| **3. Рефакторинг** | Очистите код, оставив тесты зелеными |
| Выгода | Описание |
|---------|-------------|
| **Отзывы о дизайне** | Тесты заставляют думать об интерфейсах перед реализацией |
| **Безопасность регрессии** | Каждая ошибка проходит проверку; ошибка никогда не вернется |
| **Документация** | Тесты служат живой документацией ожидаемого поведения |
| **Уверенность** | Высокое тестовое покрытие позволяет проводить бесстрашный рефакторинг |
---

## Разработка, основанная на поведении (BDD)
BDD расширяет TDD за счет написания тестов на естественном языке, описывающих поведение с точки зрения пользователя.
### Формат «Дано-когда-то»
```
Given a user with an empty shopping cart
When they add a "Python Book" priced at $29.99
Then the cart total should be $29.99
And the cart should contain 1 item
```

| Инструмент | Язык |
|------|----------|
| **Огурец** | Java, JavaScript, Ruby и другие |
| **Вести** | Питон |
| **СпецФлоу** | С# |
| **Шутка** (с описанием/этим) | JavaScript |

## Другие типы тестирования
| Тип | Что он тестирует | Инструменты |
|------|--------------|-------|
| **Производительность/Нагрузка** | Поведение системы под нагрузкой | k6, JMeter, Саранча, Гатлинг |
| **Безопасность** | Уязвимости и векторы атак | OWASP ZAP, Burp Suite, Сник |
| **Доступность** | Соответствие WCAG | топор, Маяк, pa11y |
| **Контракт** | Совместимость API между сервисами | Пакт, Контракт весеннего облака |
| **Мутация** | Качество самого набора тестов | Страйкер, черт возьми, PIT |
| **Визуальная регрессия** | Изменения пользовательского интерфейса между версиями | Перси, хроматический, BackstopJS |
| **Хаос** | Устойчивость системы к сбоям | Обезьяна Хаоса, Лакмус, Гремлин |
| **Дым** | Базовая функциональность после развертывания | Пользовательские скрипты; медицинские осмотры |
| **Замочить** | Поведение системы в течение длительного времени | Длительные нагрузочные тесты |

## Тестовая организация
| Узор | Описание | Когда использовать |
|---------|-------------|-------------|
| **Совместное расположение** | Тесты рядом с кодом, который они тестируют (`src/utils.test.ts`) | Большинство проектов; легко найти |
| **Отдельный каталог** | Тесты в папке`tests/`или`__tests__/`| Крупные проекты; четкое разделение |
| **Тестовые приспособления** | Общие тестовые данные в каталоге`fixtures/`| Когда нескольким тестам нужны одни и те же данные |
| **Тестовые утилиты** | Общие помощники в каталоге`test-utils/`| Когда логика настройки сложна |

## Покрытие кода
| Метрическая | Что он измеряет | Ограничение |
|--------|-----------------|------------|
| **Охват линии** | Процент строк кода, выполненных тестами | Не измеряет качество утверждений |
| **Охват филиалов** | Процент занятых ветвей (если/иначе) | Лучше, чем покрытие линии; все еще не обнаруживает все ошибки |
| **Покрытие маршрута** | Процент использованных путей выполнения | Самый тщательный; экспонента в сложном коде |
| **Оценка мутаций** | Процент мутаций, обнаруженных тестами | Лучший показатель качества тестирования |
**Цель**: разумное значение по умолчанию — 80 % покрытия линии. Но покрытие — это ориентир, а не цель: 100%-ное покрытие при слабых утверждениях хуже, чем 70%-ное покрытие при тщательном тестировании.

## Непрерывная интеграция и тестирование
| Практика | Описание |
|----------|-------------|
| **Запускать все модульные тесты при каждом коммите** | Быстрая обратная связь; немедленно улавливает регрессию |
| **Выполните интеграционные тесты PR** | Выявляет проблемы, которые пропускают модульные тесты |
| **Запускайте E2E-тесты каждую ночь или при слиянии с основной ** | Медленно, но тщательно |
| **Быстро проваливайтесь** | Остановите трубопровод при первой неудаче, чтобы сэкономить время |
| **Ненадежная политика тестирования** | Немедленно помещайте в карантин или удаляйте нестабильные тесты; никогда не игнорируй |
| **Тестовое распараллеливание** | Запускайте тесты параллельно, чтобы сократить время CI |

## Практические советы
- **Четко называйте тесты.**`test_calculates_tax_for_high_earner`сообщает, что сломалось. `test_1`ничего вам не говорит.
- **Одно утверждение на тест (если это возможно).** Облегчает диагностику сбоев.
- **Не тестируйте детали реализации.** Тестируйте поведение. Если вы проводите рефакторинг внутренних компонентов, тесты не должны ломаться.
- **Избегайте тестирования стороннего кода.** Имитируйте внешние библиотеки; проверьте взаимодействие вашего кода с ними.
- **Делайте тесты быстро.** Если набор тестов занимает 10 минут, разработчики перестанут его запускать. Неустанно оптимизируйте.
- **Удалять неработающие тесты.** Тесты, которые всегда проходят успешно, или тестируют удаленный код, являются шумом.
- **Относитесь к тестовому коду как к рабочему коду.** Он должен быть читабельным, удобным в сопровождении и хорошо структурированным.

## Краткое содержание
Тестирование не является обязательным — именно так вы создаете программное обеспечение, которое не ломается. Пирамида тестирования поможет вам выполнить множество быстрых модульных тестов, некоторые интеграционные тесты и несколько тестов E2E. TDD и BDD обеспечивают структурированные подходы. Mocking изолирует модули для тестирования. Покрытие кода измеряет ширину, а не глубину. Самый важный принцип таков: если что-то не проверено, значит оно сломано — вы просто еще об этом не знаете.
