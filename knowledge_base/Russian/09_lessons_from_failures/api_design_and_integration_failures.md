# Ошибки проектирования и интеграции API
API (интерфейсы прикладного программирования) — это соединительная ткань современного программного обеспечения. Они позволяют службам взаимодействовать, позволяют третьим сторонам интегрироваться и позволяют командам работать независимо. Когда дизайн API идет не так, последствия распространяются на каждую систему, которая от него зависит: нарушенная интеграция, уязвимости безопасности, разочарование разработчиков и дорогостоящие переписывания. Сбои интеграции, когда системы не могут надежно взаимодействовать, являются одними из наиболее распространенных источников производственных инцидентов.

## Распространенные ошибки проектирования API
### Ошибки дизайна
| Ошибка | Описание | Следствие |
|---------|-------------|-------------|
| **Несогласованное название** | `/getUsers`против`/list_users`против`/fetch-users`| Путаница; ошибки; медленное развитие |
| **Перегруженные конечные точки** | Одна конечная точка, которая выполняет 10 разных действий в зависимости от параметров | Трудно понять; трудно проверить; трудно изменить |
| **Неполная выборка** | Клиенту необходимо сделать 5 вызовов API, чтобы получить соответствующие данные | Медленный; расточительный; сложный клиентский код |
| **Чрезмерная выборка** | API возвращает все поля, когда клиенту нужно только 2 | Потерянная пропускная способность; медленный на мобильном телефоне; риск безопасности (раскрытие ненужных данных) |
| **Нет версий** | Критические изменения внедряются без предупреждения | Клиенты ломаются; злые разработчики |
| **Неопределенные сообщения об ошибках** | «Ошибка 500: Внутренняя ошибка сервера» без подробностей | Невозможно отладить; медленное разрешение |
| **Отсутствует нумерация страниц** | Конечная точка возвращает все записи (может быть миллионы) | Таймауты; истощение памяти; разбились клиенты |
| **Несовместимые коды состояния** | 200 ОК для ошибок; 500 за ошибки клиента | Клиенты не могут отличить успех от неудачи |
### Антишаблоны REST API
| Анти-паттерн | Описание | Лучший подход |
|-------------|-------------|-----------------|
| **Использование GET для мутаций** | `GET /delete-user?id=5`| Используйте метод DELETE |
| **Использование POST для всего** | `POST /get-users`; `POST /update-user`| Используйте соответствующие методы HTTP (GET, POST, PUT, PATCH, DELETE) |
| **Возврат HTML из API** | API возвращает фрагменты HTML | Вернуть JSON; пусть клиент визуализирует |
| **Бизнес-логика в URL-адресах** | `/users/active/premium/from-2023`| Используйте параметры запроса или тело запроса для сложных фильтров |
| **Раскрытие схемы базы данных** | `/api/table_name/column`| Разрабатывайте API с учетом ресурсов и концепций предметной области, а не таблиц |
| **Нет HATEOAS/ссылок** | Клиент жестко закодирует все URL-адреса | Включайте в ответы ссылки на соответствующие ресурсы |

## Сбои безопасности
### Распространенные уязвимости API
| Уязвимость | Описание | Пример |
|--------------|-------------|---------|
| **Сломанная аутентификация** | API неправильно проверяет личность | Отсутствует проверка токена; принимаются жетоны с истекшим сроком действия |
| **Чрезмерное раскрытие данных** | API возвращает больше данных, чем нужно клиенту | Конечная точка пользователя возвращает хэши паролей и внутренние идентификаторы |
| **Массовое задание** | Клиент может устанавливать поля, которые ему не нужны | `PATCH /user`позволяет установить`role: "admin"`|
| **Инъекция** | Пользовательский ввод интерпретируется как код | SQL-инъекция; NoSQL-инъекция; внедрение команд |
| **IDOR** (Небезопасная прямая ссылка на объект) | Доступ к ресурсам путем изменения идентификатора в URL | `/api/users/5`→ измените на `/api/users/6`, чтобы увидеть чужие данные |
| **Отсутствует ограничение скорости** | Нет ограничений на вызовы API | Грубая сила; отказ в обслуживании; соскабливание |
| **Неправильная конфигурация CORS** | Чрезмерно либеральный доступ из разных источников | `Access-Control-Allow-Origin: *`на аутентифицированных конечных точках |
### Сбои аутентификации и авторизации
| Неудача | Описание | Воздействие |
|---------|-------------|--------|
| **Жестко запрограммированные учетные данные** | Ключи API или пароли в исходном коде | Утечка через контроль версий; доступен всем разработчикам |
| **Токен не имеет срока действия** | Срок действия токенов никогда не истекает | Украденный токен дает постоянный доступ |
| **Слабые секретные ключи** | Короткие или предсказуемые ключи подписи | Токены можно подделать |
| **Нет области/разрешений** | Все токены имеют полный доступ | Скомпрометированный токен = полный доступ к системе |
| **Запись конфиденциальных данных** | Токены или пароли в журналах | Доступно всем, у кого есть доступ к журналу |
| **Несогласованная авторизация** | Некоторые конечные точки проверяют разрешения; другие этого не делают | Несанкционированный доступ через незащищенные конечные точки |

## Сбои интеграции
### Проблемы интеграции распределенных систем
| Неудача | Описание | Пример |
|---------|-------------|---------|
| **Тесная связь** | Сервисы зависят от деталей внутренней реализации друг друга | Изменение базы данных одного сервиса приводит к поломке трех других |
| **Синхронные цепи** | Служба A вызывает B вызывает C вызывает D; задержка накапливается | 200 мс + 300 мс + 500 мс = время отклика 1 секунда |
| **Без автоматического выключателя** | Сбой в обслуживании вызывает каскадные сбои | Служба D работает медленно; все вышестоящие службы исчерпывают свои потоки ожидания |
| **Нет логики повтора** | Временные сбои становятся постоянными | Сетевой сигнал = неудачная транзакция; пользователю приходится повторить попытку вручную |
| **Чрезмерное количество попыток** | Повторные попытки без отсрочки перегружают службы восстановления | Проблема грохота стада |
| **Нет идемпотентности** | Повторная попытка неидемпотентной операции приводит к созданию дубликатов | Оплата взимается дважды; заказ создан дважды |
| **Постоянные сюрпризы** | Клиент читает устаревшие данные после записи | Профиль обновлений пользователя; обновляет страницу; старые данные все еще отображаются |
### Сбои сторонней интеграции
| Неудача | Описание | смягчение последствий |
|---------|-------------|------------|
| **Изменения в API поставщиков** | Сторонние производители изменяют свой API без предварительного уведомления | Закрепление версии; уровень абстракции; мониторинг журналов изменений поставщиков |
| **Ограничение скорости** | Третья сторона ограничивает ваши запросы | Кэширование; очередь запросов; переговоры о более высоких лимитах |
| **Простой поставщика** | Сторонний сервис недоступен | автоматические выключатели; резервное поведение; мультивендорная стратегия |
| **Изменения формата данных** | Формат ответа на сторонние изменения | Проверка схемы; слой трансформации; оповещения об изменении формата |
| **Устаревшая версия без пути миграции** | Поставщик объявляет устаревшей конечную точку без эквивалента | Будьте в курсе; сохранять абстракцию; планируйте миграцию заранее |

## Тематические исследования
### Пример 1: API, который возвращает все
| Аспект | Описание |
|--------|-------------|
| **Сценарий** | Пользовательский API SaaS-компании вернул все пользовательские поля, включая внутренние метаданные |
| **Что пошло не так** | Нет фильтрации полей; ответ включал хэши паролей, внутренние примечания и флаги администратора |
| **Воздействие** | Исследователи безопасности обнаружили уязвимость; публичное раскрытие информации; GDPR-расследование |
| **Основная причина** | API сериализовал всю модель базы данных без фильтрации |
| **Исправление** | Модели явного реагирования; контроль доступа на уровне поля; проверка безопасности всех конечных точек |
| **Урок** | Никогда не раскрывайте свою модель базы данных напрямую через API; использовать DTO (объекты передачи данных) |
### Пример 2: Каскадный сбой
| Аспект | Описание |
|--------|-------------|
| **Сценарий** | Микросервисная архитектура с синхронным межсервисным взаимодействием |
| **Что пошло не так** | В одной службе наблюдалось замедление работы базы данных; вышестоящие службы ждали ответов; пулы потоков исчерпаны |
| **Воздействие** | Полное отключение системы на 45 минут; затронуты все услуги |
| **Основная причина** | Нет автоматических выключателей; нет таймаутов; синхронная цепочка зависимостей |
| **Исправление** | автоматические выключатели; таймауты; асинхронная связь, где это возможно; переборки |
| **Урок** | Синхронные вызовы между службами создают хрупкие цепочки; дизайн на провал |

## Лучшие практики
### Контрольный список проектирования API
| Площадь | Практика |
|------|----------|
| **Именование** | Используйте существительные для обозначения ресурсов; HTTP-методы для действий; последовательное соглашение об именах |
| **Версии** | Версия с первого дня; используйте управление версиями URL (`/v1/`) или управление версиями заголовка |
| **Разбивка на страницы** | Всегда разбивать конечные точки списка на страницы; использовать нумерацию страниц на основе курсора для больших наборов данных |
| **Обработка ошибок** | Согласованный формат ошибок; включать коды ошибок; предоставить действенные сообщения |
| **Ограничение скорости** | Внедрить ограничения скорости; вернуть 429 с заголовком retry-after |
| **Идемпотентность** | Поддержка ключей идемпотентности для конечных точек мутаций |
| **Документация** | Спецификация OpenAPI/Swagger; держать его в курсе; привести примеры |
| **Тестирование** | Контрактные испытания; интеграционные тесты; контрактные испытания, ориентированные на потребителя |
| **Мониторинг** | Отслеживать задержку; уровень ошибок; пропускная способность; здоровье зависимости |
| **Устаревшая** | Объявляйте о прекращении поддержки заблаговременно; предоставить руководства по миграции |

## Краткое содержание
Ошибки проектирования API варьируются от косметических (несогласованное именование) до катастрофических (уязвимости безопасности, каскадные сбои). Наиболее распространенные ошибки проектирования — перегруженные конечные точки, чрезмерная выборка, отсутствие нумерации страниц, неясные ошибки — затрудняют использование и обслуживание API. Сбои в системе безопасности — нарушение аутентификации, IDOR, массовое присвоение, чрезмерное раскрытие данных — подвергают системы атакам. Сбои интеграции — жесткая связь, синхронные цепочки, отсутствие автоматических выключателей, отсутствие идемпотентности — создают хрупкие системы, в которых один сбой распространяется на все службы. Сторонние интеграции добавляют внешний риск: изменения API, ограничение скорости и простои поставщиков. Стратегии предотвращения хорошо известны: используйте явные модели реагирования; версия с первого дня; реализовать автоматические выключатели и таймауты; конструкция для идемпотентности; проверять и дезинфицировать все входные данные; следить за всем; и рассматривать контракты API как обязательные соглашения, изменения которых требуют координации. Лучшие API скучны — они предсказуемы, последовательны, хорошо документированы и устойчивы к сбоям.
