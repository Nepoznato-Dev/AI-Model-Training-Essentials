# Сбои конвейера данных и ETL
Конвейеры данных — это водопровод современных организаций: они перемещают данные из исходных систем посредством преобразований в базы данных, хранилища и озера, где они используются для аналитики, машинного обучения и принятия решений. Когда они работают, никто этого не замечает. Когда они терпят неудачу, решения принимаются на основе устаревших данных, модели тренируются на мусоре, отчеты показывают невозможные цифры, а доверие ко всей платформе данных подрывается. Сбои конвейеров данных являются одними из наиболее распространенных и дорогостоящих сбоев в технологических организациях.
---

## Распространенные режимы отказа
### Проблемы с качеством данных
| Неудача | Описание | Воздействие | Сложность обнаружения |
|---------|-------------|--------|---------------------|
| **Тихое повреждение данных** | Данные изменены неправильно, без каких-либо ошибок | Последующие системы доверяют неверным данным; решения, основанные на ложной информации | Очень сложно — нет сигнала ошибки |
| **Дрейф схемы** | Исходная система меняет схему (добавляет, удаляет, переименовывает столбцы) | Конвейер прерывается или данные автоматически удаляются | Средний — конвейер может выйти из строя или дать частичные результаты |
| **Несоответствие типов данных** | Источник отправляет строку там, где ожидается целое число; изменения точности плавающего режима | Трубопровод выходит из строя; данные усечены; ошибки округления | Средний — может вызвать ошибку конвейера или незначительные проблемы с данными |
| **Повторяющиеся записи** | Одно и то же событие обработано несколько раз | Завышенные показатели; неправильные агрегаты | Сложный — каждая запись выглядит корректной индивидуально |
| **Нулевые/отсутствующие значения** | Ожидаемые поля пусты | Расчеты терпят неудачу; модели дают неверные прогнозы | Средний — зависит от обработки нулей |
| **Значения вне диапазона** | Значения за пределами ожидаемых границ (отрицательный возраст; будущие даты) | Искаженная статистика; сломанная бизнес-логика | Средний — требуются правила проверки |
| **Поздние данные** | Данные поступают после закрытия окна обработки | Неполные результаты; пропущенные записи | Сложный — результаты выглядят полными, но это не так |
### Проблемы с трубопроводной инфраструктурой
| Неудача | Описание | Воздействие |
|---------|-------------|--------|
| **Ошибка оркестрации** | Планировщик (Airflow, Prefect) не запускает конвейер | Данные устарели; никакой обработки не происходит |
| **Исчерпание ресурсов** | Конвейеру не хватает памяти, процессора или диска | Аварии трубопровода; частичные результаты |
| **Ошибка зависимости** | Восходящая система не работает или работает медленно | Конвейер ожидает неопределенное время или выходит из строя |
| **Проблемы параллелизма** | Несколько конвейеров одновременно изменяют одни и те же данные | Условия гонки; повреждение данных |
| **Дрейф конфигурации** | Изменения среды (сеть, учетные данные, конечные точки) не отражены в конвейере | Трубопровод неожиданно выходит из строя |
| **Противодавление** | Данные поступают быстрее, чем конвейер может обработать | Растущие очереди; увеличение задержки |

## Тематические исследования
### Пример 1: автоматическое дублирование данных
| Аспект | Описание |
|--------|-------------|
| **Сценарий** | Конвейер заказов компании электронной коммерции обрабатывает события из очереди сообщений |
| **Что пошло не так** | Перезапуск потребителя приводил к повторному использованию сообщений; логики дедупликации не существовало |
| **Воздействие** | Показатели доходов были завышены на 15% за 3 недели, прежде чем кто-либо это заметил |
| **Основная причина** | Нет ключей идемпотентности; доставка «хотя бы один раз» без дедупликации |
| **Исправление** | Добавлены ключи идемпотентности на основе идентификатора заказа; реализована семантика «точно один раз» |
| **Урок** | Доставка «хотя бы один раз» требует дедупликации; всегда проверять итоговые значения по исходным системам |
### Пример 2: изменение схемы нарушает нисходящий поток
| Аспект | Описание |
|--------|-------------|
| **Сценарий** | Поставщик платежей меняет имя поля в ответе API |
| **Что пошло не так** | Конвейер ETL молча начал записывать нулевые значения; нет проверки схемы |
| **Воздействие** | Финансовые отчеты показали нулевую прибыль от этого способа оплаты в течение 2 месяцев |
| **Основная причина** | Никакой проверки схемы при приеме; нулевые значения считаются действительными |
| **Исправление** | Добавлена ​​проверка схемы с оповещениями; обязательные поля включены; нулевые чеки |
| **Урок** | Никогда не доверяйте внешним схемам, чтобы они оставались стабильными; проверить на границе |
### Пример 3: Катастрофа часового пояса
| Аспект | Описание |
|--------|-------------|
| **Сценарий** | Глобальная компания агрегирует ежедневные показатели по офисам |
| **Что пошло не так** | В некоторых источниках использовалось время UTC, в других — местное время; трубопровод не нормализовался |
| **Воздействие** | Ежедневные итоги не совпадали; некоторые транзакции засчитаны не в тот день; закрытие месяца было неправильным |
| **Основная причина** | Нет стандартной политики часовых поясов; временные метки хранятся непоследовательно |
| **Исправление** | Все временные метки хранятся в формате UTC; преобразование в местное время только на уровне представления |
| **Урок** | Стандартизируйте UTC повсеместно; четко указывайте часовые пояса на каждой границе |

## Стратегии профилактики
### Проверка данных
| Стратегия | Описание | Примеры инструментов |
|----------|-------------|---------------|
| **Проверка схемы** | Проверка соответствия данных ожидаемой схеме на каждом этапе | Большие надежды; Дику; Сода |
| **Проверка диапазона** | Значения находятся в ожидаемых пределах | Пользовательские утверждения; тесты дбт |
| **Проверка свежести** | Данные достаточно свежие, чтобы быть полезными | Мониторинг временных меток; Оповещения SLA |
| **Проверка объема** | Количество строк находится в пределах ожидаемого диапазона | Обнаружение аномалий при подсчете строк |
| **Ссылочная целостность** | Внешние ключи совпадают; нет потерянных записей | ограничения SQL; инструменты качества данных |
| **Сверка данных между источниками** | Итоговые значения совпадают между источником и целью | Автоматизированные задания по сверке |
### Шаблоны проектирования конвейеров
| Узор | Описание | Выгода |
|---------|-------------|---------|
| **Идемпотентность** | Запуск конвейера несколько раз дает тот же результат | Безопасно повторить попытку; нет дубликатов |
| **Атомность** | Конвейер либо полностью завершается успешно, либо полностью терпит неудачу (без частичного состояния) | Никаких полуобработанных данных |
| **КПП** | Сохраняйте прогресс на каждом этапе; резюме с последнего КПП | Отказоустойчивость; никакой переработки |
| **Очереди недоставленных писем** | Неудачные записи отправляются в отдельную очередь для расследования | Никакой потери данных; может исследовать и переиграть |
| **Автоматические выключатели** | Остановить обработку при сбое нисходящего потока | Предотвращение каскадных сбоев |
| **Контракты данных** | Соглашение между производителями и потребителями о формате данных | Изменения схемы согласовываются |
### Мониторинг и оповещение
| Что контролировать | Почему | Как |
|-----------------|-----|-----|
| **Продолжительность конвейера** | Проблемы с сигналами увеличения продолжительности | Анализ тенденций; Отслеживание SLA |
| **Счетчик строк** | Внезапные изменения указывают на проблемы | Сравните со средними историческими показателями |
| **Нулевые ставки** | Увеличение схемы нулевых сигналов или проблемы с источником | Отслеживание значений NULL на уровне столбца |
| **Актуальность данных** | Устаревшие данные означают, что конвейер не работает | Временная метка последней записи |
| **Воздействие на переработку** | Используют ли отчеты и модели правильные данные? | Сквозная линия передачи данных |
| **Использование ресурсов** | ПРОЦЕССОР; память; диск; сеть | Мониторинг инфраструктуры |

## Стратегии восстановления
| Ситуация | Стратегия |
|-----------|----------|
| **Неверные данные уже на складе** | Определить затронутый временной диапазон; повторная обработка из источника; уведомить последующих потребителей |
| **Отказ трубопровода в середине периода** | Идемпотентная конструкция обеспечивает безопасный повторный запуск; КПП позволяет возобновить работу |
| **Изменение схемы нарушило конвейер** | Исправление трансформации; заполнение затронутых данных; добавить обработку эволюции схемы |
| **Тихая коррупция обнаружена поздно** | Анализ первопричин; определить радиус взрыва; повторная обработка; добавить мониторинг, чтобы отловить повторение |
| **Потеря данных** | Восстановление из резервной копии; повтор из источника; оценить, возмещается ли убыток |

## Краткое содержание
Сбои конвейера данных происходят повсеместно и часто обходятся дороже, чем сбои в работе приложений, поскольку они приводят к неверным ответам, а не к очевидным ошибкам. Наиболее распространенными причинами являются скрытое повреждение данных, дрейф схемы, дубликаты, ошибки часовых поясов и пропущенные значения. Ключевыми стратегиями предотвращения являются: проверка данных на каждой границе (схема, диапазон, объем, актуальность); спроектировать конвейеры как идемпотентные и атомарные; контролировать все (длительность, количество строк, нулевые скорости, свежесть); используйте очереди недоставленных писем для неудачных записей; и заключать контракты на передачу данных между производителями и потребителями. В случае возникновения сбоев реагирование должно включать анализ первопричин, повторную обработку затронутых данных, уведомление последующих потребителей и, что особенно важно, добавление мониторинга для выявления того же класса сбоев в будущем. Организации, получившие это право, относятся к конвейерам данных с той же строгостью, что и к производственному программному обеспечению: тестирование, мониторинг, оповещение, реагирование на инциденты и вскрытие.
