# DevOps وCI/CD
DevOps عبارة عن مزيج من الفلسفة والممارسات والأدوات الثقافية التي تمكن الفرق من تقديم البرامج بشكل أسرع وأكثر موثوقية. إنه يكسر الجدار بين المطورين (الذين يريدون تقديم التغييرات) والعمليات (الذين يريدون الاستقرار). CI/CD — التكامل المستمر والتسليم المستمر — هو العمود الفقري للأتمتة الذي يجعل ذلك ممكنًا.
---

## خطوط أنابيب CI/CD
### ماذا يعني CI/CD في الواقع
| مصطلح | ماذا يفعل |
|------|------------|
| **التكامل المستمر (CI)** | يقوم المطورون بدمج التعليمات البرمجية بشكل متكرر؛ يؤدي كل دمج إلى تشغيل عمليات إنشاء واختبارات تلقائية |
| **التسليم المستمر (قرص مضغوط)** | الكود دائمًا في حالة قابلة للنشر؛ الإطلاق للإنتاج هو قرار يدوي |
| **النشر المستمر** | كل تغيير يجتاز الاختبارات يذهب إلى الإنتاج تلقائيًا — لا توجد بوابة يدوية |
### مراحل خطوط الأنابيب النموذجية
| المرحلة | ماذا يحدث | أدوات |
|-------|------------|-------|
| **المصدر** | يدفع المطور الكود إلى Git | جيثب، جيتلاب، بيتبوكيت |
| **بناء** | ترجمة التعليمات البرمجية وتثبيت التبعيات | مخضرم، جرادل، npm، نقطة |
| **اختبار** | تشغيل الوحدة، التكامل، فحص الوبر | دعابة، بيتيست، JUnit |
| **الباقة** | إنشاء صورة أو قطعة أثرية لـ Docker | عامل الميناء، Buildpacks |
| **النشر (التدريجي)** | النشر في بيئة التدريج | كوبيرنيتيس، ECS، VM |
| **الاختبار (التدريجي)** | اختبارات التكامل، اختبارات الدخان | السيلينيوم، ساعي البريد |
| **النشر (الإنتاج)** | الافراج عن الإنتاج | الأزرق والأخضر، الكناري، المتداول |
| **المراقب** | مراقبة الصحة والأخطاء والأداء | بروميثيوس، جرافانا، داتا دوج |
### مقارنة أدوات CI/CD
| أداة | اكتب | القوة |
|------|------|----------|
| ** إجراءات جيثب ** | سحابة CI/CD | متكاملة بعمق مع جيثب. سير عمل YAML |
| **جيتلاب سي** | CI/CD مدمج | منصة واحدة للريبو + خط الأنابيب |
| **جنكينز** | CI/CD مستضاف ذاتيًا | قابل للتكوين بدرجة عالية؛ النظام البيئي المساعد الضخم |
| ** سيركل سي ** | سحابة CI/CD | سريع؛ جيدة لسير العمل في حاويات |
| **أرجو سي دي** | GitOps لـ Kubernetes | عمليات النشر التعريفية المستندة إلى Git |

## عامل الميناء والحاويات
### لماذا الحاويات؟
قبل الحاويات، كانت المشكلة التقليدية هي "أنها تعمل على جهازي". تحل الحاويات هذه المشكلة عن طريق تجميع التطبيق بكل تبعياته - المكتبات ووقت التشغيل والتكوين - في وحدة واحدة محمولة تعمل بشكل مماثل في أي مكان.
### أساسيات عامل الميناء
| المفهوم | الوصف |
|---------|------------|
| **صورة** | قالب للقراءة فقط مع تبعيات التطبيق + |
| **حاوية** | تشغيل مثيل لصورة |
| **ملف الإرساء** | وصفة لبناء الصورة |
| ** التسجيل ** | تخزين الصور (Docker Hub، ECR، GCR) |
| **الحجم** | تخزين مستمر ينجو من إعادة تشغيل الحاوية |
| **الشبكة** | طبقة شبكية معزولة للحاويات |
### أفضل ممارسات ملف Dockerfile
```dockerfile
# Use specific base image tags, not 'latest'
FROM python:3.12-slim

# Set working directory
WORKDIR /app

# Copy dependency file first (leverage Docker layer caching)
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# Copy application code
COPY . .

# Run as non-root user
USER appuser

# Expose port and define entrypoint
EXPOSE 8000
CMD ["python", "main.py"]
```

الممارسات الأساسية: استخدام الصور الأساسية/النحيفة، وتشغيلها كغير جذر، والاستفادة من التخزين المؤقت للطبقة، واستخدام `.dockerignore`، ومسح الصور بحثًا عن الثغرات الأمنية (`trivy`، و`docker scan`)، وتعيين حدود الموارد.
### عامل الميناء يؤلف
لتشغيل حاويات متعددة معًا (التطبيق + قاعدة البيانات + ذاكرة التخزين المؤقت):
```yaml
services:
  app:
    build: .
    ports: ["8000:8000"]
    depends_on: [db, redis]
    environment:
      DATABASE_URL: postgresql://user:pass@db:5432/mydb
  db:
    image: postgres:16
    volumes: [pgdata:/var/lib/postgresql/data]
  redis:
    image: redis:7-alpine
volumes:
  pgdata:
```

## كوبيرنتس (K8s)
Kubernetes هو منسق الحاويات المتوافق مع معايير الصناعة. فهو يدير نشر التطبيقات المعبأة في حاويات وتوسيع نطاقها وتشغيلها.
### البنية الأساسية
| مكون | الدور |
|-----------|------|
| **طائرة التحكم** | يدير المجموعة (خادم API، المجدول، إلخ، مدير وحدة التحكم) |
| **العقدة** | الآلة العاملة (VM أو المادية) التي تقوم بتشغيل الحاويات |
| **جراب** | أصغر وحدة قابلة للنشر؛ حاوية واحدة أو أكثر تشترك في الشبكات |
| **الخدمة** | نقطة نهاية شبكة مستقرة تقوم بتوجيه حركة المرور إلى القرون |
| **النشر** | التعريف التعريفي لحالة الجراب المرغوبة (النسخ المتماثلة، الصورة، إلخ) |
| **دخول** | قواعد توجيه HTTP لحركة المرور الخارجية |
| **خريطة التكوين/السر** | التكوين والبيانات الحساسة التي تم حقنها في القرون |
### أوامر كوبيكتل الأساسية
```bash
kubectl get pods                    # List pods
kubectl get services                # List services
kubectl describe pod <name>         # Detailed pod info
kubectl logs <pod-name>             # View pod logs
kubectl exec -it <pod> -- /bin/sh   # Shell into a pod
kubectl apply -f deployment.yaml    # Apply a manifest
kubectl rollout status deploy/myapp # Check rollout progress
kubectl scale deploy/myapp --replicas=5  # Scale to 5 replicas
```

### خوذة
Helm هو مدير الحزم في Kubernetes. **المخطط** عبارة عن حزمة من موارد Kubernetes التي تم تكوينها مسبقًا. فكر في الأمر على أنه`apt`أو`brew`لـ K8s.
```bash
helm install my-release bitnami/postgresql   # Install a chart
helm upgrade my-release bitnami/postgresql   # Upgrade
helm rollback my-release 1                   # Rollback to revision 1
helm list                                    # List releases
```

## البنية التحتية كرمز (IaC)
يتعامل IaC مع تكوين البنية التحتية بنفس الطريقة التي تتعامل بها مع كود التطبيق: حيث يتم التحكم في الإصدار واختباره ونشره عبر المسارات.
### Terraform مقابل Ansible
| أداة | اكتب | النهج | الأفضل لـ |
|------|------|----------|----------|
| **تيرافورم** | التزويد | تصريحي (HCL)؛ على أساس الدولة | إنشاء موارد سحابية (VPCs، VMs، قواعد البيانات) |
| ** غير مقبول ** | التكوين | تصريحي (YAML)؛ بلا وكيل | تكوين الخوادم وتثبيت البرامج |
| **بولومي** | التزويد | الأمر (Python، Go، TS) | الفرق التي تفضل لغات البرمجة الحقيقية |
| **تكوين السحابة** | التزويد | تعريفي (YAML/JSON)؛ AWS أصلي | البنية التحتية لـ AWS فقط |
### مثال Terraform
```hcl
provider "aws" {
  region = "us-east-1"
}

resource "aws_instance" "web" {
  ami           = "ami-0c55b159cbfafe1f0"
  instance_type = "t3.micro"

  tags = {
    Name = "web-server"
  }
}
```

أفضل الممارسات: استخدم الوحدات النمطية لإعادة الاستخدام، وقم بتخزين الحالة عن بُعد (S3 + DynamoDB للقفل)، وعدم استخدام الأسرار مطلقًا، والتحكم في الإصدار في كل شيء.

## الرصد والملاحظة
### الركائز الثلاث
| عمود | ماذا يخبرك | أدوات |
|--------|------------------|-------|
| **المقاييس** | القياسات الرقمية مع مرور الوقت (وحدة المعالجة المركزية، معدل الطلب، معدل الخطأ) | بروميثيوس، CloudWatch، Datadog |
| **السجلات** | أحداث منفصلة ذات سياق (أخطاء، طلبات، تغييرات الحالة) | ELK Stack، Loki، سجلات CloudWatch |
| **آثار** | رحلة طلب شاملة عبر الخدمات | جايجر، أشعة سينية، زيبكين |
### بروميثيوس + جرافانا ستاك
مكدس المراقبة القياسي مفتوح المصدر:
| مكون | الدور |
|-----------|------|
| ** بروميثيوس ** | قاعدة بيانات السلاسل الزمنية؛ تسحب المقاييس من الخدمات |
| **جرافانا** | التصور ولوحات المعلومات |
| ** مدير التنبيهات ** | توجيه التنبيهات إلى Slack وPagerDuty والبريد الإلكتروني |
| **مصدر العقدة** | يعرض المقاييس على مستوى النظام (وحدة المعالجة المركزية، ذاكرة الوصول العشوائي، القرص) |
| **مصدر الصندوق الأسود** | تحقيقات نقاط النهاية (HTTP، TCP، ICMP) |
### المقاييس الرئيسية التي يجب تتبعها
| الفئة | المقاييس |
|----------|--------|
| **البنية التحتية** | وحدة المعالجة المركزية، ذاكرة الوصول العشوائي، استخدام القرص، شبكة الإدخال / الإخراج |
| **التطبيق** | معدل الطلب، زمن الوصول (ص50، ص95، ص99)، معدل الخطأ |
| **قاعدة البيانات** | عدد الاستعلامات، الاستعلامات البطيئة، استخدام تجمع الاتصال |
| **الأعمال** | الاشتراكات والتحويلات والإيرادات |

## جيتوبس
يأخذ GitOps IaC إلى نهايته المنطقية: مستودع Git هو المصدر الوحيد للحقيقة للحالة المرغوبة للبنية التحتية والتطبيقات الخاصة بك.
| المبدأ | الوصف |
|-----------|------------|
| **تصريحي** | كل شيء موصوف بالرمز (YAML، HCL) |
| **النسخة** | جيت هو مصدر الحقيقة |
| **آلي** | تعمل الأدوات باستمرار على التوفيق بين الحالة المطلوبة والحالة الفعلية |
| **قابل للتدقيق** | كل تغيير هو التزام Git |
**ArgoCD** و **Flux** هما أدوات GitOps الرائدة لـ Kubernetes. يمكنك دفع التغيير إلى Git repo الخاص بك، وتقوم الأداة تلقائيًا بنشره على المجموعة.

## الاستجابة للحوادث
عندما ينكسر شيء ما في الساعة 3 صباحًا:
1. **الإقرار** بالتنبيه.
2. **تقييم النطاق**: ما هي الخدمات والمستخدمين والبيانات المتأثرة؟
3. **حدد** السبب الجذري — تحقق من السجلات والمقاييس وعمليات النشر الأخيرة.
4. **تحتوي على** إن أمكن — قواطع الدائرة، وأعلام الميزات، وتحويل حركة المرور.
5. **الإصلاح** — التراجع أو التصحيح للأمام.
6. **التواصل** — قم بتحديث أصحاب المصلحة والمستخدمين (صفحة الحالة).
7. **بعد الوفاة** — في غضون 24 إلى 48 ساعة، قم بتوثيق السبب الجذري وعناصر الإجراء.
الهدف ليس فقط حل الحادث ولكن ضمان عدم تكرار نفس الحادث.
