# تصميم واجهة برمجة التطبيقات والهندسة المعمارية
API (واجهة برمجة التطبيقات) هي الطريقة التي تتواصل بها مكونات البرنامج مع بعضها البعض. تعتبر واجهة برمجة التطبيقات (API) المصممة جيدًا بديهية ومتسقة ويسعد العمل معها. التصميم السيئ يسبب الارتباك والأخطاء والإحباط. يغطي هذا الملف المبادئ والأنماط والممارسات الخاصة ببناء واجهات برمجة التطبيقات التي يرغب المطورون في استخدامها بالفعل.
---

## مبادئ REST API
REST (نقل الحالة التمثيلية) هو النمط المعماري السائد لواجهات برمجة تطبيقات الويب. فهو يتعامل مع البيانات باعتبارها **موارد** محددة بواسطة عناوين URL، ويستخدم أساليب HTTP للعمل عليها.
### المبادئ الأساسية
| المبدأ | الوصف |
|-----------|------------|
| **الموارد** | كل شيء عبارة عن مورد له URI (`/users/123`,`/orders/456`) |
| **طرق HTTP** | الحصول على (قراءة)، نشر (إنشاء)، وضع (استبدال)، تصحيح (تحديث جزئي)، حذف (إزالة) |
| **انعدام الجنسية** | يحتوي كل طلب على جميع المعلومات المطلوبة؛ لا توجد حالة جلسة من جانب الخادم |
| **واجهة موحدة** | تسمية الموارد المتسقة، والأساليب القياسية، ورموز الحالة القياسية |
| **التمثيل** | يمكن تمثيل الموارد بتنسيقات متعددة (JSON، XML) |
### اصطلاحات تسمية الموارد
| افعل | لا |
|----|-------|
| `/users`(اسم الجمع) | `/user`(مفرد) |
| `/users/123/orders`(متداخل) | `/getOrdersForUser?id=123`|
| `/products?category=electronics`(معلمات الاستعلام للتصفية) | `/productsByCategory/electronics`|
| استخدم الواصلات:`/user-profiles`| استخدم الشرطة السفلية:`/user_profiles`|
### أساليب HTTP والعجز
| الطريقة | الغرض | عاجز؟ | آمن؟ |
|--------|---------|-------------|-------|
| ** احصل على ** | اقرأ المصدر | ✅ نعم | ✅ نعم |
| ** مشاركة ** | إنشاء مورد | ❌ لا | ❌ لا |
| **ضع** | استبدال مورد بالكامل | ✅ نعم | ❌ لا |
| **التصحيح** | تحديث مورد جزئيًا | ❌ لا* | ❌ لا |
| **حذف** | إزالة مورد | ✅ نعم | ❌ لا |
* يمكن جعل التصحيح ضعيفًا من خلال التصميم الدقيق.
### رموز حالة HTTP
| الكود | معنى | متى تستخدم |
|------|---------|-------------|
| **200** | موافق | تم الحصول على النجاح ووضعه وتصحيحه وحذفه |
| **201** | تم الإنشاء | مشاركة ناجحة (تم إنشاء المورد) |
| **204** | لا يوجد محتوى | تم الحذف بنجاح (لا يوجد شيء للعودة) |
| **400** | طلب سيء | إدخال غير صالح أو طلب مشوه |
| **401** | غير مصرح به | المصادقة مفقودة أو غير صالحة |
| **403** | ممنوع | تمت المصادقة عليه ولكن غير مصرح به |
| **404** | لم يتم العثور عليه | المورد غير موجود |
| **409** | الصراع | تكرار المورد أو تعارض الدولة |
| **422** | كيان غير قابل للمعالجة | JSON صالح ولكن هناك أخطاء دلالية |
| **429** | طلبات كثيرة جدًا | تم تجاوز حد المعدل |
| **500** | خطأ داخلي في الخادم | خطأ غير متوقع في الخادم |
| **502** | بوابة سيئة | فشل خدمة المنبع |
| **503** | الخدمة غير متاحة | التحميل الزائد المؤقت أو الصيانة |

## إصدار واجهة برمجة التطبيقات
تتطور واجهات برمجة التطبيقات. عندما تحتاج إلى إجراء تغييرات جذرية، فإن إصدار الإصدار يسمح للعملاء الحاليين بمواصلة العمل.
| استراتيجية | مثال | الايجابيات | سلبيات |
|----------|--------|------|------|
| ** مسار URL ** | `/v1/users`,`/v2/users`| بسيطة وصريحة | تغييرات URL لكل إصدار |
| **معلمة الاستعلام** | `/users?version=2`| مرنة | من السهل أن تنسى |
| **الرأس** | `Accept: application/vnd.myapi.v2+json`| عناوين URL النظيفة | أقل قابلية للاكتشاف |
| ** لا يوجد إصدار ** | تطور المخطط فقط | أبسط | التغييرات العاجلة تؤثر على الجميع |
**أفضل الممارسات**: استخدم إصدار مسار URL (`/v1/`) للتوضيح. دعم إصدار سابق واحد على الأقل. إهمال الإصدارات القديمة بجداول زمنية واضحة.

## طرق المصادقة
| الطريقة | كيف يعمل | الأفضل لـ |
|--------|------------|----------|
| **مفاتيح واجهة برمجة التطبيقات** | المفتاح السري في الرأس (`X-API-Key: abc123`) | خادم إلى خادم، عمليات تكامل بسيطة |
| **OAuth2** | التفويض القائم على الرمز المميز مع النطاقات | وصول طرف ثالث، التطبيقات المصرح بها من قبل المستخدم |
| **جوت** | رمز قائم بذاته مع المطالبات | المصادقة عديمة الحالة عبر الخدمات |
| **المصادقة الأساسية** | اسم المستخدم المشفر بـ Base64: كلمة المرور | التطوير فقط — لا يتم الإنتاج مطلقًا بدون TLS |
| **ملفات تعريف الارتباط للجلسة** | معرف الجلسة من جانب الخادم في ملف تعريف الارتباط HTTP فقط | تطبيقات الويب التقليدية |
### تدفق OAuth2 (مبسط)
1. يقوم العميل بإعادة توجيه المستخدم إلى خادم الترخيص.
2. يقوم المستخدم بتسجيل الدخول ويمنح الإذن.
3. يقوم خادم التفويض بإرجاع رمز التفويض.
4. يقوم العميل بتبادل رمز الوصول (ورمز التحديث اختياريًا).
5. يستخدم العميل رمز الوصول لاستدعاء واجهة برمجة التطبيقات.
6. عند انتهاء صلاحية رمز الوصول، استخدم رمز التحديث للحصول على رمز جديد.

## أنماط واجهة برمجة التطبيقات: REST vs GraphQL vs gRPC
| ميزة | راحة | الرسم البيانيQL | جي آر بي سي |
|---------|------|---------|------|
| **تنسيق البيانات** | JSON (عادة) | جيسون | بروتوبوف (ثنائي) |
| **نقاط النهاية** | متعددة (واحد لكل مورد) | نقطة نهاية واحدة | تم تحديده بواسطة ملف .proto |
| ** الجلب الزائد ** | شائع (الحصول على أكثر من الحاجة) | لا شيء (يحدد العميل الحقول) | لا شيء (محدد بالمخطط) |
| ** نقص الجلب ** | يتطلب مكالمات متعددة | لا شيء (احصل على ما هو مطلوب بالضبط) | لا شيء |
| ** في الوقت الحقيقي ** | مطلوب WebSockets | الاشتراكات المضمنة | الجري المدمج في |
| ** التخزين المؤقت ** | يعمل التخزين المؤقت لـ HTTP بشكل طبيعي | أصعب للتخزين المؤقت | محدودة |
| **منحنى التعلم** | منخفض | متوسطة | متوسطة – عالية |
| **الأفضل لـ** | واجهات برمجة التطبيقات العامة وتطبيقات CRUD | واجهات المستخدم المعقدة، تطبيقات الهاتف المحمول | خدمات صغيرة داخلية، عالية الأداء |

## ترقيم الصفحات والتصفية والفرز
بالنسبة لنقاط النهاية التي تُرجع القوائم:
| تقنية | مثال | متى تستخدم |
|-----------|--------|-------------|
| **الإزاحة/الحد** | `?offset=20&limit=10`| بسيط؛ يعمل لمجموعات البيانات الصغيرة |
| ** القائم على المؤشر ** | `?cursor=abc123&limit=10`| مجموعات بيانات كبيرة؛ نتائج متسقة |
| ** مجموعة المفاتيح ** | `?created_after=2024-01-01&limit=10`| فعال جداً؛ يتطلب مفتاحًا فريدًا |
```json
// Cursor-based response
{
  "data": [...],
  "pagination": {
    "next_cursor": "abc123",
    "has_more": true
  }
}
```

## الحد من المعدل
قم بحماية واجهة برمجة التطبيقات (API) الخاصة بك من سوء الاستخدام وتأكد من الاستخدام العادل.
| استراتيجية | كيف يعمل |
|----------|------------|
| **نافذة ثابتة** | عدد N من الطلبات لكل نافذة زمنية (على سبيل المثال، 100/ساعة) |
| **نافذة منزلقة** | أكثر تفصيلاً؛ بحساب الطلبات في النافذة المتداول |
| **دلو الرمز** | الرموز المضافة بسعر ثابت؛ كل طلب يستهلك رمزًا مميزًا |
إرجاع`429 Too Many Requests`مع الرؤوس:```
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1625097600
Retry-After: 60
```

## معالجة الأخطاء
تجعل استجابات الأخطاء المتسقة واجهات برمجة التطبيقات أسهل بكثير في العمل معها:
```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Invalid input data",
    "details": [
      {
        "field": "email",
        "issue": "Invalid email format"
      }
    ]
  }
}
```

**المبادئ**: استخدام بنية أخطاء متسقة، وتضمين رسائل قابلة للتنفيذ، واستخدام رموز حالة HTTP القياسية، وتسجيل الأخطاء من جانب الخادم باستخدام معرفات الارتباط، وعدم الكشف مطلقًا عن آثار المكدس أو التفاصيل الداخلية.

## وثائق واجهة برمجة التطبيقات
| أداة | الوصف |
|------|------------|
| ** واجهة برمجة التطبيقات المفتوحة (Swagger) ** | معيار الصناعة لوثائق REST API |
| ** واجهة مستخدم Swagger ** | وثائق واجهة برمجة التطبيقات التفاعلية من مواصفات OpenAPI |
| ** ساعي البريد ** | اختبار API والتوثيق ومشاركة المجموعة |
| **إعادة** | مستندات مرجعية جميلة لواجهة برمجة التطبيقات (API) من مواصفات OpenAPI |
| **ملعب GraphQL / GraphiQL** | استكشاف GraphQL التفاعلي |
**أفضل الممارسات**: اكتب مواصفات OpenAPI أولاً (تطوير يعتمد على المواصفات)، ثم قم بإنشاء الوثائق وحزم SDK للعميل منها.

## أنماط بوابة API
تقع بوابة API بين العملاء والخدمات الخلفية، مما يوفر نقطة دخول واحدة.
| المسؤولية | الوصف |
|---------------|-------------|
| **التوجيه** | الطلبات المباشرة إلى الخدمات الخلفية المناسبة |
| **المصادقة** | التحقق من صحة الرموز المميزة على مستوى البوابة |
| ** تحديد المعدل ** | تطبيق الحدود العالمية أو لكل عميل |
| **التحول** | التحويل بين البروتوكولات (REST ↔ gRPC) |
| ** التخزين المؤقت ** | ذاكرة التخزين المؤقت الاستجابات المشتركة |
| **الرصد** | التسجيل والمقاييس المركزية |
| **موازنة التحميل** | توزيع حركة المرور عبر مثيلات الخدمة |
| أداة | اكتب |
|------|------|
| **كونج** | بوابة API مفتوحة المصدر (معتمدة على Nginx) |
| ** بوابة AWS API ** | مُدار بالكامل ومتكامل مع AWS |
| **إدارة Azure API** | بوابة مُدارة مع بوابة المطور |
| **المبعوث/إستيو** | شبكة الخدمة مع إمكانيات بوابة API |
| **ترافيك** | الاكتشاف التلقائي، دعونا نقوم بالتشفير |

## خطافات الويب
تسمح خطافات الويب لواجهة برمجة التطبيقات (API) الخاصة بك بإرسال الأحداث إلى العملاء في الوقت الفعلي، بدلاً من جعل العملاء يستطلعون التغييرات.
| الجانب | أفضل الممارسات |
|--------|-------------|
| **التوصيل** | طلب POST مع حمولة JSON إلى عنوان URL الخاص بالعميل |
| **الأمن** | تسجيل الحمولات باستخدام HMAC؛ يتحقق العميل من التوقيع |
| **الموثوقية** | أعد محاولة عمليات التسليم الفاشلة مع التراجع الأسي |
| **العجز** | تضمين معرف الحدث الفريد؛ يعالج العميل التكرارات |
| **الإصدار** | قم بتضمين إصدار API في حمولة webhook |

## قائمة مراجعة التصميم
- [ ] Resources عبارة عن أسماء جمع (`/users`، وليس`/getUser`)
- [ ] استخدام أساليب HTTP بشكل صحيح (GET للقراءات، وPOST للإنشاء، وما إلى ذلك)
- [ ] تنسيق الاستجابة للأخطاء المتسق
- [ ] ترقيم الصفحات لجميع نقاط نهاية القائمة
- [ ] تحديد المعدل برؤوس واضحة
- [ ] تم تحديد إستراتيجية إصدار واجهة برمجة التطبيقات (API).
- [ ] المصادقة والترخيص ساري المفعول
- [ ] التحقق من صحة الإدخال على كافة نقاط النهاية
- [ ] تمت المحافظة على وثائق OpenAPI/Swagger
- [ ] تم تكوين CORS بشكل صحيح
- [ ] فرض HTTPS في الإنتاج
- [ ] مفاتيح العجز لعمليات POST عند الحاجة
