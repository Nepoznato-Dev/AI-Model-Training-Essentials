# ML 工程和 MLOps
建構機器學習模型只是成功的一半。將其投入生產、保持其可靠運作、監控漂移並對其進行迭代——這就是 ML 工程和 MLOps 的用武之地。該文件涵蓋了從實驗到生產系統的整個生命週期。
---

## 機器學習生命週期
|相|描述 |主要活動|
|--------|-------------|---------------|
| **1.問題定義** |將業務問題建構成 ML 任務 |定義指標、限制、成功標準 |
| **2.資料收集** |收集並標記訓練資料 | ETL、標籤、增強 |
| **3.實驗** |訓練與評估模型 |特徵工程、超參數調整 |
| **4.型號選擇** |選擇最佳型號 |比較指標，評估權衡 |
| **5.部署** |將模型交付生產 |服務基礎設施、API、批量 |
| **6。監控** |注意漂移與退化 |資料漂移、概念漂移、效能 |
| **7.再培訓** |使用新資料更新模型 |規劃或觸發的再培訓 |
大部分價值（和難度）都在第 5-7 階段。 Jupyter 筆記本中的模型不會創造商業價值。

## 模型服務模式
|图案|描述 |延迟 |使用案例|
|--------|-------------|---------|---------|
| **批量推理** |按計劃對一批數據運行模型 |營業時間 |每日推薦、欺詐評分 |
| **線上推理** |根據請求進行即時預測 |毫秒 |搜尋排名，即時分類 |
| **串流推理** |對資料流的處理預測 |秒|異常偵測、事件處理 |

|工具|類型 |最適合 |

| **TensorFlow 服務** |模型伺服器| TensorFlow 模型 |

| **Triton 推理伺服器** |多框架| GPU 推理，多種框架 |
| **vLLM** |法學碩士服務|高通量LLM推理|

| **雷發球** |可擴展的服務 |大型模型、分佈式推理 |

## 模型註冊表
模型登錄是用於管理 ML 模型（模型的版本、元資料、指標和部署狀態）的集中儲存。
|能力|描述 |
|------------|-------------|
| **版本控制** |使用唯一 ID 追蹤每個模型版本 |
| **元資料** |訓練資料、超參數、指標、作者 |
| **階段轉換** |通過階段移動模型：暫存 → 生產 → 檔案 |
| **血統** |追蹤哪些資料和程式碼產生了每個模型 |
|工具|描述 |
|------|-------------|
| **MLflow** |開源；模型註冊+實驗追蹤|
| **權重與偏差 (W&B)** |商業的;實驗追蹤+模型註冊|
| **DVC** |使用 Git 進行資料與模型版本控制 |
| **Azure ML / SageMaker** |雲端原生模型管理 |

## 實驗跟踪
每個機器學習實驗都應該被追蹤：使用了哪些數據、哪些超參數、產生了哪些指標。
|工具|主要特點|
|------|-------------|
| **MLflow** |開源、自架、追蹤參數/指標/工件 |
| **W&B** |豐富的 UI、掃描、工件版本控制、報表 |
| **海王星** | MLOps 的元資料儲存 |
| **張量板** |內建於 TensorFlow 中；視覺化訓練曲線 |
### 追蹤什麼
|類別 |範例 |
|----------|---------|
| **參數** |學習率、批次大小、模型架構、紀元數 |
| **指標** |準確率、損失、F1、AUC-ROC（每個 epoch 和最終）|
| **文物** |模型權重、混淆矩陣、預測樣本 |
| **資料** |資料集版本、分割比、預處理步驟 |
| **環境** | Python 版本、函式庫版本、硬體 |

## 模型部署策略
|戰略|它是如何運作的 |風險|
|----------|-------------|------|
| **影子部署** |新模式與舊模式並行；預測已進行比較但未實現 |零風險；上線前驗證 |
| **金絲雀發布** |將小部分流量路由至新模型；逐漸增加|風險低；快速回滾|
| **A/B 測試** |將使用者分為新舊用戶；比較業務指標|衡量實際影響 |
| **藍綠** |兩個相同的環境；一次切換所有流量 |即時回滾；轉型期間的雙重成本|
| **功能標誌** |依使用者細分開啟/關閉模型 |細微控制 |

## 監控機器學習系統
機器學習系統比傳統軟體需要更多的監控，因為資料本身可能會改變。
### 漂移的類型
|漂移類型|有何變化？範例|
|------------|-------------|---------|
| **資料漂移** |輸入分配變化|行銷活動後客戶人口統計資料變更 |
| **概念漂移** |輸入輸出變化關係|經濟衰退期間消費者行為改變|
| **標籤漂移** |目標分佈變化|詐欺率從 1% 上升至 5% |
### 監控什麼
|類別 |指標|
|----------|---------|
| **模型性能** |準確率、精確率、召回率、F1、AUC（與基線相比）|
| **資料品質** |缺失值、特徵分佈、異常值 |
| **漂移偵測** |統計檢定（KS 檢定、PSI、KL 散度）|
| **基礎設施** |延遲、吞吐量、GPU 使用率、記憶體 |
| **業務指標** |轉換率、收入影響、用戶滿意度 |
### 監控工具
|工具|類型 |
|------|------|
| **顯然是人工智慧** |開源資料漂移和模型效能監控 |
| **格拉法納** |儀表板視覺化（與 Prometheus 搭配使用）|
| **為什麼實驗室** |資料可觀測平台|
| **阿里茲** |機器學習可觀察性與根本原因分析 |
| **普羅米修斯 + Grafana** |基礎設施和應用程式指標|

## 可重複的培訓
可重複性意味著您可以重新運行實驗並獲得相同的結果。它對於調試、審核和合規性至關重要。
＃＃＃ 要求
|要求 |如何實現？
|------------------------|--------------------|
| **資料版本控制** | DVC、Delta Lake 或帶有雜湊值的資料集快照 |
| **代碼版本控制** |所有培訓代碼的 Git |
| **環境固定** |`requirements.txt`、`conda env`、具有確切版本的 Docker 映像 |
| **播種** |修復 numpy、torch、tensorflow 的隨機種子 |
| **設定管理** |所有超參數的 Hydra、OmegaConf 或 YAML 設定 |
| **文物追蹤** | MLflow 或 W&B 記錄每個實驗 |
---

## 縮放推理
當模型每天需要處理數百萬個請求時，效能就很重要。
|技術|描述 |
|------------|-------------|
| **批次** |將多個請求分組到單一前向傳遞 |
| **量化** |降低模型精確度（FP32 → INT8 或 INT4）以加快推理速度 |
| **模型蒸餾** |訓練較小的模型來模仿較大的模型 |
| **修剪** |刪除不重要的權重或神經元 |
| **快取** |快取頻繁的預測以避免重新計算 |
| **GPU 最佳化** | TensorRT、ONNX 執行時間、Flash 注意 |
| **水平縮放** |在負載平衡器後面執行多個模型副本 |

## ML 的功能標誌
功能標誌可讓您控制哪個模型版本為哪些使用者提供服務，而無需重新部署。
|使用案例|描述 |
|----------|-------------|
| **逐步推出** |向 5% 的用戶提供新模型，然後增加 |
| **終止開關** |如果偵測到問題，立即恢復到先前的模型 |
| **基於細分** |不同的機型適合不同的用戶群|
| **實驗** |具有業務指標的 A/B 測試模型變體 |
工具：LaunchDarkly、Unleash、Flagsmith 或簡單的資料庫支援的功能標誌。

## MLOps 成熟度曲線
|水平|特點 |
|--------|----------------|
| **0 級 — 手動** |手動訓練、手動部署、無監控 |
| ** 1 級 — 實驗** |實驗追蹤、模型註冊、基本 CI |
| **2 級 — 自動化** |自動再訓練、模型 CI/CD、自動化測試 |
| **3 級 — 完整管道** |具有監控、漂移檢測和自動重新訓練功能的端到端自動化管道 |
大多數組織處於 0 級和 1 級之間。目標是 2-3 級，其中 ML 生命週期是自動化和自我修復的。
