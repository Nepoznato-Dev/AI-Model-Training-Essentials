# API 設計和整合失敗
API（應用程式介面）是現代軟體的結締組織－它們讓服務進行通信，讓第三方集成，讓團隊獨立工作。當 API 設計出錯時，後果會波及到依賴它的每個系統：整合中斷、安全漏洞、開發人員沮喪以及代價高昂的重寫。整合故障（系統無法可靠地通訊）是生產事件最常見的來源之一。
---

## 常見的 API 設計失敗
### 設計錯誤
|錯誤|描述 |後果|
|---------|-------------|----------|
| **命名不一致** |`/getUsers`與`/list_users`與`/fetch-users`|困惑;錯誤；發展緩慢|
| **過載端點** |一個端點根據參數執行 10 項不同的操作 |難以理解；難以測試；很難改變|
| **取得不足** |客戶端需要呼叫5次API才能取得相關資料 |慢的;浪費；複雜的客戶端程式碼|
| **過度取得** |當客戶端只需要 2 個時 API 傳回所有欄位 |浪費頻寬；移動速度慢；安全風險（暴露不必要的資料）|
| **無版本控制** |在沒有警告的情況下部署重大變更 |客戶中斷；憤怒的開發商|
| **含糊的錯誤訊息** | “錯誤 500：內部伺服器錯誤”，沒有詳細資料 |無法偵錯；解析度慢|
| **缺少分頁** |端點傳回所有記錄（可能是數百萬筆）|逾時；記憶力耗盡；崩潰的客戶端|
| **狀態代碼不一致** | 200 OK 表示錯誤；客戶錯誤 500 |客戶無法區分成功與失敗|
### REST API 反模式
|反模式 |描述 |更好的方法|
|----------|-------------|-----------------|
| **使用 GET 進行突變** |`GET /delete-user?id=5`|使用刪除方法 |
| **使用 POST 處理所有事情** | `POST /get-users`;`POST /update-user`|使用適當的 HTTP 方法（GET、POST、PUT、PATCH、DELETE） |
| **從 API 返回 HTML** | API 返回 HTML 片段 |返回 JSON；讓客戶端渲染 |
| **URL 中的業務邏輯** |`/users/active/premium/from-2023`|使用查詢參數或請求正文進行複雜過濾器 |
| **公開資料庫架構** |`/api/table_name/column`|圍繞資源和領域概念而不是表格設計 API |
| **沒有 HATEOAS / 連結** |客戶端硬編碼所有 URL |在回覆中包含相關資源的連結 |

## 安全失敗
### 常見 API 漏洞
|漏洞|描述 |範例|
|--------------|-------------|---------|
| **身份驗證被破壞** | API 無法正確驗證身份 |缺少令牌驗證；接受過期令牌 |
| **過多的資料暴露** | API 傳回的資料多於客戶端需求 |用戶端點回傳密碼雜湊值和內部 ID |
| **集體作業** |客戶可以設定不應該設定的欄位 |`PATCH /user`允許設定`role: "admin"`|
| **注射** |使用者輸入解釋為程式碼 | SQL注入；NoSQL 注入；指令注入|
| **IDOR**（不安全的直接物件參考）|透過改變URL中的ID來存取資源| `/api/users/5`→換成`/api/users/6`看別人的資料|
| **缺少速率限制** | API呼叫無限制|蠻力；拒絕服務；刮|
| **CORS 設定錯誤** |過於寬鬆的跨網域存取 | 經過驗證的端點上的`Access-Control-Allow-Origin: *`|
### 身份驗證和授權失敗
|失敗|描述 |影響 |
|--------|-------------|--------|
| **硬編碼憑證** |原始程式碼中的 API 金鑰或密碼 |透過版本控制外洩；所有開發人員均可使用|
| **無令牌過期** |令牌永不過期 |被盜的令牌可提供永久存取權限 |
| **弱密鑰** |簡短或可預測的簽名密鑰 |代幣可以偽造 |
| **無範圍/權限** |所有代幣都具有完全存取權限 |受損的令牌 = 完全系統存取權 |
| **記錄敏感資料** |日誌中的令牌或密碼 |具有日誌存取權限的任何人都可以存取 |
| **授權不一致** |某些端點檢查權限；其他人則不然 |透過不受保護的端點進行未經授權的存取 |

## 整合失敗
### 分散式系統整合問題
|失敗|描述 |範例|
|---------|-------------|---------|
| **緊密耦合** |服務之間相互依賴內部實作細節 |更改一項服務的資料庫會破壞其他三項服務 |
| **同步鏈** |服務A呼叫B呼叫C呼叫D；延遲累積| 200ms + 300ms + 500ms = 1 秒回應時間 |
| **無斷路器** |服務失敗導致級聯故障 |服務D慢；所有上游服務都耗盡了等待的線程|
| **沒有重試邏輯** |暫時性故障變成永久性故障 |網路訊號=交易失敗；使用者必須手動重試 |
| **重試次數過多** |沒有回退的重試壓倒了恢復服務|雷霆羊群問題|
| **無冪等性** |重試非冪等操作會建立重複項 |兩次付款；訂單建立兩次 |
| **最終一致性驚喜** |客戶端在寫入後讀取陳舊資料 |使用者更新個人資料；刷新頁面；舊資料仍顯示 |
### 第三方整合失敗
|失敗|描述 |緩解措施 |
|--------|-------------|------------|
| **供應商 API 更改** |第三方更改其 API，恕不另行通知 |版本固定；抽象層；監控供應商變更日誌|
| **速率限制** |第三方限制您的請求 |快取；請求排隊；談判更高的限制|
| **供應商停機** |第三方服務無法使用 |斷路器；後備行為；多供應商策略|
| **資料格式變更** |第三方變更回應格式 |模式驗證；轉換圖層；格式變更警報 |
| **不帶遷移路徑的棄用** |供應商棄用沒有等效項的端點 |隨時了解情況；保持抽象；儘早計劃遷移|

## 案例研究
### 案例研究 1：傳回所有內容的 API
|方面|描述 |
|--------|-------------|
| **場景** |某SaaS公司的用戶API傳回所有用戶字段，包括內部元資料 |
| **出了什麼問題** |無欄位過濾；回應包括密碼雜湊、內部註解和管理標誌 |
| **影響** |安全研究人員發現了這一漏洞；公開披露； GDPR 調查 |
| **根本原因** | API序列化整個資料庫模型，無需過濾 |
| **修復** |明確的回應模型；現場級存取控制；所有端點的安全審查|
| **課程** |切勿直接透過 API 公開您的資料庫模型；使用DTO（資料傳輸物件）|
### 案例研究 2：級聯故障
|方面|描述 |
|--------|-------------|
| **場景** |具有同步服務間通訊的微服務架構 |
| **出了什麼問題** |一項服務經歷了資料庫速度減慢；上游服務等待回應；線程池已耗盡|
| **影響** |系統完全停駛45分鐘；所有受影響的服務|
| **根本原因** |無斷路器；沒有逾時；同步依賴鏈|
| **修復** |斷路器；超時；盡可能進行非同步通訊；艙壁|
| **課程** |服務之間的同步呼叫會造成脆弱的鏈條；失敗設計|

## 最佳實踐
### API 設計清單
|面積 |實踐|
|------|----------|
| **命名** |使用名詞來表示資源；操作的 HTTP 方法；一致的命名約定|
| **版本控制** |從第一天開始的版本；使用 URL 版本控制 (`/v1/`) 或標頭版本控制 |
| **分頁** |始終對清單端點進行分頁；對大型資料集使用基於遊標的分頁
| **錯誤處理** |一致的錯誤格式；包含錯誤代碼；提供可操作的訊息|
| **速率限制** |實施速率限制；返回 429 並帶有 retry-after 標頭 |
| **冪等性** |支援突變端點的冪等鍵 |
| **文檔** | OpenAPI / Swagger 規範；保持更新；提供範例 |
| **測試** |合約測試；整合測試；消費者驅動的契約測試|
| **監控** |追蹤延遲；錯誤率；吞吐量；依賴性健康 |
| **棄用** |提前宣布棄用；提供遷移指南|
---

＃＃ 概括
API 設計失敗的範圍從表面性的（命名不一致）到災難性的（安全漏洞、級聯故障）。最常見的設計錯誤——端點過載、過度獲取、缺少分頁、模糊錯誤——使得 API 難以使用和維護。安全故障——身份驗證失效、IDOR、大規模分配、過多的資料暴露——使系統容易受到攻擊。整合故障——緊密耦合、同步鏈、缺少斷路器、無冪等性——會創造出脆弱的系統，其中一個故障會跨服務級聯。第三方整合增加了外部風險：API 變更、速率限制和供應商停機。預防策略很完善：使用明確的反應模型；從第一天開始的版本；實施斷路器和超時；冪等性設計；驗證和清理所有輸入；監控一切；並將 API 合約視為具有約束力的協議，需要協調才能更改。最好的 API 都是乏味的——可預測、一致、文件齊全且能夠抵禦故障。
