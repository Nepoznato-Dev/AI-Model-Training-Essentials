# 資料管道和 ETL 失敗
資料管道是現代組織的管道——它們透過轉換將資料從來源系統轉移到資料庫、倉庫和湖泊中，用於分析、機器學習和決策。當他們工作時，沒有人注意到。當它們失敗時，決策會基於陳舊的數據，模型會基於垃圾進行訓練，報告會顯示不可能的數字，並且對整個數據平台的信任也會受到削弱。資料管道故障是技術組織中最常見、成本最高的故障之一。
---

## 常見故障模式
### 資料品質問題
|失敗|描述 |影響 |偵測難度|
|--------|-------------|--------|------------------------|
| **靜默資料損壞** |資料被錯誤修改，沒有引發任何錯誤 |下游系統信任不良資料；基於虛假資訊的決策|非常困難－沒有錯誤訊號|
| **架構漂移** |來源系統變更架構（新增、刪除、重新命名列）|管道中斷或默默丟棄資料 |中 - 管道可能會失敗或產生部分結果 |
| **資料類型不符** |來源在需要整數的地方發送字串；浮動精度變化 |管道故障；資料被截斷；舍入誤差 |中 — 可能會導致管道錯誤或微妙的資料問題 |
| **重複記錄** |同一事件被處理多次 |誇大的計數；不正確的聚合 |困難 — 每筆記錄看起來單獨有效 |
| **空值/缺失值** |預期欄位為空 |計算失敗；模型產生錯誤的預測|中 — 取決於 null 處理 |
| **超出範圍的值** |超出預期範圍的值（負年齡；未來日期）|統計資料有偏差；破碎的業務邏輯|中 — 需要驗證規則 |
| **遲到的資料** |處理視窗關閉後資料到達 |結果不完整；錯過的記錄|很難－結果看起來很完整，但實際上並非如此 |
### 管道基礎設施問題
|失敗|描述 |影響 |
|--------|-------------|--------|
| **編排失敗** |調度程序（Airflow、Prefect）不會觸發管道 |資料陳舊；沒有處理發生 |
| **資源耗盡** |管道耗盡記憶體、CPU 或磁碟 |管道崩潰；部分結果 |
| **依賴失敗** |上游系統宕機或速度緩慢 |管道無限期等待或失敗 |
| **並發問題** |多個管道同時修改相同的資料 |比賽條件；資料損壞|
| **配置漂移** |環境變化（網路、憑證、端點）未反映在管道中 |管道意外失敗 |
| **背壓** |資料到達速度快於管道處理速度 |排隊人數不斷增加；增加延遲|

## 案例研究
### 案例研究 1：靜默資料複製
|方面|描述 |
|--------|-------------|
| **場景** |一家電子商務公司的訂單管道處理訊息佇列中的事件 |
| **出了什麼問題** |消費者重啟導致訊息被重新消費；不存在重複資料刪除邏輯|
| **影響** |在沒有人注意到之前，收入數字在三週內被誇大了 15% |
| **根本原因** |無冪等鍵；至少一次交付，無需重複資料刪除 |
| **修復** |新增基於訂單ID的冪等鍵；實作一次性語意 |
| **課程** |至少一次投遞需要重複資料刪除；始終根據來源系統驗證總計 |
### 案例研究 2：架構變更破壞下游
|方面|描述 |
|--------|-------------|
| **場景** |付款提供者更改其 API 回應中的欄位名稱 |
| **出了什麼問題** | ETL 管道默默地開始寫入空值；沒有架構驗證 |
| **影響** |財務報告顯示該支付方式的收入連續兩個月為零 |
| **根本原因** |攝取時無需模式驗證；空值被視為有效 |
| **修復** |新增了帶有警報的模式驗證；強制執行必填欄位；空白檢查 |
| **課程** |永遠不要相信外部模式會保持穩定；在邊界處驗證 |
### 案例研究 3：時區災難
|方面|描述 |
|--------|-------------|
| **場景** |一家跨國公司匯總各個辦事處的每日指標 |
| **出了什麼問題** |一些來源使用 UTC，其他來源使用本地時間；管道未正常化|
| **影響** |每日總計不符；一些交易在錯誤的日期計算；月末結算錯誤 |
| **根本原因** |無標準時區政策；時間戳存儲不一致 |
| **修復** |所有時間戳記均儲存為 UTC；僅在表示層轉換為本機時間|
| **課程** |各地都採用 UTC 標準化；明確每個邊界的時區 |

## 預防策略
### 資料驗證
|戰略|描述 |工具範例 |
|----------|-------------|----------------|
| **架構驗證** |驗證每個階段的資料是否符合預期模式 |遠大的期望；迪曲；蘇打水|
| **範圍檢查** |值落在預期範圍內 |自訂斷言； DBT 測試 |
| **新鮮度檢查** |資料是最新的，足夠有用 |監控時間戳； SLA 警報 |
| **數量檢查** |行數在預期範圍內 |行計數異常檢測 |
| **參照完整性** |外鍵匹配；沒有孤兒記錄| SQL 約束；資料品質工具|
| **跨來源對帳** |來源與目標之間的總計配對 |自動對帳作業 |
### 管道設計模式
|圖案|描述 |效益 |
|---------|-------------|---------|
| **冪等性** |多次運行管道會產生相同的結果 |可以安全重試；沒有重複|
| **原子性** |管道要麼完全成功，要麼完全失敗（無部分狀態）|沒有半處理的資料 |
| **檢查點** |保存每個階段的進度；從上一個檢查點恢復 |容錯；無需再處理|
| **死信佇列** |失敗的記錄將進入單獨的隊列進行調查 |無資料遺失；可以調查和重播|
| **斷路器** |當下游故障時停止處理 |防止級聯故障|
| **資料合約** |生產者與消費者之間關於資料格式的協定|協調架構變更 |
### 監控和警報
|監控什麼？為什麼 |如何|
|----------------|-----|-----|
| **管道持續時間** |持續時間增加表示存在問題趨勢分析； SLA 追蹤 |
| **行數** |突然的變化預示著問題|與歷史平均水準比較|
| **零利率** |增加空值訊號模式或來源問題 |列級 null 追蹤 |
| **數據新鮮度** |過時的數據意味著管道未運行 |最新記錄時間戳|
| **下游影響** |報告和模型是否使用正確的資料？ |端對端資料沿襲|
| **資源使用** |中央處理器;記憶;磁碟;網路|基礎設施監控|

## 復原策略
|情況|戰略|
|------------|----------|
| **倉庫中已存在錯誤資料** |確定受影響的時間範圍；從源頭進行再加工；通知下游消費者|
| **運行中途管道故障** |冪等設計允許安全重新運行；檢查點允許恢復|
| **架構變更破壞了管道** |修復變換；回填受影響的資料；新增模式演化處理 |
| **無聲腐敗被發現較晚** |根本原因分析；確定爆炸半徑；重新加工；添加監控以捕捉復發情況 |
| **資料遺失** |從備份還原；從源頭重播；評估損失是否可挽回|
---

＃＃ 概括
資料管道故障無所不在，而且通常比應用程式中斷成本更高，因為它們產生錯誤的答案而不是明顯的錯誤。無聲資料損壞、模式漂移、重複、時區錯誤和缺失值是最常見的罪魁禍首。關鍵的預防策略是： 在每個邊界（模式、範圍、體積、新鮮度）驗證數據；將管道設計為冪等和原子的；監控一切（持續時間、行數、空率、新鮮度）；對失敗的記錄使用死信隊列；並在生產者和消費者之間建立數據合約。當發生故障時，回應應包括根本原因分析、受影響資料的重新處理、下游消費者的通知，以及最重要的是添加監控以捕獲未來同類的故障。正確對待這一點的組織會像對待生產軟體一樣嚴格地對待資料管道：測試、監控、警報、事件回應和事後分析。
