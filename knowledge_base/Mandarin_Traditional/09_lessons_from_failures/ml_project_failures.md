# 機器學習專案失敗
机器学习项目的失败率惊人——行业估计表明 60-85% 的机器学习项目从未投入生产。失敗通常不在於演算法；而在於演算法。它们位于流程、数据、期望和组织环境中。了解機器學習專案失敗的原因對於任何建立機器學習系統的人來說都是至關重要的，因為失敗模式是可以預測的並且在很大程度上是可以避免的。
---

## 為什麼機器學習專案會失敗
### 失敗類別
|類別 |失敗的份額|說明 |
|----------|----------------|-------------|
| **資料問題** | 〜30% |資料不足、有偏見、陳舊或無法存取 |
| **問題定義** | 〜20% | ML 問題與業務需求不符 |
| **期望不匹配** | ~15% |利害關係人期待魔法；現實是漸進式改進|
| **部署失敗** | ~15% |模型適用於筆記型電腦，但無法量產 |
| ** 組織問題** | 〜10% |沒有明確的所有權；團隊缺乏技能；沒有行政支援|
| **模型表現** | 〜10% |模型未達到所需的準確度或泛化能力較差 |

## 資料相關的故障
### 常見資料問題
|問題 |描述 |範例|
|---------|-------------|---------|
| **資料不足** |沒有足夠的例子來學習有意義的模式 |針對 500 筆交易訓練詐欺偵測模型 |
| **標籤品質** |訓練標籤錯誤、不一致或主觀 |由非專家標記的醫學影像；評估者間一致性較低的情緒標籤 |
| **資料外洩** |來自未來或目標的資訊外洩到功能中 |使用客戶流失結果作為特徵；在訓練中包含測試資料 |
| **選擇偏差** |訓練資料並不代表部署人群 |根據一家醫院的資料訓練醫學模式；全國部署 |
| **概念漂移** |特徵和目標之間的關係隨著時間的推移而變化|大流行後消費者行為發生變化；根據大流行前資料訓練的模型
| **功能不匹配** |培訓期間可用的功能與生產中可用的功能不同|使用手動標籤進行培訓；生產採用不同分佈的自動化標籤|
| **類別不平衡** |目標類別高度傾斜 | 99% 陰性，1% 陽性；模型學會總是預測負面結果
### 資料外洩問題
|類型 |描述 |範例|
|------|-------------|---------|
| **目标泄漏** |某项功能仅在目标发生后才可用 | “治疗结果”用作预测“治疗成功”的特征 |
| **列车测试污染** |测试数据影响训练 |通过全球统计数据进行扩展（包括测试数据）；泄漏的数据增强 |
| **抽样偏差** |训练和生产使用不同的采样|网络流量培训；部署在移动应用程序流量上
| **预处理泄漏** |预处理步骤使用完整数据集中的信息 |用全局平均值（包括测试数据）估算缺失值 |

## 問題定義失敗
### 錯位模式
|圖案|描述 |後果|
|---------|-------------|----------|
| **解決錯誤的問題** |業務需求X；團隊建立 Y |模型技術上好但沒什麼用|
| **當規則足夠時機器學習** |問題具有確定性規則；機器學習增加了複雜性 |過度設計；更難維護；難以解釋|
| **資料不存在時的機器學習** |問題需要尚未收集的資料 |專案無法啟動；在可行性上浪費了幾個月的時間
| **沒有業務背景的準確度目標** | 「我們需要 95% 的準確率」—但這對企業意味著什麼？ |模型滿足準確度但無法解決業務問題 |
| **忽略錯誤的成本** |誤報和漏報有不同的成本|模型最佳化了錯誤的指標 |
| **沒有基準** |與現有方法沒有比較|無法判斷 ML 是否真的比簡單的啟發式更好 |

## 期望失敗
### 機器學習專案的技術成熟度曲線
|相|描述 |風險|
|--------|-------------|------|
| **興奮** | “人工智慧會解決一切！” |過度承諾；資源不足|
| **概念證明** |模型適用於筆記本中的乾淨數據 |虛假的信心； “有用！” |
| **現實檢驗** |生產資料混亂；效能下降|失望；「機器學習不起作用」|
| **死亡行軍** |團隊試圖將其投入生產 |技術債；職業倦怠|
| **放棄或安靜部署** |專案在沒有監控的情況下被取消或部署 |浪費投資|
### 管理期望
|戰略|描述 |
|----------|-------------|
| **從基線開始** |與最簡單的方法（規則；人類表現）進行比較 |
| **預先定義成功指標** |業務指標（收入；成本節省）不僅僅是 ML 指標（準確性；F1）|
| **時間盒探索** |在提交之前給團隊 2-4 週的時間來評估可行性 |
| **展示機器學習不能做什麼** |誠實面對限制；設定現實的期望|
| **增量迭代** |先部署一個簡單的模型；迭代改進|
| **量化錯誤成本** |將模型效能轉換為業務影響 |

## 部署失敗
### 為什麼模型無法投入生產
|問題 |說明 |解決方案 |
|---------|-------------|----------|
| **筆記本與生產差距** |程式碼可以在 Jupyter 中運行，但尚未做好生產準備 | MLOps 實踐；機器學習的 CI/CD；程式碼審查 |
| **延遲要求** |模型推理速度太慢，無法即時使用 |模型優化；量化；快取|
| **可擴展性** |模型無法處理生產流量 |批量處理；水平縮放；模型服務基礎設施|
| **監控差距** |無法偵測模型何時降級 |資料漂移監控；績效監控；警報|
| **依賴管理** |培訓和服務環境不同 |貨櫃化；可重複的環境|
| **沒有回滾計畫** |新模型失敗時無法還原到先前的模型 |模型註冊；版本控制；自動回滾 |
### 模型衰減
|類型 |描述 |偵測|
|------|-------------|------------|
| **資料漂移** | 輸入特徵分佈變化 |監控功能統計；KL 散度；PSI |
| **概念漂移** |特徵與目標變化之間的關係|隨著時間的推移監控預測準確度 |
| **標籤漂移** |目標變化的定義或分佈|追蹤標籤分佈；業務指標相關性|
| **上游變更** |資料來源變更格式、時間或品質 |模式驗證；新鮮度監控 |

## 組織失敗
|失敗|描述 |預防|
|--------|-------------|------------|
| **沒有明確的所有權** |沒有人對生產中的模型負責|指定模型所有者；定義 RACI |
| **孤立的團隊** |資料科學家建立模型；工程師部署；沒有人交流|跨職能團隊；共同目標|
| **無 MLOps 成熟度** |沒有型號註冊；沒有 CI/CD；沒有監控|增量投資 MLOps 基礎設施 |
| **不切實際的時間表** | “在 2 週內建立一個生產 ML 系統” |時間盒探索；迭代；溝通複雜性|
| **缺乏領域專業知識** | ML 團隊不了解業務問題 |在 ML 團隊中嵌入領域專家 |
| **沒有評估架構** |無法判斷模型是否在生產環境中運作 |定義業務指標；設定儀表板；定期評論|

## 經驗教訓
### ML 項目清單
|相|關鍵問題|
|--------|-------------|
| **問題定義** |這其實是個機器學習問題嗎？底線是什麼？成功是什麼樣的？ |
| **數據評估** |我們有足夠的數據嗎？有代表性嗎？標籤可靠嗎？ |
| **可行性** |我們可以在 2-4 週內建造一個工作原型嗎？有哪些風險？ |
| **發展** |是否有資料外洩？我們是否使用了正確的評估指標？ |
| **預製作** |它適用於生產資料嗎？夠快嗎？是否受到監控？ |
| **部署** |我們可以回滾嗎？誰在值班？當它降解時會發生什麼？ |
| **部署後** |我們正在監測漂移嗎？是否追蹤業務指標？有再培訓計畫嗎？ |
---

＃＃ 概括
機器學習專案失敗並不是因為演算法太難，而是因為圍繞它們的流程被破壞了。資料問題——資料不足、標籤不良、洩漏、漂移——是故障的最大組成部分。問題定義失敗——解決錯誤的問題，在規則足夠的情況下使用機器學習，忽略錯誤的成本——浪費數月的努力。預期失敗——承諾過多、交付不足、不管理利害關係人——會破壞組織對機器學習的信任。部署失敗——筆記本到生產的差距、延遲問題、無監控——意味著在開發中工作的模型永遠不會在生產中創造價值。組織失敗——沒有所有權、孤立的團隊、沒有 MLO——從結構上來說不可能成功。解藥是嚴格的練習：從基準開始；時間盒探索；嚴格驗證資料；檢查是否有洩漏；定義業務指標；增量部署；持續監控；並迭代。最好的機器學習團隊在資料和流程上花費的時間比在模型上花費的時間更多。
