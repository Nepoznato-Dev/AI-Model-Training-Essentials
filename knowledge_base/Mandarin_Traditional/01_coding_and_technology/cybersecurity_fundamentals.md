# 網路安全基礎知識
安全性是一門學科，必須從一開始就整合到系統的每一層，而不是事後添加。無論是建立 Web 應用程式、管理基礎架構或發布 API，了解威脅情勢和防禦基礎知識都是至關重要的。
---

## 加密與密碼學
### 對稱加密與非對稱加密
|类型 |它是如何运作的 |速度|密钥分发 |示例 |
|------|-------------|--------|------|----------|
| **对称** |加密和解密使用相同的密钥 |快|挑战：如何共享密钥？ | AES-256、ChaCha20 |
| **不对称** |公钥加密，私钥解密 |慢一点 |公钥可以公开共享 | RSA、ECC（椭圆曲线）|
在實踐中，大多數系統都使用**兩者**：使用非對稱加密來安全地交換對稱金鑰，然後使用對稱加密來處理大量資料。这就是 TLS/HTTPS 的工作原理。
### 哈希
雜湊是一種單向函數：它將輸入轉換為固定大小的字串。你無法反轉它，但相同的輸入總是產生相同的輸出。
|使用案例|推薦演算法 |避免 |
|----------|------------------------|--------|
| **密碼儲存** | Argon2id、bcrypt、scrypt | MD5、SHA-1、普通 SHA-256（太快）|
| **資料完整性** | SHA-256、SHA-3 | MD5（損壞）、SHA-1（損壞）|
| **數位簽章** | Ed25519、RSA-2048+ | DSA |
### TLS/HTTPS
HTTPS 是基於 TLS（傳輸層安全性）的 HTTP。它提供：
- **加密**：傳輸中的資料無法被竊聽者讀取。
- **身份驗證**：伺服器透過憑證證明其身分。
- **完整性**：資料在傳輸過程中無法被修改而不被偵測到。
使用 TLS 1.2 或 1.3。停用 TLS 1.0 和 1.1。啟用 HSTS（HTTP 嚴格傳輸安全性）以強制瀏覽器始終使用 HTTPS。

## 身份驗證和授權
### 身份驗證：你是誰？
|方法|安全等級|使用案例|
|--------|----------------|----------|
| **密碼** |低-中 |基本帳戶（強制執行 12 個以上字符，檢查是否有違規行為）|
| **藝術碩士（TOTP）** |高|敏感帳號標準（Google Authenticator、Authy）|
| **硬體金鑰 (FIDO2/WebAuthn)** |非常高 |高安全性帳戶（YubiKey）|
| **生物辨識** |中-高|裝置解鎖（指紋、臉部）－不是唯一的因素 |
| **OAuth2 / OIDC** |高|第三方登入（「使用 Google 登入」）|
**密碼規則**：強制執行最小長度（12-16 個字元）、檢查違反的密碼清單、使用 Argon2id 或 bcrypt 與每個使用者鹽進行雜湊處理。
### 授權：你能做什麼？
|型號|描述 |範例|
|--------|-------------|---------|
| **RBAC**（基於角色的存取控制）|指派給角色的權限；使用者取得角色 |管理員、編輯、檢視者 |
| **ABAC**（基於屬性）|基於使用者屬性、資源、環境的規則 | 「經理可以批准其團隊的請求」|
| **ACL**（存取控制清單）|每個使用者/資源的明確權限 |檔案權限（讀取/寫入/執行）|
**最小權限原則**：僅向每個使用者、服務和進程提供他們所需的最低存取權限。
### JWT（JSON Web 令牌）
|方面|推薦|
|--------|----------------|
| **簽署** | RS256或ES256（非對稱）優先；HS256 可接受託管機密 |
| **到期** |存取權杖需要 15-60 分鐘；對較長的會話使用刷新令牌 |
| **儲存** |僅 HTTP cookie（不是 localStorage — 容易受到 XSS 攻擊）|
| **驗證** |總是驗證簽名、發行者、受眾和過期日期 |

## OWASP 前 10 名 (2021)
OWASP Top 10 是 Web 應用程式安全性的標準意識文件。它代表了最嚴重的風險：
| ＃|風險|這意味著什麼？
|---|------|----------|
| 1 | **存取控制損壞** |使用者可以存取不應該存取的資源 |
| 2 | **加密失敗** |敏感資料加密薄弱或遺失 |
| 3 | **注射** | SQL、NoSQL、作業系統指令或 LDAP 注入 |
| 4 | **不安全的設計** |無法透過實作修復的架構缺陷 |
| 5 | **安全設定錯誤** |預設密碼、開放連接埠、詳細錯誤訊息 |
| 6 | **易受攻擊的元件** |依賴項中的已知 CVE |
| 7 | **身分驗證失敗** |弱密碼、會話管理不善 |
| 8 | **誠信失敗** |供應鏈攻擊、未簽章更新|
| 9 | **記錄/監控故障** |未發現違規行為 |
| 10 | 10 **SSRF** |伺服器被欺騙向內部系統發出請求 |

## 安全編碼實踐
### 輸入驗證
|規則|為什麼 |
|------|-----|
| **白名单>黑名单** |定义允许的内容，而不是阻止的内容 |
| **参数化查询** |切勿将用户输入连接到 SQL 中 — 使用准备好的语句或 ORM |
| **HTML 编码** |编码`<`、`>`、`&`、`"`、`'`以防止 XSS |
| **外壳逃逸** |避免从用户输入构建 shell 命令；使用`shlex.quote()` |
| **长度限制** |强制执行最大长度以防止缓冲区溢出和 DoS |
| **类型检查** |确保整数是整数，布尔值是布尔值 |
### 常見漏洞
|漏洞|攻擊|防禦|
|--------------|--------|---------|
| **SQL 注入** | 登入表單中的`' OR 1=1 --`|參數化查詢 |
| **XSS** | 評論區`<script>alert('hacked')</script>` |輸出編碼，內容安全策略|
| **CSRF** |欺騙使用者的瀏覽器發出未經授權的請求 | CSRF 令牌、SameSite cookie |
| **路徑遍歷** | 檔案參數中的`../../etc/passwd`|驗證與清理檔案路徑 |
| **伊多爾** |將`/user/123`更改為`/user/124`以查看別人的資料 |對每個請求進行授權檢查 |

## 網路安全
### 防火牆
|類型 |描述 |
|------|-------------|
| **封包過濾** |基於IP、連接埠、協定的規則|
| **有狀態** |追蹤連線狀態；更聰明的過濾|
| **應用程式等級（WAF）** |檢查 HTTP 流量；阻止SQL注入、XSS等|
| **雲端安全群組** |雲端實例的虛擬防火牆（AWS SG、Azure NSG）|
**經驗法則**：預設封鎖所有入站流量；只開啟明確需要的內容（Web 為 80、443）。
### 網路分段
將資料庫和快取放置在無法直接存取 Internet 的私有子網路中。將 DMZ 用於面向大眾的服務（Web 伺服器、負載平衡器）。將最小權限原則應用於網路存取。

## 秘密管理
### 黃金法則
**切勿對機密進行硬編碼。 **原始碼中沒有 API 金鑰、密碼或資料庫 URL。提交給 Git 的環境變數中沒有秘密。 Docker 映像中沒有秘密。
＃＃＃ 工具
|工具|類型 |最適合 |
|------|------|----------|
| **HashiCorp 金庫** |企業機密管家|動態秘密，加密即服務 |
| **AWS Secrets Manager** |雲端原生 | AWS 環境 |
| **Azure 金鑰保管庫** |雲端原生 | Azure 環境 |
| **標準作業規程** |加密檔案 |在 Git 中加密機密（使用 KMS 或 GPG） |
| **Docker 的秘密** |容器原生 | Docker Swarm（對於 K8s，請考慮 Secrets Store CSI）|
| **dotenv (.env)** |本地發展|僅限開發 - 從未投入生產或承諾 |
### 旋轉
定期自動輪換機密。如果秘密被洩露（例如，提交到公共倉庫），請立即輪換它 - 即使您認為沒有人看到它。

## 依賴安全
您的應用程式的安全性取決於其最弱的依賴項。
### 掃描工具
|語言 |工具|
|----------|--------|
| **Python** | `safety`、`pip-audit`、`bandit` |
| **Node.js** | `npm audit`、`yarn audit`、`snyk` |
| **生鏽** |`cargo audit`|
| **去** |`govulncheck`|
| **一般** |`Dependabot`(GitHub)、`Renovate`、`Trivy` |
### 供應鏈完整性
- 使用鎖定檔案（`package-lock.json`、`Cargo.lock`、`go.sum`）進行可重現的建置。
- 驗證下載的依賴項的校驗和。
- 喜歡官方註冊機構和經過驗證的發布者。
- 透過 Dependabot 或 Renovate 自動進行次要/補丁更新。

## 緊急檢查表
當您懷疑有違規行為時：
1. **不要驚慌**－但要迅速採取行動。
2. **隔離**受影響的系統（如果需要，請中斷網路連線）。
3. **保留證據**：捕獲日誌、記憶體轉儲、磁碟映像。
4. **確定範圍**：哪些系統，哪些資料？
5. **輪換**所有洩漏的憑證和機密。
6. **修補**漏洞。
7. 如有需要，**通知**受影響的使用者和監管機構（在法定期限內）。
8. **事後分析**：在 24-48 小時內記錄根本原因和行動項目。
