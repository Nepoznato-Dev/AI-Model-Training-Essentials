# 測試方法
測試是您如何獲得程式碼工作的信心——更重要的是，對程式碼的更改不會破壞已經工作的內容。良好的測試可以在使用者之前發現錯誤，記錄預期行為，並實現無畏的重構。該文件涵蓋了從單元測試到端到端測試的全部測試策略，以及使測試有效的原則。
---

## 測試金字塔
測試金字塔描述了項目中測試的理想分佈。
```
        /  E2E  \          ← Few; slow; expensive; test the whole system
       /─────────\
      / Integration\       ← Some; test how components work together
     /───────────────\
    /   Unit Tests    \    ← Many; fast; cheap; test individual functions
   /─────────────────────\
```

|水平|計數 |速度|成本|它測試什麼 |
|--------|--------|--------|------|---------------|
| **單位** |許多|快速（毫秒）|低|單獨的函數、類別、方法 |
| **整合** |一些|中（100ms-s）|中等|元件如何互動；資料庫查詢； API 呼叫 |
| **端對端** |很少|慢（秒-分鐘）|高|真實系統中完整的使用者流程|
---

## 單元測試
單獨測試各個程式碼單元。
### 原則
|原理|說明 |
|------------|-------------|
| **快** |每個測試應以毫秒為單位運行 |
| **隔離** |測試並不互相依賴；沒有共享狀態 |
| **確定性** |相同的輸入→每次相同的輸出（無隨機性，無時間依賴性）|
| **自我檢測** |測試自動通過或失敗；無需人工檢查|
| **及時** |寫在代碼旁邊或之前 (TDD) |
### 測試剖析
|相|描述 |
|--------|-------------|
| **安排** |設定測試資料和依賴關係 |
| **行動** |呼叫正在測試的函數或方法 |
| **斷言** |驗證結果符合預期 |
### 測試什麼
|類別 |範例 |
|----------|---------|
| **幸福之路** |正常輸入產生預期輸出 |
| **邊緣情況** |空白輸入、null、零、最大值、單一元素 |
| **錯誤案例** |輸入無效、資料遺失、權限被拒絕 |
| **邊界條件** |落後一分；完全處於極限|
### 模擬與存根
|術語 |說明 |何時使用 |
|------|-------------|-------------|
| **模擬** |一個記錄它如何被呼叫的假物件 |驗證互動（這個方法被呼叫了嗎？） |
| **存根** |傳回預定值的假物件 |提供測試資料（從資料庫傳回該使用者） |
| **間諜** |記錄對真實物件的呼叫的包裝器 |部分驗證 |
| **假** |一個簡化但有效的實作 |用於測試的記憶體資料庫 |
|模擬庫 |語言 |
|----------------|--------|
| **單元測試.mock** |蟒蛇 |
| **開玩笑** | JavaScript/TypeScript |
| **莫基托** |爪哇 |
| **訂購量** | C# |
| **作證/gomock** |去 |

## 整合測試
測試多個元件如何協同工作。
|測試什麼 |範例|
|-------------|---------|
| **資料庫查詢** | ORM 是否產生正確的 SQL？是否使用索引？ |
| **API 端點** |完整的請求-回應週期是否有效？ |
| **服務互動** |服務A是否正確呼叫服務B？ |
| **外部依賴** |支付網關整合是否有效？ |
### 策略
|戰略|描述 |權衡|
|----------|-------------|------------|
| **真正的依賴** |使用真實的資料庫、真實的訊息佇列|最現實；慢點;更難設定|
| **測試容器** |為每次測試運行啟動 Docker 容器 |良好的平衡性；可重複|
| **記憶體中的替代品** | H2取代PostgreSQL；記憶體訊息匯流排|快速地;可能會錯過現實世界的問題|
| **合約測試** |驗證服務是否遵守其 API 合約 |捕捉介面變更 |
---

## 端對端 (E2E) 測試
從使用者的角度測試整個系統。
|工具|類型 |最適合 |
|------|------|----------|
| **劇作家** |瀏覽器自動化 |網頁應用程式；跨瀏覽器 |
| **柏樹** |瀏覽器自動化 |網頁應用程式；開發者經驗|
| **硒** |瀏覽器自動化 |遺產;廣泛的語言支援|
| **排毒** |行動端對端 | React Native 應用程式 |
| **Appium** |行動端對端 |本機與混合行動應用程式 |
| **大師** |行動端對端 |行動應用程式；簡單的 YAML 語法 |
| **k6 / 蝗蟲** |負載測試|負載下的性能|
### 端對端最佳實踐
|實踐|為什麼 |
|----------|-----|
| **僅測試關鍵路徑** | E2E測試速度慢；專注於最重要的事情 |
| **使用測試資料工廠** |以程式設計方式建立測試資料；不要依賴種子資料 |
| **測試後清理** |每次測試都應該讓系統處於已知狀態 |
| **避免測試 UI 細節** |測試行為，而不是 CSS 類別或元素位置 |
| **在 CI 中執行** | E2E 測試必須在每次變更時自動執行 |

## 測試驅動開發 (TDD)
先編寫測試，然後編寫程式碼使其通過。
|步驟|描述 |
|------|-------------|
| **1.紅色** |寫一個描述所需行為的失敗測試 |
| **2.綠色** |寫出最少的程式碼使測試通過 |
| **3.重構** |清理程式碼，同時保持測試綠色 |
|效益 |說明 |
|---------|-------------|
| **設計回饋** |測試迫使您在實作之前考慮介面 |
| **回歸安全性** |每個錯誤都會經過測試； bug 永遠不會再出現 |
| **文檔** |測試是預期行為的活生生的記錄 |
| **信心** |高測試覆蓋率實現無畏的重構 |
---

## 行為驅動開發（BDD）
BDD 透過以自然語言編寫從使用者角度描述行為的測試來擴展 TDD。
### 給定-當時-那麼格式
```
Given a user with an empty shopping cart
When they add a "Python Book" priced at $29.99
Then the cart total should be $29.99
And the cart should contain 1 item
```

|工具|語言 |
|------|----------|
| **黃瓜** | Java、JavaScript、Ruby 等 |
| **行為** |蟒蛇 |
| **SpecFlow** | C# |
| **開玩笑**（用描述/它）| JavaScript |

## 其他測試類型
|類型 |它測試什麼 |工具|
|------|--------------|--------|
| **效能/負載** |負載下的系統行為| k6、JMeter、Locust、加特林 |
| **安全性** |漏洞與攻擊向量| OWASP ZAP、Burp Suite、Snyk |
| **輔助功能** | WCAG 合規性 |斧頭，燈塔，pa11y |
| **合約** |服務之間的API相容性| Pact、Spring Cloud 合約 |
| **突變** |測試套件本身的品質| Stryker、mutmut、PIT |
| **視覺回歸** |版本之間的 UI 變化 | Percy、Chromatic、BackstopJS |
| **混亂** |系統的故障復原能力|混沌猴、石蕊、小魔怪 |
| **煙** |部署後的基本功能 |自訂腳本；健康檢查|
| **浸泡** |長時間內的系統行為 |長時間運行的負載測試|

## 測試組織
|圖案|說明 |何時使用 |
|---------|-------------|----------|
| **同地辦公** |在他們測試的程式碼旁邊進行測試（`src/utils.test.ts`）|大多數專案；很容易找到|
| **單獨的目錄** |在`tests/`或`__tests__/`資料夾中進行測試 |大型專案；清晰的分離|
| **測試夾具** |`fixtures/`目錄中的共享測試資料 |當多個測試需要相同的資料時|
| **測試實用程式** |`test-utils/`目錄中的共用助手 |當設定邏輯複雜時 |
---

## 程式碼覆蓋率
|公制|它測量什麼 |限制|
|--------|-----------------|------------|
| **線路覆蓋** |測試執行的程式碼行的百分比 |不衡量斷言的品質 |
| **分支機構覆蓋** |採取的分支（if/else）百分比 |比線路覆蓋更好；仍然沒有捕獲所有錯誤|
| **路徑覆蓋** |所採用的執行路徑的百分比 |最徹底；複雜程式碼中的指數 |
| **突變分數** |測試發現突變的百分比|測試品質的最佳衡量標準 |
**目標**：80% 的線路覆蓋率是合理的預設值。但覆蓋率只是一個指導，而不是目標——弱斷言的 100% 覆蓋率比徹底測試的 70% 覆蓋率要差。

## 持續整合和測試
|實踐|描述 |
|----------|-------------|
| **在每次提交時運行所有單元測試** |快速反饋；立即捕獲回歸 |
| **在 PR 上執行整合測試** |捕獲單元測試遺漏的問題 |
| **每晚執行 E2E 測試或合併到主程式** |緩慢而徹底|
| **快速失敗** |在第一次失敗時停止管道以節省時間 |
| **不穩定的測試政策** |立即隔離或刪除不穩定的測試；永遠不要忽視 |
| **測試並行化** |並行運行測試以減少 CI 時間 |
---

## 實用技巧
- **清楚地命名測試。 **`test_calculates_tax_for_high_earner`告訴您什麼出了問題。 `test_1`什麼也沒告訴你。
- **每次測試一個斷言（實用時）。 ** 使故障易於診斷。
- **不要測試實作細節。 ** 測試行為。如果重構內部結構，測試就不會中斷。
- **避免測試第三方程式碼。 ** 模擬外部函式庫；測試您的程式碼與它們的互動。
- **加快測試速度。 ** 如果您的測試套件需要 10 分鐘，開發人員將停止運行它。不斷優化。
- **刪除死測試。 ** 總是通過的測試或測試已刪除的程式碼是雜訊。
- **像對待生產程式碼一樣對待測試程式碼。 **它應該是可讀、可維護且結構良好。
---

＃＃ 概括
測試不是可選的——它是構建不會崩潰的軟體的方式。測試金字塔引導您進行許多快速單元測試、一些整合測試和一些 E2E 測試。 TDD 和 BDD 提供了結構化方法。模擬隔離單元進行測試。程式碼覆蓋率衡量的是廣度，而不是深度。最重要的原則是：如果它沒有經過測試，它就壞了——你只是還不知道而已。
