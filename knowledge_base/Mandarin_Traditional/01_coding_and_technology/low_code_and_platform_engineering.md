# 低程式碼和平台工程
低程式碼平台讓人們可以用最少的手寫程式碼建立應用程式——通常透過拖放介面、視覺化工作流程和預先建置的連接器。平台工程是建立內部開發人員平台 (IDP) 的學科，使產品團隊可以輕鬆地自助基礎設施、CI/CD 和操作工具。這兩個趨勢都是對同一問題的回應：軟體需求與能夠建立軟體的開發人員的供應之間的差距。
---

## 低程式碼平台
### 低程式碼實際上意味著什麼
|方面|描述 |
|--------|-------------|
| **視覺開發** |拖放式 UI 建構器；視覺化工作流程編輯器；表單設計師|
| **預先建置元件** |現成的小工具、連接器、範本和整合 |
| **聲明性邏輯** |透過規則和條件而不是編寫程式碼來配置行為 |
| **可擴展性** |當平台的內建功能不夠時，能夠添加自訂程式碼 |
| **託管基礎架構** |平台處理託管、擴充、安全性修補程式|
### 流行的低程式碼平台
|平台|實力|典型用例|
|----------|----------|-----------------|
| **微軟 Power Platform** |深度 Microsoft 365/Azure 整合; Power Apps、Power Automate、Power BI |企業工作流程；內部工具|
| **Salesforce 平台** | CRM 原生；用於擴展的 Apex；流程產生器 |面向客戶的應用程式；銷售工作流程 |
| **立即服務** | IT服務管理；工作流程自動化 |資訊科技營運；人力資源；設施 |
| **亞庇** |流程挖掘；案例管理 |業務流程複雜；合規|
| **外部系統** |全端網路與行動裝置；企業級|客戶入口網站；行動應用程式 |
| **重組** |內部工具建構器；連接到資料庫和 API |管理面板；儀表板；操作工具|
| **氣墊** |電子表格-資料庫混合；自動化|專案追蹤；輕量級CRM |
### 當低程式碼運作良好時
|場景 |為什麼低程式碼適合？
|----------|--------------------|
| **內部工具** |快速建置；用戶是內部用戶，因此 UI 彈性不太重要 |
| **表格和批准** |視覺化工作流程建立器在這方面表現出色 |
| **CRUD 應用程式** |大多數低程式碼平台都針對建立-讀取-更新-刪除模式進行了最佳化 |
| **原型製作** |在數小時而不是數週內驗證一個想法 |
| **公民發展** |業務分析師可以利用 IT 治理來建立自己的解決方案 |
### 當低程式碼無法達到要求時
|限制|影響 |
|------------|--------|
| **供應商鎖定** |應用程式無法輕易地從平台遷移出去 |
| **效能上限** |不適合高吞吐量或延遲敏感的應用程式 |
| **使用者介面限制** |客製化設計很困難；您僅限於平台支援的內容 |
| **整合複雜性** |無論如何，連接到不尋常的 API 或遺留系統可能需要自訂程式碼 |
| **規模成本** |隨著使用量的增長，每個用戶或每個應用程式的定價可能會變得昂貴 |
| **調試難度** |視覺抽象使得診斷複雜問題變得困難 |

## 平台工程
### 平台工程解決的問題
|沒有平台工程|與平台工程|
|----------------------------|----------------------------|
|每個團隊管理自己的基礎設施 |自助服務平台抽象基礎設施|
|跨團隊的工具不一致 |標準化工具鏈；黃金之路|
|開發人員等待運營商提供資源 |開發者按需提供資源|
|知識孤島；部落知識|記錄在案；自動化；可發現|
|新工程師入職緩慢|新工程師第一天就可以部署 |
### 內部開發者平台的核心元件
|組件|目的|範例工具 |
|------------|---------|---------------|
| **服務目錄** |所有服務及其所有者的中央登記處|後台;港口;皮質|
| **模板化鷹架** |從核准的模板產生新服務 |後台軟體模板；餅乾切割機|
| **自助服務基礎設施** |開發者無需提交工單即可配置雲端資源 |地形模組；普魯米；十字平面|
| **CI/CD 管道** |標準化建置、測試、部署管道 | GitHub 操作；亞搏體育appGitLab持續整合；阿爾戈CD |
| **環境管理** |按需提供臨時開發/登台環境 | V簇；命名空間；吉特波德 |
| **可觀察性** |每個服務中內建的日誌記錄、指標和追蹤 |普羅米修斯；格拉法納；打開遙測；數據狗 |
| **秘密管理** |憑證的安全存儲和輪換 |保險庫； AWS 秘密管理器；標準操作規程 |
| **身份和訪問** |單點登錄；基於角色的訪問；服務到服務的身份驗證奧克塔；鑰匙斗篷；斯皮夫 |
### 黃金之路
黃金之路是受支持的、固執己見的做某事的方式。這是阻力最小的道路——如果你遵循它，一切都會順利。你可以偏離正軌，但你只能靠自己。
|黃金之路|它提供什麼 |
|----------|------------------|
| **新服務** |範本倉庫；持續整合/持續交付；監控；日誌記錄；部署配置 |
| **新資料庫** |配置實例；秘密中的連接字串；備份配置|
| **新前端** |建造管道； CDN；預覽環境；燈塔檢查|
| **資料管道** |編排；模式驗證；監控；警報|
### 建構與購買決策
|因素|建構客製化|使用現有工具 |
|--------|-------------|--------------------|
| **核心能力** |您的業務獨一無二；競爭優勢 |商品;每個公司都需要它|
| **維護負擔** |你有能力維護它 |工具由供應商/社區維護良好 |
| **整合需求** |需要與內部系統深度整合 |標準 API 和連接器就足夠了 |
| **成本** |建造成本比許可更便宜許可比建造更便宜|

## 低程式碼與平台工程的關係
|尺寸|低碼 |平台工程|
|------------|----------|---------------------|
| **目標使用者** |商業使用者；公民開發商|專業軟體工程師|
| **目標** |減少程式碼；提高速度|減少認知負荷；增加自主權|
| **抽象層次** |非常高；視覺|中等的;基於代碼但經過簡化 |
| **靈活性** |受平台能力限制 |充分的彈性；你可以寫任何程式碼 |
| **治理** |平台執行規則 |平台提供黃金通道|
它們是互補的：平台工程使專業開發人員更快，而低程式碼使非開發人員能夠建立簡單的應用程式。它們共同從不同角度解決了軟體交付差距。
---

＃＃ 概括
低程式碼平台和內部開發人員平台都旨在增加能夠交付軟體的人員數量。低程式碼透過完全抽象程式碼來實現這一點——視覺化建構器、預先建置連接器、聲明性邏輯。平台工程透過提供自助服務基礎設施、黃金路徑和標準化工具為專業開發人員做到這一點，使他們花在維運工作上的時間更少，而將更多的時間花在產品功能上。兩者都不是靈丹妙藥：低程式碼具有供應商鎖定和效能限制，且平台工程需要持續投資來維護。但當應用於正確的問題時——內部工具、CRUD 應用程式、標準化服務交付——兩者都可以大大縮短從想法到生產的時間。
