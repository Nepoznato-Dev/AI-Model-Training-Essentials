# 區塊鏈與分散式系統
區塊鏈是一種特定類型的分散式系統——一種分散的、僅附加的分類賬，其中記錄（區塊）透過加密雜湊連結。分散式系統是使多台電腦作為一台電腦協同工作的更廣泛的領域。這兩個概念對於理解現代基礎設施都很重要，從加密貨幣到分散式資料庫，再到為全球服務提供支援的共識演算法。
---

## 分散式系統基礎知識
### 為什麼是分散式系統？
|動機|描述 |
|------------|-------------|
| **可擴展性** |增加更多機器來處理更多負載 |
| **容錯** |即使某些機器故障，系統仍能繼續運作 |
| **地理分佈** |為附近資料中心的使用者提供服務 |
| **專業化** |不同的機器處理不同的任務|
### 關鍵概念
|概念 |描述 |挑戰|
|--------|-------------|------------|
| **共識** |讓所有節點就一個值達成一致|網路分區；拜占庭式的錯誤
| **複製** |跨多個節點複製資料 |一致性與可用性|
| **分區（分片）** |跨節點分割資料 |熱點；跨分片查詢 |
| **一致性模型** |保證不同讀者看到的內容 |強一致性速度慢；最終一致性可以讓使用者大吃一驚|
| **CAP定理** |你只能擁有其中的2個：一致性、可用性、分區容錯性|實際上需要分區容錯性；選擇 C 或 A |
### CAP 定理
|選擇|你得到什麼 |你放棄什麼 |範例|
|--------|-------------|-----------------|---------|
| **CP** |一致+分區容忍|分區期間某些節點可能無法使用 | HBase、MongoDB、Redis |
| **美聯社** |可用+分區容忍|讀取可能會返回陳舊資料 |卡桑德拉、DynamoDB、CouchDB |
| **CA** |一致+可用|不能容忍網路分區 |單節點資料庫（非真正分散式）|

## 共識演算法
分散式節點如何就係統狀態達成一致？
|演算法|型別 |容錯 |用於 |
|------------|------|----------------|---------|
| **Paxos** |崩潰容錯| 2f+1 個節點最多 f 個故障 |Google胖乎乎的；基礎理論|
| **木筏** |崩潰容錯| 2f+1 個節點最多 f 個故障 | etcd、領事、TiKV |
| **PBFT** |拜占庭容錯 | 3f+1 個節點最多 f 個故障 |超級帳本結構 |
| **工作證明** |拜占庭容錯 |取決於算力 |比特幣 |
| **權益證明** |拜占庭容錯 |取決於股份 |以太坊 2.0，卡爾達諾 |
### 筏（簡化）
|角色 |責任|
|------|----------------|
| **領導者** |處理所有客戶請求；向追蹤者發送日誌條目 |
| **追蹤者** |回應領導的要求；選舉投票|
| **候選人** |請求投票成為領導者 |
1. 所有節點均以追隨者身分啟動
2. 如果追隨者在選舉超時期間沒有收到領導者的消息，它將成為候選人
3. 候選人請求投票；得票最多的人成為領導者
4.領導者將日誌條目複製給追隨者
5. 當多數人確認時，條目被提交

## 區塊鏈
### 區塊鏈如何運作
|組件|描述 |
|------------|-------------|
| **阻止** |一批交易+元資料+前一個區塊的雜湊值|
| **哈希** |區塊內容的加密指紋 |
| **鏈** |每個區塊都引用前一個區塊的雜湊值，創建一個不可變的鏈 |
| **共識** |網路參與者就增加哪些區塊達成一致 |
| **梅克爾樹** |總結區塊中所有交易的哈希樹 |
### 為什麼區塊鏈難以篡改
1. 每個區塊都包含前一個區塊的哈希值
2. 更改任何交易都會更改區塊的哈希值
3. 改變的哈希值破壞了鏈條－所有後續的區塊都變得無效
4. 攻擊者需要重新挖掘所有後續區塊並控制超過 50% 的網絡
### 區塊鏈的類型
|類型 |訪問 |驗證者 |範例|
|------|--------|------------|---------|
| **公開（無需許可）** |任何人都可以讀寫 |開放共識（PoW、PoS）|比特幣、以太坊 |
| **私人（許可）** |限制存取 |已知驗證器 |超級帳本、Corda |
| **財團** |由一組組織管理 |選定的驗證者 | R3 Corda 銀行業 |
### 智能合約
儲存在區塊鏈上的自動執行程式碼，在滿足預定條件時運行。
|平台|語言 |顯著特點|
|----------|----------|-----------------|
| **以太坊** |堅固性，Vyper |最大的智慧合約生態系 |
| **索拉納** |魯斯特，C |高通量；費用低|
| **卡爾達諾** |哈斯克爾（普利托斯）|同行評審；形式驗證|
| **超級帳本** | Go、Java、JavaScript |企業;許可|

## 分散式資料庫
|資料庫|建築|一致性|最適合 |
|----------|-------------|-------------|---------|
| **卡桑德拉** |寬柱；點對點|可調整（最終達到法定人數）|高寫入吞吐量；時間序列|
| **MongoDB** |文檔;副本集 |最終（具有因果一致性選項）|靈活的架構；快速發展|
| **CockroachDB** |分散式SQL; Raft 共識 |強|分散式SQL；全球部署|
| **TiDB** |分散式SQL； Raft（透過 TiKV）|強|相容MySQL；水平縮放 |
| **DynamoDB** |鍵值；管理 |最終（或具有一致讀取的強）|無伺服器； AWS 整合 |
| **扳手** |分散式SQL；帕克索斯|強|Google雲端；全球一致性|

## 分散式系統模式
|圖案|描述 |使用案例|
|---------|-------------|----------|
| **領導人選舉** |選擇一個節點進行協調 |筏首領；動物園管理員 |
| **複製** |複製資料以實現冗餘並讀取擴展 |資料庫副本； CDN |
| **分片** |按鍵範圍或哈希對資料進行分區 |大型資料庫|
| **MapReduce** |跨節點分割計算；匯總結果|大數據處理|
| **八卦協定** |節點定期與隨機對等點共享狀態 |叢集成員資格；故障偵測|
| **兩階段提交** |協調跨多個節點的交易 |分散式資料庫|
| **傳奇模式** |具有補償動作的一系列本地事務|微服務交易|
| **斷路器** |停止呼叫失敗的服務；快速失敗|彈性;防止級聯故障|

## 分散式系統中的挑戰
|挑戰|描述 |緩解措施 |
|------------|-------------|------------|
| **網路分區** |節點無法通訊 | CAP 權衡；後退重試 |
| **時鐘偏差** |不同節點有不同的時鐘|使用邏輯時鐘；國家時間規劃；避免依賴掛鐘時間|
| **拜占庭式錯誤** |說謊或任意行為的節點 | BFT共識；區塊鏈|
| **裂腦** |兩個節點都認為自己是領導者 |擊劍;基於法定人數的決策 |
| **級聯故障** |一次失敗引發其他失敗 |斷路器；艙壁；優雅降級|
| **資料一致性** |保持副本同步 |一致性模型；衝突解決|
---

＃＃ 概括
分散式系統是現代軟體擴展、抵禦故障以及為全球用戶提供服務的方式。共識演算法（Raft、Paxos）確保節點達成一致。區塊鏈增加了加密驗證和去中心化，以創建不可信的分類帳。分散式資料庫（Cassandra、CockroachDB、DynamoDB）大規模處理資料。 CAP 定理所體現的基本權衡是網路不可靠時的一致性和可用性之間的權衡。理解這些概念對於建立在互聯網規模上運行的系統至關重要。
