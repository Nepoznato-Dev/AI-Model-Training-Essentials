# 軟體架構模式
架構是關於系統如何組織的一組結構決策——它有哪些元件、它們如何溝通以及職責所在。良好的架構使系統易於理解、修改和擴展。糟糕的架構會讓每一次改變都變得困難。該文件涵蓋了主要模式、何時使用每種模式以及所涉及的權衡。
---

## 整體架構與微服務
這是最基本的架構決策，值得正確執行。
|方面|巨石|微服務|
|--------|----------|----------------|
| **結構** |單一可部署單元|許多小型、可獨立部署的服務 |
| **資料** |共享資料庫|每個服務都有自己的資料|
| **通訊** |進程內函數呼叫 |網路呼叫（HTTP、gRPC、訊息傳遞）|
| **縮放** |擴展整個應用程式 |擴展個人化服務|
| **部署** |單一發佈週期 |獨立部署|
| **複雜性** |初期開發更簡單 |營運複雜性（網路、監控）|
| **最適合** |小團隊，早期產品|大型團隊、複雜領域、高規模|
### 何時開始使用單體架構
大多數應用程式應該作為一個整體開始。建置、測試、部署和調試更加簡單。當您對域邊界有了更清晰的了解後，您隨時可以提取服務。這有時被稱為「模組化整體」——具有清晰內部邊界的整體，使以後的提取變得容易。
### 何時採用微服務
在以下情況下考慮微服務：
- 團隊規模夠大，協調成為瓶頸。
- 系統的不同部分有非常不同的擴充要求。
- 您需要獨立部署元件。
- 您的網域具有明確的有界上下文（請參閱下面的 DDD）。

## 分層架構（N 層）
最常見的架構模式。代碼被組織成多個層，每個層都有特定的職責。
```
â”Œ─────────────────────────┐
│   Presentation Layer    │  ← UI, controllers, API endpoints
├─────────────────────────┤
│   Application Layer     │  ← Use cases, orchestration
├─────────────────────────┤
│   Domain Layer          │  ← Business logic, entities
├─────────────────────────┤
│   Infrastructure Layer  │  ← Database, external services, file I/O
└─────────────────────────┘
```

|層|責任|規則|
|--------|----------------|------|
| **示範** |處理使用者/HTTP 請求 |只能呼叫應用層 |
| **應用** |編排用例|可以呼叫Domain層|
| **網域** |核心業務邏輯 |不應依賴其他層 |
| **基礎架構** |技術問題|實作 Domain | 中定義的介面
**關鍵規則**：依賴關係指向內部。領域層不了解資料庫或 Web 框架。

## 事件驅動架構
組件透過發出**事件**（已發生的事情）並做出反應來進行通訊。
|圖案|描述 |
|---------|-------------|
| **活動通知** |服務 A 發出「OrderPlaced」；服務 B、C、D 反應 |
| **事件溯源** |將所有狀態變更儲存為事件序列（不只是目前狀態）|
| **CQRS** |將讀取模型（查詢）與寫入模型（指令）分開 |
### 事件溯源
不要將「目前狀態」儲存在資料庫中，而是將每個狀態變更儲存為事件：
```
OrderCreated(order_id=123, total=$50)
OrderPaid(order_id=123, payment_id=456)
OrderShipped(order_id=123, tracking=ABC)
```

好處：完整的審計跟踪，能夠重建任何過去的狀態，解耦消費者。挑戰：事件模式演變、最終一致性、調試複雜性。
### CQRS（命令查詢職責分離）
|側面|目的|資料庫|
|------|---------|----------|
| **命令（寫）** |處理突變；執行業務規則|針對寫入進行最佳化（標準化）|
| **查詢（讀取）** |服務讀取請求 |針對讀取進行最佳化（非規範化）|
CQRS 與事件溯源自然配對：來自寫入端的事件投影到讀取最佳化的視圖中。

## 訊息佇列和事件代理
當服務需要非同步通訊時，訊息佇列就是骨幹。
|工具|類型 |最適合 |
|------|------|----------|
| **阿帕契卡夫卡** |分散式事件日誌|高吞吐量事件流、事件溯源 |
| **RabbitMQ** |有路由的訊息代理程式|任務佇列、複雜的路由模式|
| **AWS SQS** |託管佇列 | AWS 原生，簡單排程 |
| **AWS SNS** |發布/訂閱通知 |扇出至多個訂閱者 |
| **Google發佈/訂閱** |託管發布/訂閱 | GCP 原生事件流 |
| **Redis 流** |輕量級流|簡單的事件記錄、快取用例|
### 訊息傳遞模式
|圖案|描述 |
|---------|-------------|
| **點對點** |每個訊息有一個生產者，一個消費者 |
| **發布/訂閱** |一名製作者，多名訂閱者 |
| **請求/回覆** |非同步傳輸上的同步風格 |
| **死信佇列** |處理失敗的訊息將進入單獨的佇列進行檢查 |

## 領域驅動設計（DDD）
DDD 是一種軟體設計的策略方法，它將程式碼集中在業務概念而不是技術問題上。
### 關鍵概念
|概念 |描述 |
|---------|-------------|
| **有界上下文** |域模型在其中保持一致的邊界（例如「訂購」、「運輸」、「計費」）|
| **無所不在的語言** |開發人員與領域專家之間的共享詞彙|
| **聚合** |相關實體的叢集被視為資料變更的單一單元 |
| **實體** |具有身分的物件（例如，具有 user_id 的使用者）|
| **值物件** |沒有身分的物件；由其屬性定義（例如，金錢、地址）|
| **領域活動** |域中發生的事情（例如，OrderPlaced） |
| **反腐敗層** |您的網域與外部系統之間的轉換層 |
### 當 DDD 有幫助時
當業務領域複雜時，DDD 最為有價值——例如電子商務、物流、金融服務、醫療保健。如果您的領域很簡單（部落格、待辦事項應用程式），那麼 DDD 就太過分了。

## 快取策略
快取是提高效能最有效的方法之一，但它帶來了一致性方面的複雜性。
|戰略|描述 |權衡|
|----------|-------------|------------|
| **快取旁路** |應用程式首先檢查快取；未命中時從資料庫載入 |簡單的;最終一致性|
| **直寫式** |同時寫入快取和資料庫 |持續的;寫入速度較慢|
| **後寫式** |寫入快取；非同步寫入資料庫|快速寫入；資料遺失的風險|
| **通讀** |透明地在未命中時從資料庫快取載入 |比快取更簡單 |
### 快取什麼
|層|什麼 |工具|
|--------|------|--------|
| **CDN** |靜態資產、API 回應 | CloudFront、Cloudflare |
| **應用** |計算結果、會話資料 | Redis、Memcached |
| **資料庫** |查詢結果、經常存取的行|查詢快取、物化視圖 |
**快取失效**是出了名的困難。常見策略：TTL（生存時間）、事件驅動的失效（資料變更時清除快取）和 LRU（最近最少使用）驅逐。

## 設計模式
### 堅實的原則
|原理|這意味著什麼？
|------------|--------------|
| **S** — 單一職責 |一個類別應該有一個改變的理由 |
| **O** — 開啟/關閉 |開放擴展，關閉修改 |
| **L** — 利斯可夫換人 |子類型應該可以取代它們的基底類型 |
| **I** — 介面隔離 |多個專用介面>一個通用介面|
| **D** — 依賴倒置 |依賴抽象，而非具體 |
### 常見模式
|圖案|意圖 |範例|
|--------|--------|---------|
| **單例** |確保一個類別只有一個實例 |資料庫連線池|
| **工廠** |建立物件而不指定確切的類別 |`UserFactory.create(type="admin")`|
| **觀察員** |狀態發生變化時通知家屬 |事件監聽器，發布/訂閱 |
| **策略** |在運行時交換演算法 |付款策略：信用卡、PayPal、加密貨幣 |
| **儲存庫** |乾淨的介面背後的抽象資料存取|`UserRepository.find_by_id(123)`|
| **裝飾器** |動態新增行為 |圍繞服務記錄裝飾器 |
| **適配器** |讓不相容的介面協同工作 |舊版 API 適配器 |

## 選擇正確的架構
不存在普遍的「最佳」架構。正確的選擇取決於：
|因素|在以下情況下青睞整體式架構：在下列情況下青睞微服務：
|--------|------------------------|----------------------------------------|
| **團隊規模** |< 10 developers | >20 名開發人員，多個團隊 |
| **領域複雜性** |簡單或易於理解 |複雜的、許多有界脈絡 |
| **規模要求** |統一縮放需求|不同的組件需要不同的規模 |
| **部署節奏** |單一發布週期 |需要獨立部署|
| **技術多樣性** |一堆就可以了 |不同的服務需要不同的技術|
**實用建議**：從模組化整體開始。僅當您有明確的需求和明確的領域邊界時才提取服務。過早的微服務是業界最常見的架構錯誤之一。
