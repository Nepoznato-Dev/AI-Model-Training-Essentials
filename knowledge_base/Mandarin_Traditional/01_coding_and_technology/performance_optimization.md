# 效能優化
效能優化是使軟體更快的實踐——減少回應時間、提高吞吐量、降低記憶體使用量並消除瓶頸。這是開發人員可以擁有的最有影響力的技能之一，因為緩慢的軟體會失去用戶，浪費資源，並使每個人都感到沮喪。但這也是最常見的錯誤之一，開發人員根據直覺而不是證據來優化錯誤的事情。
---

## 黃金法則
> **首先測量，其次優化。 ** 切勿基於假設進行最佳化。分析程式碼，找到實際的瓶頸，然後修復它。
|反模式|為什麼它不好 |
|-------------|-------------|
| **過早優化** |花時間加速並不慢的程式碼 |
| **無需測量即可優化** |修復錯誤的瓶頸；無法驗證改進|
| **為了速度而犧牲可讀性** |不可讀程式碼的成本超過了效能增益 |
| **快取所有內容** |陳舊資料、記憶體膨脹、複雜性 |
---

## 分析
在你能夠更快地完成某些事情之前，你需要知道時間花在了「哪裡」。
|工具類型|它測量什麼 |範例 |
|------------|----------------|----------|
| **CPU 分析器** |哪些函數消耗最多的CPU時間| cProfile (Python)、perf (Linux)、Chrome DevTools (JS) |
| **記憶體分析器** |記憶體分配與洩漏| tracemalloc (Python)、Valgrind、heaptrack |
| **I/O 分析器** |磁碟與網路 I/O 瓶頸 | iotop、strace、Wireshark |
| **APM（應用程式效能監控）** |端對端請求時序 | New Relic、Datadog、Jaeger |
| **瀏覽器開發工具** |前端渲染、JavaScript 執行、網頁 | Chrome 開發者工具、Firefox 分析器 |
### 分析工作流程
|步驟|描述 |
|------|-------------|
| 1.識別運行緩慢|用戶報告頁面載入緩慢；監控顯示高延遲 |
| 2.分析完整路徑 |尋找哪個元件花費最多時間 |
| 3. 深入探究 |分析特定組件以尋找熱門功能 |
| 4.修復瓶頸|應用適當的最佳化 |
| 5.再次測量|驗證改善；檢查回歸 |
---

## 演算法最佳化
最大的效能提升來自於選擇更好的演算法，而不是來自微觀優化。
|改變 |改進|
|--------|------------|
|線性搜尋 O(n) → 哈希表查找 O(1) |大型資料集 100 倍以上 |
|嵌套循環 O(n²) → 排序 + 二分查找 O(n log n) |大 n 的數量級 |
|重複計算→記憶/快取|消除多餘的工作 |
|循環中的字串連接 → Builder / join |避免二次字串複製 |
|未排序的資料 → 使用二分查找排序的資料 |每次查找 O(log n) 而不是 O(n) |
---

## 快取策略
快取儲存計算結果，因此不需要重新計算。
|快取類型|地點 |速度|終身|
|------------|----------|--------|----------|
| **CPU 快取** | L1/L2/L3 | ~1 奈秒 |自動|
| **記憶體中** |應用程式 RAM（字典、HashMap）| ~100 奈秒 |直到被清除或驅逐為止|
| **分散式快取** | Redis、Memcached | ~1 毫秒 |可設定的TTL |
| **CDN** |全球邊緣伺服器 | ~10-50 毫秒 |可設定的TTL |
| **瀏覽器快取** |使用者的瀏覽器| ~1 毫秒 | HTTP 快取標頭 |
| **資料庫查詢快取** |資料庫或ORM等級| ~1-10 毫秒 |直到資料變更 |
### 快取模式
|图案|描述 |何时使用 |
|---------|-------------|----------|
| **快取旁路** |應用程式檢查快取；未命中時從資料庫載入；儲存在快取中|最常見；簡單|
| **直寫** |同時寫入快取和資料庫 |當讀取>>寫入時；一致性很重要|
| **後寫** |寫入快取；非同步寫入資料庫|高寫入吞吐量；一些資料遺失風險|
| **TTL（生存時間）** |快取條目在設定時間後過期 |當資料週期性變化時 |
| **無效** |明確刪除過時的快取項目 |當您確切知道資料何時發生變化時 |
### 快取失效
電腦科學中兩個最難的問題：快取失效、命名事物和差一錯誤。
|戰略|描述 |
|----------|-------------|
| **基於 TTL** |條目在 N 秒後過期；簡單但可能提供過時的資料|
| **事件驅動** |資料改變時失效；更複雜但更準確|
| **基於版本** |包含版本號；變化增量 |
| **基於標籤** |標籤相關的快取條目；使所有帶有標籤 | 的條目無效

## 資料庫優化
資料庫往往是 Web 應用程式中最大的瓶頸。
|技術|描述 |影響 |
|------------|-------------|--------|
| **索引** |在 WHERE、JOIN、ORDER BY | 中使用的列上新增索引查詢速度提高 10-1000 倍 |
| **查詢最佳化** |避免選擇 *;使用 EXPLAIN 分析查詢 |減少 I/O |
| **連線池** |重複使用資料庫連線而非建立新連線 |消除連線開銷 |
| **讀取副本** |將讀取查詢路由到副本資料庫 |分配讀取負載 |
| **分區** |將大表拆分為較小的分區 |更快地查詢大型資料集 |
| **非規範化** |新增冗餘資料以避免連線 |讀取速度更快；寫入速度較慢|
| **物化視圖** |預先計算的查詢結果 |即時複雜查詢|
| **N+1預防** |使用 JOIN、預先載入或批次查詢 |消除數千個查詢 |

## 並發與平行
|概念 |說明 |何時使用 |
|---------|-------------|----------|
| **執行緒** |單一行程內的多個執行緒 | I/O 密集型任務（網路、磁碟）|
| **多重處理** |多重進程（繞過Python中的GIL）| CPU 密集型任務 |
| **非同步/等待** |協作多工處理；單執行緒|高並發 I/O（Web 伺服器）|
| **GPU 計算** |數千個平行核心 |矩陣運算；影像處理；機器學習 |
### 非同步與線程
|方面|異步/等待 |線程 |
|--------|------------|------------|
| **型號** |合作（任務產量控制）|搶佔式（操作系統切換線程）|
| **開銷** |非常低（無上下文切換）|更高（線程創建、上下文切換）|
| **複雜性** |更簡單的推理（單線程） |競爭條件、死鎖、鎖 |
| **最適合** |許多同時 I/O 操作 |阻止無法非同步的操作 |
| **限制** |無法在不阻塞的情況下使用 CPU 密集型程式碼 | Python 中的 GIL 限制了真正的並行性 |

## 前端效能
|技術|描述 |影響 |
|------------|-------------|--------|
| **縮小** |刪除空格並縮短變數名稱 |檔案小 20-40% |
| **捆綁** |將多個檔案合併為較少的請求 |較少的 HTTP 請求 |
| **程式碼分割** |僅載入目前頁面所需的程式碼 |更快的初始載入 |
| **延遲載入** |在需要時載入圖片和元件 |更快的初始渲染 |
| **搖樹** |從捆綁包中刪除未使用的代碼 |較小的捆綁 |
| **影像優化** |使用WebP/AVIF；響應式影像；延遲載入 |影像小 50-80% |
| **CDN** |從邊緣伺服器提供靜態資產 |降低全球延遲 |
| **HTTP/2 和 HTTP/3** |多路復用；標頭壓縮； 0-RTT |更快的協定開銷|
| **服務人員** |快取資源以供離線使用；推播通知 |更快的重複存取 |

## 記憶體優化
|技術|描述 |
|------------|-------------|
| **物件池** |重複使用物件而非建立新物件 |
| **串流媒體** |分塊處理數據，而不是將所有內容載入到記憶體中 |
| **生成器/迭代器** |一次產生一個值，而不是建構列表 |
| **記憶體映射檔案** |存取大檔案而不完全載入它們 |
| **垃圾收集調整** |根據您的工作負載調整 GC 參數 |
| **資料結構選擇** |使用陣列而不是鍊錶來實現快取局部性；使用集合進行成員資格測試 |

＃＃ 概括
效能優化是一個系統的過程：測量、識別瓶頸、修復它、再次測量。最大的勝利來自演算法改進和消除不必要的工作，而不是微觀優化。快取、資料庫索引和並發是最強大的工具。前端效能取決於最小化有效負載大小和往返行程。最重要的規則始終是相同的：不要猜測 - 個人資料。
