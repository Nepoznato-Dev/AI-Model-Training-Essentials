# การออกแบบ API และความล้มเหลวในการบูรณาการ
API (Application Programming Interfaces) เป็นเนื้อเยื่อเกี่ยวพันของซอฟต์แวร์สมัยใหม่ ช่วยให้บริการต่างๆ สื่อสาร ให้บุคคลที่สามบูรณาการ และปล่อยให้ทีมทำงานได้อย่างอิสระ เมื่อการออกแบบ API ผิดพลาด ผลที่ตามมาจะกระเพื่อมในทุกระบบที่ขึ้นอยู่กับระบบนั้น: การบูรณาการที่เสียหาย ช่องโหว่ด้านความปลอดภัย ความหงุดหงิดของนักพัฒนา และการเขียนใหม่ซึ่งมีค่าใช้จ่ายสูง ความล้มเหลวในการบูรณาการ ซึ่งระบบไม่สามารถสื่อสารได้อย่างน่าเชื่อถือ เป็นสาเหตุหนึ่งของเหตุการณ์การผลิตที่พบบ่อยที่สุด
---

## ความล้มเหลวในการออกแบบ API ทั่วไป
### ข้อผิดพลาดในการออกแบบ
| ความผิดพลาด | คำอธิบาย | ผลที่ตามมา |
|---------|-------------|-------------|
| **การตั้งชื่อไม่สอดคล้องกัน** | `/getUsers`กับ`/list_users`กับ`/fetch-users`| ความสับสน; ข้อผิดพลาด; การพัฒนาช้า |
| **ปลายทางโอเวอร์โหลด** | จุดสิ้นสุดหนึ่งจุดที่ทำ 10 สิ่งที่แตกต่างกันตามพารามิเตอร์ | ยากที่จะเข้าใจ ยากที่จะทดสอบ ยากที่จะเปลี่ยน |
| **ดึงข้อมูลน้อยเกินไป** | ลูกค้าจำเป็นต้องทำการเรียก API 5 ครั้งเพื่อรับข้อมูลที่เกี่ยวข้อง | ช้า; สิ้นเปลือง; รหัสลูกค้าที่ซับซ้อน |
| **ดึงข้อมูลมากเกินไป** | API ส่งคืนฟิลด์ทั้งหมดเมื่อไคลเอ็นต์ต้องการเพียง 2 | แบนด์วิธที่สิ้นเปลือง ช้าบนมือถือ ความเสี่ยงด้านความปลอดภัย (เปิดเผยข้อมูลที่ไม่จำเป็น) |
| **ไม่มีเวอร์ชัน** | การเปลี่ยนแปลงที่นำไปใช้งานโดยไม่มีการเตือน | ลูกค้าแตก; นักพัฒนาโกรธ |
| **ข้อความแสดงข้อผิดพลาดคลุมเครือ** | "ข้อผิดพลาด 500: ข้อผิดพลาดเซิร์ฟเวอร์ภายใน" โดยไม่มีรายละเอียด | ไม่สามารถแก้ไขข้อบกพร่องได้ ความละเอียดช้า |
| **ไม่มีการแบ่งหน้า** | Endpoint ส่งคืนบันทึกทั้งหมด (อาจเป็นล้าน) | หมดเวลา; ความจำเสื่อม; ลูกค้าขัดข้อง |
| **รหัสสถานะไม่สอดคล้องกัน** | 200 ตกลงสำหรับข้อผิดพลาด 500 สำหรับความผิดพลาดของลูกค้า | ลูกค้าไม่สามารถแยกแยะความสำเร็จจากความล้มเหลว | ได้
### รูปแบบการต่อต้าน REST API
| ต่อต้านรูปแบบ | คำอธิบาย | แนวทางที่ดีกว่า |
|-----------------|-------------|-----------------|
| **การใช้ GET เพื่อการกลายพันธุ์** | `GET /delete-user?id=5`| ใช้วิธี DELETE |
| **ใช้ POST เพื่อทุกสิ่ง** | `POST /get-users`; `POST /update-user`| ใช้วิธีการ HTTP ที่เหมาะสม (GET, POST, PUT, PATCH, DELETE) |
| **การส่งคืน HTML จาก API** | API ส่งคืนแฟรกเมนต์ HTML | ส่งคืน JSON; ให้ลูกค้าเรนเดอร์ |
| **ตรรกะทางธุรกิจใน URL** | `/users/active/premium/from-2023`| ใช้พารามิเตอร์การค้นหาหรือเนื้อหาคำขอสำหรับตัวกรองที่ซับซ้อน |
| **การเปิดเผยสคีมาฐานข้อมูล** | `/api/table_name/column`| ออกแบบ API เกี่ยวกับทรัพยากรและแนวคิดโดเมน ไม่ใช่ตาราง |
| **ไม่มี HATEOAS / ลิงก์** | ไคลเอนต์ฮาร์ดโค้ด URL ทั้งหมด | รวมลิงก์ไปยังแหล่งข้อมูลที่เกี่ยวข้องในการตอบกลับ |

## ความล้มเหลวด้านความปลอดภัย
### ช่องโหว่ API ทั่วไป
| ช่องโหว่ | คำอธิบาย | ตัวอย่าง |
|--------------|-------------|---------|
| **การรับรองความถูกต้องใช้งานไม่ได้** | API ไม่ยืนยันตัวตนอย่างถูกต้อง | ไม่มีการตรวจสอบโทเค็น ยอมรับโทเค็นที่หมดอายุแล้ว |
| **การเปิดเผยข้อมูลมากเกินไป** | API ส่งคืนข้อมูลมากกว่าความต้องการของลูกค้า | จุดสิ้นสุดของผู้ใช้ส่งคืนแฮชของรหัสผ่านและรหัสภายใน |
| **การมอบหมายงานจำนวนมาก** | ลูกค้าสามารถตั้งค่าฟิลด์ที่ไม่ควร | `PATCH /user`อนุญาตให้ตั้งค่า`role: "admin"`|
| **ฉีด** | อินพุตของผู้ใช้ตีความว่าเป็นรหัส | การฉีด SQL; การฉีด NoSQL; คำสั่งฉีด |
| **IDOR** (การอ้างอิงวัตถุโดยตรงที่ไม่ปลอดภัย) | การเข้าถึงทรัพยากรโดยการเปลี่ยน ID ใน URL | `/api/users/5`→ เปลี่ยนเป็น`/api/users/6`เพื่อดูข้อมูลของผู้อื่น |
| **ไม่มีการจำกัดอัตรา** | ไม่จำกัดการเรียก API | กำลังดุร้าย; การปฏิเสธการให้บริการ การขูด |
| **การกำหนดค่า CORS ไม่ถูกต้อง** | การเข้าถึงแบบข้ามต้นทางที่อนุญาตมากเกินไป | `Access-Control-Allow-Origin: *`บนจุดสิ้นสุดที่ได้รับการรับรองความถูกต้อง |
### การรับรองความถูกต้องและการอนุญาตล้มเหลว
| ความล้มเหลว | คำอธิบาย | ผลกระทบ |
|---------|-------------|--------|
| **ข้อมูลรับรองฮาร์ดโค้ด** | คีย์ API หรือรหัสผ่านในซอร์สโค้ด | รั่วไหลผ่านการควบคุมเวอร์ชัน เข้าถึงได้โดยนักพัฒนาทุกคน |
| **โทเค็นไม่มีวันหมดอายุ** | โทเค็นไม่มีวันหมดอายุ | โทเค็นที่ถูกขโมยให้การเข้าถึงแบบถาวร |
| **รหัสลับที่อ่อนแอ** | คีย์การลงนามแบบสั้นหรือคาดเดาได้ | โทเค็นสามารถปลอมแปลงได้ |
| **ไม่มีขอบเขต / สิทธิ์** | โทเค็นทั้งหมดมีสิทธิ์เข้าถึงแบบเต็ม | โทเค็นที่ถูกบุกรุก = การเข้าถึงระบบเต็มรูปแบบ |
| **การบันทึกข้อมูลที่ละเอียดอ่อน** | โทเค็นหรือรหัสผ่านในบันทึก | เข้าถึงได้โดยทุกคนที่มีสิทธิ์เข้าถึงบันทึก |
| **การอนุญาตไม่สอดคล้องกัน** | จุดสิ้นสุดบางแห่งตรวจสอบสิทธิ์ คนอื่นไม่ได้ | การเข้าถึงโดยไม่ได้รับอนุญาตผ่านจุดสิ้นสุดที่ไม่ได้รับการปกป้อง |

## ความล้มเหลวในการบูรณาการ
### ปัญหาการรวมระบบแบบกระจาย
| ความล้มเหลว | คำอธิบาย | ตัวอย่าง |
|---------|-------------|---------|
| **ข้อต่อแน่น** | บริการขึ้นอยู่กับรายละเอียดการใช้งานภายในของกันและกัน | การเปลี่ยนฐานข้อมูลของบริการหนึ่งจะทำลายฐานข้อมูลอีกสามรายการ |
| **โซ่ซิงโครนัส** | บริการ A โทร B โทร C โทร D; เวลาแฝงสะสม | 200ms + 300ms + 500ms = เวลาตอบสนอง 1 วินาที |
| **ไม่มีเบรกเกอร์** | บริการที่ล้มเหลวทำให้เกิดความล้มเหลวแบบเรียงซ้อน | บริการ D ช้า; บริการอัปสตรีมทั้งหมดหมดเธรดที่รอ |
| **ไม่มีตรรกะในการลองใหม่อีกครั้ง** | ความล้มเหลวชั่วคราวกลายเป็น | ถาวร Network blip = ธุรกรรมล้มเหลว ผู้ใช้ต้องลองอีกครั้งด้วยตนเอง |
| **ลองใหม่มากเกินไป** | การลองใหม่โดยไม่มีการถอยกลับจะทำให้บริการกู้คืนเสียหายมากเกินไป ปัญหาฝูงฟ้าร้อง |
| **ไม่มีค่าคงที่** | การลองการดำเนินการที่ไม่ใช่ idempotent อีกครั้งจะสร้างรายการที่ซ้ำกัน | เรียกเก็บเงินสองครั้ง; คำสั่งซื้อสร้างสองครั้ง |
| **ความสม่ำเสมอที่น่าประหลาดใจในที่สุด** | ลูกค้าอ่านข้อมูลเก่าหลังจากเขียน | โปรไฟล์การอัปเดตผู้ใช้ รีเฟรชหน้า; ข้อมูลเก่ายังคงแสดงอยู่ |
### ความล้มเหลวในการรวมระบบของบุคคลที่สาม
| ความล้มเหลว | คำอธิบาย | การบรรเทาผลกระทบ |
|---------|-------------|------------|
| **การเปลี่ยนแปลง API ของผู้ขาย** | บุคคลที่สามเปลี่ยนแปลง API ของตนโดยไม่ต้องแจ้งให้ทราบล่วงหน้า | การปักหมุดเวอร์ชัน ชั้นนามธรรม การตรวจสอบบันทึกการเปลี่ยนแปลงของผู้ขาย |
| **จำกัดอัตรา** | บุคคลที่สามควบคุมคำขอของคุณ | แคช; ขอคิว; กำลังเจรจาขีดจำกัดที่สูงขึ้น |
| **การหยุดทำงานของผู้ขาย** | บริการของบุคคลที่สามไม่พร้อมใช้งาน | เบรกเกอร์วงจร; พฤติกรรมทางเลือก กลยุทธ์ผู้ค้าหลายราย |
| **รูปแบบข้อมูลเปลี่ยนแปลง** | รูปแบบการตอบกลับการเปลี่ยนแปลงของบุคคลที่สาม | การตรวจสอบสคีมา ชั้นการเปลี่ยนแปลง การแจ้งเตือนเกี่ยวกับการเปลี่ยนแปลงรูปแบบ |
| **การเลิกใช้งานโดยไม่มีเส้นทางการโยกย้าย** | ผู้ขายเลิกใช้จุดสิ้นสุดโดยไม่มีค่าเทียบเท่า | ติดตามข่าวสาร; รักษาความเป็นนามธรรม วางแผนการโยกย้ายในช่วงต้น |

## กรณีศึกษา
### กรณีศึกษา 1: API ที่ส่งคืนทุกสิ่ง
| ด้าน | คำอธิบาย |
|--------|-------------|
| **สถานการณ์** | API ผู้ใช้ของบริษัท SaaS ส่งคืนช่องผู้ใช้ทั้งหมด รวมถึงข้อมูลเมตาภายใน |
| **เกิดอะไรขึ้น** | ไม่มีการกรองฟิลด์ การตอบสนองรวมถึงการแฮชรหัสผ่าน บันทึกภายใน และการตั้งค่าสถานะของผู้ดูแลระบบ |
| **ผลกระทบ** | นักวิจัยด้านความปลอดภัยค้นพบความเสี่ยงดังกล่าว การเปิดเผยต่อสาธารณะ การสอบสวน GDPR |
| **สาเหตุที่แท้จริง** | API ทำให้โมเดลฐานข้อมูลทั้งหมดเป็นอนุกรมโดยไม่ต้องกรอง |
| **แก้ไข** | โมเดลการตอบสนองที่ชัดเจน การควบคุมการเข้าถึงระดับฟิลด์ การตรวจสอบความปลอดภัยของปลายทางทั้งหมด |
| **บทเรียน** | อย่าเปิดเผยโมเดลฐานข้อมูลของคุณโดยตรงผ่าน API ใช้ DTO (วัตถุการถ่ายโอนข้อมูล) |
### กรณีศึกษา 2: ความล้มเหลวแบบเรียงซ้อน
| ด้าน | คำอธิบาย |
|--------|-------------|
| **สถานการณ์** | สถาปัตยกรรมไมโครเซอร์วิสพร้อมการสื่อสารระหว่างบริการแบบซิงโครนัส
| **เกิดอะไรขึ้น** | บริการหนึ่งประสบปัญหาการชะลอตัวของฐานข้อมูล บริการต้นน้ำรอการตอบสนอง เธรดพูลหมด |
| **ผลกระทบ** | ระบบหยุดทำงานอย่างสมบูรณ์เป็นเวลา 45 นาที; บริการทั้งหมดที่ได้รับผลกระทบ |
| **สาเหตุที่แท้จริง** | ไม่มีเบรกเกอร์วงจร ไม่มีการหมดเวลา ห่วงโซ่การพึ่งพาแบบซิงโครนัส |
| **แก้ไข** | เบรกเกอร์วงจร; หมดเวลา; การสื่อสารแบบอะซิงก์หากเป็นไปได้ กั้น |
| **บทเรียน** | การโทรแบบซิงโครนัสระหว่างบริการจะสร้างเครือข่ายที่เปราะบาง การออกแบบเพื่อความล้มเหลว |

## แนวทางปฏิบัติที่ดีที่สุด
### รายการตรวจสอบการออกแบบ API
| พื้นที่ | การปฏิบัติ |
|------|----------|
| **การตั้งชื่อ** | ใช้คำนามสำหรับทรัพยากร วิธีการ HTTP สำหรับการดำเนินการ แบบแผนการตั้งชื่อที่สอดคล้องกัน |
| **เวอร์ชัน** | เวอร์ชันตั้งแต่วันแรก ใช้การกำหนดเวอร์ชัน URL (`/v1/`) หรือการกำหนดเวอร์ชันส่วนหัว |
| **การแบ่งหน้า** | แบ่งหน้ารายการปลายทางเสมอ ใช้การแบ่งหน้าตามเคอร์เซอร์สำหรับชุดข้อมูลขนาดใหญ่ |
| **การจัดการข้อผิดพลาด** | รูปแบบข้อผิดพลาดที่สอดคล้องกัน รวมรหัสข้อผิดพลาด ระบุข้อความที่สามารถดำเนินการได้ |
| **จำกัดอัตรา** | ดำเนินการจำกัดอัตรา ส่งคืน 429 พร้อมส่วนหัวลองใหม่อีกครั้ง |
| **ความเป็นอมตะ** | รองรับคีย์ idempotency สำหรับจุดสิ้นสุดการกลายพันธุ์ |
| **เอกสาร** | ข้อมูลจำเพาะ OpenAPI / Swagger; อัปเดตอยู่เสมอ ให้ตัวอย่าง |
| **การทดสอบ** | การทดสอบสัญญา การทดสอบบูรณาการ การทดสอบสัญญาที่ขับเคลื่อนโดยผู้บริโภค |
| **การตรวจสอบ** | ติดตามเวลาแฝง; อัตราความผิดพลาด ปริมาณงาน; สุขภาพพึ่งพา |
| **การคัดค้าน** | ประกาศการเลิกใช้งานล่วงหน้า ให้คำแนะนำการโยกย้าย |

## สรุป
ความล้มเหลวในการออกแบบ API มีตั้งแต่ความสวยงาม (การตั้งชื่อไม่สอดคล้องกัน) ไปจนถึงภัยพิบัติ (ช่องโหว่ด้านความปลอดภัย ความล้มเหลวแบบเรียงซ้อน) ข้อผิดพลาดในการออกแบบที่พบบ่อยที่สุด — ตำแหน่งข้อมูลโอเวอร์โหลด, การดึงข้อมูลมากเกินไป, การแบ่งหน้าหายไป, ข้อผิดพลาดที่คลุมเครือ — ทำให้ใช้งานและบำรุงรักษา API ได้ยาก ความล้มเหลวในการรักษาความปลอดภัย - การรับรองความถูกต้องที่เสียหาย, IDOR, การมอบหมายจำนวนมาก, การเปิดเผยข้อมูลมากเกินไป - ทำให้ระบบถูกโจมตี ความล้มเหลวในการบูรณาการ - การมีเพศสัมพันธ์ที่แน่นหนา, โซ่ซิงโครนัส, เซอร์กิตเบรกเกอร์หายไป, ไม่มีความสม่ำเสมอ - สร้างระบบที่เปราะบางซึ่งความล้มเหลวหนึ่งทอดข้ามบริการต่างๆ การบูรณาการกับบุคคลที่สามเพิ่มความเสี่ยงภายนอก: การเปลี่ยนแปลง API การจำกัดอัตรา และการหยุดทำงานของผู้ขาย กลยุทธ์การป้องกันได้รับการยอมรับอย่างดี: ใช้แบบจำลองการตอบสนองที่ชัดเจน เวอร์ชันตั้งแต่วันแรก ใช้เซอร์กิตเบรกเกอร์และการหมดเวลา การออกแบบเพื่อความสม่ำเสมอ ตรวจสอบและฆ่าเชื้ออินพุตทั้งหมด ตรวจสอบทุกอย่าง และถือว่าสัญญา API เป็นข้อตกลงที่มีผลผูกพันซึ่งต้องมีการประสานงานในการเปลี่ยนแปลง API ที่ดีที่สุดนั้นน่าเบื่อ — คาดเดาได้ สม่ำเสมอ มีการจัดทำเอกสารอย่างดี และทนทานต่อความล้มเหลว
