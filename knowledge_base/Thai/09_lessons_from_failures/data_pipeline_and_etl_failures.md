# Data Pipeline และความล้มเหลวของ ETL
ไปป์ไลน์ข้อมูลเป็นเหมือนระบบประปาขององค์กรยุคใหม่ โดยจะย้ายข้อมูลจากระบบต้นทางผ่านการเปลี่ยนแปลงไปยังฐานข้อมูล คลังสินค้า และทะเลสาบ ซึ่งใช้สำหรับการวิเคราะห์ การเรียนรู้ของเครื่อง และการตัดสินใจ เมื่อพวกเขาทำงานไม่มีใครสังเกตเห็น เมื่อล้มเหลว การตัดสินใจจะดำเนินการกับข้อมูลเก่า ฝึกแบบจำลองเกี่ยวกับขยะ รายงานแสดงตัวเลขที่เป็นไปไม่ได้ และความไว้วางใจในแพลตฟอร์มข้อมูลทั้งหมดก็กัดกร่อน ความล้มเหลวไปป์ไลน์ข้อมูลถือเป็นความล้มเหลวที่พบบ่อยที่สุดและมีค่าใช้จ่ายสูงที่สุดในองค์กรเทคโนโลยี
---

## โหมดความล้มเหลวทั่วไป
### ปัญหาคุณภาพของข้อมูล
| ความล้มเหลว | คำอธิบาย | ผลกระทบ | ความยากในการตรวจจับ |
|---------|-------------|--------|---------------------|
| **ความเสียหายของข้อมูลเงียบ** | ข้อมูลถูกแก้ไขอย่างไม่ถูกต้องโดยไม่มีข้อผิดพลาดใดๆ | ระบบดาวน์สตรีมเชื่อถือข้อมูลที่ไม่ดี การตัดสินใจบนพื้นฐานของข้อมูลเท็จ | ยากมาก — ไม่มีสัญญาณข้อผิดพลาด |
| **สคีมาดริฟท์** | ระบบต้นทางเปลี่ยนสคีมา (เพิ่ม ลบ เปลี่ยนชื่อคอลัมน์) | ไปป์ไลน์หยุดหรือปล่อยข้อมูลอย่างเงียบ ๆ | ปานกลาง — ไปป์ไลน์อาจล้มเหลวหรือให้ผลลัพธ์บางส่วน |
| **ประเภทข้อมูลไม่ตรงกัน** | Source ส่งสตริงโดยที่คาดว่าจะเป็นจำนวนเต็ม การเปลี่ยนแปลงความแม่นยำของโฟลต | ไปป์ไลน์ล้มเหลว ข้อมูลถูกตัดทอน ข้อผิดพลาดในการปัดเศษ | ปานกลาง — อาจทำให้เกิดข้อผิดพลาดไปป์ไลน์หรือปัญหาข้อมูลที่ละเอียดอ่อน |
| **บันทึกซ้ำ** | เหตุการณ์เดียวกันได้รับการประมวลผลหลายครั้ง | จำนวนที่สูงเกินจริง; การรวมตัวไม่ถูกต้อง | ยาก — แต่ละระเบียนดูถูกต้องแยกกัน |
| **ค่า Null / หายไป** | ช่องที่คาดหวังจะว่างเปล่า | การคำนวณล้มเหลว โมเดลสร้างการทำนายที่ผิด | ปานกลาง — ขึ้นอยู่กับการจัดการค่าว่าง |
| **ค่าอยู่นอกช่วง** | ค่าอยู่นอกขอบเขตที่คาดไว้ (อายุเชิงลบ วันที่ในอนาคต) | สถิติบิดเบือน; ตรรกะทางธุรกิจที่พัง | ปานกลาง — ต้องมีกฎการตรวจสอบ |
| **ข้อมูลที่มาล่าช้า** | ข้อมูลมาถึงหลังจากหน้าต่างการประมวลผลปิด | ผลลัพธ์ที่ไม่สมบูรณ์ บันทึกที่ไม่ได้รับ | ยาก — ผลลัพธ์ดูสมบูรณ์แต่ไม่ใช่ |
### ปัญหาโครงสร้างพื้นฐานไปป์ไลน์
| ความล้มเหลว | คำอธิบาย | ผลกระทบ |
|---------|-------------|--------|
| **การเรียบเรียงล้มเหลว** | Scheduler (Airflow, Prefect) ไม่ทริกเกอร์ไปป์ไลน์ | ข้อมูลเก่าแล้ว ไม่มีการประมวลผลเกิดขึ้น |
| **การสิ้นเปลืองทรัพยากร** | ไปป์ไลน์หน่วยความจำ CPU หรือดิสก์ไม่เพียงพอ | ท่อล่ม; ผลลัพธ์บางส่วน |
| **ความล้มเหลวในการพึ่งพา** | ระบบอัปสตรีมล่มหรือช้า | ไปป์ไลน์รออย่างไม่มีกำหนดหรือล้มเหลว |
| **ปัญหาที่เกิดขึ้นพร้อมกัน** | ไปป์ไลน์หลายรายการแก้ไขข้อมูลเดียวกันพร้อมกัน | สภาพการแข่งขัน; ข้อมูลเสียหาย |
| **การกำหนดค่าลอยตัว** | การเปลี่ยนแปลงสภาพแวดล้อม (เครือข่าย ข้อมูลประจำตัว อุปกรณ์ปลายทาง) ไม่แสดงในไปป์ไลน์ | ไปป์ไลน์ล้มเหลวโดยไม่คาดคิด |
| **แรงดันต้านกลับ** | ข้อมูลมาถึงเร็วกว่าที่ไปป์ไลน์สามารถประมวลผลได้ | คิวที่เพิ่มขึ้น เวลาแฝงที่เพิ่มขึ้น |

## กรณีศึกษา
### กรณีศึกษา 1: การทำสำเนาข้อมูลแบบเงียบ
| ด้าน | คำอธิบาย |
|--------|-------------|
| **สถานการณ์** | ไปป์ไลน์คำสั่งซื้อของบริษัทอีคอมเมิร์ซจะประมวลผลเหตุการณ์จากคิวข้อความ |
| **เกิดอะไรขึ้น** | การรีสตาร์ทของผู้บริโภคทำให้มีการใช้ข้อความอีกครั้ง ไม่มีตรรกะการขจัดข้อมูลซ้ำซ้อน |
| **ผลกระทบ** | ตัวเลขรายได้สูงเกินจริง 15% เป็นเวลา 3 สัปดาห์ก่อนที่จะมีใครสังเกตเห็น |
| **สาเหตุที่แท้จริง** | ไม่มีคีย์ idempotency จัดส่งอย่างน้อยหนึ่งครั้งโดยไม่มีการขจัดข้อมูลซ้ำซ้อน |
| **แก้ไข** | เพิ่มคีย์ idempotency ตามรหัสคำสั่งซื้อ ดำเนินการความหมายเพียงครั้งเดียว |
| **บทเรียน** | การส่งมอบอย่างน้อยหนึ่งครั้งต้องมีการขจัดข้อมูลซ้ำซ้อน ตรวจสอบผลรวมกับระบบต้นทางเสมอ |
### กรณีศึกษา 2: การเปลี่ยนแปลงสคีมาเกิดขึ้นที่ปลายน้ำ
| ด้าน | คำอธิบาย |
|--------|-------------|
| **สถานการณ์** | ผู้ให้บริการชำระเงินเปลี่ยนชื่อฟิลด์ในการตอบกลับ API |
| **เกิดอะไรขึ้น** | ไปป์ไลน์ ETL เริ่มเขียนค่าว่างอย่างเงียบๆ ไม่มีการตรวจสอบสคีมา |
| **ผลกระทบ** | รายงานทางการเงินแสดงรายได้จากวิธีการชำระเงินดังกล่าวเป็นศูนย์เป็นเวลา 2 เดือน |
| **สาเหตุที่แท้จริง** | ไม่มีการตรวจสอบความถูกต้องของสคีมาเมื่อนำเข้า ค่า Null ถือเป็นค่าที่ถูกต้อง |
| **แก้ไข** | เพิ่มการตรวจสอบสคีมาพร้อมการแจ้งเตือน ฟิลด์บังคับบังคับ; การตรวจสอบเป็นโมฆะ |
| **บทเรียน** | อย่าเชื่อถือสคีมาภายนอกให้คงความเสถียร ตรวจสอบที่ขอบเขต |
### กรณีศึกษา 3: ภัยพิบัติเขตเวลา
| ด้าน | คำอธิบาย |
|--------|-------------|
| **สถานการณ์** | บริษัทระดับโลกรวบรวมตัวชี้วัดรายวันจากสำนักงานต่างๆ |
| **เกิดอะไรขึ้น** | แหล่งข้อมูลบางแห่งใช้ UTC แหล่งอื่นใช้เวลาท้องถิ่น ไปป์ไลน์ไม่ทำให้เป็นมาตรฐาน |
| **ผลกระทบ** | ยอดรวมรายวันไม่ตรงกัน ธุรกรรมบางรายการนับผิดวัน ปิดสิ้นเดือนผิด |
| **สาเหตุที่แท้จริง** | ไม่มีนโยบายเขตเวลามาตรฐาน การประทับเวลาถูกจัดเก็บไม่สอดคล้องกัน |
| **แก้ไข** | การประทับเวลาทั้งหมดจัดเก็บเป็น UTC แปลงเป็นเวลาท้องถิ่นที่เลเยอร์การนำเสนอเท่านั้น |
| **บทเรียน** | สร้างมาตรฐานให้กับ UTC ทุกที่ มีความชัดเจนเกี่ยวกับเขตเวลาในทุกขอบเขต |

## กลยุทธ์การป้องกัน
### การตรวจสอบข้อมูล
| กลยุทธ์ | คำอธิบาย | ตัวอย่างเครื่องมือ |
|----------|-------------|---------------|
| **การตรวจสอบสคีมา** | ตรวจสอบข้อมูลที่ตรงกับสคีมาที่คาดหวังในแต่ละขั้นตอน | ความคาดหวังอันยิ่งใหญ่; ดีคู; โซดา |
| **ตรวจสอบระยะ** | ค่าอยู่ภายในขอบเขตที่คาดไว้ | การยืนยันที่กำหนดเอง การทดสอบ dbt |
| **เช็คความสด** | ข้อมูลล่าสุดเพียงพอที่จะมีประโยชน์ | การตรวจสอบการประทับเวลา การแจ้งเตือน SLA |
| **ตรวจสอบปริมาณ** | จำนวนแถวอยู่ภายในช่วงที่คาดไว้ | การตรวจจับความผิดปกติในการนับแถว |
| **ความสมบูรณ์ของการอ้างอิง** | การจับคู่คีย์ต่างประเทศ ไม่มีบันทึกกำพร้า | ข้อจำกัดของ SQL เครื่องมือคุณภาพข้อมูล |
| **การกระทบยอดข้ามแหล่งที่มา** | ผลรวมตรงกันระหว่างแหล่งที่มาและเป้าหมาย | งานกระทบยอดอัตโนมัติ |
### รูปแบบการออกแบบท่อ
| รูปแบบ | คำอธิบาย | ผลประโยชน์ |
|---------|-------------|---------|
| **ความเป็นอมตะ** | การเรียกใช้ไปป์ไลน์หลายครั้งจะให้ผลลัพธ์เดียวกัน | ปลอดภัยที่จะลองอีกครั้ง ไม่ซ้ำกัน |
| **ความเป็นปรมาณู** | ไปป์ไลน์สำเร็จอย่างสมบูรณ์หรือล้มเหลวทั้งหมด (ไม่มีสถานะบางส่วน) | ไม่มีข้อมูลที่ประมวลผลครึ่งหนึ่ง |
| **จุดตรวจ** | บันทึกความคืบหน้าในแต่ละขั้นตอน ดำเนินการต่อจากจุดตรวจสุดท้าย | ความทนทานต่อความผิดพลาด ไม่มีการประมวลผลซ้ำ |
| **คิวจดหมายตาย** | บันทึกที่ล้มเหลวไปที่คิวแยกต่างหากเพื่อตรวจสอบ | ไม่มีข้อมูลสูญหาย สามารถตรวจสอบและเล่นซ้ำ |
| **เซอร์กิตเบรกเกอร์** | หยุดการประมวลผลเมื่อดาวน์สตรีมล้มเหลว | ป้องกันความล้มเหลวแบบเรียงซ้อน |
| **สัญญาข้อมูล** | ข้อตกลงระหว่างผู้ผลิตและผู้บริโภคเกี่ยวกับรูปแบบข้อมูล | การเปลี่ยนแปลงสคีมาได้รับการประสานงาน |
### การตรวจสอบและการแจ้งเตือน
| สิ่งที่ต้องตรวจสอบ | ทำไม | อย่างไร |
|-----------------|-----|-----|
| **ระยะเวลาของท่อ** | ระยะเวลาที่เพิ่มขึ้นบ่งบอกถึงปัญหา | การวิเคราะห์แนวโน้ม การติดตาม SLA |
| **การนับแถว** | การเปลี่ยนแปลงกะทันหันบ่งบอกถึงปัญหา | เปรียบเทียบกับค่าเฉลี่ยในอดีต |
| **อัตราว่าง** | การเพิ่มสคีมาสัญญาณ null หรือปัญหาแหล่งที่มา | การติดตามโมฆะระดับคอลัมน์ |
| **ความใหม่ของข้อมูล** | ข้อมูลเก่าหมายความว่าไปป์ไลน์ไม่ทำงาน | การประทับเวลาของบันทึกล่าสุด |
| **ผลกระทบปลายน้ำ** | รายงานและแบบจำลองใช้ข้อมูลที่ถูกต้องหรือไม่ | สายข้อมูลแบบ end-to-end |
| **การใช้ทรัพยากร** | ซีพียู; หน่วยความจำ; ดิสก์; เครือข่าย | การตรวจสอบโครงสร้างพื้นฐาน |

## กลยุทธ์การกู้คืน
| สถานการณ์ | กลยุทธ์ |
|----------|----------|
| **ข้อมูลไม่ถูกต้องในคลังสินค้าแล้ว** | ระบุช่วงเวลาที่ได้รับผลกระทบ ประมวลผลใหม่จากแหล่งที่มา แจ้งผู้บริโภคปลายน้ำ |
| **ไปป์ไลน์ล้มเหลวระหว่างดำเนินการ** | การออกแบบ Idempotent ช่วยให้สามารถรันซ้ำได้อย่างปลอดภัย จุดตรวจอนุญาตให้ดำเนินการต่อ |
| **การเปลี่ยนแปลงสคีมาทำให้ไปป์ไลน์เสียหาย** | แก้ไขการเปลี่ยนแปลง ทดแทนข้อมูลที่ได้รับผลกระทบ เพิ่มการจัดการวิวัฒนาการสคีมา |
| **คอรัปชั่นเงียบๆ ค้นพบช้า** | การวิเคราะห์สาเหตุที่แท้จริง กำหนดรัศมีการระเบิด ประมวลผลใหม่; เพิ่มการตรวจสอบเพื่อตรวจจับการเกิดซ้ำ |
| **ข้อมูลสูญหาย** | กู้คืนจากข้อมูลสำรอง เล่นซ้ำจากแหล่งที่มา ประเมินว่าขาดทุนสามารถขอคืนได้หรือไม่ |

## สรุป
ความล้มเหลวของไปป์ไลน์ข้อมูลมีอยู่ทั่วไปและมักมีค่าใช้จ่ายสูงกว่าการหยุดทำงานของแอปพลิเคชัน เนื่องจากทำให้เกิดคำตอบที่ผิดมากกว่าข้อผิดพลาดที่ชัดเจน ความเสียหายของข้อมูลโดยไม่โต้ตอบ การเคลื่อนของสคีมา การซ้ำกัน ข้อบกพร่องของเขตเวลา และค่าที่หายไปคือสาเหตุที่พบบ่อยที่สุด กลยุทธ์การป้องกันที่สำคัญคือ: ตรวจสอบความถูกต้องของข้อมูลในทุกขอบเขต (สคีมา ช่วง ปริมาณ ความสดใหม่) ออกแบบท่อให้เป็นแบบไอดีโมเทนต์และแบบอะตอมมิก ตรวจสอบทุกอย่าง (ระยะเวลา, จำนวนแถว, อัตราว่าง, ความใหม่); ใช้คิวจดหมายที่ไม่ทำงานสำหรับบันทึกที่ล้มเหลว และจัดทำสัญญาข้อมูลระหว่างผู้ผลิตและผู้บริโภค เมื่อเกิดความล้มเหลว การตอบสนองควรรวมถึงการวิเคราะห์สาเหตุที่แท้จริง การประมวลผลข้อมูลที่ได้รับผลกระทบใหม่ การแจ้งเตือนผู้บริโภคขั้นปลาย และ — ขั้นวิกฤต — เพิ่มการตรวจสอบเพื่อตรวจจับความล้มเหลวระดับเดียวกันในอนาคต องค์กรที่ได้รับสิทธิ์นี้ปฏิบัติต่อไปป์ไลน์ข้อมูลด้วยความเข้มงวดเช่นเดียวกับซอฟต์แวร์ที่ใช้งานจริง: การทดสอบ การตรวจสอบ การแจ้งเตือน การตอบสนองต่อเหตุการณ์ และการชันสูตรพลิกศพ
