# ความล้มเหลวของโครงการการเรียนรู้ของเครื่อง
โปรเจ็กต์แมชชีนเลิร์นนิงล้มเหลวในอัตราที่น่าตกใจ - ประมาณการทางอุตสาหกรรมแนะนำว่า 60-85% ของโปรเจ็กต์ ML ไม่เคยมีการผลิตจริง ความล้มเหลวมักจะไม่อยู่ในอัลกอริธึม พวกเขาอยู่ในกระบวนการ ข้อมูล ความคาดหวัง และบริบทขององค์กร การทำความเข้าใจว่าเหตุใดโปรเจ็กต์ ML จึงล้มเหลวถือเป็นสิ่งสำคัญสำหรับทุกคนที่สร้างระบบ ML เนื่องจากโหมดความล้มเหลวนั้นสามารถคาดเดาได้และหลีกเลี่ยงได้เป็นส่วนใหญ่
---

## เหตุใดโครงการ ML จึงล้มเหลว
### หมวดหมู่ความล้มเหลว
| หมวดหมู่ | ส่วนแบ่งของความล้มเหลว | คำอธิบาย |
|----------|------------------|-------------|
| **ปัญหาข้อมูล** | ~30% | ข้อมูลไม่เพียงพอ มีอคติ ไม่มีข้อมูลเก่า หรือไม่สามารถเข้าถึงได้ |
| **คำจำกัดความของปัญหา** | ~20% | ปัญหา ML ไม่ตรงกับความต้องการทางธุรกิจ |
| **ความคาดหวังไม่ตรงกัน** | ~15% | ผู้มีส่วนได้ส่วนเสียคาดหวังความมหัศจรรย์ ความเป็นจริงคือการปรับปรุงแบบค่อยเป็นค่อยไป |
| **ความล้มเหลวในการปรับใช้** | ~15% | โมเดลใช้งานได้ในโน้ตบุ๊กแต่ไม่สามารถผลิตได้ |
| ** ปัญหาองค์กร** | ~10% | ไม่มีความเป็นเจ้าของที่ชัดเจน ทีมขาดทักษะ ไม่มีการสนับสนุนจากผู้บริหาร |
| **ประสิทธิภาพของโมเดล** | ~10% | โมเดลไม่มีความแม่นยำตามที่กำหนดหรือสรุปได้ไม่ดี |

## ความล้มเหลวเกี่ยวกับข้อมูล
### ปัญหาข้อมูลทั่วไป
| ปัญหา | คำอธิบาย | ตัวอย่าง |
|---------|-------------|---------|
| **ข้อมูลไม่เพียงพอ** | ตัวอย่างไม่เพียงพอที่จะเรียนรู้รูปแบบที่มีความหมาย | ฝึกอบรมโมเดลการตรวจจับการฉ้อโกงในธุรกรรม 500 รายการ |
| **คุณภาพฉลาก** | ป้ายกำกับการฝึกอบรมไม่ถูกต้อง ไม่สอดคล้องกัน หรือเป็นอัตวิสัย | ภาพทางการแพทย์ที่ติดป้ายกำกับโดยผู้ที่ไม่ใช่ผู้เชี่ยวชาญ ป้ายกำกับความเชื่อมั่นที่มีข้อตกลงระหว่างผู้ประเมินต่ำ |
| **ข้อมูลรั่วไหล** | ข้อมูลจากอนาคตหรือเป้าหมายรั่วไหลเข้าสู่ฟีเจอร์ | การใช้ผลลัพธ์การเลิกใช้งานของลูกค้าเป็นคุณลักษณะ รวมถึงข้อมูลการทดสอบในการฝึกอบรม |
| **อคติในการเลือก** | ข้อมูลการฝึกอบรมไม่ได้แสดงถึงประชากรการปรับใช้ | ฝึกอบรมโมเดลทางการแพทย์จากข้อมูลจากโรงพยาบาลแห่งหนึ่ง ปรับใช้ในระดับประเทศ |
| **แนวคิดล่องลอย** | ความสัมพันธ์ระหว่างคุณลักษณะและเป้าหมายเปลี่ยนแปลงตลอดเวลา | พฤติกรรมผู้บริโภคเปลี่ยนแปลงไปหลังเกิดโรคระบาด โมเดลที่ได้รับการฝึกอบรมเกี่ยวกับข้อมูลก่อนการแพร่ระบาด |
| **คุณสมบัติไม่ตรงกัน** | คุณลักษณะที่มีให้ในระหว่างการฝึกอบรมแตกต่างจากคุณลักษณะที่มีอยู่ในเวอร์ชันที่ใช้งานจริง | การฝึกอบรมโดยใช้ป้ายกำกับแบบแมนนวล การผลิตใช้ฉลากอัตโนมัติที่มีการแจกจ่ายที่แตกต่างกัน |
| **ความไม่สมดุลของคลาส** | คลาสเป้าหมายมีความเบ้อย่างมาก | ลบ 99%, บวก 1%; โมเดลเรียนรู้ที่จะทำนายเชิงลบเสมอ |
### ปัญหาข้อมูลรั่วไหล
| พิมพ์ | คำอธิบาย | ตัวอย่าง |
|------|-------------|---------|
| **เป้าหมายรั่ว** | คุณลักษณะจะพร้อมใช้งานเฉพาะหลังจากที่เป้าหมายเกิดขึ้น | “ผลการรักษา” ใช้เป็นคุณลักษณะในการทำนาย “ความสำเร็จของการรักษา” |
| **รถไฟ-ทดสอบการปนเปื้อน** | ข้อมูลการทดสอบมีอิทธิพลต่อการฝึกอบรม | ปรับขนาดด้วยสถิติทั่วโลก (รวมถึงข้อมูลการทดสอบ) การเพิ่มข้อมูลที่รั่วไหล |
| **อคติในการสุ่มตัวอย่าง** | การฝึกอบรมและการผลิตใช้การสุ่มตัวอย่างต่างกัน การฝึกอบรมเกี่ยวกับปริมาณการใช้เว็บ การปรับใช้กับการรับส่งข้อมูลแอพมือถือ |
| **การรั่วไหลก่อนการประมวลผล** | ขั้นตอนการประมวลผลล่วงหน้าใช้ข้อมูลจากชุดข้อมูลเต็ม | การใส่ค่าที่หายไปด้วยค่าเฉลี่ยส่วนกลาง (รวมข้อมูลการทดสอบ) |

## ความล้มเหลวในการนิยามปัญหา
### รูปแบบที่ไม่ตรงแนว
| รูปแบบ | คำอธิบาย | ผลที่ตามมา |
|---------|-------------|-------------|
| **แก้ปัญหาผิด** | ความต้องการทางธุรกิจ X; ทีมงานสร้าง Y | โมเดลมีเทคนิคดีแต่ไร้ประโยชน์ |
| **ML เมื่อกฎจะเพียงพอ** | ปัญหามีกฎเกณฑ์กำหนดไว้ ML เพิ่มความซับซ้อน | ออกแบบมากเกินไป; ยากต่อการบำรุงรักษา ตีความได้น้อย |
| **ML เมื่อไม่มีข้อมูล** | ปัญหาต้องใช้ข้อมูลที่ยังไม่ได้รวบรวม | โครงการไม่สามารถเริ่มต้นได้ เดือนที่เสียไปกับความเป็นไปได้ |
| **เป้าหมายที่แม่นยำโดยไม่มีบริบททางธุรกิจ** | "เราต้องการความแม่นยำ 95%" แต่สิ่งนี้มีความหมายต่อธุรกิจอย่างไร | โมเดลตรงตามความแม่นยำแต่ไม่ได้แก้ปัญหาทางธุรกิจ |
| **ละเว้นต้นทุนของข้อผิดพลาด** | ผลบวกลวงและผลลบลวงมีค่าใช้จ่ายต่างกัน | โมเดลเพิ่มประสิทธิภาพเมตริกที่ไม่ถูกต้อง |
| **ไม่มีพื้นฐาน** | ไม่มีการเปรียบเทียบกับแนวทางที่มีอยู่ | ไม่สามารถบอกได้ว่า ML นั้นดีกว่าฮิวริสติกแบบธรรมดาจริงหรือไม่ |

## ความล้มเหลวตามความคาดหวัง
### วงจรกระแสเกินจริงในโครงการ ML
| เฟส | คำอธิบาย | ความเสี่ยง |
|-------|-------------|-|
| **ความตื่นเต้น** | “AI จะแก้ปัญหาทุกอย่าง!” | เกินคาด; ภายใต้ทรัพยากร |
| **การพิสูจน์แนวคิด** | โมเดลทำงานกับข้อมูลที่สะอาดในโน้ตบุ๊ก | ความมั่นใจที่ผิด; "มันได้ผล!" |
| **ตรวจสอบความเป็นจริง** | ข้อมูลการผลิตยุ่งเหยิง ประสิทธิภาพลดลง | ความผิดหวัง; "ML ใช้งานไม่ได้" |
| **เดธมาร์ช** | ทีมงานพยายามบังคับเข้าสู่การผลิต | หนี้ทางเทคนิค เหนื่อยหน่าย |
| **การละทิ้งหรือการใช้งานอย่างเงียบๆ** | โครงการถูกยกเลิกหรือปรับใช้โดยไม่มีการตรวจสอบ | การลงทุนที่สูญเปล่า |
### การจัดการความคาดหวัง
| กลยุทธ์ | คำอธิบาย |
|----------|-------------|
| **เริ่มต้นด้วยพื้นฐาน** | เปรียบเทียบกับแนวทางที่ง่ายที่สุดที่เป็นไปได้ (กฎ; ประสิทธิภาพของมนุษย์) |
| **กำหนดตัวชี้วัดความสำเร็จล่วงหน้า** | ตัวชี้วัดทางธุรกิจ (รายได้; ประหยัดต้นทุน) ไม่ใช่แค่ตัวชี้วัด ML (ความแม่นยำ; F1) |
| **การสำรวจกล่องเวลา** | ให้เวลาทีม 2-4 สัปดาห์ในการประเมินความเป็นไปได้ก่อนดำเนินการ |
| **แสดงสิ่งที่ ML ทำไม่ได้** | ซื่อสัตย์เกี่ยวกับข้อจำกัด ตั้งความคาดหวังที่สมจริง |
| **ทำซ้ำแบบค่อยเป็นค่อยไป** | ปรับใช้โมเดลอย่างง่ายก่อน ปรับปรุงซ้ำ |
| **ปริมาณต้นทุนของข้อผิดพลาด** | แปลประสิทธิภาพของโมเดลให้เป็นผลกระทบทางธุรกิจ |

## ความล้มเหลวในการปรับใช้
### ทำไมโมเดลถึงไม่ผลิต
| ปัญหา | คำอธิบาย | โซลูชั่น |
|---------|-------------|----------|
| **Notebook ถึงช่องว่างการผลิต** | รหัสใช้งานได้ใน Jupyter แต่ยังไม่พร้อมสำหรับการผลิต | แนวทางปฏิบัติของ MLOps; CI/ซีดีสำหรับ ML; รีวิวโค้ด |
| **ข้อกำหนดด้านเวลาแฝง** | การอนุมานโมเดลช้าเกินไปสำหรับการใช้งานแบบเรียลไทม์ | การเพิ่มประสิทธิภาพโมเดล การหาปริมาณ; แคช |
| **ความสามารถในการปรับขนาด** | โมเดลไม่สามารถจัดการปริมาณการใช้งานจริงได้ | การประมวลผลเป็นชุด; มาตราส่วนแนวนอน โมเดลโครงสร้างพื้นฐานการให้บริการ |
| **การตรวจสอบช่องว่าง** | ไม่มีวิธีตรวจจับเมื่อโมเดลลดระดับ | การตรวจสอบการเลื่อนข้อมูล การตรวจสอบประสิทธิภาพ การแจ้งเตือน |
| **การจัดการการพึ่งพา** | สภาพแวดล้อมการฝึกอบรมและการให้บริการแตกต่างกัน | การบรรจุหีบห่อ; สภาพแวดล้อมที่ทำซ้ำได้ |
| **ไม่มีแผนย้อนกลับ** | ไม่สามารถเปลี่ยนกลับไปเป็นรุ่นก่อนหน้าได้เมื่อโมเดลใหม่ล้มเหลว | ทะเบียนโมเดล; การกำหนดเวอร์ชัน; การย้อนกลับอัตโนมัติ |
### โมเดลเสื่อม
| พิมพ์ | คำอธิบาย | การตรวจจับ |
|------|-------------|-----------|
| **การดริฟท์ข้อมูล** | การกระจายคุณสมบัติอินพุตเปลี่ยนแปลง | ตรวจสอบสถิติคุณสมบัติ ความแตกต่างของ KL; พีเอสไอ |
| **แนวคิดล่องลอย** | ความสัมพันธ์ระหว่างคุณลักษณะและการเปลี่ยนแปลงเป้าหมาย | ตรวจสอบความแม่นยำในการทำนายเมื่อเวลาผ่านไป |
| **ฉลากดริฟ** | ความหมายหรือการกระจายของการเปลี่ยนแปลงเป้าหมาย | ติดตามการกระจายฉลาก ความสัมพันธ์ตัวชี้วัดทางธุรกิจ |
| **การเปลี่ยนแปลงต้นน้ำ** | แหล่งข้อมูลเปลี่ยนรูปแบบ เวลา หรือคุณภาพ | การตรวจสอบสคีมา การตรวจสอบความสด |

## ความล้มเหลวขององค์กร
| ความล้มเหลว | คำอธิบาย | การป้องกัน |
|---------|-------------|------------|
| **ไม่มีกรรมสิทธิ์ที่ชัดเจน** | ไม่มีใครรับผิดชอบต่อโมเดลในการผลิต | กำหนดเจ้าของโมเดล กำหนด RACI |
| **ทีมแยกตัว** | นักวิทยาศาสตร์ข้อมูลสร้างแบบจำลอง วิศวกรปรับใช้ ไม่มีใครสื่อสาร | ทีมงานข้ามสายงาน เป้าหมายร่วมกัน |
| **ไม่มี MLOps ที่ครบกำหนด** | ไม่มีการลงทะเบียนโมเดล ไม่มี CI/ซีดี; ไม่มีการตรวจสอบ | ลงทุนในโครงสร้างพื้นฐาน MLOps แบบค่อยเป็นค่อยไป |
| **ไทม์ไลน์ที่ไม่สมจริง** | “สร้างระบบ ML การผลิตใน 2 สัปดาห์” | การสำรวจกล่องเวลา ย้ำ; สื่อสารความซับซ้อน |
| **ขาดความเชี่ยวชาญด้านโดเมน** | ทีม ML ไม่เข้าใจปัญหาทางธุรกิจ | ฝังผู้เชี่ยวชาญด้านโดเมนไว้ในทีม ML |
| **ไม่มีกรอบการประเมินผล** | ไม่สามารถบอกได้ว่าโมเดลกำลังทำงานอยู่ในการผลิตหรือไม่ | กำหนดตัวชี้วัดทางธุรกิจ ตั้งค่าแดชบอร์ด รีวิวประจำ |

## บทเรียนที่ได้รับ
### รายการตรวจสอบโครงการ ML

## สรุป
โปรเจ็กต์ ML ล้มเหลวไม่ใช่เพราะอัลกอริธึมยากเกินไป แต่เป็นเพราะกระบวนการรอบตัวเสียหาย ปัญหาด้านข้อมูล — ข้อมูลไม่เพียงพอ ป้ายกำกับที่ไม่ดี การรั่วไหล การเบี่ยงเบน — เป็นสาเหตุให้เกิดความล้มเหลวที่ใหญ่ที่สุด ความล้มเหลวในการนิยามปัญหา — การแก้ปัญหาที่ไม่ถูกต้อง โดยใช้ ML เมื่อกฎเกณฑ์เพียงพอ โดยไม่สนใจต้นทุนของข้อผิดพลาด — สิ้นเปลืองความพยายามหลายเดือน ความล้มเหลวด้านความคาดหวัง — มีแนวโน้มมากเกินไป ส่งมอบได้น้อยเกินไป และไม่ได้จัดการผู้มีส่วนได้ส่วนเสีย — ทำลายความไว้วางใจขององค์กรใน ML ความล้มเหลวในการปรับใช้ — ช่องว่างระหว่างโน้ตบุ๊กกับการใช้งานจริง ปัญหาด้านเวลาแฝง ไม่มีการตรวจสอบ — หมายความว่าแบบจำลองที่ทำงานในการพัฒนาไม่เคยสร้างมูลค่าในการใช้งานจริง ความล้มเหลวขององค์กร — ไม่มีการเป็นเจ้าของ, ทีมแยกส่วน, ไม่มี MLOps — ทำให้เป็นไปไม่ได้ในเชิงโครงสร้างที่จะประสบความสำเร็จ ยาแก้พิษคือการปฏิบัติที่มีระเบียบวินัย: เริ่มต้นด้วยพื้นฐาน การสำรวจกล่องเวลา ตรวจสอบข้อมูลอย่างเข้มงวด ตรวจสอบการรั่วไหล กำหนดตัวชี้วัดทางธุรกิจ ปรับใช้ทีละน้อย; ติดตามอย่างต่อเนื่อง และทำซ้ำ ทีม ML ที่ดีที่สุดใช้เวลากับข้อมูลและประมวลผลมากกว่าโมเดล
