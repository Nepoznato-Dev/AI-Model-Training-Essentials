# วิศวกรรมข้อมูลและท่อส่ง
วิศวกรรมข้อมูลเป็นสาขาวิชาในการสร้างระบบที่เคลื่อนย้าย เปลี่ยนแปลง และจัดเก็บข้อมูลตามขนาดที่ต้องการ หากไม่มีไปป์ไลน์ข้อมูลที่เชื่อถือได้ โมเดลแมชชีนเลิร์นนิงจะไม่สามารถฝึกได้ แดชบอร์ดจะแสดงตัวเลขเก่า และการตัดสินใจทางธุรกิจจะขึ้นอยู่กับการคาดเดา ไฟล์นี้ครอบคลุมถึงสถาปัตยกรรม เครื่องมือ และแนวทางปฏิบัติในการสร้างโครงสร้างพื้นฐานข้อมูลที่ใช้งานได้
---

## ETL กับ ELT
| วิธีการ | มันทำงานอย่างไร | ดีที่สุดสำหรับ | เครื่องมือ |
|----------|-------------|----------|-------|
| **ETL** (แยก → แปลง → โหลด) | แปลงข้อมูล*ก่อน*โหลดเข้าโกดัง | คลังสินค้าแบบดั้งเดิมที่มีคอมพิวเตอร์จำกัด | Informatica, Talend, Apache NiFi |
| **ELT** (แยก → โหลด → แปลง) | โหลดข้อมูลดิบก่อน แปลงร่าง *ภายใน* โกดัง | คลังสินค้าคลาวด์สมัยใหม่พร้อมการประมวลผลแบบยืดหยุ่น | dbt, Fivetran, Airbyte + BigQuery/Snowflake |
การเปลี่ยนจาก ETL มาเป็น ELT ได้รับการขับเคลื่อนโดยคลังข้อมูลบนคลาวด์ (BigQuery, Snowflake, Redshift) ที่สามารถปรับขนาดการประมวลผลแยกจากพื้นที่จัดเก็บข้อมูลได้ ไม่จำเป็นต้องประมวลผลทุกอย่างล่วงหน้าก่อนที่จะโหลดอีกต่อไป
---

## Data Lakes กับคลังข้อมูล
| คุณสมบัติ | ทะเลสาบข้อมูล | คลังข้อมูล |
|---------|-----------|---------------|
| **รูปแบบข้อมูล** | Raw รูปแบบเนทิฟ (สคีมาเมื่ออ่าน) | มีโครงสร้าง ประมวลผล (สคีมาเมื่อเขียน) |
| **สคีมา** | กำหนด ณ เวลาสืบค้น | กำหนดก่อนที่จะโหลด |
| **ประเภทข้อมูล** | มีโครงสร้าง, กึ่งมีโครงสร้าง, ไม่มีโครงสร้าง | โครงสร้างหลัก |
| **ผู้ใช้** | นักวิทยาศาสตร์ข้อมูล วิศวกร | นักวิเคราะห์ธุรกิจ เครื่องมือ BI |
| **ราคา** | การจัดเก็บที่ถูกกว่า (การจัดเก็บวัตถุ) | แพงกว่า (ปรับให้เหมาะสมสำหรับการสืบค้น) |
| **ตัวอย่าง** | AWS S3, Azure Data Lake, GCS | เกล็ดหิมะ, BigQuery, Redshift |
แนวทางที่ทันสมัยคือ **บ้านทะเลสาบ**: ผสมผสานการจัดเก็บทะเลสาบราคาถูกและยืดหยุ่นเข้ากับคุณสมบัติการจัดการและประสิทธิภาพของคลังสินค้า Delta Lake, Apache Iceberg และ Apache Hudi เป็นเทคโนโลยีหลักที่นี่

## สถาปัตยกรรมไปป์ไลน์
### แบทช์เทียบกับสตรีมมิ่ง
| โหมด | คำอธิบาย | เวลาแฝง | ใช้กรณี |
|------|-------------|---------|----------|
| **ชุด** | ประมวลผลข้อมูลเป็นชิ้นใหญ่ตามช่วงเวลาที่กำหนด | นาที ถง ชั่วโมง | รายงานรายวัน, งาน ETL, การเพิ่มคุณค่าของข้อมูล |
| **สตรีมมิ่ง** | ประมวลผลข้อมูลอย่างต่อเนื่องเมื่อมาถึง | มิลลิวินาที เป็น วินาที | แดชบอร์ดแบบเรียลไทม์ การตรวจจับการฉ้อโกง การแจ้งเตือน |
| **ไมโครแบทช์** | ชุดเล็กในช่วงเวลาสั้นมาก | วินาที | ใกล้เรียลไทม์ด้วยความเรียบง่ายแบบแบตช์ |
### ส่วนประกอบท่อ
ไปป์ไลน์ข้อมูลทั่วไปมีขั้นตอนเหล่านี้:
| เวที | คำอธิบาย | เครื่องมือ |
|-------|-------------|-------|
| **การกลืนกิน** | รวบรวมข้อมูลจากแหล่งที่มา | คาฟคา, แอร์ไบต์, ไฟว์ทราน, เดเบเซียม |
| **การเปลี่ยนแปลง** | สะอาด เสริมสร้าง รวม | dbt, สปาร์ก, นุ่น |
| **การจัดเก็บ** | คงข้อมูลที่ประมวลผลไว้ | BigQuery, Snowflake, S3, เดลต้าเลค |
| **เสิร์ฟ** ​​| ทำให้ข้อมูลเข้าถึงผู้บริโภคได้ | API, แดชบอร์ด, ร้านค้าฟีเจอร์ ML |
| **การเรียบเรียง** | กำหนดเวลาและจัดการการขึ้นต่อกัน | Airflow, นายอำเภอ, Dagster |
| **การตรวจสอบ** | ติดตามความสมบูรณ์ของไปป์ไลน์และคุณภาพข้อมูล | ความคาดหวังที่ยอดเยี่ยม, มอนติคาร์โล, การแจ้งเตือนแบบกำหนดเอง |

## เครื่องมือการเรียบเรียง
| เครื่องมือ | วิธีการ | ความแข็งแกร่ง |
|------|----------|----------|
| **Apache การไหลของอากาศ** | DAG ที่ใช้ Python; มาตรฐานอุตสาหกรรม | ระบบนิเวศขนาดใหญ่ สมบูรณ์ ยืดหยุ่น |
| **นายอำเภอ** | Python-พื้นเมือง; API ที่สะอาดกว่า Airflow | การออกแบบที่ทันสมัย ​​การจัดการข้อผิดพลาดที่ดีเยี่ยม |
| **แด็กสเตอร์** | สินทรัพย์เป็นศูนย์กลาง; แนวทางวิศวกรรมซอฟต์แวร์ | พิมพ์ระบบ การทดสอบ ความสามารถในการสังเกต |
| **ลุยจิ** | เครื่องมือไปป์ไลน์ดั้งเดิมของ Spotify | เรียบง่าย แต่มีการพัฒนาน้อย |
### ตัวอย่างการไหลของอากาศ
```python
from airflow import DAG
from airflow.operators.python import PythonOperator
from datetime import datetime

def extract():
    # Pull data from source
    pass

def transform():
    # Clean and process
    pass

    # Write to warehouse
    pass

with DAG("etl_pipeline", start_date=datetime(2024, 1, 1),
```

## อาปาเช่ คาฟคา
Kafka เป็นแกนหลักของระบบข้อมูลแบบเรียลไทม์มากมาย เป็นบันทึกเหตุการณ์แบบกระจายที่ให้การรับส่งข้อความสูงและทนทานต่อข้อผิดพลาด
### แนวคิดหลัก
| แนวคิด | คำอธิบาย |
|---------|-------------|
| **หัวข้อ** | หมวดหมู่ของข้อความ (เช่น`orders`,`user-events`) |
| **พาร์ติชั่น** | หัวข้อจะถูกแบ่งออกเป็นพาร์ติชั่นเพื่อความขนาน |
| **ผู้ผลิต** | แอปพลิเคชั่นที่เขียนข้อความในหัวข้อ |
| **ผู้บริโภค** | แอปพลิเคชั่นที่อ่านข้อความจากหัวข้อ |
| **กลุ่มผู้บริโภค** | กลุ่มผู้บริโภคที่แบ่งปันภาระในการอ่านหัวข้อต่างๆ |
| **ออฟเซ็ต** | ตำแหน่งของคอนซูเมอร์ภายในพาร์ติชัน |
| **นายหน้า** | โหนดเซิร์ฟเวอร์ Kafka |
### เมื่อใดจึงควรใช้คาฟคา
- **การสตรีมกิจกรรม**: การประมวลผลเหตุการณ์แบบเรียลไทม์ในวงกว้าง
- **บริการแยกส่วน**: ผู้ผลิตและผู้บริโภคไม่จำเป็นต้องรู้จักกัน
- **เล่นซ้ำ**: ข้อความยังคงอยู่ ผู้บริโภคสามารถอ่านซ้ำได้จากออฟเซ็ตใดก็ได้
- **แรงดันย้อนกลับ**: คาฟคาจะจัดการกับความแตกต่างด้านความเร็วระหว่างผู้ผลิตและผู้บริโภคโดยธรรมชาติ

## การสร้างแบบจำลองข้อมูล
### สคีมาสตาร์กับสคีมาเกล็ดหิมะ
| สคีมา | โครงสร้าง | ข้อดี | ข้อเสีย |
|--------|-----------|--------------|
| **สตาร์** | ตารางข้อเท็จจริงกลางที่ล้อมรอบด้วยตารางมิติแบบดีนอร์มอลไลซ์ | คำสั่งง่ายๆ อ่านเร็ว | ความซ้ำซ้อนของข้อมูล |
| **เกล็ดหิมะ** | ตารางไดเมนชันถูกทำให้เป็นมาตรฐาน (แบ่งออกเป็นตารางย่อย) | ความซ้ำซ้อนน้อยลง | เข้าร่วมมากขึ้น การค้นหาช้าลง |
### ตารางข้อเท็จจริงและมิติข้อมูล
| ประเภทตาราง | ประกอบด้วย | ตัวอย่าง |
|----------|----------|---------|
| **ข้อเท็จจริง** | เหตุการณ์ที่วัดได้ (เมตริก) | `orders`(order_id, product_id, customer_id, จำนวน, วันที่) |
| **ขนาด** | คุณลักษณะเชิงพรรณนา | `products`(product_id, ชื่อ, หมวดหมู่, ราคา),`customers`(customer_id, ชื่อ, เมือง) |

## ร้านค้าคุณสมบัติ
ที่เก็บฟีเจอร์คือที่เก็บข้อมูลส่วนกลางของฟีเจอร์ ML — ค่าที่ได้รับซึ่งใช้เป็นอินพุตสำหรับโมเดล (เช่น "มูลค่าการสั่งซื้อเฉลี่ยของผู้ใช้ใน 30 วันที่ผ่านมา")
| ความสามารถ | คำอธิบาย |
|-----------|-------------|
| **คุณสมบัติการลงทะเบียน** | แค็ตตาล็อกของคุณสมบัติที่มีพร้อมข้อมูลเมตา |
| **ร้านค้าออฟไลน์** | คุณสมบัติทางประวัติศาสตร์สำหรับการฝึกโมเดล (แบทช์) |
| **ร้านค้าออนไลน์** | คุณลักษณะเวลาแฝงต่ำที่ให้บริการสำหรับการอนุมานแบบเรียลไทม์ |
| **การตรวจสอบคุณสมบัติ** | ตรวจจับการดริฟท์ ค่าที่หายไป การเปลี่ยนแปลงการกระจาย |
| เครื่องมือ | คำอธิบาย |
|-|-------------|
| **งานฉลอง** | โอเพ่นซอร์ส; ทำงานร่วมกับกรอบงาน ML ใด ๆ |
| **เทคตัน** | ทางการค้า; แพลตฟอร์มฟีเจอร์แบบเรียลไทม์ |
| **ฮอปส์เวิร์คส์** | โอเพ่นซอร์ส; แพลตฟอร์ม ML เต็มรูปแบบพร้อมฟีเจอร์สโตร์ |
| **ร้านค้าฟีเจอร์ Databricks** | บูรณาการกับ Databricks/Spark |

## คุณภาพของข้อมูล
คุณภาพของข้อมูลเป็นตัวทำลายเงียบของโปรเจ็กต์ ML ขยะเข้าขยะออก
### ขนาดคุณภาพ
| มิติข้อมูล | คำถาม |
|----------|----------|
| **ความแม่นยำ** | ข้อมูลสะท้อนความเป็นจริงหรือไม่? |
| **ความสมบูรณ์** | มีการกรอกข้อมูลในช่องที่ต้องกรอกหรือไม่ |
| **ความสม่ำเสมอ** | ค่าต่างๆ สอดคล้องกันในแหล่งที่มาต่างๆ หรือไม่ |
| **ความทันเวลา** | ข้อมูลเป็นปัจจุบันหรือไม่? |
| **ความถูกต้อง** | ค่าต่างๆ เป็นไปตามกฎที่กำหนดไว้หรือไม่ |
| **ความเป็นเอกลักษณ์** | มีบันทึกซ้ำกันหรือไม่? |
### เครื่องมือคุณภาพข้อมูล
| เครื่องมือ | วิธีการ |
|------|----------|
| **ความคาดหวังที่ดี** | ที่ใช้ภาษาไพธอน; กำหนด "ความคาดหวัง" เกี่ยวกับข้อมูล |
| **มอนติคาร์โล** | แพลตฟอร์มการสังเกตข้อมูลที่ขับเคลื่อนด้วย ML |
| **การทดสอบ dbt** | การทดสอบในตัวสำหรับข้อมูลคลังสินค้า (ไม่ซ้ำกัน ไม่ใช่ null ความสัมพันธ์) |
| **โซดา** | การสแกนคุณภาพข้อมูลโอเพ่นซอร์ส |

## การกำกับดูแลข้อมูล
การกำกับดูแลข้อมูลช่วยให้มั่นใจได้ว่าข้อมูลได้รับการจัดการอย่างมีความรับผิดชอบทั่วทั้งองค์กร
| พื้นที่ | คำอธิบาย |
|-|-------------|
| **แคตตาล็อกข้อมูล** | รายการชุดข้อมูลที่ค้นหาได้ด้วยข้อมูลเมตา (Amundsen, DataHub, Atlan) |
| **สายข้อมูล** | ติดตามว่าข้อมูลมาจากไหนและแปลงอย่างไร |
| **การควบคุมการเข้าถึง** | สิทธิ์ตามบทบาท ใครอ่าน/เขียนอะไรได้บ้าง |
| **การปฏิบัติตามข้อกำหนด** | GDPR, CCPA, การปฏิบัติตาม HIPAA |
| **การเป็นเจ้าของข้อมูล** | ล้างความเป็นเจ้าของชุดข้อมูลแต่ละชุด (การดูแล) |
| **นโยบายการเก็บรักษา** | กำหนดระยะเวลาที่จะเก็บข้อมูลและเวลาที่จะถูกลบ |

## กองข้อมูลสมัยใหม่
"ชุดข้อมูลสมัยใหม่" หมายถึงการผสมผสานเครื่องมือทั่วไปที่ทีมข้อมูลใช้ในปัจจุบัน:
| เลเยอร์ | เครื่องมือทั่วไป |
