# สถาปัตยกรรม AI ท้องถิ่น
คู่มือที่เป็นประโยชน์ในการใช้งานโมเดลภาษาขนาดใหญ่บนอุปกรณ์ทั้งหมด - ข้อควรพิจารณาด้านฮาร์ดแวร์ กลไกการอนุมาน การเพิ่มประสิทธิภาพหน่วยความจำ และการออกแบบระบบสำหรับการใช้งาน Edge
---

## ทำไมต้องใช้ AI ในพื้นที่?
- **ความเป็นส่วนตัว**: ไม่มีข้อมูลออกจากอุปกรณ์
- **ค่าใช้จ่าย**: ไม่มีค่าธรรมเนียม API ต่อโทเค็น
- **เวลาแฝง**: การอนุมานแบบไร้เครือข่ายที่คาดการณ์ได้
- **ความพร้อมใช้งานออฟไลน์**: ทำงานโดยไม่ใช้อินเทอร์เน็ต
- **การควบคุม**: ควบคุมเวอร์ชันของโมเดล การปรับแต่ง และการปรับแต่งได้อย่างสมบูรณ์
---

## ข้อกำหนดด้านฮาร์ดแวร์
### หน่วยความจำ GPU (VRAM)
ทรัพยากรที่สำคัญที่สุด ขนาดโมเดลในหน่วยความจำ γ **พารามิเตอร์ × ไบต์ต่อพารามิเตอร์**
| ความแม่นยำ | ไบต์ต่อพารามิเตอร์ | รุ่น 3.8B | รุ่น 7B | รุ่น 13B | รุ่น 70B |
|-----------|---------------------|------------|----------|-----------|-----------|
| FP32 | 4 | ~15GB | ~28GB | ~52GB | ~280GB |
| FP16 | 2 | ~7.6GB | ~14GB | ~26GB | ~140GB |
| INT8 (8 บิต) | 1 | ~3.8GB | ~7GB | ~13GB | ~70GB |
| INT4 (4 บิต) | 0.5 | ~1.9GB | ~3.5GB | ~6.5GB | ~35GB |
**แนวทางปฏิบัติ:**
- 8GB VRAM → สูงสุด 7B รุ่น 4 บิต
- 12GB VRAM → สูงสุด 13B รุ่น 4 บิต
- 24GB VRAM → สูงสุดรุ่น 70B ที่ 4 บิต (หรือ 13B ที่ 8 บิต)
- Apple Silicon (หน่วยความจำแบบรวม) สามารถเรียกใช้รุ่น 70B บนระบบ 64GB+
### RAM (หน่วยความจำระบบ)
- สำหรับการอนุมาน CPU คุณต้องมี RAM ระบบเพียงพอที่จะโหลดโมเดล (คล้ายกับหมายเลข VRAM)
- สำหรับการอนุมาน GPU RAM ของระบบมีความสำคัญต่อการโหลดโมเดลลงในหน่วยความจำก่อนที่จะออฟโหลดไปยัง VRAM
### ที่เก็บข้อมูล
- น้ำหนักโมเดลเชิงปริมาณใช้พื้นที่ไม่กี่ GB (เช่น 7B 4 บิต 4 บิตบนดิสก์) ตรวจสอบให้แน่ใจว่ามีพื้นที่ว่างอย่างน้อย 20–50 GB สำหรับหลายรุ่น
### ซีพียู
- สำหรับการประมวลผลที่รวดเร็ว (เติมล่วงหน้า) และการถ่าย CPU CPU แบบมัลติคอร์ที่ทันสมัยจะช่วยได้
- ชิป Apple M-series มีประสิทธิภาพที่ยอดเยี่ยมสำหรับ LLM เนื่องจากมีหน่วยความจำแบบรวมและ Neural Engine

## ปริมาณ
การหาปริมาณจะลดความแม่นยำเชิงตัวเลขของตุ้มน้ำหนัก ลดหน่วยความจำลงอย่างมาก และเพิ่มความเร็วโดยเสียความแม่นยำเพียงเล็กน้อย
### รูปแบบยอดนิยม
| รูปแบบ | บิต | คำอธิบาย | การใช้งานทั่วไป |
|--------|-|-------------|-------------|
| **กุกฟ์** | 4–8 | รูปแบบ llama.cpp ปรับให้เหมาะสมสำหรับ CPU/GPU ไฮบริด | ดีที่สุดสำหรับการอนุมานเฉพาะที่ |
| **GPTQ** | 4–8 | GPU เท่านั้น มีประสิทธิภาพบน CUDA | ดีที่สุดสำหรับ NVIDIA GPU |
| **AWQ** | 4 | การรับรู้การเปิดใช้งาน GPU เท่านั้น | เหมาะสำหรับการอนุมานแบบแบตช์บน GPU |
| **ONNX** | ตัวแปร | ข้ามแพลตฟอร์มที่ได้มาตรฐาน | ให้บริการด้านการผลิต |
### การเลือกระดับปริมาณ
- **Q8_0** (8 บิต): การสูญเสียคุณภาพน้อยที่สุด, ขนาดที่ใหญ่ที่สุด
- **Q6_K** (6 บิต): คุณภาพดี การบีบอัดที่เหมาะสม
- **Q5_K_M** (5 บิต): จุดหวานทั่วไป
- **Q4_K_M** (4 บิต): เล็กที่สุด คุณภาพที่ยอมรับได้สำหรับงานส่วนใหญ่
- **IQ4_XS** / **IQ3_XS**: ปรับปรุงการหาปริมาณด้วยความฉงนสนเท่ห์ที่ดีขึ้นที่ 4/3 บิต
**หลักทั่วไป:** ใช้ Q4_K_M เพื่อความสมดุลระหว่างคุณภาพและขนาด หากคุณมี VRAM เพิ่มเติม ให้ใช้ Q5 หรือ Q6

## เครื่องมืออนุมาน (ท้องถิ่น)
### llama.cpp
- เขียนด้วยภาษา C++
- รองรับรูปแบบ GGUF
- ปรับให้เหมาะสมสำหรับ CPU และ GPU (ผ่าน CUDA, Metal, OpenCL)
- เร็วมาก โดยเฉพาะบน CPU
- บรรทัดคำสั่ง โหมดเซิร์ฟเวอร์ และการเชื่อมโยง Python
**คำสั่งตัวอย่าง:**```bash
./llama-cli -m model.Q4_K_M.gguf -p "Tell me a joke" -n 100 -ngl 32
# -ngl 32 offloads 32 layers to GPU
```

### โอลามะ
- ล้อม llama.cpp ด้วย CLI และ REST API แบบธรรมดา
- ดาวน์โหลดโมเดลอัตโนมัติและจัดการโมเดลเหล่านั้น
- เหมาะสำหรับการสร้างต้นแบบและแอปเดสก์ท็อป
- รองรับ Modelfiles แบบกำหนดเองสำหรับการแจ้งเตือนของระบบ
```bash
ollama run phi3:3.8b
ollama run llama3:8b
```

### แอลเอ็ม สตูดิโอ
- แอพเดสก์ท็อปกราฟิกสำหรับ Windows, macOS, Linux
- ดาวน์โหลดเพียงคลิกเดียวและอินเทอร์เฟซการแชท
- เซิร์ฟเวอร์ท้องถิ่นในตัวพร้อม API ที่เข้ากันได้กับ OpenAI
- เหมาะสำหรับผู้ใช้ที่ไม่ใช่ด้านเทคนิคและการทดสอบอย่างรวดเร็ว
### กอดใบหน้า Transformers + บิตแซนด์ไบต์
- ไลบรารี Python มาตรฐานสำหรับรุ่น HF
- ใช้`bitsandbytes`สำหรับการหาปริมาณ 4 บิต (`load_in_4bit=True`)
- มีความยืดหยุ่นมากกว่าสำหรับการปรับแต่งแบบละเอียด แต่ช้ากว่า llama.cpp สำหรับการอนุมาน
### ExLlamaV2
- การอนุมาน GPU ที่รวดเร็วมากสำหรับ GPTQ และ AWQ
- ประสิทธิภาพที่ดีที่สุดบน NVIDIA GPU
- รองรับการสร้างแบบแบตช์
### mlx (แอปเปิ้ล)
- เฟรมเวิร์กของ Apple สำหรับชิป M-series
- ปรับให้เหมาะสมที่สุดสำหรับ Apple Silicon
- หลาม API

## การจัดการหน่วยความจำ
### หน้าต่างบริบทและแคช KV
แคช KV จะจัดเก็บคู่คีย์-ค่าสำหรับทุกเลเยอร์และทุกโทเค็นในบริบท มันเติบโตเป็นเส้นตรงตามความยาวของบริบท
ราคาหน่วยความจำ 2 × เลเยอร์ × (หัว KV × สลัวหัว) × โทเค็น × ไบต์ต่อค่า
สำหรับรุ่น 32 เลเยอร์ที่มีเฮด 8 KV และเฮดดิม 128 โทเค็น แต่ละโทเค็นมีราคา ~32 × 8 × 128 × 2 ไบต์ = 65 KB ต่อโทเค็น สำหรับโทเค็น 128,000 โทเค็น นั่นคือ ~8 GB สำหรับแคชเท่านั้น
### กลยุทธ์การขนถ่าย
- **การถ่ายเลเยอร์**: ใส่เลเยอร์บางเลเยอร์บน GPU และเลเยอร์อื่น ๆ บน CPU เร็วกว่า CPU เพียงอย่างเดียว ความต้องการ VRAM ต่ำกว่า
- **การสตรีมโทเค็น**: ประมวลผลโทเค็นทีละน้อย แทนที่จะดำเนินการทั้งหมดในคราวเดียว
### แคชพร้อมท์
ใช้แคช KV ซ้ำกับพร้อมท์ที่คล้ายกันเพื่อหลีกเลี่ยงการคำนวณเฟสการเติมล่วงหน้าใหม่ เฟรมเวิร์กบางตัวรองรับสิ่งนี้ (เช่น vLLM, llama.cpp พร้อม`--prompt-cache`)
### ไฟล์ที่แมปหน่วยความจำ
โหลดน้ำหนักโมเดลโดยตรงจากดิสก์โดยไม่ต้องโหลดลงใน RAM ทั้งหมด (มีประโยชน์สำหรับโมเดลขนาดใหญ่บนระบบที่จำกัดหน่วยความจำ) llama.cpp ใช้การแมปหน่วยความจำเป็นค่าเริ่มต้น

## สถาปัตยกรรมการปรับใช้
### โหมดอุปกรณ์เดียว
รุ่นหนึ่งทำงานบนเครื่องเดียว (แล็ปท็อป สมาร์ทโฟน อุปกรณ์ Edge) ใช้สำหรับผู้ช่วยส่วนตัว แอพจดบันทึก การกรอกโค้ด
### ไฮบริด Edge-Cloud
โมเดลโลคัลจัดการคำค้นหาทั่วไป ทางเลือกกลับไปใช้โมเดลคลาวด์สำหรับคำถามที่ซับซ้อน สิ่งนี้มอบสิ่งที่ดีที่สุดของทั้งสองโลก — ความเร็ว/ส่วนตัวสำหรับคนส่วนใหญ่ และความสามารถสำหรับเคส Edge
### การอนุมานแบบกระจาย (Multi-GPU)
สำหรับรุ่นขนาดใหญ่ ให้แบ่งเลเยอร์ระหว่าง GPU หลายตัว (เทนเซอร์ขนาน) หรือแบ่งบริบทระหว่างอุปกรณ์ (ไปป์ไลน์ขนาน) ใช้ llama.cpp กับ`-ngl`หรือ ExLlamaV2 กับ `--num-gpu-layers`
### การใช้งานมือถือ
- **Android**: ใช้ llama.cpp ผ่านการผูก JNI หรือ ML Kit
- **iOS**: ใช้ llama.cpp ผ่านการผูก Swift หรือ mlx
- **เว็บ**: ใช้ WebLLM (ทำงานบน WebGPU ผ่านรันไทม์ ONNX) หรือ Transformers.js
---

## การเพิ่มประสิทธิภาพประสิทธิภาพ
### แฟลชความสนใจ
เพิ่มความเร็วในการคำนวณความสนใจและลดการใช้หน่วยความจำ มีอยู่ใน llama.cpp, ExLlamaV2 และไลบรารี Transformers สมัยใหม่
### การอนุมานแบบกลุ่ม
ประมวลผลพร้อมท์หลายรายการในการส่งต่อครั้งเดียว เพิ่มปริมาณงานอย่างมาก ใช้`llama-batch`หรือ vLLM
### การหยุดก่อนเวลา / การจัดทำงบประมาณโทเค็น
กำหนดงบประมาณโทเค็นสูงสุดเพื่อป้องกันการสร้างที่ไม่จำกัด
### การถอดรหัสเก็งกำไร
ใช้โมเดลด่วนขนาดเล็ก (ร่าง) เพื่อทำนายโทเค็น จากนั้นตรวจสอบกับโมเดลขนาดใหญ่พร้อมกัน สามารถให้ผลเร่งความเร็วได้ 2–3 เท่า

## คู่มือการตั้งค่าเชิงปฏิบัติ
### 1. ติดตั้ง Ollama
```bash
curl -fsSL https://ollama.com/install.sh | sh
```

### 2. ดึงโมเดล
```bash
ollama pull phi3:3.8b-q4_K_M
```

### 3. รันด้วย API
```bash
ollama serve
```

จากนั้นส่งคำขอไปที่ `http://localhost:11434/api/generate`
### 4. บูรณาการหลาม
```python
import requests

response = requests.post(
    "http://localhost:11434/api/generate",
    json={"model": "phi3:3.8b", "prompt": "Hello", "stream": False}
)
print(response.json()["response"])
```

### 5. (ทางเลือก) ใช้ llama.cpp โดยตรง
```bash
# Download GGUF from Hugging Face
wget https://huggingface.co/microsoft/Phi-3-mini-4k-instruct-gguf/resolve/main/Phi-3-mini-4k-instruct-q4_K_M.gguf

# Run server
./llama-server -m Phi-3-mini-4k-instruct-q4_K_M.gguf --host 0.0.0.0 --port 8080
```

## ข้อจำกัดและการแลกเปลี่ยน
- **ช่องว่างด้านคุณภาพ**: โมเดลท้องถิ่นขนาดเล็ก (3.8B–7B) โดยทั่วไปมีประสิทธิภาพต่ำกว่าโมเดลคลาวด์ขนาดใหญ่ (GPT-4, Claude 3.5) ในด้านการใช้เหตุผลที่ซับซ้อน
- **การตัดความรู้**: ความรู้ของโมเดลหยุดนิ่งในขณะฝึกอบรม ใช้ RAG เพื่อแทรกข้อมูลปัจจุบัน
- **หลายภาษา**: รุ่นเล็กอาจมีความสามารถหลายภาษาน้อยกว่า
- **การใช้เครื่องมือ**: เวิร์กโฟลว์แบบตัวแทน (การเรียกใช้ฟังก์ชัน) อาจเชื่อถือได้น้อยลงในรุ่นขนาดเล็ก
สำหรับงานประจำวันหลายอย่าง (การสรุป การถามตอบ การเติมโค้ดให้สมบูรณ์ การจัดหมวดหมู่) โมเดลในเครื่องก็เพียงพอแล้วและปรับปรุงอย่างรวดเร็ว
