# การเข้าถึงและการออกแบบที่ครอบคลุม
การเข้าถึง (มักเรียกโดยย่อว่า a11y) คือแนวทางปฏิบัติในการทำให้ทุกคนสามารถใช้ซอฟต์แวร์ได้ รวมถึงผู้ที่มีความบกพร่องทางการมองเห็น การได้ยิน การเคลื่อนไหว การรับรู้ และระบบประสาท เป็นข้อกำหนดทางกฎหมายในเขตอำนาจศาลหลายแห่งและเป็นมาตรฐานการปฏิบัติงานด้านวิศวกรรม ซอฟต์แวร์ที่สามารถเข้าถึงได้เป็นซอฟต์แวร์ที่ดีกว่าสำหรับทุกคน เนื่องจากการตัดสินใจในการออกแบบที่สนับสนุนผู้ใช้ที่พิการ — โครงสร้างที่ชัดเจน การนำทางด้วยแป้นพิมพ์ คอนทราสต์ที่เพียงพอ ข้อความที่อ่านได้ — ปรับปรุงประสบการณ์สำหรับผู้ใช้ทุกคน
---

## ใครได้ประโยชน์จากการเข้าถึง?
| ประเภทความพิการ | ตัวอย่าง | เทคโนโลยีสิ่งอำนวยความสะดวก |
|----------------|---------|---------------------|
| **ภาพ** | ตาบอด มองเห็นเลือนลาง ตาบอดสี | โปรแกรมอ่านหน้าจอ (JAWS, NVDA, VoiceOver); แว่นขยาย; โหมดคอนทราสต์สูง |
| **การได้ยิน** | หูหนวก ได้ยินไม่ชัด | คำบรรยาย; ใบรับรองผลการเรียน; การแจ้งเตือนด้วยภาพ |
| **มอเตอร์** | ความชำนาญจำกัด อัมพาต ตัวสั่น | การนำทางด้วยคีย์บอร์ดเท่านั้น การควบคุมด้วยเสียง สลับอุปกรณ์ การติดตามดวงตา |
| **ความรู้ความเข้าใจ** | โรคดิสเล็กเซีย สมาธิสั้น ออทิสติก ความจำเสื่อม | ภาษาที่ชัดเจน การนำทางที่สอดคล้องกัน ลดการรบกวน |
| **ชั่วคราว** | แขนหัก แสงแดดจ้า สภาพแวดล้อมที่มีเสียงดัง | ที่พักเดียวกันกับผู้ทุพพลภาพถาวร |
| **สถานการณ์** | อุ้มลูก ขับรถ มือเดียว | อินเทอร์เฟซเสียง เป้าหมายการสัมผัสขนาดใหญ่ |
**ข้อมูลเชิงลึกที่สำคัญ**: คุณลักษณะการเข้าถึงที่ออกแบบมาสำหรับผู้ใช้ที่มีความพิการสามารถช่วยเหลือทุกคนได้ ขอบทาง (ทางลาดที่ทางเท้า) ได้รับการออกแบบสำหรับรถเข็นวีลแชร์ แต่ผู้ปกครองที่ใช้รถเข็นเด็ก พนักงานส่งของพร้อมรถเข็น และนักเดินทางที่มีกระเป๋าเดินทางใช้

## การเข้าถึงเว็บ (WCAG)
แนวทางการเข้าถึงเนื้อหาเว็บ (WCAG) เป็นมาตรฐานสากลสำหรับการเข้าถึงเว็บ
### หลักการ WCAG (เท)
| หลักการ | ข้อกำหนด |
|-----------|-------------|
| **รับรู้ได้** | ข้อมูลต้องนำเสนอในลักษณะที่ผู้ใช้สามารถรับรู้ได้ (ข้อความทางเลือก คำบรรยาย รูปแบบที่ปรับเปลี่ยนได้) |
| **ใช้งานได้** | อินเทอร์เฟซต้องสามารถนำทางและใช้งานได้ (แป้นพิมพ์เข้าถึงได้ มีเวลาเพียงพอ ไม่มีเนื้อหาที่ชักจูง) |
| **เข้าใจได้** | ข้อมูลและการดำเนินการจะต้องเข้าใจได้ (อ่านได้ คาดเดาได้ ช่วยเหลือในการป้อนข้อมูล) |
| **แข็งแกร่ง** | เนื้อหาต้องทำงานร่วมกับเทคโนโลยีช่วยเหลือในปัจจุบันและอนาคต |
### ระดับความสอดคล้องของ WCAG
| ระดับ | ข้อกำหนด | เป้าหมายทั่วไป |
|-------|-------------|---------------|
| **เอ** | ระดับต่ำสุด; 30 เกณฑ์ความสำเร็จ | ขั้นต่ำทางกฎหมายในเขตอำนาจศาลบางแห่ง |
| **เอเอ** | จัดการกับอุปสรรคที่พบบ่อยที่สุด | เป้าหมายมาตรฐานสำหรับองค์กรส่วนใหญ่ |
| **เอเอ** | ระดับสูงสุด ไม่ใช่เนื้อหาทั้งหมดที่สามารถบรรลุได้ | เนื้อหาเฉพาะทาง เว็บไซต์การศึกษา |
### เกณฑ์ความสำเร็จที่สำคัญ (ระดับ AA)
| เกณฑ์ | ข้อกำหนด | วิธีบรรลุผล |
|----------|-------------|---------------|
| **1.1.1 เนื้อหาที่ไม่ใช่ข้อความ** | รูปภาพทั้งหมดมีตัวเลือกข้อความ |  แอ็ตทริบิวต์ `alt`; `aria-label`สำหรับไอคอน |
| **1.3.1 ข้อมูลและความสัมพันธ์** | โครงสร้างถ่ายทอดโดยทางโปรแกรม | ความหมาย HTML; หัวเรื่อง; รายการ; สถานที่สำคัญ |
| **1.4.3 คอนทราสต์ (ขั้นต่ำ)** | ข้อความมีอัตราส่วนคอนทราสต์อย่างน้อย 4.5:1 | ทดสอบด้วยตัวตรวจสอบความคมชัด เลือกจานสีที่สามารถเข้าถึงได้ |
| **1.4.4 ปรับขนาดข้อความ** | ข้อความสามารถปรับขนาดได้ถึง 200% โดยไม่สูญเสีย | ใช้หน่วยสัมพันธ์ (rem, em); การออกแบบที่ตอบสนอง |
| **2.1.1 คีย์บอร์ด** | ฟังก์ชั่นทั้งหมดมีให้ใช้งานผ่านแป้นพิมพ์ | ไม่มีกับดักคีย์บอร์ด ตัวบ่งชี้โฟกัสที่มองเห็นได้ |
| **2.4.3 ลำดับโฟกัส** | ลำดับโฟกัสจะคงความหมายและความสามารถในการใช้งาน | ลำดับแท็บแบบลอจิคัล ลำดับ DOM ตรงกับลำดับภาพ |
| **2.4.7 มองเห็นโฟกัส** | โฟกัสของแป้นพิมพ์ถูกระบุด้วยสายตา | รูปแบบ CSS `:focus-visible`; ไม่เคย`outline: none`โดยไม่มีการเปลี่ยน |
| **3.3.2 ฉลากหรือคำแนะนำ** | อินพุตมีป้ายกำกับ |  องค์ประกอบ `<label>`; `aria-label`|
| **4.1.2 ชื่อ บทบาท คุณค่า** | ส่วนประกอบ UI มีชื่อและบทบาทที่สามารถเข้าถึงได้ | คุณลักษณะอาเรีย; ความหมาย HTML |

## ARIA (แอปพลิเคชั่นอินเทอร์เน็ตที่เข้าถึงได้มากมาย)
ARIA เพิ่มข้อมูลการเข้าถึงให้กับองค์ประกอบ HTML ที่ไม่มีความหมายในตัว
### บทบาท ARIA
| บทบาท | วัตถุประสงค์ | ตัวอย่าง |
|------|---------|---------|
| `button`| ระบุองค์ประกอบเป็นปุ่ม |`<div>`สไตล์เป็นปุ่ม |
| `dialog`| กล่องโต้ตอบแบบโมดอลหรือแบบไม่ใช่โมดัล | ส่วนประกอบกิริยาที่กำหนดเอง |
| `tablist`/`tab`/`tabpanel`| ส่วนต่อประสานแท็บ | ส่วนประกอบของแท็บแบบกำหนดเอง |
| `alert`| ข้อความสำคัญที่ปรากฏขึ้นแบบไดนามิก | การแจ้งเตือนข้อผิดพลาด |
| `progressbar`| ตัวบ่งชี้ความคืบหน้า | กำลังโหลดสถานะ |
| `menu`/`menuitem`| การนำทางเมนู | เมนูแบบเลื่อนลง |
### คุณสมบัติ ARIA
| คุณสมบัติ | วัตถุประสงค์ | ตัวอย่าง |
|----------|---------|---------|
| `aria-label`| ชื่อที่เข้าถึงได้เมื่อไม่มีข้อความที่มองเห็นได้ | ปุ่มเฉพาะไอคอน:`aria-label="Search"`|
| `aria-describedby`| เชื่อมโยงองค์ประกอบไปยังคำอธิบาย | ฟิลด์แบบฟอร์มพร้อมข้อความช่วยเหลือ |
| `aria-expanded`| บ่งชี้ว่าส่วนถูกขยายหรือไม่ | หีบเพลง; แบบเลื่อนลง |
| `aria-hidden`| ซ่อนองค์ประกอบจากเทคโนโลยีช่วยเหลือ | ไอคอนตกแต่ง |
| `aria-live`| ประกาศการเปลี่ยนแปลงเนื้อหาแบบไดนามิก | อัปเดตสด; การแจ้งเตือน |
| `aria-disabled`| บ่งชี้ว่าองค์ประกอบถูกปิดใช้งาน | ปุ่มเป็นสีเทา |
### กฎข้อแรกของ ARIA
> **อย่าใช้ ARIA หากคุณสามารถใช้ HTML ดั้งเดิมแทนได้**`<button>`สามารถเข้าถึงได้แล้ว`<div role="button">`กำหนดให้คุณต้องเพิ่มการจัดการแป้นพิมพ์ การจัดการโฟกัส และการรองรับโปรแกรมอ่านหน้าจอด้วยตนเอง ใช้ HTML เชิงความหมายก่อน ARIA เฉพาะเมื่อองค์ประกอบดั้งเดิมไม่สามารถทำงานได้

## การนำทางด้วยแป้นพิมพ์
| คีย์ | พฤติกรรมที่คาดหวัง |
|-----|-------------------|
| **แท็บ** | ย้ายโฟกัสไปยังองค์ประกอบเชิงโต้ตอบถัดไป |
| **Shift + Tab** | ย้ายโฟกัสไปยังองค์ประกอบแบบโต้ตอบก่อนหน้า |
| **เข้า / เว้นวรรค** | เปิดใช้งานองค์ประกอบที่โฟกัส (ปุ่ม, ลิงก์) |
| **ปุ่มลูกศร** | นำทางภายในส่วนประกอบ (เมนู แท็บ กลุ่มวิทยุ) |
| **หนี** | ปิดกล่องโต้ตอบ เมนู หรือป๊อปโอเวอร์ |
| **หน้าแรก / จบ** | ข้ามไปที่รายการแรก / สุดท้ายในรายการ |
### กับดักคีย์บอร์ดทั่วไป
| ปัญหา | แก้ไข |
|---------|-----|
| โฟกัสเข้าสู่องค์ประกอบแต่ไม่สามารถออกจาก | ตรวจสอบให้แน่ใจว่า Tab ย้ายโฟกัสออก จัดการ Escape |
| Modal ไม่ดักจับโฟกัส | โฟกัสควรหมุนเวียนภายในโมดอล กลับไปทริกเกอร์เมื่อปิด |
| ส่วนประกอบที่กำหนดเองไม่ตอบสนองต่อแป้นพิมพ์ | เพิ่มตัวจัดการการกดแป้นสำหรับ Enter, Space, arrows |

## สีและการออกแบบภาพ
| แนวทาง | ข้อกำหนด |
|-----------|-------------|
| **อัตราส่วนคอนทราสต์** | 4.5:1 สำหรับข้อความปกติ 3:1 สำหรับข้อความขนาดใหญ่ (18pt+ หรือ 14pt+ ตัวหนา) |
| **อย่าพึ่งสีเพียงอย่างเดียว** | ใช้ไอคอน ข้อความ หรือรูปแบบ นอกเหนือจากสี |
| **ตัวแสดงโฟกัส** | มองเห็นได้เสมอ คอนทราสต์สูง ไม่เคยถอดออกโดยไม่มีการเปลี่ยน |
| **การปรับขนาดข้อความ** | เค้าโครงต้องทำงานเมื่อซูม 200% |
| **ตอบสนอง** | เนื้อหาจะต้องมีขนาดความกว้าง 320px (มือถือ) |
### ข้อควรพิจารณาเกี่ยวกับตาบอดสี
| พิมพ์ | สีที่ได้รับผลกระทบ | เคล็ดลับการออกแบบ |
|------|-----------------|------------|
| **ดิวเทอเรโนเปีย** | แดง-เขียว (พบมากที่สุด) | อย่าใช้สีแดง/เขียวในการสื่อสถานะ ใช้ไอคอน + สี |
| **สายตาสั้น** | แดง-เขียว | เหมือนข้างบน |
| **ภาวะสายตาเอียง** | ฟ้า-เหลือง | อย่าใช้สีน้ำเงิน/เหลืองเพื่อสร้างความแตกต่างแต่เพียงผู้เดียว |

## การทดสอบการเข้าถึง
| วิธีการ | เครื่องมือ | สิ่งที่จับได้ |
|--------|-----------------------|
| **สแกนอัตโนมัติ** | ขวาน, ประภาคาร, WAVE | ข้อความแสดงแทนหายไป ปัญหาความขัดแย้ง ข้อผิดพลาด ARIA |
| **การทดสอบแป้นพิมพ์** | คู่มือ: ถอดปลั๊กเมาส์ ใช้เฉพาะแป้นพิมพ์ | ลำดับโฟกัส กับดักคีย์บอร์ด ตัวจัดการหายไป |
| **การทดสอบโปรแกรมอ่านหน้าจอ** | NVDA (ฟรี), VoiceOver (macOS), JAWS | ป้ายกำกับหายไป โครงสร้างไม่ดี การเปลี่ยนแปลงที่ไม่ได้แจ้งล่วงหน้า |
| **การทดสอบการซูม** | เบราว์เซอร์ซูมเป็น 200%, 400% | เค้าโครงแตก; ข้อความที่ถูกตัด; ปัญหาล้น |
| **คอนทราสต์ของสี** | ตัวตรวจสอบความคมชัดของ WebAIM, ปลั๊กอิน Stark | อัตราส่วนคอนทราสต์ไม่เพียงพอ |
| **การทดสอบโดยผู้ใช้** | ทดสอบกับผู้ใช้ที่ถูกปิดการใช้งาน | อุปสรรคในโลกแห่งความเป็นจริงที่เครื่องมืออัตโนมัติพลาด |

## ข้อกำหนดทางกฎหมาย
| กฎหมาย | ภูมิภาค | ข้อกำหนด |
|-----|--------|-------------|
| **ADA** (พระราชบัญญัติคนพิการแห่งอเมริกา) | สหรัฐอเมริกา | ต้องเข้าถึงเว็บไซต์ที่พักสาธารณะได้ |
| **มาตรา 508** | สหรัฐอเมริกา (รัฐบาลกลาง) | ต้องเข้าถึง ICT ของหน่วยงานรัฐบาลกลางได้ |
| **EAA** (พระราชบัญญัติการเข้าถึงของยุโรป) | สหภาพยุโรป (2025+) | สินค้าและบริการต้องเป็นไปตามข้อกำหนดด้านการเข้าถึง |
| **มน 301 549** | สหภาพยุโรป | มาตรฐานทางเทคนิคสำหรับการเข้าถึง ICT |
| **ACA** (พระราชบัญญัติการเข้าถึงของแคนาดา) | แคนาดา | ภาครัฐและอุตสาหกรรมที่ได้รับการควบคุม |
| **พระราชบัญญัติความเท่าเทียมกันปี 2010** | สหราชอาณาจักร | ผู้ให้บริการต้องทำการปรับเปลี่ยนตามสมควร |

## การเข้าถึงผ่านมือถือ
| แพลตฟอร์ม | แนวทางปฏิบัติ | เครื่องมือสำคัญ |
|----------|-----------|-----------|
| **iOS** | แนวทางปฏิบัติของ Apple Human Interface (ส่วนการช่วยการเข้าถึง) | วอยซ์โอเวอร์; ประเภทไดนามิก; สวิตช์ควบคุม |
| **แอนดรอยด์** | แนวทางการเข้าถึงของ Android | ทอล์คแบ็ค; การเข้าถึงด้วยสวิตช์; เลือกเพื่อให้พูด |
| ความกังวลเรื่องมือถือ | โซลูชั่น |
|---------------|----------|
| **สัมผัสเป้าหมาย** | ขั้นต่ำ 44×44 จุด (iOS) / 48×48 dp (Android) |

| **ขนาดข้อความแบบไดนามิก** | รองรับขนาดตัวอักษรของระบบ ใช้หน่วยข้อความที่ปรับขนาดได้ |

## สรุป
การช่วยสำหรับการเข้าถึงเป็นหลักการออกแบบที่ควรแจ้งทุกการตัดสินใจตั้งแต่เริ่มต้น ไม่ใช่คุณลักษณะที่เพิ่มเข้ามาในตอนท้าย ใช้ HTML ความหมาย ตรวจสอบให้แน่ใจว่าการนำทางด้วยแป้นพิมพ์ใช้งานได้ รักษาคอนทราสต์ของสีให้เพียงพอ ระบุทางเลือกข้อความสำหรับเนื้อหาที่ไม่ใช่ข้อความ ทดสอบกับโปรแกรมอ่านหน้าจอและผู้ใช้ที่ถูกปิดใช้งาน ผลลัพธ์ที่ได้คือซอฟต์แวร์ที่ทำงานได้ดีขึ้นสำหรับทุกคน รวมถึงผู้ที่มีความบกพร่องชั่วคราว ข้อจำกัดด้านสถานการณ์ อุปกรณ์รุ่นเก่า การเชื่อมต่อที่ช้า และหลายวิธีที่ทำให้การใช้งานในโลกแห่งความเป็นจริงแตกต่างจากสภาพแวดล้อมการพัฒนาที่มีการควบคุม
