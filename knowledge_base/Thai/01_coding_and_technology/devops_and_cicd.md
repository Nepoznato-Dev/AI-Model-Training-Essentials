# DevOps และ CI/CD
DevOps คือการผสมผสานระหว่างปรัชญาวัฒนธรรม แนวปฏิบัติ และเครื่องมือที่ช่วยให้ทีมส่งมอบซอฟต์แวร์ได้รวดเร็วและเชื่อถือได้มากขึ้น มันทลายกำแพงระหว่างนักพัฒนา (ที่ต้องการจัดส่งการเปลี่ยนแปลง) และการดำเนินงาน (ที่ต้องการความมั่นคง) CI/CD — การบูรณาการอย่างต่อเนื่องและการส่งมอบอย่างต่อเนื่อง — คือแกนหลักอัตโนมัติที่ทำให้เป็นไปได้
---

## ไปป์ไลน์ CI/CD
### จริงๆ แล้ว CI/CD หมายถึงอะไร
| ระยะเวลา | มันทำอะไร |
|-|-------------|
| **การบูรณาการอย่างต่อเนื่อง (CI)** | นักพัฒนาซอฟต์แวร์รวมโค้ดบ่อยครั้ง การผสานแต่ละครั้งจะทริกเกอร์การสร้างและการทดสอบอัตโนมัติ |
| **จัดส่งต่อเนื่อง (CD)** | รหัสอยู่ในสถานะปรับใช้ได้เสมอ การปล่อยสู่การผลิตเป็นการตัดสินใจด้วยตนเอง |
| **การใช้งานอย่างต่อเนื่อง** | ทุกการเปลี่ยนแปลงที่ผ่านการทดสอบจะเข้าสู่การใช้งานจริงโดยอัตโนมัติ — ไม่ต้องใช้เกต |
### ขั้นตอนไปป์ไลน์ทั่วไป
| เวที | เกิดอะไรขึ้น | เครื่องมือ |
|-------|-------------|-------|
| **ที่มา** | นักพัฒนาพุชโค้ดไปที่ Git | GitHub, GitLab, Bitbucket |
| **สร้าง** | คอมไพล์โค้ด ติดตั้งการอ้างอิง | Maven, Gradle, npm, pip |
| **ทดสอบ** | รันยูนิต, บูรณาการ, การตรวจสอบผ้าสำลี | ตลก, ไพเทสต์, JUnit |
| **แพ็คเกจ** | สร้างอิมเมจ Docker หรือสิ่งประดิษฐ์ | นักเทียบท่า, Buildpacks |
| **ปรับใช้ (จัดเตรียม)** | ปรับใช้กับสภาพแวดล้อมการแสดงละคร | Kubernetes, ECS, VM |
| **การทดสอบ (การแสดงละคร)** | การทดสอบบูรณาการ การทดสอบควัน | ซีลีเนียม, บุรุษไปรษณีย์ |
| **ปรับใช้ (การผลิต)** | เผยแพร่สู่การผลิต | ฟ้า-เขียว นกคีรีบูน กลิ้ง |
| **จอภาพ** | สังเกตความสมบูรณ์ ข้อผิดพลาด ประสิทธิภาพ | โพรมีธีอุส กราฟาน่า ดาต้าด็อก |
### เปรียบเทียบเครื่องมือ CI/CD
| เครื่องมือ | พิมพ์ | ความแข็งแกร่ง |
|------|-|---------|
| **การดำเนินการ GitHub** | คลาวด์ CI/ซีดี | บูรณาการอย่างล้ำลึกกับ GitHub; เวิร์กโฟลว์ YAML |
| **GitLab CI** | CI/CD ในตัว | แพลตฟอร์มเดียวสำหรับ repo + ไปป์ไลน์ |
| **เจนกินส์** | CI/CD ที่โฮสต์เอง | กำหนดค่าได้สูง ระบบนิเวศปลั๊กอินขนาดใหญ่ |
| **วงกลมCI** | คลาวด์ CI/ซีดี | เร็ว; เหมาะสำหรับเวิร์กโฟลว์แบบคอนเทนเนอร์ |
| **อาร์โกซีดี** | GitOps สำหรับ Kubernetes | การปรับใช้ที่ประกาศและขับเคลื่อนด้วย Git |

## นักเทียบท่าและคอนเทนเนอร์
### ทำไมต้องคอนเทนเนอร์?
ก่อนที่จะมีคอนเทนเนอร์ ปัญหาคลาสสิกคือ "มันใช้งานได้กับเครื่องของฉัน" คอนเทนเนอร์แก้ปัญหานี้ด้วยการบรรจุแอปพลิเคชันที่มีการขึ้นต่อกันทั้งหมด เช่น ไลบรารี รันไทม์ และการกำหนดค่า ลงในหน่วยแบบพกพาเครื่องเดียวที่ทำงานเหมือนกันทุกที่
### สิ่งจำเป็นสำหรับนักเทียบท่า
| แนวคิด | คำอธิบาย |
|---------|-------------|
| **รูปภาพ** | เทมเพลตแบบอ่านอย่างเดียวพร้อมแอป + การอ้างอิง |
| **ตู้คอนเทนเนอร์** | เรียกใช้อินสแตนซ์ของรูปภาพ |
| **ไฟล์นักเทียบท่า** | สูตรสร้างภาพ |
| **ทะเบียน** | พื้นที่จัดเก็บรูปภาพ (Docker Hub, ECR, GCR) |
| **ปริมาณ** | ที่เก็บข้อมูลถาวรที่รอดจากการรีสตาร์ทคอนเทนเนอร์ |
| **เครือข่าย** | แยกเลเยอร์เครือข่ายสำหรับคอนเทนเนอร์ |
### แนวทางปฏิบัติที่ดีที่สุดของ Dockerfile
```dockerfile
# Use specific base image tags, not 'latest'
FROM python:3.12-slim

# Set working directory
WORKDIR /app

# Copy dependency file first (leverage Docker layer caching)
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# Copy application code
COPY . .

# Run as non-root user
USER appuser

# Expose port and define entrypoint
EXPOSE 8000
CMD ["python", "main.py"]
```

แนวทางปฏิบัติหลัก: ใช้อิมเมจพื้นฐานแบบบาง/อัลไพน์, รันแบบไม่ใช่รูท, ใช้ประโยชน์จากการแคชเลเยอร์, ​​ใช้`.dockerignore`, สแกนอิมเมจเพื่อหาช่องโหว่ (`trivy`,`docker scan`) และตั้งค่าขีดจำกัดทรัพยากร
### นักเทียบท่าเขียน
สำหรับการเรียกใช้หลายคอนเทนเนอร์ร่วมกัน (แอป + ฐานข้อมูล + แคช):
```yaml
services:
  app:
    build: .
    ports: ["8000:8000"]
    depends_on: [db, redis]
    environment:
      DATABASE_URL: postgresql://user:pass@db:5432/mydb
  db:
    image: postgres:16
    volumes: [pgdata:/var/lib/postgresql/data]
  redis:
    image: redis:7-alpine
volumes:
  pgdata:
```

## Kubernetes (K8)
Kubernetes คือผู้ประสานงานคอนเทนเนอร์มาตรฐานอุตสาหกรรม โดยจะจัดการการปรับใช้ การปรับขนาด และการทำงานของแอปพลิเคชันในคอนเทนเนอร์
### สถาปัตยกรรมหลัก
| ส่วนประกอบ | บทบาท |
|-----------|-|
| **เครื่องบินควบคุม** | จัดการคลัสเตอร์ (เซิร์ฟเวอร์ API, ตัวกำหนดเวลา, ฯลฯ, ตัวจัดการคอนโทรลเลอร์) |
| **โหนด** | เครื่องของผู้ปฏิบัติงาน (VM หรือฟิสิคัล) ที่รันคอนเทนเนอร์ |
| **พ็อด** | หน่วยปรับใช้ที่เล็กที่สุด คอนเทนเนอร์อย่างน้อยหนึ่งรายการที่ใช้เครือข่ายร่วมกัน |
| **บริการ** | จุดสิ้นสุดเครือข่ายที่เสถียรซึ่งกำหนดเส้นทางการรับส่งข้อมูลไปยังพ็อด
| **การปรับใช้** | คำจำกัดความที่ประกาศของสถานะพ็อดที่ต้องการ (แบบจำลอง รูปภาพ ฯลฯ) |
| **ทางเข้า** | กฎการกำหนดเส้นทาง HTTP สำหรับการรับส่งข้อมูลภายนอก
| **ConfigMap / ความลับ** | การกำหนดค่าและข้อมูลที่ละเอียดอ่อนที่แทรกเข้าไปในพ็อด |
### คำสั่ง kubectl ที่จำเป็น
```bash
kubectl get pods                    # List pods
kubectl get services                # List services
kubectl describe pod <name>         # Detailed pod info
kubectl logs <pod-name>             # View pod logs
kubectl exec -it <pod> -- /bin/sh   # Shell into a pod
kubectl apply -f deployment.yaml    # Apply a manifest
kubectl rollout status deploy/myapp # Check rollout progress
kubectl scale deploy/myapp --replicas=5  # Scale to 5 replicas
```

### หมวกกันน็อค
Helm เป็นตัวจัดการแพ็คเกจสำหรับ Kubernetes **แผนภูมิ** คือชุดทรัพยากร Kubernetes ที่กำหนดค่าไว้ล่วงหน้า คิดว่าเป็น`apt`หรือ`brew`สำหรับ K8
```bash
helm install my-release bitnami/postgresql   # Install a chart
helm upgrade my-release bitnami/postgresql   # Upgrade
helm rollback my-release 1                   # Rollback to revision 1
helm list                                    # List releases
```

## โครงสร้างพื้นฐานเป็นรหัส (IaC)
IaC ปฏิบัติต่อการกำหนดค่าโครงสร้างพื้นฐานในลักษณะเดียวกับที่คุณปฏิบัติต่อโค้ดแอปพลิเคชัน: ควบคุมเวอร์ชัน ทดสอบ และปรับใช้ผ่านไปป์ไลน์
### Terraform กับ Ansible
| เครื่องมือ | พิมพ์ | วิธีการ | ดีที่สุดสำหรับ |
|------|-|----------|----------|
| **ภูมิประเทศ** | การจัดเตรียม | ประกาศ (HCL); ตามรัฐ | การสร้างทรัพยากรคลาวด์ (VPC, VM, ฐานข้อมูล) |
| **เข้าใจได้** | การกำหนดค่า | ประกาศ (YAML); ไร้ตัวแทน | การกำหนดค่าเซิร์ฟเวอร์การติดตั้งซอฟต์แวร์ |
| **ปูลูมิ** | การจัดเตรียม | ความจำเป็น (Python, Go, TS) | ทีมที่ชอบภาษาโปรแกรมจริง |
| **การสร้างคลาวด์** | การจัดเตรียม | ประกาศ (YAML/JSON); AWS-เนทิฟ | โครงสร้างพื้นฐาน AWS เท่านั้น |
### ตัวอย่าง Terraform
```hcl
provider "aws" {
  region = "us-east-1"
}

resource "aws_instance" "web" {
  ami           = "ami-0c55b159cbfafe1f0"
  instance_type = "t3.micro"

  tags = {
    Name = "web-server"
  }
}
```

แนวทางปฏิบัติที่ดีที่สุด: ใช้โมดูลเพื่อให้นำมาใช้ซ้ำ เก็บสถานะจากระยะไกล (S3 + DynamoDB สำหรับการล็อค) ไม่ต้องฮาร์ดโค้ดความลับ และควบคุมเวอร์ชันทุกอย่าง

## การติดตามและการสังเกต
### สามเสาหลัก
| เสา | สิ่งที่บอกคุณ | เครื่องมือ |
|--------|------------------|-------|
| **ตัวชี้วัด** | การวัดเชิงตัวเลขในช่วงเวลาหนึ่ง (CPU, อัตราคำขอ, อัตราข้อผิดพลาด) | โพร, CloudWatch, ดาต้าด็อก |
| **บันทึก** | เหตุการณ์ที่ไม่ต่อเนื่องพร้อมบริบท (ข้อผิดพลาด คำขอ การเปลี่ยนแปลงสถานะ) | ELK Stack, Loki, บันทึก CloudWatch |
| **ร่องรอย** | การเดินทางของคำขอแบบ end-to-end ข้ามบริการ | เยเกอร์, เอ็กซ์เรย์, ซิปกิ้น |
### โพรมีธีอุส + กราฟาน่าสแต็ค
สแต็กการตรวจสอบโอเพ่นซอร์สมาตรฐาน:
| ส่วนประกอบ | บทบาท |
|-----------|-|
| **โพรมีธีอุส** | ฐานข้อมูลอนุกรมเวลา ดึงเมตริกจากบริการ |
| **กราฟาน่า** | การแสดงภาพและแดชบอร์ด |
| **ผู้จัดการแจ้งเตือน** | กำหนดเส้นทางการแจ้งเตือนไปยัง Slack, PagerDuty, อีเมล |
| **ผู้ส่งออกโหนด** | เปิดเผยตัวชี้วัดระดับระบบ (CPU, RAM, ดิสก์) |
| **ผู้ส่งออกกล่องดำ** | จุดสิ้นสุดของโพรบ (HTTP, TCP, ICMP) |
### ตัวชี้วัดสำคัญในการติดตาม
| หมวดหมู่ | ตัวชี้วัด |
|----------|---------|
| **โครงสร้างพื้นฐาน** | CPU, RAM, การใช้งานดิสก์, I/O เครือข่าย |
| **ใบสมัคร** | อัตราคำขอ เวลาแฝง (p50, p95, p99) อัตราข้อผิดพลาด |
| **ฐานข้อมูล** | จำนวนการสืบค้น การสืบค้นที่ช้า การใช้พูลการเชื่อมต่อ |
| **ธุรกิจ** | การสมัครสมาชิก การแปลง รายได้ |

## กลยุทธ์การปรับใช้
| กลยุทธ์ | มันทำงานอย่างไร | ความเสี่ยง | ย้อนกลับ |
|----------|-----------------|-|----------|
| **อัพเดทต่อเนื่อง** | ค่อยๆ แทนที่อินสแตนซ์เก่าด้วยอันใหม่ | ผู้ใช้บางคนในรุ่นเก่า บางคนในเวอร์ชันใหม่ | เปลี่ยนกลับเป็นรูปภาพก่อนหน้า |
| **ฟ้า-เขียว** | รันสองสภาพแวดล้อมที่เหมือนกัน สลับการรับส่งข้อมูล | ต้นทุนโครงสร้างพื้นฐานสองเท่าระหว่างการเปลี่ยนแปลง | สลับกลับทันที |
| **นกขมิ้น** | กำหนดเส้นทาง % เล็กน้อยของการรับส่งข้อมูลไปยังเวอร์ชันใหม่ เพิ่มขึ้นเรื่อยๆ | การจัดการการรับส่งข้อมูลที่ซับซ้อน | กำหนดเส้นทางการรับส่งข้อมูลกลับสู่ความเสถียร |
| **คุณสมบัติเด่น** | ปรับใช้โค้ดแต่ซ่อนคุณสมบัติไว้เบื้องหลังการสลับ | ความซับซ้อนของโค้ดจากตรรกะแบบมีเงื่อนไข | สลับปิด |

## GitOps
GitOps นำ IaC ไปสู่ข้อสรุปเชิงตรรกะ: พื้นที่เก็บข้อมูล Git เป็นแหล่งความจริงแหล่งเดียวสำหรับสถานะที่ต้องการของโครงสร้างพื้นฐานและแอปพลิเคชันของคุณ
| หลักการ | คำอธิบาย |
|-----------|-------------|
| **ประกาศ** | ทุกอย่างที่อธิบายว่าเป็นโค้ด (YAML, HCL) |
| **เวอร์ชัน** | Git คือที่มาของความจริง |
| **อัตโนมัติ** | เครื่องมือจะปรับสถานะที่ต้องการกับสถานะจริงอย่างต่อเนื่อง |
| **ตรวจสอบได้** | ทุกการเปลี่ยนแปลงถือเป็นคอมมิตของ Git |
**ArgoCD** และ **Flux** เป็นเครื่องมือ GitOps ชั้นนำสำหรับ Kubernetes คุณส่งการเปลี่ยนแปลงไปยัง repo Git ของคุณ และเครื่องมือจะปรับใช้กับคลัสเตอร์โดยอัตโนมัติ

## การตอบสนองต่อเหตุการณ์
เมื่อมีบางอย่างพังตอนตี 3:
1. **รับทราบ** การแจ้งเตือน
2. **ประเมินขอบเขต**: บริการ ผู้ใช้ และข้อมูลใดบ้างที่ได้รับผลกระทบ
3. **ระบุ** สาเหตุที่แท้จริง — ตรวจสอบบันทึก ตัวชี้วัด การใช้งานล่าสุด
4. **มี** หากเป็นไปได้ — เบรกเกอร์วงจร ธงคุณลักษณะ การเคลื่อนตัวของการจราจร
5. **แก้ไข** — ย้อนกลับหรือแก้ไขไปข้างหน้า
6. **สื่อสาร** — อัปเดตผู้มีส่วนได้ส่วนเสียและผู้ใช้ (หน้าสถานะ)
7. **หลังชันสูตร** — ภายใน 24–48 ชั่วโมง บันทึกสาเหตุที่แท้จริงและรายการดำเนินการ
เป้าหมายไม่ใช่แค่การแก้ไขเหตุการณ์เท่านั้น แต่ยังต้องแน่ใจว่าเหตุการณ์เดิมจะไม่เกิดขึ้นอีก
