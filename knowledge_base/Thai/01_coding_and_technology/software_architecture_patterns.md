# รูปแบบสถาปัตยกรรมซอฟต์แวร์
สถาปัตยกรรมคือชุดของการตัดสินใจเชิงโครงสร้างเกี่ยวกับวิธีการจัดระบบ — องค์ประกอบอะไรบ้างที่มี การสื่อสารอย่างไร และความรับผิดชอบอยู่ที่ใด สถาปัตยกรรมที่ดีทำให้ระบบเข้าใจ ปรับเปลี่ยน และปรับขนาดได้ง่าย สถาปัตยกรรมที่ไม่ดีทำให้ทุกการเปลี่ยนแปลงต้องดิ้นรน ไฟล์นี้ครอบคลุมถึงรูปแบบหลักๆ เวลาที่ควรใช้แต่ละรูปแบบ และข้อดีข้อเสียที่เกี่ยวข้อง
---

## Monolith กับ Microservices
นี่เป็นการตัดสินใจทางสถาปัตยกรรมขั้นพื้นฐานที่สุด และมันก็คุ้มค่าที่จะทำอย่างถูกต้อง
| ด้าน | เสาหิน | ไมโครเซอร์วิส |
|--------|----------|---------------|
| **โครงสร้าง** | หน่วยปรับใช้เดียว | บริการขนาดเล็กจำนวนมากที่สามารถปรับใช้ได้อย่างอิสระ |
| **ข้อมูล** | ฐานข้อมูลที่ใช้ร่วมกัน | แต่ละบริการเป็นเจ้าของข้อมูล |
| **การสื่อสาร** | การเรียกใช้ฟังก์ชันที่กำลังดำเนินการ | การโทรผ่านเครือข่าย (HTTP, gRPC, การส่งข้อความ) |
| **การปรับขนาด** | ปรับขนาดแอปพลิเคชันทั้งหมด | ปรับขนาดบริการส่วนบุคคล |
| **การปรับใช้** | รอบการเปิดตัวเดี่ยว | การปรับใช้อิสระ |
| **ความซับซ้อน** | ง่ายต่อการพัฒนาในช่วงแรก | ความซับซ้อนในการดำเนินงาน (เครือข่าย การตรวจสอบ) |
| **ดีที่สุดสำหรับ** | ทีมเล็ก ผลิตภัณฑ์ระยะเริ่มต้น | ทีมขนาดใหญ่ โดเมนที่ซับซ้อน สเกลสูง |
### เมื่อใดควรเริ่มต้นด้วยเสาหิน
แอปพลิเคชันส่วนใหญ่ควรเริ่มต้นเป็นเสาหิน การสร้าง ทดสอบ ปรับใช้ และแก้ไขข้อบกพร่องทำได้ง่ายกว่า คุณสามารถแยกบริการได้ในภายหลังเมื่อคุณมีภาพขอบเขตโดเมนของคุณชัดเจนยิ่งขึ้น บางครั้งเรียกว่า "หินใหญ่ก้อนเดียว" ซึ่งเป็นหินใหญ่ก้อนเดียวที่มีขอบเขตภายในที่สะอาดตา ซึ่งจะทำให้การสกัดทำได้ง่ายในภายหลัง
### เมื่อใดควรใช้บริการไมโครเซอร์วิส
พิจารณาไมโครเซอร์วิสเมื่อ:
- ทีมมีขนาดใหญ่พอที่จะทำให้การประสานงานกลายเป็นคอขวด
- ส่วนต่างๆ ของระบบมีข้อกำหนดในการปรับขนาดที่แตกต่างกันมาก
- คุณต้องปรับใช้ส่วนประกอบอย่างอิสระ
- โดเมนของคุณมีบริบทที่มีขอบเขตชัดเจน (ดู DDD ด้านล่าง)

## สถาปัตยกรรมแบบเลเยอร์ (N-Tier)
รูปแบบสถาปัตยกรรมที่พบมากที่สุด โค้ดถูกจัดเป็นชั้นๆ โดยแต่ละชั้นมีหน้าที่รับผิดชอบเฉพาะ
```
â”Œ─────────────────────────┐
│   Presentation Layer    │  ← UI, controllers, API endpoints
├─────────────────────────┤
│   Application Layer     │  ← Use cases, orchestration
├─────────────────────────┤
│   Domain Layer          │  ← Business logic, entities
├─────────────────────────┤
│   Infrastructure Layer  │  ← Database, external services, file I/O
└─────────────────────────┘
```

| เลเยอร์ | ความรับผิดชอบ | กฎ |
|-------|---------------|------|
| **การนำเสนอ** | จัดการคำขอของผู้ใช้/HTTP | สามารถเรียก Application layer เท่านั้น |
| **ใบสมัคร** | เรียบเรียงกรณีการใช้งาน | สามารถเรียก Domain layer |
| **โดเมน** | ตรรกะทางธุรกิจหลัก | ไม่ควรขึ้นอยู่กับเลเยอร์อื่น |
| **โครงสร้างพื้นฐาน** | ข้อกังวลด้านเทคนิค | ใช้อินเทอร์เฟซที่กำหนดไว้ในโดเมน |
**กฎสำคัญ**: การพึ่งพาชี้เข้าด้านใน เลเยอร์โดเมนไม่รู้เกี่ยวกับฐานข้อมูลหรือกรอบงานเว็บ
---

## สถาปัตยกรรมที่ขับเคลื่อนด้วยเหตุการณ์
ส่วนประกอบต่างๆ สื่อสารโดยการปล่อยและตอบสนองต่อ **เหตุการณ์** — สิ่งต่างๆ ที่เกิดขึ้น
| รูปแบบ | คำอธิบาย |
|---------|-------------|
| **ประกาศกิจกรรม** | บริการ A ส่งเสียง "OrderPlaced"; บริการ B, C, D ตอบสนอง |
| **การจัดหากิจกรรม** | เก็บการเปลี่ยนแปลงสถานะทั้งหมดเป็นลำดับเหตุการณ์ (ไม่ใช่แค่สถานะปัจจุบัน) |
| **CQRS** | แยกโมเดลการอ่าน (แบบสอบถาม) ออกจากโมเดลการเขียน (คำสั่ง) |
### การจัดหากิจกรรม
แทนที่จะจัดเก็บ "สถานะปัจจุบัน" ไว้ในฐานข้อมูล ให้จัดเก็บการเปลี่ยนแปลงทุกสถานะเป็นเหตุการณ์:
```
OrderCreated(order_id=123, total=$50)
OrderPaid(order_id=123, payment_id=456)
OrderShipped(order_id=123, tracking=ABC)
```

ประโยชน์ที่ได้รับ: เส้นทางการตรวจสอบที่สมบูรณ์ ความสามารถในการสร้างสถานะในอดีตขึ้นมาใหม่ ผู้บริโภคที่แยกจากกัน ความท้าทาย: วิวัฒนาการของสคีมาเหตุการณ์ ความสอดคล้องในที่สุด ความซับซ้อนในการดีบัก
### CQRS (การแยกความรับผิดชอบแบบสอบถามคำสั่ง)
| ด้านข้าง | วัตถุประสงค์ | ฐานข้อมูล |
|------|---------|----------|
| **คำสั่ง (เขียน)** | จัดการกับการกลายพันธุ์ บังคับใช้กฎเกณฑ์ทางธุรกิจ | ปรับให้เหมาะสมสำหรับการเขียน (ทำให้เป็นมาตรฐาน) |
| **แบบสอบถาม (อ่าน)** | ให้บริการคำขออ่าน | ปรับให้เหมาะสมสำหรับการอ่าน (ผิดปกติ) |
CQRS จับคู่อย่างเป็นธรรมชาติกับ Event Sourcing: กิจกรรมจากด้านการเขียนจะถูกฉายในมุมมองที่ปรับให้เหมาะสมสำหรับการอ่าน

## คิวข้อความและนายหน้ากิจกรรม
เมื่อบริการจำเป็นต้องสื่อสารแบบอะซิงโครนัส คิวข้อความถือเป็นแกนหลัก
| เครื่องมือ | พิมพ์ | ดีที่สุดสำหรับ |
|------|-|---------|
| **Apache Kafka** | บันทึกเหตุการณ์แบบกระจาย | การสตรีมเหตุการณ์ที่มีปริมาณงานสูง, การจัดหาเหตุการณ์ |
| **RabbitMQ** | นายหน้าข้อความพร้อมเส้นทาง | คิวงาน รูปแบบเส้นทางที่ซับซ้อน |
| **AWS SQS** | จัดการคิว | AWS-native การเข้าคิวแบบง่าย |
| **AWS SNS** | การแจ้งเตือน Pub/sub | กระจายไปยังสมาชิกหลายราย |
| **Google Pub/Sub** | จัดการผับ/ย่อย | การสตรีมเหตุการณ์ดั้งเดิมของ GCP |
| **สตรีม Redis** | กระแสน้ำหนักเบา | การบันทึกเหตุการณ์อย่างง่าย กรณีการใช้งานแคช |
### รูปแบบการส่งข้อความ
| รูปแบบ | คำอธิบาย |
|---------|-------------|
| **จุดต่อจุด** | ผู้ผลิตหนึ่งราย ผู้บริโภคหนึ่งรายต่อข้อความ |
| **เผยแพร่/สมัครสมาชิก** | โปรดิวเซอร์หนึ่งราย สมาชิกหลายราย |
| **ขอ/ตอบ** | แบบซิงโครนัสบนการขนส่งแบบอะซิงโครนัส |
| **คิวจดหมายถึงตาย** | ข้อความที่ประมวลผลไม่สำเร็จจะไปยังคิวแยกต่างหากเพื่อตรวจสอบ |

## การออกแบบที่ขับเคลื่อนด้วยโดเมน (DDD)
DDD เป็นแนวทางเชิงกลยุทธ์ในการออกแบบซอฟต์แวร์ที่เน้นโค้ดไปที่แนวคิดทางธุรกิจมากกว่าข้อกังวลทางเทคนิค
### แนวคิดหลัก
| แนวคิด | คำอธิบาย |
|---------|-------------|
| **บริบทมีขอบเขต** | ขอบเขตที่รูปแบบโดเมนมีความสอดคล้องกัน (เช่น "การสั่งซื้อ" "การจัดส่ง" "การเรียกเก็บเงิน") |
| **ภาษาที่แพร่หลาย** | คำศัพท์ที่ใช้ร่วมกันระหว่างนักพัฒนาและผู้เชี่ยวชาญโดเมน |
| **มวลรวม** | กลุ่มของเอนทิตีที่เกี่ยวข้องถือเป็นหน่วยเดียวสำหรับการเปลี่ยนแปลงข้อมูล |
| **หน่วยงาน** | ออบเจ็กต์ที่มีข้อมูลระบุตัวตน (เช่น ผู้ใช้ที่มี user_id) |
| **วัตถุมีค่า** | วัตถุที่ไม่มีตัวตน กำหนดโดยคุณลักษณะ (เช่น เงิน ที่อยู่) |
| **กิจกรรมโดเมน** | สิ่งที่เกิดขึ้นในโดเมน (เช่น OrderPlaced) |
| **ชั้นต่อต้านคอร์รัปชัน** | เลเยอร์การแปลระหว่างโดเมนของคุณและระบบภายนอก |
### เมื่อ DDD ช่วย
DDD จะมีคุณค่ามากที่สุดเมื่อโดเมนธุรกิจมีความซับซ้อน เช่น อีคอมเมิร์ซ โลจิสติกส์ บริการทางการเงิน การดูแลสุขภาพ หากโดเมนของคุณเป็นแบบเรียบง่าย (บล็อก แอปสิ่งที่ต้องทำ) DDD ก็ถือว่าเกินความจำเป็น

## กลยุทธ์การแคช
การแคชเป็นหนึ่งในวิธีที่มีประสิทธิภาพที่สุดในการปรับปรุงประสิทธิภาพ แต่จะนำมาซึ่งความซับซ้อนในด้านความสม่ำเสมอ
| กลยุทธ์ | คำอธิบาย | การแลกเปลี่ยน |
|----------|-------------|-----------|
| **นอกเหนือจากแคช** | แอปพลิเคชันตรวจสอบแคชก่อน โหลดจาก DB เมื่อ miss | เรียบง่าย; ความสม่ำเสมอในที่สุด |
| **เขียนผ่าน** | เขียนลงแคชและ DB พร้อมกัน | สม่ำเสมอ; เขียนช้าลง |
| **เขียนข้างหลัง** | เขียนลงแคช async เขียนถึง DB | เขียนเร็ว; ความเสี่ยงต่อการสูญเสียข้อมูล |
| **อ่านผ่าน** | โหลดแคชจาก DB เมื่อพลาดอย่างโปร่งใส | ง่ายกว่าแคชกัน |
### สิ่งที่ต้องแคช
| เลเยอร์ | อะไร | เครื่องมือ |
|-------|-------|-------|
| **ซีดีเอ็น** | สินทรัพย์คงที่ การตอบสนองของ API | CloudFront, Cloudflare |
| **ใบสมัคร** | ผลลัพธ์ที่คำนวณ ข้อมูลเซสชัน | Redis, Memcached |
| **ฐานข้อมูล** | ผลลัพธ์การค้นหา แถวที่เข้าถึงบ่อย | แคชแบบสอบถาม มุมมองที่เป็นรูปธรรม |
**การทำให้แคชใช้ไม่ได้** เป็นเรื่องยากอย่างฉาวโฉ่ กลยุทธ์ทั่วไป: TTL (time-to-live) การทำให้เหตุการณ์เป็นโมฆะ (ล้างแคชเมื่อมีการเปลี่ยนแปลงข้อมูล) และการขับไล่ LRU (ใช้ล่าสุดน้อยที่สุด)

## รูปแบบการออกแบบ
### หลักการที่มั่นคง
| หลักการ | มันหมายถึงอะไร |
|----------|--------------|
| **S** — ความรับผิดชอบเดี่ยว | คลาสควรมีเหตุผลเดียวที่จะเปลี่ยน |
| **O** — เปิด/ปิด | เปิดเพื่อขยาย ปิดเพื่อแก้ไข |
| **L** — การทดแทนลิสคอฟ | ชนิดย่อยควรทดแทนได้สำหรับประเภทพื้นฐาน |
| **I** — การแยกส่วนต่อประสาน | อินเทอร์เฟซเฉพาะจำนวนมาก > อินเทอร์เฟซอเนกประสงค์หนึ่งรายการ |
| **D** — การผกผันการพึ่งพา | ขึ้นอยู่กับนามธรรม ไม่ใช่คอนกรีต |
### รูปแบบทั่วไป
| รูปแบบ | เจตนา | ตัวอย่าง |
|---------|--------|---------|
| **ซิงเกิลตัน** | ตรวจสอบให้แน่ใจว่าคลาสมีอินสแตนซ์เดียวเท่านั้น | พูลการเชื่อมต่อฐานข้อมูล |
| **โรงงาน** | สร้างวัตถุโดยไม่ต้องระบุคลาสที่แน่นอน | `UserFactory.create(type="admin")`|
| **ผู้สังเกตการณ์** | แจ้งผู้อยู่ในอุปการะเมื่อสถานะเปลี่ยนแปลง | ผู้ฟังเหตุการณ์ pub/sub |
| **กลยุทธ์** | สลับอัลกอริธึมที่รันไทม์ | กลยุทธ์การชำระเงิน: บัตรเครดิต, PayPal, Crypto |
| **พื้นที่เก็บข้อมูล** | การเข้าถึงข้อมูลเชิงนามธรรมเบื้องหลังอินเทอร์เฟซใหม่ทั้งหมด | `UserRepository.find_by_id(123)`|

## การเลือกสถาปัตยกรรมที่เหมาะสม
ไม่มีสถาปัตยกรรมที่ "ดีที่สุด" ในระดับสากล ทางเลือกที่เหมาะสมขึ้นอยู่กับ:
| ปัจจัย | ชอบ Monolith เมื่อ... | ชอบไมโครเซอร์วิสเมื่อ... |
|--------|------------------------|----------------------------------|
| **ขนาดทีม** | < 10 developers | >นักพัฒนา 20 คน หลายทีม |
| **ความซับซ้อนของโดเมน** | ง่ายหรือเข้าใจดี | บริบทที่ซับซ้อนและมีขอบเขตมากมาย |
| **ข้อกำหนดด้านขนาด** | ความต้องการปรับขนาดสม่ำเสมอ | ส่วนประกอบที่แตกต่างกันต้องใช้ขนาดที่แตกต่างกัน |
| **จังหวะการปรับใช้** | รอบการเปิดตัวเดี่ยว | จำเป็นต้องปรับใช้อย่างอิสระ |
| **ความหลากหลายของเทคโนโลยี** | สแต็คเดียวก็ได้ | บริการที่แตกต่างกันต้องการเทคโนโลยีที่แตกต่างกัน |
**คำแนะนำเชิงปฏิบัติ**: เริ่มต้นด้วยเสาหินแบบโมดูลาร์ แยกบริการเฉพาะเมื่อคุณมีความต้องการที่ชัดเจนและขอบเขตโดเมนที่ชัดเจน ไมโครเซอร์วิสก่อนกำหนดเป็นหนึ่งในข้อผิดพลาดทางสถาปัตยกรรมที่พบบ่อยที่สุดในอุตสาหกรรม
