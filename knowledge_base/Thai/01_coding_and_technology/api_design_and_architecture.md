# การออกแบบและสถาปัตยกรรม API
API (Application Programming Interface) คือวิธีที่ส่วนประกอบซอฟต์แวร์พูดคุยกัน API ที่ออกแบบมาอย่างดีนั้นใช้งานง่าย สม่ำเสมอ และน่าใช้งาน การออกแบบที่ไม่ดีทำให้เกิดความสับสน บั๊ก และความคับข้องใจ ไฟล์นี้ครอบคลุมถึงหลักการ รูปแบบ และแนวทางปฏิบัติในการสร้าง API ที่นักพัฒนาต้องการใช้จริงๆ
---

## หลักการ REST API
REST (Representational State Transfer) คือรูปแบบสถาปัตยกรรมที่โดดเด่นสำหรับ Web API โดยถือว่าข้อมูลเป็น **ทรัพยากร** ที่ระบุโดย URL และใช้วิธีการ HTTP เพื่อดำเนินการกับข้อมูลเหล่านั้น
### หลักการสำคัญ
| หลักการ | คำอธิบาย |
|-----------|-------------|
| **แหล่งข้อมูล** | ทุกอย่างเป็นทรัพยากรที่มี URI (`/users/123`,`/orders/456`) |
| **วิธี HTTP** | GET (อ่าน), POST (สร้าง), PUT (แทนที่), PATCH (อัพเดตบางส่วน), DELETE (ลบ) |
| **การไร้สัญชาติ** | แต่ละคำขอมีข้อมูลทั้งหมดที่จำเป็น ไม่มีสถานะเซสชันฝั่งเซิร์ฟเวอร์ |
| **อินเทอร์เฟซแบบยูนิฟอร์ม** | การตั้งชื่อทรัพยากรที่สอดคล้องกัน วิธีการมาตรฐาน รหัสสถานะมาตรฐาน |
| **การเป็นตัวแทน** | ทรัพยากรสามารถแสดงได้หลายรูปแบบ (JSON, XML) |
### อนุสัญญาการตั้งชื่อทรัพยากร
| ทำ | อย่า |
|----|-------|
| `/users`(คำนามพหูพจน์) | `/user`(เอกพจน์) |
| `/users/123/orders`(ซ้อนกัน) |  __ป้องกัน_3__ |
| `/products?category=electronics`(พารามิเตอร์แบบสอบถามสำหรับการกรอง) |  __ป้องกัน_5__ |
| ใช้เครื่องหมายขีดกลาง:`/user-profiles`| ใช้ขีดล่าง:`/user_profiles`|
### วิธีการ HTTP และ Idempotency
| วิธีการ | วัตถุประสงค์ | ไร้อำนาจ? | ปลอดภัย? |
|--------|---------|-------------|-------|
| **รับ** | อ่านทรัพยากร | ✅ ใช่ | ✅ ใช่ |
| **โพสต์** | สร้างทรัพยากร | ❌ ไม่ | ❌ ไม่ |
| **ใส่** | แทนที่ทรัพยากรทั้งหมด | ✅ ใช่ | ❌ ไม่ |
| **แพทช์** | อัปเดตทรัพยากรบางส่วน | ❌ ไม่* | ❌ ไม่ |
| **ลบ** | ลบทรัพยากร | ✅ ใช่ | ❌ ไม่ |
*PATCH สามารถสร้าง idempotent ได้ด้วยการออกแบบอย่างระมัดระวัง
### รหัสสถานะ HTTP
| รหัส | ความหมาย | เมื่อใดควรใช้ |
|------|---------|-------------|
| **200** | ตกลง | รับ วาง แพทช์ ลบ | สำเร็จแล้ว
| **201** | สร้างแล้ว | POST สำเร็จ (สร้างทรัพยากรแล้ว) |
| **204** | ไม่มีเนื้อหา | ลบสำเร็จ (ไม่มีอะไรจะคืน) |
| **400** | คำขอไม่ถูกต้อง | อินพุตไม่ถูกต้องหรือคำขอมีรูปแบบไม่ถูกต้อง |
| **401** | ไม่ได้รับอนุญาต | การรับรองความถูกต้องหายไปหรือไม่ถูกต้อง |
| **403** | ต้องห้าม | รับรองความถูกต้องแต่ไม่ได้รับอนุญาต |
| **404** | ไม่พบ | ไม่มีทรัพยากร |
| **409** | ความขัดแย้ง | ทรัพยากรซ้ำหรือข้อขัดแย้งของสถานะ |
| **422** | เอนทิตีที่ไม่สามารถประมวลผลได้ | JSON ที่ถูกต้อง แต่มีข้อผิดพลาดทางความหมาย |
| **429** | คำขอมากเกินไป | เกินขีดจำกัดอัตรา |
| **500** | ข้อผิดพลาดภายในเซิร์ฟเวอร์ | ข้อผิดพลาดของเซิร์ฟเวอร์ที่ไม่คาดคิด |
| **502** | เกตเวย์ไม่ถูกต้อง | บริการต้นทางล้มเหลว |
| **503** | ไม่มีบริการ | โอเวอร์โหลดหรือบำรุงรักษาชั่วคราว |

## การกำหนดเวอร์ชัน API
API พัฒนาขึ้น เมื่อคุณจำเป็นต้องทำการเปลี่ยนแปลงที่สำคัญ การกำหนดเวอร์ชันจะช่วยให้ไคลเอ็นต์ที่มีอยู่ทำงานต่อไปได้
| กลยุทธ์ | ตัวอย่าง | ข้อดี | ข้อเสีย |
|----------|---------|-------|-|
| **เส้นทาง URL** |  __ป้องกัน_0__ , __ป้องกัน_1__ | เรียบง่าย ชัดเจน | การเปลี่ยนแปลง URL ต่อเวอร์ชัน |
| **พารามิเตอร์การค้นหา** |  __ป้องกัน_2__ | ยืดหยุ่น | ลืมง่าย |
| **ส่วนหัว** |  __ป้องกัน_3__ | ล้าง URL | ค้นพบได้น้อยลง |
| **ไม่มีเวอร์ชัน** | วิวัฒนาการสคีมาเท่านั้น | ง่ายที่สุด | การเปลี่ยนแปลงที่ทำลายล้างส่งผลต่อทุกคน |
**แนวทางปฏิบัติที่ดีที่สุด**: ใช้การกำหนดเวอร์ชันเส้นทาง URL (`/v1/`) เพื่อความชัดเจน รองรับเวอร์ชันก่อนหน้าอย่างน้อยหนึ่งเวอร์ชัน เลิกใช้เวอร์ชันเก่าโดยมีไทม์ไลน์ที่ชัดเจน
---

## วิธีการรับรองความถูกต้อง
| วิธีการ | มันทำงานอย่างไร | ดีที่สุดสำหรับ |
|--------|-------------|----------|
| **คีย์ API** | รหัสลับในส่วนหัว (`X-API-Key: abc123`) | การผสานรวมแบบเซิร์ฟเวอร์ต่อเซิร์ฟเวอร์อย่างง่าย |
| **OAuth2** | การมอบหมายตามโทเค็นพร้อมขอบเขต | การเข้าถึงของบุคคลที่สาม แอปที่ได้รับอนุญาตจากผู้ใช้ |
| **เจดับบลิว** | โทเค็นที่มีอยู่ในตัวเองพร้อมการอ้างสิทธิ์ | การรับรองความถูกต้องไร้สัญชาติในบริการต่างๆ |
| **การตรวจสอบสิทธิ์ขั้นพื้นฐาน** | ชื่อผู้ใช้ที่เข้ารหัส Base64:รหัสผ่าน | การพัฒนาเท่านั้น — ไม่เคยผลิตโดยไม่มี TLS |
| **คุกกี้เซสชั่น** | รหัสเซสชันฝั่งเซิร์ฟเวอร์ในคุกกี้ HTTP เท่านั้น | เว็บแอปพลิเคชันแบบดั้งเดิม |
### ขั้นตอน OAuth2 (แบบง่าย)
1. ลูกค้าเปลี่ยนเส้นทางผู้ใช้ไปยังเซิร์ฟเวอร์การอนุญาต
2. ผู้ใช้เข้าสู่ระบบและให้สิทธิ์
3. เซิร์ฟเวอร์การอนุญาตส่งคืนรหัสการอนุญาต
4. ลูกค้าแลกเปลี่ยนรหัสสำหรับโทเค็นการเข้าถึง (และอาจรีเฟรชโทเค็นหรือไม่ก็ได้)
5. ลูกค้าใช้โทเค็นการเข้าถึงเพื่อเรียก API
6. เมื่อโทเค็นการเข้าถึงหมดอายุ ให้ใช้โทเค็นการรีเฟรชเพื่อรับโทเค็นใหม่

## รูปแบบ API: REST เทียบกับ GraphQL เทียบกับ gRPC
| คุณสมบัติ | ส่วนที่เหลือ | GraphQL | gRPC |
|---------|-|---------|-|
| **รูปแบบข้อมูล** | JSON (โดยทั่วไป) | เจสัน | Protobuf (ไบนารี) |
| **ปลายทาง** | หลายรายการ (หนึ่งรายการต่อทรัพยากร) | ปลายทางเดียว | กำหนดโดยไฟล์ .proto |
| **ดึงข้อมูลมากเกินไป** | ธรรมดา (ได้เกินความจำเป็น) | ไม่มี (ลูกค้าระบุฟิลด์) | ไม่มี (กำหนดสคีมา) |
| **ดึงข้อมูลน้อยเกินไป** | ต้องมีการโทรหลายครั้ง | ไม่มี (ได้รับสิ่งที่จำเป็นอย่างแน่นอน) | ไม่มี |
| **เรียลไทม์** | จำเป็นต้องมี WebSockets | การสมัครสมาชิกในตัว | สตรีมมิ่งในตัว |
| **แคช** | การแคช HTTP ทำงานได้ตามปกติ | แคชยากกว่า | จำกัด |
| **เส้นโค้งการเรียนรู้** | ต่ำ | ปานกลาง | ปานกลาง–สูง |
| **ดีที่สุดสำหรับ** | API สาธารณะ, แอป CRUD | UIs ที่ซับซ้อน แอพมือถือ | ไมโครเซอร์วิสภายใน ประสิทธิภาพสูง |

## การแบ่งหน้า การกรอง และการเรียงลำดับ
สำหรับปลายทางที่ส่งคืนรายการ:
| เทคนิค | ตัวอย่าง | เมื่อใดควรใช้ |
|----------|---------|-------------|
| **ออฟเซ็ต/ขีดจำกัด** |  __ป้องกัน_0__ | เรียบง่าย; ใช้ได้กับชุดข้อมูลขนาดเล็ก |
| **ตามเคอร์เซอร์** |  __ป้องกัน_1__ | ชุดข้อมูลขนาดใหญ่ ผลลัพธ์ที่สม่ำเสมอ |
| **ชุดคีย์** |  __ป้องกัน_2__ | มีประสิทธิภาพมาก ต้องใช้คีย์เฉพาะ |
```json
// Cursor-based response
{
  "data": [...],
  "pagination": {
    "next_cursor": "abc123",
    "has_more": true
  }
}
```

## การจำกัดอัตรา
ปกป้อง API ของคุณจากการละเมิดและรับรองการใช้งานโดยชอบธรรม
| กลยุทธ์ | มันทำงานอย่างไร |
|----------|-------------|
| **แก้ไขหน้าต่าง** | N คำขอต่อกรอบเวลา (เช่น 100/ชั่วโมง) |
| **หน้าต่างบานเลื่อน** | ละเอียดยิ่งขึ้น นับคำขอในหน้าต่างกลิ้ง |
| **ถังโทเค็น** | โทเค็นเพิ่มในอัตราคงที่ แต่ละคำขอใช้โทเค็น |
ส่งคืน`429 Too Many Requests`พร้อมส่วนหัว:```
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1625097600
Retry-After: 60
```

## การจัดการข้อผิดพลาด
การตอบสนองข้อผิดพลาดที่สอดคล้องกันทำให้ API ทำงานได้ง่ายขึ้นมาก:
```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Invalid input data",
    "details": [
      {
        "field": "email",
        "issue": "Invalid email format"
      }
    ]
  }
}
```

**หลักการ**: ใช้โครงสร้างข้อผิดพลาดที่สอดคล้องกัน รวมข้อความที่ดำเนินการได้ ใช้รหัสสถานะ HTTP มาตรฐาน บันทึกข้อผิดพลาดฝั่งเซิร์ฟเวอร์ด้วยรหัสความสัมพันธ์ และไม่เปิดเผยสแต็กเทรซหรือรายละเอียดภายใน

## เอกสาร API
| เครื่องมือ | คำอธิบาย |
|-|-------------|
| **OpenAPI (ผยอง)** | มาตรฐานอุตสาหกรรมสำหรับเอกสารประกอบ REST API |
| **Swagger UI** | เอกสารประกอบ API แบบโต้ตอบจากข้อกำหนด OpenAPI |
| **บุรุษไปรษณีย์** | การทดสอบ API เอกสาร และการแชร์คอลเลกชัน |
| **ทำซ้ำ** | เอกสารอ้างอิง API ที่สวยงามจากข้อมูลจำเพาะ OpenAPI |
| **GraphQL Playground / GraphiQL** | การสำรวจ GraphQL แบบโต้ตอบ |
**แนวทางปฏิบัติที่ดีที่สุด**: เขียนข้อมูลจำเพาะของ OpenAPI ก่อน (การพัฒนาที่ขับเคลื่อนด้วยข้อมูลจำเพาะ) จากนั้นสร้างเอกสารประกอบและ SDK ไคลเอ็นต์จากข้อมูลจำเพาะนั้น

## รูปแบบเกตเวย์ API
เกตเวย์ API ตั้งอยู่ระหว่างไคลเอ็นต์และบริการแบ็กเอนด์ โดยมีจุดเริ่มต้นเพียงจุดเดียว
| ความรับผิดชอบ | คำอธิบาย |
|---------------|-------------|
| **การกำหนดเส้นทาง** | คำขอโดยตรงไปยังบริการแบ็กเอนด์ที่เหมาะสม |
| **การรับรองความถูกต้อง** | ตรวจสอบโทเค็นที่ระดับเกตเวย์ |
| **การจำกัดอัตรา** | ใช้ขีดจำกัดสากลหรือต่อไคลเอ็นต์ |
| **การเปลี่ยนแปลง** | แปลงระหว่างโปรโตคอล (REST ↔ gRPC) |
| **แคช** | แคชคำตอบทั่วไป |
| **การตรวจสอบ** | การบันทึกและการวัดแบบรวมศูนย์ |
| **โหลดบาลานซ์** | กระจายการรับส่งข้อมูลข้ามอินสแตนซ์บริการ |
| เครื่องมือ | พิมพ์ |
|-|------|
| **ก้อง** | เกตเวย์ API โอเพ่นซอร์ส (อิง Nginx) |
| **เกตเวย์ AWS API** | จัดการอย่างเต็มรูปแบบ บูรณาการกับ AWS |
| **การจัดการ Azure API** | เกตเวย์ที่ได้รับการจัดการด้วยพอร์ทัลนักพัฒนา |
| **ทูต / อิสติโอ** | บริการตาข่ายที่มีความสามารถเกตเวย์ API |
| **เทรฟิก** | การค้นพบอัตโนมัติ มาเข้ารหัสการรวมเข้าด้วยกัน |

## เว็บฮุค
Webhooks ช่วยให้ API ของคุณส่งเหตุการณ์ไปยังไคลเอนต์แบบเรียลไทม์ แทนที่จะทำการสำรวจความคิดเห็นของลูกค้าเกี่ยวกับการเปลี่ยนแปลง
| ด้าน | แนวปฏิบัติที่ดีที่สุด |
|--------|--------------|
| **จัดส่ง** | คำขอ POST พร้อมเพย์โหลด JSON ไปยัง URL ของลูกค้า |
| **ความปลอดภัย** | ลงนามเพย์โหลดด้วย HMAC ลูกค้าตรวจสอบลายเซ็น |
| **ความน่าเชื่อถือ** | ลองนำส่งที่ล้มเหลวอีกครั้งด้วย Exponential Backoff |
| **ความเป็นอมตะ** | รวมรหัสเหตุการณ์ที่ไม่ซ้ำ ไคลเอ็นต์จัดการรายการที่ซ้ำกัน |
| **เวอร์ชัน** | รวมเวอร์ชัน API ใน payload ของ webhook |

## รายการตรวจสอบการออกแบบ
- [ ] ทรัพยากรเป็นคำนามพหูพจน์ (`/users`ไม่ใช่`/getUser`)
- [ ] ใช้วิธี HTTP อย่างถูกต้อง (GET สำหรับการอ่าน POST สำหรับการสร้าง ฯลฯ )
- [ ] รูปแบบการตอบสนองข้อผิดพลาดที่สอดคล้องกัน
- [ ] การแบ่งหน้าสำหรับจุดสิ้นสุดรายการทั้งหมด
- [ ] การจำกัดอัตราด้วยส่วนหัวที่ชัดเจน
- [ ] กำหนดกลยุทธ์การกำหนดเวอร์ชัน API
- [ ] มีการรับรองความถูกต้องและการอนุญาตแล้ว
- [ ] การตรวจสอบอินพุตบนปลายทางทั้งหมด
- [ ] เก็บรักษาเอกสาร OpenAPI/Swagger
- [ ] CORS กำหนดค่าอย่างถูกต้อง
- [ ] HTTPS บังคับใช้ในการผลิต
- [ ] ปุ่ม Idempotency สำหรับการดำเนินการ POST เมื่อจำเป็น
