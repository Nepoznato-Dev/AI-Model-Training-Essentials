# วิธีการทดสอบ
การทดสอบเป็นวิธีที่ทำให้คุณมั่นใจว่าโค้ดของคุณใช้งานได้ และที่สำคัญกว่านั้น การเปลี่ยนแปลงจะไม่ทำลายสิ่งที่ใช้ได้ผลอยู่แล้ว การทดสอบที่ดีจะตรวจจับจุดบกพร่องก่อนที่ผู้ใช้จะดำเนินการ บันทึกพฤติกรรมที่คาดหวัง และเปิดใช้งานการปรับโครงสร้างใหม่อย่างไม่เกรงกลัว ไฟล์นี้ครอบคลุมกลยุทธ์การทดสอบทั้งหมด ตั้งแต่การทดสอบหน่วยไปจนถึงการทดสอบแบบ end-to-end และหลักการที่ทำให้การทดสอบมีประสิทธิภาพ
---

## ปิรามิดทดสอบ
ปิระมิดการทดสอบอธิบายถึงการกระจายการทดสอบในอุดมคติในโครงการ
```
        /  E2E  \          ← Few; slow; expensive; test the whole system
       /─────────\
      / Integration\       ← Some; test how components work together
     /───────────────\
    /   Unit Tests    \    ← Many; fast; cheap; test individual functions
   /─────────────────────\
```

| ระดับ | นับ | ความเร็ว | ราคา | มันทดสอบอะไร |
|-------|-------|-------|-|---------------|
| **หน่วย** | มากมาย | เร็ว (มิลลิวินาที) | ต่ำ | ฟังก์ชันส่วนบุคคล คลาส วิธีการ |
| **บูรณาการ** | บางส่วน | ปานกลาง (100ms-s) | ปานกลาง | ส่วนประกอบโต้ตอบกันอย่างไร การสืบค้นฐานข้อมูล การเรียก API |
| **E2E** | ไม่กี่ | ช้า (วินาที-นาที) | สูง | User เต็มไหลผ่านระบบจริง |

## การทดสอบหน่วย
การทดสอบโค้ดแต่ละหน่วยแยกกัน
###หลักการ
| หลักการ | คำอธิบาย |
|-----------|-------------|
| **รวดเร็ว** | การทดสอบแต่ละครั้งควรรันในหน่วยมิลลิวินาที |
| **โดดเดี่ยว** | การทดสอบไม่ได้ขึ้นอยู่กับกันและกัน ไม่มีสถานะที่ใช้ร่วมกัน |
| **กำหนด** | อินพุตเดียวกัน → เอาต์พุตเดียวกันทุกครั้ง (ไม่มีการสุ่ม ไม่มีการพึ่งพาเวลา) |
| **ตรวจสอบด้วยตนเอง** | การทดสอบผ่านหรือล้มเหลวโดยอัตโนมัติ ไม่มีการตรวจสอบด้วยตนเอง |
| **ทันเวลา** | เขียนข้างหรือข้างหน้าโค้ด (TDD) |
### กายวิภาคของการทดสอบ
| เฟส | คำอธิบาย |
|-------|-------------|
| **จัด** | ตั้งค่าข้อมูลทดสอบและการขึ้นต่อกัน |
| **พระราชบัญญัติ** | เรียกใช้ฟังก์ชันหรือเมธอดที่กำลังทดสอบ |
| **ยืนยัน** | ตรวจสอบผลลัพธ์ที่ตรงกับความคาดหวัง |
### สิ่งที่ต้องทดสอบ
| หมวดหมู่ | ตัวอย่าง |
|----------|---------|
| **เส้นทางแห่งความสุข** | อินพุตปกติจะสร้างเอาต์พุตที่คาดหวัง |
| **เคสขอบ** | อินพุตว่าง, null, ศูนย์, ค่าสูงสุด, องค์ประกอบเดียว |
| **กรณีข้อผิดพลาด** | อินพุตไม่ถูกต้อง ข้อมูลหายไป สิทธิ์ถูกปฏิเสธ |
| **เงื่อนไขขอบเขต** | ทีละคน; ตรงขีดจำกัด |
### การเยาะเย้ยและการขัดจังหวะ
| ระยะเวลา | คำอธิบาย | เมื่อใดควรใช้ |
|------|-------------|-------------|
| **ล้อเลียน** | วัตถุปลอมที่บันทึกวิธีการเรียกว่า | การตรวจสอบการโต้ตอบ (วิธีนี้เรียกว่าหรือไม่) |
| **ต้นขั้ว** | วัตถุปลอมที่ส่งคืนค่าที่กำหนดไว้ล่วงหน้า | ให้ข้อมูลการทดสอบ (ส่งคืนผู้ใช้รายนี้จากฐานข้อมูล) |
| **สายลับ** | wrapper ที่บันทึกการเรียกไปยังวัตถุจริง | การยืนยันบางส่วน |
| **ของปลอม** | การใช้งานที่เรียบง่ายแต่ใช้งานได้จริง | ฐานข้อมูลในหน่วยความจำสำหรับการทดสอบ |
| ห้องสมุดจำลอง | ภาษา |
|----------------|--------|
| **unittest.mock** | หลาม |
| **เจส** | จาวาสคริปต์/ไทป์สคริปต์ |
| **ม็อกกิ้ง** | ชวา |
| **ขั้นต่ำ** | ซี# |
| **เป็นพยาน / gomock** | ไป |

## การทดสอบบูรณาการ
ทดสอบว่าส่วนประกอบต่างๆ ทำงานร่วมกันอย่างไร
| สิ่งที่ต้องทดสอบ | ตัวอย่าง |
|-------------|---------|
| **แบบสอบถามฐานข้อมูล** | ORM สร้าง SQL ที่ถูกต้องหรือไม่ มีการใช้ดัชนีหรือไม่? |
| **จุดสิ้นสุด API** | วงจรการตอบกลับคำขอทั้งหมดใช้งานได้หรือไม่ |
| **การโต้ตอบการบริการ** | บริการ A เรียกใช้บริการ B อย่างถูกต้องหรือไม่ |
| **การพึ่งพาภายนอก** | การรวมเกตเวย์การชำระเงินใช้งานได้หรือไม่ |
### กลยุทธ์
| กลยุทธ์ | คำอธิบาย | การแลกเปลี่ยน |
|----------|-------------|-----------|
| **การพึ่งพาที่แท้จริง** | ใช้ฐานข้อมูลจริงคิวข้อความจริง | สมจริงที่สุด; ช้าลง; ตั้งค่ายากขึ้น |
| **ทดสอบตู้คอนเทนเนอร์** | หมุนคอนเทนเนอร์ Docker สำหรับการทดสอบแต่ละครั้ง | สมดุลที่ดี ทำซ้ำได้ |
| **ทางเลือกในหน่วยความจำ** | H2 แทน PostgreSQL; บัสข้อความในหน่วยความจำ | เร็ว; อาจพลาดประเด็นโลกแห่งความเป็นจริง |
| **ทดสอบสัญญา** | ตรวจสอบว่าบริการเป็นไปตามสัญญา API | จับการเปลี่ยนแปลงอินเทอร์เฟซ |

## การทดสอบแบบครบวงจร (E2E)
การทดสอบระบบที่สมบูรณ์จากมุมมองของผู้ใช้
| เครื่องมือ | พิมพ์ | ดีที่สุดสำหรับ |
|------|-|---------|
| **นักเขียนบทละคร** | เบราว์เซอร์อัตโนมัติ | แอปพลิเคชันเว็บ ข้ามเบราว์เซอร์ |
| **ไซเปรส** | เบราว์เซอร์อัตโนมัติ | แอปพลิเคชันเว็บ ประสบการณ์ของนักพัฒนา |
| **ซีลีเนียม** | เบราว์เซอร์อัตโนมัติ | มรดก; รองรับภาษาที่หลากหลาย |
| **ดีท็อกซ์** | มือถือ E2E | ตอบสนองแอปเนทีฟ |
| **แอปเปียม** | มือถือ E2E | แอพมือถือเนทีฟและไฮบริด |
| **เกจิ** | มือถือ E2E | แอพมือถือ ไวยากรณ์ YAML อย่างง่าย |
| **k6 / ตั๊กแตน** | โหลดการทดสอบ | ประสิทธิภาพภายใต้ภาระงาน |
### แนวทางปฏิบัติที่ดีที่สุดของ E2E
| การปฏิบัติ | ทำไม |
|----------|-----|
| **ทดสอบเส้นทางวิกฤตเท่านั้น** | การทดสอบ E2E ช้า มุ่งเน้นไปที่สิ่งที่สำคัญที่สุด |
| **ใช้โรงงานข้อมูลทดสอบ** | สร้างข้อมูลทดสอบโดยทางโปรแกรม ไม่ต้องพึ่งพาข้อมูลเริ่มต้น |
| **ทำความสะอาดหลังการทดสอบ** | การทดสอบแต่ละครั้งควรปล่อยให้ระบบอยู่ในสถานะที่ทราบ |
| **หลีกเลี่ยงการทดสอบรายละเอียด UI** | ทดสอบพฤติกรรม ไม่ใช่คลาส CSS หรือตำแหน่งองค์ประกอบ |
| **ทำงานใน CI** | การทดสอบ E2E จะต้องทำงานโดยอัตโนมัติในทุกการเปลี่ยนแปลง |

## การพัฒนาที่ขับเคลื่อนด้วยการทดสอบ (TDD)
เขียน test ก่อน แล้วจึงเขียน code เพื่อให้ผ่าน
| ขั้นตอน | คำอธิบาย |
|-|-------------|
| **1. แดง** | เขียนการทดสอบที่ล้มเหลวซึ่งอธิบายพฤติกรรมที่ต้องการ |
| **2. เขียว** | เขียนโค้ดขั้นต่ำเพื่อให้การทดสอบผ่าน |
| **3. รีแฟคเตอร์** | ทำความสะอาดโค้ดในขณะที่ยังคงทดสอบสีเขียว |
| ผลประโยชน์ | คำอธิบาย |
|---------|-------------|
| **คำติชมการออกแบบ** | การทดสอบบังคับให้คุณคิดถึงอินเทอร์เฟซก่อนใช้งาน |
| **ความปลอดภัยในการถดถอย** | ทุกจุดบกพร่องจะได้รับการทดสอบ ข้อผิดพลาดไม่สามารถย้อนกลับได้ |
| **เอกสาร** | การทดสอบทำหน้าที่เป็นเอกสารสำคัญของพฤติกรรมที่คาดหวัง |
| **ความมั่นใจ** | ความครอบคลุมของการทดสอบสูงทำให้สามารถปรับเปลี่ยนโครงสร้างใหม่ได้อย่างไม่เกรงกลัว
---

## การพัฒนาที่ขับเคลื่อนด้วยพฤติกรรม (BDD)
BDD ขยาย TDD ด้วยการเขียนการทดสอบในภาษาธรรมชาติที่อธิบายพฤติกรรมจากมุมมองของผู้ใช้
### รูปแบบที่ให้ไว้เมื่อไรแล้ว
```
Given a user with an empty shopping cart
When they add a "Python Book" priced at $29.99
Then the cart total should be $29.99
And the cart should contain 1 item
```

| เครื่องมือ | ภาษา |
|------|----------|
| **แตงกวา** | Java, JavaScript, Ruby และอื่นๆ |
| **ประพฤติตน** | หลาม |
| **SpecFlow** | ซี# |
| **Jest** (พร้อมคำอธิบาย/มัน) | จาวาสคริปต์ |

## ประเภทการทดสอบอื่น ๆ
| พิมพ์ | มันทดสอบอะไร | เครื่องมือ |
|------|------------------|-------|
| **ประสิทธิภาพ/โหลด** | ลักษณะการทำงานของระบบภายใต้โหลด | k6, JMeter, ตั๊กแตน, Gatling |
| **ความปลอดภัย** | เวกเตอร์ช่องโหว่และการโจมตี | OWASP ZAP, Burp Suite, Snyk |
| **การเข้าถึง** | การปฏิบัติตาม WCAG | ขวาน ประภาคาร pa11y |
| **สัญญา** | ความเข้ากันได้ของ API ระหว่างบริการ | สนธิสัญญา สัญญา Spring Cloud |
| **การกลายพันธุ์** | คุณภาพของชุดทดสอบนั้นเอง | สไตรเกอร์, โง่เขลา, PIT |
| **การถดถอยทางสายตา** | UI เปลี่ยนแปลงระหว่างเวอร์ชัน | เพอร์ซี่, รงค์, BackstopJS |
| **ความโกลาหล** | ความยืดหยุ่นของระบบต่อความล้มเหลว | ลิงแห่งความโกลาหล สารสีน้ำเงิน เกรมลิน |
| **ควัน** | ฟังก์ชั่นพื้นฐานหลังจากการปรับใช้ | สคริปต์ที่กำหนดเอง ตรวจสุขภาพ |
| **แช่อิ่ม** | ลักษณะการทำงานของระบบในช่วงเวลาที่ขยายออกไป | การทดสอบโหลดระยะยาว |

## องค์กรทดสอบ
| รูปแบบ | คำอธิบาย | เมื่อใดควรใช้ |
|---------|-------------|-------------|
| **ตั้งอยู่ร่วมกัน** | การทดสอบถัดจากโค้ดที่พวกเขาทดสอบ (`src/utils.test.ts`) | โครงการส่วนใหญ่ หาง่าย |
| **ไดเรกทอรีแยกต่างหาก** | ทดสอบในโฟลเดอร์`tests/`หรือ`__tests__/`| โครงการขนาดใหญ่ แยกชัดเจน |
| **โปรแกรมทดสอบ** | ข้อมูลการทดสอบที่ใช้ร่วมกันในไดเร็กทอรี`fixtures/`| เมื่อการทดสอบหลายรายการต้องการข้อมูลเดียวกัน |
| **ทดสอบสาธารณูปโภค** | ผู้ช่วยเหลือที่แชร์ในไดเร็กทอรี`test-utils/`| เมื่อตรรกะการตั้งค่าซับซ้อน |

## ความคุ้มครองรหัส
| เมตริก | มันวัดอะไร | ข้อจำกัด |
|--------|-----------------|------------|
| **ความครอบคลุมของสาย** | เปอร์เซ็นต์ของบรรทัดโค้ดที่ดำเนินการโดยการทดสอบ | ไม่ได้วัดคุณภาพของการยืนยัน |
| **ความคุ้มครองสาขา** | เปอร์เซ็นต์ของสาขา (ถ้า/อื่น) ที่ได้รับ | ดีกว่าการครอบคลุมของเส้น ยังจับจุดบกพร่องไม่หมด |
| **ความคุ้มครองเส้นทาง** | เปอร์เซ็นต์ของเส้นทางการดำเนินการที่ใช้ | ละเอียดที่สุด; เอ็กซ์โปเนนเชียลในโค้ดที่ซับซ้อน |
| **คะแนนการกลายพันธุ์** | เปอร์เซ็นต์ของการกลายพันธุ์ที่จับได้โดยการทดสอบ | การวัดคุณภาพการทดสอบที่ดีที่สุด |
**เป้าหมาย**: ความครอบคลุมของบรรทัด 80% เป็นค่าเริ่มต้นที่สมเหตุสมผล แต่ความครอบคลุมเป็นเพียงแนวทาง ไม่ใช่เป้าหมาย — ความครอบคลุม 100% ด้วยการยืนยันที่ไม่ชัดเจนนั้นแย่กว่าการครอบคลุม 70% ด้วยการทดสอบอย่างละเอียด

## การบูรณาการและการทดสอบอย่างต่อเนื่อง
| การปฏิบัติ | คำอธิบาย |
|----------|-------------|

## เคล็ดลับการปฏิบัติ
- **ทดสอบชื่อให้ชัดเจน**`test_calculates_tax_for_high_earner`จะบอกคุณว่ามีอะไรเสียหาย `test_1`ไม่ได้บอกอะไรคุณเลย
- **การยืนยันหนึ่งครั้งต่อการทดสอบ (เมื่อใช้งานได้จริง)** ทำให้วินิจฉัยความล้มเหลวได้ง่าย
- **อย่าทดสอบรายละเอียดการใช้งาน** ทดสอบพฤติกรรม หากคุณปรับโครงสร้างภายในใหม่ การทดสอบก็ไม่ควรเสียหาย
- **หลีกเลี่ยงการทดสอบโค้ดของบุคคลที่สาม** จำลองไลบรารีภายนอก ทดสอบการโต้ตอบของโค้ดของคุณกับพวกเขา
- **ทำการทดสอบอย่างรวดเร็ว** หากชุดการทดสอบของคุณใช้เวลา 10 นาที นักพัฒนาจะหยุดทำงาน เพิ่มประสิทธิภาพอย่างไม่ลดละ
- **ลบการทดสอบที่ไม่ทำงาน** การทดสอบที่ผ่านหรือทดสอบโค้ดที่ถูกลบเสมอนั้นเป็นปัญหา
- **ปฏิบัติต่อโค้ดทดสอบเหมือนกับโค้ดที่ใช้งานจริง** ควรอ่านได้ บำรุงรักษาได้ และมีโครงสร้างที่ดี

## สรุป
การทดสอบไม่ใช่ทางเลือก แต่เป็นวิธีการสร้างซอฟต์แวร์ที่ไม่เสียหาย ปิระมิดการทดสอบจะนำคุณไปสู่การทดสอบหน่วยที่รวดเร็ว การทดสอบบูรณาการบางส่วน และการทดสอบ E2E บางส่วน TDD และ BDD ให้แนวทางที่มีโครงสร้าง การเยาะเย้ยแยกหน่วยสำหรับการทดสอบ การครอบคลุมโค้ดวัดความกว้างแต่ไม่ใช่ความลึก หลักการที่สำคัญที่สุดคือ: หากไม่ผ่านการทดสอบ แสดงว่าเสียหาย คุณยังไม่รู้
