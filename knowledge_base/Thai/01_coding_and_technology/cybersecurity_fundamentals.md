# พื้นฐานความปลอดภัยทางไซเบอร์
การรักษาความปลอดภัยไม่ใช่คุณลักษณะที่คุณต้องคำนึงถึงในตอนท้าย แต่เป็นวินัยที่ต้องถักทอเข้ากับทุกชั้นของระบบตั้งแต่วันแรก ไม่ว่าคุณกำลังสร้างเว็บแอป จัดการโครงสร้างพื้นฐาน หรือจัดส่ง API การทำความเข้าใจภูมิทัศน์ภัยคุกคามและพื้นฐานของการป้องกันถือเป็นสิ่งสำคัญ
---

## การเข้ารหัสและการเข้ารหัส
### การเข้ารหัสแบบสมมาตรและแบบอสมมาตร
| พิมพ์ | มันทำงานอย่างไร | ความเร็ว | การกระจายคีย์ | ตัวอย่าง |
|------|-----------------|-------|-----------------|---------|
| **สมมาตร** | คีย์เดียวกันสำหรับการเข้ารหัสและถอดรหัส | รวดเร็ว | ความท้าทาย: จะแบ่งปันกุญแจได้อย่างไร? | AES-256, ชาช่า20 |
| **ไม่สมมาตร** | การเข้ารหัสคีย์สาธารณะ, ถอดรหัสคีย์ส่วนตัว | ช้าลง | กุญแจสาธารณะสามารถแชร์ได้อย่างเปิดเผย | RSA, ECC (เส้นโค้งรูปไข่) |
ในทางปฏิบัติ ระบบส่วนใหญ่ใช้ **ทั้งสอง**: การเข้ารหัสแบบอสมมาตรเพื่อแลกเปลี่ยนคีย์แบบสมมาตรอย่างปลอดภัย จากนั้นจึงใช้การเข้ารหัสแบบสมมาตรสำหรับข้อมูลจำนวนมาก นี่คือวิธีการทำงานของ TLS/HTTPS
### แฮช
การแฮชเป็นฟังก์ชันทางเดียว: จะแปลงอินพุตให้เป็นสตริงที่มีขนาดคงที่ คุณไม่สามารถย้อนกลับได้ แต่อินพุตเดียวกันจะสร้างเอาต์พุตเดียวกันเสมอ
| ใช้กรณี | อัลกอริทึมที่แนะนำ | หลีกเลี่ยง |
|----------|----------------------|-------|
| **การจัดเก็บรหัสผ่าน** | Argon2id, bcrypt, สคริปต์ | MD5, SHA-1, SHA-256 ธรรมดา (เร็วเกินไป) |
| **ความสมบูรณ์ของข้อมูล** | SHA-256, SHA-3 | MD5 (เสีย), SHA-1 (เสีย) |
| **ลายเซ็นดิจิทัล** | Ed25519, RSA-2048+ | ดีเอสเอ |
### TLS/HTTPS
HTTPS คือ HTTP ผ่าน TLS (Transport Layer Security) มันมี:
- **การเข้ารหัส**: ผู้ดักฟังไม่สามารถอ่านข้อมูลที่อยู่ระหว่างการส่งได้
- **การรับรองความถูกต้อง**: เซิร์ฟเวอร์พิสูจน์ตัวตนผ่านใบรับรอง
- **ความสมบูรณ์**: ข้อมูลไม่สามารถแก้ไขได้ในระหว่างการขนส่งหากไม่มีการตรวจจับ
ใช้ TLS 1.2 หรือ 1.3 ปิดการใช้งาน TLS 1.0 และ 1.1 เปิดใช้งาน HSTS (HTTP Strict Transport Security) เพื่อบังคับให้เบราว์เซอร์ใช้ HTTPS เสมอ

## การรับรองความถูกต้องและการอนุญาต
### การรับรองความถูกต้อง: คุณเป็นใคร?
| วิธีการ | ระดับความปลอดภัย | ใช้กรณี |
|--------|---------------|----------|
| **รหัสผ่าน** | ต่ำ–ปานกลาง | บัญชีพื้นฐาน (บังคับใช้ 12+ ตัวอักษร ตรวจสอบการละเมิด) |
| **MFA (TOTP)** | สูง | มาตรฐานสำหรับบัญชีที่ละเอียดอ่อน (Google Authenticator, Authy) |
| **คีย์ฮาร์ดแวร์ (FIDO2/WebAuthn)** | สูงมาก | บัญชีที่มีความปลอดภัยสูง (YubiKey) |
| **ไบโอเมตริกซ์** | ปานกลาง–สูง | การปลดล็อคอุปกรณ์ (ลายนิ้วมือ ใบหน้า) — ไม่ดีเท่าปัจจัยเดียว |
| **OAuth2 / OIDC** | สูง | การเข้าสู่ระบบของบุคคลที่สาม ("ลงชื่อเข้าใช้ด้วย Google") |
**กฎรหัสผ่าน**: บังคับใช้ความยาวขั้นต่ำ (12–16 ตัวอักษร) ตรวจสอบรายการรหัสผ่านที่ละเมิด ใช้ Argon2id หรือ bcrypt สำหรับการแฮชด้วยเกลือต่อผู้ใช้
### การอนุญาต: คุณทำอะไรได้บ้าง?
| รุ่น | คำอธิบาย | ตัวอย่าง |
|-------|-------------|---------|
| **RBAC** (การควบคุมการเข้าถึงตามบทบาท) | สิทธิ์ที่กำหนดให้กับบทบาท ผู้ใช้ได้รับบทบาท | ผู้ดูแลระบบ, ผู้แก้ไข, ผู้ดู |
| **ABAC** (ตามคุณสมบัติ) | กฎตามคุณลักษณะผู้ใช้ ทรัพยากร สภาพแวดล้อม | "ผู้จัดการสามารถอนุมัติคำขอของทีมได้" |
| **ACL** (รายการควบคุมการเข้าถึง) | สิทธิ์ที่ชัดเจนต่อผู้ใช้/ทรัพยากร | การอนุญาตไฟล์ (อ่าน/เขียน/ดำเนินการ) |
**หลักการของสิทธิ์ขั้นต่ำ**: ให้สิทธิ์การเข้าถึงขั้นต่ำแก่ผู้ใช้ บริการ และกระบวนการทั้งหมดเท่านั้น
### JWT (โทเค็นเว็บ JSON)
| ด้าน | คำแนะนำ |
|--------|---------------|
| **ลงนาม** | แนะนำให้ใช้ RS256 หรือ ES256 (ไม่สมมาตร) HS256 ยอมรับได้โดยมีการจัดการความลับ |
| **หมดอายุ** | 15–60 นาทีสำหรับโทเค็นการเข้าถึง ใช้โทเค็นการรีเฟรชสำหรับเซสชันที่ยาวขึ้น |
| **การจัดเก็บ** | คุกกี้ HTTP เท่านั้น (ไม่ใช่ localStorage — เสี่ยงต่อ XSS) |
| **การตรวจสอบความถูกต้อง** | ตรวจสอบลายเซ็น ผู้ออก ผู้ชม และการหมดอายุ | เสมอ

## OWASP 10 อันดับแรก (2021)
OWASP Top 10 เป็นเอกสารการรับรู้มาตรฐานสำหรับการรักษาความปลอดภัยแอปพลิเคชันบนเว็บ มันแสดงถึงความเสี่ยงที่สำคัญที่สุด:
| # | ความเสี่ยง | มันหมายถึงอะไร |
|---|-|--------------|
| 1 | **การควบคุมการเข้าถึงที่เสียหาย** | ผู้ใช้สามารถเข้าถึงทรัพยากรที่พวกเขาไม่ควร |
| 2 | **ความล้มเหลวในการเข้ารหัส** | การเข้ารหัสที่อ่อนแอหรือขาดหายไปสำหรับข้อมูลที่ละเอียดอ่อน |
| 3 | **ฉีด** | SQL, NoSQL, คำสั่ง OS หรือการฉีด LDAP |
| 4 | **การออกแบบที่ไม่ปลอดภัย** | ข้อบกพร่องทางสถาปัตยกรรมที่ไม่สามารถแก้ไขได้ด้วยการใช้งาน |
| 5 | **การกำหนดค่าความปลอดภัยผิดพลาด** | รหัสผ่านเริ่มต้น พอร์ตที่เปิดอยู่ ข้อความแสดงข้อผิดพลาดโดยละเอียด |
| 6 | **ส่วนประกอบที่มีช่องโหว่** | CVE ที่รู้จักในการพึ่งพา |
| 7 | **การตรวจสอบสิทธิ์ล้มเหลว** | รหัสผ่านที่อ่อนแอ การจัดการเซสชั่นผิดพลาด |
| 8 | **ความล้มเหลวด้านความสมบูรณ์** | การโจมตีห่วงโซ่อุปทาน การอัปเดตที่ไม่ได้ลงนาม |
| 9 | **การบันทึก/การตรวจสอบความล้มเหลว** | ไม่พบการละเมิด |
| 10 | **สสส.** | เซิร์ฟเวอร์ถูกหลอกให้ทำการร้องขอไปยังระบบภายใน |

## วิธีปฏิบัติการเข้ารหัสที่ปลอดภัย
### การตรวจสอบอินพุต
| กฎ | ทำไม |
|------|-----|
| **บัญชีขาว > บัญชีดำ** | กำหนดสิ่งที่ได้รับอนุญาต ไม่ใช่สิ่งที่ถูกบล็อก |
| **แบบสอบถามแบบมีพารามิเตอร์** | อย่าเชื่อมอินพุตของผู้ใช้เข้ากับ SQL — ใช้คำสั่งที่เตรียมไว้หรือ ORM |
| **การเข้ารหัส HTML** | เข้ารหัส`<`,`>`,`&`,`"`,`'`เพื่อป้องกัน XSS |
| **เปลือกหอยหนี** | หลีกเลี่ยงการสร้างคำสั่งเชลล์จากอินพุตของผู้ใช้ ใช้`shlex.quote()`|
| **จำกัดความยาว** | บังคับใช้ความยาวสูงสุดเพื่อป้องกันบัฟเฟอร์ล้นและ DoS |
| **ตรวจสอบประเภท** | ตรวจสอบให้แน่ใจว่าจำนวนเต็มเป็นจำนวนเต็ม บูลีนคือบูลีน |
### ช่องโหว่ทั่วไป
| ช่องโหว่ | โจมตี | กลาโหม |
|--------------|--------|---------|
| **การฉีด SQL** | `' OR 1=1 --`ในแบบฟอร์มเข้าสู่ระบบ | แบบสอบถามแบบมีพารามิเตอร์ |
| **XSS** | `<script>alert('hacked')</script>`ในช่องความคิดเห็น | การเข้ารหัสเอาต์พุต นโยบายความปลอดภัยของเนื้อหา |
| **สสส.** | หลอกเบราว์เซอร์ของผู้ใช้ให้ส่งคำขอโดยไม่ได้รับอนุญาต | โทเค็น CSRF, คุกกี้ SameSite |
| **เส้นทางลัดเลาะ** | `../../etc/passwd`ในพารามิเตอร์ไฟล์ | ตรวจสอบและฆ่าเชื้อเส้นทางไฟล์ |
| **ไอดอร์** | เปลี่ยน`/user/123`เป็น`/user/124`เพื่อดูข้อมูลของผู้อื่น | ตรวจสอบการอนุญาตทุกคำขอ |

## ความปลอดภัยเครือข่าย
### ไฟร์วอลล์
| พิมพ์ | คำอธิบาย |
|-|-------------|
| **การกรองแพ็คเก็ต** | กฎตาม IP, พอร์ต, โปรโตคอล |
| **เก็บสถานะ** | ติดตามสถานะการเชื่อมต่อ การกรองที่ชาญฉลาดยิ่งขึ้น |
| **ระดับแอปพลิเคชัน (WAF)** | ตรวจสอบการรับส่งข้อมูล HTTP; บล็อกการฉีด SQL, XSS ฯลฯ |
| **กลุ่มความปลอดภัยบนคลาวด์** | ไฟร์วอลล์เสมือนสำหรับอินสแตนซ์คลาวด์ (AWS SGs, Azure NSGs) |
**หลักทั่วไป**: บล็อกการรับส่งข้อมูลขาเข้าทั้งหมดตามค่าเริ่มต้น เปิดเฉพาะสิ่งที่จำเป็นอย่างชัดเจน (80, 443 สำหรับเว็บ)
### การแบ่งส่วนเครือข่าย
วางฐานข้อมูลและแคชในซับเน็ตส่วนตัวโดยไม่ต้องมีการเข้าถึงอินเทอร์เน็ตโดยตรง ใช้ DMZ สำหรับบริการสาธารณะ (เว็บเซิร์ฟเวอร์ ตัวจัดสรรภาระงาน) ใช้หลักการของสิทธิ์ขั้นต่ำในการเข้าถึงเครือข่าย

## การจัดการความลับ
### กฎทอง
**ห้ามฮาร์ดโค้ดเป็นความลับ** ไม่มีคีย์ API, รหัสผ่าน หรือ URL ฐานข้อมูลในซอร์สโค้ด ไม่มีความลับในตัวแปรสภาพแวดล้อมที่คอมมิตกับ Git ไม่มีความลับในภาพนักเทียบท่า
### เครื่องมือ
| เครื่องมือ | พิมพ์ | ดีที่สุดสำหรับ |
|------|-|---------|
| **ห้องนิรภัย HashiCorp** | ผู้จัดการความลับขององค์กร | ความลับแบบไดนามิก การเข้ารหัสเป็นบริการ |
| **ตัวจัดการความลับ AWS** | คลาวด์เนทิฟ | สภาพแวดล้อม AWS |
| **Azure Key Vault** | คลาวด์เนทิฟ | สภาพแวดล้อม Azure |
| **สปส.** | ไฟล์ที่เข้ารหัส | เข้ารหัสความลับใน Git (ด้วย KMS หรือ GPG) |
| **ความลับนักเทียบท่า** | คอนเทนเนอร์เนทิฟ | Docker Swarm (สำหรับ K8 ให้พิจารณา Secrets Store CSI) |
| **dotenv (.env)** | การพัฒนาท้องถิ่น | การพัฒนาเท่านั้น — ไม่เคยอยู่ในการผลิตหรือมุ่งมั่น |
### การหมุน
หมุนเวียนความลับอย่างสม่ำเสมอและอัตโนมัติ หากความลับรั่วไหล (เช่น มุ่งมั่นที่จะซื้อคืนสาธารณะ) ให้หมุนเวียนข้อมูลนั้นทันที แม้ว่าคุณจะคิดว่าไม่มีใครเห็นก็ตาม

## ความปลอดภัยในการพึ่งพา
แอปพลิเคชันของคุณจะปลอดภัยพอๆ กับการอ้างอิงที่อ่อนแอที่สุดเท่านั้น
### เครื่องมือสแกน
| ภาษา | เครื่องมือ |
|----------|-------|
| **หลาม** | `safety`,`pip-audit`,`bandit`|
| **Node.js** | `npm audit`,`yarn audit`,`snyk`|
| **สนิม** | `cargo audit`|
| **ไป** | `govulncheck`|
| **ทั่วไป** | `Dependabot`(GitHub),`Renovate`,`Trivy`|
### ความซื่อสัตย์ในห่วงโซ่อุปทาน
- ใช้ lockfiles (`package-lock.json`,`Cargo.lock`,`go.sum`) สำหรับการสร้างที่ทำซ้ำได้
- ตรวจสอบการตรวจสอบการพึ่งพาที่ดาวน์โหลด
- ต้องการการลงทะเบียนอย่างเป็นทางการและผู้จัดพิมพ์ที่ได้รับการยืนยัน
- อัปเดตเล็กน้อย/แพตช์อัตโนมัติผ่าน Dependabot หรือ Renovate
---

## วงจรการพัฒนาความปลอดภัย (SDL)
| เฟส | กิจกรรม |
|-------|----------|
| **การฝึกอบรม** | ตรวจสอบให้แน่ใจว่านักพัฒนาเข้าใจช่องโหว่ทั่วไป |

## รายการตรวจสอบฉุกเฉิน
เมื่อคุณสงสัยว่ามีการละเมิด:
1. **อย่าตกใจ** — แต่ดำเนินการอย่างรวดเร็ว
2. **แยก** ระบบที่ได้รับผลกระทบ (ตัดการเชื่อมต่อจากเครือข่ายหากจำเป็น)
3. **เก็บหลักฐาน**: บันทึกการจับภาพ ดัมพ์หน่วยความจำ อิมเมจของดิสก์
4. **ระบุขอบเขต**: ระบบใด ข้อมูลใด
5. **หมุนเวียน** ข้อมูลประจำตัวและความลับที่ถูกบุกรุกทั้งหมด
6. **แก้ไข** ช่องโหว่
7. **แจ้ง** ผู้ใช้ที่ได้รับผลกระทบและหน่วยงานกำกับดูแล หากจำเป็น (ภายในกรอบเวลาทางกฎหมาย)
8. **หลังชันสูตร**: บันทึกสาเหตุที่แท้จริงและรายการดำเนินการภายใน 24–48 ชั่วโมง
