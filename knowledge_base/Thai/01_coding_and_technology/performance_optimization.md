# การเพิ่มประสิทธิภาพประสิทธิภาพ
การเพิ่มประสิทธิภาพการทำงานเป็นแนวทางปฏิบัติในการทำให้ซอฟต์แวร์เร็วขึ้น — ลดเวลาตอบสนอง เพิ่มปริมาณงาน ลดการใช้หน่วยความจำ และขจัดปัญหาคอขวด นี่เป็นหนึ่งในทักษะที่มีผลกระทบมากที่สุดที่นักพัฒนาสามารถทำได้ เนื่องจากซอฟต์แวร์ที่ช้าทำให้สูญเสียผู้ใช้ เปลืองทรัพยากร และทำให้ทุกคนหงุดหงิด แต่มันก็เป็นหนึ่งในสิ่งที่ทำผิดบ่อยที่สุดเช่นกัน โดยนักพัฒนาจะปรับสิ่งที่ผิดให้เหมาะสมโดยยึดตามสัญชาตญาณมากกว่าหลักฐาน
---

## กฎทอง
> **วัดก่อน ปรับให้เหมาะสมเป็นอันดับสอง** อย่าปรับให้เหมาะสมตามสมมติฐาน จัดทำโปรไฟล์โค้ด ค้นหาจุดคอขวดที่เกิดขึ้นจริง และแก้ไขปัญหานั้น
| ต่อต้านรูปแบบ | ทำไมมันแย่ |
|-------------|-------------|
| **การเพิ่มประสิทธิภาพก่อนกำหนด** | ใช้เวลาเร่งโค้ดที่ไม่ช้า |
| **การเพิ่มประสิทธิภาพโดยไม่ต้องวัดผล** | แก้ไขคอขวดที่ไม่ถูกต้อง ไม่มีวิธีตรวจสอบการปรับปรุง |
| **เสียสละความสามารถในการอ่านเพื่อความรวดเร็ว** | รหัสที่อ่านไม่ได้มีค่าใช้จ่ายมากกว่าประสิทธิภาพที่เพิ่มขึ้น |
| **แคชทุกอย่าง** | ข้อมูลเก่า หน่วยความจำขยายตัว ความซับซ้อน |

## การทำโปรไฟล์
ก่อนที่คุณจะทำอะไรบางอย่างได้เร็วขึ้น คุณต้องรู้ว่า *เวลาไหน* ถูกใช้ไปเสียก่อน
| ประเภทเครื่องมือ | มันวัดอะไร | ตัวอย่าง |
|----------|-----------------|----------|
| **ตัวสร้างโปรไฟล์ CPU** | ฟังก์ชั่นใดกินเวลา CPU มากที่สุด | cProfile (Python), perf (Linux), Chrome DevTools (JS) |
| **เครื่องมือสร้างโปรไฟล์หน่วยความจำ** | การจัดสรรหน่วยความจำและการรั่วไหล | Tracemalloc (Python), Valgrind, heaptrack |
| **ตัวสร้างโปรไฟล์ I/O** | ปัญหาคอขวด I/O ของดิสก์และเครือข่าย iotop, strace, Wireshark |
| **APM (การตรวจสอบประสิทธิภาพของแอปพลิเคชัน)** | ระยะเวลาการร้องขอจากต้นทางถึงปลายทาง | ใหม่ของที่ระลึก, ดาต้าด็อก, เยเกอร์ |
| **เครื่องมือพัฒนาเบราว์เซอร์** | การเรนเดอร์ส่วนหน้า, การดำเนินการ JavaScript, เครือข่าย | Chrome DevTools, ตัวสร้างโปรไฟล์ Firefox |
### ขั้นตอนการทำโปรไฟล์
| ขั้นตอน | คำอธิบาย |
|-|-------------|
| 1. ระบุการทำงานที่ช้า | ผู้ใช้รายงานการโหลดหน้าเว็บที่ช้า การตรวจสอบแสดงเวลาแฝงสูง |
| 2. โปรไฟล์เส้นทางแบบเต็ม | ค้นหาองค์ประกอบใดที่ใช้เวลามากที่สุด |
| 3. เจาะลึก | โปรไฟล์ส่วนประกอบเฉพาะนั้นเพื่อค้นหาฟังก์ชันสุดฮอต |
| 4. แก้ไขคอขวด | ใช้การเพิ่มประสิทธิภาพที่เหมาะสม |
| 5. วัดอีกครั้ง | ตรวจสอบการปรับปรุง; ตรวจสอบการถดถอย |

## การเพิ่มประสิทธิภาพอัลกอริทึม
ประสิทธิภาพที่เพิ่มขึ้นสูงสุดมาจากการเลือกอัลกอริธึมที่ดีกว่า ไม่ใช่จากการเพิ่มประสิทธิภาพแบบไมโคร
| เปลี่ยน | การปรับปรุง |
|--------|------------|
| การค้นหาเชิงเส้น O(n) → การค้นหาตารางแฮช O(1) | 100x+ สำหรับชุดข้อมูลขนาดใหญ่ |
| วนซ้ำซ้อน O(n²) → เรียงลำดับ + การค้นหาแบบไบนารี O(n log n) | ลำดับความสำคัญสำหรับขนาดใหญ่ n |
| การคำนวณซ้ำ → การบันทึก / แคช | ขจัดงานที่ซ้ำซ้อน |
| การต่อสตริงในลูป → Builder / join | หลีกเลี่ยงการคัดลอกสตริงกำลังสอง |
| ข้อมูลที่ไม่ได้เรียงลำดับ → จัดเรียงข้อมูลด้วยการค้นหาแบบไบนารี | O(log n) แทนที่จะเป็น O(n) ต่อการค้นหา |

## กลยุทธ์การแคช
การแคชจะเก็บผลลัพธ์ที่คำนวณไว้ ดังนั้นจึงไม่จำเป็นต้องคำนวณใหม่
| ประเภทแคช | ที่ตั้ง | ความเร็ว | ตลอดชีวิต |
|----------|----------|-------|----------|
| **แคชซีพียู** | L1/L2/L3 | ~1ns | อัตโนมัติ |
| **ในความทรงจำ** | แอปพลิเคชัน RAM (dict, HashMap) | ~100ns | จนกว่าจะเคลียร์หรือไล่ออก |
| **กระจายแคช** | Redis, Memcached | ~1 มิลลิวินาที | TTL ที่กำหนดค่าได้ |
| **ซีดีเอ็น** | เซิร์ฟเวอร์ Edge ทั่วโลก | ~10-50 มิลลิวินาที | TTL ที่กำหนดค่าได้ |
| **แคชของเบราว์เซอร์** | เบราว์เซอร์ของผู้ใช้ | ~1 มิลลิวินาที | ส่วนหัวแคช HTTP |
| **แคชแบบสอบถามฐานข้อมูล** | ระดับฐานข้อมูลหรือ ORM | ~1-10 มิลลิวินาที | จนกว่าข้อมูลจะเปลี่ยนแปลง |
### รูปแบบการแคช
| รูปแบบ | คำอธิบาย | เมื่อใดควรใช้ |
|---------|-------------|-------------|
| **ยกเว้นแคช** | แอปพลิเคชันตรวจสอบแคช โหลดจาก DB เมื่อพลาด; เก็บในแคช | พบมากที่สุด; ง่าย |
| **เขียนผ่าน** | เขียนลงแคชและ DB พร้อมกัน | เมื่ออ่าน >> เขียน; ความสม่ำเสมอสำคัญ |
| **เขียนหลัง** | เขียนลงแคช เขียนแบบอะซิงโครนัสไปยัง DB | ปริมาณงานเขียนสูง ความเสี่ยงในการสูญเสียข้อมูลบางส่วน |
| **TTL (ไทม์ทูไลฟ์)** | รายการแคชจะหมดอายุหลังจากเวลาที่กำหนด | เมื่อข้อมูลมีการเปลี่ยนแปลงเป็นระยะ |
| **การใช้ไม่ได้** | ลบรายการแคชเก่าอย่างชัดเจน | เมื่อคุณรู้แน่ชัดเมื่อข้อมูลมีการเปลี่ยนแปลง |
### แคชใช้ไม่ได้
ปัญหาที่ยากที่สุดสองประการในวิทยาการคอมพิวเตอร์: แคชใช้ไม่ได้ การตั้งชื่อสิ่งต่าง ๆ และข้อผิดพลาดแบบทีละรายการ
| กลยุทธ์ | คำอธิบาย |
|----------|-------------|
| **ใช้ TTL** | รายการจะหมดอายุหลังจาก N วินาที เรียบง่าย แต่อาจให้บริการข้อมูลเก่า |
| **ขับเคลื่อนด้วยเหตุการณ์** | ใช้งานไม่ได้เมื่อข้อมูลมีการเปลี่ยนแปลง ซับซ้อนกว่าแต่แม่นยำ |
| **ตามเวอร์ชัน** | รวมหมายเลขเวอร์ชัน เพิ่มขึ้นจากการเปลี่ยนแปลง |
| **ตามแท็ก** | แท็กรายการแคชที่เกี่ยวข้อง ทำให้รายการทั้งหมดไม่ถูกต้องด้วยแท็ก |

## การเพิ่มประสิทธิภาพฐานข้อมูล
ฐานข้อมูลมักเป็นจุดคอขวดที่ใหญ่ที่สุดในเว็บแอปพลิเคชัน
| เทคนิค | คำอธิบาย | ผลกระทบ |
|----------|-------------|--------|
| **การจัดทำดัชนี** | เพิ่มดัชนีในคอลัมน์ที่ใช้ใน WHERE, JOIN, ORDER BY | สืบค้นเร็วขึ้น 10-1,000 เท่า |
| **การเพิ่มประสิทธิภาพแบบสอบถาม** | หลีกเลี่ยง SELECT *; ใช้ EXPLAIN เพื่อวิเคราะห์ข้อความค้นหา | ลด I/O |
| **การรวมการเชื่อมต่อ** | ใช้การเชื่อมต่อฐานข้อมูลซ้ำแทนที่จะสร้างใหม่ | กำจัดค่าใช้จ่ายในการเชื่อมต่อ |
| **อ่านแบบจำลอง** | กำหนดเส้นทางการอ่านแบบสอบถามไปยังฐานข้อมูลจำลอง | กระจายโหลดการอ่าน |
| **การแบ่งพาร์ติชัน** | แบ่งตารางขนาดใหญ่ออกเป็นพาร์ติชั่นขนาดเล็ก | สืบค้นชุดข้อมูลขนาดใหญ่ได้เร็วขึ้น |
| **การทำให้ปกติ** | เพิ่มข้อมูลที่ซ้ำซ้อนเพื่อหลีกเลี่ยงการรวม | อ่านเร็วขึ้น เขียนช้าลง |
| **มุมมองที่เป็นสาระสำคัญ** | ผลลัพธ์การสืบค้นที่คำนวณไว้ล่วงหน้า | แบบสอบถามที่ซับซ้อนทันที |
| **การป้องกัน N+1** | ใช้ JOIN การโหลดอย่างกระตือรือร้น หรือการสืบค้นแบบแบตช์ | กำจัดคำถามนับพัน |

## การเห็นพ้องและความเท่าเทียม
| แนวคิด | คำอธิบาย | เมื่อใดควรใช้ |
|---------|-------------|-------------|
| **การทำเกลียว** | หลายเธรดภายในกระบวนการเดียว | งาน I/O-bound (เครือข่าย, ดิสก์) |
| **การประมวลผลหลายตัว** | หลายกระบวนการ (ข้าม GIL ใน Python) | งานที่เชื่อมโยงกับ CPU |
| **Async/รอ** | มัลติทาสก์ร่วมกัน; เธรดเดียว | I/O พร้อมกันสูง (เว็บเซิร์ฟเวอร์) |
| **การประมวลผล GPU** | แกนขนานหลายพันคอร์ | การดำเนินงานเมทริกซ์ การประมวลผลภาพ มล |
### Async กับเธรด
| ด้าน | Async/รอ | การทำเกลียว |
|--------|------------|-----------|
| **รุ่น** | สหกรณ์ (การควบคุมผลผลิตงาน) | ยึดเอาเสียก่อน (OS สลับเธรด) |
| **ค่าโสหุ้ย** | ต่ำมาก (ไม่มีการสลับบริบท) | สูงกว่า (การสร้างเธรด การสลับบริบท) |
| **ความซับซ้อน** | การใช้เหตุผลที่ง่ายกว่า (เธรดเดียว) | สภาพการแข่งขัน การหยุดชะงัก ล็อค |
| **ดีที่สุดสำหรับ** | การดำเนินการ I/O พร้อมกันจำนวนมาก | การบล็อกการดำเนินการที่ไม่สามารถทำแบบอะซิงโครนัส |
| **ข้อจำกัด** | ไม่สามารถใช้โค้ดที่ผูกกับ CPU โดยไม่บล็อก | GIL ใน Python จำกัดความเท่าเทียมที่แท้จริง |

## ประสิทธิภาพส่วนหน้า
| เทคนิค | คำอธิบาย | ผลกระทบ |
|----------|-------------|--------|
| **การลดขนาด** | ลบช่องว่างและย่อชื่อตัวแปรให้สั้นลง | ไฟล์เล็กลง 20-40% |
| **การรวมกลุ่ม** | รวมหลายไฟล์ให้เป็นคำขอที่น้อยลง | คำขอ HTTP น้อยลง |
| **การแยกโค้ด** | โหลดเฉพาะโค้ดที่จำเป็นสำหรับหน้าปัจจุบัน | โหลดเริ่มแรกเร็วขึ้น |
| **ขี้เกียจโหลด** | โหลดรูปภาพและส่วนประกอบเมื่อจำเป็น | การเรนเดอร์เริ่มต้นที่เร็วขึ้น |
| **ต้นไม้สั่น** | ลบโค้ดที่ไม่ได้ใช้ออกจากบันเดิล | ชุดเล็กกว่า |
| **การเพิ่มประสิทธิภาพรูปภาพ** | ใช้ WebP/AVIF; ภาพที่ตอบสนอง; ขี้เกียจโหลด | ภาพเล็กลง 50-80% |
| **ซีดีเอ็น** | ให้บริการสินทรัพย์คงที่จากเซิร์ฟเวอร์ Edge | เวลาแฝงที่ต่ำกว่าทั่วโลก |
| **HTTP/2 และ HTTP/3** | มัลติเพล็กซ์; การบีบอัดส่วนหัว; 0-RTT | โอเวอร์เฮดโปรโตคอลที่เร็วขึ้น |
| **พนักงานบริการ** | ทรัพย์สินแคชสำหรับการใช้งานออฟไลน์ การแจ้งเตือนแบบพุช | การเข้าชมซ้ำเร็วขึ้น |

## การเพิ่มประสิทธิภาพหน่วยความจำ
| เทคนิค | คำอธิบาย |
|-----------|-------------|
| **การรวมวัตถุ** | นำวัตถุมาใช้ซ้ำแทนที่จะสร้างวัตถุใหม่ |
| **สตรีมมิ่ง** | ประมวลผลข้อมูลเป็นชิ้นๆ แทนที่จะโหลดทุกอย่างลงในหน่วยความจำ |
| **เครื่องกำเนิดไฟฟ้า / ตัววนซ้ำ** | ให้ค่าทีละรายการแทนการสร้างรายการ |
| **ไฟล์แมปหน่วยความจำ** | เข้าถึงไฟล์ขนาดใหญ่โดยไม่ต้องโหลดทั้งหมด |
| **ปรับแต่งการเก็บขยะ** | ปรับพารามิเตอร์ GC สำหรับภาระงานของคุณ |
| **ตัวเลือกโครงสร้างข้อมูล** | ใช้อาร์เรย์แทนรายการที่เชื่อมโยงสำหรับพื้นที่แคช ใช้ชุดสำหรับทดสอบความเป็นสมาชิก |

## การเพิ่มประสิทธิภาพเครือข่าย
| เทคนิค | คำอธิบาย |
|-----------|-------------|
| **การบีบอัด** | gzip, brotli สำหรับการตอบกลับ HTTP |
| **การใช้การเชื่อมต่อซ้ำ** | การเชื่อมต่อแบบ Keep-alive; HTTP/2 มัลติเพล็กซ์ |
| **ขอเป็นชุด** | รวมการเรียก API หลายรายการเป็นหนึ่ง |
| **การแบ่งหน้า** | โหลดข้อมูลในหน้าต่างๆ แทนที่จะโหลดทั้งหมดในคราวเดียว |
| **การบีบอัดขณะพัก** | บีบอัดข้อมูลในฐานข้อมูลและแคช |
| **ตัวเลือกโปรโตคอล** | gRPC (ไบนารี มีประสิทธิภาพ) กับ REST (มนุษย์อ่านได้) |

## การตรวจสอบและการแจ้งเตือน
| เมตริก | สิ่งที่บอกคุณ |
|--------|------------------|
| **เวลาแฝง P50 / P95 / P99** | เวลาตอบสนองที่เปอร์เซ็นไทล์ต่างๆ |
| **ปริมาณงาน** | คำขอต่อวินาที |
| **อัตราข้อผิดพลาด** | เปอร์เซ็นต์ของคำขอที่ล้มเหลว |
| **การใช้งาน CPU** | ใช้ความสามารถในการประมวลผลเท่าใด |
| **การใช้หน่วยความจำ** | ปริมาณการใช้แรม ใกล้ถึงขีดจำกัดแล้วเหรอ? |
| **เวลาสืบค้นฐานข้อมูล** | ข้อความค้นหาที่ช้าซึ่งจำเป็นต้องปรับให้เหมาะสม |

## สรุป
การเพิ่มประสิทธิภาพการทำงานเป็นกระบวนการที่เป็นระบบ: วัด ระบุปัญหาคอขวด แก้ไข และวัดอีกครั้ง ชัยชนะที่ยิ่งใหญ่ที่สุดมาจากการปรับปรุงอัลกอริธึมและกำจัดงานที่ไม่จำเป็น ไม่ใช่จากการเพิ่มประสิทธิภาพในระดับไมโคร การแคช การทำดัชนีฐานข้อมูล และการทำงานพร้อมกันเป็นเครื่องมือที่ทรงพลังที่สุด ประสิทธิภาพส่วนหน้าขึ้นอยู่กับการลดขนาดเพย์โหลดและการไปกลับ และกฎที่สำคัญที่สุดก็เหมือนกันเสมอ: อย่าเดา — โปรไฟล์
