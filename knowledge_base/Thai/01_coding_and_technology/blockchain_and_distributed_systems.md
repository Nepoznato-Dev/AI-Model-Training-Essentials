# Blockchain และระบบกระจาย
บล็อคเชนเป็นระบบกระจายประเภทเฉพาะ — บัญชีแยกประเภทแบบกระจายอำนาจที่ผนวกเฉพาะซึ่งมีการเชื่อมโยงบันทึก (บล็อก) ด้วยแฮชที่เข้ารหัสลับ ระบบแบบกระจายเป็นสาขาที่กว้างกว่าในการทำให้คอมพิวเตอร์หลายเครื่องทำงานร่วมกันเป็นหนึ่งเดียว แนวคิดทั้งสองมีความสำคัญต่อการทำความเข้าใจโครงสร้างพื้นฐานสมัยใหม่ ตั้งแต่สกุลเงินดิจิทัลไปจนถึงฐานข้อมูลแบบกระจายไปจนถึงอัลกอริธึมที่เป็นเอกฉันท์ที่ขับเคลื่อนบริการระดับโลก
---

## พื้นฐานระบบแบบกระจาย
### ทำไมต้องระบบแบบกระจาย?
| แรงจูงใจ | คำอธิบาย |
|-----------|-------------|
| **ความสามารถในการปรับขนาด** | เพิ่มเครื่องจักรเพื่อรองรับโหลดมากขึ้น |
| **ความทนทานต่อข้อผิดพลาด** | ระบบยังคงทำงานต่อไปแม้ว่าบางเครื่องจะล้มเหลว |
| **การกระจายทางภูมิศาสตร์** | ให้บริการผู้ใช้จากศูนย์ข้อมูลใกล้เคียง |
| **ความเชี่ยวชาญ** | เครื่องจักรต่างกันจัดการงานต่างกัน |
### แนวคิดหลัก
| แนวคิด | คำอธิบาย | ท้าทาย |
|---------|-------------|-----------|
| **ฉันทามติ** | การรับโหนดทั้งหมดเห็นด้วยกับค่า | พาร์ติชันเครือข่าย ความผิดพลาดของไบเซนไทน์ |
| **การจำลอง** | การคัดลอกข้อมูลข้ามหลายโหนด | ความสม่ำเสมอเทียบกับความพร้อมใช้งาน |
| **การแบ่งพาร์ติชัน (การแบ่งส่วน)** | การแยกข้อมูลระหว่างโหนด | ฮอตสปอต; ข้อความค้นหาแบบข้ามส่วน |
| **โมเดลความสอดคล้อง** | รับประกันสิ่งที่ผู้อ่านเห็นต่างกัน | ความสม่ำเสมอที่แข็งแกร่งนั้นช้า ความสอดคล้องในที่สุดอาจทำให้ผู้ใช้ประหลาดใจ |
| **ทฤษฎีบทหมวก** | คุณสามารถมีได้เพียง 2 รายการเท่านั้น: ความสม่ำเสมอ ความพร้อมใช้งาน ความทนทานต่อพาร์ติชัน | ในทางปฏิบัติ จำเป็นต้องมีความทนทานต่อพาร์ติชัน เลือก C หรือ A |
### ทฤษฎีบท CAP
| ทางเลือก | สิ่งที่คุณได้รับ | สิ่งที่คุณยอมแพ้ | ตัวอย่าง |
|----------------------|-------------|-----------------|---------|
| **ซีพี** | สอดคล้อง + ทนต่อพาร์ติชัน | บางโหนดอาจไม่พร้อมใช้งานระหว่างพาร์ติชัน | HBase, MongoDB, Redis |
| **เอพี** | พร้อมใช้งาน + ทนต่อพาร์ติชัน | การอ่านอาจส่งคืนข้อมูลเก่า | คาสซานดรา, DynamoDB, CouchDB |
| **แคลิฟอร์เนีย** | สม่ำเสมอ + ใช้ได้ | ไม่สามารถทนต่อพาร์ติชันเครือข่าย | ฐานข้อมูลโหนดเดียว (ไม่กระจายอย่างแท้จริง) |

## อัลกอริธึมฉันทามติ
โหนดแบบกระจายเห็นด้วยกับสถานะของระบบอย่างไร
| อัลกอริทึม | พิมพ์ | ความทนทานต่อข้อผิดพลาด | ใช้ใน |
|----------|-|----------------|---------|
| **ปาซอส** | ทนต่อความผิดพลาดจากการชน | ความล้มเหลวสูงสุดถึง f ด้วย 2f+1 โหนด | Google อ้วน; ทฤษฎีพื้นฐาน |
| **แพ** | ทนต่อความผิดพลาดจากการชน | ความล้มเหลวสูงสุดถึง f ด้วย 2f+1 โหนด | ฯลฯ กงสุล TiKV |
| **PBFT** | ทนต่อข้อผิดพลาดของไบเซนไทน์ ความล้มเหลวสูงสุดถึง f ด้วยโหนด 3f+1 | ผ้าไฮเปอร์เลดเจอร์ |
| **หลักฐานการทำงาน** | ทนต่อข้อผิดพลาดของไบเซนไทน์ ขึ้นอยู่กับพลังแฮช | บิทคอยน์ |
| **หลักฐานการเดิมพัน** | ทนต่อข้อผิดพลาดของไบเซนไทน์ ขึ้นอยู่กับสัดส่วนการถือหุ้น | Ethereum 2.0, คาร์ดาโน |
### แพ (แบบง่าย)
| บทบาท | ความรับผิดชอบ |
|------|---------------|
| **ผู้นำ** | จัดการคำขอของลูกค้าทั้งหมด ส่งข้อมูลบันทึกไปยังผู้ติดตาม |
| **ผู้ติดตาม** | ตอบสนองต่อคำขอของผู้นำ ลงคะแนนเสียงในการเลือกตั้ง |
| **ผู้สมัคร** | ขอคะแนนโหวตเป็นผู้นำ |
1. โหนดทั้งหมดเริ่มต้นจากการเป็นผู้ติดตาม
2. หากผู้ติดตามไม่ได้รับการติดต่อจากผู้นำเกี่ยวกับการหมดเวลาการเลือกตั้ง ผู้ติดตามคนนั้นจะกลายเป็นผู้สมัคร
3. ผู้สมัครขอคะแนนเสียง; ผู้ที่มีคะแนนโหวตมากที่สุดจะกลายเป็นผู้นำ
4. ผู้นำจำลองรายการบันทึกให้กับผู้ติดตาม
5. เมื่อเสียงข้างมากยืนยัน รายการจะถูกกระทำ

## บล็อคเชน
### Blockchain ทำงานอย่างไร
| ส่วนประกอบ | คำอธิบาย |
|-----------|-------------|
| **บล็อก** | ชุดธุรกรรม + ข้อมูลเมตา + แฮชของบล็อกก่อนหน้า |
| **แฮช** | ลายนิ้วมือเข้ารหัสของเนื้อหาของบล็อก |
| **เชน** | แต่ละบล็อกอ้างอิงถึงแฮชของบล็อกก่อนหน้า สร้าง chain ที่ไม่เปลี่ยนรูป |
| **ฉันทามติ** | ผู้เข้าร่วมเครือข่ายตกลงว่าจะเพิ่มบล็อกใด |
| **ต้นเมิร์เคิล** | แผนผังแฮชสรุปธุรกรรมทั้งหมดในบล็อก |
### เหตุใด Blockchain จึงยากที่จะแก้ไข
1. แต่ละบล็อกจะมีแฮชของบล็อกก่อนหน้า
2. การเปลี่ยนแปลงธุรกรรมใดๆ จะเปลี่ยนแฮชของบล็อก
3. แฮชที่เปลี่ยนแปลงจะทำให้เชนแตก — บล็อกที่ตามมาทั้งหมดจะไม่ถูกต้อง
4. ผู้โจมตีจะต้องขุดบล็อกที่ตามมาทั้งหมดอีกครั้ง และควบคุม >50% ของเครือข่าย
### ประเภทของบล็อคเชน
| พิมพ์ | เข้าถึง | เครื่องมือตรวจสอบ | ตัวอย่าง |
|------|--------|-----------|---------|
| **สาธารณะ (ไม่ได้รับอนุญาต)** | ใครๆ ก็สามารถอ่านและเขียนได้ | ฉันทามติแบบเปิด (PoW, PoS) | Bitcoin, อีเธอเรียม |
| **ส่วนตัว (ได้รับอนุญาต)** | การเข้าถึงแบบจำกัด | เครื่องมือตรวจสอบที่รู้จัก | ไฮเปอร์เลดเจอร์, คอร์ดา |
| **สมาคม** | ปกครองโดยกลุ่มองค์กร | เครื่องมือตรวจสอบความถูกต้องที่เลือก | R3 Corda สำหรับการธนาคาร |
### สัญญาอัจฉริยะ
รหัสที่ดำเนินการด้วยตนเองที่จัดเก็บไว้ในบล็อกเชนที่ทำงานเมื่อตรงตามเงื่อนไขที่กำหนดไว้ล่วงหน้า
| แพลตฟอร์ม | ภาษา | คุณสมบัติเด่น |
|----------|----------|-----------------|
| **อีเธอเรียม** | ความแข็งแกร่ง, Vyper | ระบบนิเวศสัญญาอัจฉริยะที่ใหญ่ที่สุด |
| **โซลานา** | สนิม, ซี | ปริมาณงานสูง ค่าธรรมเนียมต่ำ |
| **คาร์ดาโน** | Haskell (พลูตัส) | ตรวจสอบโดยผู้ทรงคุณวุฒิ; การตรวจสอบอย่างเป็นทางการ |
| **ไฮเปอร์เลดเจอร์** | ไป, Java, JavaScript | องค์กร; ได้รับอนุญาต |

## สกุลเงินดิจิทัล
| สกุลเงิน | ฉันทามติ | อุปทาน | การใช้งานหลัก |
|----------|-----------|--------|-------------|
| **บิทคอยน์** | หลักฐานการทำงาน | 21 ล้าน (ต่อยอด) | การจัดเก็บมูลค่า ทองดิจิทัล |
| **อีเธอเรียม** | หลักฐานการเดิมพัน | ไม่มีฝาปิดแข็ง | สัญญาอัจฉริยะ เดไฟ; NFT |
| **โซลานา** | หลักฐานการเดิมพัน + หลักฐานประวัติศาสตร์ | ไม่มีฝาปิดแข็ง | ธุรกรรมความเร็วสูง |
| **คาร์ดาโน** | Proof of Stake (อูโรโบรอส) | 45 พันล้าน (ต่อยอด) | แนวทางวิชาการ ความยั่งยืน |

## ฐานข้อมูลแบบกระจาย
| ฐานข้อมูล | สถาปัตยกรรม | ความสม่ำเสมอ | ดีที่สุดสำหรับ |
|----------|-------------|-------------|----------|
| **แคสแซนดรา** | คอลัมน์กว้าง; เพียร์ทูเพียร์ | ปรับได้ (ในที่สุดก็ถึงองค์ประชุม) | ปริมาณงานเขียนสูง อนุกรมเวลา |
| **MongoDB** | เอกสาร; ชุดจำลอง | ในที่สุด (พร้อมตัวเลือกความสอดคล้องเชิงสาเหตุ) | สคีมาแบบยืดหยุ่น การพัฒนาอย่างรวดเร็ว |
| **แมลงสาบDB** | SQL แบบกระจาย; ฉันทามติแพ | แข็งแกร่ง | SQL แบบกระจาย; การปรับใช้ทั่วโลก |
| **TIDB** | SQL แบบกระจาย; แพ (ผ่าน TiKV) | แข็งแกร่ง | รองรับ MySQL; มาตราส่วนแนวนอน |
| **DynamoDB** | คีย์-ค่า; จัดการ | ในที่สุด (หรือรุนแรงโดยอ่านสม่ำเสมอ) | ไร้เซิร์ฟเวอร์; | . รวม AWS
| **ประแจ** | SQL แบบกระจาย; ปาซอส | แข็งแกร่ง | กูเกิลคลาวด์; ความสอดคล้องระดับโลก |

## รูปแบบระบบแบบกระจาย
| รูปแบบ | คำอธิบาย | ใช้กรณี |
|---------|-------------|----------|
| **การเลือกตั้งผู้นำ** | เลือกหนึ่งโหนดเพื่อประสานงาน | หัวหน้าแพ; ZooKeeper |
| **การจำลอง** | คัดลอกข้อมูลเพื่อความซ้ำซ้อนและมาตราส่วนการอ่าน | แบบจำลองฐานข้อมูล ซีดีเอ็น |
| **การแบ่งส่วน** | ข้อมูลพาร์ติชันตามช่วงคีย์หรือแฮช | ฐานข้อมูลขนาดใหญ่ |
| **ลดแผนที่** | แยกการคำนวณข้ามโหนด ผลลัพธ์รวม | การประมวลผลข้อมูลขนาดใหญ่ |
| **ระเบียบการนินทา** | โหนดจะแบ่งปันสถานะกับเพื่อนแบบสุ่มเป็นระยะๆ สมาชิกคลัสเตอร์; การตรวจจับความล้มเหลว |
| **การคอมมิตแบบสองเฟส** | ประสานงานการทำธุรกรรมข้ามหลายโหนด | ฐานข้อมูลแบบกระจาย |
| **ลายซากะ** | ชุดของธุรกรรมท้องถิ่นพร้อมการดำเนินการชดเชย | ธุรกรรมไมโครเซอร์วิส |
| **เซอร์กิตเบรกเกอร์** | หยุดการเรียกใช้บริการที่ล้มเหลว ล้มเหลวอย่างรวดเร็ว | ความยืดหยุ่น; ป้องกันความล้มเหลวแบบเรียงซ้อน |

## ความท้าทายในระบบแบบกระจาย
| ท้าทาย | คำอธิบาย | การบรรเทาผลกระทบ |
|----------|-------------|------------|
| **พาร์ติชันเครือข่าย** | โหนดไม่สามารถสื่อสาร | การแลกเปลี่ยน CAP; ลองอีกครั้งโดย backoff |
| **นาฬิกาเอียง** | โหนดที่ต่างกันมีนาฬิกาที่แตกต่างกัน | ใช้นาฬิกาแบบลอจิคัล เอ็นทีพี; หลีกเลี่ยงการพึ่งเวลานาฬิกาแขวน |
| **ความผิดพลาดของไบแซนไทน์** | โหนดที่อยู่หรือทำงานโดยพลการ | ฉันทามติ BFT; บล็อกเชน |
| **แยกสมอง** | สองโหนดต่างคิดว่าพวกเขาเป็นผู้นำ | ฟันดาบ; การตัดสินใจตามองค์ประชุม |
| **ความล้มเหลวแบบเรียงซ้อน** | ความล้มเหลวอย่างหนึ่งทำให้เกิดความล้มเหลว | เบรกเกอร์วงจร; กั้น; การย่อยสลายอย่างสง่างาม |
| **ความสอดคล้องของข้อมูล** | การรักษาแบบจำลองในการซิงค์ | แบบจำลองความสม่ำเสมอ การแก้ไขข้อขัดแย้ง |

## สรุป
ระบบแบบกระจายคือวิธีที่ซอฟต์แวร์สมัยใหม่สามารถปรับขนาด รอดพ้นจากความล้มเหลว และให้บริการผู้ใช้ทั่วโลก อัลกอริธึมฉันทามติ (Raft, Paxos) ช่วยให้มั่นใจว่าโหนดเห็นด้วย Blockchains เพิ่มการตรวจสอบการเข้ารหัสและการกระจายอำนาจเพื่อสร้างบัญชีแยกประเภทที่น่าเชื่อถือ ฐานข้อมูลแบบกระจาย (Cassandra, CockroachDB, DynamoDB) จัดการข้อมูลในวงกว้าง ข้อเสียเปรียบพื้นฐาน - ยึดถือโดยทฤษฎีบท CAP - อยู่ระหว่างความสอดคล้องและความพร้อมใช้งานเมื่อเครือข่ายไม่น่าเชื่อถือ การทำความเข้าใจแนวคิดเหล่านี้ถือเป็นสิ่งสำคัญสำหรับการสร้างระบบที่ทำงานในระดับอินเทอร์เน็ต
