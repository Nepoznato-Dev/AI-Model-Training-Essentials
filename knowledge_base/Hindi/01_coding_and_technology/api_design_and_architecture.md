# एपीआई डिजाइन और वास्तुकला
एक एपीआई (एप्लिकेशन प्रोग्रामिंग इंटरफ़ेस) वह तरीका है जिससे सॉफ्टवेयर घटक एक दूसरे से बात करते हैं। एक अच्छी तरह से डिज़ाइन की गई एपीआई सहज, सुसंगत है और इसके साथ काम करना आनंददायक है। खराब तरीके से डिज़ाइन किया गया भ्रम, बग और निराशा का कारण बनता है। यह फ़ाइल एपीआई बनाने के सिद्धांतों, पैटर्न और प्रथाओं को शामिल करती है जिन्हें डेवलपर्स वास्तव में उपयोग करना चाहते हैं।
---

## रेस्ट एपीआई सिद्धांत
REST (प्रतिनिधि राज्य स्थानांतरण) वेब एपीआई के लिए प्रमुख वास्तुशिल्प शैली है। यह डेटा को यूआरएल द्वारा पहचाने गए **संसाधनों** के रूप में मानता है, और उन पर काम करने के लिए HTTP तरीकों का उपयोग करता है।
### मूल सिद्धांत
| सिद्धांत | विवरण |
|----|----|
| **संसाधन** | हर चीज़ एक यूआरआई (`/users/123`, `/orders/456`) के साथ एक संसाधन है |
| **HTTP तरीके** | प्राप्त करें (पढ़ें), पोस्ट करें (बनाएं), डालें (बदलें), पैच करें (आंशिक अद्यतन करें), हटाएं (हटाएं) |
| **राज्यविहीनता** | प्रत्येक अनुरोध में सभी आवश्यक जानकारी शामिल होती है; कोई सर्वर-साइड सत्र स्थिति नहीं |
| **यूनिफ़ॉर्म इंटरफ़ेस** | सुसंगत संसाधन नामकरण, मानक विधियाँ, मानक स्थिति कोड |
| **प्रतिनिधित्व** | संसाधनों को कई प्रारूपों (JSON, XML) में प्रस्तुत किया जा सकता है |
### संसाधन नामकरण परंपराएँ
| करो | मत करो |
|----|-------|
|  __संरक्षित_0__ (बहुवचन संज्ञा) |  __संरक्षित_1__ (एकवचन) |
|  __संरक्षित_2__ (नेस्टेड) ​​|  __संरक्षित_3__ |
| `/products?category=electronics`(फ़िल्टरिंग के लिए क्वेरी पैरामीटर) |  __संरक्षित_5__ |
| हाइफ़न का उपयोग करें:`/user-profiles`| अंडरस्कोर का प्रयोग करें:`/user_profiles`|
### HTTP तरीके और निष्क्रियता
| विधि | उद्देश्य | नपुंसक? | सुरक्षित? |
|--------|---|---|-------|
| **प्राप्त करें** | एक संसाधन पढ़ें | ✅ हाँ | ✅ हाँ |
| **पोस्ट** | एक संसाधन बनाएं | ❌ नहीं | ❌ नहीं |
| **पुट** | किसी संसाधन को पूरी तरह से बदलें | ✅ हाँ | ❌ नहीं |
| **पैच** | किसी संसाधन को आंशिक रूप से अद्यतन करें | ❌ नहीं* | ❌ नहीं |
| **हटाएं** | एक संसाधन निकालें | ✅ हाँ | ❌ नहीं |
*पैच को सावधानीपूर्वक डिजाइन के साथ निष्क्रिय बनाया जा सकता है।
### HTTP स्थिति कोड
| कोड | मतलब | कब उपयोग करें |
|------|---------|----------------|
| **200** | ठीक है | सफल प्राप्त करें, लगाएं, पैच करें, हटाएं |
| **201** | बनाया गया | सफल पोस्ट (संसाधन निर्मित) |
| **204** | कोई सामग्री नहीं | सफल डिलीट (वापस करने के लिए कुछ नहीं) |
| **400** | ख़राब अनुरोध | अमान्य इनपुट या विकृत अनुरोध |
| **401** | अनाधिकृत | गुम या अमान्य प्रमाणीकरण |
| **403** | निषिद्ध | प्रमाणित लेकिन अधिकृत नहीं |
| **404** | नहीं मिला | संसाधन मौजूद नहीं है |
| **409** | संघर्ष | डुप्लिकेट संसाधन या राज्य संघर्ष |
| **422** | असंसाधित इकाई | वैध JSON लेकिन अर्थ संबंधी त्रुटियाँ |
| **429** | बहुत सारे अनुरोध | दर सीमा पार हो गई |
| **500** | आंतरिक सर्वर त्रुटि | अनपेक्षित सर्वर त्रुटि |
| **502** | ख़राब गेटवे | अपस्ट्रीम सेवा विफलता |
| **503** | सेवा अनुपलब्ध | अस्थायी अधिभार या रखरखाव |

## एपीआई संस्करण
एपीआई विकसित होते हैं। जब आपको महत्वपूर्ण परिवर्तन करने की आवश्यकता होती है, तो संस्करण मौजूदा ग्राहकों को काम करते रहने देता है।
| रणनीति | उदाहरण | पेशेवरों | विपक्ष |
|-------|------|------|------|
| **यूआरएल पथ** |  __संरक्षित_0__ , __संरक्षित_1__ | सरल, स्पष्ट | प्रति संस्करण URL बदलता है |
| **क्वेरी पैरामीटर** |  __संरक्षित_2__ | लचीला | भूलना आसान है |
| **हेडर** |  __संरक्षित_3__ | साफ़ यूआरएल | कम खोजने योग्य |
| **कोई संस्करण नहीं** | केवल स्कीमा विकास | सरलतम | ब्रेकिंग परिवर्तन हर किसी को प्रभावित करते हैं |
**सर्वोत्तम अभ्यास**: स्पष्टता के लिए यूआरएल पथ संस्करण (`/v1/`) का उपयोग करें। कम से कम एक पिछले संस्करण का समर्थन करें. स्पष्ट समयसीमा के साथ पुराने संस्करणों का बहिष्कार करें।

## प्रमाणीकरण विधियाँ
| विधि | यह कैसे काम करता है | के लिए सर्वश्रेष्ठ |
|-------|---|---|---|
| **एपीआई कुंजी** | हेडर में गुप्त कुंजी (`X-API-Key: abc123`) | सर्वर-टू-सर्वर, सरल एकीकरण |
| **OAuth2** | कार्यक्षेत्रों के साथ टोकन-आधारित प्रतिनिधिमंडल | तृतीय-पक्ष पहुंच, उपयोगकर्ता-अधिकृत ऐप्स |
| **जेडब्ल्यूटी** | दावों के साथ स्व-निहित टोकन | सभी सेवाओं में स्टेटलेस प्रमाणीकरण |
| **मूल प्रामाणिक** | बेस64-एन्कोडेड उपयोगकर्ता नाम: पासवर्ड | केवल विकास - टीएलएस के बिना कभी उत्पादन नहीं |
| **सत्र कुकीज़** | HTTP-केवल कुकी में सर्वर-साइड सत्र आईडी | पारंपरिक वेब अनुप्रयोग |
### OAuth2 प्रवाह (सरलीकृत)
1. क्लाइंट उपयोगकर्ता को प्राधिकरण सर्वर पर पुनर्निर्देशित करता है।
2. उपयोगकर्ता लॉग इन करता है और अनुमति देता है।
3. प्राधिकरण सर्वर एक प्राधिकरण कोड लौटाता है।
4. क्लाइंट एक्सेस टोकन के लिए कोड का आदान-प्रदान करता है (और वैकल्पिक रूप से टोकन रीफ्रेश करता है)।
5. क्लाइंट एपीआई को कॉल करने के लिए एक्सेस टोकन का उपयोग करता है।
6. जब एक्सेस टोकन समाप्त हो जाए, तो नया प्राप्त करने के लिए रीफ्रेश टोकन का उपयोग करें।

## एपीआई शैलियाँ: REST बनाम GraphQL बनाम gRPC
| फ़ीचर | विश्राम | ग्राफक्यूएल | जीआरपीसी |
|------|------|------|------|
| **डेटा प्रारूप** | JSON (आम तौर पर) | जेएसओएन | प्रोटोबफ (बाइनरी) |
| **अंतबिंदु** | एकाधिक (प्रति संसाधन एक) | एकल समापन बिंदु | .proto फ़ाइल द्वारा परिभाषित |
| **अति-लाभ** | सामान्य (आवश्यकता से अधिक मिलना) | कोई नहीं (क्लाइंट फ़ील्ड निर्दिष्ट करता है) | कोई नहीं (स्कीमा-परिभाषित) |
| **अंडर-फ़ेचिंग** | एकाधिक कॉल की आवश्यकता है | कोई नहीं (बिल्कुल वही प्राप्त करें जिसकी आवश्यकता है) | कोई नहीं |
| **वास्तविक समय** | वेबसॉकेट की आवश्यकता | सदस्यताएँ अंतर्निहित | स्ट्रीमिंग अंतर्निर्मित |
| **कैशिंग** | HTTP कैशिंग स्वाभाविक रूप से काम करती है | कैश करना कठिन | सीमित |
| **सीखने की अवस्था** | निम्न | मध्यम | मध्यम-उच्च |
| **के लिए सर्वश्रेष्ठ** | सार्वजनिक एपीआई, सीआरयूडी ऐप्स | जटिल यूआई, मोबाइल ऐप्स | आंतरिक माइक्रोसर्विसेज, उच्च प्रदर्शन |

  }

## दर सीमित करना
अपने एपीआई को दुरुपयोग से बचाएं और उचित उपयोग सुनिश्चित करें।
| रणनीति | यह कैसे काम करता है |
|---|----|
| **फिक्स्ड विंडो** | एन अनुरोध प्रति समय विंडो (उदाहरण के लिए, 100/घंटा) |
| **स्लाइडिंग विंडो** | अधिक दानेदार; रोलिंग विंडो में अनुरोधों की गणना करता है |
| **टोकन बाल्टी** | निश्चित दर पर टोकन जोड़े गए; प्रत्येक अनुरोध एक टोकन का उपभोग करता है |
हेडर के साथ`429 Too Many Requests`लौटें:```
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1625097600
Retry-After: 60
```

## त्रुटि प्रबंधन
लगातार त्रुटि प्रतिक्रियाएँ एपीआई के साथ काम करना बहुत आसान बनाती हैं:
```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Invalid input data",
    "details": [
      {
        "field": "email",
        "issue": "Invalid email format"
      }
    ]
  }
}
```

**सिद्धांत**: सुसंगत त्रुटि संरचना का उपयोग करें, कार्रवाई योग्य संदेश शामिल करें, मानक HTTP स्थिति कोड का उपयोग करें, सहसंबंध आईडी के साथ सर्वर-साइड त्रुटियों को लॉग करें, और कभी भी स्टैक ट्रेस या आंतरिक विवरण को उजागर न करें।

## एपीआई दस्तावेज़ीकरण
| उपकरण | विवरण |
|------|----||
| **ओपनएपीआई (स्वैगर)** | REST API दस्तावेज़ीकरण के लिए उद्योग मानक |
| **स्वैगर यूआई** | ओपनएपीआई स्पेक से इंटरैक्टिव एपीआई दस्तावेज़ीकरण |
| **डाकिया** | एपीआई परीक्षण, दस्तावेज़ीकरण, और संग्रह साझाकरण |
| **रीडॉक** | OpenAPI विनिर्देश से सुंदर API संदर्भ दस्तावेज़ |
| **ग्राफक्यूएल खेल का मैदान / ग्राफीक्यूएल** | इंटरैक्टिव ग्राफक्यूएल अन्वेषण |
**सर्वोत्तम अभ्यास**: पहले ओपनएपीआई स्पेक (स्पेक-संचालित विकास) लिखें, फिर उससे दस्तावेज़ीकरण और क्लाइंट एसडीके तैयार करें।

## एपीआई गेटवे पैटर्न
एक एपीआई गेटवे क्लाइंट और बैकएंड सेवाओं के बीच बैठता है, जो एकल प्रवेश बिंदु प्रदान करता है।
| जिम्मेदारी | विवरण |
|----------------------|-----------------|
| **रूटिंग** | उपयुक्त बैकएंड सेवाओं के लिए सीधे अनुरोध |
| **प्रमाणीकरण** | गेटवे स्तर पर टोकन मान्य करें |
| **दर सीमित** | वैश्विक या प्रति-ग्राहक सीमाएँ लागू करें |
| **परिवर्तन** | प्रोटोकॉल के बीच कनवर्ट करें (REST ↔ gRPC) |
| **कैशिंग** | सामान्य प्रतिक्रियाएँ कैश करें |
| **निगरानी** | केंद्रीकृत लॉगिंग और मेट्रिक्स |
| **लोड संतुलन** | सेवा उदाहरणों में ट्रैफ़िक वितरित करें |
| उपकरण | प्रकार |
|------|------|
| **कोंग** | ओपन-सोर्स एपीआई गेटवे (Nginx-आधारित) |
| **एडब्ल्यूएस एपीआई गेटवे** | पूरी तरह से प्रबंधित, AWS के साथ एकीकृत |
| **एज़्योर एपीआई प्रबंधन** | डेवलपर पोर्टल के साथ प्रबंधित गेटवे |
| **दूत/इस्तियो** | एपीआई गेटवे क्षमताओं के साथ सेवा जाल |
| **ट्रैफ़िक** | स्वतः-खोज, आइए एकीकरण को एन्क्रिप्ट करें |

## वेबहुक
वेबहुक आपके एपीआई को ग्राहकों से बदलावों के लिए मतदान कराने के बजाय वास्तविक समय में इवेंट को ग्राहकों तक पहुंचाने देता है।
| पहलू | सर्वोत्तम अभ्यास |
|-------|----||
| **डिलीवरी** | ग्राहक के यूआरएल पर JSON पेलोड के साथ पोस्ट अनुरोध |
| **सुरक्षा** | एचएमएसी के साथ पेलोड पर हस्ताक्षर करें; ग्राहक हस्ताक्षर सत्यापित करता है |
| **विश्वसनीयता** | घातीय बैकऑफ़ के साथ विफल डिलीवरी का पुनः प्रयास करें |
| **नपुंसकता** | अद्वितीय ईवेंट आईडी शामिल करें; क्लाइंट डुप्लिकेट को संभालता है |
| **संस्करण** | वेबहुक पेलोड में एपीआई संस्करण शामिल करें |
---

## डिज़ाइन चेकलिस्ट
- [ ] संसाधन बहुवचन संज्ञा हैं (`/users`, नहीं`/getUser`)
- [ ] HTTP विधियों का सही ढंग से उपयोग किया गया (पढ़ने के लिए प्राप्त करें, बनाने के लिए पोस्ट करें, आदि)
- [ ] लगातार त्रुटि प्रतिक्रिया प्रारूप
- [ ] सभी सूची समापन बिंदुओं के लिए पृष्ठांकन
- [ ] स्पष्ट हेडर के साथ दर सीमित करना
- [ ] एपीआई संस्करण रणनीति परिभाषित
- [ ] प्रमाणीकरण और प्राधिकरण यथास्थान
- [ ] सभी समापन बिंदुओं पर इनपुट सत्यापन
- [ ] ओपनएपीआई/स्वैगर दस्तावेज़ बनाए रखा गया
- [ ] सीओआरएस सही ढंग से कॉन्फ़िगर किया गया है
- [ ] उत्पादन में HTTPS लागू किया गया
- [ ] जहां आवश्यक हो, POST संचालन के लिए इडेम्पोटेंसी कुंजियाँ
