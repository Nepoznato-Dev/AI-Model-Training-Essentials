# सीआई/सीडी पाइपलाइन कॉन्फ़िगरेशन
सतत एकीकरण (सीआई) और सतत परिनियोजन (सीडी) पाइपलाइन सॉफ्टवेयर के निर्माण, परीक्षण और तैनाती की प्रक्रिया को स्वचालित करते हैं। यह संदर्भ सबसे लोकप्रिय CI/CD प्लेटफ़ॉर्म के लिए कॉन्फ़िगरेशन पैटर्न को कवर करता है: GitHub Actions, GitLab CI, और सामान्य पाइपलाइन डिज़ाइन सिद्धांत।
---

## गिटहब क्रियाएँ
### वर्कफ़्लो संरचना
```yaml
name: CI Pipeline
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Set up language
        uses: actions/setup-python@v5
        with:
          python-version: '3.12'
      - name: Install dependencies
        run: pip install -r requirements.txt
      - name: Run tests
        run: pytest
      - name: Build
        run: python setup.py build
```

### सामान्य ट्रिगर
| ट्रिगर | विवरण |
|---------|-----------------|
| `on: push`| हर धक्के पर |
| `on: pull_request`| पीआर पर खोलें, अद्यतन करें, फिर से खोलें |
| `on: schedule`| क्रॉन-आधारित शेड्यूल |
| `on: workflow_dispatch`| मैनुअल ट्रिगर |
| `on: release`| रिलीज निर्माण पर |
| `on: workflow_call`| किसी अन्य वर्कफ़्लो द्वारा कॉल किया गया (पुन: प्रयोज्य) |
### प्रमुख विशेषताऐं
| फ़ीचर | विवरण |
|---------|-----------------|
| **मैट्रिक्स रणनीति** | विभिन्न कॉन्फ़िगरेशन के साथ एक ही कार्य चलाएँ |
| **रहस्य** | एन्क्रिप्टेड पर्यावरण चर (`${{ secrets.MY_SECRET }}`) |
| **वातावरण** | सुरक्षा नियमों के साथ तैनाती लक्ष्य |
| **कैशिंग** | रनों के बीच कैश निर्भरता |
| **कलाकृतियाँ** | नौकरियों से फ़ाइलें अपलोड करें (परीक्षण रिपोर्ट, बिल्ड) |
| **पुन: प्रयोज्य वर्कफ़्लोज़** | रिपॉजिटरी में वर्कफ़्लो तर्क साझा करें |
| **समग्र क्रियाएं** | अनेक चरणों को एक क्रिया में संयोजित करें |
### मैट्रिक्स रणनीति
```yaml
jobs:
  test:
    strategy:
      matrix:
        python-version: ['3.10', '3.11', '3.12']
        os: [ubuntu-latest, macos-latest]
    runs-on: ${{ matrix.os }}
    steps:
      - uses: actions/setup-python@v5
        with:
          python-version: ${{ matrix.python-version }}
```

## गिटलैब सीआई
### पाइपलाइन संरचना
```yaml
stages:
  - build
  - test
  - deploy

build:
  stage: build
  script:
    - docker build -t myapp:$CI_COMMIT_SHA .
    - docker push myapp:$CI_COMMIT_SHA

test:
  stage: test
  script:
    - docker run myapp:$CI_COMMIT_SHA pytest

deploy:
  stage: deploy
  script:
    - deploy.sh $CI_COMMIT_SHA
  only:
    - main
  when: manual
```

### प्रमुख कीवर्ड
| कीवर्ड | विवरण |
|---------|-----------------|
| `stages`| पाइपलाइन चरणों और उनके क्रम को परिभाषित करें |
| `stage`| किसी चरण को कोई कार्य सौंपें |
| `script`| निष्पादित करने के आदेश |
| `before_script`| कमांड मुख्य स्क्रिप्ट से पहले चलते हैं |
| `after_script`| कमांड मुख्य स्क्रिप्ट के बाद चलते हैं (विफलता पर भी) |
| `only / except`| नियंत्रित करें कि नौकरियाँ कब चलती हैं (शाखाएँ, टैग) |
| `rules`| केवल/छोड़कर | का अधिक लचीला संस्करण
| `variables`| सीआई/सीडी चर को परिभाषित करें |
| `cache`| पाइपलाइन रन के बीच कैश फ़ाइलें |
| `artifacts`| नौकरियों के बीच पास करने के लिए फ़ाइलें |
| `environment`| परिनियोजन वातावरण |
| `when`| कार्य निष्पादन को नियंत्रित करें (on_success, on_failure, मैन्युअल, हमेशा) |
| `needs`| कार्य निर्भरताएँ निर्दिष्ट करें (डीएजी मोड) |
| `extends`| किसी अन्य कार्य से कॉन्फ़िगरेशन इनहेरिट करें |
| `include`| बाहरी YAML फ़ाइलें आयात करें |
### पूर्वनिर्धारित चर
| परिवर्तनीय | विवरण |
|---|----|
| `$CI_COMMIT_SHA`| वर्तमान प्रतिबद्ध हैश |
| `$CI_COMMIT_REF_NAME`| शाखा या टैग का नाम |
| `$CI_PIPELINE_ID`| पाइपलाइन आईडी |
| `$CI_JOB_ID`| जॉब आईडी |
| `$CI_PROJECT_DIR`| परियोजना का पूरा पथ |
| `$CI_REGISTRY`| कंटेनर रजिस्ट्री यूआरएल |
| `$CI_DEFAULT_BRANCH`| डिफ़ॉल्ट शाखा का नाम |

## पाइपलाइन डिज़ाइन पैटर्न
### सामान्य पैटर्न
| पैटर्न | विवरण |
|---------|-----------------|
| **एक बार निर्माण करें, अनेकों को तैनात करें** | एक बार कलाकृतियों का निर्माण करें; प्रत्येक वातावरण में समान आर्टिफैक्ट तैनात करें |
| **गेट जांच** | उत्पादन परिनियोजन से पहले मैन्युअल अनुमोदन |
| **विशेष झंडे** | उत्पादन में तैनात करें लेकिन फ़ीचर फ़्लैग के पीछे छुपें |
| **कैनरी परिनियोजन** | छोटे प्रतिशत पर तैनाती; निगरानी करना; रोल आउट |
| **नीला-हरा परिनियोजन** | दो समान वातावरण; ट्रैफ़िक स्विच करें |
| **समानांतर परीक्षण** | पाइपलाइन समय को कम करने के लिए समानांतर में परीक्षण सुइट चलाएँ |
| **पहले लिंट** | महंगे परीक्षणों से पहले लिंटर चलाएं; जल्दी असफल हो जाओ |
| **कैश निर्भरताएँ** | बिल्ड को गति देने के लिए कैश नोड_मॉड्यूल, पिप, मेवेन |
### पाइपलाइन चरण (सामान्य)
| स्टेज | उद्देश्य |
|------|------|
| **लिंट** | कोड शैली और स्थैतिक विश्लेषण |
| **निर्माण** | संकलित करें; बंडल; कलाकृतियाँ बनाएँ |
| **यूनिट परीक्षण** | तेज़ परीक्षण; कोई बाहरी निर्भरता नहीं |
| **एकीकरण परीक्षण** | डेटाबेस के साथ परीक्षण; एपीआई; बाहरी सेवाएँ |
| **सुरक्षा स्कैन** | निर्भरता की कमजोरियाँ; गुप्त स्कैनिंग; एसएएसटी |
| **पैकेज** | डॉकर छवि बनाएं; रिलीज़ कलाकृतियों का निर्माण करें |
| **स्टेजिंग तैनात करें** | मंचन वातावरण में तैनात करें |
| **E2E परीक्षण** | स्टेजिंग के विरुद्ध पूर्ण सिस्टम परीक्षण |
| **उत्पादन तैनात करें** | उत्पादन में परिनियोजन (मैनुअल या स्वचालित) |
| **धूम्रपान परीक्षण** | सत्यापित करें कि तैनाती स्वस्थ है |

| भाषा/उपकरण | कैश पथ | उदाहरण |

| **पायथन (पिप)** | `~/.cache/pip`| `requirements.txt`हैश से कुंजी के साथ`actions/cache`|

| **जाओ** | `~/go/pkg/mod`|`go.sum`हैश से कुंजी के साथ कैश |
| **जंग (कार्गो)** | `~/.cargo/registry`|`Cargo.lock`हैश से कुंजी के साथ कैश |

## समस्या निवारण
| समस्या | समाधान |
|---------|----------|
| **पाइपलाइन धीमी है** | कैश निर्भरताएँ; नौकरियों को समानांतर बनाना; छोटी आधार छवियों का उपयोग करें |
| **रहस्य उपलब्ध नहीं** | गुप्त नाम जांचें; पर्यावरण का दायरा सत्यापित करें; चेक कांटा पीआर प्रतिबंध |
| **कलाकृति बहुत बड़ी** | अनावश्यक फ़ाइलें बहिष्कृत करें; संकुचित करें; कम अवधारण का उपयोग करें |
| **मैट्रिक्स बहुत बड़ा** | संयोजन कम करें;`include`/`exclude`| का उपयोग करें
| **परतदार परीक्षण** | संगरोध परतदार परीक्षण; मूल कारण ठीक करें;`retry:`| के साथ पुनः प्रयास करें
| **अनुमति अस्वीकृत** | टोकन स्कोप की जाँच करें; धावक अनुमतियाँ सत्यापित करें |

## सारांश
सीआई/सीडी पाइपलाइन सॉफ्टवेयर के निर्माण, परीक्षण और तैनाती को स्वचालित करती हैं। GitHub क्रियाएँ रिपॉजिटरी घटनाओं द्वारा ट्रिगर किए गए YAML वर्कफ़्लो का उपयोग करती हैं; GitLab CI लचीले नियमों के साथ चरणों और नौकरियों का उपयोग करता है। मुख्य पैटर्न में शामिल हैं: एक बार निर्माण करें और कई को तैनात करें; उत्पादन से पहले गेट की जाँच; त्वरित प्रतिक्रिया के लिए पहले लिंट; निर्माण में तेजी लाने के लिए कैश निर्भरता; और समानांतर परीक्षण। पाइपलाइन चरण आम तौर पर लिंट → निर्माण → परीक्षण → सुरक्षा → पैकेज → तैनाती → धुआं परीक्षण से आगे बढ़ते हैं। कैशिंग रणनीतियाँ भाषा के अनुसार भिन्न होती हैं लेकिन एक ही सिद्धांत का पालन करती हैं: कैश निर्भरता निर्देशिकाओं को लॉक फ़ाइल हैश द्वारा कुंजीबद्ध किया जाता है। लक्ष्य हर परिवर्तन पर तेज़, विश्वसनीय प्रतिक्रिया और उत्पादन में सुरक्षित, दोहराए जाने योग्य तैनाती है।
