# 사이버보안 기초
보안은 나중에 추가하는 것이 아니라 처음부터 시스템의 모든 계층에 통합되어야 하는 원칙입니다. 웹 애플리케이션 구축, 인프라 관리, API 제공 등 위협 환경과 방어의 기본 사항을 이해하는 것이 필수적입니다.

## 암호화 및 암호화
### 대칭 암호화와 비대칭 암호화
| 유형 | 작동 원리 | 속도 | 키 배포 | 예 |
|------|-------------|-------|----|----------|
| **대칭** | 암호화 및 복호화에 동일한 키 | 빠른 | 과제: 키를 공유하는 방법은 무엇입니까? | AES-256, 차차20 |
| **비대칭** | 공개 키는 암호화하고 개인 키는 해독합니다 | 느리게 | 공개 키는 공개적으로 공유될 수 있습니다 | RSA, ECC(타원곡선) |
실제로 대부분의 시스템은 **둘 다**, 즉 비대칭 키를 안전하게 교환하기 위해 비대칭 암호화를 사용한 다음, 대량의 데이터에 대해 대칭 암호화를 사용합니다. 이것이 TLS/HTTPS가 작동하는 방식입니다.
### 해싱
해싱은 단방향 함수입니다. 즉, 입력을 고정 크기 문자열로 변환합니다. 되돌릴 수는 없지만 동일한 입력은 항상 동일한 출력을 생성합니다.
| 사용 사례 | 권장 알고리즘 | 피하십시오 |
|----------|---------|-------|
| **비밀번호 저장** | Argon2id, bcrypt, scrypt | MD5, SHA-1, 일반 SHA-256(너무 빠름) |
| **데이터 무결성** | SHA-256, SHA-3 | MD5(깨짐), SHA-1(깨짐) |
| **디지털 서명** | Ed25519, RSA-2048+ | DSA |
### TLS/HTTPS
HTTPS는 TLS(전송 계층 보안)를 통한 HTTP입니다. 다음을 제공합니다:
- **암호화**: 전송 중인 데이터는 도청자가 읽을 수 없습니다.
- **인증**: 서버가 인증서를 통해 자신의 신원을 증명합니다.
- **무결성**: 감지 없이 ​​전송 중에 데이터를 수정할 수 없습니다.
TLS 1.2 또는 1.3을 사용하십시오. TLS 1.0 및 1.1을 비활성화합니다. 브라우저가 항상 HTTPS를 사용하도록 하려면 HSTS(HTTP Strict Transport Security)를 활성화하세요.

## 인증 및 승인
### 인증: 당신은 누구입니까?
| 방법 | 보안 수준 | 사용 사례 |
|---------|---------------|----------|
| **비밀번호** | 낮음~중간 | 기본 계정(12자 이상 필수, 위반 사항 확인) |
| **MFA(TOTP)** | 높음 | 민감한 계정을 위한 표준(Google Authenticator, Authy) |
| **하드웨어 키(FIDO2/WebAuthn)** | 매우 높음 | 보안 수준이 높은 계정(YubiKey) |
| **생체 인식** | 중간~높음 | 장치 잠금 해제(지문, 얼굴) - 유일한 요소로는 좋지 않음 |
| **OAuth2 / OIDC** | 높음 | 제3자 로그인("Google로 로그인") |
**비밀번호 규칙**: 최소 길이(12~16자)를 적용하고, 위반된 비밀번호 목록을 확인하고, 사용자별 솔트를 사용한 해싱을 위해 Argon2id 또는 bcrypt를 사용합니다.
### 승인: 무엇을 할 수 있나요?
| 모델 | 설명 | 예 |
|-------|-------------|---------|
| **RBAC**(역할 기반 액세스 제어) | 역할에 할당된 권한 사용자는 역할을 얻습니다 | 관리자, 편집자, 뷰어 |
| **ABAC**(속성 기반) | 사용자 속성, 자원, 환경을 기반으로 하는 규칙 | "관리자는 팀의 요청을 승인할 수 있습니다." |
| **ACL**(액세스 제어 목록) | 사용자/리소스별 명시적 권한 | 파일 권한(읽기/쓰기/실행) |
**최소 권한의 원칙**: 모든 사용자, 서비스 및 프로세스에 필요한 최소한의 액세스 권한만 부여합니다.
### JWT(JSON 웹 토큰)
| 측면 | 추천 |
|---------|---------------|
| **서명** | RS256 또는 ES256(비대칭)이 선호됩니다. 관리되는 비밀에 HS256이 허용됨 |
| **만료** | 액세스 토큰의 경우 15~60분, 더 긴 세션에 새로 고침 토큰 사용 |
| **스토리지** | HTTP 전용 쿠키(localStorage 아님 - XSS에 취약함) |
| **검증** | 항상 서명, 발급자, 대상 및 만료를 확인하세요 |

## OWASP 상위 10위(2021)
OWASP Top 10은 웹 애플리케이션 보안에 대한 표준 인식 문서입니다. 이는 가장 심각한 위험을 나타냅니다.
| # | 위험 | 그것이 의미하는 것 |
|---|------|---------------|
| 1 | **깨진 액세스 제어** | 사용자는 액세스해서는 안 되는 리소스에 액세스할 수 있습니다 |
| 2 | **암호화 오류** | 민감한 데이터에 대한 암호화가 약하거나 누락됨 |
| 3 | **주사** | SQL, NoSQL, OS 명령 또는 LDAP 삽입 |
| 4 | **안전하지 않은 디자인** | 구현으로 해결할 수 없는 아키텍처 결함 |
| 5 | **보안 구성 오류** | 기본 비밀번호, 열린 포트, 자세한 오류 메시지 |
| 6 | **취약한 구성요소** | 종속성의 알려진 CVE |
| 7 | **인증 실패** | 취약한 비밀번호, 잘못된 세션 관리 |
| 8 | **무결성 실패** | 공급망 공격, 서명되지 않은 업데이트 |
| 9 | **로깅/모니터링 실패** | 침해가 감지되지 않음 |
| 10 | **SSRF** | 서버가 내부 시스템에 요청하도록 속임 |

## 보안 코딩 방식
### 입력 유효성 검사
| 규칙 | 왜 |
|------|-----|
| **화이트리스트 > 블랙리스트** | 차단되는 것이 아닌 허용되는 것을 정의 |
| **매개변수화된 쿼리** | 사용자 입력을 SQL에 연결하지 마십시오. 준비된 문이나 ORM |
| **HTML 인코딩** | XSS를 방지하기 위해`<`,`>`,`&`,`"`,`'`인코딩 |
| **쉘 탈출** | 사용자 입력으로 셸 명령을 작성하지 마세요.`shlex.quote()`사용 |
| **길이 제한** | 버퍼 오버플로 및 DoS를 방지하기 위해 최대 길이를 적용 |
| **유형 확인** | 정수가 정수인지, 부울이 부울인지 확인 |
### 일반적인 취약점
| 취약점 | 공격 | 국방 |
|---------------|---------|---------|
| **SQL 주입** |  로그인 양식의`' OR 1=1 --`| 매개변수화된 쿼리 |
| **XSS** |  주석 필드의`<script>alert('hacked')</script>`| 출력 인코딩, 콘텐츠 보안 정책 |
| **CSRF** | 사용자의 브라우저를 속여 승인되지 않은 요청을 하도록 | CSRF 토큰, SameSite 쿠키 |
| **경로 탐색** |  파일 매개변수의`../../etc/passwd`| 파일 경로 검증 및 삭제 |
| **IDOR** | 다른 사람의 데이터를 보려면 `/user/123`를 `/user/124`로 변경하세요 | 모든 요청에 ​​대한 승인 확인 |

## 네트워크 보안
### 방화벽
| 유형 | 설명 |
|------|-------------|
| **패킷 필터링** | IP, 포트, 프로토콜 기반 규칙 |
| **상태 저장** | 연결 상태를 추적합니다. 더욱 지능적인 필터링 |
| **애플리케이션 수준(WAF)** | HTTP 트래픽을 검사합니다. SQL 주입, XSS 등을 차단합니다. |
| **클라우드 보안 그룹** | 클라우드 인스턴스(AWS SG, Azure NSG)용 가상 방화벽 |
**경험 법칙**: 기본적으로 모든 인바운드 트래픽을 차단합니다. 명시적으로 필요한 것(웹의 경우 80, 443)만 엽니다.
### 네트워크 세분화
직접 인터넷에 액세스할 수 없는 프라이빗 서브넷에 데이터베이스와 캐시를 배치합니다. 공용 서비스(웹 서버, 로드 밸런서)에는 DMZ를 사용합니다. 네트워크 액세스에 최소 권한 원칙을 적용합니다.

## 비밀 관리
### 황금률
**비밀을 하드코딩하지 마세요.** 소스 코드에 API 키, 비밀번호 또는 데이터베이스 URL이 없습니다. Git에 커밋된 환경 변수에는 비밀이 없습니다. Docker 이미지에는 비밀이 없습니다.
### 도구
| 도구 | 유형 | 최고의 대상 |
|------|------|----------|
| **HashiCorp 금고** | 기업 비밀 관리자 | 동적 비밀, 서비스로서의 암호화 |
| **AWS 비밀 관리자** | 클라우드 네이티브 | AWS 환경 |
| **Azure Key Vault** | 클라우드 네이티브 | Azure 환경 |
| **죄송합니다** | 암호화된 파일 | Git에서 비밀 암호화(KMS 또는 GPG 사용) |
| **Docker 비밀** | 컨테이너 네이티브 | Docker Swarm(K8s의 경우 Secrets Store CSI 고려) |
| **dotenv(.env)** | 지역개발 | 개발 전용 - 프로덕션 또는 커밋되지 않음 |
### 회전
비밀을 정기적으로 자동 교체합니다. 비밀이 유출된 경우(예: 공개 저장소에 커밋된 경우) 아무도 보지 못했다고 생각하더라도 즉시 교체하세요.

## 종속성 보안
귀하의 애플리케이션은 가장 약한 종속성만큼만 안전합니다.
### 스캔 도구
| 언어 | 도구 |
|----------|-------|
| **파이썬** | `safety`,`pip-audit`,`bandit`|
| **Node.js** | `npm audit`,`yarn audit`,`snyk`|
| **러스트** | `cargo audit`|
| **가기** | `govulncheck`|
| **일반** | `Dependabot`(GitHub),`Renovate`,`Trivy`|
### 공급망 무결성
- 재현 가능한 빌드를 위해 잠금 파일(`package-lock.json`,`Cargo.lock`,`go.sum`)을 사용하세요.
- 다운로드된 종속성의 체크섬을 확인합니다.
- 공식 레지스트리 및 검증된 게시자를 선호합니다.
- Didabot 또는 Renovate를 통해 마이너/패치 업데이트를 자동화합니다.

## 보안 개발 수명주기(SDL)
| 단계 | 활동 |
|-------|----------|
| **교육** | 개발자가 일반적인 취약점을 이해하도록 보장 |
| **위협 모델링** | 설계 중 잠재적 위협 식별 |
| **보안 코딩 표준** | 린터 및 코드 검토 체크리스트를 통해 시행 |
| **SAST** | 소스 코드의 정적 분석(SonarQube, CodeQL) |
| **DAST** | 실행 중인 애플리케이션의 동적 분석(OWASP ZAP, Burp Suite) |
| **SCA** | 소프트웨어 구성 분석 - 종속성 검색 |
| **침투 테스트** | 정기적인 윤리적 해킹 훈련 |
| **버그 현상금** | 외부 연구원이 취약점을 찾도록 장려 |
| **사고 대응 계획** | 위반이 감지된 경우에 대한 명확한 계획을 세우세요 |

## 비상 체크리스트
위반이 의심되는 경우:
1. **당황하지 마세요** — 신속하게 행동하세요.
2. 영향을 받은 시스템을 **격리**합니다(필요한 경우 네트워크 연결을 끊습니다).
3. **증거 보존**: 로그, 메모리 덤프, 디스크 이미지를 캡처합니다.
4. **범위 식별**: 어떤 시스템, 어떤 데이터?
5. 손상된 모든 자격 증명과 비밀을 **순환**합니다.
6. 취약점을 **패치**합니다.
7. 필요한 경우 (법적 기간 내에) 영향을 받는 사용자 및 규제 기관에 **알립니다**.
8. **사후 분석**: 근본 원인과 조치 항목을 24~48시간 이내에 문서화합니다.
