# 성능 최적화
성능 최적화는 응답 시간을 줄이고, 처리량을 늘리고, 메모리 사용량을 낮추고, 병목 현상을 제거하여 소프트웨어를 더 빠르게 만드는 방법입니다. 느린 소프트웨어는 사용자를 잃고 리소스를 낭비하며 모든 사람을 좌절시키기 때문에 이는 개발자가 가질 수 있는 가장 영향력 있는 기술 중 하나입니다. 그러나 이는 개발자가 증거가 아닌 직관을 기반으로 잘못된 것을 최적화하는 가장 흔히 저지르는 잘못 중 하나이기도 합니다.
---

## 황금률
> **먼저 측정하고 두 번째로 최적화하세요.** 절대 가정을 기반으로 최적화하지 마세요. 코드를 프로파일링하고 실제 병목 현상을 찾아서 수정하세요.
| 안티패턴 | 왜 나쁜가요 |
|-------------|-------------|
| **성급한 최적화** | 느리지 않은 코드 속도를 높이는 데 시간을 소비 |
| **측정 없이 최적화** | 잘못된 병목 현상을 수정합니다. 개선 여부를 확인할 방법이 없습니다 |
| **속도를 위해 가독성을 희생** | 읽을 수 없는 코드는 성능 향상보다 비용이 더 많이 듭니다 |
| **모든 것을 캐싱** | 오래된 데이터, 메모리 팽창, 복잡성 |

## 프로파일링
무언가를 더 빠르게 만들기 전에 *어디서* 시간이 소비되는지 알아야 합니다.
| 도구 유형 | 측정 대상 | 예 |
|------------|----|----------|
| **CPU 프로파일러** | CPU 시간을 가장 많이 소비하는 기능 | cProfile(Python), perf(Linux), Chrome DevTools(JS) |
| **메모리 프로파일러** | 메모리 할당 및 누수 | Tracemalloc(Python), Valgrind, heaptrack |
| **I/O 프로파일러** | 디스크 및 네트워크 I/O 병목 현상 | iotop, strace, Wireshark |
| **APM(애플리케이션 성능 모니터링)** | 엔드투엔드 요청 타이밍 | 뉴렐릭, 데이터독, 예거 |
| **브라우저 개발 도구** | 프런트엔드 렌더링, JavaScript 실행, 네트워크 | Chrome DevTools, Firefox 프로파일러 |
### 프로파일링 작업 흐름
| 단계 | 설명 |
|------|-------------|
| 1. 느린 작동 확인 | 사용자들이 페이지 로드 속도가 느리다고 보고합니다. 모니터링 결과 대기 시간이 길어짐 |
| 2. 전체 경로 프로파일링 | 가장 많은 시간이 걸리는 구성 요소 찾기 |
| 3. 드릴다운 | 핫 기능을 찾기 위해 특정 구성 요소를 프로파일링 |
| 4. 병목 현상 해결 | 적절한 최적화 적용 |
| 5. 다시 측정 | 개선 사항을 확인하십시오. 회귀 확인 |

## 알고리즘 최적화
가장 큰 성능 향상은 미세한 최적화가 아닌 더 나은 알고리즘을 선택하는 것에서 비롯됩니다.
| 변경 | 개선 |
|---------|------------|
| 선형 탐색 O(n) → 해시 테이블 탐색 O(1) | 대규모 데이터 세트의 경우 100x+ |
| 중첩 루프 O(n²) → 정렬 + 이진 검색 O(n log n) | 큰 n에 대한 크기 순서 |
| 반복계산 → 메모/캐싱 | 중복 작업 제거 |
| 루프의 문자열 연결 → Builder / Join | 2차 문자열 복사 방지 |
| 정렬되지 않은 데이터 → 이진 검색으로 정렬된 데이터 | 조회당 O(n) 대신 O(log n) |

## 캐싱 전략
캐싱은 계산된 결과를 저장하므로 다시 계산할 필요가 없습니다.
| 캐시 유형 | 위치 | 속도 | 평생 |
|------------|----------|-------|----------|
| **CPU 캐시** | L1/L2/L3 | ~1ns | 자동 |
| **인메모리** | 애플리케이션 RAM(dict, HashMap) | ~100ns | 삭제되거나 퇴거될 때까지 |
| **분산 캐시** | 레디스, 멤캐시드 | ~1ms | 구성 가능한 TTL |
| **CDN** | 전 세계 엣지 서버 | ~10-50ms | 구성 가능한 TTL |
| **브라우저 캐시** | 사용자의 브라우저 | ~1ms | HTTP 캐시 헤더 |
| **데이터베이스 쿼리 캐시** | 데이터베이스 또는 ORM 수준 | ~1-10ms | 데이터가 변경될 때까지 |
### 캐싱 패턴
| 패턴 | 설명 | 사용 시기 |
|---------|-------------|-------------|
| **캐시 배제** | 애플리케이션은 캐시를 확인합니다. 누락 시 DB에서 로드됩니다. 캐시에 저장 | 가장 일반적입니다. 간단한 |
| **연속기록** | 캐시와 DB에 동시에 쓰기 | 읽을 때 >> 쓸 때; 일관성 중요 |
| **뒤에 쓰기** | 캐시에 쓰기; 비동기적으로 DB에 쓰기 | 높은 쓰기 처리량; 일부 데이터 손실 위험 |
| **TTL(Time to Live)** | 캐시 항목은 설정된 시간 후에 만료됩니다. | 데이터가 주기적으로 변경되는 경우 |
| **무효화** | 오래된 캐시 항목을 명시적으로 제거 | 데이터가 언제 변경되는지 정확히 알 때 |
### 캐시 무효화
컴퓨터 과학에서 가장 어려운 두 가지 문제는 캐시 무효화, 이름 지정 및 하나씩 오류입니다.
| 전략 | 설명 |
|----------|-------------|
| **TTL 기반** | 항목은 N초 후에 만료됩니다. 간단하지만 오래된 데이터를 제공할 수 있음 |
| **이벤트 중심** | 데이터가 변경되면 무효화됩니다. 더 복잡하지만 정확함 |
| **버전 기반** | 버전 번호를 포함하세요. 변경사항 증가 |
| **태그 기반** | 태그 관련 캐시 항목; 태그가 있는 모든 항목을 무효화 |

## 데이터베이스 최적화
데이터베이스는 웹 애플리케이션에서 가장 큰 병목 현상이 되는 경우가 많습니다.
| 기술 | 설명 | 영향 |
|------------|-------------|---------|
| **인덱싱** | WHERE, JOIN, ORDER BY에 사용되는 열에 인덱스 추가 | 10~1000배 더 빠른 쿼리 |
| **쿼리 최적화** | SELECT *를 피하세요. EXPLAIN을 사용하여 쿼리 분석 | I/O 감소 |
| **연결 풀링** | 새 연결을 생성하는 대신 데이터베이스 연결 재사용 | 연결 오버헤드 제거 |
| **복제본 읽기** | 읽기 쿼리를 복제본 데이터베이스로 라우팅 | 읽기 부하 분산 |
| **파티셔닝** | 큰 테이블을 작은 파티션으로 분할 | 대규모 데이터 세트에 대한 쿼리 속도 향상 |
| **비정규화** | 조인을 피하기 위해 중복 데이터 추가 | 더 빠른 읽기; 느린 쓰기 |
| **구체화된 뷰** | 미리 계산된 쿼리 결과 | 즉각적인 복합 쿼리 |
| **N+1 예방** | JOIN, 즉시 로드 또는 일괄 쿼리 사용 | 수천 개의 쿼리 제거 |

## 동시성과 병렬성
| 개념 | 설명 | 사용 시기 |
|---------|-------------|-------------|
| **스레딩** | 단일 프로세스 내의 다중 스레드 | I/O 바인딩된 작업(네트워크, 디스크) |
| **멀티프로세싱** | 다중 프로세스(Python의 GIL 우회) | CPU 바인딩된 작업 |
| **비동기/대기** | 협력적인 멀티태스킹; 단일 스레드 | 높은 동시성 I/O(웹 서버) |
| **GPU 컴퓨팅** | 수천 개의 병렬 코어 | 매트릭스 운영; 이미지 처리; ML |
### 비동기 vs 스레딩
| 측면 | 비동기/대기 | 스레딩 |
|---------|------------|----------|
| **모델** | 협동조합(과제 수율 관리) | 선점형(OS가 스레드를 전환함) |
| **오버헤드** | 매우 낮음(컨텍스트 전환 없음) | 상위(스레드 생성, 컨텍스트 전환) |
| **복잡성** | 더 간단한 추론(단일 스레드) | 경쟁 조건, 교착 상태, 잠금 |
| **최고의 대상** | 많은 동시 I/O 작업 | 비동기화할 수 없는 작업 차단 |
| **제한사항** | 차단하지 않고 CPU 바인딩된 코드를 사용할 수 없습니다 | Python의 GIL은 진정한 병렬성을 제한합니다 |

## 프론트엔드 성능
| 기술 | 설명 | 영향 |
|------------|-------------|---------|
| **축소** | 공백을 제거하고 변수 이름을 줄입니다 | 20-40% 더 작은 파일 |
| **번들링** | 여러 파일을 더 적은 수의 요청으로 결합 | HTTP 요청 감소 |
| **코드 분할** | 현재 페이지에 필요한 코드만 로드 | 초기 로드 속도 향상 |
| **지연 로딩** | 필요할 때 이미지와 구성요소 로드 | 초기 렌더링 속도 향상 |
| **나무 흔들림** | 번들에서 사용하지 않는 코드 제거 | 더 작은 번들 |
| **이미지 최적화** | WebP/AVIF를 사용하세요. 반응형 이미지; 게으른 로딩 | 50-80% 더 작은 이미지 |
| **CDN** | 에지 서버에서 정적 자산 제공 | 전 세계적으로 낮은 대기 시간 |
| **HTTP/2 및 HTTP/3** | 다중화; 헤더 압축; 0-RTT | 더 빠른 프로토콜 오버헤드 |
| **서비스 워커** | 오프라인 사용을 위한 캐시 자산 푸시 알림 | 더 빠른 재방문 |

## 요약
성능 최적화는 측정, 병목 현상 식별, 수정, 다시 측정 등의 체계적인 프로세스입니다. 가장 큰 승리는 미세한 최적화가 아닌 알고리즘 개선과 불필요한 작업 제거에서 비롯됩니다. 캐싱, 데이터베이스 인덱싱 및 동시성은 가장 강력한 도구입니다. 프런트엔드 성능은 페이로드 크기와 왕복을 최소화하는 데 달려 있습니다. 그리고 가장 중요한 규칙은 항상 동일합니다. 추측하지 마세요 — 프로필입니다.
