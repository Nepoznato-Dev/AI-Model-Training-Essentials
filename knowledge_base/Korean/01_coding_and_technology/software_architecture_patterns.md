# 소프트웨어 아키텍처 패턴
아키텍처는 시스템이 구성되는 방식, 즉 구성 요소가 무엇인지, 통신 방식, 책임이 어디에 있는지에 대한 일련의 구조적 결정입니다. 좋은 아키텍처는 시스템을 쉽게 이해하고, 수정하고, 확장할 수 있게 해줍니다. 나쁜 아키텍처는 모든 변화를 어렵게 만듭니다. 이 파일은 주요 패턴, 각각의 사용 시기 및 관련된 장단점을 다룹니다.
---

## 모놀리스 vs 마이크로서비스
이는 가장 기본적인 아키텍처 결정이며 올바른 결정을 내릴 가치가 있습니다.
| 측면 | 모노리스 | 마이크로서비스 |
|---------|------------|---------------|
| **구조** | 단일 배치 가능 유닛 | 독립적으로 배포 가능한 소규모 서비스 |
| **데이터** | 공유 데이터베이스 | 각 서비스는 자체 데이터를 소유합니다 |
| **커뮤니케이션** | 처리 중인 함수 호출 | 네트워크 호출(HTTP, gRPC, 메시징) |
| **확장** | 전체 애플리케이션 확장 | 개별 서비스 확장 |
| **배포** | 단일 릴리스 주기 | 독립적 배포 |
| **복잡성** | 초기 개발이 더 간단함 | 운영 복잡성(네트워킹, 모니터링) |
| **최고의 대상** | 소규모 팀, 초기 단계 제품 | 대규모 팀, 복잡한 도메인, 대규모 |
### 모놀리스로 시작해야 하는 경우
대부분의 애플리케이션은 단일체로 시작해야 합니다. 빌드, 테스트, 배포 및 디버그가 더 간단합니다. 나중에 도메인 경계를 더 명확하게 파악하면 언제든지 서비스를 추출할 수 있습니다. 이는 나중에 쉽게 추출할 수 있도록 내부 경계가 깨끗한 단일체인 "모듈식 단일체"라고도 합니다.
### 마이크로서비스로 전환해야 하는 경우
다음과 같은 경우 마이크로서비스를 고려하십시오.
- 팀 규모가 너무 커서 조정에 병목 현상이 발생합니다.
- 시스템의 각 부분마다 확장 요구 사항이 매우 다릅니다.
- 구성 요소의 독립적인 배포가 필요합니다.
- 귀하의 도메인에는 명확하게 제한된 컨텍스트가 있습니다(아래 DDD 참조).

## 계층형 아키텍처(N 계층)
가장 일반적인 아키텍처 패턴입니다. 코드는 각각 특정 책임을 맡은 레이어로 구성됩니다.
```
â”Œ─────────────────────────┐
│   Presentation Layer    │  ← UI, controllers, API endpoints
├─────────────────────────┤
│   Application Layer     │  ← Use cases, orchestration
├─────────────────────────┤
│   Domain Layer          │  ← Business logic, entities
├─────────────────────────┤
│   Infrastructure Layer  │  ← Database, external services, file I/O
└─────────────────────────┘
```

| 레이어 | 책임 | 규칙 |
|-------|---------------|------|
| **프레젠테이션** | 사용자/HTTP 요청 처리 | 애플리케이션 계층만 호출 가능 |
| **신청** | 사용 사례 조율 | 도메인 레이어 호출 가능 |
| **도메인** | 핵심 비즈니스 로직 | 다른 레이어에 의존해서는 안 됩니다 |
| **인프라** | 기술적 문제 | Domain |
**주요 규칙**: 종속성은 내부를 가리킵니다. 도메인 계층은 데이터베이스나 웹 프레임워크에 대해 알지 못합니다.

## 이벤트 중심 아키텍처
구성 요소는 발생한 **이벤트**를 내보내고 이에 반응하여 통신합니다.
| 패턴 | 설명 |
|---------|-------------|
| **이벤트 알림** | 서비스 A는 "OrderPlaced"를 내보냅니다. 서비스 B, C, D 반응 |
| **이벤트 소싱** | 모든 상태 변경 사항을 일련의 이벤트로 저장(현재 상태뿐만 아니라) |
| **CQRS** | 읽기 모델(쿼리)을 쓰기 모델(명령)과 분리 |
### 이벤트 소싱
"현재 상태"를 데이터베이스에 저장하는 대신 모든 상태 변경을 이벤트로 저장하세요.
```
OrderCreated(order_id=123, total=$50)
OrderPaid(order_id=123, payment_id=456)
OrderShipped(order_id=123, tracking=ABC)
```

이점: 완전한 감사 추적, 과거 상태를 재구성하는 능력, 분리된 소비자. 과제: 이벤트 스키마 진화, 최종 일관성, 디버깅 복잡성.
### CQRS(명령어 쿼리 책임 분리)
| 측면 | 목적 | 데이터베이스 |
|------|---------|----------|
| **명령(쓰기)** | 돌연변이를 처리합니다. 비즈니스 규칙 시행 | 쓰기에 최적화됨(정규화됨) |
| **쿼리(읽기)** | 읽기 요청 처리 | 읽기에 최적화됨(비정규화됨) |
CQRS는 이벤트 소싱과 자연스럽게 결합됩니다. 쓰기 측의 이벤트는 읽기 최적화된 보기에 투영됩니다.

## 메시지 대기열 및 이벤트 브로커
서비스가 비동기식으로 통신해야 하는 경우 메시지 대기열이 백본입니다.
| 도구 | 유형 | 최고의 대상 |
|------|------|----------|
| **아파치 카프카** | 분산 이벤트 로그 | 처리량이 많은 이벤트 스트리밍, 이벤트 소싱 |
| **RabbitMQ** | 라우팅 기능이 있는 메시지 브로커 | 작업 대기열, 복잡한 라우팅 패턴 |
| **AWS SQS** | 관리되는 대기열 | AWS 기반의 간단한 대기열 |
| **AWS SNS** | 게시/구독 알림 | 여러 가입자에게 팬아웃 |
| **Google 게시/구독** | 관리형 게시/구독 | GCP 기반 이벤트 스트리밍 |
| **Redis 스트림** | 경량 스트림 | 단순 이벤트 로깅, 캐싱 사용 사례 |
### 메시징 패턴
| 패턴 | 설명 |
|---------|-------------|
| **지점 간** | 메시지당 하나의 생산자, 하나의 소비자 |
| **게시/구독** | 한 명의 생산자, 여러 명의 구독자 |
| **요청/응답** | 비동기 전송을 통한 동기식 |
| **배달 못한 편지 대기열** | 처리에 실패한 메시지는 검사를 위해 별도의 큐로 이동합니다. |

## 도메인 중심 설계(DDD)
DDD는 기술적 문제보다는 비즈니스 개념을 중심으로 코드를 집중시키는 소프트웨어 설계에 대한 전략적 접근 방식입니다.
### 주요 개념
| 개념 | 설명 |
|---------|-------------|
| **제한된 컨텍스트** | 도메인 모델이 일관된 경계(예: "주문", "배송", "청구") |
| **유비쿼터스 언어** | 개발자와 도메인 전문가 간의 공유 어휘 |
| **집계** | 데이터 변경에 대해 단일 단위로 처리되는 관련 엔터티 클러스터 |
| **엔티티** | ID가 있는 개체(예: user_id가 있는 사용자) |
| **값 개체** | 정체성이 없는 사물; 속성(예: 돈, 주소)으로 정의 |
| **도메인 이벤트** | 도메인에서 발생한 문제(예: OrderPlaced) |
| **부패방지 레이어** | 도메인과 외부 시스템 간의 번역 계층 |
### DDD가 도움이 될 때
DDD는 전자상거래, 물류, 금융 서비스, 의료 등 비즈니스 영역이 복잡할 때 가장 가치가 높습니다. 도메인이 단순하다면(블로그, 할 일 앱) DDD는 과잉입니다.

## 캐싱 전략
캐싱은 성능을 향상시키는 가장 효과적인 방법 중 하나이지만 일관성과 관련하여 복잡성이 발생합니다.
| 전략 | 설명 | 트레이드오프 |
|----------|-------------|----------|
| **캐시 배제** | 애플리케이션은 캐시를 먼저 확인합니다. 누락 시 DB에서 로드 | 단순한; 최종 일관성 |
| **연속 기입** | 캐시와 DB에 동시에 쓰기 | 일관된; 느린 쓰기 |
| **뒤에 쓰기** | 캐시에 쓰기; 비동기로 DB에 쓰기 | 빠른 쓰기; 데이터 손실 위험 |
| **읽기** | 누락 시 투명하게 DB에서 캐시 로드 | 캐시를 배제하는 것보다 간단함 |
### 캐시할 항목
| 레이어 | 무엇 | 도구 |
|-------|------|-------|
| **CDN** | 정적 자산, API 응답 | CloudFront, Cloudflare |
| **신청** | 계산된 결과, 세션 데이터 | 레디스, 멤캐시드 |
| **데이터베이스** | 쿼리 결과, 자주 액세스되는 행 | 쿼리 캐시, 구체화된 뷰 |
**캐시 무효화**는 매우 어렵기로 악명이 높습니다. 일반적인 전략: TTL(time-to-live), 이벤트 기반 무효화(데이터 변경 시 캐시 지우기) 및 LRU(최근에 사용됨) 제거.

## 디자인 패턴
### 견고한 원칙
| 원리 | 그것이 의미하는 것 |
|------------|---------------|
| **S** — 단일 책임 | 클래스를 변경해야 하는 한 가지 이유가 있어야 합니다 |
| **O** — 개장/폐쇄 | 확장을 위해 열림, 수정을 위해 닫음 |
| **L** — 리스코프 대체 | 하위 유형은 기본 유형으로 대체 가능해야 합니다 |
| **I** — 인터페이스 분리 | 많은 특정 인터페이스 > 하나의 범용 인터페이스 |
| **D** — 종속성 반전 | 구체화가 아닌 추상화에 의존 |
### 일반적인 패턴
| 패턴 | 의도 | 예 |
|---------|---------|---------|
| **싱글턴** | 클래스에 인스턴스가 하나만 있는지 확인 | 데이터베이스 연결 풀 |
| **공장** | 정확한 클래스를 지정하지 않고 객체 생성 |  __보호됨_0__ |
| **관찰자** | 상태가 변경되면 부양가족에게 알림 | 이벤트 리스너, 게시/구독 |
| **전략** | 런타임 시 알고리즘 교환 | 결제 전략: CreditCard, PayPal, 암호화폐 |
| **저장소** | 깔끔한 인터페이스 뒤의 추상 데이터 액세스 |  __보호됨_1__ |
| **데코레이터** | 동적으로 동작 추가 | 서비스 주변의 로깅 데코레이터 |
| **어댑터** | 호환되지 않는 인터페이스가 함께 작동하도록 만들기 | 레거시 API 어댑터 |

## 올바른 아키텍처 선택
보편적으로 "최고의" 아키텍처는 없습니다. 올바른 선택은 다음에 따라 달라집니다.
| 요인 | 모놀리스를 선호하는 경우... | 마이크로서비스를 선호하는 경우... |
|---------|------------|----------------|
| **팀 규모** | < 10 developers | >20명의 개발자, 여러 팀 |
| **도메인 복잡성** | 간단하거나 잘 이해됨 | 복잡하고 제한된 컨텍스트가 많음 |
| **규모 요구사항** | 균일한 확장 요구 | 구성 요소마다 다른 규모가 필요합니다 |
| **배포 주기** | 단일 릴리스 주기 | 독립적인 배포가 필요함 |
| **기술 다양성** | 하나의 스택은 괜찮습니다 | 다양한 서비스에는 다양한 기술이 필요합니다 |
**실용적인 조언**: 모듈식 모놀리스로 시작하세요. 명확한 필요성과 명확한 도메인 경계가 있는 경우에만 서비스를 추출하세요. 조기 마이크로서비스는 업계에서 가장 흔한 아키텍처 실수 중 하나입니다.
