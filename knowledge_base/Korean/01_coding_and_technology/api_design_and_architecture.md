# API 디자인 및 아키텍처
API(응용 프로그래밍 인터페이스)는 소프트웨어 구성 요소가 서로 통신하는 방식입니다. 잘 설계된 API는 직관적이고 일관되며 작업하기에 즐겁습니다. 제대로 설계되지 않은 것은 혼란, 버그, 좌절을 야기합니다. 이 파일은 개발자가 실제로 사용하고 싶은 API를 구축하기 위한 원칙, 패턴 및 사례를 다루고 있습니다.
---

## REST API 원칙
REST(Representational State Transfer)는 웹 API의 주요 아키텍처 스타일입니다. 데이터를 URL로 식별되는 **리소스**로 취급하고 HTTP 메서드를 사용하여 해당 데이터를 작동합니다.
### 핵심 원칙
| 원리 | 설명 |
|------------|-------------|
| **자원** | 모든 것은 URI(`/users/123`,`/orders/456`)가 있는 리소스입니다.
| **HTTP 방법** | GET(읽기), POST(생성), PUT(교체), PATCH(부분 업데이트), DELETE(제거) |
| **무국적** | 각 요청에는 필요한 모든 정보가 포함되어 있습니다. 서버측 세션 상태가 없습니다 |
| **균일한 인터페이스** | 일관된 리소스 이름 지정, 표준 방법, 표준 상태 코드 |
| **대표** | 리소스는 다양한 형식(JSON, XML)으로 표현 가능 |
### 리소스 명명 규칙
| 할 | 하지 마세요 |
|----|-------|
|  `/users`(복수명사) |  `/user`(단수) |
|  `/users/123/orders`(중첩) |  __보호됨_3__ |
|  `/products?category=electronics`(필터링을 위한 쿼리 매개변수) |  __보호됨_5__ |
| 하이픈 사용:`/user-profiles`| 밑줄 사용:`/user_profiles`|
### HTTP 메서드 및 멱등성
| 방법 | 목적 | 멱등성? | 안전한? |
|---------|---------|------------|-------|
| **받기** | 리소스 읽기 | ✅ 예 | ✅ 예 |
| **포스트** | 리소스 생성 | ❌ 아니요 | ❌ 아니요 |
| **넣어** | 리소스를 완전히 교체 | ✅ 예 | ❌ 아니요 |
| **패치** | 리소스 부분 업데이트 | ❌ 아니요* | ❌ 아니요 |
| **삭제** | 리소스 제거 | ✅ 예 | ❌ 아니요 |
*PATCH는 신중하게 설계하여 멱등성을 갖도록 만들 수 있습니다.
### HTTP 상태 코드
| 코드 | 의미 | 사용 시기 |
|------|---------|-------------|
| **200** | 알았어 | 성공적인 GET, PUT, PATCH, DELETE |
| **201** | 생성됨 | 성공적인 POST(리소스 생성) |
| **204** | 콘텐츠 없음 | DELETE 성공(반환할 항목 없음) |
| **400** | 잘못된 요청 | 잘못된 입력 또는 잘못된 요청 |
| **401** | 무단 | 인증이 누락되었거나 유효하지 않음 |
| **403** | 금지 | 인증되었지만 승인되지 않음 |
| **404** | 찾을 수 없음 | 리소스가 존재하지 않습니다 |
| **409** | 갈등 | 중복된 리소스 또는 상태 충돌 |
| **422** | 처리할 수 없는 엔터티 | 유효한 JSON이지만 의미상 오류 |
| **429** | 요청이 너무 많습니다 | 속도 제한이 초과되었습니다 |
| **500** | 내부 서버 오류 | 예상치 못한 서버 오류 |
| **502** | 나쁜 게이트웨이 | 업스트림 서비스 실패 |
| **503** | 서비스를 이용할 수 없습니다 | 일시적인 과부하 또는 유지 관리 |

## API 버전 관리
API는 진화합니다. 획기적인 변경이 필요한 경우 버전 관리를 통해 기존 클라이언트가 계속 작동할 수 있습니다.
| 전략 | 예 | 장점 | 단점 |
|----------|---------|------|------|
| **URL 경로** |  __보호_0__ , __보호_1__ | 단순하고 명시적 | 버전별 URL 변경 |
| **쿼리 매개변수** |  __보호됨_2__ | 유연한 | 잊어버리기 쉽다 |
| **헤더** |  __보호됨_3__ | URL 정리 | 검색 가능성이 낮음 |
| **버전 관리 없음** | 스키마 발전 전용 | 가장 단순한 | 획기적인 변화는 모든 사람에게 영향을 미칩니다 |
**모범 사례**: 명확성을 위해 URL 경로 버전 관리(`/v1/`)를 사용하세요. 하나 이상의 이전 버전을 지원합니다. 명확한 일정을 통해 이전 버전을 더 이상 사용하지 않습니다.

## 인증 방법
| 방법 | 작동 원리 | 최고의 대상 |
|---------|-------------|----------|
| **API 키** | 헤더의 비밀 키(`X-API-Key: abc123`) | 서버 간, 간단한 통합 |
| **OAuth2** | 범위를 사용한 토큰 기반 위임 | 제3자 액세스, 사용자 승인 앱 |
| **JWT** | 클레임이 포함된 독립형 토큰 | 서비스 전반에 걸친 무상태 인증 |
| **기본 인증** | Base64로 인코딩된 사용자 이름:비밀번호 | 개발 전용 - TLS 없이는 프로덕션이 불가능함 |
| **세션 쿠키** | HTTP 전용 쿠키의 서버측 세션 ID | 기존 웹 애플리케이션 |
### OAuth2 흐름(단순화)
1. 클라이언트는 사용자를 인증 서버로 리디렉션합니다.
2. 사용자가 로그인하고 권한을 부여합니다.
3. 인증 서버는 인증 코드를 반환합니다.
4. 클라이언트는 액세스 토큰(및 선택적으로 새로 고침 토큰)에 대한 코드를 교환합니다.
5. 클라이언트는 액세스 토큰을 사용하여 API를 호출합니다.
6. 액세스 토큰이 만료되면 새로고침 토큰을 사용하여 새 토큰을 받으세요.

## API 스타일: REST vs GraphQL vs gRPC
| 기능 | 휴식 | GraphQL | gRPC |
|---------|------|---------|------|
| **데이터 형식** | JSON(일반적으로) | JSON | Protobuf(바이너리) |
| **엔드포인트** | 다중(리소스당 하나) | 단일 엔드포인트 | .proto 파일로 정의됨 |
| **과잉** | 공통(필요 이상으로 얻기) | 없음(클라이언트가 필드를 지정함) | 없음(스키마 정의) |
| **과소평가** | 여러 번의 호출이 필요합니다 | 없음(정확히 필요한 것을 얻음) | 없음 |
| **실시간** | WebSocket 필요 | 구독 내장 | 스트리밍 내장 |
| **캐싱** | HTTP 캐싱은 자연스럽게 작동합니다 | 캐시하기가 더 어려워졌습니다 | 한정 |
| **학습 곡선** | 낮음 | 중간 | 중간~높음 |
| **최고의 대상** | 공개 API, CRUD 앱 | 복잡한 UI, 모바일 앱 | 내부 마이크로서비스, 고성능 |

## 속도 제한
API를 남용으로부터 보호하고 공정한 사용을 보장하세요.
| 전략 | 작동 원리 |
|----------|-------------|
| **고정 창** | 기간당 N개 요청(예: 시간당 100개) |
| **슬라이딩 윈도우** | 더욱 세분화되었습니다. 롤링 창에서 요청 수 계산 |
| **토큰 버킷** | 고정 비율로 토큰이 추가됩니다. 각 요청은 토큰을 소비합니다 |
헤더와 함께 `429 Too Many Requests`을 반환합니다.```
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1625097600
Retry-After: 60
```

## 오류 처리
일관된 오류 응답을 통해 API 작업이 훨씬 쉬워집니다.
```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Invalid input data",
    "details": [
      {
        "field": "email",
        "issue": "Invalid email format"
      }
    ]
  }
}
```

**원칙**: 일관된 오류 구조를 사용하고, 실행 가능한 메시지를 포함하고, 표준 HTTP 상태 코드를 사용하고, 상관 관계 ID를 사용하여 서버 측 오류를 기록하고, 스택 추적이나 내부 세부 정보를 절대 노출하지 않습니다.

## API 게이트웨이 패턴
API 게이트웨이는 클라이언트와 백엔드 서비스 사이에 위치하여 단일 진입점을 제공합니다.
| 책임 | 설명 |
|---------------|-------------|
| **라우팅** | 적절한 백엔드 서비스에 직접 요청 |
| **인증** | 게이트웨이 수준에서 토큰 유효성 검사 |
| **속도 제한** | 전역 또는 클라이언트별 제한 적용 |
| **변환** | 프로토콜 간 변환(REST ← gRPC) |
| **캐싱** | 캐시 공통 응답 |
| **모니터링** | 중앙 집중식 로깅 및 측정항목 |
| **로드 밸런싱** | 서비스 인스턴스 전체에 트래픽 분산 |
| 도구 | 유형 |
|------|------|
| **콩** | 오픈소스 API 게이트웨이(Nginx 기반) |
| **AWS API 게이트웨이** | 완전관리형, AWS와 통합 |
| **Azure API 관리** | 개발자 포털이 포함된 관리형 게이트웨이 |
| **특사/Istio** | API 게이트웨이 기능을 갖춘 서비스 메시 |
| **트래픽** | 자동 검색, Let's Encrypt 통합 |

## 웹훅
웹후크를 사용하면 클라이언트가 변경 사항을 폴링하도록 하는 대신 API가 이벤트를 클라이언트에 실시간으로 푸시할 수 있습니다.
| 측면 | 모범 사례 |
|---------|--------------|
| **배달** | 클라이언트 URL에 대한 JSON 페이로드가 포함된 POST 요청 |
| **보안** | HMAC로 페이로드에 서명합니다. 클라이언트가 서명을 확인합니다 |
| **신뢰성** | 지수 백오프를 사용하여 실패한 전달 재시도 |
| **멱등성** | 고유한 이벤트 ID를 포함합니다. 클라이언트가 중복을 처리 |
| **버전 관리** | 웹훅 페이로드에 API 버전 포함 |

## 디자인 체크리스트
- [ ] 리소스는 복수 명사입니다(`/users`,`/getUser`아님).
- [ ] HTTP 메서드가 올바르게 사용됨(읽기에는 GET, 생성에는 POST 등)
- [ ] 일관된 오류 응답 형식
- [ ] 모든 목록 끝점에 대한 페이지 매김
- [ ] 명확한 헤더로 속도 제한
- [ ] API 버전 관리 전략이 정의됨
- [ ] 인증 및 승인이 완료되었습니다.
- [ ] 모든 엔드포인트에 대한 입력 검증
- [ ] OpenAPI/Swagger 문서 유지 관리
- [ ] CORS가 올바르게 구성되었습니다.
- [ ] 프로덕션에 HTTPS가 적용됨
- [ ] 필요한 경우 POST 작업을 위한 멱등성 키
