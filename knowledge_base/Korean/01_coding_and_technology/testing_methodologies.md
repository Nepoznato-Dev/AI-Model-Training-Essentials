# 테스트 방법론
테스트는 코드가 작동한다는 확신을 얻는 방법입니다. 더 중요한 것은 코드 변경이 이미 작동하는 코드를 손상시키지 않는다는 것입니다. 좋은 테스트는 사용자보다 먼저 버그를 포착하고 예상되는 동작을 문서화하며 두려움 없는 리팩토링을 가능하게 합니다. 이 파일은 단위 테스트부터 엔드투엔드 테스트까지 테스트 전략의 전체 범위와 테스트를 효과적으로 만드는 원칙을 다루고 있습니다.
---

## 테스트 피라미드
테스트 피라미드는 프로젝트의 이상적인 테스트 배포를 설명합니다.
```
        /  E2E  \          ← Few; slow; expensive; test the whole system
       /─────────\
      / Integration\       ← Some; test how components work together
     /───────────────\
    /   Unit Tests    \    ← Many; fast; cheap; test individual functions
   /─────────────────────\
```

| 레벨 | 카운트 | 속도 | 비용 | 테스트 대상 |
|-------|-------|-------|------|---------------|
| **단위** | 많은 | 빠른 속도(ms) | 낮음 | 개별 함수, 클래스, 메소드 |
| **통합** | 일부 | 중간(100ms-s) | 중간 | 구성 요소가 상호 작용하는 방식 데이터베이스 쿼리; API 호출 |
| **E2E** | 거의 | 느림(초-분) | 높음 | 전체 사용자는 실제 시스템을 통해 이동합니다 |
---

## 단위 테스트
개별 코드 단위를 개별적으로 테스트합니다.
### 원칙
| 원리 | 설명 |
|------------|-------------|
| **빠르게** | 각 테스트는 밀리초 단위로 실행되어야 합니다 |
| **격리됨** | 테스트는 서로 의존하지 않습니다. 공유 상태 없음 |
| **결정적** | 동일한 입력 → 매번 동일한 출력(임의성 없음, 시간 종속성 없음) |
| **자체 점검** | 테스트는 자동으로 통과하거나 실패합니다. 수동 검사 없음 |
| **적절한** | 코드 옆이나 앞에 작성됨(TDD) |
### 테스트 분석
| 단계 | 설명 |
|-------|-------------|
| **정리** | 테스트 데이터 및 종속성 설정 |
| **행동** | 테스트 중인 함수 또는 메서드 호출 |
| **주장** | 결과가 기대와 일치하는지 확인 |
### 테스트 대상
| 카테고리 | 예 |
|------------|---------|
| **행복한 길** | 일반 입력은 예상되는 출력을 생성합니다 |
| **특지 사례** | 빈 입력, null, 0, 최대값, 단일 요소 |
| **오류 사례** | 잘못된 입력, 데이터 누락, 권한 거부 |
| **경계 조건** | 오프바이원; 정확히 한계에 |
### 조롱과 스터빙
| 기간 | 설명 | 사용 시기 |
|------|-------------|-------------|
| **모의** | 어떻게 호출되었는지 기록하는 가짜 객체 | 상호작용 확인(이 메소드가 호출되었나요?) |
| **스텁** | 미리 결정된 값을 반환하는 가짜 개체 | 테스트 데이터 제공(데이터베이스에서 이 사용자 반환) |
| **스파이** | 실제 객체에 대한 호출을 기록하는 래퍼 | 부분 검증 |
| **가짜** | 단순화되었지만 작동하는 구현 | 테스트용 인메모리 데이터베이스 |
| 모의도서관 | 언어 |
|---|---------|
| **unittest.mock** | 파이썬 |
| **농담** | 자바스크립트/타입스크립트 |
| **모키토** | 자바 |
| **모크** | C# |
| **증언 / 조롱** | 이동 |

## 통합 테스트
여러 구성요소가 어떻게 함께 작동하는지 테스트합니다.
| 테스트 대상 | 예 |
|---------------|---------|
| **데이터베이스 쿼리** | ORM이 올바른 SQL을 생성합니까? 인덱스가 사용됩니까? |
| **API 엔드포인트** | 전체 요청-응답 주기가 작동합니까? |
| **서비스 상호 작용** | 서비스 A가 서비스 B를 올바르게 호출합니까? |
| **외부 종속성** | 지불 게이트웨이 통합이 작동합니까? |
### 전략
| 전략 | 설명 | 트레이드오프 |
|----------|-------------|----------|
| **실제 종속성** | 실제 데이터베이스, 실제 메시지 대기열 사용 | 가장 현실적입니다. 더 느리게; 설정하기가 더 어렵습니다 |
| **테스트 컨테이너** | 각 테스트 실행에 대해 Docker 컨테이너 가동 | 좋은 균형; 재현 가능 |
| **인메모리 대안** | PostgreSQL 대신 H2; 인메모리 메시지 버스 | 빠른; 실제 문제를 놓칠 수 있음 |
| **계약 테스트** | 서비스가 API 계약을 준수하는지 확인 | 인터페이스 변경 사항 포착 |
---

## 엔드투엔드(E2E) 테스트
사용자 관점에서 전체 시스템을 테스트합니다.
| 도구 | 유형 | 최고의 대상 |
|------|------|----------|
| **극작가** | 브라우저 자동화 | 웹 애플리케이션 크로스 브라우저 |
| **사이프러스** | 브라우저 자동화 | 웹 애플리케이션 개발자 경험 |
| **셀레늄** | 브라우저 자동화 | 유산; 광범위한 언어 지원 |
| **디톡스** | 모바일 E2E | 네이티브 앱 반응 |
| **애피움** | 모바일 E2E | 네이티브 및 하이브리드 모바일 앱 |
| **마에스트로** | 모바일 E2E | 모바일 앱; 간단한 YAML 구문 |
| **k6 / 메뚜기** | 부하 테스트 | 부하 시 성능 |
### E2E 모범 사례
| 연습 | 왜 |
|------------|-----|
| **중요 경로만 테스트** | E2E 테스트는 느립니다. 가장 중요한 것에 집중 |
| **테스트 데이터 팩토리 사용** | 프로그래밍 방식으로 테스트 데이터를 생성합니다. 시드 데이터에 의존하지 마세요 |
| **테스트 후 정리** | 각 테스트는 시스템을 알려진 상태로 유지해야 합니다 |
| **UI 세부정보 테스트 방지** | CSS 클래스나 요소 위치가 아닌 테스트 동작 |
| **CI에서 실행** | E2E 테스트는 모든 변경 시 자동으로 실행되어야 합니다 |

## 테스트 주도 개발(TDD)
먼저 테스트를 작성한 다음 테스트를 통과하는 코드를 작성하세요.
| 단계 | 설명 |
|------|-------------|
| **1. 레드** | 원하는 동작을 설명하는 실패한 테스트 작성 |
| **2. 그린** | 테스트를 통과하기 위한 최소 코드 작성 |
| **3. 리팩터링** | 테스트를 녹색으로 유지하면서 코드 정리 |
| 혜택 | 설명 |
|---------|-------------|
| **디자인 피드백** | 테스트를 통해 구현 전에 인터페이스에 대해 생각하게 됩니다 |
| **회귀 안전성** | 모든 버그는 테스트를 거칩니다. 버그는 결코 돌아올 수 없습니다 |
| **문서** | 테스트는 예상되는 동작에 대한 살아있는 문서 역할을 합니다 |
| **신뢰** | 높은 테스트 적용 범위로 두려움 없는 리팩토링 가능 |
---

## 행동 중심 개발(BDD)
BDD는 사용자 관점에서 동작을 설명하는 테스트를 자연어로 작성하여 TDD를 확장합니다.
### 주어진-때-다음 형식
```
Given a user with an empty shopping cart
When they add a "Python Book" priced at $29.99
Then the cart total should be $29.99
And the cart should contain 1 item
```

| 도구 | 언어 |
|------|----------|
| **오이** | Java, JavaScript, Ruby 등 |
| **행동** | 파이썬 |
| **스펙플로우** | C# |
| **농담**(설명/it 포함) | 자바스크립트 |
---

## 기타 테스트 유형
| 유형 | 테스트 대상 | 도구 |
|------|--------------|-------|
| **성능/부하** | 로드 시 시스템 동작 | k6, JMeter, 로커스트, 개틀링 |
| **보안** | 취약점 및 공격 벡터 | OWASP ZAP, Burp Suite, Snyk |
| **접근성** | WCAG 준수 | 도끼, 등대, pa11y |
| **계약** | 서비스 간 API 호환성 | Pact, 스프링 클라우드 계약 |
| **돌연변이** | 테스트 스위트 자체의 품질 | 스트라이커, mutmut, PIT |
| **시각적 회귀** | 버전 간 UI 변경 | 퍼시, 크로매틱, BackstopJS |
| **혼돈** | 장애에 대한 시스템 복원력 | 카오스 몽키, 리트머스, 그렘린 |
| **연기** | 배포 후 기본 기능 | 사용자 정의 스크립트 건강검진 |
| **담그세요** | 장기간에 걸친 시스템 동작 | 장기 실행 부하 테스트 |

## 테스트 조직
| 패턴 | 설명 | 사용 시기 |
|---------|-------------|-------------|
| **공동 배치** | 테스트하는 코드 옆의 테스트(`src/utils.test.ts`) | 대부분의 프로젝트; 쉽게 찾을 수 |
| **별도의 디렉토리** |`tests/`또는`__tests__/`폴더에서 테스트 | 대규모 프로젝트; 명확한 분리 |
| **테스트 설비** |`fixtures/`디렉터리의 공유 테스트 데이터 | 여러 테스트에 동일한 데이터가 필요한 경우 |
| **테스트 유틸리티** |`test-utils/`디렉터리의 공유 도우미 | 설정 로직이 복잡한 경우 |

## 코드 적용 범위
| 미터법 | 측정 대상 | 제한사항 |
|---------|----|------------|
| **라인 커버리지** | 테스트에 의해 실행된 코드 줄의 비율 | 주장의 품질을 측정하지 않습니다 |
| **지점 적용 범위** | 취해진 분기 비율(if/else) | 라인 커버리지보다 낫습니다. 여전히 모든 버그를 잡을 수는 없습니다 |
| **경로 적용 범위** | 취해진 실행 경로의 비율 | 가장 철저한; 복잡한 코드의 지수 |
| **돌연변이 점수** | 테스트를 통해 발견된 돌연변이 비율 | 테스트 품질의 최선의 척도 |
**목표**: 80% 회선 적용 범위가 합리적인 기본값입니다. 그러나 적용 범위는 목표가 아니라 가이드입니다. 약한 주장을 포함하는 100% 적용 범위는 철저한 테스트를 통해 70% 적용 범위보다 나쁩니다.

## 지속적인 통합 및 테스트
| 연습 | 설명 |
|----------|-------------|
| **모든 커밋에서 모든 단위 테스트 실행** | 빠른 피드백; 즉시 회귀를 포착합니다 |
| **PR에 대한 통합 테스트 실행** | 단위 테스트에서 놓친 문제 포착 |
| **밤에 E2E 테스트를 실행하거나 메인에 병합할 때 실행** | 느리지만 철저하게 |
| **빠른 실패** | 시간을 절약하기 위해 첫 번째 실패 시 파이프라인을 중지 |
| **불안정한 테스트 정책** | 불안정한 테스트를 즉시 격리하거나 삭제하세요. 절대 무시하지 마세요 |
| **병렬화 테스트** | 테스트를 병렬로 실행하여 CI 시간 단축 |

## 실용적인 팁
- **테스트 이름을 명확하게 지정하세요.** `test_calculates_tax_for_high_earner`이(가) 무엇이 문제인지 알려줍니다.  `test_1`은(는) 아무 것도 알려주지 않습니다.
- **테스트당 하나의 어설션(실용적인 경우).** 오류를 쉽게 진단할 수 있습니다.
- **구현 세부 사항을 테스트하지 마세요.** 동작을 테스트하세요. 내부를 리팩터링하면 테스트가 중단되어서는 안 됩니다.
- **타사 코드 테스트를 피하세요.** 외부 라이브러리를 모의하세요. 코드와 코드의 상호 작용을 테스트하십시오.
- **테스트를 빠르게 수행하세요.** 테스트 도구 모음에 10분이 걸리면 개발자는 테스트 실행을 중단합니다. 끊임없이 최적화하세요.
- **데드 테스트를 삭제합니다.** 항상 통과하는 테스트 또는 제거된 코드를 테스트하는 테스트는 노이즈입니다.
- **테스트 코드를 프로덕션 코드처럼 취급합니다.** 읽기 쉽고 유지 관리가 가능하며 구조가 잘 구성되어 있어야 합니다.

## 요약
테스트는 선택 사항이 아닙니다. 중단되지 않는 소프트웨어를 구축하는 방법입니다. 테스트 피라미드는 여러 가지 빠른 단위 테스트, 일부 통합 테스트 및 몇 가지 E2E 테스트를 안내합니다. TDD와 BDD는 구조화된 접근 방식을 제공합니다. 모의는 테스트를 위해 단위를 격리합니다. 코드 적용 범위는 너비를 측정하지만 깊이는 측정하지 않습니다. 가장 중요한 원칙은 이것이다: 테스트되지 않으면 깨진 것입니다. 아직은 알 수 없습니다.
