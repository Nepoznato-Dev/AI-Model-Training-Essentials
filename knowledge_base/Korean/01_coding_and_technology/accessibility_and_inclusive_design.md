# 접근성과 포용적 디자인
접근성(흔히 a11y로 축약됨)은 시각, 청각, 운동, 인지 및 신경 장애가 있는 사람을 포함하여 모든 사람이 소프트웨어를 사용할 수 있도록 만드는 방식입니다. 이는 많은 관할권 및 표준 엔지니어링 관행에서 법적 요구 사항입니다. 접근성이 뛰어난 소프트웨어는 모든 사람을 위한 더 나은 소프트웨어입니다. 명확한 구조, 키보드 탐색, 충분한 대비, 읽기 쉬운 텍스트 등 장애가 있는 사용자를 지원하는 디자인 결정이 모든 사용자의 경험을 향상시키기 때문입니다.
---

## 접근성으로 혜택을 받는 사람은 누구인가요?
| 장애 유형 | 예 | 보조 기술 |
|---|---------|---------|
| **시각적** | 실명, 저시력, 색맹 | 스크린 리더(JAWS, NVDA, VoiceOver); 돋보기; 고대비 모드 |
| **청각** | 청각 장애, 난청 | 캡션; 성적표; 시각적 경고 |
| **모터** | 제한된 민첩성, 마비, 떨림 | 키보드 전용 탐색; 음성 제어; 스위치 장치; 시선 추적 |
| **인지** | 난독증, ADHD, 자폐증, 기억 장애 | 명확한 언어; 일관된 탐색; 산만함 감소 |
| **임시** | 부러진 팔, 밝은 햇빛, 시끄러운 환경 | 영구 장애와 동일한 편의 제공 |
| **상황에 따른** | 아기를 안고, 운전하고, 한 손으로 점유 | 음성 인터페이스; 대형 터치 타겟 |
**주요 정보**: 장애가 있는 사용자를 위해 설계된 접근성 기능은 모든 사람에게 도움이 됩니다. 연석(인도의 경사로)은 휠체어용으로 설계되었지만 유모차를 가지고 있는 부모, 카트를 가지고 있는 배달원, 수하물을 가지고 있는 여행자가 사용합니다.

## 웹 접근성(WCAG)
WCAG(웹 콘텐츠 접근성 지침)는 웹 접근성에 대한 국제 표준입니다.
### WCAG 원칙(POUR)
| 원리 | 요구사항 |
|------------|-------------|
| **인식 가능** | 정보는 사용자가 인식할 수 있는 방식으로 표시되어야 합니다(텍스트 대체, 캡션, 적응 가능한 레이아웃) |
| **작동 가능** | 인터페이스는 탐색 및 사용 가능해야 합니다(키보드 액세스 가능, 충분한 시간, 발작을 유발하는 콘텐츠 없음) |
| **이해할 수 있음** | 정보 및 조작은 이해 가능해야 합니다(읽기 가능, 예측 가능, 입력 지원) |
| **강건함** | 콘텐츠는 현재 및 미래의 보조 기술과 함께 작동해야 합니다 |
### WCAG 적합성 수준
| 레벨 | 요구사항 | 일반적인 대상 |
|-------|-------------|---------------|
| **아** | 최소 수준; 30가지 성공 기준 | 일부 관할권에서는 법적 최소값 |
| **AA** | 가장 일반적인 장벽을 해결합니다 | 대부분의 조직을 위한 표준 목표 |
| **아아아** | 최고 수준; 모든 콘텐츠가 이를 달성할 수 있는 것은 아닙니다 | 전문 콘텐츠; 교육 사이트 |
### 주요 성공 기준(AA 수준)
| 기준 | 요구사항 | 달성 방법 |
|------------|-------------|---------------|
| **1.1.1 텍스트가 아닌 콘텐츠** | 모든 이미지에는 대체 텍스트가 있습니다 | `alt`속성;  아이콘용`aria-label`|
| **1.3.1 정보 및 관계** | 프로그래밍 방식으로 전달되는 구조 | 시맨틱 HTML; 제목; 기울기; 랜드마크 |
| **1.4.3 대비(최소)** | 텍스트의 명암비는 최소 4.5:1 | 대비 체커로 테스트하세요. 접근 가능한 색상 팔레트 선택 |
| **1.4.4 텍스트 크기 조정** | 텍스트는 손실 없이 200%로 크기 조정 가능 | 상대 단위(rem, em)를 사용합니다. 반응형 디자인 |
| **2.1.1 키보드** | 키보드를 통해 모든 기능 사용 가능 | 키보드 트랩이 없습니다. 눈에 보이는 초점 표시기 |
| **2.4.3 초점 순서** | 초점 순서는 의미와 조작성을 보존합니다 | 논리적 탭 순서; DOM 순서가 시각적 순서와 일치 |
| **2.4.7 초점 표시** | 키보드 포커스가 시각적으로 표시됩니다 | CSS`:focus-visible`스타일; 교체 없이 `outline: none`를 사용하지 마세요 |
| **3.3.2 라벨 또는 지침** | 입력에는 레이블이 있습니다 | `<label>`요소; `aria-label`|
| **4.1.2 이름, 역할, 값** | UI 구성 요소에는 액세스 가능한 이름과 역할이 있습니다 | ARIA 속성; 시맨틱 HTML |

## ARIA(액세스 가능한 리치 인터넷 애플리케이션)
ARIA는 내장된 의미 체계가 없는 HTML 요소에 접근성 정보를 추가합니다.
### ARIA 역할
| 역할 | 목적 | 예 |
|------|---------|---------|
| `button`| 요소를 버튼으로 식별 | 버튼 스타일의`<div>`|
| `dialog`| 모달 또는 비모달 대화 상자 | 사용자 정의 모달 구성 요소 |
| `tablist`/`tab`/`tabpanel`| 탭 인터페이스 | 사용자 정의 탭 구성 요소 |
| `alert`| 동적으로 나타나는 중요한 메시지 | 오류 알림 |
| `progressbar`| 진행률 표시 | 로드 상태 |
| `menu`/`menuitem`| 메뉴 탐색 | 드롭다운 메뉴 |
### ARIA 속성
| 속성 | 목적 | 예 |
|------------|---------|---------|
| `aria-label`| 표시되는 텍스트가 없을 때 액세스 가능한 이름 | 아이콘 전용 버튼:`aria-label="Search"`|
| `aria-describedby`| 요소를 설명에 연결 | 도움말 텍스트가 포함된 양식 필드 |
| `aria-expanded`| 섹션이 확장되었는지 여부를 나타냅니다 | 아코디언; 드롭다운 |
| `aria-hidden`| 보조 기술에서 요소를 숨깁니다 | 장식 아이콘 |
| `aria-live`| 동적 콘텐츠 변경 사항 발표 | 실시간 업데이트; 알림 |
| `aria-disabled`| 요소가 비활성화되었음을 나타냅니다 | 회색으로 표시된 버튼 |
### ARIA의 첫 번째 규칙
> **네이티브 HTML을 대신 사용할 수 있다면 ARIA를 사용하지 마세요.** `<button>`는 이미 액세스 가능합니다. `<div role="button">`를 사용하려면 키보드 처리, 포커스 관리 및 화면 판독기 지원을 수동으로 추가해야 합니다. 의미론적 HTML을 먼저 사용하십시오. ARIA는 기본 요소가 작업을 수행할 수 없는 경우에만 가능합니다.

## 키보드 탐색
| 열쇠 | 예상되는 동작 |
|------|------|
| **탭** | 다음 대화형 요소로 초점 이동 |
| **Shift + Tab** | 이전 대화형 요소로 포커스 이동 |
| **Enter / 스페이스바** | 포커스가 있는 요소(버튼, 링크) 활성화 |
| **화살표 키** | 구성 요소(메뉴, 탭, 라디오 그룹) 내에서 탐색 |
| **탈출** | 대화상자, 메뉴 또는 팝오버 닫기 |
| **홈 / 끝** | 목록의 첫 번째/마지막 항목으로 이동 |
### 일반적인 키보드 트랩
| 문제 | 수정 |
|---------|-----|
| 포커스가 구성 요소에 들어가지만 나갈 수 없습니다. | Tab이 초점을 밖으로 이동하는지 확인하세요. 탈출 처리 |
| 모달은 포커스를 트랩하지 않습니다 | 초점은 모달 내에서 순환되어야 합니다. 닫으면 트리거로 돌아가기 |
| 사용자 정의 구성 요소가 키보드에 응답하지 않습니다 | Enter, Space, 화살표에 대한 keydown 핸들러 추가 |

## 색상 및 시각 디자인
| 지침 | 요구사항 |
|------------|-------------|
| **명암비** | 일반 텍스트의 경우 4.5:1; 큰 텍스트의 경우 3:1(굵게 18pt 이상 또는 14pt 이상) |
| **색상에만 의존하지 마세요** | 색상 외에 아이콘, 텍스트 또는 패턴 사용 |
| **초점 지표** | 항상 표시됩니다. 고대비; 교체 없이 제거되지 않음 |
| **텍스트 크기 조정** | 레이아웃은 200% 확대/축소에서 작동해야 합니다 |
| **반응형** | 콘텐츠는 320px 너비로 리플로우되어야 합니다(모바일) |
### 색맹 고려 사항
| 유형 | 영향을 받는 색상 | 디자인 팁 |
|------|----|------------|
| **녹색맹** | 빨간색-녹색(가장 일반적) | 상태를 전달하기 위해 빨간색/녹색을 사용하지 마세요. 아이콘 + 색상 사용 |
| **황색맹** | 빨강-녹색 | 위와 동일 |
| **삼맹맹** | 파란색-노란색 | 파란색/노란색을 유일한 차별화 요소로 사용하지 마세요 |

## 접근성 테스트
| 방법 | 도구 | 무엇을 잡는가 |
|---------|------|---|
| **자동 스캔** | 도끼, 등대, WAVE | 대체 텍스트가 누락되었습니다. 대비 문제; ARIA 오류 |
| **키보드 테스트** | 수동: 마우스를 분리하고 키보드만 사용 | 초점 순서; 키보드 트랩; 누락된 핸들러 |
| **스크린 리더 테스트** | NVDA(무료), VoiceOver(macOS), JAWS | 라벨이 누락되었습니다. 구조가 좋지 않음; 예고되지 않은 변경 |
| **줌 테스트** | 브라우저 확대/축소 200%, 400% | 레이아웃 파손; 잘린 텍스트; 오버플로 문제 |
| **색상 대비** | WebAIM 대비 검사기, Stark 플러그인 | 불충분한 명암비 |
| **사용자 테스트** | 비활성화된 사용자를 대상으로 테스트 | 자동화 도구가 놓친 실제 장벽 |

## 요약
접근성은 끝에 추가되는 기능이 아니라 처음부터 모든 결정을 알려야 하는 디자인 원칙입니다. 시맨틱 HTML을 사용하세요. 키보드 탐색이 작동하는지 확인하세요. 충분한 색상 대비를 유지하십시오. 텍스트가 아닌 콘텐츠에 대한 대체 텍스트를 제공하세요. 화면 판독기와 비활성화된 사용자를 대상으로 테스트합니다. 그 결과 일시적인 장애, 상황적 제한, 오래된 장치, 느린 연결, 실제 사용이 통제된 개발 환경과 다른 여러 면을 포함하여 모든 사람에게 더 잘 작동하는 소프트웨어가 탄생했습니다.
