# API 설계 및 통합 실패
API(애플리케이션 프로그래밍 인터페이스)는 현대 소프트웨어의 연결 조직입니다. 이를 통해 서비스가 통신하고, 제3자가 통합하고, 팀이 독립적으로 작업할 수 있습니다. API 설계가 잘못되면 이에 의존하는 모든 시스템에 결과가 파급됩니다. 즉, 통합 중단, 보안 취약성, 개발자 불만, 비용이 많이 드는 재작성 등이 있습니다. 시스템이 안정적으로 통신할 수 없는 통합 실패는 생산 사고의 가장 일반적인 원인 중 하나입니다.
---

## 일반적인 API 설계 실패
### 디자인 실수
| 실수 | 설명 | 결과 |
|---------|-------------|-------------|
| **일관되지 않은 명명** | `/getUsers`대`/list_users`대`/fetch-users`| 착란; 오류; 느린 개발 |
| **오버로드된 엔드포인트** | 매개변수를 기반으로 10가지 다른 작업을 수행하는 하나의 엔드포인트 | 이해하기 어렵습니다. 테스트하기 어렵다; 변경하기 어렵다 |
| **과소평가** | 클라이언트는 관련 데이터를 얻기 위해 5번의 API 호출을 수행해야 합니다 | 느린; 낭비적이다; 복잡한 클라이언트 코드 |
| **과잉** | 클라이언트에 2개만 필요한 경우 API는 모든 필드를 반환 | 낭비되는 대역폭 모바일에서는 느림; 보안 위험(불필요한 데이터 노출) |
| **버전 관리 없음** | 경고 없이 배포된 주요 변경 사항 | 클라이언트가 중단됩니다. 화난 개발자 |
| **모호한 오류 메시지** | 세부정보가 없는 "오류 500: 내부 서버 오류" | 디버깅이 불가능합니다. 느린 해상도 |
| **페이지 매김 누락** | 엔드포인트는 모든 레코드를 반환합니다(수백만 개일 수 있음) | 시간 초과; 기억력 고갈; 충돌한 클라이언트 |
| **일관되지 않은 상태 코드** | 오류의 경우 200 OK; 고객 실수에 대해 500 | 클라이언트는 성공과 실패를 구별할 수 없습니다 |
### REST API 안티 패턴
| 안티 패턴 | 설명 | 더 나은 접근 방식 |
|-------------|-------------|----|
| **변이에 GET 사용** | `GET /delete-user?id=5`| DELETE 메소드 사용 |
| **모든 것에 POST 사용** | `POST /get-users`; `POST /update-user`| 적절한 HTTP 메소드(GET, POST, PUT, PATCH, DELETE) 사용 |
| **API에서 HTML 반환** | API는 HTML 조각을 반환합니다 | JSON을 반환합니다. 클라이언트가 렌더링하도록 허용 |
| **URL의 비즈니스 로직** | `/users/active/premium/from-2023`| 복잡한 필터에 쿼리 매개변수 또는 요청 본문 사용 |
| **데이터베이스 스키마 노출** | `/api/table_name/column`| 테이블이 아닌 리소스 및 도메인 개념을 중심으로 API 설계 |
| **HATEOAS/링크 없음** | 클라이언트가 모든 URL을 하드코딩합니다 | 응답에 관련 리소스에 대한 링크 포함 |

## 보안 실패
### 일반적인 API 취약점
| 취약점 | 설명 | 예 |
|---------------|-------------|---------|
| **깨진 인증** | API가 신원을 제대로 확인하지 않음 | 토큰 유효성 검사가 누락되었습니다. 만료된 토큰 허용 |
| **과도한 데이터 노출** | API는 클라이언트가 필요로 하는 것보다 더 많은 데이터를 반환합니다 | 사용자 엔드포인트가 비밀번호 해시 및 내부 ID를 반환합니다. |
| **대량배정** | 클라이언트는 설정해서는 안 되는 필드를 설정할 수 있습니다 |  `PATCH /user`를 사용하면 `role: "admin"`를 설정할 수 있습니다.
| **주사** | 코드로 해석되는 사용자 입력 | SQL 주입; NoSQL 주입; 명령 주입 |
| **IDOR**(안전하지 않은 직접 개체 참조) | URL의 ID를 변경하여 리소스에 액세스 | `/api/users/5`→ 다른 사람의 데이터를 보려면 `/api/users/6`로 변경 |
| **속도 제한 누락** | API 호출에 제한 없음 | 무차별 대입; 서비스 거부; 긁어내기 |
| **CORS 구성 오류** | 과도하게 허용되는 교차 출처 액세스 |  인증된 엔드포인트의`Access-Control-Allow-Origin: *`|
### 인증 및 승인 실패
| 실패 | 설명 | 영향 |
|---------|-------------|---------|
| **하드코딩된 자격 증명** | 소스 코드의 API 키 또는 비밀번호 | 버전 관리를 통해 유출되었습니다. 모든 개발자가 접근 가능 |
| **토큰 만료 없음** | 토큰은 만료되지 않습니다 | 도난당한 토큰은 영구적인 액세스를 제공합니다 |
| **취약한 비밀 키** | 짧거나 예측 가능한 서명 키 | 토큰은 위조될 수 있습니다 |
| **범위/권한 없음** | 모든 토큰에는 전체 액세스 권한이 있습니다 | 손상된 토큰 = 전체 시스템 액세스 |
| **민감한 데이터 로깅** | 로그의 토큰 또는 비밀번호 | 로그 액세스 권한이 있는 사람은 누구나 액세스 가능 |
| **일관되지 않은 승인** | 일부 엔드포인트는 권한을 확인합니다. 다른 사람들은 그렇지 않습니다 | 보호되지 않은 엔드포인트를 통한 무단 액세스 |

## 통합 실패
### 분산 시스템 통합 문제
| 실패 | 설명 | 예 |
|---------|-------------|---------|
| **단단한 결합** | 서비스는 서로의 내부 구현 세부 사항에 따라 다릅니다. | 한 서비스의 데이터베이스를 변경하면 다른 서비스 3개가 중단됩니다 |
| **동기 체인** | 서비스 A는 B를 호출하고 C는 D를 호출합니다. 지연 시간이 누적됨 | 200ms + 300ms + 500ms = 응답 시간 1초 |
| **회로 차단기 없음** | 서비스 실패로 인해 계단식 오류 발생 | 서비스 D는 느립니다. 모든 업스트림 서비스는 대기 중인 스레드를 소진합니다 |
| **재시도 로직 없음** | 일시적인 실패가 영구적이 됩니다 | 네트워크 블립 = 거래 실패; 사용자가 수동으로 다시 시도해야 함 |
| **과도한 재시도** | 백오프 없이 재시도하면 복구 서비스가 압도됨 | 천둥소리가 나는 무리 문제 |
| **멱등성 없음** | 비멱등성 작업을 재시도하면 중복이 생성됩니다. | 결제 금액이 두 번 청구되었습니다. 주문이 두 번 생성됨 |
| **최종 일관성의 놀라움** | 클라이언트가 쓰기 후 오래된 데이터를 읽습니다. | 사용자가 프로필을 업데이트합니다. 페이지를 새로 고칩니다. 이전 데이터가 계속 표시됨 |
### 타사 통합 실패
| 실패 | 설명 | 완화 |
|---------|-------------|------------|
| **공급업체 API 변경** | 제3자가 예고 없이 API를 변경함 | 버전 고정; 추상화 계층; 공급업체 변경 로그 모니터링 |
| **속도 제한** | 제3자가 귀하의 요청을 제한합니다 | 캐싱; 요청 대기열; 더 높은 한도 협상 |
| **공급업체 가동 중지 시간** | 타사 서비스를 사용할 수 없습니다 | 회로 차단기; 대체 동작; 다중 공급업체 전략 |
| **데이터 형식 변경** | 타사 변경 응답 형식 | 스키마 유효성 검사 변환층; 형식 변경에 대한 경고 |
| **마이그레이션 경로 없이 지원 중단** | 공급업체는 이에 상응하는 엔드포인트가 없는 엔드포인트를 더 이상 사용하지 않습니다. 최신 정보를 받아보세요. 추상화를 유지합니다. 마이그레이션을 조기에 계획 |

## 사례 연구
### 사례 연구 1: 모든 것을 반환하는 API
| 측면 | 설명 |
|---------|-------------|
| **시나리오** | SaaS 회사의 사용자 API가 내부 메타데이터를 포함한 모든 사용자 필드를 반환했습니다.
| **무엇이 잘못됐나요** | 필드 필터링이 없습니다. 응답에 비밀번호 해시, 내부 메모 및 관리자 플래그가 포함됨 |
| **영향** | 보안 연구원들이 노출을 발견했습니다. 공개; GDPR 조사 |
| **근본 원인** | 필터링 없이 전체 데이터베이스 모델을 직렬화하는 API |
| **수정** | 명시적 응답 모델 필드 수준 액세스 제어; 모든 엔드포인트에 대한 보안 검토 |
| **강의** | API를 통해 직접 데이터베이스 모델을 노출하지 마십시오. DTO(데이터 전송 개체) 사용 |
### 사례 연구 2: 계단식 실패
| 측면 | 설명 |
|---------|-------------|
| **시나리오** | 동기식 서비스 간 통신을 갖춘 마이크로서비스 아키텍처 |
| **무엇이 잘못됐나요** | 한 서비스에서는 데이터베이스 속도 저하가 발생했습니다. 업스트림 서비스가 응답을 기다렸습니다. 스레드 풀이 소진되었습니다 |
| **영향** | 45분 동안 전체 시스템 중단; 영향을 받는 모든 서비스 |
| **근본 원인** | 회로 차단기가 없습니다. 시간 초과 없음; 동기 종속성 체인 |
| **수정** | 회로 차단기; 시간 초과; 가능한 경우 비동기 통신; 격벽 |
| **강의** | 서비스 간 동기 호출은 취약한 체인을 생성합니다. 실패를 위한 디자인 |

## 모범 사례
### API 디자인 체크리스트
| 면적 | 연습 |
|------|----------|
| **명명** | 자원에는 명사를 사용하십시오. 작업을 위한 HTTP 메서드 일관된 명명 규칙 |
| **버전 관리** | 첫날부터의 버전; URL 버전 관리(`/v1/`) 또는 헤더 버전 관리 사용 |
| **페이지 매김** | 항상 목록 끝점에 페이지를 매깁니다. 대규모 데이터 세트에 커서 기반 페이지 매김 사용 |
| **오류 처리** | 일관된 오류 형식; 오류 코드를 포함합니다. 실행 가능한 메시지 제공 |
| **속도 제한** | 비율 제한을 구현합니다. 재시도 헤더와 함께 429를 반환 |
| **멱등성** | 돌연변이 엔드포인트에 대한 멱등성 키 지원 |
| **문서** | OpenAPI/Swagger 사양; 계속 업데이트하세요. 예시 제공 |
| **테스트** | 계약 테스트 통합 테스트; 소비자 중심 계약 테스트 |
| **모니터링** | 대기 시간을 추적합니다. 오류율; 처리량; 의존성 상태 |
| **지원 중단** | 지원 중단을 미리 공지하세요. 마이그레이션 가이드 제공 |

## 요약
API 설계 실패의 범위는 외관상(일관되지 않은 이름 지정)부터 치명적인(보안 취약성, 계단식 오류)까지 다양합니다. 가장 흔한 설계 실수(엔드포인트 오버로드, 과도한 가져오기, 페이지 매김 누락, 모호한 오류)로 인해 API를 사용하고 유지 관리하기가 어렵습니다. 인증 실패, IDOR, 대량 할당, 과도한 데이터 노출 등의 보안 실패로 인해 시스템이 공격에 노출됩니다. 긴밀한 결합, 동기식 체인, 회로 차단기 누락, 멱등성 없음 등의 통합 오류로 인해 하나의 오류가 서비스 전체에 걸쳐 이어지는 취약한 시스템이 생성됩니다. 타사 통합은 API 변경, 속도 제한, 공급업체 가동 중지 시간 등 외부 위험을 추가합니다. 예방 전략은 잘 확립되어 있습니다. 명시적인 대응 모델을 사용합니다. 첫날부터 버전; 회로 차단기 및 시간 초과를 구현합니다. 멱등성을 위한 설계; 모든 입력을 검증하고 정리합니다. 모든 것을 모니터링하십시오. API 계약을 변경하려면 조정이 필요한 구속력 있는 계약으로 취급합니다. 최고의 API는 지루합니다. 예측 가능하고 일관되며 잘 문서화되어 있고 실패에 대한 복원력이 뛰어납니다.
