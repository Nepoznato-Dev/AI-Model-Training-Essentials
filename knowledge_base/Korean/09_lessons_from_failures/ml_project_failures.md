# 머신러닝 프로젝트 실패
기계 학습 프로젝트는 놀라운 속도로 실패합니다. 업계 추정에 따르면 ML 프로젝트의 60~85%는 프로덕션에 도달하지 못합니다. 실패는 일반적으로 알고리즘에 있지 않습니다. 그것은 프로세스, 데이터, 기대, 조직적 맥락에 있습니다. ML 시스템을 구축하는 모든 사람에게는 ML 프로젝트가 실패하는 이유를 이해하는 것이 필수적입니다. 실패 모드는 예측 가능하고 대부분 피할 수 있기 때문입니다.
---

## ML 프로젝트가 실패하는 이유
### 실패 카테고리
| 카테고리 | 실패율 | 설명 |
|------------|------|-------------|
| **데이터 문제** | ~30% | 데이터가 부족하거나 편향되어 있거나 오래되었거나 접근이 불가능함 |
| **문제 정의** | ~20% | ML 문제가 비즈니스 요구와 일치하지 않습니다 |
| **기대 불일치** | ~15% | 이해관계자들은 마법을 기대합니다. 현실은 점진적인 개선이다 |
| **배포 실패** | ~15% | 모델은 노트북에서 작동하지만 생산할 수는 없습니다 |
| ** 조직적 문제** | ~10% | 명확한 소유권이 없습니다. 팀의 기술이 부족합니다. 경영진 지원 없음 |
| **모델 성능** | ~10% | 모델이 필요한 정확도를 달성하지 못하거나 잘못 일반화함 |
---

## 데이터 관련 오류
### 일반적인 데이터 문제
| 문제 | 설명 | 예 |
|---------|-------------|---------|
| **데이터가 부족함** | 의미 있는 패턴을 학습하기에는 예제가 충분하지 않습니다 | 500개 거래에 대한 사기 탐지 모델 훈련 |
| **라벨 품질** | 훈련 라벨이 잘못되었거나 일관성이 없거나 주관적임 | 비전문가가 라벨링한 의료 이미지 평가자 간 일치도가 낮은 감정 라벨 |
| **데이터 유출** | 미래 또는 대상의 정보가 기능으로 누출됨 | 고객 이탈 결과를 기능으로 활용 훈련에 테스트 데이터 포함 |
| **선택 편향** | 훈련 데이터가 배포 인구를 나타내지 않습니다 | 한 병원의 데이터를 기반으로 의료 모델을 훈련합니다. 전국적으로 배포 |
| **콘셉트 드리프트** | 시간이 지남에 따라 기능과 대상 변경 사이의 관계 | 팬데믹 이후 소비자 행동 변화; 팬데믹 이전 데이터로 훈련된 모델 |
| **기능 불일치** | 교육 중에 사용할 수 있는 기능은 프로덕션에서 사용할 수 있는 기능과 다릅니다 | 수동 라벨을 사용한 교육 생산에서는 유통 방식이 다른 자동화 라벨을 사용합니다 |
| **계급 불균형** | 대상 클래스가 매우 편향되어 있습니다 | 99% 부정, 1% 긍정; 모델은 항상 부정적인 예측을 학습합니다 |
### 데이터 유출 문제
| 유형 | 설명 | 예 |
|------|-------------|---------|
| **대상 유출** | 기능은 대상이 발생한 후에만 사용할 수 있습니다 | "치료 성공"을 예측하는 특성으로 사용되는 "치료 결과" |
| **열차 테스트 오염** | 테스트 데이터가 훈련에 영향을 미침 | 전역 통계(테스트 데이터 포함)로 확장 유출되는 데이터 확대 |
| **샘플링 편향** | 교육 및 생산에서는 서로 다른 샘플링을 사용합니다 | 웹 트래픽 교육 모바일 앱 트래픽에 배포 |
| **전처리 누출** | 전처리 단계에서는 전체 데이터 세트의 정보를 사용합니다 | 전체 평균(테스트 데이터 포함)으로 결측값 대치 |
---

## 문제 정의 실패
### 정렬 불량 패턴
| 패턴 | 설명 | 결과 |
|---------|-------------|-------------|
| **잘못된 문제 해결** | 비즈니스 요구사항 X; 팀 빌드 Y | 모델은 기술적으로 훌륭하지만 쓸모가 없습니다 |
| **규칙이 충분할 경우 ML** | 문제에는 결정론적인 규칙이 있습니다. ML이 복잡성을 더하다 | 과도하게 설계되었습니다. 유지하기가 더 어렵습니다. 해석이 덜됨 |
| **데이터가 존재하지 않는 경우의 ML** | 문제에는 수집되지 않은 데이터가 필요합니다 | 프로젝트를 시작할 수 없습니다. 타당성에 낭비되는 개월 |
| **비즈니스 맥락이 없는 정확도 목표** | "우리는 95%의 정확도가 필요합니다" — 이것이 비즈니스에 어떤 의미가 있습니까? | 모델이 정확성을 충족하지만 비즈니스 문제를 해결하지 못함 |
| **오류 비용 무시** | 거짓 긍정과 거짓 부정의 비용은 다릅니다 | 모델이 잘못된 측정항목을 최적화함 |
| **기준 없음** | 기존 접근 방식과 비교 불가 | ML이 실제로 단순한 경험적 방법보다 나은지 알 수 없음 |

## 기대 실패
### ML 프로젝트의 과대광고 주기
| 단계 | 설명 | 위험 |
|-------|-------------|------|
| **흥미** | "AI가 모든 것을 해결해 드립니다!" | 지나치게 유망한; 자원 부족 |
| **개념 증명** | 모델은 노트북의 깨끗한 데이터에서 작동합니다 | 거짓된 자신감; "작동해요!" |
| **현실점검** | 생산 데이터가 지저분합니다. 성능 저하 | 실망; "ML이 작동하지 않습니다" |
| **죽음의 행진** | 팀은 이를 강제로 프로덕션에 적용하려고 합니다 | 기술 부채 소진 |
| **포기 또는 자동 배포** | 모니터링 없이 프로젝트가 취소되거나 배포됨 | 낭비된 투자 |
### 기대 관리
| 전략 | 설명 |
|----------|-------------|
| **기준으로 시작** | 가장 간단한 가능한 접근 방식(규칙, 인간 성과)과 비교 |
| **성공 지표를 미리 정의** | ML 지표(정확도, F1)뿐만 아니라 비즈니스 지표(수익, 비용 절감) |
| **타임박스 탐색** | 커밋하기 전에 팀에게 2~4주 동안 타당성을 평가할 시간을 주세요 |
| **ML이 할 수 없는 작업 보여주기** | 한계에 대해 솔직해지세요. 현실적인 기대치를 설정 |
| **점진적으로 반복** | 먼저 간단한 모델을 배포하세요. 반복적으로 개선 |
| **오류 비용의 수량화** | 모델 성능을 비즈니스 영향으로 전환 |
---

## 배포 실패
### 모델이 프로덕션에 참여하지 못하는 이유
| 문제 | 설명 | 솔루션 |
|---------|-------------|----------|
| **노트북과 생산 격차** | 코드는 Jupyter에서 작동하지만 프로덕션 준비가 되어 있지 않습니다. | MLOps 관행 ML용 CI/CD; 코드 리뷰 |
| **지연 시간 요구사항** | 모델 추론이 실시간 사용에 너무 느림 | 모델 최적화; 양자화; 캐싱 |
| **확장성** | 모델이 프로덕션 트래픽을 처리할 수 없음 | 일괄 처리; 수평적 스케일링; 모델 서비스 인프라 |
| **간격 모니터링** | 모델 성능 저하를 감지할 방법이 없음 | 데이터 드리프트 모니터링 성능 모니터링; 경고 |
| **종속성 관리** | 교육 및 서비스 환경이 다릅니다 | 컨테이너화; 재현 가능한 환경 |
| **롤백 계획 없음** | 새 모델 실패 시 이전 모델로 되돌릴 수 없음 | 모델 등록; 버전 관리; 자동 롤백 |
### 모델 붕괴
| 유형 | 설명 | 감지 |
|------|-------------|------------|
| **데이터 드리프트** | 입력 특성 분포 변경 | 기능 통계를 모니터링합니다. KL 발산; PSI |
| **콘셉트 드리프트** | 기능과 대상 변경 간의 관계 | 시간 경과에 따른 예측 정확도 모니터링 |
| **라벨 드리프트** | 대상 변경의 정의 또는 분포 | 라벨 배포를 추적합니다. 비즈니스 측정항목 상관관계 |
| **업스트림 변경** | 데이터 소스가 형식, 타이밍 또는 품질을 변경함 | 스키마 유효성 검사 신선도 모니터링 |

## 조직의 실패
| 실패 | 설명 | 예방 |
|---------|-------------|------------|
| **명확한 소유권 없음** | 누구도 생산 중인 모델에 대해 책임을 지지 않습니다 | 모델 소유자를 할당합니다. RACI 정의 |
| **사일로화된 팀** | 데이터 과학자는 모델을 구축합니다. 엔지니어가 배포합니다. 아무도 의사소통을 하지 않는다 | 다기능 팀 공유된 목표 |
| **MLOps 성숙도 없음** | 모델 등록이 없습니다. CI/CD가 없습니다. 모니터링 없음 | MLOps 인프라에 점진적으로 투자 |
| **비현실적인 일정** | "2주 만에 프로덕션 ML 시스템 구축" | 타임박스 탐색; 반복하다; 복잡성을 전달 |
| **도메인 전문성 부족** | ML팀이 비즈니스 문제를 이해하지 못함 | ML 팀에 도메인 전문가 포함 |
| **평가 프레임워크 없음** | 모델이 프로덕션에서 작동 중인지 알 수 없음 | 비즈니스 지표를 정의합니다. 대시보드 설정 정기 리뷰 |

## 배운 교훈
### ML 프로젝트 체크리스트
| 단계 | 주요 질문 |
|-------|-------------|
| **문제 정의** | 이것이 실제로 ML 문제인가요? 기준은 무엇입니까? 성공은 어떤 모습인가요? |
| **데이터 평가** | 데이터가 충분합니까? 대표인가요? 라벨은 신뢰할 수 있나요? |
| **타당성** | 2~4주 안에 작동하는 프로토타입을 만들 수 있나요? 위험은 무엇입니까? |
| **개발** | 데이터 유출이 있나요? 우리는 올바른 평가 지표를 사용하고 있나요? |
| **사전 제작** | 프로덕션 데이터에서도 작동하나요? 충분히 빠른가요? 모니터링되나요? |
| **배포** | 롤백할 수 있나요? 통화 중인 사람은 누구인가요? 품질이 저하되면 어떻게 되나요? |
| **배포 후** | 드리프트를 모니터링하고 있나요? 비즈니스 측정항목이 추적되나요? 재교육 계획이 있나요? |
---

## 요약
ML 프로젝트가 실패하는 이유는 알고리즘이 너무 어려워서가 아니라 주변 프로세스가 손상되었기 때문입니다. 데이터 문제(불충분한 데이터, 잘못된 레이블, 누출, 드리프트)가 실패의 가장 큰 부분을 차지합니다. 문제 정의 실패 - 잘못된 문제 해결, 규칙이 충분할 때 ML 사용, 오류 비용 무시 등은 수개월의 노력을 낭비합니다. 과도한 기대, 미흡한 전달, 이해관계자 관리 미흡 등의 기대 실패는 ML에 대한 조직의 신뢰를 파괴합니다. 배포 실패(노트북과 프로덕션 간 격차, 대기 시간 문제, 모니터링 없음)는 개발 중인 모델이 프로덕션에서 가치를 창출하지 못한다는 것을 의미합니다. 소유권 없음, 고립된 팀, MLOps 없음 등 조직의 실패로 인해 구조적으로 성공이 불가능해집니다. 해독제는 규율 있는 실천입니다. 기준선부터 시작하세요. 타임박스 탐색; 데이터를 엄격하게 검증합니다. 누출 여부를 확인하십시오. 비즈니스 지표를 정의합니다. 점진적으로 배포합니다. 지속적으로 모니터링합니다. 그리고 반복합니다. 최고의 ML 팀은 모델보다 데이터와 프로세스에 더 많은 시간을 소비합니다.
