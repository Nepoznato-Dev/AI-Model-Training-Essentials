# 데이터 파이프라인 및 ETL 오류
데이터 파이프라인은 현대 조직의 배관입니다. 데이터 파이프라인은 변환을 통해 원본 시스템의 데이터를 분석, 기계 학습 및 의사 결정에 사용되는 데이터베이스, 웨어하우스 및 레이크로 이동합니다. 그들이 일할 때는 아무도 눈치 채지 못합니다. 실패하면 오래된 데이터에 대한 결정이 내려지고, 모델은 쓰레기에 대해 훈련되고, 보고서에는 불가능한 숫자가 표시되며, 전체 데이터 플랫폼에 대한 신뢰가 약화됩니다. 데이터 파이프라인 오류는 기술 조직에서 가장 흔하고 비용이 많이 드는 오류 중 하나입니다.
---

## 일반적인 실패 모드
### 데이터 품질 문제
| 실패 | 설명 | 영향 | 감지 난이도 |
|---------|-------------|---------|---------|
| **조용한 데이터 손상** | 오류가 발생하지 않고 데이터가 잘못 수정되었습니다. | 다운스트림 시스템은 잘못된 데이터를 신뢰합니다. 허위정보에 따른 의사결정 | 매우 어려움 - 오류 신호 없음 |
| **스키마 드리프트** | 소스 시스템 변경 스키마(열 추가, 제거, 이름 바꾸기) | 파이프라인이 중단되거나 자동으로 데이터 삭제 | 중간 - 파이프라인이 실패하거나 부분적인 결과를 생성할 수 있음 |
| **데이터 유형 불일치** | 소스는 정수가 필요한 문자열을 보냅니다. 부동 정밀도 변경 | 파이프라인이 실패합니다. 데이터 잘림; 반올림 오류 | 중간 - 파이프라인 오류 또는 미묘한 데이터 문제가 발생할 수 있음 |
| **중복된 기록** | 동일한 이벤트가 여러 번 처리됨 | 부풀려진 수치; 잘못된 집계 | 하드 - 각 레코드가 개별적으로 유효한 것으로 보입니다 |
| **Null/누락된 값** | 예상 필드가 비어 있습니다 | 계산이 실패합니다. 모델이 잘못된 예측을 생성 | 중간 — null 처리에 따라 다름 |
| **범위를 벗어난 값** | 예상 범위를 벗어난 값(음수 연령, 미래 날짜) | 왜곡된 통계; 손상된 비즈니스 로직 | 중간 — 확인 규칙 필요 |
| **늦게 도착하는 데이터** | 처리 창이 닫힌 후 데이터가 도착함 | 불완전한 결과; 놓친 기록 | 어려움 — 결과가 완전해 보이지만 그렇지 않습니다 |
### 파이프라인 인프라 문제
| 실패 | 설명 | 영향 |
|---------|-------------|---------|
| **조정 실패** | 스케줄러(Airflow, Prefect)가 파이프라인을 트리거하지 않음 | 데이터가 오래되었습니다. 처리가 발생하지 않습니다 |
| **자원 고갈** | 파이프라인에 메모리, CPU 또는 디스크 부족 | 파이프라인 충돌; 부분 결과 |
| **종속성 실패** | 업스트림 시스템이 다운되었거나 느림 | 파이프라인이 무기한 대기하거나 실패함 |
| **동시성 문제** | 여러 파이프라인이 동일한 데이터를 동시에 수정 | 경쟁 조건; 데이터 손상 |
| **구성 드리프트** | 환경 변경(네트워크, 자격 증명, 엔드포인트)이 파이프라인에 반영되지 않음 | 파이프라인이 예기치 않게 실패함 |
| **배압** | 파이프라인이 처리할 수 있는 것보다 데이터가 더 빠르게 도착 | 대기열 증가 대기 시간 증가 |

## 사례 연구
### 사례 연구 1: 자동 데이터 복제
| 측면 | 설명 |
|---------|-------------|
| **시나리오** | 전자 상거래 회사의 주문 파이프라인이 메시지 대기열의 이벤트를 처리합니다. |
| **무엇이 잘못됐나요** | 소비자 재시작으로 인해 메시지가 다시 소비되었습니다. 중복 제거 논리가 존재하지 않습니다 |
| **영향** | 누군가 눈치채기 전에 수익 수치가 3주 동안 15% 부풀려졌습니다 |
| **근본 원인** | 멱등성 키가 없습니다. 중복 제거 없이 한 번 이상 전송 |
| **수정** | 주문 ID를 기반으로 멱등성 키가 추가되었습니다. 정확히 한 번 의미 체계를 구현했습니다 |
| **강의** | 한 번 이상 전달하려면 중복 제거가 필요합니다. 항상 소스 시스템과 비교하여 총계의 유효성을 검사합니다 |
### 사례 연구 2: 스키마 변경으로 인해 다운스트림이 중단됨
| 측면 | 설명 |
|---------|-------------|
| **시나리오** | 결제 제공업체가 API 응답의 필드 이름을 변경함 |
| **무엇이 잘못됐나요** | ETL 파이프라인은 자동으로 null 값을 쓰기 시작했습니다. 스키마 유효성 검사 없음 |
| **영향** | 재무 보고서에 따르면 해당 결제 방법으로 2개월 동안 수익이 발생하지 않았습니다 |
| **근본 원인** | 수집 시 스키마 유효성 검사가 없습니다. null 값은 유효한 것으로 간주됩니다 |
| **수정** | 경고를 통한 스키마 검증이 추가되었습니다. 필수 필드가 시행됩니다. 널 검사 |
| **강의** | 안정성을 유지하기 위해 외부 스키마를 절대 신뢰하지 마십시오. 경계에서 검증 |
### 사례 연구 3: 시간대 재앙
| 측면 | 설명 |
|---------|-------------|
| **시나리오** | 한 글로벌 기업이 여러 사무실에서 일일 지표를 집계합니다 |
| **무엇이 잘못됐나요** | 일부 소스는 UTC를 사용하고 다른 소스는 현지 시간을 사용했습니다. 파이프라인이 정규화되지 않았습니다 |
| **영향** | 일일 합계가 일치하지 않았습니다. 일부 거래가 잘못된 날짜에 계산되었습니다. 월말 마감이 잘못되었습니다 |
| **근본 원인** | 표준 시간대 정책이 없습니다. 일관되지 않게 저장된 타임스탬프 |
| **수정** | 모든 타임스탬프는 UTC로 저장됩니다. 프리젠테이션 계층에서만 현지 시간으로 변환 |
| **강의** | 모든 곳에서 UTC를 표준화합니다. 모든 경계에서 시간대를 명시해야 합니다 |

## 예방 전략
### 데이터 검증
| 전략 | 설명 | 도구 예 |
|------------|-------------|---------------|
| **스키마 유효성 검사** | 데이터가 각 단계에서 예상된 스키마와 일치하는지 확인 | 큰 기대; 디쿠; 소다 |
| **범위 확인** | 값이 예상 범위 내에 속함 | 사용자 정의 주장 DBT 테스트 |
| **신선도 확인** | 데이터가 유용할 만큼 최신임 | 타임스탬프 모니터링 SLA 경고 |
| **볼륨 확인** | 행 개수가 예상 범위 내에 있습니다. | 행 개수에 대한 이상 탐지 |
| **참조 무결성** | 외래 키가 일치합니다. 고아 기록이 없습니다 | SQL 제약조건; 데이터 품질 도구 |
| **소스 간 조정** | 소스와 대상 간의 합계 일치 | 자동화된 조정 작업 |
### 파이프라인 디자인 패턴
| 패턴 | 설명 | 혜택 |
|---------|-------------|---------|
| **멱등성** | 파이프라인을 여러 번 실행하면 동일한 결과가 생성됩니다 | 다시 시도해도 안전합니다. 중복 없음 |
| **원자성** | 파이프라인이 완전히 성공하거나 완전히 실패함(부분 상태 없음) | 절반만 처리된 데이터 없음 |
| **체크포인트** | 각 단계의 진행 상황을 저장하세요. 마지막 체크포인트에서 재개 | 내결함성; 재처리 없음 |
| **배달 못한 편지 대기열** | 실패한 기록은 조사를 위해 별도의 대기열로 이동 | 데이터 손실이 없습니다. 조사하고 재생할 수 있습니다 |
| **회로 차단기** | 다운스트림 실패 시 처리 중지 | 계단식 오류 방지 |
| **데이터 계약** | 데이터 형식에 관한 생산자와 소비자 간의 합의 | 스키마 변경이 조정되었습니다 |
### 모니터링 및 경고
| 모니터링 대상 | 왜 | 어떻게 |
|----|------|------|
| **파이프라인 기간** | 지속 시간 증가 신호 문제 | 추세 분석; SLA 추적 |
| **행 개수** | 갑작스러운 변화는 문제를 나타냅니다 | 과거 평균과 비교 |
| **Null rate** | 널 신호 스키마 또는 소스 문제 증가 | 열 수준 Null 추적 |
| **데이터 최신성** | 오래된 데이터는 파이프라인이 실행되지 않음을 의미 | 최신 기록의 타임스탬프 |
| **하류 영향** | 보고서와 모델이 올바른 데이터를 사용하고 있나요? | 엔드투엔드 데이터 계보 |
| **리소스 사용량** | CPU; 메모리; 디스크; 네트워크 | 인프라 모니터링 |

## 복구 전략
| 상황 | 전략 |
|------------|----------|
| **잘못된 데이터가 이미 창고에 있음** | 영향을 받는 시간 범위를 식별합니다. 소스에서 재처리; 다운스트림 소비자에게 알림 |
| **실행 중 파이프라인 오류** | 멱등성 설계로 안전한 재실행이 가능합니다. 체크포인트를 사용하면 재개가 가능합니다 |
| **스키마 변경으로 인해 파이프라인이 중단됨** | 변환 수정; 영향을 받은 데이터 백필 스키마 진화 처리 추가 |
| **소리 없는 부패가 뒤늦게 발견됨** | 근본 원인 분석 폭발 반경을 결정합니다. 재처리; 재발을 포착하기 위한 모니터링 추가 |
| **데이터 손실** | 백업에서 복원; 소스에서 재생; 손실이 회복 가능한지 평가 |

## 요약
데이터 파이프라인 오류는 어디에서나 발생하며 명백한 오류가 아닌 잘못된 답변을 생성하기 때문에 애플리케이션 중단보다 비용이 더 많이 드는 경우가 많습니다. 자동 데이터 손상, 스키마 드리프트, 중복, 시간대 버그 및 값 누락이 가장 일반적인 원인입니다. 주요 예방 전략은 다음과 같습니다. 모든 경계(스키마, 범위, 볼륨, 신선도)에서 데이터의 유효성을 검사합니다. 멱등성이 있고 원자적으로 파이프라인을 설계합니다. 모든 것을 모니터링합니다(기간, 행 수, null 비율, 신선도). 실패한 레코드에 대해 배달 못한 편지 대기열을 사용합니다. 생산자와 소비자 사이에 데이터 계약을 체결합니다. 장애가 발생하면 대응에는 근본 원인 분석, 영향을 받은 데이터의 재처리, 다운스트림 소비자에 대한 알림, 그리고 중요하게는 향후 동일한 종류의 장애를 포착하기 위한 모니터링 추가가 포함되어야 합니다. 이를 올바르게 수행하는 조직은 테스트, 모니터링, 경고, 사고 대응, 사후 분석 등 프로덕션 소프트웨어와 마찬가지로 데이터 파이프라인을 엄격하게 처리합니다.
