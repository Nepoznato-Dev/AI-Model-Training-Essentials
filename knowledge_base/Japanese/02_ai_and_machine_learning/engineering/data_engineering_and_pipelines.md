# データエンジニアリングとパイプライン
データ エンジニアリングは、データを大規模に移動、変換、保存するシステムを構築する学問です。信頼できるデータ パイプラインがなければ、機械学習モデルはトレーニングできず、ダッシュボードには古い数値が表示され、ビジネス上の意思決定は推測に基づいて行われます。このファイルでは、機能するデータ インフラストラクチャを構築するためのアーキテクチャ、ツール、実践方法について説明します。
---

## ETL と ELT の比較
|アプローチ |仕組み |最適な用途 |ツール |
|----------|---------------|----------|----------|
| **ETL** (抽出 → 変換 → ロード) |ウェアハウスにロードする「前」にデータを変換する |コンピューティングが制限された従来のウェアハウス | Informatica、Talend、Apache NiFi |
| **ELT** (抽出 → ロード → 変換) |最初に生データをロードします。倉庫の*内部*を変換 |柔軟なコンピューティングを備えた最新のクラウド ウェアハウス | dbt、Fivetran、Airbyte + BigQuery/Snowflake |
ETL から ELT への移行は、ストレージから独立してコンピューティングを拡張できるクラウド データ ウェアハウス (BigQuery、Snowflake、Redshift) によって推進されてきました。ロードする前にすべてを前処理する必要はなくなりました。
---

## データレイクとデータウェアハウスの比較
|特集 |データレイク |データウェアハウス |
|-----------|-----------|------|
| **データ形式** |生のネイティブ形式 (読み取り時のスキーマ) |構造化、処理 (書き込み時のスキーマ) |
| **スキーマ** |クエリ時に定義 |ロード前に定義 |
| **データ型** |構造化、半構造化、非構造化 |主に構造化された |
| **ユーザー** |データサイエンティスト、エンジニア |ビジネス アナリスト、BI ツール |
| **コスト** |より安価なストレージ (オブジェクト ストレージ) |より高価 (クエリ用に最適化) |
| **例** | AWS S3、Azure データレイク、GCS |スノーフレーク、BigQuery、Redshift |
最新のアプローチは **レイクハウス** です。湖の安価で柔軟なストレージと倉庫の管理およびパフォーマンス機能を組み合わせます。 Delta Lake、Apache Iceberg、Apache Hudi がここでの主要なテクノロジーです。

## パイプラインのアーキテクチャ
### バッチとストリーミング
|モード |説明 |レイテンシ |使用例 |
|------|---------------|----------|----------|
| **バッチ** |スケジュールされた間隔でデータを大きな塊に分けて処理する |数分から数時間 |日次レポート、ETL ジョブ、データ強化 |
| **ストリーミング** |データが到着すると継続的に処理します。ミリ秒から秒へ |リアルタイム ダッシュボード、不正行為検出、アラート |
| **マイクロバッチ** |非常に短い間隔での小さなバッチ |秒 |バッチ処理の簡素化によるほぼリアルタイム |
### パイプラインコンポーネント
一般的なデータ パイプラインには次のステージがあります。
|ステージ |説明 |ツール |
|----------|---------------|----------|
| **摂取** |ソースからデータを収集する |カフカ、Airbyte、Fivetran、Debezium |
| **変換** |クリーンアップ、強化、集約 | dbt、スパーク、パンダ |
| **ストレージ** |処理されたデータを永続化する | BigQuery、スノーフレーク、S3、デルタ レイク |
| **サービス** |消費者がデータを利用できるようにする | API、ダッシュボード、ML 機能ストア |
| **オーケストレーション** |依存関係のスケジュールと管理 |エアフロー、プリフェクト、ダグスター |
| **モニタリング** |パイプラインの健全性とデータ品質を追跡する | Great Expectations、モンテカルロ、カスタム アラート |

## オーケストレーション ツール
|ツール |アプローチ |強さ |
|------|----------|----------|
| **Apache エアフロー** | Python ベースの DAG。業界標準 |巨大なエコシステム、成熟した、柔軟な |
| **知事** | Python ネイティブ。 Airflow よりもクリーンな API |モダンなデザイン、優れたエラー処理 |
| **ダグスター** |資産中心。ソフトウェアエンジニアリングのアプローチ |型システム、テスト、可観測性 |
| **ルイージ** | Spotify のオリジナル パイプライン ツール |シンプルだがあまり積極的に開発されていない |

## アパッチカフカ
Kafka は、多くのリアルタイム データ システムのバックボーンです。これは、高スループットでフォールト トレラントなメッセージングを提供する分散イベント ログです。
### 中心となる概念
|コンセプト |説明 |
|----------|---------------|
| **トピック** |メッセージのカテゴリ (例:`orders`、`user-events`) |
| **パーティション** |トピックは並列処理のためにパーティションに分割されます。
| **プロデューサー** |トピックにメッセージを書き込むアプリケーション |
| **消費者** |トピックからメッセージを読み取るアプリケーション |
| **消費者グループ** |トピックを読む負荷を共有する消費者のグループ |
| **オフセット** |パーティション内のコンシューマの位置 |
| **ブローカー** | Kafka サーバー ノード |
### Kafka を使用する場合
- **イベント ストリーミング**: 大規模なリアルタイム イベント処理。
- **デカップリング サービス**: 生産者と消費者はお互いのことを知る必要はありません。
- **再生**: メッセージは保持されます。消費者は任意のオフセットから再読み取りできます。
- **バックプレッシャー**: Kafka は、プロデューサーとコンシューマー間の速度の違いを自然に処理します。

## データモデリング
### スター スキーマとスノーフレーク スキーマ
|スキーマ |構造 |長所 |短所 |
|------|-----------|------|------|
| **スター** |中央のファクト テーブルが非正規化されたディメンション テーブルで囲まれている |シンプルなクエリ、高速読み取り |データの冗長性 |
| **スノーフレーク** |ディメンション テーブルは正規化されます (サブテーブルに分割されます)。冗長性の低下 |結合が増えるとクエリが遅くなる |
### ファクト テーブルとディメンション テーブル
|テーブルタイプ |含まれています |例 |
|----------|----------|----------|
| **事実** |測定可能なイベント (メトリクス) | `orders`(order_id、product_id、customer_id、金額、日付) |
| **寸法** |説明的な属性 | `products`(製品 ID、名前、カテゴリ、価格)、`customers` (顧客 ID、名前、都市) |

## フィーチャー ストア
特徴ストアは、ML 特徴、つまりモデルへの入力として使用される派生値 (例: 「過去 30 日間のユーザーの平均注文額」) の一元的なリポジトリです。
|能力 |説明 |
|----------|---------------|
| **機能レジストリ** |メタデータを含む利用可能な機能のカタログ |
| **オフライン ストア** |モデルトレーニング用の履歴機能 (バッチ) |
| **オンラインストア** |リアルタイム推論のための低遅延機能 |
| **機能の監視** |ドリフト、欠損値、分布の変化を検出 |
|ツール |説明 |
|------|---------------|
| **ごちそう** |オープンソース。あらゆる ML フレームワークで動作します。
| **テクトン** |コマーシャル;リアルタイム機能プラットフォーム |
| **ホップワークス** |オープンソース。機能ストアを備えた完全な ML プラットフォーム |
| **Databricks 機能ストア** | Databricks/Spark との統合 |

## データ品質
データ品質は ML プロジェクトのサイレントキラーです。ゴミが入って、ゴミが出る。
### 品質の寸法
|寸法 |質問 |
|----------|----------|
| **精度** |データは現実を反映していますか? |
| **完全性** |必須フィールドは入力されていますか? |
| **一貫性** |値はソース間で一致していますか? |
| **適時性** |データは最新ですか? |
| **有効性** |値は定義されたルールに従っていますか? |
| **独自性** |重複したレコードはありますか? |
### データ品質ツール
|ツール |アプローチ |
|------|----------|
| **大きな期待** | Python ベース。データに関する「期待」を定義する |
| **モンテカルロ** | ML を活用したデータ可観測性プラットフォーム |
| **dbt テスト** |ウェアハウス データの組み込みテスト (一意、not_null、関係) |
| **ソーダ** |オープンソースのデータ品質スキャン |

## データガバナンス
データ ガバナンスにより、組織全体でデータが責任を持って管理されるようになります。
|エリア |説明 |
|------|---------------|
| **データカタログ** |メタデータを含むデータセットの検索可能なインベントリ (Amundsen、DataHub、Atlan) |
| **データリネージュ** |データがどこから来て、どのように変換されるかを追跡する |
| **アクセス制御** |役割ベースの権限。誰が何を読み書きできるのか |
| **コンプライアンス** | GDPR、CCPA、HIPAA 準拠 |
| **データの所有権** |各データセットの所有権を明確にする (管理) |
| **保持ポリシー** |データの保存期間と削除時期を定義する |
---

## 最新のデータスタック
「最新のデータ スタック」とは、現在データ チームが使用するツールの典型的な組み合わせを指します。
|レイヤー |代表的なツール |
|------|--------------|
| **摂取** | Fivetran、Airbyte |
| **倉庫** |スノーフレーク、BigQuery、Redshift |
| **変換** | dbt |
| **オーケストレーション** |エアフロー、プリフェクト、ダグスター |
| **BI / ビジュアライゼーション** | Looker、メタベース、Tableau |
| **リバース ETL** |国勢調査、ハイタッチ (倉庫データをツールに同期) |
| **データ品質** |大いなる期待、モンテカルロ |
トレンドは、モノリシック プラットフォームではなく、オープン スタンダード (SQL、dbt モデル、Airflow DAG) によって接続されたモジュール型の最高のツールに向かっています。
