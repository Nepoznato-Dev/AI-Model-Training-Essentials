# ML エンジニアリングと MLOps
機械学習モデルの構築は、まだ戦いの半分に過ぎません。実稼働環境への導入、確実な実行の維持、ドリフトの監視、反復処理 - ここで ML エンジニアリングと MLOps が登場します。このファイルは、実験から実稼働システムまでのライフサイクル全体をカバーします。
---

## ML ライフサイクル
|フェーズ |説明 |主な活動 |
|------|-------------|------|
| **1.問題の定義** |ビジネス上の問題を ML タスクとして組み立てる |指標、制約、成功基準を定義する |
| **2.データ収集** |トレーニング データを収集してラベルを付ける | ETL、ラベル付け、拡張 |
| **3.実験** |モデルのトレーニングと評価 |特徴量エンジニアリング、ハイパーパラメータ調整 |
| **4.モデルの選択** |最適なモデルを選択してください |メトリクスを比較し、トレードオフを評価する |
| **5.導入** |モデルを本番環境に出荷する |サービスインフラストラクチャ、API、バッチ |
| **6.モニタリング** |ドリフトと劣化に注意する |データドリフト、コンセプトドリフト、パフォーマンス |
| **7.再トレーニング** |新しいデータでモデルを更新する |スケジュールされた再トレーニングまたはトリガーされた再トレーニング |
価値 (および難易度) の大部分はフェーズ 5 ～ 7 にあります。 Jupyter ノートブックにあるモデルはビジネス価値を生み出しません。
---

## モデル提供パターン
|パターン |説明 |レイテンシ |使用例 |
|----------|---------------|----------|----------|
| **バッチ推論** |スケジュールに従ってデータのバッチに対してモデルを実行する |営業時間 |毎日の推奨事項、不正行為のスコアリング |
| **オンライン推論** |リクエストごとのリアルタイム予測 |ミリ秒 |検索ランキング、リアルタイム分類 |
| **ストリーミング推論** |データ ストリーム上の予測を処理する |秒 |異常検知、イベント処理 |
### サービス提供インフラストラクチャ
|ツール |タイプ |最適な用途 |
|------|------|----------|
| **TensorFlow の提供** |モデルサーバー | TensorFlow モデル |
| **トーチサーブ** |モデルサーバー | PyTorch モデル |
| **Triton 推論サーバー** |マルチフレームワーク | GPU 推論、複数のフレームワーク |
| **vLLM** | LLM サービス |高スループットの LLM 推論 |
| **BentoML** |統合されたサービス |フレームワークに依存しない展開 |
| **セルドン** | K8s ネイティブ | Kubernetes モデルのデプロイ |
| **レイサーブ** |スケーラブルなサービス |大規模モデル、分散推論 |

## モデル レジストリ
モデル レジストリは、ML モデル (バージョン、メタデータ、メトリクス、デプロイメント ステータス) を管理するための集中ストアです。
|能力 |説明 |
|----------|---------------|
| **バージョン管理** |すべてのモデルのバージョンを一意の ID で追跡 |
| **メタデータ** |トレーニング データ、ハイパーパラメータ、メトリクス、作成者 |
| **ステージ移行** |モデルを段階的に移動します: ステージング → 本番 → アーカイブ |
| **リネージュ** |各モデルを生成したデータとコードを追跡する |
|ツール |説明 |
|------|---------------|
| **MLflow** |オープンソース。モデル レジストリ + 実験追跡 |
| **重みとバイアス (W&B)** |コマーシャル;実験追跡 + モデル レジストリ |
| **DVC** | Git を使用したデータとモデルのバージョン管理 |
| **Azure ML / SageMaker** |クラウドネイティブなモデル管理 |
---

## 実験の追跡
どのようなデータが使用されたか、どのようなハイパーパラメータ、どのようなメトリクスが結果として得られたかなど、すべての ML 実験を追跡する必要があります。
|ツール |主な機能 |
|------|---------------|
| **MLflow** |オープンソース、自己ホスト型、パラメータ/メトリクス/アーティファクトを追跡 |
| **W&B** |豊富な UI、スイープ、アーティファクトのバージョン管理、レポート |
| **海王星** | MLOps のメタデータ ストア |
| **テンソルボード** | TensorFlow に組み込まれています。トレーニング曲線を視覚化する |
### 何を追跡するか
|カテゴリー |例 |
|----------|----------|
| **パラメータ** |学習率、バッチ サイズ、モデル アーキテクチャ、エポック数 |
| **メトリクス** |精度、損失、F1、AUC-ROC (エポックごとおよび最終) |
| **アーティファクト** |モデルの重み、混同行列、予測サンプル |
| **データ** |データセットのバージョン、分割率、前処理手順 |
| **環境** | Python のバージョン、ライブラリのバージョン、ハードウェア |

## モデルの導入戦略
|戦略 |仕組み |リスク |
|----------|---------------|------|
| **シャドウ展開** |新しいモデルは古いモデルと並行して実行されます。予測は比較されましたが提供されませんでした |リスクゼロ。ライブになる前に検証します |
| **カナリア リリース** |トラフィックのごく一部を新しいモデルにルーティングします。徐々に増加します |低リスク。高速ロールバック |
| **A/B テスト** |ユーザーを新旧に分割します。ビジネス指標を比較する |実際の影響を測定 |
| **ブルーグリーン** | 2 つの同一の環境。すべてのトラフィックを一度に切り替える |即時ロールバック。移行中の二重コスト |
| **機能フラグ** |ユーザー セグメントごとにモデルのオン/オフを切り替える |きめ細かい制御 |
---

## ML システムのモニタリング
データ自体が変更される可能性があるため、ML システムでは従来のソフトウェアよりも多くの監視が必要です。
### ドリフトの種類
|ドリフトタイプ |何が変わるのか |例 |
|----------|---------------|----------|
| **データドリフト** |入力分布の変更 |マーケティング キャンペーン後の顧客層の変化 |
| **コンセプト ドリフト** |入力と出力の関係変化 |不況下では消費者行動が変化 |
| **ラベル ドリフト** |ターゲット配布の変更 |不正行為率が 1% から 5% に増加 |
### 監視対象
|カテゴリー |メトリクス |
|----------|----------|
| **モデルのパフォーマンス** |精度、精度、再現率、F1、AUC (ベースラインとの比較) |
| **データ品質** |欠損値、特徴分布、外れ値 |
| **ドリフト検出** |統計検定（KS検定、PSI、KL発散） |
| **インフラストラクチャ** |レイテンシ、スループット、GPU 使用率、メモリ |
| **ビジネス指標** |コンバージョン率、収益への影響、ユーザー満足度 |
### 監視ツール
|ツール |タイプ |
|------|------|
| **明らかに AI** |オープンソースのデータドリフトとモデルのパフォーマンス監視 |
| **グラファナ** |ダッシュボードの視覚化 (Prometheus で動作) |
| **WhyLabs** |データ可観測性プラットフォーム |
| **アライズ** | ML の可観測性と根本原因の分析 |
| **プロメテウス + グラファナ** |インフラストラクチャとアプリケーションのメトリクス |

## 再現可能なトレーニング
再現性とは、実験を再実行して同じ結果が得られることを意味します。これはデバッグ、監査、コンプライアンスに不可欠です。
＃＃＃ 要件
|要件 |それを達成する方法 |
|-----------|-----------|
| **データのバージョン管理** | DVC、Delta Lake、またはハッシュを含むデータセットのスナップショット |
| **コードのバージョン管理** |すべてのトレーニング コードの Git |
| **環境の固定** | `requirements.txt`、`conda env`、正確なバージョンの Docker イメージ |
| **シード設定** | numpy、torch、tensorflow のランダム シードを修正 |
| **構成管理** |すべてのハイパーパラメータの Hydra、OmegaConf、または YAML 構成 |
| **アーティファクト追跡** |すべての実験を記録するための MLflow または W&B |
---

## スケーリング推論
モデルが 1 日に何百万ものリクエストに対応する必要がある場合、パフォーマンスが重要になります。
|テクニック |説明 |
|----------|---------------|
| **バッチ処理** |複数のリクエストを単一の転送パスにグループ化する |
| **量子化** |推論を高速化するためにモデルの精度を下げる (FP32 → INT8 または INT4) |
| **モデル蒸留** |より大きなモデルを模倣するようにより小さなモデルをトレーニングする |
| **剪定** |重要でない重みやニューロンを削除する |
| **キャッシング** |頻繁な予測をキャッシュして再計算を回避する |
| **GPU の最適化** | TensorRT、ONNX ランタイム、フラッシュ
| **水平スケーリング** |ロード バランサーの背後で複数のモデル レプリカを実行する |

## ML の機能フラグ
機能フラグを使用すると、再デプロイすることなく、どのモデル バージョンがどのユーザーにサービスを提供するかを制御できます。
|使用例 |説明 |
|----------|---------------|
| **段階的な展開** |新しいモデルを 5% のユーザーに提供し、その後増加 |
| **キルスイッチ** |問題が検出された場合は、すぐに以前のモデルに戻ります |
| **セグメントベース** |異なるユーザーセグメントに応じた異なるモデル |
| **実験** |ビジネス指標を使用した A/B テスト モデルのバリエーション |
ツール: LaunchDarkly、Unleash、Flagsmith、または単純なデータベースベースの機能フラグ。

## MLOps 成熟度曲線
|レベル |特徴 |
|------|----------------|
| **レベル 0 — マニュアル** |手動トレーニング、手動導入、モニタリングなし |
| **レベル 1 — 実験** |実験の追跡、モデル レジストリ、基本的な CI |
| **レベル 2 — 自動化** |自動再トレーニング、モデルの CI/CD、自動テスト |
| **レベル 3 — 完全なパイプライン** |モニタリング、ドリフト検出、自動再トレーニングを備えたエンドツーエンドの自動パイプライン |
ほとんどの組織は、レベル 0 とレベル 1 の間のどこかにあります。目標は、ML ライフサイクルが自動化され、自己修復されるレベル 2 ～ 3 です。
