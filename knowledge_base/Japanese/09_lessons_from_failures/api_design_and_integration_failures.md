# API 設計と統合の失敗
API (アプリケーション プログラミング インターフェイス) は現代のソフトウェアの結合組織であり、サービスの通信、サードパーティの統合、チームの独立した作業を可能にします。 API 設計に問題があると、統合の失敗、セキュリティの脆弱性、開発者の不満、コストのかかる書き換えなど、その影響がそれに依存するすべてのシステムに波及します。システムが確実に通信できない統合障害は、運用インシデントの最も一般的な原因の 1 つです。
---

## よくある API 設計の失敗
### 設計ミス
|間違い |説明 |結果 |
|----------|---------------|---------------|
| **一貫性のない命名** | `/getUsers`対`/list_users`対`/fetch-users`|混乱;エラー。開発が遅い |
| **エンドポイントの過負荷** |パラメーターに基づいて 10 の異なる処理を実行する 1 つのエンドポイント |理解するのが難しい。テストが難しい。変えるのは難しい |
| **取得不足** |関連データを取得するには、クライアントは 5 つの API 呼び出しを行う必要があります。遅い;無駄です。複雑なクライアント コード |
| **過剰取得** |クライアントが 2 つだけを必要とする場合、API はすべてのフィールドを返します。帯域幅の無駄。モバイルでは遅い。セキュリティリスク (不要なデータの漏洩) |
| **バージョン管理なし** |重大な変更が警告なしに展開される |クライアントは壊れます。怒っている開発者 |
| **曖昧なエラー メッセージ** | 「エラー 500: 内部サーバー エラー」詳細なし |デバッグ不可能。解像度が遅い |
| **ページネーションがありません** |エンドポイントはすべてのレコード (数百万件になる可能性があります) を返します。タイムアウト。記憶力の枯渇。クラッシュしたクライアント |
| **一貫性のないステータス コード** |エラーの場合は 200 OK。クライアントのミスには 500 |クライアントは成功と失敗を区別できない |
### REST API のアンチパターン
|アンチパターン |説明 |より良いアプローチ |
|---------------|---------------|------|
| **突然変異に GET を使用する** | `GET /delete-user?id=5`| DELETE メソッドを使用する |
| **すべてに POST を使用する** | `POST /get-users`; `POST /update-user`|適切な HTTP メソッド (GET、POST、PUT、PATCH、DELETE) を使用します。
| **API から HTML を返す** | API は HTML フラグメントを返します | JSON を返します。クライアントにレンダリングさせます |
| **URL 内のビジネス ロジック** | `/users/active/premium/from-2023`|複雑なフィルターにはクエリ パラメーターまたはリクエスト本文を使用します。
| **データベース スキーマの公開** | `/api/table_name/column`|テーブルではなく、リソースとドメインの概念に基づいて API を設計する |
| **HATEOAS / リンクはありません** |クライアントはすべての URL をハードコードします。関連リソースへのリンクを応答に含める |

## セキュリティ障害
### 一般的な API の脆弱性
|脆弱性 |説明 |例 |
|--------------|-------------|----------|
| **認証が壊れました** | API が ID を適切に検証しません |トークンの検証がありません。期限切れのトークンは受け入れられます |
| **過度のデータ露出** | API はクライアントが必要とするよりも多くのデータを返します。ユーザー エンドポイントはパスワード ハッシュと内部 ID を返します。
| **一括割り当て** |クライアントは設定すべきではないフィールドを設定できる | `PATCH /user`では`role: "admin"`を設定できます |
| **注射** |ユーザー入力がコードとして解釈される | SQL インジェクション。 NoSQL インジェクション。コマンドインジェクション |
| **IDOR** (安全でない直接オブジェクト参照) | URL の ID を変更してリソースにアクセスする | `/api/users/5`→`/api/users/6`に変更して他の人のデータを表示 |
| **レート制限がありません** | API 呼び出しに制限なし |ブルーフォース;サービス拒否。スクレイピング |
| **CORS の構成ミス** |過度に寛容なクロスオリジンアクセス |  認証されたエンドポイント上の`Access-Control-Allow-Origin: *`|
### 認証と認可の失敗
|失敗 |説明 |影響 |
|----------|---------------|----------|
| **ハードコードされた資格情報** |ソース コード内の API キーまたはパスワード |バージョン管理を通じて漏洩。すべての開発者がアクセス可能 |
| **トークンの有効期限なし** |トークンは期限切れになりません |盗まれたトークンは永久アクセスを与える |
| **弱い秘密鍵** |短いまたは予測可能な署名キー |トークンは偽造できる |
| **スコープ/権限なし** |すべてのトークンには完全なアクセス権があります |侵害されたトークン = フル システム アクセス |
| **機密データのログ記録** |ログ内のトークンまたはパスワード |ログアクセス権を持つ誰でもアクセス可能 |
| **一貫性のない認証** |一部のエンドポイントは権限をチェックします。他の人はそうではありません |保護されていないエンドポイントを介した不正アクセス |

## 統合の失敗
### 分散システム統合の問題
|失敗 |説明 |例 |
|----------|---------------|----------|
| **密結合** |サービスは相互の内部実装の詳細に依存します。 1 つのサービスのデータベースを変更すると、他の 3 つのサービスが破損します。
| **同期チェーン** |サービス A が B を呼び出し、C が D を呼び出します。遅延が蓄積する | 200ms + 300ms + 500ms = 1 秒の応答時間 |
| **サーキットブレーカーなし** |サービスの障害により連鎖的な障害が発生する |サービス D は遅いです。すべてのアップストリーム サービスは、待機中のスレッドを使い果たします。
| **再試行ロジックなし** |一時的な障害が永続的になる |ネットワークブリップ = 失敗したトランザクション。ユーザーは手動で再試行する必要があります。
| **過剰な再試行** |バックオフなしで再試行すると、回復サービスに負荷がかかります。雷鳴のような群れの問題 |
| **冪等性なし** |冪等でない操作を再試行すると重複が作成されます。支払いは 2 回請求されます。注文は 2 回作成されました |
| **結果整合性の驚き** |クライアントが書き込み後に古いデータを読み取る |ユーザーはプロフィールを更新します。ページを更新します。古いデータがまだ表示されています |
### サードパーティ統合の失敗
|失敗 |説明 |緩和 |
|----------|---------------|---------------|
| **ベンダー API の変更** |サードパーティは予告なく API を変更します |バージョンの固定。抽象化層。ベンダー変更ログの監視 |
| **レート制限** |サードパーティがリクエストを抑制する |キャッシング;リクエストキューイング。上限の交渉 |
| **ベンダーのダウンタイム** |サードパーティのサービスは利用できません |サーキットブレーカー;フォールバック動作。マルチベンダー戦略 |
| **データ形式の変更** |サードパーティによる応答形式の変更 |スキーマの検証。変換層。フォーマット変更に関するアラート |
| **移行パスのない非推奨** |ベンダーは同等のエンドポイントを廃止しました |常に最新情報を入手してください。抽象性を維持する。移行を早めに計画する |

## ケーススタディ
### ケーススタディ 1: すべてを返す API
|側面 |説明 |
|----------|---------------|
| **シナリオ** | SaaS 企業のユーザー API は、内部メタデータを含むすべてのユーザー フィールドを返しました。
| **何が問題だったのか** |フィールドのフィルタリングはありません。応答にはパスワード ハッシュ、内部メモ、管理者フラグが含まれていました。
| **影響** |セキュリティ研究者が暴露を発見しました。一般公開。 GDPR調査 |
| **根本原因** | API はフィルタリングせずにデータベース モデル全体をシリアル化します。
| **修正** |明示的な応答モデル。フィールドレベルのアクセス制御。すべてのエンドポイントのセキュリティレビュー |
| **レッスン** | API を通じてデータベース モデルを直接公開しないでください。 DTO (データ転送オブジェクト) を使用する |
### ケーススタディ 2: 連鎖的な障害
|側面 |説明 |
|----------|---------------|
| **シナリオ** |同期サービス間通信を備えたマイクロサービス アーキテクチャ |
| **何が問題だったのか** | 1 つのサービスでデータベースの速度低下が発生しました。上流のサービスは応答を待ちました。スレッド プールが使い果たされました |
| **影響** | 45 分間の完全なシステム停止。影響を受けるすべてのサービス |
| **根本原因** |サーキットブレーカーはありません。タイムアウトはありません。同期依存関係チェーン |
| **修正** |サーキットブレーカー;タイムアウト。可能な場合は非同期通信。隔壁 |
| **レッスン** |サービス間の同期呼び出しにより、脆弱なチェーンが作成されます。失敗に備えた設計 |

## ベストプラクティス
### API 設計チェックリスト
|エリア |練習 |
|------|----------|
| **ネーミング** |リソースには名詞を使用します。アクションの HTTP メソッド。一貫した命名規則 |
| **バージョン管理** |初日のバージョン。 URL バージョン管理 (`/v1/`) またはヘッダー バージョン管理を使用します。
| **ページネーション** |リストのエンドポイントは常にページ分割されます。大規模なデータセットにはカーソルベースのページネーションを使用します。
| **エラー処理** |一貫したエラー形式。エラーコードを含めます。実用的なメッセージを提供する |
| **レート制限** |レート制限を実装します。 retry-after ヘッダーを付けて 429 を返す |
| **べき等性** |突然変異エンドポイントの冪等性キーをサポート |
| **ドキュメント** | OpenAPI / Swagger 仕様。常に最新の状態に保ちます。例を示します |
| **テスト** |契約テスト;統合テスト。消費者主導の契約テスト |
| **モニタリング** |遅延を追跡します。エラー率。スループット;依存関係の健全性 |
| **非推奨** |非推奨を十分前もって発表します。移行ガイドを提供する |

＃＃ まとめ
API 設計の失敗は、表面的なもの (一貫性のない命名) から致命的なもの (セキュリティの脆弱性、連鎖的な障害) まで多岐にわたります。最も一般的な設計ミス (エンドポイントの過負荷、過剰なフェッチ、ページネーションの欠落、あいまいなエラー) により、API の使用と保守が困難になります。セキュリティ障害 (認証の破損、IDOR、大量割り当て、過剰なデータ漏洩) は、システムを攻撃にさらします。統合の障害 (密結合、同期チェーン、サーキット ブレーカーの欠落、冪等性の欠如) は、1 つの障害がサービス全体に連鎖する脆弱なシステムを作成します。サードパーティの統合により、API の変更、レート制限、ベンダーのダウンタイムなどの外部リスクが追加されます。予防戦略は十分に確立されています。明示的な対応モデルを使用します。初日のバージョン。サーキットブレーカーとタイムアウトを実装します。冪等性を考慮した設計。すべての入力を検証し、サニタイズします。すべてを監視します。 API 契約を、変更するには調整が必要な拘束力のある契約として扱います。最高の API は退屈なものであり、予測可能で、一貫性があり、十分に文書化されており、障害に強いものです。
