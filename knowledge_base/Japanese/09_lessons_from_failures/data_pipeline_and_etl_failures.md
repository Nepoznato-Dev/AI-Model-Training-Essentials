# データ パイプラインと ETL の障害
データ パイプラインは現代の組織の配管です。データ パイプラインは、変換を通じてソース システムからデータベース、ウェアハウス、レイクにデータを移動し、そこで分析、機械学習、意思決定に使用されます。彼らが働いているとき、誰も気づきません。失敗すると、古いデータに基づいて意思決定が行われ、モデルはガベージでトレーニングされ、レポートにはありえない数字が示され、データ プラットフォーム全体に対する信頼が失われます。データ パイプラインの障害は、テクノロジー組織において最も一般的で、最もコストがかかる障害の 1 つです。
---

## 一般的な障害モード
### データ品質の問題
|失敗 |説明 |影響 |検出の難易度 |
|----------|---------------|----------|---------------------|
| **サイレントデータ破損** |エラーが発生せずにデータが誤って変更されます。下流システムは不正なデータを信頼します。誤った情報に基づいた決定 |非常に難しい — エラー信号なし |
| **スキーマ ドリフト** |ソース システムのスキーマ変更 (列の追加、削除、名前変更) |パイプラインが中断するか、サイレントにデータを削除します。中 - パイプラインが失敗するか、部分的な結果が生成される可能性があります。
| **データ型が一致しません** |ソースは整数が期待される場所に文字列を送信します。 float 精度の変更 |パイプラインが失敗します。データは切り捨てられました。丸め誤差 |中 - パイプライン エラーや微妙なデータの問題が発生する可能性があります。
| **レコードが重複しています** |同じイベントが複数回処理されました。水増しされたカウント。不正な集計 |ハード — 各レコードは個別に有効であるように見えます。
| **NULL/欠損値** |予期されたフィールドが空です |計算は失敗します。モデルは間違った予測を生成します。中 — null 処理に依存します。
| **範囲外の値** |予想範囲外の値 (マイナスの年齢、将来の日付) |歪んだ統計。壊れたビジネス ロジック |中 - 検証ルールが必要 |
| **遅れて到着したデータ** |処理ウィンドウが閉じられた後にデータが到着します。不完全な結果。見逃した記録 |難しい — 結果は完全に見えますが、完全ではありません |
### パイプラインインフラストラクチャの問題
|失敗 |説明 |影響 |
|----------|---------------|----------|
| **オーケストレーションの失敗** |スケジューラー (Airflow、Prefect) がパイプラインをトリガーしません。データが古い。処理は行われません |
| **リソース枯渇** |パイプラインのメモリ、CPU、またはディスクが不足します。パイプラインがクラッシュする。部分的な結果 |
| **依存関係の失敗** |上流のシステムがダウンしているか遅い |パイプラインが無期限に待機するか失敗します。
| **同時実行の問題** |複数のパイプラインが同じデータを同時に変更する |競合状態。データ破損 |
| **構成のドリフト** |環境の変更 (ネットワーク、資格情報、エンドポイント) がパイプラインに反映されない |パイプラインが予期せず失敗します。
| **背圧** |データはパイプラインの処理よりも速く到着します。増大するキュー。遅延の増加 |

## ケーススタディ
### ケーススタディ 1: サイレントデータ複製
|側面 |説明 |
|----------|---------------|
| **シナリオ** |電子商取引会社の注文パイプラインはメッセージ キューからのイベントを処理します。
| **何が問題だったのか** |コンシューマーの再起動により、メッセージが再消費されます。重複排除ロジックが存在しませんでした。
| **影響** |収益数値は、誰もが気づかないうちに 3 週間で 15% 膨らみました |
| **根本原因** |冪等性キーはありません。重複排除なしの少なくとも 1 回の配信 |
| **修正** |注文 ID に基づいた冪等キーを追加しました。 1 回限りのセマンティクスを実装 |
| **レッスン** |少なくとも 1 回の配信には重複排除が必要です。常にソース システムに対して合計を検証します。
### ケーススタディ 2: スキーマ変更がダウンストリームで中断される
|側面 |説明 |
|----------|---------------|
| **シナリオ** |決済プロバイダーが API 応答のフィールド名を変更する |
| **何が問題だったのか** | ETL パイプラインはサイレントに null 値の書き込みを開始しました。スキーマ検証なし |
| **影響** |財務報告書では、その支払い方法からの収益が 2 か月間ゼロであることが示されました。
| **根本原因** |取り込み時にスキーマ検証は行われません。 null 値は有効なものとして扱われます。
| **修正** |アラートによるスキーマ検証を追加しました。必須フィールドが強制されます。 null チェック |
| **レッスン** |外部スキームが安定していることを決して信頼しないでください。境界で検証する |
### ケーススタディ 3: タイムゾーンの大惨事
|側面 |説明 |
|----------|---------------|
| **シナリオ** |あるグローバル企業は、オフィス全体で毎日の指標を集計しています。
| **何が問題だったのか** |一部のソースは UTC を使用し、他のソースは現地時間を使用しました。パイプラインが正規化されませんでした |
| **影響** | 1 日の合計が一致しませんでした。一部のトランザクションは間違った日にカウントされました。月末締めが間違っていました |
| **根本原因** |標準のタイムゾーンポリシーはありません。タイムスタンプが一貫性なく保存されている |
| **修正** |すべてのタイムスタンプは UTC として保存されます。プレゼンテーション層でのみ現地時間に変換 |
| **レッスン** |あらゆる場所で UTC を標準化します。すべての境界におけるタイムゾーンを明示する |

## 予防戦略
### データ検証
|戦略 |説明 |ツールの例 |
|----------|---------------|----------|
| **スキーマの検証** |各段階でデータが予想されるスキーマと一致することを確認します。大きな期待。ディーク;ソーダ |
| **範囲チェック** |値は予想される範囲内にあります |カスタム アサーション。 dbt テスト |
| **鮮度チェック** |データは十分に新しいので役に立つ |タイムスタンプの監視。 SLA アラート |
| **ボリュームチェック** |行数は予想範囲内です |行数の異常検出 |
| **参照整合性** |外部キーが一致します。孤立したレコードはありません | SQL 制約。データ品質ツール |
| **ソース間の調整** |合計はソースとターゲットの間で一致します |自動調整ジョブ |
### パイプライン設計パターン
|パターン |説明 |メリット |
|----------|---------------|----------|
| **べき等性** |パイプラインを複数回実行しても同じ結果が得られます。安全に再試行できます。重複はありません |
| **原子性** |パイプラインは完全に成功するか、完全に失敗します (部分的な状態はありません)。中途半端に処理されたデータはありません |
| **チェックポイント** |各ステージの進行状況を保存します。最後のチェックポイントから再開 |耐障害性。再処理なし |
| **配信不能キュー** |失敗したレコードは調査のために別のキューに送られます。データの損失はありません。調査と再生が可能 |
| **サーキットブレーカー** |ダウンストリームに障害が発生した場合に処理を停止する |連鎖的な障害を防ぐ |
| **データ契約** |データ形式に関する生産者と消費者間の合意 |スキーマの変更は調整されます |
### 監視と警告
|何を監視するか |なぜ |どのように |
|------|-----|-----|
| **パイプライン期間** |持続時間の増加は問題を示します |傾向分析; SLA 追跡 |
| **行数** |突然の変化は問題を示しています |過去の平均と比較 |
| **ヌルレート** | Null の増加は、スキーマまたはソースの問題を信号します。列レベルの null 追跡 |
| **データの鮮度** |データが古いということはパイプラインが実行されていないことを意味します |最新レコードのタイムスタンプ |
| **下流への影響** |レポートとモデルは正しいデータを使用していますか? |エンドツーエンドのデータ系統 |
| **リソース使用量** | CPU;メモリ;ディスク;ネットワーク |インフラ監視 |

## 回復戦略
|状況 |戦略 |
|----------|----------|
| **不良データがすでにウェアハウスにあります** |影響を受ける時間範囲を特定します。ソースから再処理します。下流の消費者に通知する |
| **実行中のパイプライン障害** |冪等設計により安全な再実行が可能になります。チェックポイントにより再開が可能になります。
| **スキーマ変更によりパイプラインが中断されました** |変換を修正します。影響を受けたデータをバックフィルします。スキーマ進化処理を追加 |
| **サイレント破損が遅れて発見されました** |根本原因の分析。爆発範囲を決定する。再処理。再発を検出するためにモニタリングを追加する |
| **データ損失** |バックアップから復元します。ソースからの再生。損失が回復可能かどうかを評価する |
---

＃＃ まとめ
データ パイプラインの障害は至るところで発生しており、明らかなエラーではなく誤った答えが生成されるため、多くの場合、アプリケーションの停止よりもコストが高くなります。最も一般的な原因は、サイレント データ破損、スキーマ ドリフト、重複、タイム ゾーン バグ、および欠損値です。主な防止戦略は次のとおりです。すべての境界 (スキーマ、範囲、ボリューム、鮮度) でデータを検証します。パイプラインを冪等かつアトミックになるように設計します。すべてを監視します (期間、行数、NULL 率、鮮度)。失敗したレコードにはデッドレターキューを使用します。生産者と消費者の間でデータ契約を確立します。障害が発生した場合の対応には、根本原因の分析、影響を受けるデータの再処理、下流の消費者への通知、そして重要なことに、将来同じクラスの障害を検出するための監視の追加が含まれる必要があります。これを正しく理解している組織は、テスト、監視、アラート、インシデント対応、事後分析など、データ パイプラインを運用ソフトウェアと同じ厳密さで扱います。
