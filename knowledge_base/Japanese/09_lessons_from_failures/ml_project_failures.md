# 機械学習プロジェクトの失敗
機械学習プロジェクトは高い割合で失敗します。業界の推定では、ML プロジェクトの 60 〜 85% が本番環境に到達しないことが示唆されています。通常、失敗はアルゴリズムにあるわけではありません。失敗はプロセス、データ、期待、組織のコンテキストの中にあります。失敗モードは予測可能であり、ほとんどの場合回避可能であるため、ML プロジェクトが失敗する理由を理解することは、ML システムを構築するすべての人にとって不可欠です。
---

## ML プロジェクトが失敗する理由
### 失敗のカテゴリ
|カテゴリー |失敗の割合 |説明 |
|----------|------|---------------|
| **データの問題** | ~30% |データが不十分、偏っている、古い、またはアクセスできない |
| **問題の定義** | ~20% | ML の問題はビジネス ニーズと一致しません。
| **期待の不一致** | ~15% |関係者は魔法を期待しています。現実は漸進的な改善です |
| **展開の失敗** | ~15% |モデルはノートブックで動作しますが、製品化することはできません |
| ** 組織の問題** | ~10% |明確な所有権がない。チームにはスキルがありません。経営陣のサポートなし |
| **モデルのパフォーマンス** | ~10% |モデルが必要な精度を達成していないか、一般化が不十分です。
---

## データ関連の障害
### 一般的なデータの問題
|問題 |説明 |例 |
|----------|---------------|----------|
| **データが不十分です** |意味のあるパターンを学ぶのに十分な例がありません | 500 件のトランザクションで不正検出モデルをトレーニングする |
| **ラベルの品質** |トレーニングのラベルが間違っている、一貫性がない、または主観的である |専門家以外によってラベル付けされた医療画像。評価者間の一致度が低い感情ラベル |
| **データ漏洩** |将来またはターゲットからの情報が機能に漏洩する |顧客離れの結果を機能として使用する。トレーニングにテストデータを含める |
| **選択バイアス** |トレーニング データは導入母集団を表すものではありません。 1 つの病院からのデータに基づいて医療モデルをトレーニングする。全国展開 |
| **コンセプトドリフト** |機能とターゲットの関係は時間の経過とともに変化します。パンデミック後に消費者の行動は変化します。パンデミック前のデータでトレーニングされたモデル |
| **機能の不一致** |トレーニング中に利用できる機能は、本番環境で利用できる機能とは異なります。手動ラベルを使用したトレーニング。生産では、異なる配布の自動ラベルが使用されます。
| **クラスの不均衡** |ターゲット クラスは大きく偏っています。 99% が陰性、1% が陽性。モデルは常に負の予測を学習します。
### データ漏洩問題
|タイプ |説明 |例 |
|------|-------------|----------|
| **ターゲットリーク** |機能は、ターゲットが発生した後にのみ使用可能になります。 「治療の成功」を予測するための特徴として使用される「治療結果」 |
| **トレーニングテストの汚染** |テストデータはトレーニングに影響を与える |グローバル統計によるスケーリング (テストデータを含む)。漏洩するデータの増強 |
| **サンプリングバイアス** |トレーニングと本番環境では異なるサンプリングが使用されます。 Web トラフィックに関するトレーニング。モバイルアプリトラフィックへの展開 |
| **前処理漏れ** |前処理ステップでは、完全なデータセットからの情報を使用します。欠損値をグローバル平均で代入する (テスト データを含む) |

## 問題定義の失敗
### 位置ずれパターン
|パターン |説明 |結果 |
|----------|---------------|---------------|
| **間違った問題を解決する** |ビジネスには X が必要です。チームは Y | を構築しますモデルは技術的には優れていますが役に立ちません |
| **ルールだけで十分な場合は ML** |問題には決定的なルールがあります。 ML により複雑さが増す |オーバースペック。維持するのが難しい。解釈が難しくなります |
| **データが存在しない場合の ML** |問題には収集されていないデータが必要です。プロジェクトを開始できません。実現可能性のために数か月を無駄にした |
| **ビジネスコンテキストのない精度目標** | 「95% の精度が必要です」 – しかし、それはビジネスにとって何を意味するのでしょうか? |モデルは精度を満たしていますが、ビジネス上の問題は解決しません |
| **エラーのコストを無視する** |偽陽性と偽陰性ではコストが異なります。モデルが間違ったメトリクスを最適化する |
| **ベースラインなし** |既存のアプローチと比較することはできません | ML が実際に単純なヒューリスティックよりも優れているかどうかはわかりません。
---

## 期待の失敗
### ML プロジェクトにおけるハイプ サイクル
|フェーズ |説明 |リスク |
|------|---------------|------|
| **興奮** | 「AIがすべてを解決してくれる！」 |期待しすぎます。リソース不足 |
| **概念実証** |モデルはノートブック内のクリーンなデータで動作します。誤った自信。 "それは動作します！" |
| **現実の確認** |本番データは乱雑です。パフォーマンスが低下します。失望; 「ML が機能しない」 |
| **デスマーチ** |チームはそれを本番環境に強制的に導入しようとします。技術的負債。燃え尽き症候群 |
| **放棄または静かな展開** |プロジェクトがキャンセルされたか、監視なしで展開されました。無駄な投資 |
### 期待を管理する
|戦略 |説明 |
|----------|---------------|
| **ベースラインから始める** |可能な限り単純なアプローチ (ルール、人間のパフォーマンス) と比較します。
| **成功指標を事前に定義する** | ML 指標 (精度、F1) だけでなく、ビジネス指標 (収益、コスト削減) |
| **タイムボックスの探索** |コミットする前に、チームに 2 ～ 4 週間かけて実現可能性を評価してもらいます |
| **ML ではできないことを示す** |制限については正直に考えてください。現実的な期待を設定する |
| **段階的に反復処理** |最初に単純なモデルをデプロイします。繰り返し改善する |
| **エラーのコストを定量化** |モデルのパフォーマンスをビジネスへの影響に変換する |

## デプロイメントの失敗
### モデルが実稼働環境に移行しない理由
|問題 |説明 |ソリューション |
|----------|---------------|----------|
| **ノートブックと生産のギャップ** |コードは Jupyter で動作しますが、本番環境には対応していません。 MLOps の実践。 ML 用の CI/CD。コードレビュー |
| **レイテンシ要件** |モデル推論はリアルタイムで使用するには遅すぎる |モデルの最適化。量子化。キャッシング |
| **スケーラビリティ** |モデルは運用トラフィックを処理できません |バッチ処理。水平方向のスケーリング。モデルサービスインフラストラクチャ |
| **ギャップの監視** |モデルの劣化を検出する方法がない |データドリフトの監視。パフォーマンスの監視。警告 |
| **依存関係の管理** |トレーニング環境とサービス環境は異なります |コンテナ化。再現可能な環境 |
| **ロールバック計画はありません** |新しいモデルに障害が発生した場合、以前のモデルに戻せない |モデルレジストリ。バージョン管理。自動ロールバック |
### モデルの崩壊
|タイプ |説明 |検出 |
|------|---------------|----------|
| **データドリフト** |入力特徴分布の変化 |機能統計を監視します。 KL ダイバージェンス。 PSI |
| **コンセプトドリフト** |機能とターゲット変更の関係 |長期にわたる予測精度を監視する |
| **ラベル ドリフト** |ターゲット変更の定義または配布 |ラベルの配布を追跡します。ビジネス指標の相関関係 |
| **上流の変更** |データ ソースの形式、タイミング、品質が変更される |スキーマの検証。鮮度モニタリング |
---

## 組織の失敗
|失敗 |説明 |予防 |
|----------|---------------|---------------|
| **明確な所有権がありません** |本番環境のモデルについては誰も責任を負いません。モデルの所有者を割り当てます。 RACI を定義する |
| **サイロ化されたチーム** |データサイエンティストはモデルを構築します。エンジニアが展開します。誰もコミュニケーションを取らない |部門横断的なチーム。共有目標 |
| **MLOps の成熟度がありません** |モデルレジストリはありません。 CI/CD なし。監視なし | MLOps インフラストラクチャに段階的に投資する |
| **非現実的なタイムライン** | 「本番環境の ML システムを 2 週間で構築」 |タイムボックスの探索。反復します。複雑さを伝える |
| **ドメインに関する専門知識の欠如** | ML チームはビジネス上の問題を理解していません | ML チームにドメインの専門家を組み込む |
| **評価枠組みなし** |モデルが本番環境で動作しているかどうかがわかりません |ビジネス指標を定義します。ダッシュボードをセットアップする。定期的なレビュー |

## 学んだ教訓
### ML プロジェクトのチェックリスト
|フェーズ |重要な質問 |
|------|-----------|
| **問題の定義** |これは実際に ML の問題なのでしょうか?ベースラインは何ですか?成功とはどのようなものでしょうか? |
| **データ評価** |十分なデータはありますか?代表的なものでしょうか？ラベルは信頼できるものですか? |
| **実現可能性** |実用的なプロトタイプを 2 ～ 4 週間で構築できますか?リスクは何ですか? |
| **開発** |データ漏洩はありますか?適切な評価指標を使用しているでしょうか? |
| **プリプロダクション** |実稼働データでも機能しますか?十分速いですか?監視されていますか？ |
| **展開** |ロールバックできますか?誰がオンコールですか?劣化するとどうなるのでしょうか？ |
| **展開後** |ドリフトを監視していますか?ビジネス指標は追跡されていますか?再研修計画はありますか? |

＃＃ まとめ
ML プロジェクトが失敗するのは、アルゴリズムが難しすぎるためではなく、その周りのプロセスが壊れているためです。データの問題 (データ不足、不適切なラベル、漏洩、ドリフト) が、障害の最大の割合を占めています。問題定義の失敗、つまり間違った問題を解決したり、ルールで十分な場合に ML を使用したり、エラーのコストを無視したりすると、数か月の労力が無駄になります。過剰な約束、不十分な成果、利害関係者の管理不足など、期待の失敗は、ML に対する組織の信頼を破壊します。デプロイメントの失敗 (ノートブックと本番環境のギャップ、レイテンシーの問題、モニタリングの欠如) は、開発で機能するモデルが本番環境では価値を生み出さないことを意味します。組織の失敗 (オーナーシップの欠如、サイロ化されたチーム、MLOps の欠如) により、構造的に成功することが不可能になります。解毒剤は規律ある練習です。ベースラインから始めます。タイムボックスの探索。データを厳密に検証します。漏れがないか確認します。ビジネス指標を定義する。段階的にデプロイします。継続的に監視する。そしてそれを繰り返します。優れた ML チームは、モデルよりもデータとプロセスに多くの時間を費やします。
