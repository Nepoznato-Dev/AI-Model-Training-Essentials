# パフォーマンスの最適化
パフォーマンスの最適化とは、応答時間の短縮、スループットの向上、メモリ使用量の削減、ボトルネックの排除などにより、ソフトウェアを高速化する実践です。これは、開発者が持つことができる最も影響力のあるスキルの 1 つです。なぜなら、ソフトウェアが遅いとユーザーを失い、リソースが無駄になり、全員がイライラするからです。しかし、これは最もよく行われる間違いの 1 つでもあり、開発者は証拠ではなく直感に基づいて間違ったことを最適化します。
---

## 黄金律
> **最初に測定し、次に最適化します。** 仮定に基づいて最適化しないでください。コードをプロファイリングし、実際のボトルネックを見つけて修正します。
|アンチパターン |なぜダメなのか |
|---------------|---------------|
| **時期尚早な最適化** |遅くないコードを高速化するために時間を費やす |
| **測定を行わない最適化** |間違ったボトルネックを修正する。改善を確認する方法がない |
| **速度のために読みやすさを犠牲にする** |判読できないコードはパフォーマンスの向上よりもコストがかかります。
| **すべてをキャッシュする** |古いデータ、メモリの肥大化、複雑さ |
---

## プロファイリング
何かをより速く作成する前に、「どこに」時間が費やされているかを知る必要があります。
|ツールの種類 |何を測定するのか |例 |
|----------|------|----------|
| **CPU プロファイラー** |どの関数が最も多くの CPU 時間を消費するのか | cProfile (Python)、perf (Linux)、Chrome DevTools (JS) |
| **メモリ プロファイラー** |メモリ割り当てとリーク | Tracemalloc (Python)、Valgrind、heaptrack |
| **I/O プロファイラー** |ディスクとネットワークの I/O ボトルネック | iotop、strace、Wireshark |
| **APM (アプリケーション パフォーマンス監視)** |エンドツーエンドのリクエストのタイミング | New Relic、Datadog、Jaeger |
| **ブラウザ開発ツール** |フロントエンド レンダリング、JavaScript 実行、ネットワーク | Chrome DevTools、Firefox プロファイラー |
### プロファイリングのワークフロー
|ステップ |説明 |
|------|---------------|
| 1. 遅い動作を特定する |ユーザーはページの読み込みが遅いと報告しています。モニタリングにより高い遅延が示される |
| 2. フルパスのプロファイルを作成します |どのコンポーネントに最も時間がかかるかを調べる |
| 3. ドリルダウン |その特定のコンポーネントをプロファイリングして、ホットな機能を見つけます。
| 4. ボトルネックを修正する |適切な最適化を適用します。
| 5. 再度測定 |改善を確認します。回帰をチェックする |
---

## アルゴリズムの最適化
パフォーマンスの最大の向上は、微細な最適化ではなく、より優れたアルゴリズムを選択することによってもたらされます。
|変更 |改善 |
|------|-----------|
|線形検索 O(n) → ハッシュ テーブル検索 O(1) |大規模なデータセットの場合は 100 倍以上 |
|入れ子ループ O(n²) → ソート + 二分探索 O(n log n) | n が大きい場合は桁違い |
|繰り返し計算 → メモ化 / キャッシュ |余分な作業を排除 |
|ループ内の文字列連結 → Builder / join |文字列の 2 次コピーを回避します。
|ソートされていないデータ → 二分探索でソートされたデータ |検索ごとに O(n) ではなく O(log n) |
---

## キャッシュ戦略
キャッシュにより計算結果が保存されるため、再計算する必要がありません。
|キャッシュの種類 |場所 |スピード |生涯 |
|----------|----------|----------|----------|
| **CPU キャッシュ** | L1/L2/L3 | ~1ns |自動 |
| **インメモリ** |アプリケーション RAM (辞書、ハッシュマップ) | ~100ns |許可または立ち退きがされるまで |
| **分散キャッシュ** | Redis、Memcached | ~1 ミリ秒 |構成可能な TTL |
| **CDN** |世界中のエッジサーバー | ～10～50ミリ秒 |構成可能な TTL |
| **ブラウザ キャッシュ** |ユーザーのブラウザ | ~1 ミリ秒 | HTTP キャッシュ ヘッダー |
| **データベース クエリ キャッシュ** |データベースまたは ORM レベル | ~1 ～ 10 ミリ秒 |データが変更されるまで |
### キャッシュパターン
|パターン |説明 |いつ使用するか |
|----------|---------------|---------------|
| **キャッシュアサイド** |アプリケーションはキャッシュをチェックします。ミス時に DB からロードします。キャッシュに保存する |最も一般的です。シンプル |
| **ライトスルー** |キャッシュと DB に同時に書き込み |読み取り >> 書き込みの場合一貫性が重要 |
| **後書き** |キャッシュに書き込みます。 DB への非同期書き込み |高い書き込みスループット。ある程度のデータ損失のリスク |
| **TTL (生存時間)** |キャッシュ エントリは設定された時間が経過すると期限切れになります。データが定期的に変更される場合 |
| **無効化** |古いキャッシュ エントリを明示的に削除する |データがいつ変更されるかを正確に知っている場合 |
### キャッシュの無効化
コンピューター サイエンスにおける 2 つの最も困難な問題: キャッシュの無効化、名前の付け方、およびオフバイワン エラーです。
|戦略 |説明 |
|----------|---------------|
| **TTL ベース** |エントリは N 秒後に期限切れになります。シンプルですが、古いデータが提供される可能性があります。
| **イベント駆動型** |データが変更されると無効になります。より複雑だが正確 |
| **バージョンベース** |バージョン番号を含めます。変更時に増分 |
| **タグベース** |タグ関連のキャッシュ エントリ。タグを持つすべてのエントリを無効にする |

## データベースの最適化
多くの場合、データベースは Web アプリケーションにおける最大のボトルネックになります。
|テクニック |説明 |影響 |
|----------|---------------|----------|
| **インデックス作成** | WHERE、JOIN、ORDER BY | で使用される列にインデックスを追加します。 10 ～ 1000 倍高速なクエリ |
| **クエリの最適化** | SELECT * は避けてください。 EXPLAIN を使用してクエリを分析する | I/O を削減 |
| **接続プーリング** |新しいデータベース接続を作成する代わりにデータベース接続を再利用する |接続のオーバーヘッドを排除 |
| **リードレプリカ** |読み取りクエリをレプリカ データベースにルーティングする |読み取り負荷を分散する |
| **パーティショニング** |大きなテーブルを小さなパーティションに分割する |大規模なデータセットに対するクエリの高速化 |
| **非正規化** |結合を避けるために冗長データを追加する |読み取りが高速化。書き込みが遅い |
| **具体化されたビュー** |事前に計算されたクエリ結果 |複雑なクエリを即座に実行 |
| **N+1 防止** | JOIN、一括読み込み、またはバッチ クエリを使用する |数千のクエリを排除 |
---

## 同時実行性と並列処理
|コンセプト |説明 |いつ使用するか |
|----------|---------------|---------------|
| **スレッド** |単一プロセス内の複数のスレッド | I/O バウンドのタスク (ネットワーク、ディスク) |
| **マルチプロセッシング** |複数のプロセス (Python で GIL をバイパス) | CPU バウンドのタスク |
| **非同期/待機** |協調的なマルチタスク。シングルスレッド |同時実行性の高い I/O (Web サーバー) |
| **GPU コンピューティング** |数千の並列コア |行列演算。画像処理。 ML |
### 非同期とスレッド
|側面 |非同期/待機 |スレッド |
|----------|-----------|----------|
| **モデル** |協同組合（タスク収量管理） |プリエンプティブ (OS はスレッドを切り替えます) |
| **オーバーヘッド** |非常に低い (コンテキスト切り替えなし) |上位 (スレッド作成、コンテキスト切り替え) |
| **複雑さ** |より単純な推論 (シングルスレッド) |競合状態、デッドロック、ロック |
| **こんな用途に最適** |多くの同時 I/O 操作 |非同期にできない操作をブロックする |
| **制限事項** |ブロックせずに CPU バウンドのコードを使用することはできません。 Python の GIL は真の並列処理を制限します。

## フロントエンドのパフォーマンス
|テクニック |説明 |影響 |
|----------|---------------|----------|
| **縮小化** |空白を削除し、変数名を短くします。ファイルが 20 ～ 40% 小さくなる |
| **バンドル** |複数のファイルを少数のリクエストに結合する | HTTP リクエストの削減 |
| **コード分割** |現在のページに必要なコードのみをロードします |初期ロードの高速化 |
| **遅延読み込み** |必要なときに画像とコンポーネントをロードする |初期レンダリングの高速化 |
| **木の揺れ** |バンドルから未使用のコードを削除する |より小さなバンドル |
| **画像の最適化** | WebP/AVIF を使用します。レスポンシブな画像。遅延読み込み |画像を 50 ～ 80% 小さく |
| **CDN** |エッジサーバーから静的資産を提供する |グローバルなレイテンシーの低減 |
| **HTTP/2 と HTTP/3** |多重化。ヘッダー圧縮。 0-RTT |プロトコルのオーバーヘッドの高速化 |
| **サービスワーカー** |オフラインで使用できるように資産をキャッシュします。プッシュ通知 |再訪問の迅速化 |

## メモリの最適化
|テクニック |説明 |
|----------|---------------|
| **オブジェクト プーリング** |新しいオブジェクトを作成する代わりにオブジェクトを再利用する |
| **ストリーミング** |すべてをメモリにロードするのではなく、データをチャンクに分けて処理します。
| **ジェネレータ / イテレータ** |リストを作成する代わりに、一度に 1 つずつ値を生成します。
| **メモリマップされたファイル** |大きなファイルを完全にロードせずにアクセスする |
| **ガベージ コレクションのチューニング** |ワークロードに合わせて GC パラメーターを調整する |
| **データ構造の選択** |キャッシュの局所性を確保するには、リンク リストの代わりに配列を使用します。メンバーシップのテストにセットを使用する |
---

## ネットワークの最適化
|テクニック |説明 |
|----------|---------------|
| **圧縮** | HTTP 応答用の gzip、brotli |
| **接続の再利用** |キープアライブ接続。 HTTP/2 多重化 |
| **リクエストのバッチ処理** |複数の API 呼び出しを 1 つに結合する |
| **ページネーション** |データを一度にすべてではなくページ単位でロードする |
| **静止時の圧縮** |データベースとキャッシュ内のデータを圧縮する |
| **プロトコルの選択** | gRPC (バイナリ、効率的) vs REST (人間が読める形式) |

＃＃ まとめ
パフォーマンスの最適化は、測定、ボトルネックの特定、修正、再測定という体系的なプロセスです。最大の成果は、微細な最適化ではなく、アルゴリズムの改善と不必要な作業の排除によってもたらされます。キャッシュ、データベースのインデックス作成、同時実行は最も強力なツールです。フロントエンドのパフォーマンスは、ペイロード サイズとラウンドトリップを最小限に抑えることに依存します。そして最も重要なルールは常に同じです。「推測しないでください。プロフィール」です。
