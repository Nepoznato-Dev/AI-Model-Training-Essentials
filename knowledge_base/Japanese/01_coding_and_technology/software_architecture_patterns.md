# ソフトウェア アーキテクチャ パターン
アーキテクチャとは、システムがどのように構成されているか、つまりどのコンポーネントがあり、それらがどのように通信し、責任がどこにあるのかについての一連の構造的な決定です。優れたアーキテクチャにより、システムの理解、変更、拡張が容易になります。アーキテクチャが悪いと、あらゆる変更が困難になります。このファイルでは、主要なパターン、それぞれをいつ使用するか、およびそれに伴うトレードオフについて説明します。
---

## モノリスとマイクロサービス
これはアーキテクチャ上の最も基本的な決定であり、正しく行う価値があります。
|側面 |モノリス |マイクロサービス |
|----------|----------|----------|
| **構造** |単一の展開可能なユニット |多数の小規模で独立して展開可能なサービス |
| **データ** |共有データベース |各サービスは独自のデータを所有します。
| **コミュニケーション** |インプロセス関数呼び出し |ネットワーク呼び出し (HTTP、gRPC、メッセージング) |
| **スケーリング** |アプリケーション全体をスケールする |個々のサービスを拡張する |
| **展開** |単一リリースサイクル |独立した展開 |
| **複雑さ** |最初の開発が簡単 |運用の複雑さ (ネットワーキング、監視) |
| **最適な用途** |小規模チーム、初期段階の製品 |大規模なチーム、複雑なドメイン、大規模 |
### モノリスをいつ始めるか
ほとんどのアプリケーションはモノリスとして開始する必要があります。構築、テスト、デプロイ、デバッグがより簡単になります。ドメインの境界を明確に把握できたら、後でいつでもサービスを抽出できます。これは、「モジュラー モノリス」と呼ばれることもあります。これは、後で簡単に抽出できるように、内部境界がきれいなモノリスです。
### マイクロサービスを使用する時期
次の場合にマイクロサービスを検討してください。
- チームの規模が大きいため、調整がボトルネックになります。
- システムの異なる部分には、非常に異なるスケーリング要件があります。
- コンポーネントを独立して展開する必要がある。
- ドメインには明確に境界付けられたコンテキストがあります (下記の DDD を参照)。

## 階層化アーキテクチャ (N 層)
最も一般的なアーキテクチャ パターン。コードは複数の層に編成されており、それぞれに特定の責任があります。
```
â”Œ─────────────────────────┐
│   Presentation Layer    │  ← UI, controllers, API endpoints
├─────────────────────────┤
│   Application Layer     │  ← Use cases, orchestration
├─────────────────────────┤
│   Domain Layer          │  ← Business logic, entities
├─────────────────────────┤
│   Infrastructure Layer  │  ← Database, external services, file I/O
└─────────────────────────┘
```

|レイヤー |責任 |ルール |
|------|------|------|
| **プレゼンテーション** |ユーザー/HTTP リクエストを処理する |アプリケーション層のみを呼び出すことができます |
| **アプリケーション** |ユースケースを調整する |ドメイン層を呼び出すことができます |
| **ドメイン** |コアビジネスロジック |他のレイヤーに依存しないでください。
| **インフラストラクチャ** |技術的な懸念事項 | Domain | で定義されたインターフェイスを実装します。
**重要なルール**: 依存関係は内側を向いています。ドメイン層はデータベースや Web フレームワークについては知りません。

## イベント駆動型アーキテクチャ
コンポーネントは、**イベント** (起こったこと) を発行し、それに反応することで通信します。
|パターン |説明 |
|----------|---------------|
| **イベントのお知らせ** |サービス A は「OrderPlaced」を発行します。サービス B、C、D が反応する |
| **イベントソーシング** |すべての状態変化を (現在の状態だけでなく) 一連のイベントとして保存します。
| **CQRS** |読み取りモデル (クエリ) を書き込みモデル (コマンド) から分離する |
### イベントソーシング
「現在の状態」をデータベースに保存する代わりに、すべての状態変化をイベントとして保存します。
```
OrderCreated(order_id=123, total=$50)
OrderPaid(order_id=123, payment_id=456)
OrderShipped(order_id=123, tracking=ABC)
```

利点: 完全な監査証跡、過去の状態を再構築する機能、消費者を分離します。課題: イベントスキーマの進化、結果整合性、デバッグの複雑さ。
### CQRS (コマンドクエリ責任分離)
|側面 |目的 |データベース |
|------|--------|----------|
| **コマンド (書き込み)** |突然変異を処理します。ビジネスルールを強制する |書き込み用に最適化 (正規化) |
| **クエリ (読み取り)** |読み取りリクエストを処理する |読み取り用に最適化 (非正規化) |
CQRS はイベント ソーシングと自然に組み合わされます。書き込み側からのイベントは読み取りに最適化されたビューに投影されます。

## メッセージ キューとイベント ブローカー
サービスが非同期通信する必要がある場合、メッセージ キューがバックボーンとなります。
|ツール |タイプ |最適な用途 |
|------|------|----------|
| **Apache Kafka** |分散イベントログ |高スループットのイベント ストリーミング、イベント ソーシング |
| **ウサギMQ** |ルーティングを備えたメッセージ ブローカー |タスクキュー、複雑なルーティングパターン |
| **AWS SQS** |マネージドキュー | AWS ネイティブのシンプルなキューイング |
| **AWS SNS** |パブリッシュ/サブスクライブ通知 |複数の加入者へのファンアウト |
| **Google Pub/Sub** |マネージド パブ/サブ | GCP ネイティブ イベント ストリーミング |
| **Redis ストリーム** |軽量ストリーム |単純なイベントログ、キャッシュの使用例 |
### メッセージング パターン
|パターン |説明 |
|----------|---------------|
| **ポイントツーポイント** |メッセージごとに 1 つのプロデューサー、1 つのコンシューマー |
| **発行/購読** | 1 人のプロデューサー、複数のサブスクライバー |
| **リクエスト/返信** |非同期トランスポートを介した同期スタイル |
| **配信不能キュー** |処理に失敗したメッセージは、検査のために別のキューに送られます。

## ドメイン駆動設計 (DDD)
DDD は、技術的な問題ではなくビジネス コンセプトを中心にコードを集中させるソフトウェア設計への戦略的アプローチです。
### 主要な概念
|コンセプト |説明 |
|----------|---------------|
| **境界されたコンテキスト** |ドメイン モデルが一貫している境界 (例: 「注文」、「配送」、「請求」) |
| **ユビキタス言語** |開発者とドメイン専門家の間で共通の語彙 |
| **集計** |関連エンティティのクラスターはデータ変更の単一単位として扱われます。
| **エンティティ** | ID を持つオブジェクト (例: user_id を持つユーザー) |
| **値オブジェクト** |アイデンティティのないオブジェクト。属性 (例: お金、住所) によって定義されます。
| **ドメイン イベント** |ドメイン内で起こった何か (例: OrderPlaced) |
| **腐敗防止層** |ドメインと外部システム間の変換層 |
### DDD が役立つ場合
DDD は、電子商取引、物流、金融サービス、ヘルスケアなど、ビジネス ドメインが複雑な場合に最も価値があります。ドメインが単純 (ブログ、ToDo アプリ) の場合、DDD は過剰です。
---

## キャッシュ戦略
キャッシュはパフォーマンスを向上させる最も効果的な方法の 1 つですが、一貫性に関して複雑さが生じます。
|戦略 |説明 |トレードオフ |
|----------|---------------|----------|
| **キャッシュアサイド** |アプリケーションは最初にキャッシュをチェックします。ミス時に DB からロード |単純;最終的な整合性 |
| **ライトスルー** |キャッシュと DB に同時に書き込み |一貫性のある;書き込みが遅い |
| **後書き** |キャッシュに書き込みます。 DB への非同期書き込み |高速書き込み。データ損失のリスク |
| **お読みください** |ミス時に DB からのロードを透過的にキャッシュします。キャッシュアサイドよりもシンプル |
### 何をキャッシュするか
|レイヤー |何を |ツール |
|------|------|------|
| **CDN** |静的アセット、API レスポンス | CloudFront、Cloudflare |
| **アプリケーション** |計算結果、セッションデータ | Redis、Memcached |
| **データベース** |クエリ結果、頻繁にアクセスされる行 |クエリ キャッシュ、マテリアライズド ビュー |
**キャッシュの無効化**は難しいことで知られています。一般的な戦略: TTL (存続時間)、イベント駆動型の無効化 (データ変更時のキャッシュのクリア)、および LRU (最も最近使用されていないもの) の削除。

## デザインパターン
### 確固たる原則
|原則 |意味 |
|----------|--------------|
| **S** — 単一責任 |クラスには、変更する理由が 1 つある必要があります。
| **O** — オープン/クローズ |拡張用にオープン、変更用にクローズ |
| **L** — リスコフの置換 |サブタイプはその基本タイプと置き換え可能である必要があります。
| **I** — インターフェイスの分離 |多数の特定のインターフェイス > 1 つの汎用インターフェイス |
| **D** — 依存関係の反転 |具体化ではなく抽象化に依存する |
### 一般的なパターン
|パターン |意図 |例 |
|----------|----------|----------|
| **シングルトン** |クラスにインスタンスが 1 つだけあることを確認してください。データベース接続プール |
| **工場** |正確なクラスを指定せずにオブジェクトを作成する | `UserFactory.create(type="admin")`|
| **観察者** |状態が変化したときに扶養家族に通知する |イベント リスナー、パブリッシュ/サブスクライブ |
| **戦略** |実行時にアルゴリズムを交換する |支払い戦略: クレジットカード、PayPal、暗号通貨 |
| **リポジトリ** |クリーンなインターフェイスの背後にある抽象的なデータ アクセス | `UserRepository.find_by_id(123)`|
| **デコレーター** |動作を動的に追加する |サービス周りのロギングデコレータ |
| **アダプター** |互換性のないインターフェイスを連携させる |レガシー API アダプター |

## 適切なアーキテクチャの選択
普遍的に「最適な」アーキテクチャはありません。正しい選択は以下によって決まります。
|係数 |モノリスを支持するのは次の場合です... |次の場合はマイクロサービスを優先します... |
|--------|------------------------|----------------------------|
| **チームの規模** | < 10 developers | >20 人の開発者、複数のチーム |
| **ドメインの複雑さ** |シンプルまたはよく理解できる |複雑で多くの境界のあるコンテキスト |
| **スケール要件** |均一なスケーリングのニーズ |コンポーネントが異なれば、必要なスケールも異なります。
| **導入頻度** |単一リリースサイクル |独立した展開が必要 |
| **テクノロジーの多様性** | 1 つのスタックで問題ありません |サービスが異なれば、必要な技術も異なります。
**実践的なアドバイス**: モジュール式モノリスから始めます。明確なニーズと明確なドメイン境界がある場合にのみ、サービスを抽出します。時期尚早なマイクロサービスは、業界で最も一般的なアーキテクチャ上の間違いの 1 つです。
