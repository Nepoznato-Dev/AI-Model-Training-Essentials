# サイバーセキュリティの基礎
セキュリティは、後付けで追加するのではなく、最初からシステムのすべての層に統合する必要がある規律です。 Web アプリケーションの構築、インフラストラクチャの管理、API の配布のいずれにおいても、脅威の状況と防御の基本を理解することが不可欠です。
---

## 暗号化と暗号化
### 対称暗号化と非対称暗号化
|タイプ |仕組み |スピード |キーの配布 |例 |
|------|---------------|----------|------|----------|
| **対称** |暗号化と復号化に同じキー |速い |課題: キーを共有する方法は? | AES-256、チャチャ20 |
| **非対称** |公開鍵で暗号化、秘密鍵で復号化 |遅い |公開鍵はオープンに共有できる | RSA、ECC (楕円曲線) |
実際には、ほとんどのシステムは**両方**を使用します。対称キーを安全に交換するために非対称暗号化を使用し、その後、大部分のデータに対して対称暗号化を使用します。これが TLS/HTTPS の仕組みです。
### ハッシュ化
ハッシュは一方向関数です。入力を固定サイズの文字列に変換します。これを逆にすることはできませんが、同じ入力からは常に同じ出力が生成されます。
|使用例 |推奨アルゴリズム |避ける |
|----------|----------------------|----------|
| **パスワードの保管** | Argon2id、bcrypt、暗号化 | MD5、SHA-1、プレーン SHA-256 (速すぎる) |
| **データの整合性** | SHA-256、SHA-3 | MD5 (壊れた)、SHA-1 (壊れた) |
| **デジタル署名** | Ed25519、RSA-2048+ | DSA |
### TLS/HTTPS
HTTPS は HTTP over TLS (Transport Layer Security) です。それは以下を提供します:
- **暗号化**: 転送中のデータは盗聴者によって読み取られることはありません。
- **認証**: サーバーは証明書を通じてその身元を証明します。
- **整合性**: 転送中に検出されずにデータが変更されることはありません。
TLS 1.2 または 1.3 を使用します。 TLS 1.0 および 1.1 を無効にします。 HSTS (HTTP Strict Transport Security) を有効にして、ブラウザに常に HTTPS の使用を強制します。

## 認証と認可
### 認証: あなたは誰ですか?
|方法 |セキュリティレベル |使用例 |
|----------|------|----------|
| **パスワード** |低～中 |基本アカウント (12 文字以上を強制し、違反をチェック) |
| **MFA (TOTP)** |高 |機密性の高いアカウントの標準 (Google Authenticator、Authy) |
| **ハードウェア キー (FIDO2/WebAuthn)** |非常に高い |高セキュリティアカウント (YubiKey) |
| **生体認証** |中～高 |デバイスのロック解除 (指紋、顔) — 唯一の要素としてはあまり良くない |
| **OAuth2 / OIDC** |高 |サードパーティのログイン (「Google でサインイン」) |
**パスワード ルール**: 最小長 (12 ～ 16 文字) を強制し、違反したパスワード リストをチェックし、ユーザーごとのソルトによるハッシュに Argon2id または bcrypt を使用します。
### 権限: 何ができるのですか?
|モデル |説明 |例 |
|----------|---------------|----------|
| **RBAC** (ロールベースのアクセス制御) |ロールに割り当てられた権限。ユーザーはロールを取得します |管理者、編集者、閲覧者 |
| **ABAC** (属性ベース) |ユーザー属性、リソース、環境に基づくルール | 「マネージャーはチームのリクエストを承認できます」 |
| **ACL** (アクセス制御リスト) |ユーザー/リソースごとの明示的なアクセス許可 |ファイル権限 (読み取り/書き込み/実行) |
**最小特権の原則**: すべてのユーザー、サービス、プロセスに必要な最小限のアクセス権のみを与えます。
### JWT (JSON Web トークン)
|側面 |推薦 |
|------|------|
| **署名** | RS256 または ES256 (非対称) が推奨されます。 HS256 は管理シークレットで許容可能 |
| **有効期限** |アクセス トークンの場合は 15 ～ 60 分。より長いセッションにはリフレッシュ トークンを使用します。
| **ストレージ** | HTTP のみの Cookie (localStorage ではない - XSS に対して脆弱) |
| **検証** |署名、発行者、対象者、有効期限を常に検証する |

## OWASP トップ 10 (2021)
OWASP Top 10 は、Web アプリケーションのセキュリティに関する標準的な啓発文書です。これは最も重大なリスクを表します。
| # |リスク |意味 |
|---|------|--------------|
| 1 | **アクセス制御の違反** |ユーザーがアクセスすべきではないリソースにアクセスできる |
| 2 | **暗号化の失敗** |機密データの暗号化が弱い、または暗号化されていない |
| 3 | **注射** | SQL、NoSQL、OS コマンド、または LDAP インジェクション |
| 4 | **安全でない設計** |実装では修正できないアーキテクチャ上の欠陥 |
| 5 | **セキュリティの設定ミス** |デフォルトのパスワード、開いているポート、詳細なエラー メッセージ |
| 6 | **脆弱なコンポーネント** |依存関係における既知の CVE |
| 7 | **認証の失敗** |弱いパスワード、セッション管理の誤り |
| 8 | **整合性の失敗** |サプライチェーン攻撃、署名のないアップデート |
| 9 | **ログ/モニタリング障害** |侵害は検出されません |
| 10 | **SSRF** |サーバーがだまされて内部システムにリクエストを送信する |

## 安全なコーディングの実践
### 入力の検証
|ルール |なぜ |
|------|-----|
| **ホワイトリスト > ブラックリスト** |何をブロックするかではなく、何を許可するかを定義する |
| **パラメータ化されたクエリ** |ユーザー入力を SQL に連結しないでください。プリペアド ステートメントまたは ORM を使用してください。
| **HTML エンコーディング** | XSS を防ぐために`<`、`>`、`&`、`"`、`'`をエンコードします。
| **シェルエスケープ** |ユーザー入力からシェルコマンドを構築することは避けてください。`shlex.quote()`を使用する |
| **長さの制限** |バッファ オーバーフローや DoS を防ぐために最大長を強制します。
| **型チェック** |整数が整数であること、ブール値がブール値であることを確認してください。
### 一般的な脆弱性
|脆弱性 |攻撃 |ディフェンス |
|--------------|--------|----------|
| **SQL インジェクション** |  ログインフォームの`' OR 1=1 --` |パラメータ化されたクエリ |
| **XSS** |  コメント欄に`<script>alert('hacked')</script>`|出力エンコーディング、コンテンツ セキュリティ ポリシー |
| **CSRF** |ユーザーのブラウザをだまして不正なリクエストを行わせる | CSRF トークン、SameSite Cookie |
| **パストラバーサル** |  ファイルパラメータ内の`../../etc/passwd`|ファイル パスの検証とサニタイズ |
| **アイドル** |他の人のデータを表示するには、`/user/123` を`/user/124`に変更します。すべてのリクエストに対する認可チェック |

## ネットワークセキュリティ
### ファイアウォール
|タイプ |説明 |
|------|---------------|
| **パケットフィルタリング** | IP、ポート、プロトコルに基づくルール |
| **ステートフル** |接続状態を追跡します。よりインテリジェントなフィルタリング |
| **アプリケーション レベル (WAF)** | HTTP トラフィックを検査します。 SQL インジェクション、XSS などをブロックします。
| **クラウド セキュリティ グループ** |クラウド インスタンス用の仮想ファイアウォール (AWS SG、Azure NSG) |
**経験則**: デフォルトではすべての受信トラフィックをブロックします。明示的に必要なものだけを開きます (Web の場合は 80、443)。
### ネットワークのセグメンテーション
インターネットに直接アクセスできないプライベート サブネットにデータベースとキャッシュを配置します。公開サービス (Web サーバー、ロード バランサー) には DMZ を使用します。ネットワーク アクセスに最小特権の原則を適用します。

## 秘密の管理
### 黄金律
**シークレットをハードコードしないでください。** ソース コードに API キー、パスワード、データベース URL を含めないでください。 Git にコミットされた環境変数にシークレットはありません。 Docker イメージにはシークレットはありません。
### ツール
|ツール |タイプ |最適な用途 |
|------|------|----------|
| **HashiCorp 保管庫** |エンタープライズ シークレット マネージャー |動的なシークレット、サービスとしての暗号化 |
| **AWS Secrets Manager** |クラウドネイティブ | AWS 環境 |
| **Azure Key Vault** |クラウドネイティブ | Azure環境 |
| **SOPS** |暗号化されたファイル | Git でシークレットを暗号化する (KMS または GPG を使用) |
| **Docker の秘密** |コンテナネイティブ | Docker Swarm (K8 の場合は、Secrets Store CSI を検討してください) |
| **dotenv (.env)** |地域開発 |開発のみ — 運用やコミットは決して行われません |
### 回転
シークレットを定期的かつ自動的にローテーションします。シークレットが漏洩した場合 (例: パブリック リポジトリにコミットされた場合)、誰も見ていないと思われる場合でも、直ちにシークレットをローテーションしてください。

## 依存関係のセキュリティ
アプリケーションの安全性は、その最も弱い依存関係によって決まります。
### スキャンツール
|言語 |ツール |
|----------|----------|
| **Python** | `safety`、`pip-audit`、`bandit`|
| **Node.js** |  `npm audit`、`yarn audit`、`snyk` |
| **錆** | `cargo audit`|
| **行く** | `govulncheck`|
| **一般** | `Dependabot`(GitHub)、`Renovate`、`Trivy` |
### サプライチェーンの完全性
- Use lockfiles (`package-lock.json`, `Cargo.lock`, `go.sum`) for reproducible builds.
- ダウンロードされた依存関係のチェックサムを検証します。
- Prefer official registries and verified publishers.
- Automate minor/patch updates via Dependabot or Renovate.

## セキュリティ開発ライフサイクル (SDL)
|フェーズ |アクティビティ |
|------|----------|
| **トレーニング** |開発者が一般的な脆弱性を確実に理解できるようにする |
| **脅威モデリング** |設計中に潜在的な脅威を特定する |
| **安全なコーディング標準** |リンターとコードレビューチェックリストを介して強制する |
| **SAST** |ソースコードの静的解析（SonarQube、CodeQL） |
| **ダスト** |実行中のアプリケーションの動的分析 (OWASP ZAP、Burp Suite) |
| **SCA** |ソフトウェア構成分析 - 依存関係のスキャン |
| **侵入テスト** |定期的な倫理的ハッキング演習 |
| **バグ報奨金** |外部の研究者に脆弱性を発見するよう奨励する |
| **インシデント対応計画** |侵害が検出されたときの明確な計画を立てる |

## 緊急時のチェックリスト
侵害の疑いがある場合:
1. **パニックに陥らないでください** – ただし、すぐに行動してください。
2. 影響を受けるシステムを **隔離**します (必要に応じてネットワークから切断します)。
3. **証拠を保存**: ログ、メモリ ダンプ、ディスク イメージをキャプチャします。
4. **範囲を特定する**: どのシステム、どのデータですか?
5. 侵害されたすべての資格情報とシークレットを **ローテーション**します。
6. 脆弱性を**パッチ**します。
7. 必要に応じて (法定の期限内に) 影響を受けるユーザーと規制当局に **通知** します。
8. **事後分析**: 24 ～ 48 時間以内に根本原因とアクション項目を文書化します。
