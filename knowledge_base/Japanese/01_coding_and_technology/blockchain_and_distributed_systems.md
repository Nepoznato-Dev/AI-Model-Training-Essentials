# ブロックチェーンと分散システム
ブロックチェーンは、特定の種類の分散システムです。記録 (ブロック) が暗号化ハッシュによってリンクされている、分散型の追加専用台帳です。分散システムは、複数のコンピュータを 1 台として連携させる広範な分野です。どちらの概念も、暗号通貨から分散データベース、グローバル サービスを強化するコンセンサス アルゴリズムに至るまで、最新のインフラストラクチャを理解するために重要です。
---

## 分散システムの基礎
### なぜ分散システムなのか?
|モチベーション |説明 |
|----------|---------------|
| **スケーラビリティ** |より多くの負荷を処理するにはマシンを追加します。
| **フォールトトレランス** |一部のマシンに障害が発生しても、システムは動作し続けます。
| **地理的分布** |近くのデータセンターからユーザーにサービスを提供 |
| **専門分野** |異なるマシンは異なるタスクを処理します。
### 主要な概念
|コンセプト |説明 |チャレンジ |
|----------|---------------|----------|
| **コンセンサス** |すべてのノードを値に同意させる |ネットワークパーティション。ビザンチン断層 |
| **レプリケーション** |複数のノード間でのデータのコピー |一貫性と可用性 |
| **パーティショニング (シャーディング)** |ノード間でのデータの分割 |ホットスポット。クロスシャードクエリ |
| **一貫性モデル** |さまざまな読者に何が表示されるかを保証 |強い一貫性は遅いです。最終的な整合性はユーザーを驚かせる可能性があります。
| **CAP 定理** |一貫性、可用性、パーティション許容度のうち 2 つだけを持つことができます。実際には、分割耐性が必要です。 C または A を選択します |
### CAP定理
|選択 |得られるもの |あなたが諦めるもの |例 |
|----------|---------------|------|----------|
| **CP** |一貫性 + パーティション耐性 |一部のノードはパーティション分割中に使用できない場合があります。 HBase、MongoDB、Redis |
| **AP** |利用可能 + パーティショントレラント |読み取りにより古いデータが返される場合があります。 Cassandra、DynamoDB、CouchDB |
| **カリフォルニア** |一貫性のある + 利用可能 |ネットワークの分断を許容できない |単一ノード データベース (完全に分散されていない) |

## コンセンサスアルゴリズム
分散ノードはシステムの状態についてどのように合意するのでしょうか?
|アルゴリズム |タイプ |フォールトトレランス |使用場所 |
|----------|------|-----|----------|
| **パクソス** |クラッシュフォールトトレラント | 2f+1 ノードで最大 f 個の障害 | Google ぽっちゃり;基礎理論 |
| **ラフト** |クラッシュフォールトトレラント | 2f+1 ノードで最大 f 個の障害 | etcd、領事、TiKV |
| **PBFT** |ビザンチンフォールトトレラント | 3f+1 ノードで最大 f 個の障害 |ハイパーレジャーファブリック |
| **作業証明** |ビザンチンフォールトトレラント |ハッシュパワーに依存 |ビットコイン |
| **ステークの証明** |ビザンチンフォールトトレラント |賭け金に応じて |イーサリアム 2.0、カルダノ |
### ラフト (簡略化)
|役割 |責任 |
|------|---------------|
| **リーダー** |すべてのクライアント要求を処理します。ログエントリをフォロワーに送信します |
| **フォロワー** |リーダーのリクエストに応えます。選挙の投票 |
| **候補者** |リーダーになるための投票を要求します |
1. すべてのノードはフォロワーとして開始します
2. フォロワーが選挙タイムアウトになってもリーダーから連絡がなかった場合、そのフォロワーは候補者になります
3. 候補者が投票を要求します。最も多くの票を獲得した人がリーダーになります
4. リーダーはログエントリをフォロワーに複製します。
5. 過半数が承認すると、エントリはコミットされます

## ブロックチェーン
### ブロックチェーンの仕組み
|コンポーネント |説明 |
|----------|---------------|
| **ブロック** |トランザクションのバッチ + メタデータ + 前のブロックのハッシュ |
| **ハッシュ** |ブロックの内容の暗号化フィンガープリント |
| **チェーン** |各ブロックは前のブロックのハッシュを参照し、不変のチェーンを作成します。
| **コンセンサス** |ネットワーク参加者は、どのブロックを追加するかについて同意します。
| **マークル ツリー** |ブロック内のすべてのトランザクションを要約するハッシュのツリー |
### ブロックチェーンが改ざんされにくい理由
1. 各ブロックには前のブロックのハッシュが含まれます
2. トランザクションを変更すると、ブロックのハッシュが変更されます
3. 変更されたハッシュによりチェーンが切断される - 後続のブロックはすべて無効になります
4. 攻撃者は後続のブロックをすべて再マイニングし、ネットワークの 50% 以上を制御する必要がある
### ブロックチェーンの種類
|タイプ |アクセス |バリデータ |例 |
|------|--------|-----------|-----------|
| **パブリック (許可なし)** |誰でも読み書きできる |オープンコンセンサス (PoW、PoS) |ビットコイン、イーサリアム |
| **非公開 (許可)** |アクセス制限 |既知のバリデータ |ハイパーレジャー、Corda |
| **コンソーシアム** |組織グループによって管理されています |選択されたバリデータ |銀行業務用の R3 Corda |
### スマートコントラクト
ブロックチェーンに保存されている自己実行コードで、所定の条件が満たされた場合に実行されます。
|プラットフォーム |言語 |注目の機能 |
|----------|----------|------|
| **イーサリアム** |ソリディティ、バイパー |最大のスマートコントラクトエコシステム |
| **ソラナ** |錆、C |高スループット。低料金 |
| **カルダノ** |ハスケル (Plutus) |査読済み。正式な検証 |
| **ハイパーレジャー** | Go、Java、JavaScript |企業;許可済み |

## 分散データベース
|データベース |建築 |一貫性 |最適な用途 |
|----------|---------------|---------------|----------|
| **カサンドラ** |ワイドカラム。ピアツーピア |調整可能 (最終的にクォーラムに達する) |高い書き込みスループット。時系列 |

| **ゴキブリDB** |分散 SQL。ラフトのコンセンサス |強い |分散 SQL。グローバル展開 |
| **TiDB** |分散 SQL。ラフト (TiKV経由) |強い | MySQL 互換。水平スケーリング |
| **DynamoDB** |キーと値。管理された |最終的 (または一貫した読み取りで強力) |サーバーレス。 AWS 統合 |
| **スパナ** |分散 SQL。パクソス |強い | Googleクラウド;グローバルな一貫性 |

## 分散システム パターン
|パターン |説明 |使用例 |
|----------|---------------|----------|
| **リーダー選挙** |調整するノードを 1 つ選択します |いかだのリーダー。動物園の飼育員 |
| **レプリケーション** |冗長性を確保するためにデータをコピーし、スケーリングを読み取ります。データベースのレプリカ。 CDN |
| **シャーディング** |キー範囲またはハッシュによるデータのパーティション分割 |大規模データベース |
| **MapReduce** |ノード間で計算を分割します。集計結果 |大規模データ処理 |
| **ゴシッププロトコル** |ノードはランダムなピアと定期的に状態を共有します。クラスターのメンバーシップ。障害検出 |
| **2 フェーズ コミット** |複数のノードにわたるトランザクションを調整する |分散データベース |
| **佐賀パターン** |補償アクションを伴う一連のローカル トランザクション |マイクロサービストランザクション |
| **サーキットブレーカー** |失敗したサービスの呼び出しを停止します。失敗が早い |回復力;連鎖的な障害を防ぐ |

## 分散システムにおける課題
|チャレンジ |説明 |緩和 |
|----------|---------------|---------------|
| **ネットワーク パーティション** |ノードが通信できません | CAP のトレードオフ。バックオフで再試行 |
| **クロック スキュー** |ノードが異なればクロックも異なります。論理クロックを使用します。 NTP;実時間に依存しないようにする |
| **ビザンチン断層** |嘘をついたり、恣意的に行動するノード | BFT のコンセンサス。ブロックチェーン |
| **スプリット ブレイン** | 2 つのノードは両方とも自分たちがリーダーであると考えています。フェンシング;定足数ベースの決定 |
| **連鎖的な障害** | 1 つの失敗が他の失敗を引き起こす |サーキットブレーカー;隔壁。優雅な劣化 |
| **データの一貫性** |レプリカの同期を維持する |一貫性モデル。競合の解決 |

＃＃ まとめ
分散システムは、最新のソフトウェアがスケールし、障害に耐え、世界中のユーザーにサービスを提供する方法です。コンセンサス アルゴリズム (Raft、Paxos) により、ノードの同意が保証されます。ブロックチェーンは暗号検証と分散化を追加して、トラストレスな台帳を作成します。分散データベース (Cassandra、CockroachDB、DynamoDB) は大規模なデータを処理します。 CAP 定理によって捉えられる基本的なトレードオフは、ネットワークの信頼性が低い場合の一貫性と可用性の間です。これらの概念を理解することは、インターネット規模で動作するシステムを構築するために不可欠です。
