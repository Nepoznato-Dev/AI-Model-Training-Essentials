# API の設計とアーキテクチャ
API (アプリケーション プログラミング インターフェイス) は、ソフトウェア コンポーネントが相互に通信する方法です。適切に設計された API は直感的で一貫性があり、楽しく作業できます。設計が不十分だと、混乱、バグ、フラストレーションが発生します。このファイルでは、開発者が実際に使用したい API を構築するための原則、パターン、実践方法について説明します。
---

## REST API の原則
REST (Representational State Transfer) は、Web API の主要なアーキテクチャ スタイルです。データを URL で識別される **リソース** として扱い、HTTP メソッドを使用してそれらを操作します。
### 基本原則
|原則 |説明 |
|----------|---------------|
| **リソース** |すべては URI (`/users/123`、`/orders/456`) を持つリソースです。
| **HTTP メソッド** | GET (読み取り)、POST (作成)、PUT (置換)、PATCH (部分更新)、DELETE (削除) |
| **無国籍** |各リクエストには、必要なすべての情報が含まれています。サーバー側のセッション状態がありません |
| **均一なインターフェイス** |一貫したリソース命名、標準メソッド、標準ステータス コード |
| **代表者** |リソースは複数の形式 (JSON、XML) で表現できます。
### リソースの命名規則
|する |しないでください |
|----|------|
| `/users`(複数名詞) | `/user`(単数) |
| `/users/123/orders`(ネスト) | `/getOrdersForUser?id=123`|
| `/products?category=electronics`(フィルタリング用のクエリパラメータ) | `/productsByCategory/electronics`|
|ハイフンを使用します:`/user-profiles`|アンダースコアを使用します:`/user_profiles`|
### HTTP メソッドとべき等性
|方法 |目的 |べき等ですか？ |安全？ |
|----------|----------|---------------|----------|
| **入手** |リソースを読む | ✅ はい | ✅ はい |
| **投稿** |リソースを作成する | ❌ いいえ | ❌ いいえ |
| **置く** |リソースを完全に置き換える | ✅ はい | ❌ いいえ |
| **パッチ** |リソースを部分的に更新する | ❌ いいえ* | ❌ いいえ |
| **削除** |リソースを削除する | ✅ はい | ❌ いいえ |
*PATCH は慎重に設計すれば冪等にすることができます。
### HTTPステータスコード
|コード |意味 |いつ使用するか |
|------|--------|---------------|
| **200** | OK | GET、PUT、PATCH、DELETE が成功しました |
| **201** |作成された | POST が成功しました (リソースが作成されました) |
| **204** |コンテンツなし | DELETE に成功しました (何も返されません) |
| **400** |不正なリクエスト |無効な入力または不正な形式のリクエスト |
| **401** |不正 |認証が欠落しているか無効です |
| **403** |禁止 |認証されましたが許可されていません |
| **404** |見つかりません |リソースが存在しません |
| **409** |紛争 |重複したリソースまたは状態の競合 |
| **422** |処理できないエンティティ |有効な JSON ですが、セマンティック エラーが発生します。
| **429** |リクエストが多すぎます |レート制限を超えました |
| **500** |内部サーバーエラー |予期しないサーバー エラー |
| **502** |不正なゲートウェイ |アップストリーム サービスの障害 |
| **503** |サービスが利用できません |一時的な過負荷またはメンテナンス |

## API のバージョン管理
API は進化します。重大な変更を加える必要がある場合、バージョン管理により既存のクライアントは動作し続けることができます。
|戦略 |例 |長所 |短所 |
|----------|-----------|------|------|
| **URL パス** |  `/v1/users`、`/v2/users` |シンプル、明示的 |バージョンごとの URL の変更 |
| **クエリパラメータ** | `/users?version=2`|柔軟 |忘れやすい |
| **ヘッダー** | `Accept: application/vnd.myapi.v2+json`|クリーンな URL |発見されにくい |
| **バージョン管理なし** |スキーマの進化のみ |最も単純な |重大な変更は全員に影響を与えます |
**ベスト プラクティス**: わかりやすくするために、URL パスのバージョン管理 (`/v1/`) を使用します。少なくとも 1 つの以前のバージョンをサポートします。明確なスケジュールで古いバージョンを非推奨にします。

## 認証方法
|方法 |仕組み |最適な用途 |
|----------|---------------|----------|
| **API キー** |ヘッダーの秘密キー (`X-API-Key: abc123`) |サーバー間のシンプルな統合 |
| **OAuth2** |スコープを使用したトークンベースの委任 |サードパーティのアクセス、ユーザーが承認したアプリ |
| **JWT** |クレームを含む自己完結型トークン |サービス間のステートレス認証 |
| **基本認証** | Base64 でエンコードされたユーザー名:パスワード |開発のみ — TLS を使用しない運用は決して行わない |
| **セッション Cookie** | HTTP 専用 Cookie のサーバー側セッション ID |従来の Web アプリケーション |
### OAuth2 フロー (簡略化)
1. クライアントはユーザーを認可サーバーにリダイレクトします。
2. ユーザーはログインし、権限を付与します。
3. 認可サーバーは認可コードを返します。
4. クライアントは、アクセス トークン (およびオプションでリフレッシュ トークン) のコードを交換します。
5. クライアントはアクセス トークンを使用して API を呼び出します。
6. アクセス トークンの有効期限が切れたら、リフレッシュ トークンを使用して新しいトークンを取得します。

## API スタイル: REST、GraphQL、gRPC
|特集 |休憩 |グラフQL | gRPC |
|-------|------|-----------|------|
| **データ形式** | JSON (通常) | JSON | Protobuf (バイナリ) |
| **エンドポイント** |複数 (リソースごとに 1 つ) |単一のエンドポイント | .proto ファイルで定義 |
| **過剰取得** |共通 (必要以上のものを取得) |なし (クライアントがフィールドを指定) |なし (スキーマ定義) |
| **取得不足** |複数の呼び出しが必要 |なし (必要なものを正確に入手) |なし |
| **リアルタイム** | WebSocket が必要 |組み込みのサブスクリプション |ストリーミング内蔵 |
| **キャッシング** | HTTP キャッシュは自然に機能します。キャッシュが難しくなる |限定 |
| **学習曲線** |低い |中 |中～高 |
| **最適な用途** |パブリック API、CRUD アプリ |複雑な UI、モバイル アプリ |内部マイクロサービス、高パフォーマンス |

## ページネーション、フィルタリング、並べ替え
リストを返すエンドポイントの場合:
|テクニック |例 |いつ使用するか |
|----------|-----------|---------------|
| **オフセット/制限** | `?offset=20&limit=10`|単純;小規模なデータセットで機能します。
| **カーソルベース** | `?cursor=abc123&limit=10`|大規模なデータセット。一貫した結果 |
| **キーセット** | `?created_after=2024-01-01&limit=10`|非常に効率的です。一意のキーが必要です |
```json
// Cursor-based response
{
  "data": [...],
  "pagination": {
    "next_cursor": "abc123",
    "has_more": true
  }
}
```

## レート制限
API を悪用から保護し、公正な使用を保証します。
|戦略 |仕組み |
|----------|---------------|
| **固定窓** |時間枠ごとの N リクエスト (例: 100/時間) |
| **引き違い窓** |より詳細な;ローリング ウィンドウ内のリクエストをカウントします。
| **トークン バケット** |トークンは固定レートで追加されます。各リクエストはトークンを消費します。
ヘッダー付きの`429 Too Many Requests`を返します。```
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1625097600
Retry-After: 60
```

## エラー処理
一貫したエラー応答により、API の操作がはるかに簡単になります。
```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Invalid input data",
    "details": [
      {
        "field": "email",
        "issue": "Invalid email format"
      }
    ]
  }
}
```

**原則**: 一貫したエラー構造を使用し、アクション可能なメッセージを含め、標準の HTTP ステータス コードを使用し、相関 ID を使用してサーバー側でエラーをログに記録し、スタック トレースや内部詳細を決して公開しません。

## API ドキュメント
|ツール |説明 |
|------|---------------|
| **OpenAPI (Swagger)** | REST API ドキュメントの業界標準 |
| **Swagger UI** | OpenAPI 仕様からの対話型 API ドキュメント |
| **郵便配達員** | API テスト、ドキュメント、コレクションの共有 |
| **レドック** | OpenAPI 仕様からの美しい API リファレンス ドキュメント |
| **GraphQL プレイグラウンド / GraphiQL** |インタラクティブな GraphQL 探索 |
**ベスト プラクティス**: まず OpenAPI 仕様を作成し (仕様主導開発)、次にそこからドキュメントとクライアント SDK を生成します。

## API ゲートウェイ パターン
API ゲートウェイはクライアントとバックエンド サービスの間に位置し、単一のエントリ ポイントを提供します。
|責任 |説明 |
|--------------|---------------|
| **ルーティング** |リクエストを適切なバックエンド サービスに送信する |
| **認証** |ゲートウェイ レベルでトークンを検証する |
| **レート制限** |グローバルまたはクライアントごとの制限を適用する |
| **変換** |プロトコル間の変換 (REST ↔ gRPC) |
| **キャッシング** |一般的な応答をキャッシュする |
| **モニタリング** |一元化されたログとメトリクス |
| **負荷分散** |サービス インスタンス間でトラフィックを分散する |
|ツール |タイプ |
|------|------|
| **コン** |オープンソース API ゲートウェイ (Nginx ベース) |
| **AWS API ゲートウェイ** |フルマネージド、AWS と統合 |
| **Azure API 管理** |開発者ポータルを備えたマネージド ゲートウェイ |
| **Envoy / Istio** | API ゲートウェイ機能を備えたサービス メッシュ |
| **トレフィク** |自動検出、Let's Encrypt の統合 |

## Webhook
Webhook を使用すると、クライアントに変更をポーリングさせるのではなく、API がイベントをクライアントにリアルタイムでプッシュできるようになります。
|側面 |ベストプラクティス |
|------|--------------|
| **配送** | JSON ペイロードを含む POST リクエストをクライアントの URL に送信します。
| **セキュリティ** | HMAC を使用してペイロードに署名します。クライアントは署名を検証します |
| **信頼性** |指数バックオフを使用して失敗した配信を再試行する |
| **べき等性** |一意のイベント ID を含めます。クライアントは重複を処理します。
| **バージョン管理** | Webhook ペイロードに API バージョンを含める |
