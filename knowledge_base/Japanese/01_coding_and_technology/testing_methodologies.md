# テスト方法
テストは、コードが機能すること、そしてさらに重要なことに、コードを変更してもすでに機能しているものが壊れていないことを確信する方法です。優れたテストは、ユーザーが行う前にバグを発見し、予想される動作を文書化して、大胆なリファクタリングを可能にします。このファイルは、単体テストからエンドツーエンドのテストまで、あらゆるテスト戦略と、テストを効果的にするための原則をカバーしています。
---

## テストのピラミッド
テスト ピラミッドは、プロジェクト内のテストの理想的な配分を表します。
```
        /  E2E  \          ← Few; slow; expensive; test the whole system
       /─────────\
      / Integration\       ← Some; test how components work together
     /───────────────\
    /   Unit Tests    \    ← Many; fast; cheap; test individual functions
   /─────────────────────\
```

|レベル |カウント |スピード |コスト |テスト内容 |
|------|-------|-------|------|------|
| **ユニット** |たくさん |高速 (ミリ秒) |低い |個々の関数、クラス、メソッド |
| **統合** |いくつか |中 (100ms-秒) |中 |コンポーネントがどのように相互作用するか。データベースクエリ。 API 呼び出し |
| **E2E** |少数 |遅い (秒-分) |高 |実際のシステムを介した完全なユーザー フロー |
---

## 単体テスト
コードの個々のユニットを分離してテストします。
### 原則
|原則 |説明 |
|----------|---------------|
| **速い** |各テストはミリ秒以内に実行する必要があります。
| **孤立** |テストは相互に依存しません。共有状態なし |
| **決定論的** |毎回同じ入力→同じ出力 (ランダム性なし、時間依存性なし) |
| **自己チェック** |テストは自動的に合格または不合格になります。手動検査なし |
| **タイムリー** |コードの横または前に記述 (TDD) |
### テストの構造
|フェーズ |説明 |
|------|-----------|
| **アレンジ** |テスト データと依存関係を設定する |
| **行動** |テスト対象の関数またはメソッドを呼び出します。
| **断言** |結果が期待どおりであることを確認します。
### 何をテストするか
|カテゴリー |例 |
|----------|----------|
| **ハッピーパス** |通常の入力は期待どおりの出力を生成します。
| **エッジケース** |空の入力、null、ゼロ、最大値、単一要素 |
| **エラーの場合** |無効な入力、データの欠落、アクセス許可の拒否 |
| **境界条件** | 1つずつオフ。まさに限界です |
### モッキングとスタブ
|用語 |説明 |いつ使用するか |
|------|---------------|---------------|
| **モック** |呼び出された方法を記録する偽のオブジェクト |インタラクションの検証 (このメソッドが呼び出されましたか?) |
| **スタブ** |あらかじめ決められた値を返す偽のオブジェクト |テスト データの提供 (データベースからこのユーザーを返す) |
| **スパイ** |実際のオブジェクトへの呼び出しを記録するラッパー |部分的な検証 |
| **偽物** |簡素化されているが機能する実装 |テスト用のインメモリ データベース |
|モッキングライブラリ |言語 |
|--|-------|
| **unittest.mock** |パイソン |
| **冗談** | JavaScript/TypeScript |
| **モキト** |ジャワ |
| **モク** | C# |
| **証言 / ゴモック** |行く |
---

## 統合テスト
複数のコンポーネントがどのように連携して動作するかをテストします。
|何をテストするか |例 |
|-----------|-----------|
| **データベース クエリ** | ORM は正しい SQL を生成しますか?インデックスは使用されていますか? |
| **API エンドポイント** |完全な要求と応答のサイクルは機能しますか? |
| **サービスの相互作用** |サービス A はサービス B を正しく呼び出しますか? |
| **外部依存関係** |支払いゲートウェイの統合は機能しますか? |
### 戦略
|戦略 |説明 |トレードオフ |
|----------|---------------|----------|
| **実際の依存関係** |実際のデータベース、実際のメッセージ キューを使用する |最も現実的です。もっとゆっくり;セットアップが難しい |
| **テストコンテナ** |テスト実行ごとに Docker コンテナをスピンアップする |バランスが良い。再現性のある |
| **インメモリの代替手段** | PostgreSQL の代わりに H2。インメモリメッセージバス |速い;現実世界の問題を見逃す可能性があります。
| **契約テスト** |サービスが API 契約を遵守していることを確認する |インターフェースの変更をキャッチ |
---

## エンドツーエンド (E2E) テスト
ユーザーの観点からシステム全体をテストします。
|ツール |タイプ |最適な用途 |
|------|------|----------|
| **劇作家** |ブラウザの自動化 | Web アプリケーション。クロスブラウザ |
| **サイプレス** |ブラウザの自動化 | Web アプリケーション。開発者の経験 |
| **セレン** |ブラウザの自動化 |遺産;幅広い言語サポート |
| **デトックス** |モバイル E2E |ネイティブ アプリに反応する |
| **アピウム** |モバイル E2E |ネイティブおよびハイブリッド モバイル アプリ |
| **マエストロ** |モバイル E2E |モバイルアプリ;単純な YAML 構文 |
| **k6 / イナゴ** |負荷テスト |負荷時のパフォーマンス |
### E2E のベスト プラクティス
|練習 |なぜ |
|----------|-----|
| **クリティカル パスのみをテストします** | E2E テストは遅いです。最も重要なことに集中する |
| **テスト データ ファクトリを使用する** |プログラムでテスト データを作成します。シードデータに依存しないでください。
| **テスト後のクリーンアップ** |各テストでは、システムを既知の状態のままにしておく必要があります。
| **UI の詳細のテストは避ける** | CSS クラスや要素の位置ではなく、動作をテストします。
| **CI で実行** | E2E テストは変更のたびに自動的に実行する必要があります。

## テスト駆動開発 (TDD)
最初にテストを作成し、次にテストに合格するコードを作成します。
|ステップ |説明 |
|------|---------------|
| **1.赤** |望ましい動作を説明する失敗するテストを作成します。
| **2.緑** |テストに合格するための最小限のコードを記述します。
| **3.リファクタリング** |テストをグリーンに保ちながらコードをクリーンアップする |
|メリット |説明 |
|----------|---------------|
| **デザインのフィードバック** |テストでは、実装前にインターフェイスについて考える必要があります。
| **回帰安全性** |すべてのバグはテストを受けます。バグは元に戻らない |
| **ドキュメント** |テストは、予想される動作の生きた文書として機能します。
| **自信** |高いテスト カバレッジにより、大胆なリファクタリングが可能になります。
---

## 行動駆動型開発 (BDD)
BDD は、ユーザーの観点から動作を記述する自然言語でテストを作成することで TDD を拡張します。
### 指定時形式
```
Given a user with an empty shopping cart
When they add a "Python Book" priced at $29.99
Then the cart total should be $29.99
And the cart should contain 1 item
```

|ツール |言語 |
|------|----------|
| **キュウリ** | Java、JavaScript、Ruby、その他 |
| **行動** |パイソン |
| **スペックフロー** | C# |
| **Jest** (describe/it 付き) | JavaScript |
---

## 他のテストの種類
|タイプ |テスト内容 |ツール |
|------|--------------|------|
| **パフォーマンス/負荷** |負荷時のシステム動作 | k6、JMeter、ローカスト、ガトリング |
| **セキュリティ** |脆弱性と攻撃ベクトル | OWASP ZAP、バープスイート、Snyk |
| **アクセシビリティ** | WCAG コンプライアンス |斧、灯台、pa11y |
| **契約** |サービス間の API 互換性 | Pact、Spring Cloud 契約 |
| **突然変異** |テストスイート自体の品質 |ストライカー、ムムムット、PIT |
| **視覚的回帰** |バージョン間の UI の変更 | Percy、クロマチック、BackstopJS |
| **カオス** |障害に対するシステムの回復力 |カオス モンキー、リトマス、グレムリン |
| **煙** |導入後の基本機能 |カスタムスクリプト。健康診断 |
| **浸す** |長時間にわたるシステム動作 |長時間にわたる負荷テスト |

## テスト組織
|パターン |説明 |いつ使用するか |
|----------|---------------|---------------|
| **同じ場所にあります** |テストするコードの横にあるテスト (`src/utils.test.ts`) |ほとんどのプロジェクト。見つけやすい |
| **別のディレクトリ** |`tests/`または`__tests__/`フォルダー内のテスト |大規模プロジェクト。明確な分離 |
| **テスト治具** |`fixtures/`ディレクトリ内の共有テスト データ |複数のテストで同じデータが必要な場合 |
| **テスト ユーティリティ** |`test-utils/`ディレクトリ内の共有ヘルパー |設定ロジックが複雑な場合 |
---

## コードカバレッジ
|メトリック |何を測定するのか |制限 |
|----------|------|-----------|
| **回線範囲** |テストによって実行されたコード行の割合 |アサーションの品質を測定しません。
| **支店の対象範囲** |選択された分岐 (if/else) の割合 |ラインカバレッジよりも優れています。まだすべてのバグを捕捉できていない |
| **パスの適用範囲** |実行された実行パスの割合 |最も徹底的です。複雑なコードにおける指数関数 |
| **突然変異スコア** |テストで検出された突然変異の割合 |テスト品質の最良の尺度 |
**目標**: 80% のライン カバレッジが妥当なデフォルトです。ただし、カバレッジはガイドであり、目標ではありません。弱いアサーションによる 100% のカバレッジは、徹底的なテストによる 70% のカバレッジよりも劣ります。
---

## 継続的な統合とテスト
|練習 |説明 |
|----------|---------------|
| **コミットごとにすべての単体テストを実行します** |素早いフィードバック。回帰を即座にキャッチします。
| **PR で統合テストを実行** |単体テストで見逃される問題を発見 |
| **E2E テストを毎晩実行するか、メインへのマージ時に実行します** |ゆっくりだけど徹底した |
| **早く失敗してください** |最初の失敗時にパイプラインを停止して時間を節約する |
| **不安定なテスト ポリシー** |不安定なテストはすぐに隔離または削除します。決して無視しないでください |
| **テストの並列化** |テストを並行して実行して CI 時間を短縮する |
---

## 実践的なヒント
- **テストに明確に名前を付けます。**`test_calculates_tax_for_high_earner`は何が壊れたかを示します。 `test_1`は何も教えてくれません。
- **テストごとに 1 つのアサーション (実用的な場合)。** 障害の診断が簡単になります。
- **実装の詳細をテストしないでください。** 動作をテストします。内部をリファクタリングしても、テストが中断されることはありません。
- **サードパーティのコードのテストは避けてください。** 外部ライブラリをモックします。コードとそれらの対話をテストします。
- **テストを高速化します。** テスト スイートに 10 分かかると、開発者はテストの実行を中止します。絶え間なく最適化します。
- **デッドテストを削除します。** 常に合格するテストまたは削除されたコードのテストはノイズです。
- **テスト コードを運用コードと同様に扱います。** テスト コードは読みやすく、保守しやすく、適切に構造化されている必要があります。
---

＃＃ まとめ
テストは任意ではありません。テストは、壊れないソフトウェアを構築する方法です。テスト ピラミッドは、多くの高速単体テスト、いくつかの統合テスト、およびいくつかの E2E テストに導きます。 TDD と BDD は構造化されたアプローチを提供します。モッキングでは、テスト用にユニットを分離します。コード カバレッジは幅を測定しますが、深さは測定しません。最も重要な原則は次のとおりです。テストされていない場合、それは壊れています。それは、あなたがまだそれを知らないだけです。
