# جانچ کے طریقے
جانچ یہ ہے کہ آپ کو یہ اعتماد کیسے حاصل ہوتا ہے کہ آپ کا کوڈ کام کرتا ہے — اور اس سے بھی اہم بات یہ ہے کہ اس میں ہونے والی تبدیلیاں پہلے سے کام کرنے والی چیزوں کو نہیں توڑتی ہیں۔ اچھی جانچ صارفین کے کرنے سے پہلے کیڑے پکڑتی ہے، دستاویزات کی توقع کی جاتی ہے، اور بے خوف ری فیکٹرنگ کو قابل بناتی ہے۔ یہ فائل جانچ کی حکمت عملیوں کے مکمل اسپیکٹرم کا احاطہ کرتی ہے، یونٹ ٹیسٹ سے لے کر آخر تک کے ٹیسٹ تک، اور ان اصولوں کو جو جانچ کو مؤثر بناتے ہیں۔
---

## ٹیسٹنگ اہرام
ٹیسٹنگ اہرام ایک پروجیکٹ میں ٹیسٹوں کی مثالی تقسیم کو بیان کرتا ہے۔
```
        /  E2E  \          ← Few; slow; expensive; test the whole system
       /─────────\
      / Integration\       ← Some; test how components work together
     /───────────────\
    /   Unit Tests    \    ← Many; fast; cheap; test individual functions
   /─────────────────────\
```

| سطح | شمار | رفتار | لاگت | یہ کیا ٹیسٹ کرتا ہے |
|-------|---------|------|------|---------------|
| **یونٹ** | بہت سے | تیز (ms) | کم | انفرادی افعال، کلاسز، طریقے |
| **انٹیگریشن** | کچھ | میڈیم (100ms-s) | میڈیم | اجزاء کیسے تعامل کرتے ہیں؛ ڈیٹا بیس کے سوالات؛ API کالز |
| **E2E** | چند | آہستہ (سیکنڈ منٹ) | ہائی | مکمل صارف حقیقی نظام سے گزرتا ہے |

## یونٹ ٹیسٹنگ
کوڈ کی انفرادی اکائیوں کو تنہائی میں جانچنا۔
### اصول
| اصول | تفصیل |
|------------|-------------|
| **تیز** | ہر ٹیسٹ کو ملی سیکنڈ میں چلنا چاہیے۔
| ** الگ تھلگ** | ٹیسٹ ایک دوسرے پر انحصار نہیں کرتے؛ کوئی مشترکہ ریاست نہیں |
| **ڈیٹرمنسٹک** | ہر بار ایک ہی ان پٹ → ایک ہی آؤٹ پٹ (کوئی بے ترتیب پن، وقت پر انحصار نہیں) |
| **خود جانچ** | ٹیسٹ خود بخود پاس یا ناکام ہو جاتا ہے؛ کوئی دستی معائنہ نہیں |
| **بروقت** | کوڈ (TDD) کے ساتھ یا اس سے پہلے لکھا ہوا |
### ٹیسٹ کی اناٹومی۔
| مرحلہ | تفصیل |
|---------|---------------|
| ** ترتیب دیں** | ٹیسٹ ڈیٹا اور انحصار سیٹ اپ کریں |
| **ایکٹ** | فنکشن یا طریقہ کو کال کریں جس کی جانچ کی جا رہی ہے |
| **اصرار** | تصدیق کریں کہ نتیجہ توقعات سے میل کھاتا ہے |
### کیا ٹیسٹ کرنا ہے۔
| زمرہ | مثالیں |
|------------|---------|
| **خوشی کا راستہ** | عام ان پٹ متوقع آؤٹ پٹ پیدا کرتے ہیں |
| **ایج کیسز** | خالی ان پٹ، کالعدم، صفر، زیادہ سے زیادہ اقدار، واحد عنصر |
| **خرابی کے معاملات** | غلط ان پٹ، ڈیٹا غائب، اجازت سے انکار |
| **حدود کی شرائط** | ایک کے بعد ایک; بالکل حد میں |
### طنز اور ضد
| مدت | تفصیل | کب استعمال کریں |
|------|---------------|------------|
| **مذاق** | ایک جعلی چیز جو ریکارڈ کرتی ہے کہ اسے کیسے بلایا گیا تھا | تعاملات کی تصدیق کرنا (کیا اس طریقہ کو کہا جاتا تھا؟) |
| **نامکمل** | ایک جعلی آبجیکٹ جو پہلے سے طے شدہ اقدار واپس کرتا ہے | ٹیسٹ ڈیٹا فراہم کرنا (اس صارف کو ڈیٹا بیس سے واپس کریں) |
| **جاسوس** | ایک ریپر جو کسی حقیقی چیز کو کالز ریکارڈ کرتا ہے | جزوی تصدیق |
| **جعلی** | ایک آسان لیکن عملی نفاذ | ٹیسٹ کے لیے ان میموری ڈیٹا بیس |
| طنزیہ لائبریری | زبان |
|----------------|---------|
| **unittest.mock** | ازگر |
| **مذاق** | JavaScript/TypeScript |
| **موکیٹو** | جاوا |
| **Moq** | C# |
| **گواہی/گومک** | جاؤ |

## انٹیگریشن ٹیسٹنگ
جانچنا کہ متعدد اجزاء ایک ساتھ کیسے کام کرتے ہیں۔
| کیا جانچنا ہے | مثال |
|---------------|---------|
| **ڈیٹا بیس کے سوالات** | کیا ORM درست SQL تیار کرتا ہے؟ کیا اشاریہ جات استعمال ہوتے ہیں؟ |
| **API اینڈ پوائنٹس** | کیا مکمل درخواست جوابی سائیکل کام کرتا ہے؟ |
| **سروس کے تعاملات** | کیا سروس A صحیح طریقے سے سروس B کو کال کرتی ہے؟ |
| **بیرونی انحصار** | کیا ادائیگی کے گیٹ وے کا انضمام کام کرتا ہے؟ |
### حکمت عملی
| حکمت عملی | تفصیل | تجارت بند |
|------------|------------|------------|
| **حقیقی انحصار** | ایک حقیقی ڈیٹا بیس کا استعمال کریں، حقیقی پیغام کی قطار | سب سے زیادہ حقیقت پسندانہ؛ سست قائم کرنا مشکل |
| **ٹیسٹ کنٹینرز** | ہر ٹیسٹ رن کے لیے ڈوکر کنٹینرز کو گھماؤ | اچھا توازن؛ تولیدی |
| **ان میموری متبادل** | PostgreSQL کے بجائے H2؛ ان میموری پیغام بس | تیز؛ حقیقی دنیا کے مسائل سے محروم ہو سکتے ہیں |
| **معاہدے کی جانچ** | تصدیق کریں کہ خدمات اپنے API معاہدوں کا احترام کرتی ہیں۔ انٹرفیس کی تبدیلیوں کو پکڑتا ہے |

## اینڈ ٹو اینڈ (E2E) ٹیسٹنگ
صارف کے نقطہ نظر سے مکمل نظام کی جانچ کرنا۔
| ٹول | قسم | کے لیے بہترین |
|------|------|---------|
| ** ڈرامہ نگار** | براؤزر آٹومیشن | ویب ایپلیکیشنز؛ کراس براؤزر |
| **صنوبر** | براؤزر آٹومیشن | ویب ایپلیکیشنز؛ ڈویلپر کا تجربہ |
| **سیلینیم** | براؤزر آٹومیشن | میراث وسیع زبان کی حمایت |
| **ڈیٹاکس** | موبائل E2E | مقامی ایپس پر ردعمل ظاہر کریں |
| **Appium** | موبائل E2E | مقامی اور ہائبرڈ موبائل ایپس |
| **استاد** | موبائل E2E | موبائل ایپس؛ سادہ YAML نحو |
| **k6 / ٹڈی** | لوڈ ٹیسٹنگ | لوڈ کے تحت کارکردگی |
### E2E بہترین طرز عمل
| مشق | کیوں |
|------------|------|
| **صرف اہم راستوں کی جانچ کریں** | E2E ٹیسٹ سست ہیں؛ سب سے اہم چیز پر توجہ مرکوز کریں |
| **ٹیسٹ ڈیٹا فیکٹریوں کا استعمال کریں** | پروگرام کے مطابق ٹیسٹ ڈیٹا بنائیں؛ بیج کے اعداد و شمار پر بھروسہ نہ کریں |
| **ٹیسٹوں کے بعد صاف کریں** | ہر ٹیسٹ کو سسٹم کو ایک معلوم حالت میں چھوڑنا چاہیے۔
| **UI تفصیلات کی جانچ کرنے سے گریز کریں** | ٹیسٹ رویے، CSS کلاسز یا عنصر کی پوزیشنز نہیں۔
| ** CI میں چلائیں** | E2E ٹیسٹوں کو ہر تبدیلی پر خود بخود چلنا چاہیے۔

## ٹیسٹ سے چلنے والی ترقی (TDD)
پہلے ٹیسٹ لکھیں، پھر اسے پاس کرنے کے لیے کوڈ لکھیں۔
| مرحلہ | تفصیل |
|------|---------------|
| **1۔ سرخ** | ایک ناکام ٹیسٹ لکھیں جو مطلوبہ رویے کی وضاحت کرتا ہو |
| **2۔ سبز** | ٹیسٹ پاس کرنے کے لیے کم از کم کوڈ لکھیں۔
| **3۔ ریفیکٹر** | ٹیسٹ کو سبز رکھتے ہوئے کوڈ کو صاف کریں۔
| فائدہ | تفصیل |
|---------|---------------|
| **ڈیزائن کی رائے** | ٹیسٹ آپ کو لاگو کرنے سے پہلے انٹرفیس کے بارے میں سوچنے پر مجبور کرتے ہیں۔
| **ریگریشن سیفٹی** | ہر بگ کو ایک ٹیسٹ ملتا ہے۔ بگ کبھی واپس نہیں آ سکتا |
| **دستاویزات** | ٹیسٹ متوقع رویے کی زندہ دستاویز کے طور پر کام کرتے ہیں۔
| **اعتماد** | ہائی ٹیسٹ کوریج نڈر ریفیکٹرنگ کو قابل بناتا ہے |
---

## طرز عمل سے چلنے والی ترقی (BDD)
BDD قدرتی زبان میں ٹیسٹ لکھ کر TDD کو بڑھاتا ہے جو صارف کے نقطہ نظر سے رویے کی وضاحت کرتا ہے۔
### دیا گیا-جب-پھر فارمیٹ
```
Given a user with an empty shopping cart
When they add a "Python Book" priced at $29.99
Then the cart total should be $29.99
And the cart should contain 1 item
```

| ٹول | زبان |
|------|------------|
| **کھیرا** | جاوا، جاوا اسکرپٹ، روبی، اور دیگر |
| **رویہ** | ازگر |
| **SpecFlow** | C# |
| **مذاق** (وضاحت/اس کے ساتھ) | جاوا اسکرپٹ |

## کوڈ کوریج
| میٹرک | یہ کیا پیمائش کرتا ہے | حد |
|---------|------|------------|
| **لائن کوریج** | کوڈ لائنوں کا فیصد ٹیسٹوں کے ذریعے دعووں کے معیار کی پیمائش نہیں کرتا |
| **برانچ کوریج** | شاخوں کا فیصد (اگر/اور) لیا گیا | لائن کوریج سے بہتر؛ اب بھی تمام کیڑے نہیں پکڑتے |
| **پاتھ کوریج** | پھانسی کے راستوں کا فیصد لیا گیا | سب سے زیادہ مکمل؛ پیچیدہ کوڈ میں کفایتی |
| **میوٹیشن سکور** | ٹیسٹوں کے ذریعے پکڑے گئے تغیرات کا فیصد | ٹیسٹ کے معیار کا بہترین پیمانہ |
**ٹارگٹ**: 80% لائن کوریج ایک معقول ڈیفالٹ ہے۔ لیکن کوریج ایک رہنما ہے، مقصد نہیں — کمزور دعووں کے ساتھ 100% کوریج مکمل ٹیسٹ کے ساتھ 70% کوریج سے بھی بدتر ہے۔

## عملی نکات
- **نام کے ٹیسٹ واضح طور پر۔**`test_calculates_tax_for_high_earner`آپ کو بتاتا ہے کہ کیا ٹوٹ گیا۔ `test_1`آپ کو کچھ نہیں بتاتا۔
- **ہر ٹیسٹ میں ایک دعویٰ (جب عملی ہو)۔** ناکامیوں کی تشخیص کرنا آسان بناتا ہے۔
- **عمل درآمد کی تفصیلات کی جانچ نہ کریں۔** طرز عمل کی جانچ کریں۔ اگر آپ انٹرنل ریفیکٹر کرتے ہیں تو ٹیسٹ نہیں ٹوٹنے چاہئیں۔
- **تیسرے فریق کوڈ کی جانچ کرنے سے گریز کریں۔** بیرونی لائبریریوں کا مذاق اڑائیں؛ ان کے ساتھ اپنے کوڈ کے تعامل کی جانچ کریں۔
- **ٹیسٹ تیزی سے کریں۔** اگر آپ کے ٹیسٹ سوٹ میں 10 منٹ لگتے ہیں تو ڈویلپرز اسے چلانا بند کر دیں گے۔ مسلسل اصلاح کریں۔
- **ڈیڈ ٹیسٹ کو حذف کریں۔** ٹیسٹ جو ہمیشہ پاس ہوتے ہیں یا ہٹائے گئے کوڈ کی جانچ کرتے ہیں وہ شور ہوتے ہیں۔
- **ٹیسٹ کوڈ کو پروڈکشن کوڈ کی طرح برتاؤ۔** یہ پڑھنے کے قابل، برقرار رکھنے کے قابل، اور اچھی طرح سے ساختہ ہونا چاہیے۔
---

## خلاصہ
ٹیسٹنگ اختیاری نہیں ہے - اس طرح آپ سافٹ ویئر بناتے ہیں جو ٹوٹتا نہیں ہے۔ ٹیسٹنگ اہرام آپ کو بہت سے تیز یونٹ ٹیسٹ، کچھ انضمام ٹیسٹ، اور چند E2E ٹیسٹوں کی طرف رہنمائی کرتا ہے۔ TDD اور BDD ساختی نقطہ نظر فراہم کرتے ہیں۔ موکنگ یونٹس کو جانچ کے لیے الگ کر دیتی ہے۔ کوڈ کوریج چوڑائی کی پیمائش کرتا ہے لیکن گہرائی نہیں۔ سب سے اہم اصول یہ ہے: اگر اس کی جانچ نہیں کی جاتی ہے، تو یہ ٹوٹ جاتا ہے — آپ ابھی تک اسے نہیں جانتے۔
