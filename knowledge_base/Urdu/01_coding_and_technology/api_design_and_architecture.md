# API ڈیزائن اور فن تعمیر
ایک API (ایپلیکیشن پروگرامنگ انٹرفیس) یہ ہے کہ کس طرح سافٹ ویئر کے اجزاء ایک دوسرے سے بات کرتے ہیں۔ ایک اچھی طرح سے ڈیزائن کیا گیا API بدیہی، مستقل، اور اس کے ساتھ کام کرنے میں خوشی ہے۔ ایک ناقص ڈیزائن کنفیوژن، کیڑے اور مایوسی کا سبب بنتا ہے۔ یہ فائل APIs بنانے کے اصولوں، نمونوں اور طریقوں کا احاطہ کرتی ہے جنہیں ڈویلپر درحقیقت استعمال کرنا چاہتے ہیں۔
---

## REST API اصول
REST (نمائندہ ریاست کی منتقلی) ویب APIs کے لیے غالب آرکیٹیکچرل اسٹائل ہے۔ یہ ڈیٹا کو URLs کے ذریعے شناخت کردہ **وسائل** کے طور پر دیکھتا ہے، اور ان پر کام کرنے کے لیے HTTP طریقے استعمال کرتا ہے۔
### بنیادی اصول
| اصول | تفصیل |
|------------|-------------|
| **وسائل** | ہر چیز URI کے ساتھ ایک وسیلہ ہے (`/users/123`,`/orders/456`) |
| **HTTP طریقے** | حاصل کریں (پڑھیں)، پوسٹ کریں (تخلیق کریں)، ڈالیں (بدلیں)، پیچ (جزوی اپ ڈیٹ)، حذف کریں (ہٹائیں) |
| **بے ​​وطنی** | ہر درخواست میں تمام ضروری معلومات شامل ہیں؛ کوئی سرور سائیڈ سیشن کی حالت نہیں |
| **یکساں انٹرفیس** | وسائل کا مستقل نام، معیاری طریقے، معیاری اسٹیٹس کوڈز |
| **نمائندگی** | وسائل کو متعدد فارمیٹس (JSON, XML) میں پیش کیا جا سکتا ہے |
### وسائل کے نام کے کنونشنز
| کرو | مت کرو |
|----|-------|
| `/users`(کثرت اسم) | `/user`(واحد) |
| `/users/123/orders`(گھوںسلا) | `/getOrdersForUser?id=123`|
| `/products?category=electronics`(فلٹرنگ کے لیے استفسار پیرامز) | `/productsByCategory/electronics`|
| ہائفنز استعمال کریں:`/user-profiles`| انڈر سکور استعمال کریں:`/user_profiles`|
### HTTP طریقے اور Idempotency
| طریقہ | مقصد | بے حس؟ | محفوظ؟ |
|---------|---------|------------|-------|
| ** حاصل کریں** | ایک وسیلہ پڑھیں | ✅ ہاں | ✅ ہاں |
| **پوسٹ** | ایک وسیلہ بنائیں | ❌ نہیں | ❌ نہیں |
| ** ڈالیں** | ایک وسائل کو مکمل طور پر تبدیل کریں | ✅ ہاں | ❌ نہیں |
| **پیچ** | جزوی طور پر ایک وسائل کو اپ ڈیٹ کریں | ❌ نہیں* | ❌ نہیں |
| **ڈیلیٹ** | ایک وسائل کو ہٹا دیں | ✅ ہاں | ❌ نہیں |
*پیچ کو محتاط ڈیزائن کے ساتھ غیرمعمولی بنایا جا سکتا ہے۔
### HTTP اسٹیٹس کوڈز
| کوڈ | معنی | کب استعمال کریں |
|------|---------|------------|
| **200** | ٹھیک ہے | کامیاب GET, PUT, PATCH, DELETE |
| **201** | بنایا | کامیاب پوسٹ (وسائل تخلیق) |
| **204** | کوئی مواد نہیں | کامیاب DELETE (واپس کرنے کے لیے کچھ نہیں) |
| **400** | بری درخواست | غلط ان پٹ یا غلط درخواست |
| **401** | غیر مجاز | غائب یا غلط تصدیق |
| **403** | حرام | تصدیق شدہ لیکن مجاز نہیں |
| **404** | نہیں ملا | وسیلہ موجود نہیں ہے |
| **409** | تنازعہ | ڈپلیکیٹ وسائل یا ریاستی تنازعہ |
| **422** | ناقابل عمل ہستی | درست JSON لیکن سیمنٹک غلطیاں |
| **429** | بہت ساری درخواستیں | شرح کی حد سے تجاوز کر گیا |
| **500** | اندرونی سرور کی خرابی | غیر متوقع سرور کی خرابی |
| **502** | خراب گیٹ وے | اپ اسٹریم سروس کی ناکامی |
| **503** | سروس دستیاب نہیں ہے | عارضی اوورلوڈ یا دیکھ بھال |

## API ورژننگ
APIs تیار ہوتے ہیں۔ جب آپ کو بریکنگ تبدیلیاں کرنے کی ضرورت ہوتی ہے، ورژننگ موجودہ کلائنٹس کو کام کرتے رہنے دیتی ہے۔
| حکمت عملی | مثال | پیشہ | Cons |
|------------|---------|------|------|
| **URL کا راستہ** | `/v1/users`,`/v2/users`| سادہ، واضح | یو آر ایل تبدیلیاں فی ورژن |
| **سوال کا پیرامیٹر** | `/users?version=2`| لچکدار | بھولنے کے لئے آسان |
| **ہیڈر** | `Accept: application/vnd.myapi.v2+json`| صاف URLs | کم دریافت |
| **کوئی ورژن نہیں** | صرف اسکیما ارتقاء | سب سے آسان | بریکنگ تبدیلیاں سب کو متاثر کرتی ہیں |
**بہترین عمل**: وضاحت کے لیے URL پاتھ ورژننگ (`/v1/`) استعمال کریں۔ کم از کم ایک پچھلے ورژن کو سپورٹ کریں۔ واضح ٹائم لائنز کے ساتھ پرانے ورژن کو فرسودہ کریں۔
---

## توثیق کے طریقے
| طریقہ | یہ کیسے کام کرتا ہے | کے لیے بہترین |
|---------|------------|------------|
| **API کیز** | ہیڈر میں خفیہ کلید (`X-API-Key: abc123`) | سرور سے سرور، سادہ انضمام |
| **OAuth2** | دائرہ کار کے ساتھ ٹوکن پر مبنی وفد | فریق ثالث تک رسائی، صارف کی اجازت یافتہ ایپس |
| **JWT** | دعووں کے ساتھ خود ساختہ ٹوکن | تمام خدمات میں اسٹیٹ لیس تصدیق |
| **بنیادی توثیق** | بیس 64 انکوڈ شدہ صارف نام: پاس ورڈ | صرف ترقی - TLS کے بغیر پیداوار کبھی نہیں |
| **سیشن کوکیز** | صرف HTTP کوکی میں سرور سائیڈ سیشن ID | روایتی ویب ایپلیکیشنز |
### OAuth2 فلو (آسان)
1. کلائنٹ صارف کو اجازت دینے والے سرور پر بھیجتا ہے۔
2. صارف لاگ ان ہوتا ہے اور اجازت دیتا ہے۔
3. اجازت دینے والا سرور اجازت کا کوڈ واپس کرتا ہے۔
4. رسائی ٹوکن کے لیے کلائنٹ ایکسچینج کوڈ (اور اختیاری طور پر ٹوکن ریفریش کریں)۔
5. کلائنٹ API کو کال کرنے کے لیے رسائی ٹوکن کا استعمال کرتا ہے۔
6. رسائی ٹوکن کی میعاد ختم ہونے پر، نیا حاصل کرنے کے لیے ریفریش ٹوکن استعمال کریں۔

## API طرزیں: REST بمقابلہ GraphQL بمقابلہ gRPC
| خصوصیت | آرام | گراف کیو ایل | gRPC |
|---------|------|---------|------|
| **ڈیٹا فارمیٹ** | JSON (عام طور پر) | JSON | پروٹوبف (بائنری) |
| **اینڈ پوائنٹ** | متعدد (ایک فی وسیلہ) | سنگل اختتامی نقطہ | پروٹو فائل |
| **زیادہ بازیافت** | عام (ضرورت سے زیادہ حاصل کریں) | کوئی نہیں (کلائنٹ فیلڈز کی وضاحت کرتا ہے) | کوئی نہیں (اسکیما سے طے شدہ) |
| **انڈر فیچنگ** | متعدد کالز کی ضرورت ہے | کوئی نہیں (بالکل وہی حاصل کریں جس کی ضرورت ہے) | کوئی نہیں |
| **ریئل ٹائم** | WebSockets کی ضرورت ہے | سبسکرپشنز بلٹ ان | سٹریمنگ بلٹ ان |
| **کیشنگ** | HTTP کیشنگ قدرتی طور پر کام کرتی ہے۔ کیش کرنا مشکل | محدود |
| **سیکھنے کا وکر** | کم | میڈیم | میڈیم – ہائی |
| ** کے لیے بہترین** | عوامی APIs، CRUD ایپس | پیچیدہ UIs، موبائل ایپس | اندرونی مائیکرو سروسز، اعلی کارکردگی |

## صفحہ بندی، فلٹرنگ، اور چھانٹنا
فہرستوں کو واپس کرنے والے اختتامی پوائنٹس کے لیے:
| تکنیک | مثال | کب استعمال کریں |
|------------|---------|------------|
| **آفسیٹ/حد** | `?offset=20&limit=10`| سادہ؛ چھوٹے ڈیٹاسیٹس کے لیے کام کرتا ہے |
| **کرسر پر مبنی** | `?cursor=abc123&limit=10`| بڑے ڈیٹاسیٹس؛ مسلسل نتائج |
| **کی سیٹ** | `?created_after=2024-01-01&limit=10`| بہت موثر؛ منفرد کلید کی ضرورت ہے |
```json
// Cursor-based response
{
  "data": [...],
  "pagination": {
    "next_cursor": "abc123",
    "has_more": true
  }
}
```

## شرح کی حد
اپنے API کو غلط استعمال سے بچائیں اور مناسب استعمال کو یقینی بنائیں۔
| حکمت عملی | یہ کیسے کام کرتا ہے |
|------------|---------------|
| **فکسڈ ونڈو** | N درخواستیں فی ٹائم ونڈو (جیسے 100/hour) |
| **سلائیڈنگ ونڈو** | زیادہ دانے دار؛ رولنگ ونڈو میں درخواستوں کو شمار کرتا ہے |
| **ٹوکن بالٹی** | مقررہ شرح پر ٹوکن شامل کیے گئے؛ ہر درخواست ایک ٹوکن استعمال کرتی ہے۔
ہیڈر کے ساتھ`429 Too Many Requests`واپس کریں:```
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1625097600
Retry-After: 60
```

## ہینڈلنگ کی خرابی۔
مستقل غلطی کے جوابات APIs کے ساتھ کام کرنا بہت آسان بناتے ہیں:
```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Invalid input data",
    "details": [
      {
        "field": "email",
        "issue": "Invalid email format"
      }
    ]
  }
}
```

**اصول**: مستقل خرابی کا ڈھانچہ استعمال کریں، قابل عمل پیغامات شامل کریں، معیاری HTTP اسٹیٹس کوڈز استعمال کریں، کورلیشن آئی ڈی کے ساتھ سرور کی طرف سے غلطیوں کو لاگ کریں، اور کبھی بھی اسٹیک ٹریس یا اندرونی تفصیلات کو ظاہر نہ کریں۔

## API دستاویزات
| ٹول | تفصیل |
|------|---------------|
| **OpenAPI (Swagger)** | REST API دستاویزات کے لیے صنعت کا معیار |
| **Swagger UI** | OpenAPI spec سے انٹرایکٹو API دستاویزات |
| **پوسٹ مین** | API ٹیسٹنگ، دستاویزات، اور مجموعہ کا اشتراک |
| **ریڈاک** | OpenAPI spec سے خوبصورت API حوالہ دستاویزات |
| **GraphQL پلے گراؤنڈ / GraphiQL** | انٹرایکٹو گراف کیو ایل ایکسپلوریشن |
**بہترین عمل**: پہلے OpenAPI spec لکھیں (spec-driven development)، پھر اس سے دستاویزات اور کلائنٹ SDKs بنائیں۔
---

## API گیٹ وے پیٹرنز
ایک API گیٹ وے کلائنٹس اور بیک اینڈ سروسز کے درمیان بیٹھتا ہے، ایک ہی انٹری پوائنٹ فراہم کرتا ہے۔
| ذمہ داری | تفصیل |
|---------------|---------------|
| **روٹنگ** | مناسب پسدید خدمات کے لیے براہ راست درخواستیں |
| **توثیق** | گیٹ وے کی سطح پر ٹوکنز کی توثیق کریں |
| **شرح کی حد** | عالمی یا فی کلائنٹ کی حدود کا اطلاق کریں |
| **تبدیلی** | پروٹوکول کے درمیان تبدیل کریں (REST ↔ gRPC) |
| **کیشنگ** | کیش عام جوابات |
| **مانیٹرنگ** | مرکزی لاگنگ اور میٹرکس |
| **لوڈ بیلنسنگ** | ٹریفک کو سروس کی صورتوں میں تقسیم کریں |
| ٹول | قسم |
|------|------|
| **کانگ** | اوپن سورس API گیٹ وے (Nginx-based) |
| **AWS API گیٹ وے** | مکمل طور پر منظم، AWS کے ساتھ مربوط |
| **Azure API مینجمنٹ** | ڈویلپر پورٹل کے ساتھ منظم گیٹ وے |
| ** ایلچی / اسٹیو** | API گیٹ وے کی صلاحیتوں کے ساتھ سروس میش |
| **ٹریفک** | خودکار دریافت، آئیے انکرپٹ انٹیگریشن |

## ویب ہکس
ویب ہکس تبدیلیوں کے لیے کلائنٹس کی رائے شماری کرنے کے بجائے، آپ کے API کو ریئل ٹائم میں کلائنٹس تک واقعات کو آگے بڑھانے دیتے ہیں۔
| پہلو | بہترین عمل |
|---------|---------------|
| **ڈیلیوری** | کلائنٹ کے URL پر JSON پے لوڈ کے ساتھ درخواست پوسٹ کریں۔
| **سیکیورٹی** | HMAC کے ساتھ پے لوڈز پر دستخط کریں؛ کلائنٹ دستخط کی تصدیق کرتا ہے |
| ** وشوسنییتا** | ایکسپونینشل بیک آف کے ساتھ ناکام ڈیلیوری کی دوبارہ کوشش کریں |
| **آدمی** | منفرد ایونٹ ID شامل کریں؛ کلائنٹ ڈپلیکیٹ ہینڈل کرتا ہے |
| **ورژننگ** | ویب ہک پے لوڈ میں API ورژن شامل کریں |

## ڈیزائن چیک لسٹ
- [ ] وسائل جمع اسم ہیں ( `/users`،`/getUser`نہیں)
- [ ] HTTP طریقے درست طریقے سے استعمال کیے گئے (پڑھنے کے لیے GET، تخلیق کے لیے POST، وغیرہ)
- [ ] مستقل غلطی کے جواب کی شکل
- تمام فہرست کے اختتامی پوائنٹس کے لیے صفحہ بندی
- واضح ہیڈر کے ساتھ شرح کو محدود کرنا
- [ ] API ورژن بنانے کی حکمت عملی کی وضاحت کی گئی۔
- [ ] جگہ پر توثیق اور اجازت
- تمام اینڈ پوائنٹس پر ان پٹ کی توثیق
- [ ] OpenAPI/Swagger دستاویزات کو برقرار رکھا گیا۔
- [ ] CORS درست طریقے سے ترتیب دیا گیا ہے۔
- [ ] HTTPS پیداوار میں نافذ ہے۔
- جہاں ضرورت ہو POST آپریشنز کے لیے Idempotency کیز
