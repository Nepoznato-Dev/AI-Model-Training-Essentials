# کارکردگی کی اصلاح
پرفارمنس آپٹیمائزیشن سافٹ ویئر کو تیز تر بنانے کا عمل ہے — ردعمل کے اوقات کو کم کرنا، تھرو پٹ بڑھانا، میموری کے استعمال کو کم کرنا، اور رکاوٹوں کو ختم کرنا۔ یہ ایک ڈویلپر کے پاس سب سے زیادہ مؤثر مہارتوں میں سے ایک ہے، کیونکہ سست سافٹ ویئر صارفین کو کھو دیتا ہے، وسائل کو ضائع کرتا ہے، اور سب کو مایوس کر دیتا ہے۔ لیکن یہ سب سے عام غلط کاموں میں سے ایک ہے، جس میں ڈویلپرز ثبوت کے بجائے وجدان کی بنیاد پر غلط چیزوں کو بہتر بناتے ہیں۔
---

## سنہری اصول
> **پہلے پیمائش کریں، دوسری کو بہتر بنائیں۔** کبھی بھی مفروضوں کی بنیاد پر اصلاح نہ کریں۔ کوڈ کو پروفائل کریں، اصل رکاوٹ تلاش کریں، اور اسے ٹھیک کریں۔
| اینٹی پیٹرن | یہ برا کیوں ہے |
|---------------|---------------|
| **قبل از وقت اصلاح** | کوڈ کو تیز کرنے میں وقت گزارنا جو سست نہیں ہے |
| **بغیر پیمائش کے بہتر بنانا** | غلط رکاوٹ کو ٹھیک کرنا؛ بہتری کی تصدیق کرنے کا کوئی طریقہ نہیں ہے |
| **رفتار کے لیے پڑھنے کی اہلیت کی قربانی** | ناقابل پڑھے ہوئے کوڈ کی لاگت کارکردگی کے حصول سے زیادہ ہے |
| **سب کچھ کیشنگ** | باسی ڈیٹا، میموری پھولنا، پیچیدگی |

## پروفائلنگ
اس سے پہلے کہ آپ کچھ تیز کر سکیں، آپ کو یہ جاننا ہوگا کہ *کہاں* وقت گزارا جا رہا ہے۔
| ٹول کی قسم | یہ کیا پیمائش کرتا ہے | مثالیں |
|------------|-----------------|------------|
| **CPU پروفائلر** | کون سے فنکشنز سب سے زیادہ CPU وقت استعمال کرتے ہیں | cProfile (Python)، perf (Linux)، Chrome DevTools (JS) |
| **میموری پروفائلر** | میموری مختص اور لیک | tracemalloc (Python)، Valgrind، heaptrack |
| **I/O پروفائلر** | ڈسک اور نیٹ ورک I/O رکاوٹیں | iotop، strace، Wireshark |
| **APM (ایپلی کیشن پرفارمنس مانیٹرنگ)** | آخر سے آخر تک درخواست کا وقت | نیو ریلک، ڈیٹا ڈوگ، جیگر |
| **براؤزر ڈیو ٹولز** | فرنٹ اینڈ رینڈرنگ، جاوا اسکرپٹ پر عمل درآمد، نیٹ ورک | کروم ڈیو ٹولز، فائر فاکس پروفائلر |
### پروفائلنگ ورک فلو
| مرحلہ | تفصیل |
|------|---------------|
| 1. سست آپریشن کی شناخت کریں | صارفین سست صفحہ لوڈ کی اطلاع دیتے ہیں۔ نگرانی زیادہ تاخیر کو ظاہر کرتی ہے |
| 2. مکمل راستے کی پروفائل | معلوم کریں کہ کون سا جزو سب سے زیادہ وقت لیتا ہے |
| 3. ڈرل ڈاؤن | ہاٹ فنکشن کو تلاش کرنے کے لیے اس مخصوص جزو کی پروفائل |
| 4. رکاوٹ کو درست کریں | مناسب اصلاح کا اطلاق کریں |
| 5. دوبارہ پیمائش کریں | بہتری کی تصدیق کریں؛ رجعت کے لیے چیک کریں |

## الگورتھمک آپٹیمائزیشن
کارکردگی کا سب سے بڑا فائدہ بہتر الگورتھم کے انتخاب سے حاصل ہوتا ہے، نہ کہ مائیکرو آپٹیمائزیشن سے۔
| تبدیلی | بہتری |
|---------|------------|
| لکیری تلاش O(n) → ہیش ٹیبل تلاش O(1) | 100x+ بڑے ڈیٹا سیٹس کے لیے |
| نیسٹڈ لوپ O(n²) → Sort + binary search O(n log n) | بڑے n کے لیے طول و عرض کے احکامات |
| بار بار کی گنتی → یادداشت / کیشنگ | بے کار کام کو ختم کرتا ہے |
| ایک لوپ میں سٹرنگ جوڑنا → بلڈر / جوائن | چوکور سٹرنگ کاپی کرنے سے گریز کرتا ہے |
| غیر ترتیب شدہ ڈیٹا → بائنری تلاش کے ساتھ ترتیب شدہ ڈیٹا | O(log n) کی بجائے O(n) فی تلاش |

## کیشنگ کی حکمت عملی
کیشنگ نتائج کو شمار کرتی ہے تاکہ انہیں دوبارہ گنتی کی ضرورت نہ پڑے۔
| کیشے کی قسم | مقام | رفتار | زندگی بھر |
|------------|---------|---------|------------|
| **CPU کیشے** | L1/L2/L3 | ~1 ns | خودکار |
| **یادداشت میں** | ایپلیکیشن RAM (ڈکٹ، ہیش میپ) | ~100 این ایس | کلیئر یا بے دخل ہونے تک |
| **تقسیم شدہ کیش** | Redis, Memcached | ~1 ms | قابل ترتیب TTL |
| **CDN** | دنیا بھر میں ایج سرورز | ~10-50 ms | قابل ترتیب TTL |
| **براؤزر کیشے** | صارف کا براؤزر | ~1 ms | HTTP کیشے ہیڈر |
| **ڈیٹا بیس استفسار کیشے** | ڈیٹا بیس یا ORM کی سطح | ~1-10 ms | ڈیٹا تبدیل ہونے تک |
### کیشنگ پیٹرنز
| پیٹرن | تفصیل | کب استعمال کریں |
|---------|------------|------------|
| **کیشے ایک طرف** | ایپلیکیشن چیک کیشے؛ مس پر DB سے بوجھ؛ کیشے میں اسٹورز | سب سے عام؛ سادہ |
| **لکھ کر** | بیک وقت کیشے اور ڈی بی پر لکھیں | جب پڑھتا ہے >> لکھتا ہے؛ مستقل مزاجی اہم |
| **لکھنے کے پیچھے** | کیش پر لکھیں؛ متضاد طور پر DB کو لکھیں | ہائی رائٹ تھرو پٹ؛ کچھ ڈیٹا ضائع ہونے کا خطرہ |
| **TTL (زندگی کا وقت)** | کیش اندراجات ایک مقررہ وقت کے بعد ختم ہو جاتے ہیں | جب ڈیٹا وقتا فوقتا تبدیل ہوتا ہے |
| ** باطل ** | واضح طور پر باسی کیش اندراجات کو ہٹا دیں | جب آپ جانتے ہیں کہ ڈیٹا کب تبدیل ہوتا ہے |
### کیشے کی غلط کاری
کمپیوٹر سائنس میں دو مشکل ترین مسائل: کیشے کی غلطیاں، چیزوں کا نام دینا، اور ایک سے ایک غلطیاں۔
| حکمت عملی | تفصیل |
|------------|---------------|
| **TTL پر مبنی** | اندراجات N سیکنڈ کے بعد ختم ہو جاتے ہیں۔ سادہ لیکن باسی ڈیٹا پیش کر سکتا ہے |
| **ایونٹ پر مبنی** | ڈیٹا تبدیل ہونے پر باطل کریں؛ زیادہ پیچیدہ لیکن درست |
| **ورژن پر مبنی** | ایک ورژن نمبر شامل کریں؛ تبدیلیوں پر اضافہ |
| **ٹیگ پر مبنی** | ٹیگ متعلقہ کیشے اندراجات؛ ٹیگ کے ساتھ تمام اندراجات کو باطل کریں |

## ڈیٹا بیس کی اصلاح
ڈیٹا بیس اکثر ویب ایپلیکیشنز میں سب سے بڑی رکاوٹ ہوتے ہیں۔
| تکنیک | تفصیل | اثر |
|------------|---------------|---------|
| **انڈیکسنگ** | WHERE, JOIN, ORDER BY | میں استعمال ہونے والے کالموں پر اشاریہ جات شامل کریں۔ 10-1000x تیز سوالات |
| **سوال کی اصلاح** | منتخب کرنے سے گریز کریں *؛ استفسارات کا تجزیہ کرنے کے لیے EXPLAIN کا استعمال کریں | I/O کو کم کریں |
| **کنکشن پولنگ** | نئے بنانے کے بجائے ڈیٹا بیس کنکشن دوبارہ استعمال کریں | کنکشن اوور ہیڈ کو ختم کریں |
| ** نقلیں پڑھیں** | ریپلیکا ڈیٹا بیس میں سوالات پڑھنے کا راستہ | پڑھنے کا بوجھ تقسیم کریں |
| **تقسیم** | بڑی میزوں کو چھوٹے پارٹیشنز میں تقسیم کریں۔ بڑے ڈیٹا سیٹس پر تیز تر استفسارات |
| **ڈی نارملائزیشن** | شمولیت سے بچنے کے لیے بے کار ڈیٹا شامل کریں | تیز پڑھتا ہے؛ آہستہ لکھتا ہے |
| **مادی خیالات** | پہلے سے شمار شدہ استفسار کے نتائج | فوری پیچیدہ سوالات |
| **N+1 کی روک تھام** | JOINs، بے چین لوڈنگ، یا بیچ کے سوالات کا استعمال کریں۔ ہزاروں سوالات کو ختم کریں |

## ہم آہنگی اور ہم آہنگی۔
| تصور | تفصیل | کب استعمال کریں |
|---------|------------|------------|
| **تھریڈنگ** | ایک ہی عمل کے اندر ایک سے زیادہ تھریڈز | I/O- پابند کام (نیٹ ورک، ڈسک) |
| **ملٹی پروسیسنگ** | متعدد عمل (ازگر میں GIL کو نظرانداز کرتا ہے) | CPU کے پابند کام |
| **Async/انتظار** | کوآپریٹو ملٹی ٹاسکنگ؛ واحد دھاگہ | اعلی ہم آہنگی I/O (ویب سرورز) |
| **GPU کمپیوٹنگ** | ہزاروں متوازی کور | میٹرکس آپریشنز؛ تصویری پروسیسنگ؛ ایم ایل |
### Async بمقابلہ تھریڈنگ
| پہلو | Async/انتظار | تھریڈنگ |
|---------|------------|------------|
| **ماڈل** | کوآپریٹو (کاموں کی پیداوار کنٹرول) | قبل از وقت (OS دھاگوں کو تبدیل کرتا ہے) |
| **اوور ہیڈ** | بہت کم (کوئی سیاق و سباق سوئچنگ نہیں) | اعلی (دھاگے کی تخلیق، سیاق و سباق کی تبدیلی) |
| **پیچیدگی** | آسان استدلال (واحد دھاگہ) | دوڑ کے حالات، تعطل، تالے |
| ** کے لیے بہترین ** | کئی ایک ساتھ I/O آپریشنز | بلاکنگ آپریشنز جنہیں async نہیں کیا جا سکتا |
| **حد بندی** | بلاک کیے بغیر CPU- پابند کوڈ کا استعمال نہیں کر سکتا Python میں GIL حقیقی متوازی کو محدود کرتا ہے |

## فرنٹ اینڈ پرفارمنس
| تکنیک | تفصیل | اثر |
|------------|---------------|---------|
| **منفیفیکیشن** | خالی جگہ کو ہٹا دیں اور متغیر ناموں کو مختصر کریں | 20-40% چھوٹی فائلیں |
| **بنڈلنگ** | متعدد فائلوں کو کم درخواستوں میں جوڑیں۔ کم HTTP درخواستیں |
| **کوڈ کی تقسیم** | صرف موجودہ صفحہ کے لیے درکار کوڈ لوڈ کریں۔ تیز تر ابتدائی بوجھ |
| **سست لوڈنگ** | تصاویر اور اجزاء کو لوڈ کریں جب ان کی ضرورت ہو | تیز تر ابتدائی رینڈر |
| **درخت ہلنا** | بنڈلز سے غیر استعمال شدہ کوڈ کو ہٹا دیں | چھوٹے بنڈل |
| **تصویر کی اصلاح** | WebP/AVIF استعمال کریں؛ ذمہ دار تصاویر؛ سست لوڈنگ | 50-80% چھوٹی تصاویر |

| **HTTP/2 اور HTTP/3** | ملٹی پلیکسنگ ہیڈر کمپریشن؛ 0-RTT | تیز تر پروٹوکول اوور ہیڈ |
| **سروس ورکرز** | آف لائن استعمال کے لیے کیش اثاثے؛ پش اطلاعات | تیزی سے دہرائے جانے والے دورے |

## میموری آپٹیمائزیشن

|------------|-------------|

| **سٹریمنگ** | ہر چیز کو میموری میں لوڈ کرنے کے بجائے ٹکڑوں میں ڈیٹا پراسیس کریں |
| **جنریٹرز / تکرار کرنے والے** | فہرستیں بنانے کے بجائے ایک وقت میں ایک ہی پیداوار کی قدریں |

## خلاصہ
کارکردگی کی اصلاح ایک منظم عمل ہے: پیمائش کریں، رکاوٹ کی نشاندہی کریں، اسے ٹھیک کریں، دوبارہ پیمائش کریں۔ سب سے بڑی جیت الگورتھم میں بہتری اور غیر ضروری کام کو ختم کرنے سے حاصل ہوتی ہے — نہ کہ مائیکرو آپٹیمائزیشن سے۔ کیشنگ، ڈیٹا بیس انڈیکسنگ، اور کنکرنسی سب سے طاقتور ٹولز ہیں۔ فرنٹ اینڈ پرفارمنس پے لوڈ کے سائز اور راؤنڈ ٹرپس کو کم سے کم کرنے پر منحصر ہے۔ اور سب سے اہم اصول ہمیشہ ایک جیسا ہوتا ہے: اندازہ نہ لگائیں - پروفائل۔
