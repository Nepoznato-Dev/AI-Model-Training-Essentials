# API ڈیزائن اور انضمام کی ناکامیاں
APIs (ایپلی کیشن پروگرامنگ انٹرفیس) جدید سافٹ ویئر کے مربوط ٹشو ہیں — وہ خدمات کو بات چیت کرنے دیتے ہیں، فریق ثالث کو انضمام کرنے دیتے ہیں، اور ٹیموں کو آزادانہ طور پر کام کرنے دیتے ہیں۔ جب API ڈیزائن غلط ہو جاتا ہے، تو اس کے نتائج ہر اس سسٹم میں پھیل جاتے ہیں جو اس پر منحصر ہوتا ہے: ٹوٹا ہوا انضمام، حفاظتی کمزوریاں، ڈویلپر کی مایوسی، اور مہنگی دوبارہ لکھنا۔ انضمام کی ناکامیاں - جہاں سسٹم قابل اعتماد طریقے سے بات چیت نہیں کرسکتے ہیں - پیداوار کے واقعات کے سب سے عام ذرائع میں سے ہیں۔
---

## عام API ڈیزائن کی ناکامیاں
### ڈیزائن کی غلطیاں
| غلطی | تفصیل | نتیجہ |
|---------|------------|------------|
| **متضاد نام** | `/getUsers`بمقابلہ`/list_users`بمقابلہ`/fetch-users`| الجھاؤ؛ غلطیاں سست ترقی |
| **اوور لوڈڈ اینڈ پوائنٹس** | ایک اختتامی نقطہ جو پیرامیٹرز کی بنیاد پر 10 مختلف چیزیں کرتا ہے | سمجھنا مشکل؛ ٹیسٹ کرنے کے لئے مشکل؛ تبدیل کرنا مشکل |
| **انڈر فیچنگ** | متعلقہ ڈیٹا حاصل کرنے کے لیے کلائنٹ کو 5 API کالز کرنے کی ضرورت ہے۔ سست؛ فضول پیچیدہ کلائنٹ کوڈ |
| **زیادہ بازیافت** | API تمام فیلڈز واپس کرتا ہے جب کلائنٹ کو صرف 2 کی ضرورت ہوتی ہے۔ ضائع شدہ بینڈوڈتھ؛ موبائل پر سست؛ سیکورٹی رسک (غیر ضروری ڈیٹا کو بے نقاب کرنا) |
| **کوئی ورژن نہیں** | بریکنگ تبدیلیاں بغیر انتباہ کے تعینات | کلائنٹ ٹوٹ جاتے ہیں؛ ناراض ڈویلپرز |
| **غلطی کے مبہم پیغامات** | "خرابی 500: اندرونی سرور کی خرابی" بغیر کسی تفصیلات کے | ڈیبگ کرنا ناممکن؛ سست قرارداد |
| **لاپتہ صفحہ بندی** | اختتامی نقطہ تمام ریکارڈ واپس کرتا ہے (لاکھوں ہوسکتا ہے) | ٹائم آؤٹ؛ یادداشت کی تھکن؛ گر کر تباہ کلائنٹس |
| **متضاد اسٹیٹس کوڈز** | غلطیوں کے لیے 200 ٹھیک ہے؛ کلائنٹ کی غلطیوں کے لیے 500 | کلائنٹس کامیابی کو ناکامی سے الگ نہیں کر سکتے
### REST API اینٹی پیٹرنز
| اینٹی پیٹرن | تفصیل | بہتر نقطہ نظر |
|---------------|---------------|-------------------|
| **میوٹیشنز کے لیے GET استعمال کرنا** | `GET /delete-user?id=5`| DELETE طریقہ استعمال کریں۔
| **ہر چیز کے لیے POST استعمال کرنا** | `POST /get-users`; `POST /update-user`| مناسب HTTP طریقے استعمال کریں (GET, POST, PUT, PATCH, DELETE) |
| **API سے HTML کی واپسی** | API HTML کے ٹکڑے واپس کرتا ہے | واپس JSON؛ کلائنٹ کو رینڈر کرنے دیں |
| **یو آر ایل میں کاروباری منطق** | `/users/active/premium/from-2023`| استفسار کے پیرامیٹرز کا استعمال کریں یا پیچیدہ فلٹرز کے لیے باڈی کی درخواست کریں |
| **ڈیٹا بیس اسکیما کو بے نقاب کرنا** | `/api/table_name/column`| ڈیزائن API وسائل اور ڈومین تصورات کے ارد گرد، میزیں نہیں |
| **کوئی HATEOAS / لنکس نہیں** | کلائنٹ تمام URLs کو ہارڈ کوڈ کرتا ہے | جوابات میں متعلقہ وسائل کے لنکس شامل کریں |

## سیکیورٹی کی ناکامیاں
### عام API کمزوریاں
| کمزوری | تفصیل | مثال |
|---------------|---------------|---------|
| **ٹوٹی ہوئی تصدیق** | API شناخت کی درست طریقے سے تصدیق نہیں کرتا ہے | لاپتہ ٹوکن کی توثیق؛ میعاد ختم ہونے والے ٹوکن قبول کر لیے گئے |
| ** ضرورت سے زیادہ ڈیٹا کی نمائش** | API کلائنٹ کی ضروریات سے زیادہ ڈیٹا واپس کرتا ہے | صارف کا اختتامی نقطہ پاس ورڈ ہیشز اور اندرونی IDs واپس کرتا ہے |
| **بڑے پیمانے پر تفویض** | کلائنٹ وہ فیلڈ سیٹ کر سکتا ہے جو انہیں نہیں کرنا چاہیے | `PATCH /user``role: "admin"` | ترتیب دینے کی اجازت دیتا ہے۔
| **انجیکشن** | صارف کے ان پٹ کو کوڈ سے تعبیر کیا جاتا ہے | ایس کیو ایل انجکشن؛ NoSQL انجکشن؛ کمانڈ انجیکشن |
| **IDOR** (غیر محفوظ براہ راست آبجیکٹ حوالہ) | URL میں ID تبدیل کرکے وسائل تک رسائی حاصل کرنا |  کسی اور کا ڈیٹا دیکھنے کے لیے`/api/users/5`→`/api/users/6`میں تبدیل کریں |
| **ریٹ محدود کرنا غائب** | API کالز پر کوئی حد نہیں | وحشیانہ قوت؛ سروس سے انکار؛ سکریپنگ |
| **CORS غلط کنفیگریشن** | حد سے زیادہ اجازت یافتہ کراس اوریجن رسائی | `Access-Control-Allow-Origin: *`توثیق شدہ اختتامی پوائنٹس پر |
### توثیق اور اجازت کی ناکامیاں
| ناکامی | تفصیل | اثر |
|---------|------------|---------|
| **ہارڈ کوڈ شدہ اسناد** | ماخذ کوڈ میں API کیز یا پاس ورڈز | ورژن کنٹرول کے ذریعے لیک؛ تمام ڈویلپرز کے لیے قابل رسائی |
| **کوئی ٹوکن ایکسپائری نہیں** | ٹوکن کبھی ختم نہیں ہوتے | چوری شدہ ٹوکن مستقل رسائی دیتا ہے |
| **کمزور خفیہ چابیاں** | مختصر یا متوقع دستخطی چابیاں | ٹوکن جعلی ہو سکتے ہیں |
| **کوئی گنجائش / اجازت نہیں** | تمام ٹوکنز کو مکمل رسائی حاصل ہے | سمجھوتہ شدہ ٹوکن = مکمل سسٹم تک رسائی |
| **لاگنگ حساس ڈیٹا** | لاگ ان میں ٹوکنز یا پاس ورڈز | لاگ رسائی کے ساتھ ہر کسی کے لیے قابل رسائی |
| **متضاد اجازت** | کچھ اینڈ پوائنٹس پرمیشن چیک کرتے ہیں۔ دوسرے نہیں کرتے | غیر محفوظ شدہ اختتامی پوائنٹس کے ذریعے غیر مجاز رسائی |

## انضمام کی ناکامیاں
### تقسیم شدہ نظام کے انضمام کے مسائل
| ناکامی | تفصیل | مثال |
|---------|------------|---------|
| **تنگ کپلنگ** | خدمات ایک دوسرے کے داخلی نفاذ کی تفصیلات پر منحصر ہیں | ایک سروس کا ڈیٹا بیس تبدیل کرنے سے تین دوسرے ٹوٹ جاتے ہیں |
| ** ہم وقت ساز زنجیریں** | سروس A کال کرتا ہے B کال کرتا ہے C کال کرتا ہے D؛ تاخیر جمع ہوتی ہے | 200ms + 300ms + 500ms = 1 سیکنڈ جوابی وقت |
| **کوئی سرکٹ بریکر نہیں** | سروس میں ناکامی کاسکیڈنگ ناکامی کا سبب بنتی ہے | سروس D سست ہے۔ تمام اپ اسٹریم سروسز ان کے تھریڈز کا انتظار کر رہی ہیں |
| **کوئی دوبارہ کوشش کی منطق نہیں** | عارضی ناکامیاں مستقل ہو جاتی ہیں | نیٹ ورک بلپ = ناکام ٹرانزیکشن؛ صارف کو دستی طور پر دوبارہ کوشش کرنی ہوگی |
| ** ضرورت سے زیادہ کوششیں** | بیک آف کے بغیر دوبارہ کوششیں ریکورینگ سروسز کو مغلوب کر دیتی ہیں | گرجنے والے ریوڑ کا مسئلہ |
| **کوئی قابلیت نہیں** | غیر قابل عمل آپریشن کی دوبارہ کوشش کرنے سے ڈپلیکیٹس بنتا ہے | ادائیگی دو بار چارج کی گئی؛ آرڈر دو بار بنایا |
| **مستقل مستقل مزاجی** | کلائنٹ لکھنے کے بعد باسی ڈیٹا پڑھتا ہے | صارف کی تازہ کاری پروفائل؛ صفحہ تازہ کرتا ہے؛ پرانا ڈیٹا اب بھی دکھایا گیا ہے |
### تیسرے فریق کے انضمام کی ناکامیاں
| ناکامی | تفصیل | تخفیف |
|---------|------------|------------|
| **وینڈر API تبدیلیاں** | فریق ثالث بغیر اطلاع کے اپنا API تبدیل کرتا ہے۔ ورژن پننگ؛ تجریدی پرت؛ وینڈر چینج لاگز کی نگرانی |
| **شرح محدود** | فریق ثالث آپ کی درخواستوں کو روکتا ہے | کیشنگ قطار لگانے کی درخواست؛ زیادہ حدوں پر گفت و شنید |
| **وینڈر ڈاؤن ٹائم** | تھرڈ پارٹی سروس دستیاب نہیں ہے | سرکٹ بریکر؛ فال بیک رویہ؛ ملٹی وینڈر حکمت عملی |
| **ڈیٹا فارمیٹ میں تبدیلیاں** | فریق ثالث ردعمل کی شکل میں تبدیلیاں | سکیما کی توثیق؛ تبدیلی کی پرت؛ فارمیٹ تبدیلیوں پر الرٹس |
| **ہجرت کے راستے کے بغیر فرسودگی** | وینڈر بغیر کسی مساوی کے اختتامی نقطہ کو فرسودہ کرتا ہے | باخبر رہنا؛ تجرید کو برقرار رکھنا؛ جلد ہجرت کا منصوبہ بنائیں |

## کیس اسٹڈیز
### کیس اسٹڈی 1: وہ API جس نے سب کچھ لوٹا دیا۔
| پہلو | تفصیل |
|---------|---------------|
| **منظرنامہ** | SaaS کمپنی کے صارف API نے تمام صارف فیلڈز بشمول اندرونی میٹا ڈیٹا |
| **کیا غلط ہوا** | کوئی فیلڈ فلٹرنگ نہیں؛ جواب میں پاس ورڈ ہیشز، اندرونی نوٹس، اور ایڈمن فلیگ شامل تھے۔
| **اثر** | سیکورٹی محققین نے نمائش کو دریافت کیا؛ عوامی انکشاف؛ GDPR تحقیقات |
| **بنیادی وجہ** | API نے بغیر فلٹرنگ کے پورے ڈیٹا بیس ماڈل کو سیریلائز کیا |
| ** درست کریں** | واضح جوابی ماڈل؛ فیلڈ لیول تک رسائی کا کنٹرول؛ تمام اینڈ پوائنٹس کا سیکورٹی جائزہ |
| **سبق** | کبھی بھی اپنے ڈیٹا بیس ماڈل کو کسی API کے ذریعے براہ راست ظاہر نہ کریں۔ DTOs (ڈیٹا ٹرانسفر آبجیکٹ) کا استعمال کریں |
### کیس اسٹڈی 2: کاسکیڈنگ ناکامی۔
| پہلو | تفصیل |
|---------|---------------|
| **منظرنامہ** | ہم وقت ساز انٹر سروس کمیونیکیشن کے ساتھ ایک مائیکرو سروسز فن تعمیر |
| **کیا غلط ہوا** | ایک سروس کو ڈیٹا بیس کی سست روی کا سامنا کرنا پڑا۔ اپ اسٹریم سروسز جوابات کا انتظار کر رہی تھیں۔ دھاگے کے تالاب ختم |
| **اثر** | 45 منٹ کے لیے سسٹم کی مکمل بندش؛ تمام خدمات متاثر |
| **بنیادی وجہ** | کوئی سرکٹ بریکر نہیں؛ کوئی ٹائم آؤٹ نہیں؛ ہم وقت ساز انحصار کا سلسلہ |
| ** درست کریں** | سرکٹ بریکر؛ ٹائم آؤٹ async مواصلات جہاں ممکن ہو؛ بلک ہیڈز |
| **سبق** | خدمات کے درمیان ہم وقت ساز کالیں نازک زنجیریں پیدا کرتی ہیں۔ ناکامی کے لئے ڈیزائن |

## بہترین طرز عمل
### API ڈیزائن چیک لسٹ
| علاقہ | مشق |
|------|------------|
| **نام دینا** | وسائل کے لیے اسم استعمال کریں؛ کارروائیوں کے لیے HTTP طریقے؛ مسلسل نام دینے کا کنونشن |
| **ورژننگ** | پہلے دن سے ورژن؛ یو آر ایل ورژننگ (`/v1/`) یا ہیڈر ورژننگ کا استعمال کریں۔
| **صفحہ بندی** | فہرست کے اختتامی نکات کو ہمیشہ صفحہ بندی کریں؛ بڑے ڈیٹاسیٹس کے لیے کرسر پر مبنی صفحہ بندی کا استعمال کریں |
| **خرابی کو سنبھالنا** | مستقل غلطی کی شکل؛ ایرر کوڈز شامل کریں؛ قابل عمل پیغامات فراہم کریں |
| **شرح محدود** | شرح کی حدود کو لاگو کریں؛ دوبارہ کوشش کے بعد ہیڈر کے ساتھ 429 واپس کریں۔
| **آدمی** | اتپریورتن کے اختتامی نکات کے لیے آئیڈیمپوٹینسی کیز کو سپورٹ کریں |
| **دستاویزات** | OpenAPI / سویگر اسپیک؛ اسے اپ ڈیٹ رکھیں؛ مثالیں فراہم کریں |
| **ٹیسٹنگ** | معاہدہ ٹیسٹ؛ انضمام ٹیسٹ؛ صارفین پر مبنی معاہدہ ٹیسٹ |
| **مانیٹرنگ** | ٹریک لیٹینسی؛ غلطی کی شرح؛ تھرو پٹ انحصار صحت |
| **فرسودگی** | فرسودگیوں کا پہلے سے اعلان کریں۔ نقل مکانی کے رہنما فراہم کریں |

## خلاصہ
API ڈیزائن کی ناکامیاں کاسمیٹک (متضاد نام دینے) سے لے کر تباہ کن (سیکیورٹی کی کمزوریاں، جھڑنے والی ناکامیاں) تک ہوتی ہیں۔ ڈیزائن کی سب سے عام غلطیاں — اوورلوڈ اینڈ پوائنٹس، اوور فیچنگ، صفحہ بندی کی کمی، مبہم غلطیاں — APIs کو استعمال اور برقرار رکھنا مشکل بنا دیتی ہیں۔ سیکیورٹی کی ناکامیاں — ٹوٹی ہوئی تصدیق، IDOR، بڑے پیمانے پر تفویض، ضرورت سے زیادہ ڈیٹا کی نمائش — سسٹم کو حملے کے لیے بے نقاب کرنا۔ انضمام کی ناکامیاں — سخت جوڑے، ہم آہنگی کی زنجیریں، گمشدہ سرکٹ بریکرز، کوئی قابلیت نہیں — ایسے نازک نظام تخلیق کرتے ہیں جہاں ایک ناکامی تمام سروسز میں جھڑ جاتی ہے۔ فریق ثالث کے انضمام سے بیرونی خطرے میں اضافہ ہوتا ہے: API تبدیلیاں، شرح کو محدود کرنا، اور وینڈر ڈاؤن ٹائم۔ روک تھام کی حکمت عملی اچھی طرح سے قائم ہے: واضح جوابی ماڈلز استعمال کریں۔ پہلے دن سے ورژن؛ سرکٹ بریکر اور ٹائم آؤٹ کو لاگو کرنا؛ کمزوری کے لئے ڈیزائن؛ تمام ان پٹ کی توثیق اور جراثیم کشی؛ ہر چیز کی نگرانی؛ اور API کے معاہدوں کو پابند معاہدوں کے طور پر مانتے ہیں جن میں تبدیلی کے لیے کوآرڈینیشن کی ضرورت ہوتی ہے۔ بہترین APIs بورنگ ہیں — پیشین گوئی کے قابل، مستقل، اچھی طرح سے دستاویزی، اور ناکامی کے لیے لچکدار۔
