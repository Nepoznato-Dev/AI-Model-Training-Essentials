# ML 工程和 MLOps
构建机器学习模型只是成功的一半。将其投入生产、保持其可靠运行、监控漂移并对其进行迭代——这就是 ML 工程和 MLOps 的用武之地。该文件涵盖了从实验到生产系统的整个生命周期。
---

## 机器学习生命周期
|相|描述 |主要活动|
|--------|-------------|---------------|
| **1.问题定义** |将业务问题构建为 ML 任务 |定义指标、约束、成功标准 |
| **2.数据收集** |收集并标记训练数据 | ETL、标签、增强 |
| **3.实验** |训练和评估模型 |特征工程、超参数调整 |
| **4.型号选择** |选择最佳型号 |比较指标，评估权衡 |
| **5.部署** |将模型交付生产 |服务基础设施、API、批量 |
| **6。监控** |注意漂移和退化 |数据漂移、概念漂移、性能 |
| **7.再培训** |使用新数据更新模型 |计划或触发的再培训 |
大部分价值（和难度）都在第 5-7 阶段。 Jupyter 笔记本中的模型不会创造商业价值。

## 模型服务模式
|图案|描述 |延迟 |使用案例|
|--------|-------------|---------|---------|
| **批量推理** |按计划对一批数据运行模型 |营业时间 |每日推荐、欺诈评分 |
| **在线推理** |根据请求进行实时预测 |毫秒 |搜索排名，实时分类 |
| **流式推理** |对数据流的处理预测 |秒|异常检测、事件处理 |
### 服务基础设施
|工具|类型 |最适合 |
|------|------|----------|
| **TensorFlow 服务** |模型服务器| TensorFlow 模型 |
| **火炬服务** |模型服务器| PyTorch 模型 |
| **Triton 推理服务器** |多框架| GPU 推理，多种框架 |
| **vLLM** |法学硕士服务|高通量LLM推理|
| **BentoML** |统一服务|与框架无关的部署 |
| **谢尔顿** | K8s 原生 | Kubernetes 模型部署 |
| **雷发球** |可扩展的服务 |大型模型、分布式推理 |

## 模型注册表
模型注册表是用于管理 ML 模型（模型的版本、元数据、指标和部署状态）的集中存储。
|能力|描述 |
|------------|-------------|
| **版本控制** |使用唯一 ID 跟踪每个模型版本 |
| **元数据** |训练数据、超参数、指标、作者 |
| **阶段转换** |通过阶段移动模型：暂存 → 生产 → 存档 |
| **血统** |跟踪哪些数据和代码生成了每个模型 |
|工具|描述 |
|------|-------------|
| **MLflow** |开源；模型注册+实验跟踪|
| **权重和偏差 (W&B)** |商业的;实验跟踪+模型注册|
| **DVC** |使用 Git 进行数据和模型版本控制 |
| **Azure ML / SageMaker** |云原生模型管理 |

## 实验跟踪
每个机器学习实验都应该被跟踪：使用了哪些数据、哪些超参数、产生了哪些指标。
|工具|主要特点|
|------|-------------|
| **MLflow** |开源、自托管、跟踪参数/指标/工件 |
| **W&B** |丰富的 UI、扫描、工件版本控制、报告 |
| **海王星** | MLOps 的元数据存储 |
| **张量板** |内置于 TensorFlow 中；可视化训练曲线 |
### 追踪什么
|类别 |示例 |
|----------|---------|
| **参数** |学习率、批量大小、模型架构、纪元数 |
| **指标** |准确率、损失、F1、AUC-ROC（每个 epoch 和最终）|
| **文物** |模型权重、混淆矩阵、预测样本 |
| **数据** |数据集版本、分割比、预处理步骤 |
| **环境** | Python 版本、库版本、硬件 |

## 模型部署策略
|战略|它是如何运作的 |风险|
|----------|-------------|------|
| **影子部署** |新模式与旧模式并行；预测已进行比较但未实现 |零风险；上线前验证 |
| **金丝雀发布** |将小部分流量路由至新模型；逐渐增加|风险低；快速回滚|
| **A/B 测试** |将用户分为新老用户；比较业务指标|衡量实际影响 |
| **蓝绿** |两个相同的环境；一次切换所有流量 |即时回滚；转型期间的双重成本|
| **功能标志** |按用户细分打开/关闭模型 |细粒度控制 |

## 监控机器学习系统
机器学习系统比传统软件需要更多的监控，因为数据本身可能会发生变化。
### 漂移的类型
|漂移类型|有何变化？示例|
|------------|-------------|---------|
| **数据漂移** |输入分配变化|营销活动后客户人口统计数据发生变化 |
| **概念漂移** |输入输出变化关系|经济衰退期间消费者行为发生变化|
| **标签漂移** |目标分布变化|欺诈率从 1% 上升至 5% |
### 监控什么
|类别 |指标|
|----------|---------|
| **模型性能** |准确率、精确率、召回率、F1、AUC（与基线相比）|
| **数据质量** |缺失值、特征分布、异常值 |
| **漂移检测** |统计检验（KS 检验、PSI、KL 散度）|
| **基础设施** |延迟、吞吐量、GPU 利用率、内存 |
| **业务指标** |转化率、收入影响、用户满意度 |
### 监控工具
|工具|类型 |
|------|------|
| **显然是人工智能** |开源数据漂移和模型性能监控 |
| **格拉法纳** |仪表板可视化（与 Prometheus 配合使用）|
| **为什么实验室** |数据可观测平台|
| **阿里兹** |机器学习可观察性和根本原因分析 |
| **普罗米修斯 + Grafana** |基础设施和应用程序指标|

## 可重复的培训
可重复性意味着您可以重新运行实验并获得相同的结果。它对于调试、审核和合规性至关重要。
＃＃＃ 要求
|要求 |如何实现？
|------------------------|--------------------|
| **数据版本控制** | DVC、Delta Lake 或带有哈希值的数据集快照 |
| **代码版本控制** |所有培训代码的 Git |
| **环境固定** | `requirements.txt`、`conda env`、具有确切版本的 Docker 映像 |
| **播种** |修复 numpy、torch、tensorflow 的随机种子 |
| **配置管理** |所有超参数的 Hydra、OmegaConf 或 YAML 配置 |
| **文物追踪** | MLflow 或 W&B 记录每个实验 |

## 缩放推理
当模型每天需要处理数百万个请求时，性能就很重要。
|技术|描述 |
|------------|-------------|
| **批处理** |将多个请求分组到单个前向传递中 |
| **量化** |降低模型精度（FP32 → INT8 或 INT4）以加快推理速度 |
| **模型蒸馏** |训练较小的模型来模仿较大的模型 |
| **修剪** |删除不重要的权重或神经元 |
| **缓存** |缓存频繁的预测以避免重新计算 |
| **GPU 优化** | TensorRT、ONNX 运行时、Flash 注意 |
| **水平缩放** |在负载均衡器后面运行多个模型副本 |

## ML 的功能标志
功能标志可让您控制哪个模型版本为哪些用户提供服务，而无需重新部署。
|使用案例|描述 |
|----------|-------------|
| **逐步推出** |向 5% 的用户提供新模型，然后增加 |
| **终止开关** |如果检测到问题，立即恢复到以前的模型 |
| **基于细分** |不同的机型适合不同的用户群|
| **实验** |具有业务指标的 A/B 测试模型变体 |
工具：LaunchDarkly、Unleash、Flagsmith 或简单的数据库支持的功能标志。

## MLOps 成熟度曲线
|水平|特点 |
|--------|----------------|
| **0 级 — 手动** |手动训练、手动部署、无监控 |
| **级别 1 — 实验** |实验跟踪、模型注册、基本 CI |
| **2 级 — 自动化** |自动再训练、模型 CI/CD、自动化测试 |
| **3 级 — 完整管道** |具有监控、漂移检测和自动重新训练功能的端到端自动化管道 |
大多数组织处于 0 级和 1 级之间。目标是 2-3 级，其中 ML 生命周期是自动化和自我修复的。
