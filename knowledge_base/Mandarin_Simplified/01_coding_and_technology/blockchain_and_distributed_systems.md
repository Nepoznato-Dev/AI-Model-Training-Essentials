# 区块链和分布式系统
区块链是一种特定类型的分布式系统——一种分散的、仅附加的分类账，其中记录（块）通过加密哈希链接。分布式系统是使多台计算机作为一台计算机协同工作的更广泛的领域。这两个概念对于理解现代基础设施都很重要，从加密货币到分布式数据库，再到为全球服务提供支持的共识算法。
---

## 分布式系统基础知识
### 为什么是分布式系统？
|动机|描述 |
|------------|-------------|
| **可扩展性** |添加更多机器来处理更多负载 |
| **容错** |即使某些机器出现故障，系统仍能继续工作 |
| **地理分布** |为附近数据中心的用户提供服务 |
| **专业化** |不同的机器处理不同的任务|
### 关键概念
|概念 |描述 |挑战|
|--------|-------------|------------|
| **共识** |让所有节点就一个值达成一致|网络分区；拜占庭式的错误
| **复制** |跨多个节点复制数据 |一致性与可用性|
| **分区（分片）** |跨节点分割数据 |热点；跨分片查询 |
| **一致性模型** |保证不同读者看到的内容 |强一致性速度慢；最终一致性可以让用户大吃一惊|
| **CAP定理** |你只能拥有其中的2个：一致性、可用性、分区容错性|实际中需要分区容错性；选择 C ​​或 A |
### CAP 定理
|选择|你得到什么 |你放弃什么 |示例|
|--------|-------------|-----------------|---------|
| **CP** |一致+分区容忍|分区期间某些节点可能不可用 | HBase、MongoDB、Redis |
| **美联社** |可用+分区容忍|读取可能会返回陈旧数据 |卡桑德拉、DynamoDB、CouchDB |
| **CA** |一致+可用|不能容忍网络分区 |单节点数据库（非真正分布式）|

## 共识算法
分布式节点如何就系统状态达成一致？
|算法|类型 |容错 |用于 |
|------------|------|----------------|---------|
| **Paxos** |崩溃容错 | 2f+1 个节点最多 f 个故障 |谷歌胖乎乎的；基础理论|
| **木筏** |崩溃容错| 2f+1 个节点最多 f 个故障 | etcd、领事、TiKV |
| **PBFT** |拜占庭容错 | 3f+1 个节点最多 f 个故障 |超级账本结构 |
| **工作证明** |拜占庭容错 |取决于算力 |比特币 |
| **权益证明** |拜占庭容错 |取决于股份 |以太坊 2.0，卡尔达诺 |
### 筏（简化）
|角色 |责任|
|------|----------------|
| **领导者** |处理所有客户请求；向关注者发送日志条目 |
| **关注者** |响应领导的要求；选举投票|
| **候选人** |请求投票成为领导者 |
1. 所有节点均以追随者身份启动
2. 如果追随者在选举超时期间没有收到领导者的消息，它将成为候选人
3. 候选人请求投票；得票最多的人成为领导者
4.领导者将日志条目复制给追随者
5. 当多数人确认时，条目被提交

## 区块链
### 区块链如何运作
|组件|描述 |
|------------|-------------|
| **阻止** |一批交易+元数据+前一个区块的哈希值|
| **哈希** |区块内容的加密指纹 |
| **链** |每个块都引用前一个块的哈希值，创建一个不可变的链 |
| **共识** |网络参与者就添加哪些区块达成一致 |
| **默克尔树** |总结区块中所有交易的哈希树 |
### 为什么区块链难以篡改
1. 每个区块都包含前一个区块的哈希值
2. 更改任何交易都会更改区块的哈希值
3. 改变的哈希值破坏了链条——所有后续的块都变得无效
4. 攻击者需要重新挖掘所有后续区块并控制超过 50% 的网络
### 区块链的类型
|类型 |访问 |验证者 |示例|
|------|--------|------------|---------|
| **公开（无需许可）** |任何人都可以读写 |开放共识（PoW、PoS）|比特币、以太坊 |
| **私人（许可）** |限制访问 |已知验证器 |超级账本、Corda |
| **财团** |由一组组织管理 |选定的验证者 | R3 Corda 银行业 |
### 智能合约
存储在区块链上的自动执行代码，在满足预定条件时运行。
|平台|语言 |显着特点|
|----------|----------|-----------------|
| **以太坊** |坚固性，Vyper |最大的智能合约生态系统 |
| **索拉纳** |鲁斯特，C |高通量；费用低|
| **卡尔达诺** |哈斯克尔（普利托斯）|同行评审；形式验证|
| **超级账本** | Go、Java、JavaScript |企业;许可|

## 分布式数据库
|数据库|建筑|一致性|最适合 |
|----------|-------------|-------------|---------|
| **卡桑德拉** |宽柱；点对点|可调整（最终达到法定人数）|高写入吞吐量；时间序列|
| **MongoDB** |文档;副本集 |最终（具有因果一致性选项）|灵活的架构；快速发展|
| **CockroachDB** |分布式SQL； Raft 共识 |强|分布式SQL；全球部署|
| **TiDB** |分布式SQL； Raft（通过 TiKV）|强|兼容MySQL；水平缩放 |
| **DynamoDB** |键值；管理 |最终（或具有一致读取的强）|无服务器； AWS 集成 |
| **扳手** |分布式SQL；帕克索斯|强|谷歌云；全球一致性|

## 分布式系统模式
|图案|描述 |使用案例|
|---------|-------------|----------|
| **领导人选举** |选择一个节点进行协调 |筏首领；动物园管理员 |
| **复制** |复制数据以实现冗余并读取扩展 |数据库副本； CDN |
| **分片** |按键范围或哈希对数据进行分区 |大型数据库|
| **MapReduce** |跨节点分割计算；汇总结果|大数据处理|
| **八卦协议** |节点定期与随机对等点共享状态 |集群成员资格；故障检测|
| **两阶段提交** |协调跨多个节点的交易 |分布式数据库|
| **传奇模式** |具有补偿动作的一系列本地事务|微服务交易|
| **断路器** |停止调用失败的服务；快速失败|弹力;防止级联故障|

## 分布式系统中的挑战
|挑战|描述 |缓解措施 |
|------------|-------------|------------|
| **网络分区** |节点无法通信 | CAP 权衡；后退重试 |
| **时钟偏差** |不同节点有不同的时钟|使用逻辑时钟；国家时间规划；避免依赖挂钟时间|
| **拜占庭式错误** |撒谎或任意行为的节点 | BFT共识；区块链|
| **裂脑** |两个节点都认为自己是领导者 |击剑;基于法定人数的决策 |
| **级联故障** |一次失败引发其他失败 |断路器；舱壁；优雅降级|
| **数据一致性** |保持副本同步 |一致性模型；冲突解决|
---

＃＃ 概括
分布式系统是现代软件扩展、抵御故障以及为全球用户提供服务的方式。共识算法（Raft、Paxos）确保节点达成一致。区块链增加了加密验证和去中心化，以创建不可信的分类账。分布式数据库（Cassandra、CockroachDB、DynamoDB）大规模处理数据。 CAP 定理所体现的基本权衡是网络不可靠时的一致性和可用性之间的权衡。理解这些概念对于构建在互联网规模上运行的系统至关重要。
