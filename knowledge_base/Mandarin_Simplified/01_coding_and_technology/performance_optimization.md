# 性能优化
性能优化是使软件更快的实践——减少响应时间、提高吞吐量、降低内存使用量并消除瓶颈。这是开发人员可以拥有的最有影响力的技能之一，因为缓慢的软件会失去用户，浪费资源，并使每个人都感到沮丧。但这也是最常见的错误之一，开发人员根据直觉而不是证据来优化错误的事情。
---

## 黄金法则
> **首先测量，其次优化。** 切勿基于假设进行优化。分析代码，找到实际的瓶颈，然后修复它。
|反模式|为什么它不好 |
|-------------|-------------|
| **过早优化** |花时间加速并不慢的代码 |
| **无需测量即可优化** |修复错误的瓶颈；无法验证改进|
| **为了速度而牺牲可读性** |不可读代码的成本超过了性能增益 |
| **缓存所有内容** |陈旧数据、内存膨胀、复杂性 |
---

## 分析
在你能够更快地完成某些事情之前，你需要知道时间花在了“哪里”。
|工具类型|它测量什么 |示例 |
|------------|------------------|----------|
| **CPU 分析器** |哪些函数消耗最多的CPU时间| cProfile (Python)、perf (Linux)、Chrome DevTools (JS) |
| **内存分析器** |内存分配和泄漏| tracemalloc (Python)、Valgrind、heaptrack |
| **I/O 分析器** |磁盘和网络 I/O 瓶颈 | iotop、strace、Wireshark |
| **APM（应用程序性能监控）** |端到端请求时序 | New Relic、Datadog、Jaeger |
| **浏览器开发工具** |前端渲染、JavaScript 执行、网络 | Chrome 开发者工具、Firefox 分析器 |
### 分析工作流程
|步骤|描述 |
|------|-------------|
| 1.识别运行缓慢|用户报告页面加载缓慢；监控显示高延迟 |
| 2.分析完整路径 |查找哪个组件花费最多时间 |
| 3. 深入探究 |分析特定组件以查找热门功能 |
| 4.修复瓶颈|应用适当的优化 |
| 5.再次测量|验证改进情况；检查回归 |
---

## 算法优化
最大的性能提升来自于选择更好的算法，而不是来自微观优化。
|改变 |改进|
|--------|------------|
|线性搜索 O(n) → 哈希表查找 O(1) |大型数据集 100 倍以上 |
|嵌套循环 O(n²) → 排序 + 二分查找 O(n log n) |大 n 的数量级 |
|重复计算→记忆/缓存|消除多余的工作 |
|循环中的字符串连接 → Builder / join |避免二次字符串复制 |
|未排序的数据 → 使用二分查找排序的数据 |每次查找 O(log n) 而不是 O(n) |
---

## 缓存策略
缓存存储计算结果，因此不需要重新计算。
|缓存类型|地点 |速度|终身|
|------------|----------|--------|----------|
| **CPU 缓存** | L1/L2/L3 | ~1 纳秒 |自动|
| **内存中** |应用程序 RAM（字典、HashMap）| ~100 纳秒 |直到被清除或驱逐为止|
| **分布式缓存** | Redis、Memcached | ~1 毫秒 |可配置的TTL |
| **CDN** |全球边缘服务器 | ~10-50 毫秒 |可配置的TTL |
| **浏览器缓存** |用户的浏览器| ~1 毫秒 | HTTP 缓存标头 |
| **数据库查询缓存** |数据库或ORM级别| ~1-10 毫秒 |直到数据发生变化 |
### 缓存模式
|图案|描述 |何时使用 |
|---------|-------------|----------|
| **缓存旁路** |应用程序检查缓存；未命中时从数据库加载；存储在缓存中|最常见；简单|
| **直写** |同时写入缓存和数据库 |当读>>写时；一致性很重要|
| **后写** |写入缓存；异步写入数据库|高写入吞吐量；一些数据丢失风险|
| **TTL（生存时间）** |缓存条目在设定时间后过期 |当数据周期性变化时 |
| **无效** |显式删除过时的缓存条目 |当您确切知道数据何时发生变化时 |
### 缓存失效
计算机科学中两个最难的问题：缓存失效、命名事物和差一错误。
|战略|描述 |
|----------|-------------|
| **基于 TTL** |条目在 N 秒后过期；简单但可能提供过时的数据|
| **事件驱动** |数据改变时失效；更复杂但更准确|
| **基于版本** |包含版本号；变化增量 |
| **基于标签** |标签相关的缓存条目；使带有标签 | 的所有条目无效

## 数据库优化
数据库往往是 Web 应用程序中最大的瓶颈。
|技术|描述 |影响 |
|------------|-------------|--------|
| **索引** |在 WHERE、JOIN、ORDER BY | 中使用的列上添加索引查询速度提高 10-1000 倍 |
| **查询优化** |避免选择 *;使用 EXPLAIN 分析查询 |减少 I/O |
| **连接池** |重用数据库连接而不是创建新连接 |消除连接开销 |
| **读取副本** |将读取查询路由到副本数据库 |分配读取负载 |
| **分区** |将大表拆分为较小的分区 |更快地查询大型数据集 |
| **非规范化** |添加冗余数据以避免连接 |读取速度更快；写入速度较慢|
| **物化视图** |预先计算的查询结果 |即时复杂查询|
| **N+1预防** |使用 JOIN、预加载或批量查询 |消除数千个查询 |

## 并发和并行
|概念 |描述 |何时使用 |
|---------|-------------|----------|
| **线程** |单个进程内的多个线程 | I/O 密集型任务（网络、磁盘）|
| **多处理** |多进程（绕过Python中的GIL）| CPU 密集型任务 |
| **异步/等待** |协作多任务处理；单线程|高并发 I/O（Web 服务器）|
| **GPU 计算** |数千个并行核心 |矩阵运算；图像处理；机器学习 |
### 异步与线程
|方面|异步/等待 |线程 |
|--------|------------|------------|
| **型号** |合作（任务产量控制）|抢占式（操作系统切换线程）|
| **开销** |非常低（无上下文切换）|更高（线程创建、上下文切换）|
| **复杂性** |更简单的推理（单线程） |竞争条件、死锁、锁 |
| **最适合** |许多并发 I/O 操作 |阻止无法异步的操作 |
| **限制** |无法在不阻塞的情况下使用 CPU 密集型代码 | Python 中的 GIL 限制了真正的并行性 |

## 前端性能
|技术|描述 |影响 |
|------------|-------------|--------|
| **缩小** |删除空格并缩短变量名称 |文件小 20-40% |
| **捆绑** |将多个文件合并为更少的请求 |更少的 HTTP 请求 |
| **代码分割** |仅加载当前页面所需的代码 |更快的初始加载 |
| **延迟加载** |在需要时加载图像和组件 |更快的初始渲染 |
| **摇树** |从捆绑包中删除未使用的代码 |较小的捆绑 |
| **图像优化** |使用WebP/AVIF；响应式图像；延迟加载 |图像小 50-80% |
| **CDN** |从边缘服务器提供静态资产 |降低全球延迟 |
| **HTTP/2 和 HTTP/3** |多路复用；标头压缩； 0-RTT |更快的协议开销|
| **服务人员** |缓存资源以供离线使用；推送通知 |更快的重复访问 |

## 内存优化
|技术|描述 |
|------------|-------------|
| **对象池** |重用对象而不是创建新对象 |
| **流媒体** |分块处理数据，而不是将所有内容加载到内存中 |
| **生成器/迭代器** |一次生成一个值，而不是构建列表 |
| **内存映射文件** |访问大文件而不完全加载它们 |
| **垃圾收集调整** |根据您的工作负载调整 GC 参数 |
| **数据结构选择** |使用数组而不是链表来实现缓存局部性；使用集合进行成员资格测试 |

## 网络优化
|技术|描述 |
|------------|-------------|
| **压缩** | gzip、brotli 用于 HTTP 响应 |
| **连接重用** |保持连接活跃； HTTP/2 多路复用 |
| **请求批处理** |将多个 API 调用合并为一个 |
| **分页** |分页加载数据而不是一次性加载所有数据 |
| **休息时压缩** |压缩数据库和缓存中的数据 |
| **协议选择** | gRPC（二进制、高效）与 REST（人类可读）|

## 监控和警报
|公制|它告诉你什么 |
|--------|------------------|
| **P50 / P95 / P99 延迟** |不同百分位数的响应时间 |
| **吞吐量** |每秒请求数 |
| **错误率** |失败请求的百分比 |
| **CPU 利用率** |使用了多少处理能力 |
| **内存使用情况** |内存消耗；接近极限？ |
| **数据库查询时间** |需要优化的慢查询 |

＃＃ 概括
性能优化是一个系统的过程：测量、识别瓶颈、修复它、再次测量。最大的胜利来自算法改进和消除不必要的工作，而不是微观优化。缓存、数据库索引和并发是最强大的工具。前端性能取决于最小化有效负载大小和往返行程。最重要的规则始终是相同的：不要猜测 - 个人资料。
