# 测试方法
测试是您如何获得代码工作的信心——更重要的是，对代码的更改不会破坏已经工作的内容。良好的测试可以在用户之前发现错误，记录预期行为，并实现无畏的重构。该文件涵盖了从单元测试到端到端测试的全部测试策略，以及使测试有效的原则。
---

## 测试金字塔
测试金字塔描述了项目中测试的理想分布。
```
        /  E2E  \          ← Few; slow; expensive; test the whole system
       /─────────\
      / Integration\       ← Some; test how components work together
     /───────────────\
    /   Unit Tests    \    ← Many; fast; cheap; test individual functions
   /─────────────────────\
```

|水平|计数 |速度|成本|它测试什么 |
|--------|--------|--------|------|---------------|
| **单位** |许多|快速（毫秒）|低|单独的函数、类、方法 |
| **整合** |一些|中（100ms-s）|中等|组件如何交互；数据库查询； API 调用 |
| **端到端** |很少|慢（秒-分钟）|高|真实系统中完整的用户流程|
---

## 单元测试
单独测试各个代码单元。
### 原则
|原理|描述 |
|------------|-------------|
| **快** |每个测试应以毫秒为单位运行 |
| **隔离** |测试并不相互依赖；没有共享状态 |
| **确定性** |相同的输入→每次相同的输出（无随机性，无时间依赖性）|
| **自检** |测试自动通过或失败；无需人工检查|
| **及时** |写在代码旁边或之前 (TDD) |
### 测试剖析
|相|描述 |
|--------|-------------|
| **安排** |设置测试数据和依赖关系 |
| **行动** |调用正在测试的函数或方法 |
| **断言** |验证结果符合预期 |
### 测试什么
|类别 |示例 |
|----------|---------|
| **幸福之路** |正常输入产生预期输出 |
| **边缘情况** |空输入、null、零、最大值、单个元素 |
| **错误案例** |输入无效、数据丢失、权限被拒绝 |
| **边界条件** |落后一分；完全处于极限|
### 模拟和存根
|术语 |描述 |何时使用 |
|------|-------------|-------------|
| **模拟** |一个记录它如何被调用的假对象 |验证交互（这个方法被调用了吗？） |
| **存根** |返回预定值的假对象 |提供测试数据（从数据库返回该用户） |
| **间谍** |记录对真实对象的调用的包装器 |部分验证 |
| **假** |一个简化但有效的实现 |用于测试的内存数据库 |
|模拟库 |语言 |
|----------------|--------|
| **单元测试.mock** |蟒蛇 |
| **开玩笑** | JavaScript/TypeScript |
| **莫基托** |爪哇 |
| **起订量** | C# |
| **作证/gomock** |去 |

## 集成测试
测试多个组件如何协同工作。
|测试什么 |示例|
|-------------|---------|
| **数据库查询** | ORM 是否生成正确的 SQL？是否使用索引？ |
| **API 端点** |完整的请求-响应周期是否有效？ |
| **服务交互** |服务A是否正确调用服务B？ |
| **外部依赖** |支付网关集成是否有效？ |
### 策略
|战略|描述 |权衡|
|----------|-------------|------------|
| **真正的依赖** |使用真实的数据库、真实的消息队列|最现实；慢点;更难设置|
| **测试容器** |为每次测试运行启动 Docker 容器 |良好的平衡性；可重复|
| **内存中的替代品** | H2代替PostgreSQL；内存消息总线|快速地;可能会错过现实世界的问题|
| **合同测试** |验证服务是否遵守其 API 合同 |捕捉界面变化 |
---

## 端到端 (E2E) 测试
从用户的角度测试整个系统。
|工具|类型 |最适合 |
|------|------|----------|
| **剧作家** |浏览器自动化 |网络应用程序；跨浏览器 |
| **柏树** |浏览器自动化 |网络应用程序；开发者经验|
| **硒** |浏览器自动化 |遗产;广泛的语言支持|
| **排毒** |移动端对端 | React Native 应用程序 |
| **Appium** |移动端对端 |本机和混合移动应用程序 |
| **大师** |移动端对端 |移动应用程序；简单的 YAML 语法 |
| **k6 / 蝗虫** |负载测试|负载下的性能|
### 端到端最佳实践
|实践|为什么 |
|----------|-----|
| **仅测试关键路径** | E2E测试速度慢；专注于最重要的事情 |
| **使用测试数据工厂** |以编程方式创建测试数据；不要依赖种子数据 |
| **测试后清理** |每次测试都应该让系统处于已知状态 |
| **避免测试 UI 细节** |测试行为，而不是 CSS 类或元素位置 |
| **在 CI 中运行** | E2E 测试必须在每次更改时自动运行 |

## 测试驱动开发 (TDD)
先编写测试，然后编写代码使其通过。
|步骤|描述 |
|------|-------------|
| **1.红色** |编写一个描述所需行为的失败测试 |
| **2.绿色** |编写最少的代码使测试通过 |
| **3.重构** |清理代码，同时保持测试绿色 |
|效益 |描述 |
|---------|-------------|
| **设计反馈** |测试迫使您在实现之前考虑接口 |
| **回归安全** |每个错误都会经过测试； bug 永远不会再出现 |
| **文档** |测试是预期行为的活生生的记录 |
| **信心** |高测试覆盖率实现无所畏惧的重构 |
---

## 行为驱动开发（BDD）
BDD 通过用自然语言编写从用户角度描述行为的测试来扩展 TDD。
### 给定-当时-那么格式
```
Given a user with an empty shopping cart
When they add a "Python Book" priced at $29.99
Then the cart total should be $29.99
And the cart should contain 1 item
```

|工具|语言 |
|------|----------|
| **黄瓜** | Java、JavaScript、Ruby 等 |
| **行为** |蟒蛇 |
| **SpecFlow** | C# |
| **开玩笑**（用描述/它）| JavaScript |

## 其他测试类型
|类型 |它测试什么 |工具|
|------|--------------|--------|
| **性能/负载** |负载下的系统行为| k6、JMeter、Locust、加特林 |
| **安全** |漏洞和攻击向量| OWASP ZAP、Burp Suite、Snyk |
| **辅助功能** | WCAG 合规性 |斧头，灯塔，pa11y |
| **合同** |服务之间的API兼容性| Pact、Spring Cloud 合约 |
| **突变** |测试套件本身的质量| Stryker、mutmut、PIT |
| **视觉回归** |版本之间的 UI 变化 | Percy、Chromatic、BackstopJS |
| **混乱** |系统的故障恢复能力|混沌猴、石蕊、小魔怪 |
| **烟** |部署后的基本功能 |自定义脚本；健康检查|
| **浸泡** |长时间内的系统行为 |长时间运行的负载测试|

## 测试组织
|图案|描述 |何时使用 |
|---------|-------------|----------|
| **同地办公** |在他们测试的代码旁边进行测试（`src/utils.test.ts`）|大多数项目；很容易找到|
| **单独的目录** |在`tests/`或`__tests__/`文件夹中进行测试 |大型项目；清晰的分离|
| **测试夹具** |`fixtures/`目录中的共享测试数据 |当多个测试需要相同的数据时|
| **测试实用程序** |`test-utils/`目录中的共享助手 |当设置逻辑复杂时 |
---

## 代码覆盖率
|公制|它测量什么 |限制|
|--------|-----------------|------------|
| **线路覆盖** |测试执行的代码行的百分比 |不衡量断言的质量 |
| **分支机构覆盖** |采取的分支（if/else）百分比 |比线路覆盖更好；仍然没有捕获所有错误|
| **路径覆盖** |所采用的执行路径的百分比 |最彻底；复杂代码中的指数 |
| **突变分数** |测试发现突变的百分比|测试质量的最佳衡量标准 |
**目标**：80% 的线路覆盖率是合理的默认值。但覆盖率只是一个指导，而不是目标——弱断言的 100% 覆盖率比彻底测试的 70% 覆盖率要差。
---

## 持续集成和测试
|实践|描述 |
|----------|-------------|
| **在每次提交时运行所有单元测试** |快速反馈；立即捕获回归 |
| **在 PR 上运行集成测试** |捕获单元测试遗漏的问题 |
| **每晚运行 E2E 测试或合并到主程序** |缓慢而彻底|
| **快速失败** |在第一次失败时停止管道以节省时间 |
| **不稳定的测试政策** |立即隔离或删除不稳定的测试；永远不要忽视 |
| **测试并行化** |并行运行测试以减少 CI 时间 |
---

## 实用技巧
- **清楚地命名测试。**`test_calculates_tax_for_high_earner`告诉您什么出了问题。 `test_1`什么也没告诉你。
- **每次测试一个断言（实用时）。** 使故障易于诊断。
- **不要测试实现细节。** 测试行为。如果重构内部结构，测试就不会中断。
- **避免测试第三方代码。** 模拟外部库；测试您的代码与它们的交互。
- **加快测试速度。** 如果您的测试套件需要 10 分钟，开发人员将停止运行它。不断优化。
- **删除死测试。** 总是通过的测试或测试已删除的代码是噪音。
- **像对待生产代码一样对待测试代码。**它应该可读、可维护且结构良好。
---

＃＃ 概括
测试不是可选的——它是构建不会崩溃的软件的方式。测试金字塔引导您进行许多快速单元测试、一些集成测试和一些 E2E 测试。 TDD 和 BDD 提供了结构化方法。模拟隔离单元进行测试。代码覆盖率衡量的是广度，而不是深度。最重要的原则是：如果它没有经过测试，它就坏了——你只是还不知道而已。
