# 网络安全基础知识
安全性是一门学科，必须从一开始就集成到系统的每一层，而不是事后添加。无论是构建 Web 应用程序、管理基础设施还是发布 API，了解威胁形势和防御基础知识都是至关重要的。
---

## 加密和密码学
### 对称加密与非对称加密
|类型 |它是如何运作的 |速度|密钥分发 |示例 |
|------|-------------|--------|------|----------|
| **对称** |加密和解密使用相同的密钥 |快|挑战：如何共享密钥？ | AES-256、ChaCha20 |
| **不对称** |公钥加密，私钥解密 |慢一点 |公钥可以公开共享 | RSA、ECC（椭圆曲线）|
在实践中，大多数系统都使用**两者**：使用非对称加密来安全地交换对称密钥，然后使用对称加密来处理大量数据。这就是 TLS/HTTPS 的工作原理。
### 哈希
散列是一种单向函数：它将输入转换为固定大小的字符串。你无法反转它，但相同的输入总是产生相同的输出。
|使用案例|推荐算法 |避免 |
|----------|------------------------|--------|
| **密码存储** | Argon2id、bcrypt、scrypt | MD5、SHA-1、普通 SHA-256（太快）|
| **数据完整性** | SHA-256、SHA-3 | MD5（损坏）、SHA-1（损坏）|
| **数字签名** | Ed25519、RSA-2048+ | DSA |
### TLS/HTTPS
HTTPS 是基于 TLS（传输层安全）的 HTTP。它提供：
- **加密**：传输中的数据无法被窃听者读取。
- **身份验证**：服务器通过证书证明其身份。
- **完整性**：数据在传输过程中无法被修改而不被检测到。
使用 TLS 1.2 或 1.3。禁用 TLS 1.0 和 1.1。启用 HSTS（HTTP 严格传输安全）以强制浏览器始终使用 HTTPS。

## 身份验证和授权
### 身份验证：你是谁？
|方法|安全级别|使用案例|
|--------|----------------|----------|
| **密码** |低-中 |基本帐户（强制执行 12 个以上字符，检查是否存在违规行为）|
| **艺术硕士（TOTP）** |高|敏感帐户标准（Google Authenticator、Authy）|
| **硬件密钥 (FIDO2/WebAuthn)** |非常高 |高安全性账户（YubiKey）|
| **生物识别** |中-高|设备解锁（指纹、面部）——不是唯一的因素 |
| **OAuth2 / OIDC** |高|第三方登录（“使用 Google 登录”）|
**密码规则**：强制执行最小长度（12-16 个字符）、检查违反的密码列表、使用 Argon2id 或 bcrypt 与每个用户盐进行哈希处理。
### 授权：你能做什么？
|型号|描述 |示例|
|--------|-------------|---------|
| **RBAC**（基于角色的访问控制）|分配给角色的权限；用户获得角色 |管理员、编辑、查看者 |
| **ABAC**（基于属性）|基于用户属性、资源、环境的规则 | “经理可以批准其团队的请求”|
| **ACL**（访问控制列表）|每个用户/资源的显式权限 |文件权限（读/写/执行）|
**最小权限原则**：仅向每个用户、服务和进程提供他们所需的最低访问权限。
### JWT（JSON Web 令牌）
|方面|推荐|
|--------|----------------|
| **签署** | RS256或ES256（非对称）优先； HS256 可接受托管机密 |
| **到期** |访问令牌需要 15-60 分钟；对较长的会话使用刷新令牌 |
| **存储** |仅 HTTP cookie（不是 localStorage — 容易受到 XSS 攻击）|
| **验证** |始终验证签名、颁发者、受众和过期日期 |

## OWASP 前 10 名 (2021)
OWASP Top 10 是 Web 应用程序安全性的标准意识文档。它代表了最严重的风险：
| ＃|风险|这意味着什么？
|---|------|----------|
| 1 | **访问控制损坏** |用户可以访问他们不应该访问的资源 |
| 2 | **加密失败** |敏感数据加密薄弱或丢失 |
| 3 | **注射** | SQL、NoSQL、操作系统命令或 LDAP 注入 |
| 4 | **不安全的设计** |无法通过实施修复的架构缺陷 |
| 5 | **安全配置错误** |默认密码、开放端口、详细错误消息 |
| 6 | **易受攻击的组件** |依赖项中的已知 CVE |
| 7 | **身份验证失败** |弱密码、会话管理不善 |
| 8 | **诚信失败** |供应链攻击、未签名更新|
| 9 | **记录/监控故障** |未发现违规行为 |
| 10 | 10 **SSRF** |服务器被欺骗向内部系统发出请求 |

## 安全编码实践
### 输入验证
|规则|为什么 |
|------|-----|
| **白名单>黑名单** |定义允许的内容，而不是阻止的内容 |
| **参数化查询** |切勿将用户输入连接到 SQL 中 — 使用准备好的语句或 ORM |
| **HTML 编码** |编码`<`、`>`、`&`、`"`、`'`以防止 XSS |
| **外壳逃逸** |避免从用户输入构建 shell 命令；使用`shlex.quote()` |
| **长度限制** |强制执行最大长度以防止缓冲区溢出和 DoS |
| **类型检查** |确保整数是整数，布尔值是布尔值 |
### 常见漏洞
|漏洞|攻击|防御|
|--------------|--------|---------|
| **SQL 注入** |  登录表单中的`' OR 1=1 --`|参数化查询 |
| **XSS** |  评论区`<script>alert('hacked')</script>` |输出编码，内容安全策略|
| **CSRF** |欺骗用户的浏览器发出未经授权的请求 | CSRF 令牌、SameSite cookie |
| **路径遍历** |  文件参数中的`../../etc/passwd`|验证和清理文件路径 |
| **伊多尔** |将`/user/123`更改为`/user/124`以查看别人的数据 |对每个请求进行授权检查 |

## 网络安全
### 防火墙
|类型 |描述 |
|------|-------------|
| **数据包过滤** |基于IP、端口、协议的规则|
| **有状态** |跟踪连接状态；更智能的过滤|
| **应用程序级别（WAF）** |检查 HTTP 流量；阻止SQL注入、XSS等|
| **云安全组** |云实例的虚拟防火墙（AWS SG、Azure NSG）|
**经验法则**：默认阻止所有入站流量；只打开明确需要的内容（Web 为 80、443）。
### 网络分段
将数据库和缓存放置在无法直接访问 Internet 的私有子网中。将 DMZ 用于面向公众的服务（Web 服务器、负载均衡器）。将最小权限原则应用于网络访问。

## 秘密管理
### 黄金法则
**切勿对机密进行硬编码。**源代码中没有 API 密钥、密码或数据库 URL。提交给 Git 的环境变量中没有秘密。 Docker 镜像中没有秘密。
＃＃＃ 工具
|工具|类型 |最适合 |
|------|------|----------|
| **HashiCorp 金库** |企业机密管家|动态秘密，加密即服务 |
| **AWS Secrets Manager** |云原生 | AWS 环境 |
| **Azure 密钥保管库** |云原生 | Azure 环境 |
| **标准操作规程** |加密文件 |在 Git 中加密机密（使用 KMS 或 GPG） |
| **Docker 的秘密** |容器原生 | Docker Swarm（对于 K8s，请考虑 Secrets Store CSI）|
| **dotenv (.env)** |本地发展|仅限开发 - 从未投入生产或承诺 |
### 旋转
定期自动轮换机密。如果秘密被泄露（例如，提交到公共仓库），请立即轮换它 - 即使您认为没有人看到它。

## 依赖安全
您的应用程序的安全性取决于其最弱的依赖项。
### 扫描工具
|语言 |工具|
|----------|--------|
| **Python** |  `safety`、`pip-audit`、`bandit` |
| **Node.js** |  `npm audit`、`yarn audit`、`snyk` |
| **生锈** | `cargo audit`|
| **去** | `govulncheck`|
| **一般** | `Dependabot`(GitHub)、`Renovate`、`Trivy` |
### 供应链完整性
- 使用锁定文件（`package-lock.json`、`Cargo.lock`、`go.sum`）进行可重现的构建。
- 验证下载的依赖项的校验和。
- 更喜欢官方注册机构和经过验证的发布商。
- 通过 Dependabot 或 Renovate 自动进行次要/补丁更新。

## 安全开发生命周期 (SDL)
|相|活动 |
|--------|----------|
| **培训** |确保开发人员了解常见漏洞 |
| **威胁建模** |在设计过程中识别潜在威胁 |
| **安全编码标准** |通过 linter 和代码审查清单强制执行 |
| **先科科技** |源代码静态分析（SonarQube、CodeQL）|
| **达斯特** |运行应用程序的动态分析（OWASP ZAP、Burp Suite）|
| **SCA** |软件构成分析——扫描依赖关系|
| **渗透测试** |定期进行道德黑客演习 |
| **错误赏金** |鼓励外部研究人员发现漏洞|
| **事件响应计划** |为检测到违规行为制定明确的计划 |

## 紧急检查表
当您怀疑存在违规行为时：
1. **不要惊慌**——但要迅速采取行动。
2. **隔离**受影响的系统（如果需要，请断开网络连接）。
3. **保留证据**：捕获日志、内存转储、磁盘映像。
4. **确定范围**：哪些系统，哪些数据？
5. **轮换**所有泄露的凭证和机密。
6. **修补**漏洞。
7. 如果需要，**通知**受影响的用户和监管机构（在法定期限内）。
8. **事后分析**：在 24-48 小时内记录根本原因和行动项目。
