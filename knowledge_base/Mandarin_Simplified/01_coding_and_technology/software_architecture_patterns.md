# 软件架构模式
架构是关于系统如何组织的一组结构决策——它有哪些组件、它们如何通信以及职责所在。良好的架构使系统易于理解、修改和扩展。糟糕的架构会让每一次改变都变得困难。该文件涵盖了主要模式、何时使用每种模式以及所涉及的权衡。
---

## 整体架构与微服务
这是最基本的架构决策，值得正确执行。
|方面|巨石|微服务|
|--------|----------|----------------|
| **结构** |单一可部署单元|许多小型、可独立部署的服务 |
| **数据** |共享数据库|每个服务都拥有自己的数据|
| **通讯** |进程内函数调用 |网络调用（HTTP、gRPC、消息传递）|
| **缩放** |扩展整个应用程序 |扩展个性化服务|
| **部署** |单一发布周期 |独立部署|
| **复杂性** |初期开发更简单 |运营复杂性（网络、监控）|
| **最适合** |小团队，早期产品|大型团队、复杂领域、高规模|
### 何时开始使用单体架构
大多数应用程序应该作为一个整体开始。构建、测试、部署和调试更加简单。当您对域边界有了更清晰的了解后，您随时可以提取服务。这有时被称为“模块化整体”——具有清晰内部边界的整体，使以后的提取变得容易。
### 何时采用微服务
在以下情况下考虑微服务：
- 团队规模足够大，协调成为瓶颈。
- 系统的不同部分有非常不同的扩展要求。
- 您需要独立部署组件。
- 您的域具有明确的有界上下文（请参阅下面的 DDD）。

## 分层架构（N 层）
最常见的架构模式。代码被组织成多个层，每个层都有特定的职责。
```
â”Œ─────────────────────────┐
│   Presentation Layer    │  ← UI, controllers, API endpoints
├─────────────────────────┤
│   Application Layer     │  ← Use cases, orchestration
├─────────────────────────┤
│   Domain Layer          │  ← Business logic, entities
├─────────────────────────┤
│   Infrastructure Layer  │  ← Database, external services, file I/O
└─────────────────────────┘
```

|层|责任|规则|
|--------|----------------|------|
| **演示** |处理用户/HTTP 请求 |只能调用应用层 |
| **应用** |编排用例|可以调用Domain层|
| **域名** |核心业务逻辑 |不应依赖于其他层 |
| **基础设施** |技术问题|实现 Domain | 中定义的接口
**关键规则**：依赖关系指向内部。领域层不了解数据库或 Web 框架。

## 事件驱动架构
组件通过发出**事件**（已发生的事情）并做出反应来进行通信。
|图案|描述 |
|---------|-------------|
| **活动通知** |服务 A 发出“OrderPlaced”；服务 B、C、D 反应 |
| **事件溯源** |将所有状态更改存储为事件序列（不仅仅是当前状态）|
| **CQRS** |将读取模型（查询）与写入模型（命令）分开 |
### 事件溯源
不要将“当前状态”存储在数据库中，而是将每个状态更改存储为事件：
```
OrderCreated(order_id=123, total=$50)
OrderPaid(order_id=123, payment_id=456)
OrderShipped(order_id=123, tracking=ABC)
```

好处：完整的审计跟踪，能够重建任何过去的状态，解耦消费者。挑战：事件模式演变、最终一致性、调试复杂性。
### CQRS（命令查询职责分离）
|侧面|目的|数据库|
|------|---------|----------|
| **命令（写）** |处理突变；执行业务规则|针对写入进行优化（标准化）|
| **查询（读取）** |服务读取请求 |针对读取进行优化（非规范化）|
CQRS 与事件溯源自然配对：来自写入端的事件被投影到读取优化的视图中。

## 消息队列和事件代理
当服务需要异步通信时，消息队列就是骨干。
|工具|类型 |最适合 |
|------|------|----------|
| **阿帕奇卡夫卡** |分布式事件日志|高吞吐量事件流、事件溯源 |
| **RabbitMQ** |带有路由的消息代理|任务队列、复杂的路由模式|
| **AWS SQS** |托管队列 | AWS 原生，简单排队 |
| **AWS SNS** |发布/订阅通知 |扇出至多个订阅者 |
| **谷歌发布/订阅** |托管发布/订阅 | GCP 原生事件流 |
| **Redis 流** |轻量级流|简单的事件记录、缓存用例|
### 消息传递模式
|图案|描述 |
|---------|-------------|
| **点对点** |每条消息有一个生产者，一个消费者 |
| **发布/订阅** |一名制作者，多名订阅者 |
| **请求/回复** |异步传输上的同步风格 |
| **死信队列** |处理失败的消息将进入单独的队列进行检查 |

## 领域驱动设计（DDD）
DDD 是一种软件设计的战略方法，它将代码集中在业务概念而不是技术问题上。
### 关键概念
|概念 |描述 |
|---------|-------------|
| **有界上下文** |域模型在其中保持一致的边界（例如“订购”、“运输”、“计费”）|
| **无处不在的语言** |开发人员和领域专家之间的共享词汇|
| **聚合** |相关实体的集群被视为数据更改的单个单元 |
| **实体** |具有身份的对象（例如，具有 user_id 的用户）|
| **值对象** |没有身份的物体；由其属性定义（例如，金钱、地址）|
| **领域活动** |域中发生的事情（例如，OrderPlaced） |
| **反腐败层** |您的域和外部系统之间的转换层 |
### 当 DDD 有帮助时
当业务领域复杂时，DDD 最为有价值——例如电子商务、物流、金融服务、医疗保健。如果您的领域很简单（博客、待办事项应用程序），那么 DDD 就太过分了。

## 缓存策略
缓存是提高性能的最有效方法之一，但它带来了一致性方面的复杂性。
|战略|描述 |权衡|
|----------|-------------|------------|
| **缓存旁路** |应用程序首先检查缓存；未命中时从数据库加载 |简单的;最终一致性|
| **直写式** |同时写入缓存和数据库 |持续的;写入速度较慢|
| **后写式** |写入缓存；异步写入数据库|快速写入；数据丢失的风险|
| **通读** |透明地在未命中时从数据库缓存加载 |比缓存更简单 |
### 缓存什么
|层|什么 |工具|
|--------|------|--------|
| **CDN** |静态资产、API 响应 | CloudFront、Cloudflare |
| **应用** |计算结果、会话数据 | Redis、Memcached |
| **数据库** |查询结果、经常访问的行|查询缓存、物化视图 |
**缓存失效**是出了名的困难。常见策略：TTL（生存时间）、事件驱动的失效（数据更改时清除缓存）和 LRU（最近最少使用）驱逐。

## 设计模式
### 坚实的原则
|原理|这意味着什么？
|------------|--------------|
| **S** — 单一职责 |一个类应该有一个改变的理由 |
| **O** — 打开/关闭 |开放扩展，关闭修改 |
| **L** — 利斯科夫换人 |子类型应该可以替代它们的基类型 |
| **I** — 接口隔离 |多个专用接口>一个通用接口|
| **D** — 依赖倒置 |依赖抽象，而不是具体 |
### 常见模式
|图案|意向 |示例|
|--------|--------|---------|
| **单例** |确保一个类只有一个实例 |数据库连接池|
| **工厂** |创建对象而不指定确切的类 | `UserFactory.create(type="admin")`|
| **观察员** |状态发生变化时通知家属 |事件监听器，发布/订阅 |
| **策略** |在运行时交换算法 |付款策略：信用卡、PayPal、加密货币 |
| **存储库** |干净的界面背后的抽象数据访问| `UserRepository.find_by_id(123)`|
| **装饰器** |动态添加行为 |围绕服务记录装饰器 |
| **适配器** |让不兼容的接口协同工作 |旧版 API 适配器 |

## 选择正确的架构
不存在普遍的“最佳”架构。正确的选择取决于：
|因素|在以下情况下青睐整体式架构：在以下情况下青睐微服务：
|--------|------------------------|------------------------------------------|
| **团队规模** | < 10 developers | >20 名开发人员，多个团队 |
| **领域复杂性** |简单或易于理解 |复杂的、许多有界上下文 |
| **规模要求** |统一缩放需求|不同的组件需要不同的规模 |
| **部署节奏** |单一发布周期 |需要独立部署|
| **技术多样性** |一堆就可以了 |不同的服务需要不同的技术|
**实用建议**：从模块化整体开始。仅当您有明确的需求和明确的领域边界时才提取服务。过早的微服务是业界最常见的架构错误之一。
