# 机器学习项目失败
机器学习项目的失败率惊人——行业估计表明 60-85% 的机器学习项目从未投入生产。失败通常不在于算法；而在于算法。它们位于流程、数据、期望和组织环境中。了解机器学习项目失败的原因对于任何构建机器学习系统的人来说都是至关重要的，因为失败模式是可以预测的并且在很大程度上是可以避免的。
---

## 为什么机器学习项目会失败
### 失败类别
|类别 |失败的份额|描述 |
|----------|------------------|-------------|
| **数据问题** | 〜30% |数据不足、有偏见、陈旧或无法访问 |
| **问题定义** | 〜20% | ML 问题与业务需求不匹配 |
| **期望不匹配** | ~15% |利益相关者期待魔法；现实是渐进式改进|
| **部署失败** | ~15% |模型适用于笔记本电脑，但无法量产 |
| ** 组织问题** | 〜10% |没有明确的所有权；团队缺乏技能；没有行政支持|
| **模型性能** | 〜10% |模型未达到所需的准确性或泛化能力较差 |

## 数据相关的故障
### 常见数据问题
|问题 |描述 |示例|
|---------|-------------|---------|
| **数据不足** |没有足够的例子来学习有意义的模式 |针对 500 笔交易训练欺诈检测模型 |
| **标签质量** |培训标签错误、不一致或主观 |由非专家标记的医学图像；评估者间一致性较低的情绪标签 |
| **数据泄露** |来自未来或目标的信息泄漏到功能中 |使用客户流失结果作为特征；在训练中包括测试数据 |
| **选择偏差** |训练数据并不代表部署人群 |根据一家医院的数据训练医学模型；全国部署 |
| **概念漂移** |特征和目标之间的关系随着时间的推移而变化|大流行后消费者行为发生变化；根据大流行前数据训练的模型
| **功能不匹配** |培训期间可用的功能与生产中可用的功能不同|使用手动标签进行培训；生产采用不同分布的自动化标签|
| **类别不平衡** |目标类别高度倾斜 | 99% 阴性，1% 阳性；模型学会总是预测负面结果
### 数据泄露问题
|类型 |描述 |示例|
|------|-------------|---------|
| **目标泄漏** |某项功能仅在目标发生后才可用 | “治疗结果”用作预测“治疗成功”的特征 |
| **列车测试污染** |测试数据影响训练 |通过全球统计数据进行扩展（包括测试数据）；泄漏的数据增强 |
| **抽样偏差** |训练和生产使用不同的采样|网络流量培训；部署在移动应用程序流量上
| **预处理泄漏** |预处理步骤使用完整数据集中的信息 |用全局平均值（包括测试数据）估算缺失值 |

## 问题定义失败
### 错位模式
|图案|描述 |后果|
|---------|-------------|----------|
| **解决错误的问题** |业务需求X；团队建设 Y |模型技术上好但没什么用|
| **当规则足够时机器学习** |问题具有确定性规则；机器学习增加了复杂性 |过度设计；更难维护；难以解释|
| **数据不存在时的机器学习** |问题需要尚未收集的数据 |项目无法启动；在可行性上浪费了几个月的时间
| **没有业务背景的准确度目标** | “我们需要 95% 的准确率”——但这对企业意味着什么？ |模型满足准确性但不能解决业务问题 |
| **忽略错误的成本** |误报和漏报具有不同的成本|模型优化了错误的指标 |
| **没有基线** |与现有方法没有比较|无法判断 ML 是否真的比简单的启发式更好 |

## 期望失败
### 机器学习项目的技术成熟度曲线
|相|描述 |风险|
|--------|-------------|------|
| **兴奋** | “人工智能会解决一切！” |过度承诺；资源不足|
| **概念证明** |模型适用于笔记本中的干净数据 |虚假的信心； “有用！” |
| **现实检验** |生产数据混乱；性能下降|失望； “机器学习不起作用”|
| **死亡行军** |团队试图将其投入生产 |技术债务；职业倦怠|
| **放弃或安静部署** |项目在没有监控的情况下被取消或部署 |浪费投资|
### 管理期望
|战略|描述 |
|----------|-------------|
| **从基线开始** |与最简单的方法（规则；人类表现）进行比较 |
| **预先定义成功指标** |业务指标（收入；成本节省）不仅仅是 ML 指标（准确性；F1）|
| **时间盒探索** |在提交之前给团队 2-4 周的时间来评估可行性 |
| **展示机器学习不能做什么** |诚实面对局限性；设定现实的期望|
| **增量迭代** |先部署一个简单的模型；迭代改进|
| **量化错误成本** |将模型性能转化为业务影响 |

## 部署失败
### 为什么模型无法投入生产
|问题 |描述 |解决方案 |
|---------|-------------|----------|
| **笔记本与生产差距** |代码可以在 Jupyter 中运行，但尚未做好生产准备 | MLOps 实践；机器学习的 CI/CD；代码审查 |
| **延迟要求** |模型推理速度太慢，无法实时使用 |模型优化；量化；缓存|
| **可扩展性** |模型无法处理生产流量 |批量处理；水平缩放；模型服务基础设施|
| **监控差距** |无法检测模型何时降级 |数据漂移监控；绩效监控；警报|
| **依赖管理** |培训和服务环境不同 |集装箱化；可重复的环境|
| **没有回滚计划** |新模型失败时无法恢复到以前的模型 |模型注册；版本控制；自动回滚 |
### 模型衰减
|类型 |描述 |检测|
|------|-------------|------------|
| **数据漂移** |输入特征分布变化 |监控功能统计； KL 散度； PSI |
| **概念漂移** |特征与目标变化之间的关系|随着时间的推移监控预测准确性 |
| **标签漂移** |目标变化的定义或分布|跟踪标签分布；业务指标相关性|
| **上游变化** |数据源更改格式、时间或质量 |模式验证；新鲜度监控 |

## 组织失败
|失败|描述 |预防|
|--------|-------------|------------|
| **没有明确的所有权** |没有人对生产中的模型负责|指定模型所有者；定义 RACI |
| **孤立的团队** |数据科学家建立模型；工程师部署；没有人交流|跨职能团队；共同目标|
| **无 MLOps 成熟度** |没有型号注册；没有 CI/CD；没有监控|增量投资 MLOps 基础设施 |
| **不切实际的时间表** | “在 2 周内构建一个生产 ML 系统” |时间盒探索；迭代；沟通复杂性|
| **缺乏领域专业知识** | ML 团队不了解业务问题 |在 ML 团队中嵌入领域专家 |
| **没有评估框架** |无法判断模型是否在生产环境中工作 |定义业务指标；设置仪表板；定期评论|

## 经验教训
### ML 项目清单
|相|关键问题|
|--------|-------------|
| **问题定义** |这实际上是一个机器学习问题吗？底线是什么？成功是什么样的？ |
| **数据评估** |我们有足够的数据吗？有代表性吗？标签可靠吗？ |
| **可行性** |我们可以在 2-4 周内构建一个工作原型吗？有哪些风险？ |
| **发展** |是否存在数据泄露？我们是否使用了正确的评估指标？ |
| **预制作** |它适用于生产数据吗？够快吗？是否受到监控？ |
| **部署** |我们可以回滚吗？谁在值班？当它降解时会发生什么？ |
| **部署后** |我们正在监测漂移吗？是否跟踪业务指标？有再培训计划吗？ |

＃＃ 概括
机器学习项目失败并不是因为算法太难，而是因为围绕它们的流程被破坏了。数据问题——数据不足、标签不良、泄漏、漂移——是故障的最大组成部分。问题定义失败——解决错误的问题，在规则足够的情况下使用机器学习，忽略错误的成本——浪费数月的努力。预期失败——承诺过多、交付不足、不管理利益相关者——会破坏组织对机器学习的信任。部署失败——笔记本到生产的差距、延迟问题、无监控——意味着在开发中工作的模型永远不会在生产中创造价值。组织失败——没有所有权、孤立的团队、没有 MLO——从结构上来说不可能成功。解药是严格的练习：从基线开始；时间盒探索；严格验证数据；检查是否有泄漏；定义业务指标；增量部署；持续监控；并迭代。最好的机器学习团队在数据和流程上花费的时间比在模型上花费的时间更多。
