# 数据管道和 ETL 失败
数据管道是现代组织的管道——它们通过转换将数据从源系统转移到数据库、仓库和湖泊中，用于分析、机器学习和决策。当他们工作时，没有人注意到。当它们失败时，决策会基于陈旧的数据，模型会基于垃圾进行训练，报告会显示不可能的数字，并且对整个数据平台的信任也会受到削弱。数据管道故障是技术组织中最常见、成本最高的故障之一。
---

## 常见故障模式
### 数据质量问题
|失败|描述 |影响 |检测难度|
|--------|-------------|--------|------------------------|
| **静默数据损坏** |数据被错误修改，没有引发任何错误 |下游系统信任不良数据；基于虚假信息的决策|非常难——没有错误信号|
| **架构漂移** |源系统更改架构（添加、删除、重命名列）|管道中断或默默地丢弃数据 |中 - 管道可能会失败或产生部分结果 |
| **数据类型不匹配** |源在需要整数的地方发送字符串；浮动精度变化 |管道故障；数据被截断；舍入误差 |中 — 可能会导致管道错误或微妙的数据问题 |
| **重复记录** |同一事件被处理多次 |夸大的计数；不正确的聚合 |困难 — 每条记录看起来单独有效 |
| **空值/缺失值** |预期字段为空 |计算失败；模型产生错误的预测|中 — 取决于 null 处理 |
| **超出范围的值** |超出预期范围的值（负年龄；未来日期）|统计数据有偏差；破碎的业务逻辑|中 — 需要验证规则 |
| **迟到的数据** |处理窗口关闭后数据到达 |结果不完整；错过的记录|很难——结果看起来很完整，但实际上并非如此 |
### 管道基础设施问题
|失败|描述 |影响 |
|--------|-------------|--------|
| **编排失败** |调度程序（Airflow、Prefect）不会触发管道 |数据陈旧；没有处理发生 |
| **资源耗尽** |管道耗尽内存、CPU 或磁盘 |管道崩溃；部分结果 |
| **依赖失败** |上游系统宕机或速度缓慢 |管道无限期等待或失败 |
| **并发问题** |多个管道同时修改相同的数据 |比赛条件；数据损坏|
| **配置漂移** |环境变化（网络、凭证、端点）未反映在管道中 |管道意外失败 |
| **背压** |数据到达速度快于管道处理速度 |排队人数不断增加；增加延迟|

## 案例研究
### 案例研究 1：静默数据复制
|方面|描述 |
|--------|-------------|
| **场景** |一家电子商务公司的订单管道处理消息队列中的事件 |
| **出了什么问题** |消费者重启导致消息被重新消费；不存在重复数据删除逻辑|
| **影响** |在没有人注意到之前，收入数字在三周内被夸大了 15% |
| **根本原因** |无幂等键；至少一次交付，无需重复数据删除 |
| **修复** |新增基于订单ID的幂等键；实现一次性语义 |
| **课程** |至少一次投递需要重复数据删除；始终根据源系统验证总计 |
### 案例研究 2：架构变更破坏下游
|方面|描述 |
|--------|-------------|
| **场景** |支付提供商更改其 API 响应中的字段名称 |
| **出了什么问题** | ETL 管道默默地开始写入空值；没有架构验证 |
| **影响** |财务报告显示该支付方式的收入连续两个月为零 |
| **根本原因** |摄取时无需模式验证；空值被视为有效 |
| **修复** |添加了带有警报的模式验证；强制执行必填字段；空检查 |
| **课程** |永远不要相信外部模式会保持稳定；在边界处验证 |
### 案例研究 3：时区灾难
|方面|描述 |
|--------|-------------|
| **场景** |一家跨国公司汇总各个办事处的每日指标 |
| **出了什么问题** |一些来源使用 UTC，其他来源使用本地时间；管道未正常化|
| **影响** |每日总计不匹配；一些交易在错误的日期计算；月末结算错误 |
| **根本原因** |无标准时区政策；时间戳存储不一致 |
| **修复** |所有时间戳均存储为 UTC；仅在表示层转换为本地时间|
| **课程** |各地都采用 UTC 标准化；明确每个边界的时区 |

## 预防策略
### 数据验证
|战略|描述 |工具示例 |
|----------|-------------|----------------|
| **架构验证** |验证每个阶段的数据是否符合预期模式 |远大的期望；迪曲；苏打水|
| **范围检查** |值落在预期范围内 |自定义断言； DBT 测试 |
| **新鲜度检查** |数据是最新的，足够有用 |监控时间戳； SLA 警报 |
| **数量检查** |行数在预期范围内 |行计数异常检测 |
| **参照完整性** |外键匹配；没有孤儿记录| SQL 约束；数据质量工具|
| **跨源对账** |源和目标之间的总计匹配 |自动对账作业 |
### 管道设计模式
|图案|描述 |效益 |
|---------|-------------|---------|
| **幂等性** |多次运行管道会产生相同的结果 |可以安全重试；没有重复|
| **原子性** |管道要么完全成功，要么完全失败（无部分状态）|没有半处理的数据 |
| **检查点** |保存每个阶段的进度；从上一个检查点恢复 |容错；无需再处理|
| **死信队列** |失败的记录将进入单独的队列进行调查 |无数据丢失；可以调查和重播|
| **断路器** |当下游出现故障时停止处理 |防止级联故障|
| **数据合同** |生产者和消费者之间关于数据格式的协议|协调架构更改 |
### 监控和警报
|监控什么？为什么 |如何|
|----------------|-----|-----|
| **管道持续时间** |持续时间增加表明存在问题趋势分析； SLA 跟踪 |
| **行数** |突然的变化预示着问题|与历史平均水平比较|
| **零利率** |增加空值信号模式或源问题 |列级 null 跟踪 |
| **数据新鲜度** |过时的数据意味着管道未运行 |最新记录时间戳|
| **下游影响** |报告和模型是否使用正确的数据？ |端到端数据沿袭|
| **资源使用** |中央处理器;记忆;磁盘;网络|基础设施监控|

## 恢复策略
|情况|战略|
|------------|----------|
| **仓库中已存在错误数据** |确定受影响的时间范围；从源头进行再加工；通知下游消费者|
| **运行中途管道故障** |幂等设计允许安全重新运行；检查点允许恢复|
| **架构更改破坏了管道** |修复变换；回填受影响的数据；添加模式演化处理 |
| **无声腐败被发现较晚** |根本原因分析；确定爆炸半径；重新加工；添加监控以捕捉复发情况 |
| **数据丢失** |从备份恢复；从源头重播；评估损失是否可挽回|
---

＃＃ 概括
数据管道故障无处不在，而且通常比应用程序中断成本更高，因为它们产生错误的答案而不是明显的错误。无声数据损坏、模式漂移、重复、时区错误和缺失值是最常见的罪魁祸首。关键的预防策略是： 在每个边界（模式、范围、体积、新鲜度）验证数据；将管道设计为幂等和原子的；监控一切（持续时间、行数、空率、新鲜度）；对失败的记录使用死信队列；并在生产者和消费者之间建立数据合同。当发生故障时，响应应包括根本原因分析、受影响数据的重新处理、下游消费者的通知，以及最重要的是添加监控以捕获未来同类的故障。正确对待这一点的组织会像对待生产软件一样严格地对待数据管道：测试、监控、警报、事件响应和事后分析。
