# API 设计和集成失败
API（应用程序编程接口）是现代软件的结缔组织——它们让服务进行通信，让第三方集成，让团队独立工作。当 API 设计出错时，后果会波及到依赖它的每个系统：集成中断、安全漏洞、开发人员沮丧以及代价高昂的重写。集成故障（系统无法可靠地通信）是生产事件的最常见来源之一。
---

## 常见的 API 设计失败
### 设计错误
|错误|描述 |后果|
|---------|-------------|----------|
| **命名不一致** | `/getUsers`与`/list_users`与`/fetch-users`|困惑;错误；发展缓慢|
| **过载端点** |一个端点根据参数执行 10 项不同的操作 |难以理解；难以测试；很难改变|
| **获取不足** |客户端需要调用5次API才能获取相关数据 |慢的;浪费；复杂的客户端代码|
| **过度获取** |当客户端只需要 2 个时 API 返回所有字段 |浪费带宽；移动速度慢；安全风险（暴露不必要的数据）|
| **无版本控制** |在没有警告的情况下部署重大变更 |客户中断；愤怒的开发商|
| **含糊的错误消息** | “错误 500：内部服务器错误”，没有详细信息 |无法调试；分辨率慢|
| **缺少分页** |端点返回所有记录（可能是数百万条）|超时；记忆力耗尽；崩溃的客户端|
| **状态代码不一致** | 200 OK 表示错误；客户错误 500 |客户无法区分成功与失败|
### REST API 反模式
|反模式 |描述 |更好的方法|
|----------|-------------|-----------------|
| **使用 GET 进行突变** | `GET /delete-user?id=5`|使用删除方法 |
| **使用 POST 处理所有事情** |  `POST /get-users`; `POST /update-user`|使用适当的 HTTP 方法（GET、POST、PUT、PATCH、DELETE） |
| **从 API 返回 HTML** | API 返回 HTML 片段 |返回 JSON；让客户端渲染 |
| **URL 中的业务逻辑** | `/users/active/premium/from-2023`|使用查询参数或请求正文进行复杂过滤器 |
| **公开数据库架构** | `/api/table_name/column`|围绕资源和领域概念而不是表格设计 API |
| **没有 HATEOAS / 链接** |客户端硬编码所有 URL |在回复中包含相关资源的链接 |

## 安全失败
### 常见 API 漏洞
|漏洞|描述 |示例|
|--------------|-------------|---------|
| **身份验证被破坏** | API 无法正确验证身份 |缺少令牌验证；接受过期令牌 |
| **过多的数据暴露** | API 返回的数据多于客户端需求 |用户端点返回密码哈希值和内部 ID |
| **集体作业** |客户可以设置不应该设置的字段 | `PATCH /user`允许设置`role: "admin"`|
| **注射** |用户输入解释为代码 | SQL注入； NoSQL 注入；命令注入|
| **IDOR**（不安全的直接对象引用）|通过改变URL中的ID来访问资源|  `/api/users/5`→换成`/api/users/6`看别人的数据|
| **缺少速率限制** | API调用无限制|蛮力；拒绝服务；刮|
| **CORS 配置错误** |过于宽松的跨域访问 |  经过身份验证的端点上的`Access-Control-Allow-Origin: *`|
### 身份验证和授权失败
|失败|描述 |影响 |
|--------|-------------|--------|
| **硬编码凭证** |源代码中的 API 密钥或密码 |通过版本控制泄露；所有开发人员均可使用|
| **无令牌过期** |令牌永不过期 |被盗的令牌可提供永久访问权限 |
| **弱密钥** |简短或可预测的签名密钥 |代币可以伪造 |
| **无范围/权限** |所有代币都具有完全访问权限 |受损的令牌 = 完全系统访问权限 |
| **记录敏感数据** |日志中的令牌或密码 |具有日志访问权限的任何人都可以访问 |
| **授权不一致** |一些端点检查权限；其他人则不然 |通过不受保护的端点进行未经授权的访问 |

## 集成失败
### 分布式系统集成问题
|失败|描述 |示例|
|---------|-------------|---------|
| **紧密耦合** |服务之间相互依赖内部实现细节 |更改一项服务的数据库会破坏其他三项服务 |
| **同步链** |服务A调用B调用C调用D；延迟累积| 200ms + 300ms + 500ms = 1 秒响应时间 |
| **无断路器** |服务失败导致级联故障 |服务D慢；所有上游服务都耗尽了等待的线程|
| **没有重试逻辑** |暂时性故障变成永久性故障 |网络信号=交易失败；用户必须手动重试 |
| **重试次数过多** |没有回退的重试压倒了恢复服务|雷霆羊群问题|
| **无幂等性** |重试非幂等操作会创建重复项 |两次付款；订单创建两次 |
| **最终一致性惊喜** |客户端在写入后读取陈旧数据 |用户更新个人资料；刷新页面；旧数据仍显示 |
### 第三方集成失败
|失败|描述 |缓解措施 |
|--------|-------------|------------|
| **供应商 API 更改** |第三方更改其 API，恕不另行通知 |版本固定；抽象层；监控供应商变更日志|
| **速率限制** |第三方限制您的请求 |缓存；请求排队；谈判更高的限制|
| **供应商停机** |第三方服务不可用 |断路器；后备行为；多供应商战略|
| **数据格式更改** |第三方更改响应格式 |模式验证；转换层；格式更改警报 |
| **不带迁移路径的弃用** |供应商弃用没有等效项的端点 |随时了解情况；保持抽象；尽早计划迁移|

## 案例研究
### 案例研究 1：返回所有内容的 API
|方面|描述 |
|--------|-------------|
| **场景** |某SaaS公司的用户API返回所有用户字段，包括内部元数据 |
| **出了什么问题** |无字段过滤；响应包括密码哈希、内部注释和管理标志 |
| **影响** |安全研究人员发现了这一漏洞；公开披露； GDPR 调查 |
| **根本原因** | API序列化整个数据库模型，无需过滤 |
| **修复** |明确的响应模型；现场级访问控制；所有端点的安全审查|
| **课程** |切勿直接通过 API 公开您的数据库模型；使用DTO（数据传输对象）|
### 案例研究 2：级联故障
|方面|描述 |
|--------|-------------|
| **场景** |具有同步服务间通信的微服务架构 |
| **出了什么问题** |一项服务经历了数据库速度减慢；上游服务等待响应；线程池已耗尽|
| **影响** |系统完全停运45分钟；所有受影响的服务|
| **根本原因** |无断路器；没有超时；同步依赖链|
| **修复** |断路器；超时；尽可能进行异步通信；舱壁|
| **课程** |服务之间的同步调用会造成脆弱的链条；失败设计|

## 最佳实践
### API 设计清单
|面积 |实践|
|------|----------|
| **命名** |使用名词来表示资源；操作的 HTTP 方法；一致的命名约定|
| **版本控制** |从第一天开始的版本；使用 URL 版本控制 (`/v1/`) 或标头版本控制 |
| **分页** |始终对列表端点进行分页；对大型数据集使用基于游标的分页
| **错误处理** |一致的错误格式；包括错误代码；提供可操作的消息|
| **速率限制** |实施速率限制；返回 429 并带有 retry-after 标头 |
| **幂等性** |支持突变端点的幂等键 |
| **文档** | OpenAPI / Swagger 规范；保持更新；提供例子 |
| **测试** |合同测试；集成测试；消费者驱动的契约测试|
| **监控** |跟踪延迟；错误率；吞吐量；依赖性健康 |
| **弃用** |提前宣布弃用；提供迁移指南|
---

＃＃ 概括
API 设计失败的范围从表面性的（命名不一致）到灾难性的（安全漏洞、级联故障）。最常见的设计错误——端点过载、过度获取、缺少分页、模糊错误——使得 API 难以使用和维护。安全故障——身份验证失效、IDOR、大规模分配、过多的数据暴露——使系统容易受到攻击。集成故障——紧密耦合、同步链、缺少断路器、无幂等性——会创建脆弱的系统，其中一个故障会跨服务级联。第三方集成增加了外部风险：API 更改、速率限制和供应商停机。预防策略很完善：使用明确的反应模型；从第一天开始的版本；实施断路器和超时；幂等性设计；验证和清理所有输入；监控一切；并将 API 合同视为具有约束力的协议，需要协调才能更改。最好的 API 都是乏味的——可预测、一致、文档齐全且能够抵御故障。
