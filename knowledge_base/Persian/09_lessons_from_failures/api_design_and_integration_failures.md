# اشکالات طراحی و یکپارچه سازی API
API ها (رابط برنامه نویسی کاربردی) بافت همبند نرم افزار مدرن هستند - آنها به سرویس ها اجازه می دهند با هم ارتباط برقرار کنند، به اشخاص ثالث اجازه می دهند یکپارچه شوند و به تیم ها اجازه می دهند مستقل کار کنند. وقتی طراحی API اشتباه می‌شود، پیامدهای آن در هر سیستمی که به آن وابسته است موج می‌زند: ادغام‌های خراب، آسیب‌پذیری‌های امنیتی، ناامیدی توسعه‌دهندگان و بازنویسی‌های پرهزینه. خرابی های یکپارچه سازی - جایی که سیستم ها نمی توانند به طور قابل اعتماد ارتباط برقرار کنند - یکی از رایج ترین منابع حوادث تولید هستند.

## اشکالات رایج طراحی API
### اشتباهات طراحی
| اشتباه | توضیحات | نتیجه |
|---------|------------|-------------|
| **نامگذاری ناسازگار** | `/getUsers`در مقابل`/list_users`در مقابل`/fetch-users`| گیجی؛ خطاها؛ توسعه آهسته |
| **نقاط پایانی بیش از حد** | یک نقطه پایانی که 10 کار مختلف را بر اساس پارامترها انجام می دهد | درک سخت است؛ آزمایش سخت؛ تغییر سخت |
| **کم واکشی ** | برای دریافت اطلاعات مرتبط، مشتری باید 5 تماس API برقرار کند | آهسته؛ اسراف کننده؛ کد پیچیده مشتری |
| **بیش از حد واکشی** | API همه فیلدها را زمانی برمی‌گرداند که کلاینت فقط به 2 | نیاز داشته باشد پهنای باند تلف شده؛ کند در موبایل؛ خطر امنیتی ( افشای داده های غیر ضروری) |
| **بدون نسخه** | شکستن تغییرات بدون هشدار اجرا شد | مشتریان شکستن؛ توسعه دهندگان عصبانی |
| **پیام های خطای مبهم** | "خطای 500: خطای سرور داخلی" بدون جزئیات | اشکال زدایی غیرممکن است. وضوح کند |
| **صفحه بندی موجود نیست** | نقطه پایانی همه رکوردها را برمی گرداند (ممکن است میلیون ها باشد) | تایم اوت ها؛ خستگی حافظه؛ مشتریان خراب |
| **کدهای وضعیت ناسازگار** | 200 OK برای خطاها. 500 برای اشتباهات مشتری | مشتریان نمی توانند موفقیت را از شکست تشخیص دهند |
### REST API Anti-Patterns
| ضد الگو | توضیحات | رویکرد بهتر |
|-------------|-------------|-----------------|
| **استفاده از GET برای جهش** | `GET /delete-user?id=5`| استفاده از روش DELETE |
| **استفاده از POST برای همه چیز** |  `POST /get-users`؛ `POST /update-user`| استفاده از روش های مناسب HTTP (GET، POST، PUT، PATCH، DELETE) |
| **برگرداندن HTML از API** | API قطعات HTML | JSON را برگردانید. اجازه دهید مشتری رندر |
| **منطق کسب و کار در URL** |  __محافظت شده_3__ | استفاده از پارامترهای پرس و جو یا بدنه درخواست برای فیلترهای پیچیده |
| **نمایش طرح واره پایگاه داده** | `/api/table_name/column`| طراحی API حول منابع و مفاهیم دامنه، نه جداول |
| **بدون HATEOAS / پیوند ** | کلاینت همه URL ها را کدهای سخت می کند | در پاسخ ها پیوندهایی به منابع مرتبط وارد کنید |

## نقص های امنیتی
### آسیب پذیری های رایج API
| آسیب پذیری | توضیحات | مثال |
|--------------|------------|---------|
| ** احراز هویت خراب** | API به درستی هویت را تأیید نمی کند | اعتبار سنجی رمز وجود ندارد. توکن های منقضی پذیرفته شدند |
| ** قرار گرفتن در معرض داده های بیش از حد ** | API اطلاعات بیشتری نسبت به نیاز مشتری برمی گرداند | نقطه پایانی کاربر درهم‌سازی رمز عبور و شناسه‌های داخلی |
| **تکالیف دسته جمعی** | مشتری می تواند فیلدهایی را که نباید | `PATCH /user`امکان تنظیم`role: "admin"`|
| **تزریق** | ورودی کاربر به عنوان کد | تزریق SQL؛ تزریق NoSQL؛ تزریق فرمان |
| **IDOR** (مرجع شی مستقیم ناامن) | دسترسی به منابع با تغییر ID در URL | `/api/users/5`→ تغییر به`/api/users/6`برای دیدن داده های شخص دیگری |
| **محدود کردن نرخ وجود ندارد** | بدون محدودیت در تماس های API | نیروی بی رحم؛ انکار خدمات؛ سوهان زدن |
| **پیکربندی اشتباه CORS** | دسترسی بیش از حد مجاز | `Access-Control-Allow-Origin: *`در نقاط پایانی احراز هویت شده |
### خرابی های احراز هویت و مجوز
| شکست | توضیحات | تاثیر |
|---------|-------------|--------|
| **مدارک هاردکد** | کلیدهای API یا رمزهای عبور در کد منبع | از طریق کنترل نسخه به بیرون درز کرد. قابل دسترسی برای همه توسعه دهندگان |
| **بدون انقضای توکن** | توکن ها هرگز منقضی نمی شوند | توکن دزدیده شده دسترسی دائمی می دهد |
| **کلیدهای مخفی ضعیف** | کلیدهای امضای کوتاه یا قابل پیش بینی | توکن ها را می توان جعل کرد |
| **بدون دامنه / مجوز ** | همه توکن ها دسترسی کامل دارند | توکن در معرض خطر = دسترسی کامل به سیستم |
| ** ثبت اطلاعات حساس** | نشانه ها یا رمزهای عبور در گزارش ها | قابل دسترسی برای هر کسی با دسترسی به گزارش |
| **مجوز ناسازگار** | برخی از نقاط پایانی مجوزها را بررسی می کنند. دیگران نمی کنند | دسترسی غیرمجاز از طریق نقاط پایانی بدون محافظت |

## شکست های یکپارچه سازی
### مسائل یکپارچه سازی سیستم توزیع شده
| شکست | توضیحات | مثال |
|---------|-------------|---------|
| **کوپلینگ محکم** | خدمات به جزئیات پیاده سازی داخلی یکدیگر بستگی دارد | تغییر پایگاه داده یک سرویس، سه سرویس دیگر را خراب می کند |
| **زنجیره های سنکرون** | سرویس A با B تماس می گیرد C با D تماس می گیرد. تأخیر انباشته می شود | 200ms + 300ms + 500ms = زمان پاسخگویی 1 ثانیه |
| **بدون کلید مدار ** | خرابی سرویس باعث خرابی های آبشاری می شود | سرویس D کند است. همه سرویس های بالادست رشته های خود را در انتظار خسته می کنند |
| **بدون منطق امتحان مجدد** | خرابی های گذرا دائمی می شوند | شبکه blip = تراکنش ناموفق. کاربر باید دوباره به صورت دستی تلاش کند |
| **تکرارهای بیش از حد** | تلاش مجدد بدون عقب نشینی خدمات بازیابی را تحت تأثیر قرار می دهد | مشکل گله رعد و برق |
| **بی ناتوانی** | تلاش مجدد یک عملیات غیر توانمند، تکراری ایجاد می کند | پرداخت دو بار شارژ می شود. سفارش دو بار ایجاد شد |
| **سوپرایز سازگاری نهایی** | کلاینت داده های قدیمی را بعد از نوشتن | می خواند پروفایل به روز رسانی کاربر. تازه کردن صفحه؛ داده های قدیمی هنوز نشان داده شده است |
### شکست های یکپارچه سازی شخص ثالث
| شکست | توضیحات | کاهش |
|---------|-------------|------------|
| **تغییر API فروشنده** | شخص ثالث API خود را بدون اطلاع قبلی تغییر می دهد | پین کردن نسخه؛ لایه انتزاعی؛ نظارت بر تغییرات فروشنده |
| **محدودیت نرخ** | شخص ثالث درخواست های شما را کاهش می دهد | ذخیره سازی؛ صف درخواست؛ مذاکره در مورد محدودیت های بالاتر |
| **زمان توقف فروشنده** | سرویس شخص ثالث در دسترس نیست | کلیدهای مدار؛ رفتار برگشتی؛ استراتژی چند فروشنده |
| **تغییر فرمت داده** | تغییر قالب پاسخ توسط شخص ثالث | اعتبار سنجی طرحواره؛ لایه تبدیل؛ هشدار در مورد تغییرات قالب |
| **منسوخ شدن بدون مسیر مهاجرت** | فروشنده نقطه پایانی را بدون معادل | منسوخ می کند مطلع باشید؛ حفظ انتزاع؛ برنامه ریزی زودهنگام مهاجرت |

| **چه اشتباهی شد** | بدون فیلتر میدانی؛ پاسخ شامل درهم‌سازی رمز عبور، یادداشت‌های داخلی و پرچم‌های مدیریت |

| **علت ریشه ای** | API کل مدل پایگاه داده را بدون فیلتر |. سریال کرد
| **رفع ** | مدل‌های پاسخ صریح؛ کنترل دسترسی در سطح میدانی؛ بررسی امنیتی تمام نقاط پایانی |
| **درس** | هرگز مدل پایگاه داده خود را مستقیماً از طریق API در معرض دید قرار ندهید. استفاده از DTOs (Data Transfer Objects) |

| جنبه | توضیحات |
|--------|------------|
| **سناریو** | معماری میکروسرویس با ارتباطات بین سرویسی همزمان |
| **چه اشتباهی شد** | یک سرویس کاهش سرعت پایگاه داده را تجربه کرد. خدمات بالادستی منتظر پاسخ بودند. استخرهای نخ تمام شده |
| **تاثیر** | قطع کامل سیستم به مدت 45 دقیقه؛ همه خدمات تحت تاثیر |
| **علت ریشه ای** | بدون قطع کننده مدار؛ بدون تایم اوت؛ زنجیره وابستگی همزمان |
| **رفع ** | کلیدهای مدار؛ تایم اوت ها؛ ارتباط ناهمگام در صورت امکان؛ بالک |
| **درس** | تماس های همزمان بین سرویس ها زنجیره های شکننده ایجاد می کند. طراحی برای شکست |

## بهترین شیوه ها
### چک لیست طراحی API
| منطقه | تمرین |
|------|----------|
| **نامگذاری** | استفاده از اسامی برای منابع؛ روش های HTTP برای اقدامات. کنوانسیون نامگذاری سازگار |
| **نسخه** | نسخه از روز اول؛ از نسخه‌سازی URL (`/v1/`) یا نسخه‌سازی سرصفحه |
| **صفحه بندی** | همیشه نقاط پایانی لیست را صفحه بندی کنید. استفاده از صفحه بندی مبتنی بر مکان نما برای مجموعه داده های بزرگ |
| ** رسیدگی به خطا** | فرمت خطای ثابت؛ شامل کدهای خطا ارائه پیام های قابل اجرا |
| **محدودیت نرخ** | اجرای محدودیت های نرخ؛ برگرداندن 429 با سرصفحه rery-after |
| **بی توانی** | پشتیبانی از کلیدهای ناتوانی برای نقاط پایانی جهش |
| **مستندات** | مشخصات OpenAPI / Swagger. آن را به روز نگه دارید؛ ارائه مثال |
| **تست** | تست های قرارداد؛ تست های ادغام؛ تست های قرارداد مبتنی بر مصرف کننده |
| **نظارت** | تأخیر پیگیری؛ نرخ خطا؛ توان عملیاتی؛ سلامت وابستگی |
| **منسوخ شدن** | منسوخ شدن ها را از قبل اعلام کنید. ارائه راهنماهای مهاجرت |

## خلاصه
خرابی‌های طراحی API از زیبایی (نام‌گذاری ناسازگار) تا فاجعه‌بار (آسیب‌پذیری‌های امنیتی، خرابی‌های آبشاری) متغیر است. رایج ترین اشتباهات طراحی - نقاط پایانی بیش از حد، واکشی بیش از حد، صفحه بندی از دست رفته، خطاهای مبهم - استفاده و نگهداری از API ها را سخت می کند. خرابی های امنیتی - احراز هویت شکسته، IDOR، تخصیص انبوه، قرار گرفتن در معرض بیش از حد داده ها - سیستم ها را در معرض حمله قرار می دهد. خرابی‌های یکپارچه‌سازی - کوپلینگ محکم، زنجیره‌های همزمان، قطع‌کننده‌های مدار از دست رفته، بدون ضعف - سیستم‌های شکننده‌ای را ایجاد می‌کنند که در آن یک شکست در سراسر سرویس‌ها موج می‌زند. ادغام های شخص ثالث خطر خارجی را اضافه می کند: تغییرات API، محدود کردن نرخ، و خرابی فروشنده. استراتژی های پیشگیری به خوبی تثبیت شده اند: از مدل های پاسخ صریح استفاده کنید. نسخه از روز اول؛ اجرای قطع کننده مدار و وقفه های زمانی. طراحی برای ناتوانی؛ اعتبارسنجی و ضدعفونی کردن تمام ورودی ها؛ نظارت بر همه چیز؛ و قراردادهای API را به عنوان توافق نامه های الزام آور تلقی کنید که برای تغییر نیاز به هماهنگی دارند. بهترین APIها کسل کننده هستند – قابل پیش بینی، سازگار، به خوبی مستند شده و در برابر شکست مقاوم هستند.
