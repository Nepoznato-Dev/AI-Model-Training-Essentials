# مبانی امنیت سایبری
امنیت ویژگی‌ای نیست که در انتها به آن بچسبید - این یک رشته است که باید از همان روز اول در هر لایه‌ای از سیستم بافته شود. چه در حال ساخت یک برنامه وب، مدیریت زیرساخت یا ارسال یک API باشید، درک چشم انداز تهدید و اصول اساسی دفاع ضروری است.
---

## رمزگذاری و رمزنگاری
### رمزگذاری متقارن در مقابل نامتقارن
| نوع | چگونه کار می کند | سرعت | توزیع کلید | مثال ها |
|------|-------------|------|----------------|----------|
| **متقارن** | کلید یکسان برای رمزگذاری و رمزگشایی | سریع | چالش: چگونه کلید را به اشتراک بگذاریم؟ | AES-256، ChaCha20 |
| **نامتقارن** | رمزگذاری کلید عمومی، رمزگشایی کلید خصوصی | کندتر | کلید عمومی را می توان به صورت باز به اشتراک گذاشت | RSA، ECC (منحنی بیضوی) |
در عمل، اکثر سیستم‌ها از **هردو** استفاده می‌کنند: رمزگذاری نامتقارن برای تبادل امن یک کلید متقارن، سپس رمزگذاری متقارن برای بخش عمده داده‌ها. TLS/HTTPS اینگونه کار می کند.
### هش کردن
هش کردن یک تابع یک طرفه است: ورودی را به یک رشته با اندازه ثابت تبدیل می کند. شما نمی توانید آن را معکوس کنید، اما همان ورودی همیشه همان خروجی را تولید می کند.
| مورد استفاده | الگوریتم پیشنهادی | اجتناب |
|----------|---------------------|-------|
| **ذخیره رمز** | Argon2id، bcrypt، scrypt | MD5، SHA-1، SHA-256 ساده (خیلی سریع) |
| **یکپارچگی داده** | SHA-256، SHA-3 | MD5 (شکسته)، SHA-1 (شکسته) |
| **امضای دیجیتال** | Ed25519, RSA-2048+ | DSA |
### TLS/HTTPS
HTTPS HTTP بیش از TLS (امنیت لایه حمل و نقل) است. فراهم می کند:
- **رمزگذاری**: داده های در حال انتقال توسط استراق سمع ها قابل خواندن نیستند.
- **Authentication**: سرور هویت خود را از طریق گواهی اثبات می کند.
- **یکپارچگی**: داده ها را نمی توان در حین انتقال بدون شناسایی تغییر داد.
از TLS 1.2 یا 1.3 استفاده کنید. TLS 1.0 و 1.1 را غیرفعال کنید. HSTS (امنیت حمل و نقل سخت HTTP) را فعال کنید تا مرورگرها را مجبور کند همیشه از HTTPS استفاده کنند.

## احراز هویت و مجوز
### احراز هویت: شما کی هستید؟
| روش | سطح امنیتی | مورد استفاده |
|--------|--------------|----------|
| **رمز عبور** | کم-متوسط ​​| حساب های اصلی (اجرای بیش از 12 کاراکتر، بررسی تخلفات) |
| **MFA (TOTP)** | بالا | استاندارد برای حساب های حساس (Google Authenticator، Authy) |
| **کلید سخت افزاری (FIDO2/WebAuthn)** | خیلی بالا | حساب های با امنیت بالا (YubiKey) |
| **بیومتریک** | متوسط-بالا | باز کردن قفل دستگاه (اثر انگشت، چهره) - به عنوان تنها عامل عالی نیست |
| **OAuth2 / OIDC** | بالا | ورود شخص ثالث ("ورود با Google") |
**قوانین رمز عبور**: حداقل طول (12 تا 16 کاراکتر) را اعمال کنید، لیست های رمز عبور نقض شده را بررسی کنید، از Argon2id یا bcrypt برای هش کردن با نمک های هر کاربر استفاده کنید.
### مجوز: چه کاری می توانید انجام دهید؟
| مدل | توضیحات | مثال |
|-------|-------------|---------|
| **RBAC** (کنترل دسترسی مبتنی بر نقش) | مجوزهای اختصاص داده شده به نقش ها؛ کاربران نقش دریافت می کنند | مدیر، ویرایشگر، نمایشگر |
| **ABAC** (مبتنی بر ویژگی) | قوانین مبتنی بر ویژگی های کاربر، منبع، محیط | "مدیران می توانند درخواست های تیم خود را تایید کنند" |
| **ACL** (فهرست کنترل دسترسی) | مجوزهای صریح برای هر کاربر/منبع | مجوزهای فایل (خواندن/نوشتن/اجرا) |
**اصل کمترین امتیاز**: به هر کاربر، سرویس و پردازشی فقط حداقل دسترسی لازم را بدهید.
### JWT (JSON Web Tokens)
| جنبه | توصیه |
|--------|---------------|
| **امضا** | RS256 یا ES256 (نامتقارن) ترجیح داده می شود. HS256 قابل قبول با اسرار مدیریت شده |
| **انقضا** | 15 تا 60 دقیقه برای توکن های دسترسی؛ استفاده از نشانه های رفرش برای جلسات طولانی تر |
| **ذخیره** | کوکی‌های فقط HTTP (نه محلی ذخیره‌سازی - آسیب‌پذیر در برابر XSS) |
| ** اعتبار سنجی ** | همیشه امضا، صادرکننده، مخاطب و انقضا را تأیید کنید |

## شیوه های کدنویسی ایمن
### اعتبار سنجی ورودی
| قانون | چرا |
|------|-----|
| **لیست سفید > لیست سیاه** | تعریف کنید چه چیزی مجاز است، نه آنچه مسدود شده است |
| **پرسش های پارامتری شده** | هرگز ورودی کاربر را به SQL الحاق نکنید — از عبارات آماده شده یا ORM | استفاده کنید
| **رمزگذاری HTML** | برای جلوگیری از XSS، `<`، `>`، `&`، `"`،`'`را رمزگذاری کنید |
| **پوسته فرار** | اجتناب از ساخت دستورات پوسته از ورودی کاربر. استفاده از`shlex.quote()`|
| **محدودیت طول ** | برای جلوگیری از سرریز شدن بافر و DoS | حداکثر طول ها را اعمال کنید
| **بررسی تایپ** | اطمینان حاصل کنید که اعداد صحیح اعداد صحیح هستند، بولی ها بولی هستند |
### آسیب پذیری های رایج
| آسیب پذیری | حمله | دفاع |
|--------------|--------|---------|
| **تزریق SQL** | `' OR 1=1 --`در فرم ورود | پرس و جوهای پارامتری شده |
| **XSS** | `<script>alert('hacked')</script>`در قسمت نظر | کدگذاری خروجی، سیاست امنیتی محتوا |
| **CSRF** | فریب مرورگر کاربر برای درخواست غیرمجاز | توکن های CSRF، کوکی های SameSite |
| **پیمایش مسیر** | `../../etc/passwd`در پارامتر فایل | اعتبارسنجی و پاکسازی مسیرهای فایل |
| **ایدور** |`/user/123`را به`/user/124`تغییر دهید تا داده های شخص دیگری را ببینید | بررسی مجوز در هر درخواست |

## امنیت شبکه
### فایروال ها
| نوع | توضیحات |
|------|-------------|
| **پکت-فیلتر کردن** | قوانین مبتنی بر IP، پورت، پروتکل |
| **دولتی** | وضعیت های اتصال را ردیابی می کند. فیلترینگ هوشمندتر |
| **سطح برنامه (WAF)** | ترافیک HTTP را بررسی می کند. بلوک های تزریق SQL، XSS، و غیره |
| **گروه های امنیت ابری** | فایروال های مجازی برای نمونه های ابری (AWS SGs، Azure NSGs) |
**قاعده سرانگشتی**: به طور پیش فرض تمام ترافیک ورودی را مسدود کنید. فقط آنچه را که به صراحت مورد نیاز است باز کنید (80، 443 برای وب).
### تقسیم بندی شبکه
پایگاه داده ها و کش ها را در زیرشبکه های خصوصی بدون دسترسی مستقیم به اینترنت قرار دهید. از DMZ برای خدمات عمومی (سرورهای وب، متعادل کننده بار) استفاده کنید. اصل حداقل امتیاز را برای دسترسی به شبکه اعمال کنید.

## مدیریت اسرار
### قانون طلایی
**هرگز اسرار هاردکد را وارد نکنید.** کلیدهای API، گذرواژه ها، یا URL های پایگاه داده در کد منبع وجود ندارد. هیچ رازی در متغیرهای محیطی متعهد به Git وجود ندارد. هیچ رازی در تصاویر داکر وجود ندارد.
### ابزار
| ابزار | نوع | بهترین برای |
|------|------|----------|
| **HashiCorp Vault** | مدیر اسرار سازمانی | اسرار پویا، رمزگذاری به عنوان یک سرویس |
| **AWS Secrets Manager** | Cloud-Native | محیط های AWS |
| **خزانه کلید لاجوردی** | Cloud-Native | محیط های لاجوردی |
| **SOPS** | فایل های رمزگذاری شده | رمزگذاری اسرار در Git (با KMS یا GPG) |
| **اسرار داکر** | کانتینر بومی | Docker Swarm (برای K8s، Secrets Store CSI را در نظر بگیرید) |
| **dotenv (.env)** | توسعه محلی | فقط توسعه — هرگز در تولید یا متعهد |
### چرخش
اسرار را به طور منظم و خودکار بچرخانید. اگر رازی فاش شد (مثلاً به یک مخزن عمومی متعهد شد)، فوراً آن را بچرخانید - حتی اگر فکر می کنید کسی آن را ندیده است.

| زبان | ابزار |
|----------|-------|
| **پایتون** |  `safety`، `pip-audit`،`bandit`|
| **Node.js** |  `npm audit`، `yarn audit`،`snyk`|
| **زنگ** |  __محافظت شده_6__ |

- بررسی وابستگی های دانلود شده را بررسی کنید.
- ثبت رسمی و ناشران تأیید شده را ترجیح دهید.
- به‌روزرسانی‌های جزئی/پچ را از طریق Dependabot یا Renovate خودکار کنید.

## چرخه عمر توسعه امنیت (SDL)
| فاز | فعالیت |
|-------|----------|
| **آموزش** | اطمینان حاصل کنید که توسعه دهندگان آسیب پذیری های رایج را درک می کنند |
| **مدل سازی تهدید** | شناسایی تهدیدات احتمالی در طول طراحی |
| **استانداردهای کدگذاری امن** | اعمال از طریق لینترها و چک لیست های بازبینی کد |
| **SAST** | تجزیه و تحلیل استاتیک کد منبع (SonarQube، CodeQL) |
| **DAST** | تجزیه و تحلیل پویا برنامه در حال اجرا (OWASP ZAP، Burp Suite) |
| **SCA** | تجزیه و تحلیل ترکیب نرم افزار — اسکن وابستگی ها |
| **تست نفوذ** | تمرینات منظم هک اخلاقی |
| **باگ باونتی** | تشویق محققان خارجی برای یافتن آسیب‌پذیری‌ها |
| **طرح واکنش به حوادث** | یک برنامه روشن برای زمانی که یک نقض شناسایی می شود داشته باشید |

## چک لیست اضطراری
وقتی مشکوک به نقض هستید:
1. **نترسید** - اما سریع عمل کنید.
2. **ایزوله** سیستم های آسیب دیده (در صورت نیاز از شبکه جدا شوید).
3. **حفظ شواهد**: ضبط سیاهههای مربوط، تخلیه حافظه، تصاویر دیسک.
4. **محدوده را شناسایی کنید**: کدام سیستم ها، کدام داده ها؟
5. ** چرخش ** همه اعتبارنامه ها و اسرار به خطر افتاده.
6. **وصله** آسیب پذیری.
7. **به کاربران و رگولاتورهای متاثر در صورت لزوم **اطلاع دهید (در چارچوب زمانی قانونی).
8. **پس از مرگ**: علت اصلی و موارد اقدام را ظرف 24 تا 48 ساعت مستند کنید.
