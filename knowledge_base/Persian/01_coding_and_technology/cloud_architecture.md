# معماری ابر
رایانش ابری نحوه ساخت، استقرار و مقیاس‌بندی نرم‌افزار را به طور اساسی تغییر داده است. به جای خرید و نگهداری سرورهای فیزیکی، می‌توانید منابع محاسباتی را در صورت تقاضا تهیه کنید، برای آنچه استفاده می‌کنید بپردازید و در عرض چند دقیقه مقیاس جهانی را انجام دهید. این فایل مفاهیم اصلی، الگوهای معماری، خدمات و بهترین شیوه هایی را که باید بدانید را پوشش می دهد.
---

## مبانی محاسبات ابری
### رایانش ابری چیست؟
تحویل بر اساس تقاضای منابع محاسباتی - سرورها، ذخیره‌سازی، پایگاه‌های اطلاعاتی، شبکه‌ها، نرم‌افزارها - از طریق اینترنت با قیمت‌های پرداختی.
### ویژگی های ضروری NIST
| مشخصه | معنی |
|---------------|---------|
| **سلف سرویس درخواستی** | تامین منابع بدون تعامل انسانی |
| **دسترسی به شبکه گسترده** | در شبکه از طریق مکانیسم های استاندارد موجود است |
| **تجمیع منابع** | مدل چند مستاجر؛ منابع به صورت پویا اختصاص داده شده |
| **کشسانی سریع** | به سرعت به سمت بیرون و داخل مقیاس کنید |
| **سرویس اندازه گیری شده** | استفاده نظارت و صورتحساب می شود |
### مدل های استقرار
| مدل | توضیحات | زمان استفاده |
|-------|------------|-------------|
| **ابر عمومی** | متعلق به ارائه دهندگان؛ زیرساخت مشترک (AWS، Azure، GCP) | بیشترین حجم کار؛ مقرون به صرفه |
| **ابر خصوصی** | تقدیم به یک سازمان | الزامات قانونی، داده های حساس |
| **ابر هیبریدی** | ترکیب عمومی و خصوصی | انعطاف پذیری + انطباق |
| **چند ابری** | استفاده از چندین ارائه دهنده ابر عمومی | اجتناب از قفل فروشنده، بهترین نژاد |
### مدل های خدمات
| مدل | ارائه می دهد | مثال ها | موارد استفاده |
|-------|---------|----------|-----------|
| **IaaS** | ماشین های مجازی، ذخیره سازی، شبکه ها، سیستم عامل | AWS EC2، Azure VMs، GCP Compute Engine | جابجایی های لیفت و جابجایی، کنترل کامل |
| **PaaS** | پلتفرم های توسعه، پایگاه های داده، میان افزار | Heroku، Google App Engine، AWS Elastic Beanstalk | توسعه برنامه، استقرار API |
| **SaaS** | برنامه های کامل از طریق اینترنت | Salesforce، Google Workspace، Microsoft 365 | ایمیل، CRM، همکاری |
| ** FaaS / بدون سرور ** | اجرای تابع رویداد محور | AWS Lambda، Azure Functions، GCP Cloud Functions | API ها، پردازش رویداد، وظایف برنامه ریزی شده |

## الگوهای معماری
### چارچوب خوش معماری
هر سه ارائه‌دهنده اصلی چارچوب‌هایی با معماری خوب منتشر می‌کنند که حول پنج ستون ساخته شده‌اند:
| ستون | اصول کلیدی |
|--------|---------------|
| **تعالی عملیاتی** | خودکار کردن عملیات؛ ایجاد تغییرات مکرر و برگشت پذیر؛ پیش بینی شکست |
| **امنیتی** | پایه هویتی قوی؛ اعمال امنیت در هر لایه؛ حفاظت از داده ها در حال حمل و نقل و در حالت استراحت |
| **قابلیت اطمینان** | روش های بازیابی تست؛ بازیابی خودکار از شکست؛ مقیاس افقی |
| **کارایی عملکرد** | استفاده از سرور بدون سرور؛ جهانی شدن در عرض چند دقیقه آزمایش اغلب |
| **بهینه سازی هزینه** | اتخاذ مدل مصرف؛ استفاده از خدمات مدیریت شده؛ متوقف کردن هزینه برای کارهای غیرمتمایز |
### الگوهای رایج
| الگو | توضیحات | مزایا | چالش ها |
|---------|------------|---------|------------|
| **میکروسرویس** | تجزیه برنامه به سرویس های کوچک و مستقل | مقیاس پذیری، جداسازی خطا، استقرار مستقل | پیچیدگی توزیع شده، سازگاری داده ها |
| **رویداد محور** | کامپوننت ها از طریق رویدادها ارتباط برقرار می کنند | کوپلینگ شل، پردازش بلادرنگ | پیچیدگی اشکال زدایی، ثبات نهایی |
| **بدون سرور** | بدون مدیریت سرور؛ پرداخت به ازای هر اجرا | راندمان هزینه، استقرار سریع | شروع سرد، قفل فروشنده، محدودیت های اجرا |
| **لایه (N-Tier)** | ارائه → منطق تجاری → دسترسی به داده ها → پایگاه داده | جداسازی نگرانی ها، قابلیت نگهداری | می تواند یکپارچه شود |
| **فضا محور** | داده های توزیع شده در گره های حافظه مجازی شده | کنترل همزمانی بالا، تاخیر کم | مجتمع برای طراحی و مدیریت |

## خدمات اصلی
### محاسبه کنید
| نوع خدمات | جزئیات |
|-------------|---------|
| **ماشین های مجازی** | هدف کلی، محاسباتی بهینه، حافظه بهینه، GPU. قیمت: در صورت تقاضا، رزرو شده، نقطه ای. |
| **ظروف** | زمان اجرا Docker; ارکستراسیون از طریق Kubernetes (EKS، AKS، GKE). ثبت: ECR، GCR، ACR. |
| **توابع بدون سرور** | رخدادی، بی حالت. محدودیت در زمان اجرا، حافظه، همزمانی. |
### ذخیره سازی
| نوع | مشخصات | مثال ها | بهترین برای |
|------|----------------|---------|----------|
| **شی ** | ساختار مسطح، دسترسی HTTP، غنی از ابرداده | S3، Cloud Storage، Azure Blob | دارایی های ثابت، پشتیبان گیری، دریاچه های داده |
| **بلاک** | حجم های خام متصل به VM | EBS، دیسک ماندگار، دیسک های Azure | پایگاه های داده، حجم بوت |
| **فایل** | سیستم های فایل مشترک (NFS/SMB) | EFS، Filestore، فایل های Azure | مدیریت محتوا، تنظیمات مشترک |
| **بایگانی** | کمترین هزینه، تاخیر در بازیابی | S3 Glacier, Azure Archive | انطباق، پشتیبان گیری طولانی مدت |
### پایگاه های داده
| دسته بندی | خدمات | مورد استفاده |
|----------|----------|----------|
| **مدیریت رابطه ای** | RDS، Cloud SQL، Azure SQL | برنامه های سنتی، تراکنش های ACID |
| **NoSQL — سند** | DocumentDB، Firestore، Cosmos DB | طرحواره های انعطاف پذیر، داده های JSON |
| **NoSQL — Key-Value** | DynamoDB، Redis Cache | ذخیره سازی، جلسات، جستجوهای ساده |
| **NoSQL — Wide-Column** | Bigtable، کاساندرا | نوشتن سنگین، سری زمانی |
| **NoSQL — نمودار** | Neptune, Cosmos DB (Graph API) | روابط، شبکه های اجتماعی |
| **ذخیره اطلاعات** | Snowflake، Redshift، BigQuery، Synapse | تجزیه و تحلیل، BI |
| **در حافظه پنهان** | ElastiCache، Cloud Memorystore | ذخیره سازی جلسه، ذخیره پرس و جو |

## شبکه
### شبکه های مجازی
هر استقرار ابری در داخل یک ابر خصوصی مجازی (VPC / VNet) زندگی می‌کند - یک شبکه ایزوله که شما با بلوک‌های CIDR، زیرشبکه‌ها (عمومی یا خصوصی)، جدول‌های مسیر و دروازه‌ها تعریف می‌کنید.
### Load Balancing و CDN
| خدمات | هدف |
|---------|---------|
| **لود متعادل کننده** | توزیع ترافیک در بین نمونه ها (شبکه L4، برنامه L7) |
| **CDN** | محتوای کش در مکان های لبه برای تأخیر کمتر (CloudFront، Cloud CDN، Azure CDN) |
| **DNS** | ثبت دامنه، سیاست‌های مسیریابی، بررسی سلامت (Route 53، Cloud DNS، Azure DNS) |
### گزینه های اتصال
| گزینه | توضیحات |
|--------|------------|
| **درگاه اینترنت** | دسترسی به اینترنت عمومی برای VPC |
| **درگاه NAT** | دسترسی خروجی زیرشبکه خصوصی |
| **VPN** | تونل های رمزگذاری شده به داخل محل |
| **Direct Connect / ExpressRoute** | اتصالات خصوصی اختصاصی |
| **VPC Peering** | VPC ها را در داخل یا بین حساب ها متصل کنید |

## امنیت
### مدل مسئولیت مشترک
| لایه | ارائه دهنده | مشتری |
|-------|----------|----------|
| **زیرساخت** (سخت افزار، امکانات) | ✅ | |
| **محاسبات، ذخیره سازی، شبکه** | ✅ (مدیریت شده) | ✅ (خود مدیریتی) |
| **داده ها، برنامه ها، هویت ** | | ✅ |
هر چه سرویس مدیریت بیشتری داشته باشد، ارائه دهنده بیشتر مدیریت می کند. با IaaS تقریباً همه چیز را مدیریت می کنید. با SaaS، ارائه دهنده تقریباً همه آن را مدیریت می کند.
### مدیریت هویت و دسترسی (IAM)
| مفهوم | توضیحات |
|---------|-------------|
| **کاربران** | هویت های فردی |
| **گروه** | مجموعه کاربران |
| **نقش** | اعتبار موقت خدمات یا کاربران |
| **سیاست ها** | اسناد تعریف کننده مجوز |
| **اصل** | کمترین امتیاز، تفکیک وظایف |
### حفاظت از داده ها
- **رمزگذاری در حالت استراحت**: KMS، کلیدهای مدیریت شده توسط مشتری، HSM.
- **رمزگذاری در حین حمل**: TLS/SSL، HTTPS.
- ** مدیریت اسرار **: مدیر اسرار، خزانه کلید - اسرار کد سخت هرگز.

## مدیریت هزینه
### مدل های قیمت گذاری
| مدل | توضیحات | بهترین برای |
|-------|------------|----------|
| **در صورت تقاضا** | برای چیزی که استفاده می کنید، در ثانیه/ساعت پرداخت کنید | حجم کاری متغیر و کوتاه مدت |
| **نمونه های رزرو شده** | تعهد 1 تا 3 ساله، تخفیف قابل توجه | بارهای کاری حالت ثابت |
| **نمونه های نقطه ای** | پیشنهاد ظرفیت استفاده نشده؛ می تواند قطع شود | مشاغل انعطاف پذیر و مقاوم در برابر خطا |
| **طرح های پس انداز** | قیمت گذاری تعهد انعطاف پذیر | الگوهای استفاده ترکیبی |
| **سطح رایگان** | استفاده رایگان محدود برای حساب های جدید | آموزش، نمونه سازی |
### استراتژی های بهینه سازی
نمونه هایی با اندازه مناسب برای مطابقت با حجم کاری. از مقیاس خودکار برای مدیریت افزایش تقاضا استفاده کنید. ظرفیت ذخیره برای بارهای قابل پیش بینی از نمونه های نقطه ای برای کارهای دسته ای استفاده کنید. داده‌هایی را که به‌ندرت به آن‌ها دسترسی پیدا می‌کنید به لایه‌های ذخیره‌سازی ارزان‌تر منتقل کنید. منابع استفاده نشده را حذف کنید (عکس های فوری یتیم، متعادل کننده های بار بیکار، IP های غیر متصل).

## در دسترس بودن بالا و بازیابی فاجعه
### مفاهیم در دسترس بودن
| مفهوم | توضیحات |
|---------|-------------|
| **منطقه در دسترس (AZ)** | مراکز داده از لحاظ فیزیکی در یک منطقه |
| **منطقه** | منطقه جغرافیایی با چندین AZ |
| **محل لبه** | مکان کش CDN برای تحویل محتوا |
### استراتژی های بازیابی فاجعه
| استراتژی | هزینه | RTO | RPO | توضیحات |
|----------|------|----|-----|-------------|
| **پشتیبان گیری و بازیابی** | کمترین | ساعت | ساعت-روز | پشتیبان گیری دوره ای، بازیابی در صورت نیاز |
| **چراغ خلبان** | کم | دقیقه-ساعت | دقیقه | عناصر اصلی همیشه در حال اجرا هستند، در صورت فاجعه بزرگ می شوند |
| **استندبای گرم** | متوسط ​​| دقیقه | ثانیه–دقیقه | نسخه کوچک شده همیشه در حال اجرا |
| **چند سایت فعال/فعال** | بالاترین | نزدیک به صفر | صفر | تولید کامل در مناطق متعدد |
**RTO** (Recovery Time Objective) = حداکثر زمان خرابی قابل قبول. **RPO** (Recovery Point Objective) = حداکثر از دست دادن داده قابل قبول.
