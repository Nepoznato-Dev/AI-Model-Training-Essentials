# بهینه سازی عملکرد
بهینه‌سازی عملکرد، عمل سریع‌تر کردن نرم‌افزار است - کاهش زمان پاسخ، افزایش توان عملیاتی، کاهش استفاده از حافظه و حذف تنگناها. این یکی از تاثیرگذارترین مهارت هایی است که یک توسعه دهنده می تواند داشته باشد، زیرا نرم افزار کند کاربران را از دست می دهد، منابع را هدر می دهد و همه را ناامید می کند. اما همچنین یکی از رایج‌ترین اشتباهات است که توسعه‌دهندگان به جای شواهد، چیزهای اشتباه را بر اساس شهود بهینه می‌کنند.
---

## قانون طلایی
> **اول اندازه گیری کنید، دوم بهینه سازی کنید.** هرگز بر اساس فرضیات بهینه سازی نکنید. کد را نمایه کنید، گلوگاه واقعی را پیدا کنید و آن را برطرف کنید.
| ضد الگو | چرا بد است |
|-------------|-------------|
| **بهینه سازی زودرس ** | صرف زمان برای افزایش سرعت کدهایی که کند نیست |
| **بهینه سازی بدون اندازه گیری** | رفع گلوگاه اشتباه؛ هیچ راهی برای تأیید بهبود وجود ندارد |
| **فدا کردن خوانایی برای سرعت** | هزینه کد ناخوانا بیشتر از افزایش عملکرد |
| **در حافظه پنهان همه چیز** | داده های قدیمی، نفخ حافظه، پیچیدگی |

## پروفایل
قبل از اینکه بتوانید چیزی را سریعتر بسازید، باید بدانید *کجا* زمان صرف شده است.
| نوع ابزار | آنچه را اندازه گیری می کند | مثال ها |
|-----------|----------------|----------|
| **پروفیلر CPU** | کدام توابع بیشترین زمان CPU را مصرف می کنند | cProfile (Python)، perf (Linux)، Chrome DevTools (JS) |
| **پروفیلر حافظه** | تخصیص حافظه و نشت | tracemalloc (Python)، Valgrind، Heaptrack |
| **پروفیلر ورودی/خروجی** | تنگناهای ورودی/خروجی دیسک و شبکه | iotop، strace، Wireshark |
| **APM (Application Performance Monitoring)** | زمان بندی درخواست پایان به انتها | New Relic, Datadog, Jaeger |
| **Browser DevTools** | رندر فرانت اند، اجرای جاوا اسکریپت، شبکه | Chrome DevTools, Firefox Profiler |
### گردش کار پروفایل
| مرحله | توضیحات |
|------|-------------|
| 1. شناسایی عملیات کند | کاربران بارگذاری کند صفحه را گزارش می دهند. نظارت نشان می دهد تاخیر بالا |
| 2. مشخصات مسیر کامل | پیدا کنید کدام مؤلفه بیشتر زمان می برد |
| 3. دریل کردن | برای یافتن تابع داغ | آن جزء خاص را نمایه کنید
| 4. رفع تنگنا | اعمال بهینه سازی مناسب |
| 5. دوباره اندازه گیری کنید | بررسی بهبود؛ بررسی رگرسیون |

## بهینه سازی الگوریتمی
بزرگترین دستاوردهای عملکرد از انتخاب الگوریتم های بهتر حاصل می شود، نه از بهینه سازی های خرد.
| تغییر | بهبود |
|--------|------------|
| جستجوی خطی O(n) → جستجوی جدول هش O(1) | 100x+ برای مجموعه داده های بزرگ |
| حلقه تودرتو O(n²) → مرتب سازی + جستجوی دودویی O(n log n) | ترتیب قدر برای n بزرگ |
| محاسبات مکرر → ذخیره سازی / ذخیره سازی | حذف کارهای زائد |
| الحاق رشته در یک حلقه → سازنده / پیوستن | اجتناب از کپی رشته درجه دوم |
| داده های مرتب نشده → داده های مرتب شده با جستجوی باینری | O(log n) به جای O(n) در هر جستجو |

## استراتژی های ذخیره سازی
ذخیره سازی نتایج محاسبه شده را ذخیره می کند تا نیازی به محاسبه مجدد نباشد.
| نوع کش | مکان | سرعت | طول عمر |
|-----------|----------|-------|----------|
| **کش CPU** | L1/L2/L3 | ~1 ns | اتوماتیک |
| **در حافظه** | رم برنامه (dict, HashMap) | ~100 ns | تا پاکسازی یا اخراج |
| **کش توزیع شده** | Redis، Memcached | ~1 میلی ثانیه | TTL قابل تنظیم |
| **CDN** | سرورهای لبه در سراسر جهان | ~10-50 میلی ثانیه | TTL قابل تنظیم |
| **کش مرورگر** | مرورگر کاربر | ~1 میلی ثانیه | هدرهای کش HTTP |
| **کش پرس و جو پایگاه داده** | سطح پایگاه داده یا ORM | ~1-10 میلی ثانیه | تا زمانی که داده ها تغییر کند |
### الگوهای ذخیره سازی
| الگو | توضیحات | زمان استفاده |
|---------|------------|-------------|
| **حافظه پنهان** | برنامه حافظه پنهان را بررسی می کند. بارگیری از DB در زمان از دست دادن. فروشگاه در حافظه پنهان | رایج ترین؛ ساده |
| **نوشتن از طریق** | نوشتن در حافظه پنهان و DB به طور همزمان | وقتی می خواند >> می نویسد; ثبات مهم |
| **پشت بنویس** | نوشتن در حافظه پنهان؛ به صورت ناهمزمان در DB بنویسید | توان نوشتن بالا؛ برخی از خطرات از دست دادن اطلاعات |
| **TTL (زمان برای زندگی)** | ورودی های کش پس از یک زمان تعیین شده منقضی می شوند | وقتی داده ها به صورت دوره ای تغییر می کنند |
| **ابطال** | حذف صریح ورودی‌های حافظه پنهان | وقتی دقیقاً می دانید چه زمانی داده ها تغییر می کنند |
### عدم اعتبار کش
دو مشکل سخت در علوم کامپیوتر: عدم اعتبار کش، نامگذاری چیزها، و خطاهای یک به یک.
| استراتژی | توضیحات |
|----------|-------------|
| **مبتنی بر TTL** | ورودی ها پس از N ثانیه منقضی می شوند. ساده اما ممکن است داده های قدیمی را ارائه دهد |
| **رویداد محور** | هنگام تغییر داده ها باطل شود. پیچیده تر اما دقیق |
| **بر اساس نسخه** | شامل یک شماره نسخه. افزایش تغییرات |
| **بر اساس برچسب** | برچسب‌های مربوط به حافظه پنهان؛ باطل کردن تمام ورودی ها با یک برچسب |

## بهینه سازی پایگاه داده
پایگاه داده ها اغلب بزرگترین گلوگاه در برنامه های کاربردی وب هستند.
| تکنیک | توضیحات | تاثیر |
|-----------|-------------|--------|
| **نمایه سازی** | نمایه ها را روی ستون های مورد استفاده در WHERE، JOIN، ORDER BY | اضافه کنید پرس و جوهای 10-1000 برابر سریعتر |
| **بهینه سازی پرس و جو** | اجتناب از SELECT *; از EXPLAIN برای تجزیه و تحلیل پرس و جوها استفاده کنید | کاهش I/O |
| **تجمیع اتصال** | استفاده مجدد از اتصالات پایگاه داده به جای ایجاد اتصالات جدید | حذف سربار اتصال |
| **مثنی ها را بخوانید** | مسیریابی پرس و جوهای خواندنی به پایگاه داده های مشابه | توزیع بار خوانده شده |
| **پارتیشن بندی** | جداول بزرگ را به پارتیشن های کوچکتر تقسیم کنید | جستجوهای سریعتر در مجموعه داده های بزرگ |
| **عادی سازی ** | برای جلوگیری از پیوستن، داده های اضافی اضافه کنید خواندن سریعتر؛ کندتر می نویسد |
| **نماهای مادی** | نتایج پرس و جو از پیش محاسبه شده | پرس و جوهای پیچیده فوری |
| **پیشگیری N+1** | از JOIN ها، بارگیری مشتاقانه، یا درخواست های دسته ای | استفاده کنید حذف هزاران پرس و جو |

## همزمانی و موازی
| مفهوم | توضیحات | زمان استفاده |
|---------|------------|-------------|
| **نخ زدن** | موضوعات متعدد در یک فرآیند واحد | وظایف I/O-Bound (شبکه، دیسک) |
| **چند پردازش ** | چندین فرآیند (GIL را در پایتون دور می زند) | وظایف محدود به CPU |
| **همگام سازی/انتظار** | چندوظیفه ای تعاونی؛ تک رشته | I/O با همزمانی بالا (سرورهای وب) |
| **محاسبات GPU** | هزاران هسته موازی | عملیات ماتریسی؛ پردازش تصویر؛ ML |
### Async در مقابل Threading
| جنبه | Async/Await | نخ زنی |
|--------|-----------|-----------|
| **مدل** | تعاونی (کنترل بازده وظایف) | Preemptive (سیستم عامل سوئیچ رشته ها) |
| **سربار** | بسیار کم (بدون تغییر زمینه) | بالاتر (ایجاد رشته، تغییر زمینه) |
| **پیچیدگی** | استدلال ساده تر (تک رشته) | شرایط مسابقه، بن بست، قفل |
| **بهترین برای** | بسیاری از عملیات I/O همزمان | مسدود کردن عملیاتی که نمی توان آنها را ناهمگام کرد |
| **محدودیت** | بدون مسدود کردن | نمی توان از کد محدود به CPU استفاده کرد GIL در پایتون موازی سازی واقعی را محدود می کند |

## عملکرد Frontend
| تکنیک | توضیحات | تاثیر |
|-----------|-------------|--------|
| **کوچک سازی** | فضای خالی را حذف کنید و نام متغیرها را کوتاه کنید | 20-40٪ فایل های کوچکتر |
| **بسته بندی** | چندین فایل را با درخواست های کمتر ترکیب کنید | درخواست های HTTP کمتر |
| **تقسیم کد** | فقط کد مورد نیاز برای صفحه فعلی را بارگیری کنید | بار اولیه سریعتر |
| **بارگذاری تنبل** | بارگذاری تصاویر و اجزا در صورت نیاز | رندر اولیه سریعتر |
| **لرزش درخت** | حذف کدهای استفاده نشده از بسته ها | بسته های کوچکتر |
| **بهینه سازی تصویر** | از WebP/AVIF استفاده کنید. تصاویر واکنش گرا؛ بارگذاری تنبل | 50-80% تصاویر کوچکتر |
| **CDN** | ارائه دارایی های استاتیک از سرورهای لبه | تاخیر کمتر در سطح جهانی |
| **HTTP/2 و HTTP/3** | مالتی پلکس کردن؛ فشرده سازی هدر؛ 0-RTT | سربار پروتکل سریعتر |
| **کارکنان خدمات** | دارایی های کش برای استفاده آفلاین؛ فشار اعلان ها | بازدیدهای تکراری سریعتر |

## بهینه سازی حافظه
| تکنیک | توضیحات |
|-----------|-------------|
| **تجمیع اشیاء** | استفاده مجدد از اشیاء به جای ایجاد موارد جدید |
| **استریم** | به جای بارگیری همه چیز در حافظه، داده ها را به صورت تکه ای پردازش کنید |
| ** ژنراتورها / تکرار کننده ها ** | به جای ساخت لیست ها، مقادیر را یک به یک ارائه دهید |
| **فایل های حافظه دار** | دسترسی به فایل های حجیم بدون بارگیری کامل |
| **تیونینگ جمع آوری زباله** | پارامترهای GC را برای حجم کاری خود تنظیم کنید |
| **انتخاب ساختار داده** | استفاده از آرایه ها به جای لیست های پیوندی برای محل کش. استفاده از مجموعه ها برای تست عضویت |

## خلاصه
بهینه سازی عملکرد یک فرآیند سیستماتیک است: اندازه گیری، شناسایی گلوگاه، رفع آن، اندازه گیری مجدد. بزرگ‌ترین پیروزی‌ها از پیشرفت‌های الگوریتمی و حذف کارهای غیر ضروری حاصل می‌شود - نه از بهینه‌سازی‌های خرد. کش کردن، نمایه سازی پایگاه داده و همزمانی قدرتمندترین ابزارها هستند. عملکرد Frontend به به حداقل رساندن حجم بار و رفت و برگشت بستگی دارد. و مهمترین قانون همیشه یکسان است: حدس نزن - نمایه.
