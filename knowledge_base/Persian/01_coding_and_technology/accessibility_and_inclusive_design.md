# دسترسی و طراحی فراگیر
دسترس‌پذیری (اغلب به اختصار a11y) عملی است که نرم‌افزار را برای همه قابل استفاده می‌کند - از جمله افراد دارای ناتوانی‌های بینایی، شنوایی، حرکتی، شناختی و عصبی. این یک الزام قانونی در بسیاری از حوزه های قضایی و یک روش استاندارد مهندسی است. نرم افزار در دسترس نرم افزار بهتری برای همه است، زیرا تصمیمات طراحی که از کاربران ناتوان پشتیبانی می کند - ساختار واضح، پیمایش صفحه کلید، کنتراست کافی، متن خوانا - تجربه را برای همه کاربران بهبود می بخشد.
---

## چه کسی از قابلیت دسترسی سود می برد؟
| نوع معلولیت | مثال ها | فناوری کمکی |
|----------------|---------|--------------------|
| **تصویری** | کوری، کم بینایی، کوررنگی | خوانندگان صفحه (JAWS، NVDA، VoiceOver)؛ ذره بین ها؛ حالت های کنتراست بالا |
| **شنوایی** | ناشنوایی، کم شنوایی | زیرنویس ها رونوشت ها؛ هشدارهای بصری |
| **موتور** | مهارت محدود، فلج، لرزش | ناوبری فقط با صفحه کلید؛ کنترل صدا؛ دستگاه های سوئیچ؛ ردیابی چشم |
| **شناختی** | نارساخوانی، ADHD، اوتیسم، اختلالات حافظه | زبان واضح؛ ناوبری سازگار؛ کاهش حواس پرتی |
| **موقت** | دست شکسته، نور آفتاب روشن، محیط پر سر و صدا | امکانات اقامتی مشابه معلولان دائمی |
| **وضعیت** | نگه داشتن نوزاد، رانندگی، یک دست اشغال | رابط های صوتی؛ اهداف لمسی بزرگ |
**بینش کلیدی**: ویژگی های دسترس پذیری طراحی شده برای کاربران ناتوان به همه کمک می کند. برش‌ها (رمپ‌ها در پیاده‌روها) برای ویلچر طراحی شده‌اند اما توسط والدین با کالسکه، کارگران تحویل با چرخ دستی و مسافران با چمدان استفاده می‌شوند.

## دسترسی به وب (WCAG)
دستورالعمل های دسترسی به محتوای وب (WCAG) استاندارد بین المللی برای دسترسی به وب است.
### اصول WCAG (POUR)
| اصل | مورد نیاز |
|-----------|-------------|
| **قابل درک** | اطلاعات باید به گونه‌ای قابل ارائه باشد که کاربران بتوانند آن را درک کنند (جایگزین‌های متن، زیرنویس‌ها، طرح‌بندی قابل تطبیق) |
| **قابل اجرا** | رابط باید قابل پیمایش و قابل استفاده باشد (قابلیت دسترسی به صفحه کلید، زمان کافی، بدون محتوای تشنج کننده) |
| **قابل درک** | اطلاعات و عملیات باید قابل درک باشد (قابل خواندن، قابل پیش بینی، کمک ورودی) |
| **مقاوم** | محتوا باید با فناوری های کمکی فعلی و آینده کار کند |
### سطوح انطباق WCAG
| سطح | الزامات | هدف معمولی |
|-------|------------|---------------|
| **A** | حداقل سطح؛ 30 معیار موفقیت | حداقل های قانونی در برخی حوزه های قضایی |
| **AA** | به رایج ترین موانع می پردازد | هدف استاندارد برای اکثر سازمان ها |
| **AAA** | بالاترین سطح؛ همه محتوا نمی توانند به آن دست یابند | محتوای تخصصی; سایت های آموزشی |
### معیارهای کلیدی موفقیت (سطح AA)
| معیار | مورد نیاز | چگونه به دست آوریم |
|-----------|-------------|---------------|
| **1.1.1 محتوای غیر متنی** | همه تصاویر دارای متن جایگزین هستند |  ویژگی های `alt`؛ `aria-label`برای نمادها |
| **1.3.1 اطلاعات و روابط** | ساختار به صورت برنامه ای منتقل می شود | HTML معنایی؛ سرفصل ها لیست ها نقاط دیدنی |
| **1.4.3 کنتراست (حداقل)** | متن دارای نسبت کنتراست حداقل 4.5:1 | تست با چک کننده های کنتراست؛ پالت های رنگی در دسترس را انتخاب کنید |
| **1.4.4 تغییر اندازه متن** | اندازه متن تا 200% بدون از دست دادن قابل تغییر است | از واحدهای نسبی (rem, em) استفاده کنید. طراحی واکنش گرا |
| **2.1.1 صفحه کلید ** | تمام قابلیت ها از طریق صفحه کلید در دسترس است | بدون تله صفحه کلید. نشانگرهای فوکوس قابل مشاهده |
| **2.4.3 سفارش فوکوس** | ترتیب تمرکز معنی و عملکرد را حفظ می کند | ترتیب زبانه منطقی؛ سفارش DOM با نظم بصری مطابقت دارد |
| **2.4.7 فوکوس قابل مشاهده ** | فوکوس صفحه کلید به صورت بصری نشان داده شده است | سبک های CSS `:focus-visible`؛ هرگز`outline: none`بدون تعویض |
| **3.3.2 برچسب ها یا دستورالعمل ها ** | ورودی ها دارای برچسب |  عناصر `<label>`؛ `aria-label`|
| **4.1.2 نام، نقش، ارزش** | اجزای رابط کاربری نام ها و نقش های قابل دسترسی دارند | ویژگی های ARIA؛ HTML معنایی |
---

## ARIA (برنامه‌های اینترنتی غنی در دسترس)
ARIA اطلاعات دسترسی را به عناصر HTML اضافه می کند که معنایی داخلی ندارند.
### نقش های ARIA
| نقش | هدف | مثال |
|------|---------|---------|
| `button`| یک عنصر را به عنوان دکمه | شناسایی می کند یک`<div>`به شکل یک دکمه |
| `dialog`| گفتگوی معین یا غیرمدال | اجزای مدال سفارشی |
| `tablist`/`tab`/`tabpanel`| رابط برگه | اجزای برگه سفارشی |
| `alert`| پیام مهمی که به صورت پویا ظاهر می شود | اعلان های خطا |
| `progressbar`| نشانگر پیشرفت | حالات بارگیری |
| `menu`/`menuitem`| پیمایش منو | منوهای کشویی |
### ویژگی های ARIA
| صفت | هدف | مثال |
|-----------|---------|---------|
| `aria-label`| نام قابل دسترسی زمانی که متن قابل مشاهده نیست | دکمه فقط نماد:`aria-label="Search"`|
| `aria-describedby`| پیوند عنصر به توضیحات آن | فیلد فرم با متن راهنما |
| `aria-expanded`| نشان می دهد که آیا یک بخش گسترش یافته است | آکاردئون; کشویی |
| `aria-hidden`| عنصر را از فناوری کمکی پنهان می کند | آیکون های تزئینی |
| `aria-live`| تغییرات محتوای پویا را اعلام می کند | به روز رسانی زنده؛ اطلاعیه ها |
| `aria-disabled`| نشان می دهد عنصر غیرفعال است | دکمه های خاکستری شده |
### قانون اول ARIA
> **اگر می توانید به جای آن از HTML بومی استفاده کنید از ARIA استفاده نکنید.** یک`<button>`از قبل در دسترس است.`<div role="button">`از شما می خواهد که به صورت دستی کنترل صفحه کلید، مدیریت فوکوس و پشتیبانی از صفحه خوان را اضافه کنید. ابتدا از HTML معنایی استفاده کنید. ARIA فقط زمانی که عناصر بومی نتوانند کار را انجام دهند.

## ناوبری صفحه کلید
| کلید | رفتار مورد انتظار |
|-----|------------------|
| **تب** | انتقال فوکوس به عنصر تعاملی بعدی |
| **Shift + Tab** | انتقال فوکوس به عنصر تعاملی قبلی |
| **ورود / فاصله ** | فعال کردن عنصر متمرکز (دکمه، پیوند) |
| **کلیدهای جهت دار** | پیمایش درون مؤلفه‌ها (منوها، برگه‌ها، گروه‌های رادیویی) |
| **فرار** | بستن یک گفتگو، منو یا پاپاور |
| **صفحه اصلی / پایان ** | پرش به اولین / آخرین مورد در یک لیست |
### تله های رایج صفحه کلید
| مشکل | رفع |
|---------|-----|
| فوکوس وارد یک جزء می شود اما نمی تواند از آن خارج شود | اطمینان حاصل کنید که برگه فوکوس را خارج می کند. دسته فرار |
| مدال تمرکز را به دام نمی اندازد | تمرکز باید در چرخه مدال باشد. بازگشت به ماشه در بسته |
| اجزای سفارشی به صفحه کلید پاسخ نمی دهند | اضافه کردن کنترل کننده کلید برای Enter، Space، arrows |

## رنگ و طراحی بصری
| راهنما | مورد نیاز |
|-----------|-------------|
| **نسبت کنتراست** | 4.5:1 برای متن معمولی. 3:1 برای متن بزرگ (18pt+ یا 14pt+ پررنگ) |
| **به رنگ تنها تکیه نکنید** | علاوه بر رنگ | از نمادها، متن یا الگوها استفاده کنید
| **نشانگرهای فوکوس** | همیشه قابل مشاهده است؛ کنتراست بالا؛ هرگز بدون تعویض حذف نشد |
| **تغییر اندازه متن** | Layout باید با زوم 200% کار کند |
| **پاسخگو** | محتوا باید با عرض 320 پیکسل (موبایل) |
### ملاحظات کوررنگی
| نوع | رنگ های تحت تاثیر | نکته طراحی |
|------|-----------------|-----------|
| **دوترانوپیا** | قرمز-سبز (متداول ترین) | از قرمز/سبز برای انتقال وضعیت استفاده نکنید. استفاده از نمادها + رنگ |
| **پروتانوپیا** | قرمز-سبز | مانند بالا |
| **تریتانوپیا** | آبی-زرد | از آبی/زرد به عنوان تمایز تنها استفاده نکنید |

## تست دسترسی
| روش | ابزار | آنچه می گیرد |
|--------|------|----------------|
| **اسکن خودکار** | تبر، فانوس دریایی، WAVE | متن جایگزین وجود ندارد. مسائل کنتراست؛ خطاهای ARIA |
| **تست کیبورد** | دستی: ماوس را از برق بکشید، فقط از صفحه کلید استفاده کنید | ترتیب تمرکز؛ تله صفحه کلید; کنترل کننده های گم شده |
| **تست صفحه خوان** | NVDA (رایگان)، VoiceOver (macOS)، JAWS | برچسب های گم شده؛ ساختار ضعیف؛ تغییرات اعلام نشده |
| **تست زوم** | بزرگنمایی مرورگر به 200%، 400% | شکستگی چیدمان؛ متن بریده شده؛ مسائل سرریز |
| **تضاد رنگ** | بررسی کنتراست WebAIM، پلاگین Stark | نسبت کنتراست ناکافی |
| **تست کاربر** | تست با کاربران ناتوان | موانع دنیای واقعی که ابزارهای خودکار از دست می‌دهند |

| قانون | منطقه | الزامات |
|-----|--------|-------------|
| **ADA** (قانون آمریکایی های دارای معلولیت) | آمریکا | وب سایت های اقامتی عمومی باید قابل دسترسی باشند |
| **بخش 508** | آمریکا (فدرال) | ICT آژانس های فدرال باید در دسترس باشد |

| **ACA** (قانون دسترسی کانادا) | کانادا | صنایع دولتی و تحت نظارت |
| **قانون برابری 2010** | انگلستان | ارائه دهندگان خدمات باید تنظیمات معقول را انجام دهند |

## خلاصه
دسترس‌پذیری یک اصل طراحی است که باید هر تصمیمی را از ابتدا مشخص کند، نه ویژگی اضافه شده در پایان. از HTML معنایی استفاده کنید. اطمینان حاصل کنید که پیمایش صفحه کلید کار می کند. کنتراست رنگی کافی را حفظ کنید. جایگزین های متنی برای محتوای غیر متنی ارائه دهید. با صفحه خوان ها و کاربران غیر فعال تست کنید. نتیجه نرم‌افزاری است که برای همه بهتر کار می‌کند - از جمله افرادی که دارای نقص‌های موقت، محدودیت‌های موقعیتی، دستگاه‌های قدیمی‌تر، اتصالات کند و راه‌هایی است که استفاده در دنیای واقعی با یک محیط توسعه کنترل‌شده متفاوت است.
