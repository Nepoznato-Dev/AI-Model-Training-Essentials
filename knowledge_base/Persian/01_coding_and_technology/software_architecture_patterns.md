# الگوهای معماری نرم افزار
معماری مجموعه ای از تصمیمات ساختاری در مورد چگونگی سازماندهی یک سیستم است - چه اجزایی دارد، چگونه ارتباط برقرار می کنند و مسئولیت ها در کجا قرار دارند. معماری خوب باعث می شود که یک سیستم به راحتی قابل درک، تغییر و مقیاس باشد. معماری بد هر تغییری را تبدیل به یک مبارزه می کند. این فایل الگوهای اصلی، زمان استفاده از هر کدام و مبادلات مربوط را پوشش می دهد.
---

## Monolith در مقابل Microservices
این اساسی ترین تصمیم معماری است و ارزش آن را دارد که درست انجام شود.
| جنبه | یکپارچه | میکروسرویس |
|--------|---------|---------------|
| **ساختار** | واحد قابل استقرار | بسیاری از خدمات کوچک و مستقل قابل استقرار |
| **داده** | پایگاه داده مشترک | هر سرویس دارای داده های خود است |
| **ارتباطات** | فراخوانی تابع در حال پردازش | تماس های شبکه (HTTP، gRPC، پیام رسانی) |
| **مقیاس بندی** | مقیاس کل برنامه | مقیاس خدمات فردی |
| **استقرار** | چرخه انتشار تک | استقرار مستقل |
| **پیچیدگی** | توسعه اولیه ساده تر | پیچیدگی عملیاتی (شبکه سازی، نظارت) |
| **بهترین برای** | تیم های کوچک، محصولات اولیه | تیم های بزرگ، دامنه های پیچیده، در مقیاس بالا |
### چه زمانی باید با مونولیت شروع کرد
اکثر برنامه ها باید به صورت یکپارچه شروع شوند. ساخت، آزمایش، استقرار و اشکال زدایی ساده تر است. وقتی تصویر واضح تری از مرزهای دامنه خود دارید، همیشه می توانید خدمات را استخراج کنید. گاهی اوقات به آن "مونولیت مدولار" می گویند - یکپارچه با مرزهای داخلی تمیز که استخراج را بعدا آسان می کند.
### چه زمانی به میکروسرویس ها برویم
زمانی که ریز سرویس ها را در نظر بگیرید:
- تیم ها به اندازه ای بزرگ هستند که هماهنگی به یک گلوگاه تبدیل شود.
- بخش های مختلف سیستم نیازهای مقیاس بندی بسیار متفاوتی دارند.
- شما نیاز به استقرار مستقل اجزاء دارید.
- دامنه شما دارای زمینه های محدود مشخص است (به DDD زیر مراجعه کنید).

## معماری لایه ای (N-Tier)
رایج ترین الگوی معماری کدها در لایه هایی سازماندهی شده اند که هر کدام مسئولیت خاصی دارند.
```
â”Œ─────────────────────────┐
│   Presentation Layer    │  ← UI, controllers, API endpoints
├─────────────────────────┤
│   Application Layer     │  ← Use cases, orchestration
├─────────────────────────┤
│   Domain Layer          │  ← Business logic, entities
├─────────────────────────┤
│   Infrastructure Layer  │  ← Database, external services, file I/O
└─────────────────────────┘
```

| لایه | مسئولیت | قانون |
|-------|---------------|------|
| **ارائه** | رسیدگی به درخواست های کاربر/HTTP | فقط لایه Application را می توان فراخوانی کرد |
| **برنامه** | موارد استفاده ارکستراسیون | آیا می توان لایه دامنه |
| **دامنه** | منطق اصلی کسب و کار | نباید به لایه های دیگر وابسته باشد |
| **زیرساخت** | نگرانی های فنی | رابط های تعریف شده در Domain | را پیاده سازی می کند
**قانون کلیدی**: وابستگی ها به سمت داخل هستند. لایه Domain از پایگاه داده یا چارچوب وب اطلاعی ندارد.

## معماری رویداد محور
اجزا با انتشار و واکنش به **رویدادها** - چیزهایی که اتفاق افتاده است، ارتباط برقرار می کنند.
| الگو | توضیحات |
|---------|-------------|
| **اطلاع رسانی رویداد** | سرویس A "OrderPlaced" را منتشر می کند. خدمات B, C, D react |
| **منبع رویداد** | ذخیره تمام تغییرات حالت به عنوان یک توالی از رویدادها (نه فقط وضعیت فعلی) |
| **CQRS** | جدا کردن مدل خواندن (پرس و جو) از مدل نوشتن (فرمان ها) |
### رویداد منبع یابی
به جای ذخیره "وضعیت فعلی" در پایگاه داده، هر تغییر وضعیت را به عنوان یک رویداد ذخیره کنید:
```
OrderCreated(order_id=123, total=$50)
OrderPaid(order_id=123, payment_id=456)
OrderShipped(order_id=123, tracking=ABC)
```

مزایا: پیگیری کامل حسابرسی، توانایی بازسازی هر وضعیت گذشته، مصرف کنندگان جدا شده. چالش‌ها: تکامل طرح‌واره رویداد، ثبات نهایی، پیچیدگی اشکال‌زدایی.
### CQRS (تفکیک مسئولیت پرس و جوی فرمان)
| سمت | هدف | پایگاه داده |
|------|---------|----------|
| **فرمان (نوشتن)** | کنترل جهش؛ اجرای قوانین تجاری | بهینه شده برای نوشتن (نرمال) |
| **پرس و جو (خواندن)** | ارائه درخواست های خواندن | بهینه شده برای خواندن (غیر عادی) |
CQRS به طور طبیعی با Event Sourcing جفت می‌شود: رویدادها از سمت نوشتن به نمایش‌های بهینه خواندن نمایش داده می‌شوند.

## صف های پیام و کارگزاران رویداد
هنگامی که سرویس ها نیاز به ارتباط ناهمزمان دارند، صف های پیام ستون فقرات هستند.
| ابزار | نوع | بهترین برای |
|------|------|----------|
| **آپاچی کافکا** | گزارش رویداد توزیع شده | جریان رویداد با توان بالا، منبع رویداد |
| **RabbitMQ** | کارگزار پیام با مسیریابی | صف های وظیفه، الگوهای مسیریابی پیچیده |
| **AWS SQS** | صف مدیریت شده | AWS بومی، صف ساده |
| **AWS SNS** | اطلاعیه انتشارات/فرعی | Fan out به چند مشترک |
| **Google Pub/Sub** | میخانه/فرعی مدیریت شده | پخش جریانی رویداد بومی GCP |
| **ردیس استریمز** | جریان سبک | ثبت رویدادهای ساده، موارد استفاده در حافظه پنهان |
### الگوهای پیام رسانی
| الگو | توضیحات |
|---------|-------------|
| **نقطه به نقطه** | یک تولید کننده، یک مصرف کننده در هر پیام |
| **انتشار/اشتراک** | یک تولید کننده، چند مشترک |
| **درخواست/پاسخ** | سبک همزمان بر حمل و نقل ناهمگام |
| **صف نامه مرده** | پیام‌هایی که پردازش نمی‌شوند به صف جداگانه‌ای برای بازرسی می‌روند |

## طراحی دامنه محور (DDD)
DDD یک رویکرد استراتژیک برای طراحی نرم افزار است که کد را حول مفاهیم تجاری به جای نگرانی های فنی متمرکز می کند.
### مفاهیم کلیدی
| مفهوم | توضیحات |
|---------|-------------|
| **زمینه محدود** | مرزی که در آن یک مدل دامنه سازگار است (به عنوان مثال، "سفارش"، "حمل و نقل"، "صورتحساب") |
| **زبان همه جا حاضر** | واژگان مشترک بین توسعه دهندگان و کارشناسان دامنه |
| **مجموعه** | خوشه های موجودیت های مرتبط به عنوان یک واحد واحد برای تغییرات داده ها |
| **موجودات** | اشیاء با هویت (به عنوان مثال، یک کاربر با شناسه کاربر) |
| **اشیاء ارزش** | اشیاء بدون هویت؛ با ویژگی های آنها (به عنوان مثال، پول، آدرس) تعریف می شود |
| **رویدادهای دامنه** | چیزی که در دامنه (به عنوان مثال، OrderPlaced) |
| **لایه ضد فساد** | لایه ترجمه بین دامنه شما و سیستم های خارجی |
### وقتی DDD کمک می کند
DDD زمانی ارزشمندتر است که حوزه کسب و کار پیچیده باشد - به تجارت الکترونیک، تدارکات، خدمات مالی، مراقبت های بهداشتی فکر کنید. اگر دامنه شما ساده است (یک وبلاگ، یک برنامه todo)، DDD بیش از حد است.

## استراتژی های ذخیره سازی
حافظه پنهان یکی از موثرترین راه‌ها برای بهبود عملکرد است، اما پیچیدگی را در اطراف سازگاری ایجاد می‌کند.
| استراتژی | توضیحات | معامله |
|----------|------------|-----------|
| **Cache-Aside** | برنامه ابتدا حافظه پنهان را بررسی می کند. بارگیری از DB در miss | ساده؛ ثبات نهایی |
| **نوشتن از طریق** | نوشتن در حافظه پنهان و DB به طور همزمان | سازگار؛ کندتر می نویسد |
| **نوشتن-پشت ** | نوشتن در حافظه پنهان؛ async نوشتن به DB | فست می نویسد؛ خطر از دست دادن اطلاعات |
| **خواندنی** | بارگذاری کش از DB در miss transparent | ساده تر از cache-aside |
### چه چیزی را در حافظه پنهان کنیم
| لایه | چی | ابزار |
|-------|------|-------|
| **CDN** | دارایی های استاتیک، پاسخ های API | CloudFront، Cloudflare |
| **برنامه** | نتایج محاسبه شده، داده های جلسه | Redis، Memcached |
| **پایگاه اطلاعاتی** | نتایج پرس و جو، سطرهایی که اغلب به آنها دسترسی دارند | کش پرس و جو، نماهای واقعی |
**بی اعتبار کردن حافظه نهان** بسیار سخت است. استراتژی‌های متداول: TTL (زمان تا زندگی)، باطل‌سازی مبتنی بر رویداد (پاک کردن حافظه پنهان هنگام تغییر داده‌ها)، و LRU (که اخیراً استفاده شده است) اخراج.

## الگوهای طراحی
### اصول جامد
| اصل | معنی آن |
|-----------|--------------|
| **S** — تک مسئولیت | یک کلاس باید یک دلیل برای تغییر داشته باشد |
| **O** — باز/بسته | باز برای گسترش، بسته برای اصلاح |
| **L** — تعویض لیسکوف | زیرگروه ها باید برای انواع پایه خود قابل تعویض باشند |
| **I** — جداسازی رابط | بسیاری از رابط های خاص > یک رابط همه منظوره |
| **D** — وارونگی وابستگی | به انتزاعات بستگی دارد نه انضمامی |
### الگوهای رایج
| الگو | قصد | مثال |
|---------|--------|---------|
| **سینگلتون** | اطمینان حاصل کنید که یک کلاس فقط یک نمونه | استخر اتصال پایگاه داده |
| **کارخانه** | ایجاد اشیاء بدون تعیین کلاس دقیق | `UserFactory.create(type="admin")`|
| **ناظر** | هنگام تغییر وضعیت به افراد وابسته اطلاع دهید | شنوندگان رویداد، میخانه/زیر |
| **استراتژی** | تعویض الگوریتم ها در زمان اجرا | استراتژی پرداخت: کارت اعتباری، پی پال، کریپتو |
| **مخزن** | دسترسی به داده های انتزاعی در پشت یک رابط تمیز |  __محافظت شده_1__ |
| **دکوراتور** | رفتار را به صورت پویا اضافه کنید | دکوراتور ورود به سیستم در اطراف یک سرویس |
| **آداپتور** | ایجاد رابط های ناسازگار با هم کار کنند | آداپتور API Legacy |

## انتخاب معماری مناسب
هیچ معماری جهانی "بهترین" وجود ندارد. انتخاب صحیح بستگی به این دارد:
| فاکتور | به لطف یکپارچه وقتی... | به لطف Microservices وقتی... |
|--------|-----------------------------------------------------|
| **اندازه تیم** | < 10 developers | >20 توسعه دهنده، تیم های متعدد |
| **پیچیدگی دامنه** | ساده یا قابل فهم | پیچیده، بسیاری از زمینه های محدود |
| **نیازمندی های مقیاس** | نیازهای مقیاس بندی یکنواخت | اجزای مختلف به مقیاس متفاوتی نیاز دارند |
| **سرعت استقرار** | چرخه انتشار تک | نیاز به استقرار مستقل |
| **تنوع تکنولوژی** | یک پشته خوب است | خدمات مختلف نیاز به فناوری متفاوت دارند |
**توصیه عملی**: با یک مونولیت مدولار شروع کنید. خدمات را تنها زمانی استخراج کنید که نیاز واضحی داشته باشید و مرزهای دامنه را مشخص کنید. میکروسرویس های زودرس یکی از رایج ترین اشتباهات معماری در صنعت است.
