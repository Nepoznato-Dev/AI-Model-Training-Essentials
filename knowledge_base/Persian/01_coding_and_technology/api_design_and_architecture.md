# طراحی و معماری API
API (Application Programming Interface) نحوه صحبت اجزای نرم افزار با یکدیگر است. یک API خوب طراحی شده بصری، سازگار و لذت بخش است. طراحی ضعیف باعث سردرگمی، اشکالات و ناامیدی می شود. این فایل اصول، الگوها و شیوه‌های ساخت APIهایی را که توسعه‌دهندگان واقعاً می‌خواهند استفاده کنند، پوشش می‌دهد.
---

## اصول API REST
REST (انتقال حالت نمایندگی) سبک معماری غالب برای APIهای وب است. این داده ها را به عنوان **منابع** شناسایی شده توسط URL ها در نظر می گیرد و از روش های HTTP برای کار بر روی آنها استفاده می کند.
### اصول اصلی
| اصل | توضیحات |
|-----------|-------------|
| **منابع** | همه چیز یک منبع با URI است (`/users/123`,`/orders/456`) |
| **روش های HTTP** | GET (خواندن)، POST (ایجاد)، قرار دادن (جایگزین)، PATCH (به روز رسانی جزئی)، DELETE (حذف) |
| **بی تابعیتی** | هر درخواست شامل تمام اطلاعات مورد نیاز است. بدون وضعیت جلسه سمت سرور |
| **رابط یکنواخت** | نام‌گذاری منابع، روش‌های استاندارد، کدهای وضعیت استاندارد |
| **نمایندگی** | منابع را می توان در قالب های متعدد (JSON، XML) |
### قراردادهای نامگذاری منابع
| انجام | نکن |
|----|-------|
| `/users`(اسم جمع) | `/user`(مفرد) |
| `/users/123/orders`(تودرتو) |  __محافظت شده_3__ |
| `/products?category=electronics`(پارام های پرس و جو برای فیلتر کردن) | `/productsByCategory/electronics`|
| از خط تیره استفاده کنید:`/user-profiles`| از زیرخط ها استفاده کنید:`/user_profiles`|
### روش های HTTP و عدم توانایی
| روش | هدف | بی توان؟ | امن؟ |
|--------|--------|------------|-------|
| **دریافت ** | خواندن یک منبع | ✅ بله | ✅ بله |
| **پست** | ایجاد یک منبع | ❌ نه | ❌ نه |
| ** قرار دادن ** | جایگزین یک منبع به طور کامل | ✅ بله | ❌ نه |
| **پچ** | به روز رسانی جزئی یک منبع | ❌ خیر* | ❌ نه |
| **حذف ** | حذف یک منبع | ✅ بله | ❌ نه |
*PATCH را می توان با طراحی دقیق بی توان ساخت.
### کدهای وضعیت HTTP
| کد | معنی | زمان استفاده |
|------|---------|-------------|
| **200** | باشه | GET، PUT، PATCH، DELETE با موفقیت |
| **201** | ایجاد شده | POST موفق (منبع ایجاد شده) |
| **204** | بدون محتوا | DELETE با موفقیت انجام شد (چیزی برای بازگشت وجود ندارد) |
| **400** | درخواست بد | ورودی نامعتبر یا درخواست نادرست |
| **401** | غیر مجاز | احراز هویت وجود ندارد یا نامعتبر است |
| **403** | ممنوع | احراز هویت شده اما مجاز نیست |
| **404** | یافت نشد | منبع وجود ندارد |
| **409** | درگیری | منبع تکراری یا تضاد حالت |
| **422** | موجودیت غیر قابل پردازش | JSON معتبر اما خطاهای معنایی |
| **429** | درخواست های بسیار زیاد | بیش از حد مجاز |
| **500** | خطای سرور داخلی | خطای سرور غیرمنتظره |
| **502** | دروازه بد | خرابی سرویس بالادست |
| **503** | سرویس در دسترس نیست | اضافه بار یا نگهداری موقت |

## نسخه API
API ها تکامل می یابند. زمانی که نیاز به ایجاد تغییرات اساسی دارید، نسخه سازی به مشتریان موجود اجازه می دهد به کار خود ادامه دهند.
| استراتژی | مثال | جوانب مثبت | معایب |
|----------|---------|------|------|
| **مسیر آدرس** |  `/v1/users`،`/v2/users`| ساده، صریح | تغییر URL در هر نسخه |
| **پارامتر پرس و جو** | `/users?version=2`| انعطاف پذیر | فراموش کردن آسان |
| **سربرگ** |  __محافظت شده_3__ | URL های پاک | کمتر قابل کشف |
| **بدون نسخه** | فقط تکامل طرحواره | ساده ترین | تغییرات شکسته بر همه تاثیر می گذارد |
**بهترین روش**: برای وضوح از نسخه سازی مسیر URL (`/v1/`) استفاده کنید. حداقل از یک نسخه قبلی پشتیبانی کنید. نسخه های قدیمی با جدول زمانی مشخص را منسوخ کنید.
---

## روش های احراز هویت
| روش | چگونه کار می کند | بهترین برای |
|--------|------------|----------|
| **کلیدهای API** | کلید مخفی در هدر (`X-API-Key: abc123`) | سرور به سرور، ادغام ساده |
| **OAuth2** | تفویض اختیار مبتنی بر توکن با محدوده | دسترسی شخص ثالث، برنامه های مجاز توسط کاربر |
| **JWT** | توکن خودکفا با ادعا | احراز هویت بدون تابعیت در سراسر خدمات |
| **Auth Basic** | نام کاربری رمزگذاری شده با Base64: رمز عبور | فقط توسعه — هرگز بدون TLS تولید نشود |
| **کوکی های جلسه** | شناسه جلسه سمت سرور در کوکی فقط HTTP | برنامه های کاربردی وب سنتی |
### جریان OAuth2 (ساده شده)
1. مشتری کاربر را به سرور مجوز هدایت می کند.
2. کاربر وارد سیستم می شود و اجازه می دهد.
3. سرور مجوز یک کد مجوز را برمی گرداند.
4. مشتری کد را برای توکن دسترسی (و به صورت اختیاری توکن refresh) مبادله می کند.
5. کلاینت از نشانه دسترسی برای فراخوانی API استفاده می کند.
6. زمانی که توکن دسترسی منقضی شد، از توکن refresh برای دریافت یک نشانه جدید استفاده کنید.

## سبک های API: REST در مقابل GraphQL در مقابل gRPC
| ویژگی | استراحت | GraphQL | gRPC |
|---------|------|---------|------|
| **فرمت داده** | JSON (معمولا) | JSON | پروتوبوف (دودویی) |
| **نقاط پایانی** | چندگانه (یکی در هر منبع) | نقطه پایانی واحد | تعریف شده توسط فایل پروتو |
| **بیش از حد واکشی** | رایج (بیش از نیاز دریافت کنید) | هیچ (مشتری فیلدها را مشخص می کند) | هیچکدام (تعریف شده توسط طرحواره) |
| **کم واکشی ** | نیاز به تماس های متعدد | هیچکدام (دقیقا آنچه را که لازم است دریافت کنید) | هیچکدام |
| **زمان واقعی** | وب سوکت های مورد نیاز | اشتراک های داخلی | پخش جریانی داخلی |
| **در حافظه پنهان** | کش HTTP به طور طبیعی کار می کند | کش سخت تر | محدود |
| **منحنی یادگیری** | کم | متوسط ​​| متوسط-بالا |
| **بهترین برای** | API های عمومی، برنامه های CRUD | رابط های کاربری پیچیده، برنامه های تلفن همراه | میکروسرویس های داخلی با کارایی بالا |

## صفحه بندی، فیلتر کردن، و مرتب سازی
برای نقاط پایانی که لیست ها را برمی گرداند:
| تکنیک | مثال | زمان استفاده |
|-----------|---------|-------------|
| **افست/محدودیت** | `?offset=20&limit=10`| ساده؛ برای مجموعه داده های کوچک کار می کند |
| **مکان نما** |  __محافظت شده_1__ | مجموعه داده های بزرگ؛ نتایج ثابت |
| **دستگاه کلید** | `?created_after=2024-01-01&limit=10`| بسیار کارآمد؛ نیاز به کلید منحصر به فرد |
```json
// Cursor-based response
{
  "data": [...],
  "pagination": {
    "next_cursor": "abc123",
    "has_more": true
  }
}
```

## محدودیت نرخ
از API خود در برابر سوء استفاده محافظت کنید و از استفاده منصفانه اطمینان حاصل کنید.
| استراتژی | چگونه کار می کند |
|----------|-------------|
| **پنجره ثابت** | N درخواست در هر پنجره زمانی (مثلاً 100 در ساعت) |
| **پنجره کشویی** | دانه ای بیشتر؛ تعداد درخواست ها در پنجره چرخان |
| **سطل ژتون** | توکن های اضافه شده با نرخ ثابت؛ هر درخواست یک توکن |
`429 Too Many Requests` را با هدر برگردانید:```
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1625097600
Retry-After: 60
```

## رسیدگی به خطا
پاسخ های خطای مداوم کار با API ها را بسیار آسان تر می کند:
```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Invalid input data",
    "details": [
      {
        "field": "email",
        "issue": "Invalid email format"
      }
    ]
  }
}
```

**اصول**: از ساختار خطای یکنواخت استفاده کنید، پیام‌های عملی را شامل شود، از کدهای وضعیت HTTP استاندارد استفاده کنید، خطاهای گزارش در سمت سرور با شناسه‌های همبستگی، و هرگز ردپای پشته یا جزئیات داخلی را فاش نکنید.

## الگوهای دروازه API
یک دروازه API بین سرویس گیرندگان و خدمات باطن قرار می گیرد و یک نقطه ورودی واحد را فراهم می کند.
| مسئولیت | توضیحات |
|---------------|-------------|
| **مسیریابی** | درخواست مستقیم به خدمات باطن مناسب |
| ** احراز هویت ** | اعتبارسنجی توکن ها در سطح دروازه |
| **محدودیت نرخ** | اعمال محدودیت های جهانی یا هر مشتری |
| **تحول** | تبدیل بین پروتکل ها (REST ↔ gRPC) |
| **در حافظه پنهان** | کش پاسخ های رایج |
| **نظارت** | ثبت متمرکز و متریک |
| **تعادل بار** | توزیع ترافیک در بین نمونه های خدمات |
| ابزار | نوع |
|------|------|
| **کنگ** | دروازه API منبع باز (مبتنی بر Nginx) |
| ** AWS API Gateway ** | کاملاً مدیریت شده، یکپارچه با AWS |
| **مدیریت Azure API** | دروازه مدیریت شده با پورتال توسعه دهنده |
| **فرستاده / ایستیو** | سرویس مش با قابلیت دروازه API |
| **ترافیک** | کشف خودکار، ادغام بیایید رمزگذاری کنیم |

## وب هوک
Webhooks به API شما اجازه می‌دهد رویدادها را به‌طور هم‌زمان به سمت مشتریان هدایت کند، نه اینکه مشتریان را برای تغییرات نظرسنجی کنند.
| جنبه | بهترین تمرین |
|--------|--------------|
| **تحویل** | درخواست POST با بارگیری JSON به URL مشتری |
| **امنیتی** | محموله ها را با HMAC امضا کنید. مشتری امضا را تأیید می کند |
| **قابلیت اطمینان** | سعی مجدد تحویل ناموفق با عقب نشینی نمایی |
| **بی توانی** | شامل شناسه رویداد منحصر به فرد. مشتری موارد تکراری را مدیریت می کند |
| **نسخه** | شامل نسخه API در بارگذاری وب هوک |
