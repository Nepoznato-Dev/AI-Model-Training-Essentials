# روش های تست
آزمایش به این معنی است که چگونه می‌توانید اطمینان حاصل کنید که کدتان کار می‌کند - و مهمتر از آن، اینکه تغییرات در آن چیزی که قبلاً کار می‌کرد را خراب نمی‌کند. آزمایش خوب قبل از اینکه کاربران انجام دهند، اشکالات را شناسایی می کند، رفتار مورد انتظار را مستند می کند و بازسازی بی باک را امکان پذیر می کند. این فایل طیف کاملی از استراتژی‌های تست، از تست‌های واحد گرفته تا تست‌های انتها به انتها، و اصولی که تست را موثر می‌سازد را پوشش می‌دهد.
---

## هرم تست
هرم تست توزیع ایده آل تست ها را در یک پروژه توصیف می کند.
```
        /  E2E  \          ← Few; slow; expensive; test the whole system
       /─────────\
      / Integration\       ← Some; test how components work together
     /───────────────\
    /   Unit Tests    \    ← Many; fast; cheap; test individual functions
   /─────────────────────\
```

| سطح | شمارش | سرعت | هزینه | آنچه را آزمایش می کند |
|-------|-------|------|------|--------------|
| **واحد** | بسیاری | سریع (ms) | کم | توابع، کلاس ها، روش های فردی |
| **ادغام** | برخی | متوسط ​​(100ms-s) | متوسط ​​| نحوه تعامل اجزاء پرس و جوهای پایگاه داده؛ تماس های API |
| **E2E** | تعداد کمی | آهسته (ثانیه-دقیقه) | بالا | جریان کاربر کامل از طریق سیستم واقعی |

## تست واحد
تست واحدهای منفرد کد به صورت مجزا.
### اصول
| اصل | توضیحات |
|-----------|-------------|
| **سریع** | هر تست باید در میلی ثانیه اجرا شود |
| **منزوی** | تست ها به یکدیگر وابسته نیستند. حالت مشترک وجود ندارد |
| **قطعی** | ورودی یکسان → خروجی یکسان هر بار (بدون تصادفی، بدون وابستگی زمانی) |
| **خودآزمایی** | آزمون به طور خودکار قبول می شود یا ناموفق است. بدون بازرسی دستی |
| **به موقع** | نوشته شده در کنار یا قبل از کد (TDD) |
### آناتومی یک تست
| فاز | توضیحات |
|-------|------------|
| **ترتیب** | تنظیم داده های تست و وابستگی ها |
| **عمل** | فراخوانی تابع یا روش در حال آزمایش |
| **ادعا** | بررسی کنید که نتیجه مطابق با انتظارات است |
### چه چیزی را تست کنیم
| دسته بندی | مثال ها |
|----------|---------|
| **مسیر مبارک** | ورودی های عادی خروجی های مورد انتظار را تولید می کنند |
| **اجاق های لبه** | ورودی خالی، تهی، صفر، مقادیر حداکثر، تک عنصر |
| **موارد خطا** | ورودی نامعتبر، داده از دست رفته، مجوز رد شد |
| **شرایط مرزی** | یک به یک؛ دقیقا در محدوده |
### تمسخر و لج کردن
| ترم | توضیحات | زمان استفاده |
|------|-------------|-------------|
| **مسخره** | یک شی جعلی که نحوه نامیدن آن را ثبت می کند | بررسی تعاملات (این روش نام داشت؟) |
| **خرد** | یک شی جعلی که مقادیر از پیش تعیین شده | ارائه داده های آزمایشی (این کاربر را از پایگاه داده برگردانید) |
| **جاسوس** | پوششی که تماس های یک شی واقعی را ضبط می کند | تایید جزئی |
| **جعلی** | اجرای ساده اما کارآمد | پایگاه داده درون حافظه برای تست ها |
| کتابخانه تمسخر آمیز | زبان |
|----------------|--------|
| **unittest.mock** | پایتون |
| **شوخی** | جاوا اسکریپت/تایپ اسکریپت |
| **موکیتو** | جاوا |
| **موق** | سی شارپ |
| **شهادت / گوموک ** | برو |

## تست یکپارچه سازی
آزمایش نحوه کار چندین مؤلفه با هم.
| چه چیزی را تست کنیم | مثال |
|-------------|---------|
| **پرس و جوهای پایگاه داده** | آیا ORM SQL درستی تولید می کند؟ آیا از شاخص ها استفاده می شود؟ |
| **نقاط پایانی API** | آیا چرخه کامل درخواست-پاسخ کار می کند؟ |
| **تعاملات خدماتی** | آیا سرویس A به درستی با سرویس B تماس می گیرد؟ |
| **وابستگی های خارجی** | آیا ادغام درگاه پرداخت کار می کند؟ |
### استراتژی ها
| استراتژی | توضیحات | معامله |
|----------|------------|-----------|
| **وابستگی های واقعی** | استفاده از پایگاه داده واقعی، صف پیام واقعی | واقع بینانه ترین؛ کندتر؛ راه اندازی سخت تر |
| **ظروف تست** | چرخش ظروف Docker برای هر اجرای آزمایشی | تعادل خوب؛ قابل تکرار |
| **جایگزین های درون حافظه** | H2 به جای PostgreSQL. اتوبوس پیام درون حافظه | سریع؛ ممکن است مسائل دنیای واقعی را از دست بدهد |
| **تست قرارداد** | بررسی کنید که سرویس‌ها قراردادهای API خود را رعایت می‌کنند | دریافت تغییرات رابط |

## تست پایان به انتها (E2E).
تست سیستم کامل از دید کاربر.
| ابزار | نوع | بهترین برای |
|------|------|----------|
| **نمایشنامه نویس** | اتوماسیون مرورگر | برنامه های کاربردی وب؛ مرورگر متقابل |
| **سرو** | اتوماسیون مرورگر | برنامه های کاربردی وب؛ تجربه توسعه دهنده |
| **سلنیوم** | اتوماسیون مرورگر | میراث؛ پشتیبانی از زبان گسترده |
| **سم زدایی** | موبایل E2E | React Native apps |
| **اپیوم** | موبایل E2E | برنامه های موبایل بومی و ترکیبی |
| **ماسترو** | موبایل E2E | اپلیکیشن های موبایل؛ نحو ساده YAML |
| **k6 / ملخ** | تست بار | عملکرد تحت بار |
### بهترین شیوه های E2E
| تمرین | چرا |
|----------|-----|
| **فقط مسیرهای بحرانی را آزمایش کنید** | تست های E2E کند هستند. تمرکز بر آنچه که بیشتر اهمیت دارد |
| **استفاده از کارخانه های داده تست** | ایجاد داده های تست به صورت برنامه ریزی شده؛ به داده های بذر تکیه نکنید |
| **پاکسازی بعد از آزمایش** | هر آزمایش باید سیستم را در یک وضعیت شناخته شده رها کند |
| **از آزمایش جزئیات رابط کاربری خودداری کنید** | رفتار تست، نه کلاس های CSS یا موقعیت های عنصر |
| **اجرا در CI** | تست های E2E باید در هر تغییر به صورت خودکار اجرا شوند |

## توسعه تست محور (TDD)
ابتدا تست را بنویسید سپس کد را بنویسید تا موفق شود.
| مرحله | توضیحات |
|------|-------------|
| **1. قرمز** | یک آزمون شکست خورده بنویسید که رفتار مورد نظر را توصیف کند |
| **2. سبز** | حداقل کد را برای قبولی در آزمون بنویسید |
| **3. Refactor** | با سبز نگه داشتن تست ها، کد را پاک کنید |
| سود | توضیحات |
|---------|-------------|
| **بازخورد طراحی** | تست‌ها شما را مجبور می‌کنند قبل از پیاده‌سازی در مورد رابط‌ها فکر کنید |
| **ایمنی رگرسیون** | هر اشکال تست می شود. اشکال هرگز نمی تواند برگردد |
| **مستندات** | آزمون ها به عنوان مستند زنده رفتار مورد انتظار عمل می کنند |
| **اعتماد به نفس** | پوشش تست بالا امکان بازآفرینی بی باک را فراهم می کند |
---

## توسعه رفتار محور (BDD)
BDD با نوشتن تست هایی به زبان طبیعی که رفتار را از دیدگاه کاربر توصیف می کند، TDD را گسترش می دهد.
### با توجه به زمان-پس فرمت
```
Given a user with an empty shopping cart
When they add a "Python Book" priced at $29.99
Then the cart total should be $29.99
And the cart should contain 1 item
```

| ابزار | زبان |
|------|----------|
| **خیار** | جاوا، جاوا اسکریپت، روبی و دیگران |
| **رفتار** | پایتون |
| **SpecFlow** | سی شارپ |
| **شوخی** (با توصیف/آن) | جاوا اسکریپت |
---

## سازمان آزمون
| الگو | توضیحات | زمان استفاده |
|---------|------------|-------------|
| **هم محل** | تست های کنار کدی که آزمایش می کنند (`src/utils.test.ts`) | اکثر پروژه ها؛ پیدا کردن آسان |
| **دایرکتوری جداگانه** | آزمایش در پوشه`tests/`یا`__tests__/`| پروژه های بزرگ؛ جداسازی واضح |
| **لوازم تست ** | داده های آزمایش مشترک در یک فهرست`fixtures/`| وقتی چندین آزمایش به داده های یکسانی نیاز دارند |
| **آزمایش ابزارها** | کمک های مشترک در فهرست`test-utils/`| وقتی منطق راه اندازی پیچیده است |

## پوشش کد
| متریک | آنچه را اندازه گیری می کند | محدودیت |
|--------|----------------|------------|
| **پوشش خط** | درصد خطوط کد اجرا شده توسط تست ها | کیفیت اظهارات را اندازه گیری نمی کند |
| **پوشش شعبه** | درصد شاخه ها (اگر/دیگر) گرفته شده | بهتر از پوشش خط هنوز همه اشکالات را نمی گیرد |
| **پوشش مسیر** | درصد مسیرهای اجرایی طی شده | دقیق ترین؛ نمایی در کد مختلط |
| **امتیاز جهش** | درصد جهش های کشف شده توسط آزمایش | بهترین معیار سنجش کیفیت تست |
**هدف**: پوشش خط 80% یک پیش فرض معقول است. اما پوشش یک راهنما است، نه یک هدف - پوشش 100٪ با ادعاهای ضعیف بدتر از پوشش 70٪ با آزمایش های کامل است.

## یکپارچه سازی و آزمایش مداوم
| تمرین | توضیحات |
|----------|-------------|
| **همه تست های واحد را روی هر commit اجرا کنید** | بازخورد سریع؛ فورا رگرسیون را می گیرد |
| **آزمون های یکپارچه سازی را در روابط عمومی اجرا کنید** | مسائلی را که تست های واحد از دست می دهند را می گیرد |
| **آزمون های E2E را شبانه یا در هنگام ادغام در اصلی اجرا کنید** | آهسته اما کامل |
| **سریع شکست** | توقف خط لوله در اولین شکست برای صرفه جویی در زمان |
| **خط مشی تست فلکی** | فورا تست های پوسته پوسته را قرنطینه یا حذف کنید. هرگز نادیده نگیرید |
| **آزمایش موازی سازی** | برای کاهش زمان CI تست ها را به صورت موازی اجرا کنید |

## نکات کاربردی
- **آزمایش نام واضح است.**`test_calculates_tax_for_high_earner`به شما می گوید چه چیزی خراب شده است. `test_1`چیزی به شما نمی گوید.
- **یک ادعا در هر آزمون (در صورت عملی).** تشخیص شکست را آسان می کند.
- **جزئیات پیاده سازی را آزمایش نکنید.** رفتار تست. اگر قطعات داخلی را بازسازی می کنید، آزمایش ها نباید خراب شوند.
- **از آزمایش کدهای شخص ثالث اجتناب کنید.** کتابخانه های خارجی را مسخره کنید. تعامل کد خود را با آنها تست کنید.
- **تست ها را سریع انجام دهید.** اگر مجموعه آزمایشی شما 10 دقیقه طول بکشد، توسعه دهندگان اجرای آن را متوقف خواهند کرد. بی وقفه بهینه سازی کنید.
- **تست های مرده را حذف کنید.** تست هایی که همیشه قبول می شوند یا کد حذف شده را تست می کنند نویز هستند.
- ** کد آزمایشی را مانند کد تولید در نظر بگیرید. ** باید خوانا، قابل نگهداری و دارای ساختار مناسب باشد.
---

## خلاصه
تست اختیاری نیست - نحوه ساختن نرم افزاری است که خراب نمی شود. هرم تست شما را به سمت بسیاری از تست های واحد سریع، برخی تست های یکپارچه سازی و چند تست E2E راهنمایی می کند. TDD و BDD رویکردهای ساختاری را ارائه می دهند. تمسخر واحدها را برای آزمایش جدا می کند. پوشش کد وسعت را می سنجد اما عمق را نمی سنجد. مهمترین اصل این است: اگر آزمایش نشود، خراب است - شما هنوز آن را نمی دانید.
