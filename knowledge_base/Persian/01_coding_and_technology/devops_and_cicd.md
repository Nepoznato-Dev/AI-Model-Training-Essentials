# DevOps و CI/CD
DevOps ترکیبی از فلسفه فرهنگی، شیوه‌ها و ابزارهایی است که تیم‌ها را قادر می‌سازد نرم‌افزار را سریع‌تر و قابل اطمینان‌تر ارائه دهند. دیوار بین توسعه دهندگان (که می خواهند تغییرات را ارسال کنند) و عملیات (که خواهان ثبات هستند) را می شکند. CI/CD - یکپارچه سازی مداوم و تحویل مداوم - ستون فقرات اتوماسیونی است که این امکان را فراهم می کند.

## خطوط لوله CI/CD
### CI/CD در واقع به چه معناست
| ترم | چه کاری انجام می دهد |
|------|-------------|
| **ادغام پیوسته (CI)** | توسعه دهندگان اغلب کد را ادغام می کنند. هر ادغام ساخت و آزمایش خودکار را آغاز می کند |
| **تحویل مستمر (سی دی)** | کد همیشه در وضعیت قابل استقرار است. انتشار به تولید یک تصمیم دستی است |
| **استقرار مستمر** | هر تغییری که آزمایش را پشت سر می گذارد به طور خودکار به تولید می رود — بدون گیت دستی |
### مراحل معمول خط لوله
| مرحله | چه اتفاقی می افتد | ابزار |
|-------|-------------|-------|
| **منبع** | توسعه دهنده کد را به Git | فشار می دهد GitHub، GitLab، Bitbucket |
| **ساخت ** | کامپایل کد، نصب وابستگی | Maven، Gradle، npm، pip |
| **تست** | اجرای واحد، ادغام، بررسی پرز | Jest، pytest، JUnit |
| **بسته** | ساخت تصویر یا مصنوع Docker | Docker, Buildpacks |
| **استقرار (صحنه سازی)** | استقرار در محیط صحنه سازی | Kubernetes، ECS، VM |
| **تست (مرحله بندی)** | تست های ادغام، تست دود | سلنیوم، پستچی |
| **استقرار (تولید)** | عرضه به تولید | سبز آبی، قناری، نورد |
| **مانیتور** | رعایت بهداشت، خطاها، عملکرد | پرومتئوس، گرافانا، دیتاداگ |
### ابزارهای CI/CD مقایسه شد
| ابزار | نوع | قدرت |
|------|------|----------|
| **اقدامات گیت هاب** | Cloud CI/CD | عمیقا با GitHub یکپارچه شده است. گردش کار YAML |
| **GitLab CI** | CI/CD داخلی | سکوی واحد برای مخزن + خط لوله |
| **جنکینز** | خود میزبانی CI/CD | بسیار قابل تنظیم؛ اکوسیستم پلاگین عظیم |
| **CircleCI** | Cloud CI/CD | سریع؛ خوب برای گردش کار کانتینری |
| **ArgoCD** | GitOps برای Kubernetes | استقرارهای اعلامی، Git محور |

## داکر و کانتینرها
### چرا ظروف؟
قبل از کانتینرها، مشکل کلاسیک این بود که «روی دستگاه من کار می‌کند». کانتینرها این مشکل را با بسته‌بندی یک برنامه با تمام وابستگی‌های آن - کتابخانه‌ها، زمان اجرا، پیکربندی - در یک واحد منفرد و قابل حمل که به طور یکسان در همه جا اجرا می‌شود، حل می‌کنند.
### Docker Essentials
| مفهوم | توضیحات |
|---------|-------------|
| **تصویر** | قالب فقط خواندنی با برنامه + وابستگی |
| **ظرف** | نمونه در حال اجرا یک تصویر |
| **Dockerfile** | دستور ساخت تصویر |
| **رجیستری** | ذخیره سازی برای تصاویر (Docker Hub، ECR، GCR) |
| **حجم** | ذخیره سازی پایدار که در کانتینر باقی می ماند دوباره راه اندازی می شود |
| **شبکه** | لایه شبکه ایزوله برای کانتینرها |
### بهترین روش های Dockerfile
```dockerfile
# Use specific base image tags, not 'latest'
FROM python:3.12-slim

# Set working directory
WORKDIR /app

# Copy dependency file first (leverage Docker layer caching)
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# Copy application code
COPY . .

# Run as non-root user
USER appuser

# Expose port and define entrypoint
EXPOSE 8000
CMD ["python", "main.py"]
```

روش‌های کلیدی: استفاده از تصاویر پایه باریک/آلپی، اجرا به‌عنوان غیر ریشه، ذخیره‌سازی لایه اهرمی، استفاده از `.dockerignore`، اسکن تصاویر برای آسیب‌پذیری‌ها (`trivy`، `docker scan`)، و تعیین محدودیت‌های منابع.
### Docker Compose
برای اجرای چندین کانتینر با هم (برنامه + پایگاه داده + کش):
```yaml
services:
  app:
    build: .
    ports: ["8000:8000"]
    depends_on: [db, redis]
    environment:
      DATABASE_URL: postgresql://user:pass@db:5432/mydb
  db:
    image: postgres:16
    volumes: [pgdata:/var/lib/postgresql/data]
  redis:
    image: redis:7-alpine
volumes:
  pgdata:
```

## Kubernetes (K8s)
Kubernetes ارکستراتور کانتینر استاندارد صنعتی است. این استقرار، مقیاس بندی و عملیات برنامه های کاربردی کانتینری را مدیریت می کند.
### معماری اصلی
| جزء | نقش |
|-----------|------|
| **هواپیمای کنترل** | خوشه را مدیریت می کند (سرور API، زمانبند، etcd، مدیر کنترلر) |
| **گره** | ماشین کارگر (VM یا فیزیکی) که کانتینرها را اجرا می کند |
| **پاد** | کوچکترین واحد قابل استقرار؛ یک یا چند کانتینر که شبکه را به اشتراک می گذارند |
| **سرویس** | نقطه پایانی شبکه پایدار که ترافیک را به پادها هدایت می کند |
| **استقرار** | تعریف اعلامی حالت غلاف مورد نظر (کپی، تصویر و غیره) |
| **ورود** | قوانین مسیریابی HTTP برای ترافیک خارجی |
| **ConfigMap / Secret** | پیکربندی و داده های حساس تزریق شده به غلاف |
### دستورات ضروری kubectl
```bash
kubectl get pods                    # List pods
kubectl get services                # List services
kubectl describe pod <name>         # Detailed pod info
kubectl logs <pod-name>             # View pod logs
kubectl exec -it <pod> -- /bin/sh   # Shell into a pod
kubectl apply -f deployment.yaml    # Apply a manifest
kubectl rollout status deploy/myapp # Check rollout progress
kubectl scale deploy/myapp --replicas=5  # Scale to 5 replicas
```

### هلم
Helm مدیر بسته Kubernetes است. **نمودار** مجموعه ای از منابع Kubernetes از پیش پیکربندی شده است. آن را به عنوان`apt`یا`brew`برای K8s در نظر بگیرید.
```bash
helm install my-release bitnami/postgresql   # Install a chart
helm upgrade my-release bitnami/postgresql   # Upgrade
helm rollback my-release 1                   # Rollback to revision 1
helm list                                    # List releases
```

## زیرساخت به عنوان کد (IaC)
IaC با پیکربندی زیرساخت به همان روشی رفتار می کند که با کد برنامه برخورد می کنید: نسخه کنترل شده، آزمایش شده، و از طریق خطوط لوله مستقر شده است.
### Terraform در مقابل Ansible
| ابزار | نوع | رویکرد | بهترین برای |
|------|------|----------|----------|
| **Terraform** | تامین | اعلامی (HCL)؛ ایالتی | ایجاد منابع ابری (VPC، VM، پایگاه داده) |
| **آنسیبل** | پیکربندی | اعلامی (YAML)؛ بدون نماینده | پیکربندی سرورها، نصب نرم افزار |
| **پولومی** | تامین | امری (Python، Go، TS) | تیم هایی که زبان های برنامه نویسی واقعی را ترجیح می دهند |
| **CloudFormation** | تامین | اعلامی (YAML/JSON)؛ AWS-native | زیرساخت فقط AWS |
### مثال Terraform
```hcl
provider "aws" {
  region = "us-east-1"
}

resource "aws_instance" "web" {
  ami           = "ami-0c55b159cbfafe1f0"
  instance_type = "t3.micro"

  tags = {
    Name = "web-server"
  }
}
```

بهترین روش‌ها: از ماژول‌ها برای استفاده مجدد استفاده کنید، وضعیت را از راه دور ذخیره کنید (S3 + DynamoDB برای قفل کردن)، هرگز اسرار کد سخت را ندهید، و همه چیز را با نسخه کنترل کنید.

## نظارت و قابلیت مشاهده
### سه ستون
| ستون | آنچه به شما می گوید | ابزار |
|--------|-----------------|-------|
| **متریک** | اندازه گیری عددی در طول زمان (CPU، نرخ درخواست، نرخ خطا) | Prometheus، CloudWatch، Datadog |
| **لاگ** | رویدادهای گسسته با زمینه (خطاها، درخواست ها، تغییرات حالت) | ELK Stack، Loki، CloudWatch Logs |
| **ردیابی** | سفر درخواست پایان به انتها در بین خدمات | جیگر، ایکس ری، زیپکین |
### Prometheus + Grafana Stack
پشته مانیتورینگ منبع باز استاندارد:
| جزء | نقش |
|-----------|------|
| **پرومته** | پایگاه داده سری زمانی؛ معیارها را از خدمات استخراج می کند |
| **گرافانا** | تجسم و داشبورد |
| **Alertmanager** | مسیرهای هشدار به Slack، PagerDuty، ایمیل |
| **صادر کننده گره** | معیارهای سطح سیستم (CPU، RAM، دیسک) |
| **صادر کننده بلک باکس** | نقاط پایانی کاوشگر (HTTP، TCP، ICMP) |
### معیارهای کلیدی برای ردیابی
| دسته بندی | متریک |
|----------|---------|
| **زیرساخت** | CPU، RAM، استفاده از دیسک، شبکه I/O |
| **برنامه** | نرخ درخواست، تأخیر (p50، p95، p99)، میزان خطا |
| **پایگاه اطلاعاتی** | تعداد پرس و جو، پرس و جوهای کند، استفاده از استخر اتصال |
| **کسب و کار** | ثبت نام، تبدیل، درآمد |

## GitOps
GitOps IaC را به نتیجه منطقی خود می برد: مخزن Git تنها منبع حقیقت برای وضعیت مطلوب زیرساخت و برنامه های شما است.
| اصل | توضیحات |
|-----------|-------------|
| **اعلامی** | همه چیز به عنوان کد (YAML، HCL) |
| **نسخه شده** | گیت منبع حقیقت است |
| **اتوماتیک** | ابزارها به طور مداوم حالت مورد نظر را با وضعیت واقعی تطبیق می دهند
| **قابل کنترل** | هر تغییر یک تعهد Git است |
**ArgoCD** و **Flux** ابزارهای پیشرو GitOps برای Kubernetes هستند. شما یک تغییر را به مخزن Git خود فشار می دهید و ابزار به طور خودکار آن را در خوشه مستقر می کند.

## واکنش به حادثه
وقتی چیزی در ساعت 3 صبح خراب می شود:
1. **تصدیق** هشدار.
2. **ارزیابی دامنه**: کدام سرویس ها، کاربران و داده ها تحت تأثیر قرار می گیرند؟
3. **شناسایی ** علت اصلی - بررسی سیاهههای مربوط، معیارها، استقرار اخیر.
4. در صورت امکان ** شامل ** - قطع کننده های مدار، پرچم های ویژگی، تغییر ترافیک.
5. **رفع ** - عقبگرد یا وصله به جلو.
6. **ارتباط ** - به روز رسانی سهامداران و کاربران (صفحه وضعیت).
7. **پس از مرگ** - ظرف 24 تا 48 ساعت، علت اصلی و موارد اقدام را مستند کنید.
هدف نه تنها حل و فصل حادثه است، بلکه اطمینان از عدم تکرار همان حادثه است.
